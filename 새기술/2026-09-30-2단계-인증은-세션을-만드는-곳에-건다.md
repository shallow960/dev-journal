# 2026-09-30 2단계 인증은, 로그인 화면이 아니라 세션을 만드는 곳에 건다

> 태그: #새기술 #보안 #TOTP #2단계인증 #SpringBoot

## 무엇을 / 왜

관리자 화면 보안 설정에 "2단계 인증 관리" 버튼이 있었는데, 눌러도 아무 일이 없었습니다. 이 계정은 결제, 서비스 해지, 고객 개인정보까지 다루는데 비밀번호만 새면 그대로 들어올 수 있었어요.

모든 관리자에게 강제하면 부담이 크다는 의견이 있어서, **원하는 사람만 켜는 선택 기능**으로 만들기로 했습니다. 방식은 휴대폰 인증 앱(Google Authenticator 등)에 뜨는 6자리, TOTP입니다.

막상 만들려고 보니 더 큰 질문은 "어디서 막느냐" 였습니다. 로그인 방법이 여러 개였거든요.

```
이메일 + 비밀번호
소셜 로그인(카카오 · 네이버 · 구글)
소셜 가입 도중 본인확인으로 기존 계정에 이어지는 경로
```

## 어떻게 풀었나

### TOTP는 서버와 앱이 같은 계산을 한다

TOTP(RFC 6238)는 서버와 앱이 **같은 비밀키**를 나눠 갖고, **30초 단위 시각**을 넣어 HMAC-SHA1을 계산한 뒤 6자리로 줄입니다. 네트워크 없이도 양쪽이 같은 숫자를 얻어요. 휴대폰 시계가 조금 틀려도 되도록 앞뒤 한 구간(±30초)까지 맞는 것으로 봤습니다.

등록은 이렇게 했습니다.

1. 서버가 비밀키를 만들고, 암호화(AES-GCM)해 저장합니다. 아직 "꺼짐" 상태입니다.
2. `otpauth://totp/...` 주소를 돌려주면 화면이 QR로 그립니다(브라우저에서 `qrcode` 라이브러리 사용).
3. 앱에 새로 뜬 6자리를 한 번 맞혀야 **그때 켜집니다.** 등록을 잘못한 채로 켜지면 본인이 잠기니까요.
4. 켜는 순간 1회용 복구 코드 10개를 **한 번만** 보여 주고, 서버에는 해시만 남깁니다.

### 입구마다가 아니라, 모든 입구가 지나는 한 곳에서

로그인 화면마다 확인을 넣으면, 나중에 로그인 방법이 하나 늘 때 거기서 빠질 수 있습니다. 코드를 보니 모든 경로가 **마지막에 세션(토큰)을 만드는 한 함수**를 지나고 있었어요. 그래서 거기에 걸었습니다.

```
이메일 로그인 ------------+
소셜 로그인 --------------+--> 세션 발급 --> 2단계 인증 켜짐?
가입 중 기존 계정 연결 ---+                   |- 아니오 --> 토큰 발급
                                              |- 예 ------> 5분짜리 확인표만
                                                             |
                                    6자리(또는 복구 코드) 확인 --> 토큰 발급
```

켠 계정이면 토큰도 계정 정보도 주지 않고 **확인표(challenge)** 만 줍니다. 확인표는 랜덤 문자열이고, 서버(Redis)에는 해시만 5분 동안 둡니다. 6자리가 맞으면 확인표를 지우고 그때 토큰을 발급해서, 같은 확인표로는 다시 들어올 수 없어요.

### 짧은 비밀에는 시도 제한을 붙인다

6자리는 경우의 수가 백만 가지뿐입니다. 제한이 없으면 맞을 때까지 넣어 볼 수 있어서, 틀린 입력은 계정마다 **10분에 5번**까지만 받았습니다. 끄기와 복구 코드 다시 받기도 지금 코드를 한 번 더 확인합니다. 로그인된 화면만 훔쳐 써서 끄지 못하게요.

### 복구 코드는 "한 번만" 을 DB에 맡긴다

복구 코드를 쓸 때 "있는지 확인 → 사용 표시" 로 나누면, 같은 코드를 동시에 두 번 넣었을 때 둘 다 통과할 수 있습니다. **조건부 update 한 번**으로 처리하고 바뀐 행 수로 판단했습니다.

### 암호화 코드가 있어도, 키가 없으면 소용없다

비밀키 암호화 코드는 이미 있었는데, 키 환경 변수가 없으면 개발용으로 **base64로만 저장**하게 돼 있었습니다. 운영 서버를 확인해 보니 키가 없었어요. 기능을 배포하기 전에 키부터 만들어 넣었습니다(값은 서버에서 바로 생성해 화면에 찍히지 않게 하고, 컨테이너 안에서 길이만 확인).

## 코드로 보기 (개념 재현)

```java
/** 모든 로그인 경로가 마지막에 부르는 곳. 여기서 한 번만 막는다. */
LoginResult issue(Account account) {
    if (twoFactor.isEnabled(account.id())) {
        // 토큰도 계정 정보도 주지 않는다. 5분짜리 확인표만
        return LoginResult.challenge(twoFactor.createChallenge(account.id()));
    }
    return LoginResult.session(tokens.issue(account));
}

/** 두 번째 단계. 확인표 + 6자리(또는 복구 코드). */
LoginResult completeTwoFactor(String challenge, String code) {
    UUID accountId = twoFactor.completeChallenge(challenge, code); // 틀리면 401, 확인표는 1회용
    return LoginResult.session(tokens.issue(accounts.get(accountId)));
}
```

```java
String createChallenge(UUID accountId) {
    String token = randomToken();
    // 원문은 응답으로만 나가고, 서버에는 해시만 5분
    redis.opsForValue().set("2fa-challenge:" + sha256(token), accountId.toString(), Duration.ofMinutes(5));
    return token;
}

UUID completeChallenge(String challenge, String code) {
    String key = "2fa-challenge:" + sha256(challenge);
    String accountId = redis.opsForValue().get(key);
    if (accountId == null) throw expired();          // 없거나 5분 지남
    UUID id = UUID.fromString(accountId);
    verifyOrThrow(id, code);                          // 시도 제한 + TOTP 또는 복구 코드
    redis.delete(key);                                // 성공하면 바로 지운다(재사용 불가)
    return id;
}
```

```java
/** 맞는 복구 코드면 "사용함" 으로 바꾼다. 동시에 두 번 넣어도 한 번만 성공 */
boolean useRecoveryCode(UUID accountId, String input) {
    String normalized = input.replaceAll("[\\s-]", "").toUpperCase(Locale.ROOT); // XXXX-XXXX 허용
    return jdbc.sql("""
            update recovery_codes set used_at = now()
             where account_id = :id and code_hash = :hash and used_at is null
            """)
        .param("id", accountId)
        .param("hash", sha256(normalized))
        .update() == 1;                               // 1행이 바뀌었으면 맞는 코드
}
```

## 💡 배운 것

**보안 확인은 입구마다가 아니라, 모든 입구가 지나는 한 곳에 둡니다.** 입구는 앞으로도 늘어납니다. 마지막에 반드시 지나는 곳을 찾으면 새 로그인 방법이 생겨도 따로 신경 쓸 필요가 없었습니다.

**짧은 비밀은 시도 제한과 짝입니다.** 6자리 자체보다, 몇 번까지 틀릴 수 있느냐가 실제 안전을 정합니다.

**"한 번만" 은 조건부 update로 원자적으로 처리합니다.** 확인과 표시를 나누지 않고, 바뀐 행 수로 판단하면 동시 요청에도 한 번만 성공합니다.

**암호화하는 코드가 있다고 암호화되는 건 아닙니다.** 키가 없을 때 조용히 대체 동작을 하는 코드는, 운영 설정까지 확인해야 실제로 안전한지 알 수 있었습니다.

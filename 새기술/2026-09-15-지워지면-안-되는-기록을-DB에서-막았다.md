# 2026-09-15 지워지면 안 되는 기록을, DB에서 막았다

> 태그: #새기술 #PostgreSQL #트리거 #감사로그

## 무엇을 / 왜

"누가 언제 무엇을 했는가" 를 남기는 기록이 네 종류 있습니다. 관리 화면의 작업 기록, 로그인 기록, 관리자 작업 기록, 내부 운영자 작업 기록.

이 기록의 쓸모는 하나입니다. **나중에 문제가 생겼을 때 증거가 되는 것.** 그런데 증거는 "고칠 수 없어야" 증거입니다.

화면과 API에는 삭제 기능이 없었습니다. 코드 어디에도 이 표를 수정하거나 지우는 문장이 없었고요. 하지만 **데이터베이스에 붙을 수 있는 사람은 얼마든지 지울 수 있는 상태**였습니다. "기능이 없다" 와 "할 수 없다" 는 다릅니다.

## 어떻게 풀었나

### 행 단위 트리거로 거절한다

수정·삭제가 일어나기 **전에** 가로채서 예외를 던지는 트리거를 붙였습니다.

```sql
create or replace function 감사기록_변경금지() returns trigger
    language plpgsql
as $$
begin
    raise exception '감사 기록은 추가만 가능합니다: %s 에 대한 %s 는 허용되지 않습니다', tg_table_name, tg_op
        using errcode = 'insufficient_privilege';
end;
$$;

create trigger 작업기록_추가전용
    before update or delete on 작업기록
    for each row execute function 감사기록_변경금지();
```

앱이 하는 저장은 전부 INSERT 라서(중복은 무시) 영향이 없습니다.

### 그런데 사용자를 지울 수 없게 됐다

트리거를 붙이고 시험을 돌렸더니 **엉뚱한 곳이 깨졌습니다.** 사용자를 지우는 시험이 실패했어요.

감사 기록은 사용자를 참조합니다. 참조 설정이 "사용자가 지워지면 이 칸을 비운다" 였습니다. 즉 사용자 삭제는 내부적으로 **감사 기록에 UPDATE 를 일으킵니다.** 제 트리거가 그걸 막으니 **사용자 삭제 자체가 실패**했습니다.

감사 기록을 지키려다 정상 기능을 막은 셈입니다.

### 연쇄 동작만 통과시킨다

직접 고치는 것과, 참조 대상이 사라져서 따라 바뀌는 것을 구분해야 했습니다. PostgreSQL 에서는 외래키 연쇄 동작도 내부적으로 트리거로 실행되기 때문에, **지금 트리거가 몇 겹째인지**로 구분할 수 있었습니다.

```sql
create or replace function 감사기록_변경금지() returns trigger
    language plpgsql
as $$
begin
    -- 다른 트리거 안에서 실행됐다면 외래키 연쇄 동작이다(사용자·가게 삭제에 따른 정리).
    -- 막으면 삭제 자체가 실패하므로 통과시킨다. 직접 실행한 문장은 1 이다.
    if pg_trigger_depth() > 1 then
        if tg_op = 'DELETE' then return old; end if;
        return new;
    end if;

    raise exception '감사 기록은 추가만 가능합니다: %s 에 대한 %s 는 허용되지 않습니다', tg_table_name, tg_op
        using errcode = 'insufficient_privilege';
end;
$$;
```

### 보존기간 정리는 어떻게 하나

법정 보존기간이 지나면 언젠가는 지워야 합니다. 그때 이 트리거가 걸립니다.

**그건 그대로 두기로 했습니다.** 정리해야 할 때가 오면 트리거를 끄는 마이그레이션을 따로 만들어 지우고 다시 켭니다. 번거롭지만, 그게 목적입니다. **조용히 지울 수 있는 경로를 남기지 않는 것.** 주석에도 그렇게 적어 뒀습니다.

## 코드로 보기 (개념 재현)

앱이 쓰는 계정으로 직접 시도해 봐야 의미가 있습니다.

```java
@Test
void 운영자_작업_기록은_고치거나_지울_수_없다() {
    var id = 기록심기("작업기록", 사유: "기록 보호 확인");

    assertThatThrownBy(() -> sql("update 작업기록 set 사유 = '고친 사유' where id = :id").param("id", id).update())
        .hasStackTraceContaining("추가만 가능");
    assertThatThrownBy(() -> sql("delete from 작업기록 where id = :id").param("id", id).update())
        .hasStackTraceContaining("추가만 가능");

    assertThat(사유조회(id)).isEqualTo("기록 보호 확인");   // 원본 그대로
}
```

## 💡 배운 것

**"기능이 없다" 는 "할 수 없다" 가 아닙니다.** 화면에 삭제 버튼이 없는 것과, 데이터베이스에서 지울 수 없는 것은 전혀 다른 수준입니다. 증거로 쓸 기록이라면 후자가 필요합니다.

**제약을 걸면 정상 경로도 함께 막힙니다.** 막고 싶은 건 "사람이 기록을 고치는 것" 이었는데, 실제로 막힌 건 "사용자 삭제" 였습니다. 예외를 좁게 뚫어야 합니다.

**`pg_trigger_depth()` 로 "직접 실행" 과 "연쇄 실행" 을 구분할 수 있습니다.** 외래키 연쇄 동작도 트리거로 돌기 때문에 깊이가 2 이상입니다. 이번에 처음 써 봤습니다.

**불편하게 남겨 두는 게 목적일 때가 있습니다.** 보존기간 정리를 자동화해 두면 그 경로로 언제든 지울 수 있게 됩니다. 매번 마이그레이션을 쓰게 두면 기록이 남습니다.

**한계도 같이 적어야 합니다.** 데이터베이스 최고 권한이 있으면 트리거를 끌 수 있습니다. 이건 계정 권한 분리나 외부 보관으로 풀어야 하는 별도 문제라, 문서에 그대로 적었습니다.

## 소감

시험을 돌렸다가 엉뚱한 곳이 깨진 게 오히려 다행이었습니다. 배포하고 나서 "사용자 삭제가 안 된다" 는 문의를 받았다면 원인을 찾는 데 한참 걸렸을 겁니다. 감사 기록 트리거와 사용자 삭제는 머릿속에서 전혀 연결되지 않는 두 가지니까요.

덤으로, 그 시험을 파다가 예전부터 있던 스키마 문제도 하나 발견했습니다. 로그인 기록이 사용자를 두 칸으로 참조하는데 "지워지면 비운다" 가 설정돼 있고, 그중 한 칸은 비울 수 없는 칸이었습니다. 로그인 기록이 있는 사용자는 원래부터 하드 삭제가 불가능했던 셈입니다. 지금은 탈퇴를 익명화로 처리해서 문제가 되지 않지만, 확인해서 적어 뒀습니다.

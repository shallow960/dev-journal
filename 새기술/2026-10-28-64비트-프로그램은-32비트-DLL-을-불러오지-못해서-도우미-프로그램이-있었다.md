# 2026-10-28 64비트 프로그램은 32비트 DLL 을 불러오지 못해서, 도우미 프로그램이 있었다

> 태그: #새기술 #윈도우 #DLL #32비트 #64비트 #결제

## 무엇을 / 왜
시험 키오스크에서 카드 결제가 되지 않아 로그를 따라가 보니, 결제는 '32비트 도우미 프로그램'을 거치게 되어 있었는데 그 도우미가 설치본에 들어 있지 않았습니다.

예전 앱을 찾아보니 구조가 이랬습니다.
- 카드 단말기 회사가 준 결제 모듈(DLL)은 32비트였고, 앱 본체는 64비트였습니다.
- 그래서 본체가 32비트 도우미 프로그램을 따로 띄우고, 도우미 안에서 결제 모듈을 불러 본체와 메시지를 주고받았습니다.
- 찾아보니 한 프로그램 안에는 자기와 같은 비트의 DLL 만 불러올 수 있다는 걸 알게 됐습니다. 도우미 프로그램은 바로 이 때문에 있었던 것이었습니다.

## 어떻게 풀었나
- 도우미를 새로 만드는 방법과, 단말기 회사가 낸 64비트 결제 모듈로 바로 연결하는 방법을 비교했습니다. 매장에서 준비할 것(결제 프로그램, 단말기 포트, 단말기 번호)은 두 방법이 같았습니다.
- 바로 연결하면 프로그램 하나와 메시지 주고받기가 줄어서, 64비트 모듈로 바로 연결하기로 했습니다. 단말기와 주고받는 전문은 예전 앱과 한 글자도 다르지 않게 맞췄습니다.
- 비트가 다른 DLL 을 부르면 정말 실패하는지, 윈도우에 들어 있는 같은 이름의 32비트·64비트 DLL 로 직접 확인해 봤습니다.

## 코드로 보기 (개념 재현)
64비트 PowerShell 에서 32비트·64비트 DLL 을 차례로 불러 봤습니다.

```powershell
# 64비트 PowerShell 에서 실행: 같은 이름의 32비트·64비트 DLL 을 차례로 불러 본다
[Console]::OutputEncoding = [Text.Encoding]::UTF8
"64비트 프로그램: " + [Environment]::Is64BitProcess
foreach ($dll in 'C:\Windows\SysWOW64\version.dll',   # 32비트 DLL
                 'C:\Windows\System32\version.dll') {  # 64비트 DLL
  try {
    [void][System.Runtime.InteropServices.NativeLibrary]::Load($dll)
    "불러옴: $dll"
  } catch {
    $e = $_.Exception; while ($e.InnerException) { $e = $e.InnerException }  # 감싼 예외를 벗긴다
    "실패:  $dll -> " + $e.GetType().Name + (' (0x{0:X8})' -f $e.HResult)
  }
}
```

실행 결과입니다.

```
64비트 프로그램: True
실패:  C:\Windows\SysWOW64\version.dll -> BadImageFormatException (0x8007000B)
불러옴: C:\Windows\System32\version.dll
```

반대로 32비트 Windows PowerShell 에서 불러 봤습니다.

```powershell
# 32비트 Windows PowerShell(SysWOW64 쪽)에서 실행: 윈도우 LoadLibrary 로 직접 불러 본다
[Console]::OutputEncoding = [Text.Encoding]::UTF8
Add-Type -Name Native -Namespace Demo -MemberDefinition '[DllImport("kernel32", SetLastError = true, CharSet = CharSet.Unicode)] public static extern IntPtr LoadLibrary(string path);'
"64비트 프로그램: " + [Environment]::Is64BitProcess
foreach ($dll in 'C:\Windows\SysWOW64\version.dll',    # 32비트 DLL
                 'C:\Windows\Sysnative\version.dll') {  # 64비트 DLL (32비트 프로그램에서 System32 를 쓰면 SysWOW64 로 바뀐다)
  $handle = [Demo.Native]::LoadLibrary($dll)
  if ($handle -ne [IntPtr]::Zero) { "불러옴: $dll" }
  else { "실패:  $dll -> 윈도우 오류 " + [Runtime.InteropServices.Marshal]::GetLastWin32Error() }
}
```

실행 결과입니다.

```
64비트 프로그램: False
불러옴: C:\Windows\SysWOW64\version.dll
실패:  C:\Windows\Sysnative\version.dll -> 윈도우 오류 193
```

64비트 프로그램은 32비트 DLL 에서, 32비트 프로그램은 64비트 DLL 에서 실패했습니다. 같은 비트끼리만 불러와졌습니다.

## 💡 배운 것
- 한 프로그램 안에는 같은 비트의 DLL 만 들어올 수 있다는 걸 배웠습니다. 64비트 프로그램은 32비트 DLL 에서 '잘못된 형식' 오류(0x8007000B)가 났고, 32비트 프로그램은 64비트 DLL 에서 윈도우 오류 193 이 났습니다.
- 그래서 비트가 다른 모듈을 써야 하면 그 비트의 도우미 프로그램을 따로 띄워 메시지로 주고받아야 했고, 같은 비트의 모듈이 있으면 도우미 없이 바로 부를 수 있었습니다.
- 32비트 프로그램에서 System32 경로를 열면 윈도우가 SysWOW64 쪽 파일을 보여 준다는 것도 이번에 확인했습니다. 그래서 32비트 프로그램이 64비트 DLL 을 일부러 가리키려면 Sysnative 경로를 써야 했습니다.

## 소감
도우미 프로그램이 왜 필요한지부터 따라가 보니, 예전 앱이 왜 그렇게 만들어졌는지가 이해됐습니다. 구조를 그대로 옮기기 전에 그 구조가 왜 있었는지부터 보는 게 중요하다고 느꼈습니다.

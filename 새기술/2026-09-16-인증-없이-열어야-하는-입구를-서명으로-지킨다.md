# 2026-09-16 인증 없이 열어야 하는 입구를, 서명으로 지킨다

> 태그: #새기술 #보안 #웹훅 #메일

## 무엇을 / 왜

메일 발송을 붙이면서 알게 된 사실이 있습니다. 메일 발송 서비스는 **반송률이 기준을 넘으면 계정 전체의 발송을 정지** 시킵니다. 없는 주소로 계속 보내는 것이 가장 흔한 원인입니다.

우리는 반송을 알아도 그 주소를 계속 발송 대상에 두고 있었습니다. 한 번 정지되면 광고성 메일만 막히는 게 아니라 **비밀번호 재설정 메일까지 같이 죽습니다.**

그래서 발송 서비스가 알려 주는 반송·스팸 신고를 받아 그 주소를 제외하기로 했습니다. 문제는 받는 방법입니다. 발송 서비스는 우리 서비스의 로그인 토큰을 들고 올 수 없으니, 이 수신 주소는 **인증 없이 열려 있어야** 합니다.

그리고 여기가 위험합니다. 아무나 이런 요청을 보낼 수 있다면,

```
{"종류":"반송","주소":"피해자@example.com"}
```

이 한 줄로 **남의 메일 수신을 막을 수** 있습니다. 비밀번호 재설정 메일이 안 가면 그 계정은 사실상 잠깁니다.

## 어떻게 풀었나

### 신뢰의 근거를 "서명" 으로 옮긴다

로그인으로 신원을 확인할 수 없으니, **메시지 자체가 진짜인지** 를 봅니다. 알림 서비스는 메시지에 서명을 붙여 보내고, 그 서명을 확인할 공개키는 인증서 주소로 알려 줍니다.

확인 절차는 세 단계입니다.

1. 정해진 항목을 **정해진 순서로 이어 붙여 원문** 을 만든다
2. 인증서에서 공개키를 꺼낸다
3. 원문과 서명이 공개키로 맞는지 검증한다

원문에 들어가는 항목과 순서는 서비스가 정해 둔 규칙입니다. 하나라도 빠지거나 순서가 다르면 검증은 실패합니다.

### 인증서 주소부터 검사한다 (여기가 핵심)

인증서 주소는 **요청 본문에 들어 있습니다.** 그대로 믿고 내려받으면, 공격자가 자기 인증서를 가리키고 자기 키로 서명한 메시지를 통과시킬 수 있습니다. 서명을 검증하는데도 아무 의미가 없어지는 거죠.

그래서 **주소가 그 서비스의 것인지부터** 확인합니다. 흔한 실수는 문자열 포함 검사입니다.

```
"sns.서비스.com" 이 들어 있으면 통과   →  sns.서비스.com.공격자.com 도 통과된다
```

호스트를 꺼내서 **정확히 일치하는 형태인지** 봐야 합니다.

### 일시 실패와 영구 실패를 가른다

반송에는 두 종류가 있습니다.

- **영구** : 없는 주소, 수신 거부 서버 → 다시 보내면 안 된다
- **일시** : 수신함이 꽉 참, 서버가 잠깐 안 받음 → 나중에는 받을 수 있다

일시 실패까지 막으면 멀쩡한 손님이 메일을 영영 못 받습니다. 영구 실패와 스팸 신고만 제외 목록에 넣고, 잘못 막힌 주소는 풀 수 있게 했습니다.

### 막힌 주소는 보내기 직전에 거른다

목록에 남기기만 하고 발송 직전에 확인하지 않으면 아무 소용이 없습니다. 실제로 메일을 만드는 두 경로 모두에서 확인하게 했고, 결과는 **실패가 아니라 "보내지 않음"** 으로 기록합니다. 실패로 두면 재시도가 붙어서 같은 주소로 계속 보내게 되니까요.

/** 서명 원문 - 정해진 항목을 정해진 순서로 "이름\n값\n" 으로 이어 붙인다. */
static String 서명원문(JsonNode 메시지) {
    List<String> 항목 = switch (메시지.get("Type").asText()) {
        case "Notification" -> List.of("Message", "MessageId", "Subject", "Timestamp", "TopicArn", "Type");
        case "SubscriptionConfirmation" ->
            List.of("Message", "MessageId", "SubscribeURL", "Timestamp", "Token", "TopicArn", "Type");
        default -> null;
    };
    if (항목 == null) return null;

    StringBuilder 원문 = new StringBuilder();
    for (String 이름 : 항목) {
        String 값 = 값꺼내기(메시지, 이름);
        if (값 == null) {
            if ("Subject".equals(이름)) continue;   // 이건 없을 수 있다
            return null;                            // 나머지가 비면 원문을 만들 수 없다
        }
        원문.append(이름).append('\n').append(값).append('\n');
    }
    return 원문.toString();
}
```

/**
 * 인증서 주소 검사. 이 검사가 없으면 서명 검증 전체가 무의미해진다
 * (주소가 요청 본문에서 오므로 공격자가 자기 인증서를 가리킬 수 있다).
 */
private static final Pattern 허용호스트 = Pattern.compile("^sns\\.[a-z0-9-]+\\.발송서비스\\.com$");

static boolean 서비스주소인가(String 주소) {
    URI uri = URI.create(주소);
    return "https".equalsIgnoreCase(uri.getScheme())
        && uri.getHost() != null
        && 허용호스트.matcher(uri.getHost().toLowerCase()).matches();   // 포함이 아니라 완전 일치
}
```

public boolean 검증(JsonNode 메시지) {
    try {
        String 인증서주소 = 값꺼내기(메시지, "SigningCertURL");
        if (인증서주소 == null || !서비스주소인가(인증서주소)) return false;

        String 원문 = 서명원문(메시지);
        if (원문 == null) return false;

        // 서명 방식은 메시지가 알려 준다(1 = SHA1, 2 = SHA256).
        String 방식 = "2".equals(값꺼내기(메시지, "SignatureVersion")) ? "SHA256withRSA" : "SHA1withRSA";

        Signature 검증기 = Signature.getInstance(방식);
        검증기.initVerify(공개키_가져오기(인증서주소));
        검증기.update(원문.getBytes(UTF_8));
        return 검증기.verify(Base64.getDecoder().decode(값꺼내기(메시지, "Signature")));
    } catch (Exception e) {
        return false;   // 확인할 수 없으면 받지 않는다
    }
}

검증은 "맞는 서명이 통과한다" 보다 **"틀린 것이 막힌다"** 를 더 많이 봅니다.

void 본문을_한_글자라도_바꾸면_막힌다() {
    String 본문 = 서명된_알림("반송@example.com", 개인키)
        .replace("반송@example.com", "피해자@example.com");

    assertThat(검증기.검증(읽기(본문))).isFalse();
}

@Test
void 인증서_주소가_서비스_것이_아니면_받지_않는다() {
    assertThat(서비스주소인가("https://sns.리전.발송서비스.com/인증서.pem")).isTrue();
    assertThat(서비스주소인가("https://공격자.com/인증서.pem")).isFalse();
    assertThat(서비스주소인가("https://sns.리전.발송서비스.com.공격자.com/인증서.pem")).isFalse();

## 💡 배운 것

**인증 없이 열어야 하는 입구가 있으면, 신뢰의 근거를 다른 데서 가져와야 합니다.** 여기서는 서명이었습니다. "로그인 못 하니 어쩔 수 없다" 가 아니라 "무엇으로 진짜임을 확인할까" 로 질문을 바꾸는 게 시작이었습니다.

**신뢰 근거의 출처까지 검사해야 합니다.** 서명을 검증해도 그 검증에 쓰는 공개키를 공격자가 정할 수 있으면 아무 의미가 없습니다. 이번 구현에서 제일 중요한 열 줄이 인증서 주소 검사였습니다.

**문자열 포함 검사는 도메인 검사에 쓰면 안 됩니다.** 뒤에 아무 도메인이나 붙여 통과시킬 수 있습니다. 호스트를 꺼내서 완전 일치로 봐야 합니다.

**외부 서비스의 정지 조건을 먼저 읽습니다.** "반송률이 넘으면 계정 전체 정지" 라는 조건을 몰랐다면, 반송 처리는 한참 뒤에나 손댔을 겁니다. 연동할 때 요금표보다 먼저 볼 것은 **어떻게 하면 막히는가** 입니다.

**영구 실패와 일시 실패를 갈라야 합니다.** 둘을 같이 막으면 멀쩡한 사용자가 조용히 잘립니다.

**막을 때는 푸는 길도 같이 만듭니다.** 판정이 틀릴 수 있으니, 제외 목록에서 빼는 기능을 함께 뒀습니다.

## 소감

만들면서 제일 오래 고민한 건 암호 알고리즘이 아니라 **"이 입구로 들어올 수 있는 가장 나쁜 요청이 뭘까"** 였습니다. 답이 "남의 계정을 잠글 수 있다" 로 나오니 무엇을 검사해야 하는지가 분명해졌습니다.

그리고 만들어 놓고 시험을 돌리다가, 이 수신 주소가 **가게 판별 대상에 들어 있어서** 운영이었다면 요청이 거절됐을 상황을 발견했습니다. 중앙 주소로 들어오는 요청은 특정 가게에 속하지 않는다는 걸 빠뜨린 거죠. 보안을 신경 쓴 코드도 배선을 틀리면 그냥 안 도는 코드가 된다는 걸 같이 배웠습니다.

# 2026-10-19 컨테이너의 1번 프로세스는, 종료 신호를 흘려보낼 수 있다

> 태그: #새기술 #Docker #리눅스신호 #PID1 #busybox

## 무엇을 / 왜

메시지 브로커 설정을 실제로 바꾸기 전에, 새 설정을 1회용 컨테이너에 넣고 2초 동안 띄워 봅니다. 설정을 제대로 읽으면 2초 뒤 종료 신호(TERM)를 받고 정상 종료하고, 못 읽으면 바로 오류로 끝나요. 이 종료 코드로 "읽힌다 / 안 읽힌다" 를 판정합니다.

```bash
docker run --rm image sh -c 'timeout -s TERM 2 broker -c /check.conf'
```

재검토에서, 이 모양이면 브로커가 **컨테이너의 1번 프로세스(PID 1)** 가 된다는 지적이 나왔어요. 리눅스에서 PID 1 은 특별합니다. 스스로 처리기를 달지 않은 신호는 **기본 동작(종료)이 적용되지 않고 그냥 무시**돼요. 브로커가 시작 직후 TERM 처리기를 달기 전에 TERM 이 오면, 신호는 사라지고 브로커는 계속 돕니다. 컨테이너가 끝나지 않으니 판정을 기다리던 스크립트도 작업 잠금을 쥔 채 서비스 시간 제한(20분)까지 멈춰요.

왜 브로커가 PID 1 이 되는지, 가벼운 리눅스 이미지(busybox 셸과 도구)에서 하나씩 찍어 봤습니다.

- `sh -c '명령 하나'` 는 셸이 그 명령으로 **자기 자신을 바꿔치기(exec)** 합니다. 셸이 사라지고 명령이 PID 1 이 돼요.
- busybox 의 `timeout` 은 자기 자리(같은 PID)에서 프로그램을 실행하고, 시간 재기는 자식 프로세스에게 맡깁니다. 그래서 `timeout` 을 거쳐도 프로그램이 PID 1 이에요.
- 덤으로, busybox `timeout` 은 시간이 다 돼서 끝내도 **124 를 돌려주지 않고** 프로그램의 종료 코드(TERM 이면 143)를 그대로 돌려줬습니다. GNU 판 습관대로 "124 면 시간 초과" 로 판정했다면 틀렸을 거예요.

## 어떻게 풀었나

1. **명령 끝에 `; exit $?` 를 붙였습니다.** 뒤에 할 일이 남아 있으면 셸이 바꿔치기를 못 하니, **셸이 PID 1 로 남고** 브로커는 그 자식이 됩니다. 자식 프로세스에게 온 TERM 은 기본 동작대로 프로세스를 끝내요.
2. **`timeout -k 2` 를 더했습니다.** TERM 을 보내고 2초가 지나도 안 끝나면 KILL 을 보내요.
3. **컨테이너 밖에서도 기다리는 시간에 상한(60초)을 두고, 컨테이너에 이름과 라벨을 붙였습니다.** 상한에 걸리면 이름으로 지우고, 그래도 남은 건 다음 실행이 라벨로 찾아서 지워요.
4. **판정 규칙은 그대로 두되, 컨테이너 쪽 실패(124 이상)는 "판정 못 함" 으로 따로 처리했습니다.** 설정 문제와 컨테이너 문제를 섞지 않으려고요.

다른 방법으로 `docker run --init` 도 있습니다. 작은 init 프로그램이 PID 1 을 맡아서, 받은 신호를 자식에게 넘겨줘요.

## 코드로 보기 (개념 재현)

아래 주석의 결과는 busybox 셸이 들어 있는 이미지에서 실제로 찍어 본 값입니다.

```bash
# 1) 셸의 바꿔치기: 1번 프로세스 이름을 찍어 본다
docker run --rm image sh -c 'cat /proc/1/comm'            # cat : 셸이 사라지고 cat 이 PID 1
docker run --rm image sh -c 'cat /proc/1/comm; exit $?'   # sh  : 뒤에 할 일이 있어 셸이 남는다
docker run --rm image sh -c 'timeout 5 cat /proc/1/comm'  # cat : busybox timeout 도 자리를 내준다

# 2) PID 1 은 처리기 없는 TERM 을 무시한다
docker run -d --name demo1 image sleep 60
docker kill -s TERM demo1; sleep 3
docker inspect -f '{{.State.Running}}' demo1               # true  : 아직 돈다

docker run -d --init --name demo2 image sleep 60           # init 이 PID 1 을 맡는다
docker kill -s TERM demo2; sleep 3
docker inspect -f '{{.State.Running}}' demo2               # false : 끝났다 (종료 코드 143)

# 3) busybox timeout 의 종료 코드는 124 가 아니다
docker run --rm image sh -c 'timeout -s TERM 1 sleep 5; echo $?'      # 143

# 4) TERM 을 무시하는 프로그램도 -k 가 있으면 끝난다
docker run --rm image sh -c \
  'timeout -s TERM -k 2 1 sh -c "trap \"\" TERM; sleep 30"; echo $?'   # 137 (약 3초 뒤)
```

```bash
# 5) 고친 모양: 셸을 PID 1 로 남기고, 안 끝나면 KILL, 밖에서도 상한을 둔다
name="check-$$"
timeout -k 5 60 docker run --rm --name "$name" --label purpose=throwaway \
  image sh -c 'timeout -s TERM -k 2 2 broker -c /check.conf; exit $?'
rc=$?

if [ "$rc" -ge 124 ]; then
  docker rm -f "$name" >/dev/null 2>&1   # 상한에 걸렸으면 이름으로 지운다
  echo "판정 못 함"                       # 컨테이너 쪽 문제: 설정 문제와 구분한다
elif [ "$rc" -eq 0 ]; then
  echo "설정이 읽힌다"                    # 2초 뒤 TERM 을 받고 정상 종료
else
  echo "설정이 안 읽힌다"
fi
```

## 💡 배운 것

**PID 1 에게는 신호의 기본 동작이 없다는 걸 배웠습니다.** 보통 프로그램은 TERM 을 받으면 처리기가 없어도 끝나는데, PID 1 은 처리기가 없으면 무시해요. 컨테이너 안에서는 내가 띄운 프로그램이 바로 그 PID 1 일 수 있습니다.

**셸은 마지막 명령으로 자기 자신을 바꿔치기할 수 있다는 걸 배웠습니다.** `; exit $?` 하나로 프로세스 구조가 바뀌었어요. 눈으로는 같은 명령인데 PID 1 이 누구인지가 달라집니다.

**같은 이름의 도구도 구현마다 약속이 다르다는 걸 배웠습니다.** busybox `timeout` 은 124 를 돌려주지 않았어요. 판정에 쓰는 종료 코드는 그 이미지 안에서 직접 재 봐야 합니다.

**컨테이너의 시작 명령은 감싸는 모양 하나로 동작이 바뀐다는 걸 다시 배웠습니다.** 2026-09-11 에는 시작 명령을 감쌌다가 이미지가 해 주던 준비를 잃었어요. 이번엔 반대로, 셸이 감싸고 **남아 있어야** 신호가 제대로 전달됐습니다. 감쌀지 말지보다 "감싼 뒤 누가 PID 1 인가" 를 확인하는 게 먼저였어요.

**끝나지 않을 수 있는 것은 밖에서도 상한을 둔다는 걸 배웠습니다.** 안쪽 timeout 이 있어도, 그 timeout 이 놓치는 경우를 위해 바깥 상한과 이름·라벨(치울 때 잡을 손잡이)을 같이 둡니다.

## 소감

"2초 띄워 보고 끝낸다" 는 단순한 판정이었는데, 끝난다는 것 자체가 보장이 아니었어요. 실제 이미지 안에서 PID 1 이 누구인지 찍어 본 한 줄이 어떤 설명보다 빨랐습니다.

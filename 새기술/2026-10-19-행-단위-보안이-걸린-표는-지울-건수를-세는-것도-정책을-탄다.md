# 2026-10-19 행 단위 보안이 걸린 표는, 지울 건수를 세는 것도 정책을 탄다

> 태그: #새기술 #PostgreSQL #RLS #데이터정리 #서버이전

## 무엇을 / 왜

서비스를 새 서버로 옮기면서 DB 를 통째로 가져왔습니다. 안에는 개발하며 만든 테스트 상점·계정·주문이 가득했고, 실제 서비스를 열기 전에 운영자 계정 하나와 서비스 설정(요금제, 도움말, 약관 등)만 남겨야 했어요.

지우는 건 되돌리기 어려우니, 지우기 전에 "무엇이 몇 줄 지워지는지"부터 세어 보고 싶었습니다. 그런데 이 DB 는 상점별로 데이터를 나누려고 거의 모든 표에 PostgreSQL 행 단위 보안(RLS)을 **강제(FORCE)** 로 걸어 두었고, 정리에 쓰는 계정에는 RLS 를 건너뛰는 권한(BYPASSRLS)이 없었어요.

## 어떻게 풀었나

1. **표를 먼저 나눴습니다.** 표 271개를 남김(설정 25개), 일부만 남김(운영자 표 1개), 모두 비움(245개)으로 나누고, 분류에 없는 표가 하나라도 있으면 멈추게 했어요.
2. **세는 것도 정책을 탄다는 점을 짚었습니다.** RLS 가 강제로 걸린 표는 표 주인이 `count(*)` 를 해도 정책을 통과한 줄만 셉니다. 상점 정보를 설정하지 않은 연결에서는 실제보다 적게(정책에 따라 거의 0) 나와요. 그 숫자를 믿고 지우면, 몇 줄을 지우는지 모르고 지우는 셈입니다.
3. **세는 동안만 강제를 풀었습니다.** 트랜잭션 안에서 표마다 `NO FORCE ROW LEVEL SECURITY` 로 바꾸고, 세고, 끝에 `ROLLBACK` 해서 원래대로 돌렸어요. 표 주인은 강제만 풀리면 정책을 건너뛰어서 진짜 건수가 나옵니다. 표를 잠그는 일이라 앱을 끈 뒤에 했고, 한 트랜잭션에서 표 수백 개를 잠가도 되는지(잠금 슬롯) 미리 확인했습니다.
4. **지우기는 TRUNCATE 로 했습니다.** TRUNCATE 는 RLS 정책을 타지 않아서 전부 지워져요. 245개를 한 문장으로 비우되 `CASCADE` 대신 `RESTRICT` 를 써서, 남길 표가 외래 키로 딸려 지워지는 대신 멈추게 했습니다.
5. **연습하고 지웠습니다.** 같은 스크립트를 "끝까지 해 보고 되돌리기"로 한 번 돌린 뒤, 확인 문구를 직접 입력해야만 커밋하게 했어요. 지우기 전에는 DB 버전, 남길 운영자가 정확히 한 명인지, 앱이 꺼져 있는지를 먼저 확인합니다.

## 코드로 보기 (개념 재현)

```sql
-- 세어 보기: 강제를 잠깐 풀고 세고, 전부 되돌린다
BEGIN;
ALTER TABLE shop          NO FORCE ROW LEVEL SECURITY;  -- 표 주인은 강제가 풀리면 정책을 건너뛴다
ALTER TABLE order_record  NO FORCE ROW LEVEL SECURITY;
-- ... 비울 표 전부

SELECT 'DELETE_ALL' AS plan, 'shop' AS tbl, count(*) FROM shop
UNION ALL
SELECT 'DELETE_ALL', 'order_record', count(*) FROM order_record
UNION ALL
SELECT 'KEEP', 'plan_setting', count(*) FROM plan_setting;
ROLLBACK;                                               -- FORCE 도 원래대로 돌아온다
```

```sql
-- 지우기: 안전장치를 통과해야만 진행 (psql -v keep_email=... 로 남길 운영자를 넘긴다)
BEGIN;
SELECT set_config('cleanup.keep_email', :'keep_email', true);

DO $$
BEGIN
  IF (SELECT version FROM schema_history ORDER BY installed_rank DESC LIMIT 1) <> '231.19' THEN
    RAISE EXCEPTION 'DB 버전이 예상과 다름';
  END IF;
  IF (SELECT count(*) FROM operator
       WHERE lower(email) = lower(current_setting('cleanup.keep_email'))
         AND role = 'SUPERUSER' AND active) <> 1 THEN
    RAISE EXCEPTION '남길 운영자가 정확히 한 명이 아님';
  END IF;
END $$;

TRUNCATE shop, order_record, account /* ... 245개 */ RESTRICT;  -- 정책을 타지 않고, 딸린 표를 몰래 지우지 않는다
DELETE FROM operator WHERE lower(email) <> lower(current_setting('cleanup.keep_email'));

ROLLBACK;  -- 연습. 확인 문구를 입력한 실행에서만 여기를 COMMIT 으로 바꿔 돈다
```

```bash
# 실행: 세기 -> 연습 -> 진짜. 진짜는 직접 입력해야 한다
psql -v ON_ERROR_STOP=1 -f count.sql
psql -v ON_ERROR_STOP=1 -v keep_email="$KEEP" -f cleanup.sql              # 끝에서 ROLLBACK
read -r -p "정말 지우려면 DELETE 를 입력: " ans && [ "$ans" = DELETE ] &&
  psql -v ON_ERROR_STOP=1 -v keep_email="$KEEP" -v commit=1 -f cleanup.sql  # 이때만 COMMIT
```

## 💡 배운 것

**RLS 를 강제로 걸면, 표 주인의 count(*) 도 적게 말할 수 있습니다.** 보안을 위해 건 강제가 운영 작업에서는 "적게 보이는" 함정이 돼요. 건수를 셀 때는 그 숫자가 정책을 탄 숫자인지부터 확인해야 합니다.

**PostgreSQL 은 ALTER TABLE 도 되돌릴 수 있습니다.** 그래서 "잠깐 풀고 세고 되돌리기"가 안전하게 됩니다. 다만 표를 잠그니 앱을 끄고, 잠금 슬롯이 넉넉한지 미리 봤어요.

**TRUNCATE 는 정책을 타지 않고, RESTRICT 는 딸린 표를 지우는 대신 멈춥니다.** CASCADE 는 편하지만 남길 표까지 조용히 비울 수 있어요.

**지우는 스크립트는 "세기, 연습, 진짜" 세 번으로 돌립니다.** 같은 파일을 쓰고 마지막에 커밋할지만 다르게 해서, 연습한 것과 진짜가 달라지지 않게 했습니다.

## 소감

세기 전에 정리 계정의 권한부터 확인한 덕분에, 숫자가 적게 나오는 함정에 빠지지 않았습니다. 보안 장치는 앱을 지키려고 건 건데, 운영할 때는 그 장치가 내 눈도 가릴 수 있다는 걸 배웠어요. 지울 줄의 96% 가 서버 상태 점검 기록이었다는 것도 세어 보고서야 알았습니다.

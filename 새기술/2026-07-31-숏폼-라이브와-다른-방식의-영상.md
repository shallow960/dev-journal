# 2026-07-31 숏폼 만들기 - 같은 영상인데 라이브와 올리는 방식이 달랐다

> 태그: #새기술 #숏폼 #영상 #외부연동

## 오늘 한 일 (요약)
- 쇼핑몰에 **숏폼(짧은 세로 영상)** 기능을 처음부터 붙였다. 판매자가 영상을 올리면 -> 처리 후 -> 손님이 **틱톡 같은 세로 피드**로 넘겨 보고 -> 영상에 **상품 태그**를 달아 바로 상세로 가게 했다.
- 라이브를 먼저 붙여봤던 터라 "영상이면 다 비슷하겠지" 했는데, **올리는 방식이 라이브와 완전히 달랐다.**

## 무엇을 / 왜
라이브(실시간 방송)와 숏폼(미리 찍은 영상)은 둘 다 "영상"이지만 넣는 방법이 다르다.

- **라이브**: 방송 장비(OBS)가 **실시간 송출 규격(RTMPS)** 으로 영상 서비스에 계속 흘려보낸다.
- **숏폼**: 이미 찍힌 파일을 **한 번 업로드(HTTPS)** 하면 끝이다. 우리가 흔히 쓰는 웹 요청과 같은 통로다.

그래서 라이브 때 만들어 둔 "영상 연동 통로"를 그대로 못 쓰고, **업로드 전용 통로를 따로** 뒀다. 흐름은 이렇다: 판매자가 올리기를 누르면 -> 서비스에서 **업로드 주소**를 받아 -> 브라우저가 그 주소로 파일을 직접 올리고 -> 서비스가 영상을 변환하면 -> 손님 피드에 뜬다.

## 어떻게 풀었나 - 기억에 남는 문제 하나
**"영상 변환이 끝났는지를 누가, 언제 확인하나?"**

파일을 올려도 바로 재생되진 않는다. 서비스가 화질 변환을 마쳐야 한다. 보통은 서비스가 "변환 끝났어"라고 **알림(웹훅)** 을 보내주는데, 우리 쪽엔 걸림돌이 있었다.

우리 데이터는 **가게별로 칸막이(행 수준 보안)** 가 쳐져 있어서, "지금 어느 가게인지"를 알아야만 그 가게 데이터를 건드릴 수 있다. 그런데 외부 서비스가 보내는 알림에는 "어느 가게"라는 우리 쪽 문맥이 없다. 그래서 알림으로 상태를 바꾸려면 칸막이를 우회하는 복잡한 처리가 필요했다.

그래서 방식을 뒤집었다. **판매자가 올린 뒤에 "게시" 버튼을 누르면, 그때 우리 서버가 서비스에 "변환 다 됐어?"를 물어보고 됐으면 게시**하도록 했다. 이러면 요청을 보낸 사람이 이미 "그 가게 판매자"라 칸막이 문맥이 자연스럽게 잡히고, 알림을 우회할 필요가 없다. 변환은 몇십 초라, 완료될 때까지 몇 번 되물어보게 했다.

## 💡 배운 것
- **"같은 영상"이라도 실시간 송출과 파일 업로드는 성격이 아예 다르다.** 통로를 억지로 하나로 합치지 않고, 라이브용/업로드용 인터페이스를 나눠 두니 각자 단순해졌다. 앞으로 provider(영상 서비스)를 갈아끼워도 이 경계는 유지된다.
- **업로드는 평범한 HTTPS라, 실시간 송출과 달리 막히는 데가 적다.** 라이브(RTMPS)는 회사망이나 방화벽에서 막히기도 하는데, 파일 업로드는 우리가 늘 쓰는 웹 요청과 같은 통로라 그런 제약에서 자유로웠다. 같은 "영상 기능"이라도 검증 난이도가 달랐다.
- **외부 알림(웹훅)이 우리 보안 모델과 안 맞으면, 굳이 알림을 고집하지 않아도 된다.** "사용자가 행동할 때 우리가 물어본다"로 방향을 바꾸니, 보안 칸막이를 그대로 둔 채 더 단순하게 풀렸다. 정답이 하나가 아니라는 걸 느꼈다.

## 소감
라이브를 먼저 해본 게 도움이 되면서도 발목을 잡았다. "영상은 이런 거지" 하고 라이브 통로를 재사용하려다, 숏폼은 아예 다른 방식이란 걸 중간에 깨닫고 갈아엎었다. 덕분에 "영상"이라는 뭉뚱그린 말 안에 실시간과 업로드라는 서로 다른 두 세계가 있다는 걸 배웠다. 실제 업로드 검증은 라이브와 마찬가지로 서비스 구독을 켠 뒤에 마저 할 계획인데, 숏폼 쪽은 통로가 평범한 HTTPS라 그때 훨씬 수월할 것 같다.

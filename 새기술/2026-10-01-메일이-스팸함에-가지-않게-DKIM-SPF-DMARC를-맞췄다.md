# 2026-10-01 메일이 스팸함에 가지 않게, DKIM·SPF·DMARC를 맞췄다

> 태그: #새기술 #이메일 #DKIM #SPF #DMARC #DNS #AWS-SES

## 무엇을 / 왜

서비스에서 나가는 메일(비밀번호 재설정, 주문 알림 등)은 클라우드 메일 발송 서비스(AWS SES)로 보냅니다. SES는 처음엔 "샌드박스" 라서 인증한 주소로만 보낼 수 있고, 운영 발송 승인을 받아야 아무에게나 보낼 수 있습니다.

승인이 나서 끝인 줄 알았는데, 메일이 **받은 편지함에 들어가는 것** 은 다른 문제였습니다. 받는 쪽 메일 서버는 "이 메일이 정말 그 도메인이 보낸 것인가" 를 여러 방법으로 확인하고, 어긋나면 스팸함으로 보내거나 거절할 수 있습니다.

## 어떻게 풀었나

### 세 가지가 각각 확인하는 것

| 이름 | 확인하는 것 | 우리가 할 일 |
|---|---|---|
| DKIM | 메일에 도메인의 전자서명이 붙어 있고 서명이 맞는가 | 발송 서비스가 준 공개키 레코드(CNAME)를 DNS에 등록 |
| SPF | 메일을 보낸 서버가 그 도메인이 허락한 서버인가 | "이 서버들은 보내도 된다" 는 TXT 레코드 |
| DMARC | DKIM·SPF 결과가 **보낸사람 주소의 도메인** 과 맞는가, 안 맞으면 어떻게 할까 | `_dmarc` TXT 레코드로 정책 선언 |

헷갈렸던 건 SPF였습니다. SPF는 화면에 보이는 보낸사람(From)이 아니라 **반송 주소(MAIL FROM)** 의 도메인을 봅니다. 아무 설정 없이 SES로 보내면 반송 주소가 SES 쪽 도메인이라, SPF는 통과해도 우리 도메인과 "맞지(정렬되지)" 않아 DMARC 입장에서는 SPF가 도움이 되지 않습니다. 그래서 반송 주소를 우리 하위 도메인으로 바꾸는 **사용자 지정 MAIL FROM** 을 설정했습니다.

### 반송·수신거부를 듣는 귀

없는 주소로 계속 보내거나, 스팸 신고한 사람에게 계속 보내면 발송 평판이 떨어지고 계정이 제한될 수 있습니다. 서버에는 반송·신고된 주소를 발송 금지 목록에 넣고 보내기 전에 거르는 처리가 이미 있어서, 이번에는 SES가 반송(bounce)·스팸 신고(complaint)를 알림 서비스(SNS) 주제로 보내고 그 주제가 서버의 알림 입구로 오게 연결했습니다.

알림 입구는 인터넷에 열려 있어야 해서, 아무나 가짜 알림을 보내지 못하게 두 가지를 확인합니다.

1. 우리가 구독한 **그 주제** 에서 온 알림인가
2. 알림에 붙은 **서명** 이 SNS가 서명한 것과 맞는가

연결한 뒤에는 밖에서 직접 요청을 보내, 다른 주제로 보낸 알림은 "unexpected topic" 으로, 서명이 없는 알림은 서명 검증에서 거절되는지 확인했습니다.

### DNS는 "넣었다" 가 아니라 "보인다" 를 확인

DNS 레코드는 넣은 뒤 바로 모든 곳에서 보이지 않을 수 있습니다. 그래서 도메인의 **권한 서버** 와 **공용 리졸버(8.8.8.8)** 양쪽에 물어서 같은 값이 나오는지 봤습니다. DMARC는 처음이라 정책을 `p=none` 으로 두었습니다. "어긋나도 일단 받되 결과만 알려 달라" 는 뜻이라, 설정이 틀렸을 때 정상 메일까지 막히는 위험이 없습니다.

마지막으로 실제 비밀번호 재설정 메일을 보내 받은 편지함에 들어오는 것을 확인했습니다.

## 코드로 보기 (개념 재현)

DNS 레코드 예시입니다. 도메인과 값은 예시입니다.

```
; DKIM - 발송 서비스가 알려 준 CNAME (서명 공개키가 있는 곳을 가리킨다)
token1._domainkey.example.com.   CNAME  token1.dkim.amazonses.com.

; 사용자 지정 MAIL FROM - 반송 주소용 하위 도메인
; MX: 반송 메일을 받을 곳, TXT(SPF): 이 도메인으로 보내도 되는 서버
mail.example.com.   MX   10 feedback-smtp.ap-northeast-2.amazonses.com.
mail.example.com.   TXT  "v=spf1 include:amazonses.com ~all"

; DMARC - 처음엔 막지 않고 관찰만
_dmarc.example.com. TXT  "v=DMARC1; p=none"
```

반영 확인입니다.

```bash
# 도메인의 권한 서버에 직접 묻기
dig +short TXT _dmarc.example.com @ns-1.example-dns.net
# 공용 리졸버에 묻기 - 두 결과가 같아야 "바깥에서도 보인다"
dig +short TXT _dmarc.example.com @8.8.8.8
dig +short MX mail.example.com @8.8.8.8
```

알림 입구에서 하는 확인(요약)입니다.

```java
// 반송·수신거부 알림을 받는 입구. 인터넷에 열려 있으므로 두 가지를 먼저 본다.
public Response receive(SnsMessage message) {
    // 1) 우리가 구독한 주제에서 온 것인가 (설정값과 비교)
    if (!expectedTopicArn.equals(message.topicArn())) {
        return Response.reject("unexpected topic");
    }
    // 2) SNS 가 서명한 메시지인가 (인증서로 서명 검증)
    if (!signatureVerifier.isValid(message)) {
        return Response.reject("invalid signature");
    }
    // 반송·신고된 주소는 발송 금지 목록에 넣고, 보내기 전에 이 목록으로 거른다
    suppressionList.addFrom(message);
    return Response.ok();
}
```

## 💡 배운 것

**발송 승인과 받은 편지함은 다른 이야기입니다.** 승인은 "보내도 된다" 이고, DKIM·SPF·DMARC는 "믿어도 된다" 입니다.

**SPF는 반송 주소를 봅니다.** 화면의 보낸사람 도메인과 맞추려면 사용자 지정 MAIL FROM이 필요했습니다.

**DMARC는 관찰부터.** `p=none` 으로 시작해 결과를 본 뒤에 강하게 가는 게 안전합니다.

**DNS는 여러 곳에 물어봅니다.** 권한 서버와 공용 리졸버의 답이 같아야 실제로 반영된 것입니다.

**열려 있는 알림 입구는 주제와 서명을 둘 다 봅니다.** 둘 중 하나만 보면 가짜 알림으로 멀쩡한 주소를 발송 금지시킬 수 있습니다.

## 소감

메일은 "보내면 간다" 고 생각했는데, 받는 쪽이 보낸 쪽을 믿게 만드는 장치가 이렇게 여러 겹이라는 걸 처음 제대로 정리했습니다. 콘솔에서 상태가 "성공" 으로 바뀌는 것보다, 밖에서 DNS를 조회하고 실제 메일이 받은 편지함에 도착하는 걸 본 순간이 더 확실했습니다. DMARC 보고서를 받아 보면서 정책을 올리는 건 다음 단계로 남겨 두었습니다.

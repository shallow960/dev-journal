# 2026-08-10 카드 결제에 두 가지 방식이 있었다 - 인증과 비인증, 무엇이 다른가

> 태그: #새기술 #결제연동 #NICEPAY #보안

## 오늘 한 일 (요약)
- 카드사에서 답이 왔다. "**비인증 결제**를 희망하시면 저희 결제창이 아니라 **가맹점 화면의 카드정보 입력창**이 확인되어야 합니다."
- 처음엔 무슨 말인지 몰랐다. 결제창 띄우면 되는 것 아닌가?
- 알고 보니 카드 결제에는 **인증 / 비인증** 두 방식이 있고, 우리가 쓰던 건 인증 방식이었다.
- 구독(정기결제)을 비인증으로 다시 만들었다. 카드 입력 폼 + AES 암호화 + 빌키 발급.

## 두 방식의 차이

| | 인증(Authenticated) | 비인증(Non-authenticated / Key-in) |
|---|---|---|
| 카드정보 입력 | **결제사 결제창** | **가맹점 화면(우리 폼)** |
| 사용자 경험 | 카드사 선택 → 앱카드/간편결제 인증 | 카드번호·유효기간·생년월일·비밀번호 앞2자리 입력 |
| 가맹점이 카드번호를 보나 | ❌ 안 봄 | ⭕ 받아서 전달(저장은 하지 않음) |
| 주로 쓰는 곳 | 단건 결제 | 정기결제(구독), 자동결제 |

핵심은 **카드정보를 누가 받느냐**다. 인증은 결제사가 받고, 비인증은 우리가 받아서 결제사에 넘긴다. 그래서 비인증은 가맹점 심사가 따로 있고 요건도 더 까다롭다.

## 비인증 빌키 발급은 이렇게 생겼다
"빌키(BID)"는 카드 대신 쓰는 결제용 열쇠다. 한 번 발급받으면 그걸로 매월 청구한다.

```java
// 1) 위변조 검증용 서명
String signData = sha256Hex(MID + ediDate + moid + merchantKey);

// 2) 카드정보를 AES 로 암호화 (키는 상점키 앞 16자, 결과는 hex)
String plain = "CardNo=" + cardNo
             + "&ExpYear=" + expYear
             + "&ExpMonth=" + expMonth
             + "&IDNo=" + idNo          // 생년월일 6자리
             + "&CardPw=" + cardPw;     // 비밀번호 앞 2자리
String encData = encryptAesHex(plain, merchantKey.substring(0, 16));

// 3) 서버-투-서버 발급 요청
POST /webapi/billing/billing_regist.jsp
     MID, EdiDate, Moid, EncData, SignData
// 성공 결과코드 F100 → BID(빌키) 수신
```

```java
private static String encryptAesHex(String plain, String key) {
    Cipher cipher = Cipher.getInstance("AES/ECB/PKCS5Padding");
    cipher.init(Cipher.ENCRYPT_MODE, new SecretKeySpec(key.getBytes(UTF_8), "AES"));
    return HexFormat.of().formatHex(cipher.doFinal(plain.getBytes(UTF_8)));
}
```

이후 매월 청구는 이 빌키로 승인 API를 호출하면 된다. 카드정보는 더 이상 필요 없다.

## 카드정보를 다루는 원칙
비인증은 우리가 카드번호를 만지기 때문에, 지킬 선을 처음부터 정해두고 시작했다.

- **저장하지 않는다.** 발급 요청에만 쓰고 버린다. DB에 남는 건 카드사명 · 마스킹 번호 · 빌키뿐.
- **화면에도 남기지 않는다.** 등록 성공 즉시 입력값을 비운다.
- **로그에 찍지 않는다.** 요청 본문을 그대로 로깅하면 그 순간 끝이다.
- 전 구간 HTTPS.

```java
return paymentMethodService.register(new RegisterPaymentMethodCommand(
    userId, CARD, NICEPAY,
    maskedNo,      // 결제사가 돌려준 마스킹 번호
    ..., bid       // 빌키
));                // 카드 원문은 어디에도 넘기지 않는다
```

## 검증: 실패 응답이 성공 신호였다
더미 카드번호(`4111...`)로 호출했더니 이런 답이 왔다.

```
F113 해당카드 사용불가 가맹점(타카드 사용요망)
```

처음엔 실패인 줄 알았는데, 오히려 **좋은 신호**였다. 이 응답이 왔다는 건:

- 통신 성공 ✅
- SHA-256 서명 검증 통과 ✅ (틀리면 서명 오류가 난다)
- AES 암호화·복호화 성공 ✅ (틀리면 파싱 오류가 난다)
- **카드번호만** 유효하지 않아 거부 ✅

즉 연동 규격은 전부 통과했고 남은 건 실제 카드뿐이었다. 외부 연동에서는 **에러 코드가 "어디까지 통과했는지"를 알려준다.**

## 결과: 상품별로 방식을 나눴다
| 상품 | 결제 방식 | 이유 |
|---|---|---|
| 구독(정기결제) | 비인증 | 매월 자동 청구가 필요 → 빌키 발급 |
| 1회성 서비스(단건) | 인증 | 한 번 결제하고 끝 → 결제창이 간편 |

두 방식을 함께 쓰려면 **각각 카드사 심사와 상점 ID(MID)가 따로** 필요하다는 것도 이번에 알았다.

## 💡 배운 것
- 카드 결제는 하나가 아니다. **인증/비인증**은 사용자 경험뿐 아니라 **심사·계약·보안 책임**이 달라진다.
- 비인증을 쓰면 카드정보가 우리 서버를 지나간다. **저장·로그·화면 잔존**을 처음부터 막고 시작해야 한다.
- 빌키 방식은 "카드정보를 한 번만 받고, 이후엔 열쇠로 청구"하는 구조다. 정기결제의 표준.
- 외부 연동 검증에서 **실패 응답의 종류를 읽으면** 내 구현이 어디까지 맞는지 알 수 있다. 무조건 성공만 기다릴 필요가 없다.

## 소감
"결제 붙이기"를 하나의 작업으로 생각했는데, 실제로는 방식 선택부터가 설계였다. 카드사 답변 한 줄("가맹점 화면의 카드정보 입력창이 확인되어야 합니다")이 무슨 뜻인지 이해하는 데 시간이 좀 걸렸는데, 알고 나니 왜 그렇게 요구하는지도 납득이 됐다. 우리가 카드번호를 받는 만큼 확인할 게 더 많은 것이다.

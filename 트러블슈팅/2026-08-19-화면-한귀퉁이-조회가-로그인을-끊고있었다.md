# 2026-08-19 화면 한 귀퉁이의 조회 하나가 로그인을 끊고 있었다

> 태그: #트러블슈팅 #인증 #실행순서 #프론트엔드

## 무엇을 / 왜

판매자로 로그인했는데 판매자 센터에 들어가면 **"로그인이 필요합니다"** 가 뜬다는 이야기를
들었습니다. 정산이나 상품 화면의 데이터도 안 나온다고요.

로그인 자체는 됩니다. 로그인 화면에서 아이디·비밀번호를 넣으면 통과하고, 다른 화면은
멀쩡합니다. 그런데 판매자 센터만 들어가면 로그인이 풀린 것처럼 보였습니다.

## 어떻게 풀었나

### 눈으로 보는 대신 요청을 봤다

처음엔 "세션이 짧은가", "쿠키가 안 붙나" 를 의심했습니다. 서버에 직접 로그인 요청을 보내
보니 **정상**이었어요. 로그인도 되고, 로그인 상태를 이어주는 값도 잘 내려옵니다.

그래서 추측을 멈추고 **실제 브라우저를 자동으로 조작하는 도구**로 똑같이 재현했습니다.
로그인하고, 그 화면에 들어가고, 그동안 오간 요청을 전부 찍어 봤습니다.

```
로그인          → 정상
판매자 센터 진입 → 401 (거절) /api/.../me/seller   ← 로그인 정보가 안 실려 있음
                → 401 (거절) /api/.../auth/refresh
```

거절당한 요청의 헤더를 보니 **로그인 정보가 아예 비어 있었습니다.**

### 원인은 "순서" 였다

화면 코드는 이렇게 생겼습니다.

```
export default function 판매자센터() {
  useEffect(() => {
    입점정보_불러오기();      // ① 화면이 뜨자마자 바로 실행
  }, []);

  return (
    <로그인확인>              // ② 로그인 확인은 여기 안에서 이루어진다
      ...
    </로그인확인>
  );
}
```

`useEffect` 는 화면이 뜨는 순간 실행됩니다. 반면 로그인 확인은 화면 **안쪽**에 있어서,
그때는 아직 로그인 정보가 준비되기 전이었습니다. 새로고침을 하면 로그인 정보는 메모리에서
사라지고 서버에서 다시 받아오는데, 그 과정이 끝나기 전에 ①이 먼저 출발한 겁니다.

### 진짜 문제는 그다음이었다

여기까지면 "그 조회 하나만 실패" 하고 끝났을 텐데, 우리 공용 통신 코드가 이렇게 돼 있었습니다.

```
서버가 401(거절)을 주면
  → 로그인 정보를 다시 받아 본다
  → 그것도 실패하면 저장된 로그인 정보를 지우고 로그인 화면으로 보낸다
```

**화면 한 귀퉁이를 채우는 조회 하나가 로그인 상태 전체를 끝내고 있었습니다.** 그래서 정산도
상품도 같이 안 나왔던 겁니다. 이미 로그인 정보가 지워진 뒤였으니까요.

### 고친 것

두 가지입니다.

**하나, 조회를 로그인 확인 안쪽으로 옮겼습니다.** 로그인 확인을 통과한 뒤에만 화면이 그려
지므로, 그 안에서 실행되는 조회는 로그인 정보가 반드시 준비돼 있습니다.

```
<로그인확인>
  <입점정보요약 />     // 통과한 뒤에만 여기까지 온다
</로그인확인>
```

**둘, 이런 곁다리 조회는 실패해도 로그인 상태를 건드리지 않게** 했습니다. 화면 한 칸을 채우는
조회가 로그인 여부를 결정할 이유가 없습니다. 실패하면 그 칸만 비면 됩니다.

고친 뒤 판매자 화면 6개를 다시 훑어서 실패한 요청이 **하나도 없는** 것을 확인했습니다.

## 코드로 보기 (개념 재현)

문제의 모양을 줄이면 이렇습니다.

```
// 이렇게 하면 안 된다 - 로그인 확인보다 먼저 나간다
function 페이지() {
  useEffect(() => { 서버조회(); }, []);   // ①
  return <로그인확인>{내용}</로그인확인>;   // ②
}

// 이렇게 - 확인이 끝난 뒤에만 마운트되는 자식에서 부른다
function 페이지() {
  return <로그인확인><요약 /></로그인확인>;
}
function 요약() {
  useEffect(() => { 서버조회(); }, []);   // 여기선 로그인 정보가 반드시 있다
}
```

## 💡 배운 것

- **화면이 그려지는 순서와 로그인 준비가 끝나는 순서는 다르다.** 화면 안쪽에 로그인 확인을
  두면 "확인을 하고 있다" 는 착각이 들지만, 바깥의 코드는 그걸 기다려 주지 않습니다.
- **곁다리 조회가 로그인 상태를 결정하게 두면 안 된다.** 거절 한 번에 로그인 정보를 지우는
  공용 처리는 "중요한 요청" 을 전제로 만든 것인데, 화면 한 칸 채우는 조회에도 똑같이 적용됩니다.
- **추측을 멈추고 실제로 재현하자.** 서버에 직접 요청을 보냈을 땐 다 정상이라 원인을 못
  찾았습니다. 브라우저에서 실제로 재현하고 나서야 "로그인 정보가 비어 있다" 가 보였습니다.
- 같은 날 비슷한 실수를 **한 번 더** 했습니다. 다른 화면에서도 곁다리 조회를 만들었는데,
  거기서도 실패가 세션을 건드릴 뻔했어요. 한 번 밟은 함정은 같은 날에도 다시 밟힙니다.

## 소감

제보만 들었을 때는 "로그인이 풀린다" 였고, 저는 로그인 기능을 의심했습니다. 그런데 로그인은
멀쩡했고 범인은 **엉뚱한 화면의 작은 조회 하나**였습니다.

증상이 나타나는 곳과 원인이 있는 곳이 다를 수 있다는 걸 또 배웠습니다. 그리고 이번엔 추측을
오래 하지 않고 재현부터 한 게 결과적으로 빨랐습니다. 다음에도 "이럴 것 같다" 가 두 번 빗나가면
바로 재현으로 넘어가려고 합니다.

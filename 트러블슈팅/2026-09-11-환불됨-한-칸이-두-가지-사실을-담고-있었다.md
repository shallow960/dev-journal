# 2026-09-11 "환불됨" 한 칸이 두 가지 사실을 담고 있었다

> 태그: #트러블슈팅 #상태설계 #결제 #데이터모델

## 무엇을 / 왜

이용이 끝난 카드 결제 건으로 환불을 시험했습니다. 관리 웹에서 먼저 환불을 누르고, 안내대로 매표소에 가서 카드 취소를 하려 했더니 막혔습니다.

관리 웹 환불은 **장부만 바꾸고 카드에는 손대지 않는** 버튼입니다. 그래서 그 버튼은 "카드는 매표소에서 취소하세요" 라고 안내합니다. 그런데 매표소는 **"이미 환불된 결제입니다"** 로 거절했습니다.

안내를 그대로 따른 직원이 손님에게 돈을 돌려줄 길이 없는 상태였습니다.

## 어떻게 풀었나

### 기록을 시간순으로 맞춰 봤다

그 건의 기록을 순서대로 늘어놓았습니다.

```
결제 → 이용 시작 → 이용 종료 → 관리 웹 환불(장부) → (카드 취소 기록 없음)
```

"기록이 없다" 는 것도 단서였습니다. 코드를 따라가니 원인이 둘이었습니다.

### 원인 1: 서로 다른 두 일을 한 칸에 적고 있었다

서버에는 결제마다 **"환불됨" 이라는 칸 하나뿐**이었습니다. 그런데 실제로 일어나는 일은 둘입니다.

| 일 | 누가 하나 | 돈이 움직이나 |
|---|---|---|
| 장부 환불 | 관리 웹 | 아니오 |
| 카드 취소 | 매표소·키오스크 카드 단말 | 예 |

두 일이 같은 칸을 세우니, 매표소의 사전확인은 장부만 바뀐 건을 **카드까지 돌려준 건으로** 보고 막았습니다.

### 원인 2: 카드는 돌아갔는데 장부에는 아무것도 안 남았다

이용 중이거나 끝난 건은 카드를 취소해도, 서버가 "대기 중인 예약만 취소할 수 있다" 며 기록을 거절하고 있었습니다. **돈은 나갔고 기록은 없습니다.**

### 칸을 나누고, 막는 기준을 바꿨다

- 결제에 **카드 취소 시각**을 적는 칸을 따로 뒀습니다. 비어 있으면 카드는 아직 안 돌려준 것입니다
- 카드 취소를 막는 기준을 "장부가 환불됐나" 에서 **"카드가 이미 취소됐나"** 로 바꿨습니다. 두 번 돌려주는 것은 그대로 막히고, 장부만 환불된 건은 카드를 돌려줄 수 있습니다
- 이용 중·종료 건도 카드 취소가 끝나면 결제를 환불로 기록합니다. 이용 기록은 그대로 둡니다
- 결제 조회에 **"환불됨 · 카드 미취소"** 를 따로 보여 줘서, 장부만 맞추고 카드를 안 돌려준 건을 찾을 수 있게 했습니다

이미 쌓인 데이터는 과거 카드 취소 로그가 있는 결제만 그 시각으로 채웠습니다. 몇 번을 돌려도 결과가 같게 짰습니다.

## 코드로 보기 (개념 재현)

문제가 됐던 구조입니다.

```js
// 결제 한 건에 "환불됨" 하나뿐
// { id: 1001, method: "card", refunded: false }

// 관리 웹 [환불]: 장부만 바꾼다. 카드 단말과는 대화하지 않는다.
async function refundLedger(paymentId) {
  await db.payments.update({ refunded: true }, { where: { id: paymentId } });
  return { message: "카드는 매표소에서 취소하세요" };
}

// 매표소 [카드 취소] 사전확인
async function canCancelCard(paymentId) {
  const p = await db.payments.findByPk(paymentId);
  if (p.refunded) return { ok: false, reason: "이미 환불된 결제입니다" };
  // ★ 장부 환불과 카드 취소를 구분할 수 없다. 방금 안내한 길을 스스로 막는다.
  return { ok: true };
}
```

칸을 나눈 뒤입니다.

```sql
-- 카드 단말이 취소 승인을 낸 시각. NULL 이면 카드는 아직 안 돌려줬다.
ALTER TABLE payments ADD COLUMN card_cancelled_at DATETIME NULL;
```

```js
async function canCancelCard(paymentId) {
  const p = await db.payments.findByPk(paymentId);
  // 막는 기준은 "돈이 이미 돌아갔나" 하나뿐이다.
  if (p.cardCancelledAt) return { ok: false, reason: "이미 카드 취소가 기록된 결제입니다" };

  // 장부만 환불된 건이면 막지 않고, 무엇이 이미 됐는지 함께 알린다.
  return { ok: true, note: p.refunded ? "장부 환불은 이미 되어 있습니다" : null };
}

async function recordCardCancel(paymentId) {
  // ★ 조건부 갱신: 동시에 두 번 들어와도 한 번만 기록된다.
  const [changed] = await db.payments.update(
    {
      cardCancelledAt: new Date(),
      refunded: true,          // 아직 장부 환불 전이면 같이 세운다
    },
    { where: { id: paymentId, cardCancelledAt: null } }
  );
  if (changed === 0) throw new Error("이미 카드 취소가 기록된 결제입니다");
}
```

조회 화면에서 둘을 가르는 부분입니다.

```js
function refundLabel(p) {
  if (!p.refunded) return "";
  if (p.method === "card" && !p.cardCancelledAt) return "환불됨 · 카드 미취소";
  return "환불됨";
}
```

## 💡 배운 것

**한 단어로 뭉친 상태는 실제로 일어난 일 단위로 나눠야 합니다.** "환불" 은 말로는 하나지만 장부를 고치는 일과 돈을 돌려주는 일은 다릅니다. 한 칸에 적으면 한쪽이 끝난 것을 다른 쪽도 끝났다고 보게 됩니다.

**막는 조건은 "무엇을 막고 싶은가" 에 맞춰야 합니다.** 막고 싶었던 건 "두 번 돌려주기" 였는데, 실제로 보고 있던 건 "장부 표시" 였습니다. 기준이 어긋나니 막아야 할 것은 못 막고 열어야 할 것을 막았습니다.

**"기록이 없다" 도 단서입니다.** 시간순으로 늘어놓으니 카드 취소 기록이 빠진 자리가 보였고, 거기서 두 번째 원인을 찾았습니다.

**확인하지 못한 것은 결과에 섞지 않습니다.** 매표소 실기기 첫 시도는 조회가 되지 않았는데 서버에 거절 기록조차 없었습니다. 추정은 따로 적고, 받은 값을 로그로 남기게 한 뒤 재확인 항목으로 뒀습니다.

## 소감

전날 "관리 웹 환불은 카드를 건드리지 않는다" 를 화면에 알리게 고쳤는데, 다음 날 **그 안내를 따라간 길이 막혀 있었습니다.**

안내 문구를 붙이는 것만으로는 부족하고, 안내가 가리키는 곳이 실제로 그 일을 받아 주는지까지 봐야 한다는 걸 알았습니다. 칸 하나를 나누는 작은 변경이었지만, 그 칸이 무엇을 뜻하는지 정하는 게 제일 오래 걸렸습니다.

# 2026-10-19 오류 하나가, 1초마다 요청 세 개를 만들고 있었다

> 태그: #트러블슈팅 #프론트엔드 #무한반복 #자동복구 #네트워크탭

## 무엇을 / 왜

쇼핑몰 관리자 화면의 사이드 메뉴에는 "처리할 일" 숫자가 붙어 있습니다. 화면이 뜰 때, 메뉴를 옮길 때, 무언가를 처리했을 때 서버에 숫자를 다시 물어요.

서버를 옮기는 리허설 중에, 결제가 밀려 '이용할 수 없음' 상태가 된 쇼핑몰의 관리 화면을 열어 두자 개발자 도구에 403 이 1초마다 쌓였습니다. 화면은 멀쩡해 보여서 지나칠 뻔했어요. 탭 하나가 1초마다 요청 3개(403, 세션 다시 열기, 다시 403)를 보내고 있었습니다.

## 어떻게 풀었나

네트워크 탭을 시간 순서대로 읽으니 고리가 보였습니다.

1. 메뉴 숫자 요청 → **403** (쇼핑몰이 이용할 수 없는 상태)
2. 공통 요청 함수의 **자동 복구**: 401·403 이면 로그인이 풀린 걸로 보고 쇼핑몰 세션을 다시 엽니다(POST).
3. 공통 요청 함수의 **자동 새로고침**: 바꾸는 요청(POST 등)이 성공하면 처리할 일이 바뀌었을 수 있으니 0.4초 뒤 메뉴 숫자를 다시 셉니다.
4. 다시 1번.

2번과 3번은 각자 맞는 동작입니다. 문제는 둘이 만날 때였어요. 그래서 기능은 그대로 두고 만나는 곳 세 군데만 끊었습니다.

- 쇼핑몰 **상태 때문에** 막힌 403(이용 불가·휴점·종료)은 세션을 다시 열지 않는다. 다시 열어도 같은 답이 온다.
- 로그인·토큰 재발급·로그아웃·세션 열기 같은 요청은 "처리할 일이 바뀐 신호"로 보지 않는다.
- 숫자 요청이 403 을 받으면, 같은 로그인(토큰)으로는 더 묻지 않는다. 쇼핑몰을 바꾸거나 다시 로그인해서 토큰이 바뀌면 한 번 다시 묻는다.

## 코드로 보기 (개념 재현)

```ts
// 1) 자동 복구: 상태 때문에 막힌 403 은 복구 대상이 아니다
const STATE_DENIED = new Set(["SHOP_UNAVAILABLE", "SHOP_PAUSED", "SHOP_CLOSED"]);

function isStateDenied(err: unknown): boolean {
  return err instanceof HttpError && err.status === 403 && STATE_DENIED.has(err.code ?? "");
}

async function withRetry<T>(call: () => Promise<T>): Promise<T> {
  try {
    return await call();
  } catch (err) {
    // 로그인이 풀린 경우만 되살린다. 상태 403 은 다시 열어도 같은 답이 온다
    if (err instanceof HttpError && (err.status === 401 || err.status === 403)
        && !isStateDenied(err) && (await reopenSession())) {
      return call();
    }
    throw err;
  }
}

// 2) 자동 새로고침: 로그인·세션 요청은 "할 일이 바뀐 신호"가 아니다
const SESSION_CALL = /^\/api\/(auth\/|login|logout|refresh|shops\/[^/]+\/session)/;

async function request(path: string, method = "GET") {
  const res = await send(path, method);
  if (method !== "GET" && !SESSION_CALL.test(path)) {
    refreshBadges();          // 0.4초 뒤 메뉴 숫자를 다시 센다
  }
  return res;
}

// 3) 숫자 요청: 403 을 받으면 같은 토큰으로는 다시 묻지 않는다
const deniedWith = new WeakMap<object, string | null>();   // 요청 함수 -> 거절당한 토큰

async function loadBadge(load: () => Promise<number>) {
  if (deniedWith.has(load) && deniedWith.get(load) === currentToken()) return; // 같은 토큰이면 멈춤
  try {
    const n = await load();
    deniedWith.delete(load);                  // 다시 되면 기록을 지운다
    return n;
  } catch (err) {
    if (err instanceof HttpError && err.status === 403) {
      deniedWith.set(load, currentToken());   // 토큰이 바뀌면 한 번 다시 묻는다
    }
  }
}
```

## 💡 배운 것

**각자 맞는 자동 기능도 만나면 고리가 됩니다.** "로그인이 풀리면 되살린다"와 "바꾸는 요청 뒤에는 숫자를 다시 센다"는 따로 보면 둘 다 맞아요. 되살리는 요청이 바꾸는 요청처럼 보이는 순간 서로를 불렀습니다.

**403 이라고 다 같은 403 이 아닙니다.** 로그인이 풀린 403 과 상태 때문에 막힌 403 은 대처가 달라요. 서버가 주는 오류 코드를 나눠 써야 했습니다.

**멈추는 조건에는 풀리는 조건도 같이 둡니다.** 403 뒤에 영영 안 물으면 쇼핑몰을 바꿔도 숫자가 안 떠요. 토큰이 바뀌면 다시 묻게 해서 둘 다 지켰습니다.

**화면이 멀쩡해도 네트워크 탭은 봅니다.** 사용자에게 안 보이는 반복 요청은 서버와 로그만 조용히 채웁니다.

## 소감

기능을 하나씩 만들 때는 각자 "언제 다시 부를지"만 생각했는데, 공통 요청 함수 안에서 그 규칙들이 서로 이어질 수 있다는 걸 이번에 처음 봤습니다. 자동으로 다시 부르는 코드를 쓸 때는 "이 호출이 또 다른 자동 호출을 부르지 않나"를 같이 확인하게 됐어요.

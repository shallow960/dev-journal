# 2026-09-23 오류율 5%가, 화면에서는 0.05%였다

> 태그: #트러블슈팅 #모니터링 #단위 #운영콘솔

## 무엇을 / 왜

운영 콘솔의 성능 화면이 "숫자는 많은데 보고도 문제인지 모르겠다"는 이야기를 들었습니다. 그래서 화면을 고치기 전에, 지금 찍히는 숫자가 맞는지부터 하나씩 확인해 봤습니다.

요약 칸에는 이렇게 떠 있었습니다.

```
측정 요청    13건
가장 느린 p95  15,538ms
오류율       NaN%
```

`NaN%` 는 누가 봐도 이상했습니다. 그런데 값이 제대로 나오는 경우도 계산 방식을 따라가 보니 문제가 있었어요.

## 어떻게 풀었나

### 서버가 주는 값부터 봤다

화면 코드를 보기 전에 서버가 이 값을 어떻게 계산하는지 찾아봤습니다.

```sql
sum(case when status_code >= 500 then 1 else 0 end)::decimal / count(*) as error_rate
```

500번대 응답 수를 전체 수로 나눈 값입니다. 결과는 **0에서 1 사이 비율**이에요. 100건 중 5건이 실패하면 `0.05` 가 옵니다.

### 화면은 그 값에 %만 붙이고 있었다

```tsx
<td>{endpoint.errorRate.toFixed(2)}%</td>
```

`0.05` 에 `%` 를 붙이니 `0.05%` 가 됐습니다. **실제 오류율 5%가 100배 작게** 보이고 있었어요.

색을 바꾸는 기준도 같은 착각 위에 있었습니다.

```tsx
const danger = endpoint.errorRate > 1;   // "1%보다 크면 빨강" 이라고 생각하고 쓴 줄
```

값이 비율이니 `1` 은 100%입니다. **모든 요청이 실패해도 색이 안 바뀌는** 기준이었어요. 오류가 급증해도 이 화면으로는 절대 알 수 없었습니다.

`NaN%` 는 샘플이 하나도 없는 경로가 섞였을 때 0으로 나누면서 생긴 값이었고요.

### 어디서 고칠까

방법은 두 가지였습니다.

| 방법 | 문제 |
|---|---|
| 서버가 퍼센트(0~100)로 주게 바꾼다 | 성능 알림 판정도 이 값을 쓴다. 한쪽만 바꾸면 알림 기준이 100배 어긋난다 |
| 화면에서 쓸 때마다 `* 100` 한다 | 쓰는 곳이 여러 군데다. 하나만 빠뜨려도 다시 틀린다 |

그래서 **화면이 데이터를 받아 오는 곳 한 군데에서만** 퍼센트로 바꾸기로 했습니다. 그 뒤로는 모든 화면이 "이 값은 퍼센트"라는 전제 하나로 씁니다.

### 비슷한 칸을 더 찾아봤다

한 칸이 거짓말을 하고 있었으니 다른 칸도 의심해 봤습니다. 몇 개가 더 나왔어요.

- **"요청" 칸** - 실제 요청 수가 아니라 **20%만 저장한 샘플 수**였습니다. 이름을 "샘플"로 바꾸고 안내를 붙였습니다.
- **"Redis 소요 시간" 막대** - 기록하는 함수가 있는데 **부르는 곳이 한 군데도 없어서** 항상 0이었습니다. 0을 "정상"으로 읽게 두면 안 돼서 차트에서 뺐습니다.
- **느린 쿼리의 p95, p99** - 둘이 항상 같은 숫자였는데, 저장할 때 큰 값으로 덮어써서 **실제로는 둘 다 최댓값**이었습니다. 이름을 "최대"로 바꿨습니다.
- **오류 화면의 "영향 사용자"** - 수집할 때 사용자 정보를 넣지 않아서 **항상 0명**이었습니다. "0명"은 "아무도 영향 없음"으로 읽히니 "집계하지 않음"으로 바꿨습니다.

## 코드로 보기 (개념 재현)

받아 오는 곳에서 한 번만 바꿉니다.

```ts
/** 서버는 0~1 비율을 준다. 화면에서는 이 함수를 거친 뒤 퍼센트(0~100)로만 쓴다. */
function toPercent(ratio: number | null | undefined): number | null {
  if (ratio == null || !Number.isFinite(ratio)) return null;   // NaN 이 화면까지 가지 않게
  return ratio * 100;
}

export async function getEndpoints() {
  const rows = await fetchEndpoints();
  return rows.map((row) => ({ ...row, errorRate: toPercent(row.errorRate) }));
}
```

기준도 퍼센트로 다시 잡았습니다. 성능 알림의 기본값이 5%라서 거기에 맞췄어요.

```ts
function gradeAbove(value: number, warnAt: number, badAt: number) {
  if (value >= badAt) return "bad";
  if (value >= warnAt) return "warn";
  return "ok";
}

const level = gradeAbove(endpoint.errorRate, 1, 5);   // 1% 주의, 5% 위험
```

그리고 숫자 옆에 **기준을 같이 적었습니다.** 색만 바뀌면 왜 빨간지 모르니까요.

```tsx
<Metric
  label="오류율"
  value={percentText(errorRate)}
  level={gradeAbove(errorRate, 1, 5)}
  standard="1% 넘으면 주의, 5% 넘으면 위험"
/>
```

## 💡 배운 것

**숫자를 보여 주기 전에 단위부터 맞춥니다.** 비율과 퍼센트는 같은 뜻을 100배 차이로 나타냅니다. 이름이 `errorRate` 하나라서 어느 쪽인지 코드만 봐서는 알 수 없었어요. 그래서 이제는 변환한 곳에 "이 값은 퍼센트"라고 주석으로 못 박아 둡니다.

**여러 곳이 쓰는 값은 경계에서 한 번만 바꿉니다.** 서버를 바꾸면 알림이 틀어지고, 화면 곳곳에서 바꾸면 하나를 빠뜨립니다. 들어오는 입구 하나에서 바꾸는 게 안전했습니다.

**항상 같은 값이 나오는 칸을 의심합니다.** 항상 0, 항상 두 값이 똑같음, 항상 초록. 이런 칸은 대부분 계산이 안 되고 있는 거였습니다.

**색만 바꾸지 말고 기준을 적습니다.** 빨간색을 봐도 기준을 모르면 판단할 수가 없습니다. 기준값을 같이 적어 두니, 이상한 기준(100%)도 화면만 보고 바로 알아챌 수 있게 됐습니다.

## 소감

처음 들은 요청은 "직관적으로 보이게" 해 달라는 거였습니다. 막상 들여다보니 보기 불편한 게 문제가 아니라 **숫자 자체가 틀린 곳**이 먼저였어요. 틀린 숫자를 예쁘게 정리했다면 더 그럴듯하게 틀린 화면이 됐을 겁니다.

화면을 꾸미기 전에 값이 맞는지부터 확인하는 순서가 맞았다는 걸 이번에 배웠습니다.

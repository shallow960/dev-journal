# 2026-10-20 커밋 전 검사가, 이 PC 에서는 한 번도 돌지 않았다

> 태그: #트러블슈팅 #git #훅 #개발환경 #줄바꿈

## 무엇을 / 왜

인수받은 저장소에는 git 훅이 들어 있었습니다. 커밋하기 전에 충돌 표시·비밀값·코드 검사(lint)를 돌리고, push 하기 전에는 교차 리뷰를 돌리는 훅이에요. 저장소의 작업 규칙 문서에도 "훅으로 강제한다" 고 적혀 있었습니다.

그런데 훅 설정을 보다가 이상한 걸 찾았어요.

```bash
$ git config --get core.hooksPath
$                                  # 빈 값
```

훅 파일은 저장소 안의 별도 폴더에 있고, git 이 그 폴더를 보게 하려면 git 설정(`core.hooksPath`)에 적어야 합니다. 이 설정은 **저장소 파일이 아니라 저장소를 받은 폴더마다 `.git/config` 에 따로 두는 로컬 설정**이라 clone 해도 따라오지 않아요(같은 PC 라도 새로 clone 하면 다시 켜야 해요). 이 저장소는 그 설정을 "개발 도구를 이 저장소 폴더에서 열 때" 켜 주는 시작 스크립트에 맡겨 두었는데, 저는 다른 폴더에서 작업을 시작하고 있었습니다. 직접 켜는 설정 스크립트도 있었지만 돌린 적이 없었고요.

결과적으로 인수받은 뒤 이 PC 에서 한 커밋은 **전부 검사 없이** 들어갔습니다.

## 어떻게 풀었나

1. **켜고, 지난 것을 다시 봤습니다.** 설정 스크립트로 훅을 켜고, 그사이 바뀐 화면 코드 파일 12개를 다시 검사했어요. 통과였습니다.
2. **실제로 걸렸던 일을 막는 검사를 더했어요.**
   - 리눅스 서버에서 도는 파일(.sh, 서비스 설정, .conf, Dockerfile)에 윈도우 줄바꿈(CR)이 섞이면 막기
   - 셸 스크립트 문법 검사(`bash -n`)
   - 줄 끝 공백과 파일 끝 빈 줄 막기(문서 끝 빈 줄 하나가 커밋한 뒤에야 발견된 일이 있었어요)
   - 기능 브랜치에서 계획 문서 없이 코드를 커밋하면 막기(급할 때 쓰는 우회 값은 두고, 쓰면 사유를 남기게)

   검사는 작업 폴더의 파일이 아니라 **스테이징된 내용**(실제로 커밋될 내용)을 봅니다. 일부만 add 했거나, git 이 줄바꿈을 바꿔 저장하면 둘이 다를 수 있거든요.
3. **일부러 틀려 보며 시험했습니다.** 버리는 작업 폴더를 따로 만들어, 막혀야 하는 경우(잘못된 파일)와 통과해야 하는 경우(문서만 바꾼 커밋, 우회 값 등)를 합쳐 19가지를 돌렸어요. 모두 기대대로 막히거나 통과했습니다.

그런데 시험 하나가 이상했어요. 이 저장소는 이런 파일을 LF 로 고정해 둬서, 그냥 add 한 CRLF 는 git 이 LF 로 바꿔 통과합니다. 그래서 줄바꿈 변환을 건너뛰고 CR 을 그대로 스테이징해 봤더니, "CR 이 있다" 가 아니라 **"trailing whitespace(줄 끝 공백)"** 로 막혔어요. 공백 검사(`git diff --check`)가 줄 끝의 CR 도 공백으로 보기 때문이에요. 막히긴 하지만 원인이 흐려지니, 구체적인 CR 검사를 공백 검사보다 앞에 두었습니다.

## 코드로 보기 (개념 재현)

```bash
#!/usr/bin/env bash
# 개념 재현: 경로와 파일 이름은 모두 더미다.

# 1) 훅이 실제로 켜져 있는지부터 본다. 비어 있으면 저장소에 훅이 있어도 돌지 않는다.
git config --get core.hooksPath || echo "(비어 있음: 훅이 돌지 않는다)"

# 2) 스테이징된 내용(커밋될 내용)에 CR 이 몇 개 있는지 센다. 작업 폴더 파일이 아니다.
#    ":경로" 는 스테이징된 내용을 뜻한다. -z 로 받아 이름에 공백이 있어도 안전하다.
git diff --cached --name-only -z --diff-filter=ACMR |
while IFS= read -r -d '' f; do
  case "$f" in
    *.sh|*.service|*.conf|Dockerfile*|*/Dockerfile*) ;;  # 리눅스에서 도는 파일만
    *) continue ;;
  esac
  cr=$(git show ":$f" | tr -cd '\r' | wc -c)              # CR 만 남겨 센다
  [ "$cr" -eq 0 ] || echo "CR ${cr}개: $f"
done
```

줄바꿈 변환을 끈 임시 저장소(core.autocrlf=false, .gitattributes 없음)에서 돌려 본 결과입니다. 윈도우용 git 기본값(core.autocrlf=true)이나 LF 고정 규칙이 있으면 add 할 때 CR 이 빠져서 아무것도 나오지 않아요.

```text
(비어 있음: 훅이 돌지 않는다)
CR 2개: a.sh
CR 1개: deploy/Dockerfile.app

$ git diff --cached --check -- a.sh      # 같은 파일을 공백 검사로 보면
a.sh:1: trailing whitespace.
+#!/bin/sh
a.sh:2: trailing whitespace.
+echo hi
```

## 💡 배운 것

**git 훅은 저장소에 넣는 것만으로는 돌지 않는다는 걸 배웠습니다.** 훅 경로 설정은 clone 한 저장소마다 따로 두는 로컬 설정이라 clone 에 따라오지 않아요. 켜는 일을 특정 도구의 시작에 맡기면, 그 도구를 다른 곳에서 여는 순간 꺼진 채로 갑니다.

**"있다" 와 "돈다" 는 다르다는 걸 다시 배웠습니다.** 2026-08-13 에 코드가 있어도 부르는 곳이 없으면 아무 일도 안 한다는 걸 배웠는데, 검사도 똑같았어요. 이제 새 PC 나 새 작업 폴더에서는 훅 설정부터 확인합니다.

**같은 문제를 여러 검사가 잡으면, 구체적인 검사를 앞에 둔다는 걸 다시 배웠습니다.** CR 은 공백 검사에도 걸리지만 "trailing whitespace" 라는 말로는 원인을 알기 어려워요. 2026-09-28 에 넓게 잡는 처리기가 구체적인 처리기보다 먼저 잡아 엉뚱한 응답이 나간 일을 겪었는데, 검사 순서도 같았습니다. 원인을 정확히 말해 주는 검사가 먼저 걸리게 순서를 정했어요.

**검사는 커밋될 내용을 봐야 한다는 걸 배웠습니다.** 작업 폴더의 파일과 스테이징된 내용은 다를 수 있어서, `git show ":경로"` 로 커밋될 내용을 직접 읽었어요.

## 소감

검사가 "있다" 는 걸 보고 안심하고 있었는데, 정작 한 번도 돌지 않았다는 게 머쓱했습니다. 안전장치는 켜져 있는지까지 확인해야 안전장치라는 걸 이번에 몸으로 배웠어요.

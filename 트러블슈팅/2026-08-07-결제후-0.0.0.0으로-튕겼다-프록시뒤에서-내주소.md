# 2026-08-07 결제를 마치니 0.0.0.0:3000으로 튕겼다 - 프록시 뒤에서 "내 주소"를 스스로 믿으면 안 된다

> 태그: #트러블슈팅 #리버스프록시 #Next.js #배포환경

## 오늘 한 일 (요약)
- 카드 결제창에서 결제를 마치자 브라우저가 `https://0.0.0.0:3000/...` 으로 이동하며 `ERR_ADDRESS_INVALID`.
- 원인은 서버가 리다이렉트 주소를 만들 때 **요청 URL의 origin**을 그대로 쓴 것. 프록시 뒤라 그게 내부 바인드 주소였다.
- 브라우저로 되돌릴 주소는 `x-forwarded-*` 헤더로 **공개 주소를 복원**해 만들도록 고쳤다.
- 같은 origin으로 나가던 내부 API 호출도 분리했다. 결과가 왜곡되고 있었다.

## 무엇을 / 왜 (증상)
결제사 인증창은 결과를 **브라우저 폼 POST**로 우리 서버에 보낸다. 우리는 그걸 받아 승인 처리하고, 사용자를 원래 화면으로 되돌린다.

그 되돌리는 코드가 이랬다.

```ts
// 요청 URL에서 origin을 뽑아 리다이렉트 주소를 만든다
const url = new URL(request.url);
return NextResponse.redirect(new URL(`/console/billing?...`, url.origin), 303);
```

로컬에선 잘 됐다. 그런데 배포 환경은 이렇게 생겼다.

```
브라우저 -> [Caddy: molida.co:443] -> [Next 컨테이너: 0.0.0.0:3000] -> [백엔드 컨테이너]
```

컨테이너 안의 Next는 자기가 `0.0.0.0:3000`에 떠 있다고 알고 있다. 그래서 `request.url`의 origin도 그 내부 주소가 된다. 그 주소로 리다이렉트를 만들어 브라우저에 주면, 브라우저는 당연히 `0.0.0.0`에 접속하지 못한다.

**더 나쁜 건 따로 있었다.** 승인 결과를 확인하러 가는 내부 호출도 같은 origin을 쓰고 있었다.

```ts
await fetch(`${url.origin}/api/v1/.../callback`, { ... }); // 오염된 주소로 나감
```

이 fetch가 실패하면 코드상 결과는 "결제 실패"로 처리된다. 즉 **실제 결제 결과와 무관하게 실패로 보이는** 상태였다. 화면의 "실패"를 믿고 카드사 문제로 의심하고 있었으니, 원인 추적이 한 단계 더 꼬였다.

## 어떻게 풀었나
용도를 둘로 갈랐다. **브라우저에게 줄 주소**와 **서버끼리 부를 주소**는 서로 다른 것이다.

```ts
// 브라우저용: 프록시가 알려준 원래 요청 주소를 복원한다
function publicOrigin(request: NextRequest): string {
  const proto = request.headers.get("x-forwarded-proto") ?? "https";
  const host =
    request.headers.get("x-forwarded-host") ??
    request.headers.get("host") ??
    new URL(request.url).host;
  return `${proto}://${host}`;
}

// 서버 내부 호출용: 프록시를 거치지 않고 백엔드를 직접 부른다
const apiBase = process.env.NEXT_PUBLIC_API_BASE_URL ?? new URL(request.url).origin;
await fetch(`${apiBase}/api/v1/.../callback`, { ... });

// 되돌아갈 주소는 공개 origin으로
return NextResponse.redirect(new URL(path, publicOrigin(request)), 303);
```

리버스 프록시는 원래 요청 정보를 `x-forwarded-host` / `x-forwarded-proto` 로 전달해 준다. 브라우저에게 줄 주소는 이걸로 만들어야 맞다.

여기에 하나 더 했다. **실패 사유를 쿼리로 실어 화면에 표시**하게 한 것. 이 덕분에 "왜 실패인지"가 보였고, 뒤이어 다른 원인(테넌트 해석에 막혀 승인 자체가 실행되지 않던 문제)까지 잡을 수 있었다.

## 같은 버그가 옆에도 있었다
고치고 나서 비슷한 경로를 찾아봤더니, **카드 등록 콜백 라우트도 완전히 같은 코드**였다. 아직 증상이 안 났을 뿐 같은 조건이면 똑같이 깨진다. 함께 고쳤다.

한 곳에서 발견한 환경 의존 버그는 **같은 패턴을 쓰는 다른 곳도 반드시 확인**해야 한다.

## 💡 배운 것
- **프록시 뒤에서는 서버가 아는 "내 주소"가 진짜 주소가 아니다.** 로컬에서 안 드러나고 배포에서만 터지는 전형적인 케이스.
- 브라우저에게 줄 주소(공개 origin)와 서버 내부 호출 주소(컨테이너 내부)는 **목적이 다르니 따로 만든다.**
- 실패 처리를 뭉뚱그리면(`catch { paid = false }`) **환경 문제와 도메인 실패가 구분되지 않는다.** 사유를 남기게 해야 한다.
- 환경 의존 버그를 잡았으면 **동일 패턴의 다른 경로를 즉시 훑는다.**

## 소감
"내 컴퓨터에선 되는데" 계열 중에서도 꽤 헷갈리는 종류였다. 코드에는 하드코딩된 주소가 하나도 없는데 결과적으로 잘못된 주소가 나왔으니까. 컨테이너와 프록시를 끼고 배포하면 애플리케이션이 자기 주소를 스스로는 모른다는 걸, 이번에 확실히 몸으로 배웠다.

## 무엇을 / 왜

부가세 신고 화면을 만들고 있었습니다. 백엔드를 다 짜고 브라우저에서 눌러 봤더니 **500** 이 떴어요.

방금 짠 코드니까 당연히 제 잘못이라고 생각했습니다. 쿼리를 데이터베이스에서 직접 돌려 봤더니 잘 됩니다. 숫자도 맞아요. 그런데 화면에서는 500 입니다.

한참을 헤매다가, 혹시나 해서 **원래 있던 정산 API** 를 눌러 봤습니다.

```
/api/v1/cms/settlement/accounts   500
/api/v1/cms/settlement/vat        500
```

제가 안 만든 것도 500 이었습니다.

## 어떻게 풀었나

### 로그에 없던 이유가 DB 에 있었다

서버 로그를 뒤졌는데 우리 코드의 흔적이 없었습니다. 다른 잡음만 잔뜩이었어요.

그러다 생각났습니다. 우리가 몇 달 전에 **오류 수집 기능**을 만들어 뒀다는 걸요. 처리되지 않은 예외를 잡아서 DB 표에 쌓아 두는 장치입니다. 운영 중에 무슨 오류가 났는지 화면으로 보라고 만든 건데, 그게 지금 제 문제를 그대로 물고 있었습니다.

```sql
select message, stacktrace
from error_events
where dimensions->>'path' like '%settlement%'
order by occurred_at desc limit 1;
```

한 줄이 나왔습니다.

```
Incorrect result size: expected 1, actual 2
  at CmsStaffAuthzInterceptor.membershipRole(...)
  at CmsStaffAuthzInterceptor.preHandle(...)
```

**하나를 기대했는데 둘이 왔다.** 그리고 위치가 제 코드가 아니라 **권한 검사기** 였습니다.

우리가 만든 오류 수집 기능이 우리 디버깅에 그대로 쓰인 게 좀 웃겼습니다. 만들 때는 "운영에서 손님이 겪는 오류를 보려고" 만든 건데요.

### 한 사람에게 멤버십이 둘일 수 있었다

검사기가 하는 일은 단순합니다. 정산·결제 같은 민감한 화면은 **실무자 등급은 못 들어가게** 막는 거예요. 그래서 이 사람의 역할을 하나 꺼내 봅니다.

```
select role from 멤버십
where 스토어 = ? and 사용자 = ?
```

그리고 결과가 딱 하나일 거라고 가정했습니다.

그런데 이 표의 기본키는 **(계정, 스토어)** 였습니다. 조회는 **사용자** 로 하고요.

```
기본키   (계정, 스토어)     ← 이 조합이 유일하다
조회     (스토어, 사용자)   ← 이건 유일하다고 보장한 적이 없다
```

한 사람이 계정 두 개로 같은 스토어에 묶이면 두 줄이 나옵니다. 실제로 제 로컬이 그랬어요. 전날 요금제 기능을 시험하려고 테스트 계정을 하나 만들면서, 스토어 사용자를 새로 만들지 않고 기존 것을 그대로 갖다 붙였거든요.

그 순간부터 **정산 화면 전체가 500** 이 됐습니다.

### 검사기라서 더 나빴다

이게 평범한 화면 코드였으면 그 화면 하나만 안 열렸을 겁니다. 그런데 이건 **요청이 컨트롤러에 닿기 전에 먼저 도는** 장치예요.

```
요청 → [권한 검사기] → 컨트롤러
         여기서 터짐      여기까지 오지도 못함
```

그래서 그 아래에 있는 API 가 **전부** 죽습니다. 그런데 컨트롤러를 아무리 들여다봐도 원인이 없어요. 제가 새 API 만 의심하면서 시간을 보낸 것도 그래서였습니다.

### 고친 방법 - 질문을 바꿨다

처음엔 "두 줄이면 하나만 골라 쓰자" 로 갈 뻔했습니다. 그런데 그러면 **어느 걸 고를지** 를 또 정해야 해요.

생각해 보니 이 검사기가 원래 알고 싶은 건 역할이 아니었습니다.

```
전    "이 사람의 역할이 뭐지?"        → 한 줄이어야 답할 수 있다
후    "이 사람이 실무자로만 묶였나?"  → 몇 줄이든 답할 수 있다
```

`bool_and(role = '실무자')` 한 줄로 바뀌었습니다. 집계라서 결과가 항상 한 줄이고, 여러 줄이면 **하나라도 실무자가 아니면 통과** 시킵니다.

여기서 한 가지 더 고민했습니다. 보통 권한을 판단할 때 애매하면 **막는 쪽** 이 안전합니다. 그런데 이 검사기는 반대였어요. 모두를 막는 장치가 아니라 **실무자만 골라 막는** 장치입니다. 애매할 때 막아 버리면, 오너가 자기 스토어의 정산 화면에서 잠깁니다.

그래서 여기서는 높은 권한을 따르게 했습니다. 안전한 방향이 항상 같은 쪽은 아니라는 걸 처음 실감했습니다.

시험도 같이 썼습니다. 한 사람에게 멤버십을 두 줄 만들어 두고 **한 줄일 때와 응답이 같은지** 를 봅니다. 고치기 전 코드로 되돌려서 이 시험이 실패하는 것까지 확인했어요.

## 덤 - 메뉴가 두 개씩 켜져 있었다

500 을 고치고 나니 화면이 떴습니다. 그런데 이번엔 제목이 이상했어요. **부가세 화면인데 제목이 "정산"** 입니다.

```
/cms/settlements       ← 정산
/cms/settlements/vat   ← 부가세
```

지금 어느 페이지인지 찾는 코드가 **앞에서부터 뒤져서 주소가 겹치면 먼저 나온 걸** 골랐습니다. `/cms/settlements/vat` 는 `/cms/settlements` 로 시작하니까, 정산이 부가세를 자기 것으로 가져간 거예요.

가장 구체적인 주소가 이기게 바꿨습니다. 그리고 경계를 `/` 로 봤습니다. 안 그러면 `/cms/goods` 가 `/cms/goods-list` 같은 걸 자기 하위로 삼거든요.

그런데 이걸 고치고 나서 운영 콘솔을 보다가 같은 걸 또 봤습니다. 왼쪽 메뉴에서 **"오류 알림"을 눌렀는데 "오류"도 같이 켜져** 있었어요.

원인이 같았습니다. 메뉴마다 각자 "지금 주소가 내 주소로 시작하나?" 를 묻고 있었거든요. 그러면 상위 메뉴는 하위 화면에서도 늘 참입니다.

```
지금 주소   /ops/errors/alerts

"오류"     내 주소(/ops/errors)로 시작하나? → 켠다
"오류 알림" 내 주소로 시작하나? → 켠다        ← 둘 다 켜짐
```

메뉴마다 따로 판단하지 말고, **지금 페이지를 하나 뽑아 두고 그것만 켜게** 했습니다. 뽑는 규칙은 앞에서 고친 것과 같은 규칙이고요. 그러니까 결국 한 군데서 한 번만 정하면 되는 일이었습니다.

## 배운 것

**"하나겠지" 는 가정이지 사실이 아닙니다.** 오늘 두 번 같은 실수를 봤어요. 멤버십이 하나일 거라는 가정, 주소에 맞는 메뉴가 하나일 거라는 가정. 둘 다 평소엔 맞다가 어느 순간 둘이 됩니다.

특히 데이터베이스는 **기본키로 정한 것만** 유일하다고 보장합니다. 기본키가 (계정, 스토어) 인데 (스토어, 사용자) 로 찾으면서 하나를 기대한 건 근거가 없었어요. 앞으로 한 줄을 꺼내는 코드를 쓸 때는 "이 조합이 유일하다고 누가 보장하지?" 를 한 번 물어봐야겠습니다.

**질문을 바꾸면 문제가 사라지기도 합니다.** "역할이 뭐야"는 한 줄이어야 답할 수 있는 질문이었고, "실무자로만 묶였어?"는 몇 줄이든 답할 수 있는 질문이었습니다. 예외 처리를 덧붙이는 대신 묻는 방식을 바꾸니까 애초에 터질 자리가 없어졌어요.

**요청 앞단에서 도는 코드는 고장 범위가 넓습니다.** 컨트롤러 하나가 아니라 그 아래 전부가 죽는데, 정작 컨트롤러를 봐도 아무것도 안 보입니다. 어떤 API 하나가 이상할 땐 그 코드를 보지만, **여러 개가 한꺼번에 이상하면** 공통으로 지나가는 길목부터 봐야 한다는 걸 배웠습니다.

**만들어 둔 게 나를 살렸습니다.** 로그에서 못 찾은 스택트레이스가 오류 수집 표에 그대로 있었어요. 운영에서 손님이 겪는 오류를 보려고 만든 건데, 정작 오늘은 제가 제 버그를 찾는 데 썼습니다. 다음부터는 500 이 나면 로그보다 이 표를 먼저 열어야겠습니다.

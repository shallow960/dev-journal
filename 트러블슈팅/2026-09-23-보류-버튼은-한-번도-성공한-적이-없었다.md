# 2026-09-23 보류 버튼은, 한 번도 성공한 적이 없었다

> 태그: #트러블슈팅 #DB제약 #상태전이 #운영콘솔

## 무엇을 / 왜

운영 콘솔에는 서버 오류를 비슷한 것끼리 묶어서 보여 주는 화면이 있습니다. 묶음마다 상태를 바꾸는 버튼이 세 개 있어요.

- **해결 처리** - 고쳤다
- **보류** - 지금은 못 보니 잠시 미뤄 둔다
- **무시** - 신경 쓸 필요 없다

오류 화면을 정리하면서 버튼마다 화면이 보내는 값과 서버가 받는 값을 맞춰 봤습니다. 해결과 무시는 맞았는데, **보류는 누르면 빨간 박스**가 뜨는 구조였습니다.

```
ops fetch failed: errors/groups/9f2e... (500)
```

영어 기술 메시지가 그대로 나온 것도 문제였지만, 우선 왜 500인지가 궁금했습니다.

## 어떻게 풀었나

### 서버 코드와 DB 규칙을 따라갔다

서버가 상태를 바꾸는 코드를 따라가 보니 보류 기한 칸을 비운 채로 저장하고 있었습니다. 그렇게 저장하면 DB가 이런 오류를 냅니다.

```
ERROR: new row for relation "error_groups" violates check constraint
       "ck_error_groups_snooze_status"
```

데이터베이스의 **검사 제약**에 걸린 겁니다. 테이블을 만들 때 걸어 둔 규칙이 이랬습니다.

```sql
constraint ck_error_groups_snooze_status
    check (status <> 'snoozed' or snooze_until is not null)
```

"보류 상태라면 **언제까지 보류인지** 반드시 적혀 있어야 한다"는 규칙입니다. 기한 없는 보류는 사실상 무시와 같으니까, 처음 설계할 때 이렇게 막아 둔 거였어요.

### 화면은 기한을 보내지 않았다

버튼이 보내는 요청을 보니 이랬습니다.

```ts
await patchGroup(id, { status: "snoozed", reason });   // snoozeUntil 이 없다
```

서버는 받은 값 그대로 상태를 바꾸는데, 기한이 없으니 `snooze_until` 이 비어 있는 채로 저장하려다 제약에 걸렸습니다. 서버 API는 기한을 받을 준비가 돼 있었는데, **화면에 기한을 고르는 칸이 아예 없었어요.**

즉 이 버튼은 **만들어진 뒤로 한 번도 성공한 적이 없는** 버튼이었습니다.

### 규칙은 그대로 두고 화면을 맞췄다

제약을 풀면 버튼은 바로 동작합니다. 하지만 그러면 "기한 없는 보류"가 쌓이고, 그건 처음 설계에서 막으려던 바로 그 상황이에요. 규칙이 맞고 화면이 틀린 거라 **화면 쪽을 고쳤습니다.**

- 보류를 누르면 **1일 / 3일 / 7일** 중 기한을 고르게 했습니다.
- 보류 중인 묶음에는 **"○월 ○일까지 보류 중"** 을 표시했습니다. 서버는 이 값을 이미 주고 있었는데 화면이 안 쓰고 있었어요.

### 해결 처리에도 숨은 규칙이 있었다

같이 보다가 하나 더 알게 됐습니다. "해결 처리"를 눌러도 **같은 오류가 한 번만 더 나면 다시 미해결로 돌아옵니다.** 어느 릴리스에서 고쳤는지를 적어야 그 뒤의 발생만 새 문제로 보는데, 화면에 그 칸이 없었어요.

이건 버그라기보다 규칙인데 화면에 설명이 없던 경우였습니다. "해결한 릴리스" 입력칸을 붙이고, 비워 두면 다시 열린다는 안내를 적었습니다.

### 영어 메시지도 걸렀다

빨간 박스에 뜬 `ops fetch failed: ...` 는 서버와 통신하는 공용 함수가 던지는 개발자용 메시지입니다. 여러 화면이 같이 쓰는 함수라 거기는 건드리지 않고, 이 화면의 버튼 처리에서 **기술 메시지를 걸러 한국어 안내로 바꾸도록** 했습니다.

## 코드로 보기 (개념 재현)

고치기 전입니다.

```ts
export async function snooze(id: string, reason: string) {
  try {
    await patchGroup(id, { status: "snoozed", reason });
    return { ok: true };
  } catch (error) {
    return { ok: false, message: (error as Error).message };   // 영어가 그대로 나간다
  }
}
```

고친 뒤입니다.

```ts
const SNOOZE_DAYS = [1, 3, 7] as const;

export async function snooze(id: string, reason: string, days: number) {
  const safeDays = SNOOZE_DAYS.includes(days as 1 | 3 | 7) ? days : 1;
  const snoozeUntil = new Date(Date.now() + safeDays * 24 * 60 * 60 * 1000).toISOString();
  try {
    // DB 제약: 보류라면 기한이 반드시 있어야 한다. 기한 없이 보내면 500이 난다.
    await patchGroup(id, { status: "snoozed", reason, snoozeUntil });
    return { ok: true };
  } catch (error) {
    return { ok: false, message: friendlyMessage(error) };
  }
}

/** 공용 통신 함수의 영어 기술 메시지는 화면에 내보내지 않는다. */
function friendlyMessage(error: unknown): string {
  const raw = error instanceof Error ? error.message : "";
  if (/unauthorized/i.test(raw)) return "로그인이 만료됐습니다. 다시 로그인해 주세요.";
  if (/\(5\d\d\)/.test(raw)) return "서버에서 처리하지 못했습니다. 잠시 후 다시 시도해 주세요.";
  return "처리하지 못했습니다. 잠시 후 다시 시도해 주세요.";
}
```

## 💡 배운 것

**화면 메시지 대신 요청이 가는 길을 따라갑니다.** 화면 메시지는 "실패했다"는 것만 알려 줍니다. 요청이 서버를 거쳐 DB까지 가는 길을 따라가니, 테이블에 걸린 규칙 한 줄에 원인이 있었어요.

**DB 제약은 설계자가 남긴 규칙입니다.** 제약에 걸렸을 때 제약을 푸는 게 제일 빠르지만, 그 제약이 왜 있는지부터 봐야 합니다. 이번에는 규칙이 맞고 화면이 규칙을 몰랐던 경우였습니다.

**서버가 받을 수 있는 값과 화면이 보내는 값을 맞춰 봅니다.** API는 기한을 받을 준비가 돼 있었고, 보류 기한을 돌려주기까지 했는데 화면이 둘 다 안 쓰고 있었어요. 기능이 백엔드에만 있고 화면에서 끊긴 경우는 생각보다 흔했습니다.

**버튼마다 보내는 값을 하나씩 확인합니다.** 세 버튼 중 두 개가 맞으니 세 번째도 맞을 거라고 넘어갔다면 계속 몰랐을 겁니다.

## 소감

누군가 이 버튼을 눌렀다가 빨간 영어 메시지를 보고 그냥 넘어간 적이 분명 있었을 것 같습니다. 오류를 관리하는 화면에서 오류가 나고 있었다는 게 좀 웃기기도 했어요.

고치고 나니 버튼 하나가 제대로 동작하게 된 것보다, 해결 처리가 다시 열리는 규칙처럼 **화면이 말해 주지 않던 규칙**을 같이 찾은 게 더 쓸모 있었다고 생각합니다.

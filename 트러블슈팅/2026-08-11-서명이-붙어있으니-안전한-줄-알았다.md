# 2026-08-11 서명이 붙어 있으니 안전한 줄 알았다 - 40만원짜리를 1,000원에 살 수 있었다

> 태그: #트러블슈팅 #결제연동 #보안 #NICEPAY

## 오늘 한 일 (요약)
- 결제 코드를 다시 읽다가, 결제창을 여는 주소에 **금액이 그대로 적혀 있는 것**을 봤다.
- 로그인도 필요 없는 공개 주소라, 숫자만 바꾸면 40만원짜리 서비스를 1,000원에 살 수 있었다.
- 결제창 정보에는 **위변조 방지 서명**이 이미 붙어 있었다. 그래서 안전한 줄 알았는데 아니었다.
- 금액을 아예 받지 않도록 바꿨다. 클라이언트는 **상품 코드만** 보낸다.

## 문제의 코드

1회성 서비스(기능 추가 40만원 / 디자인 변경 20만원)를 결제하는 흐름이다.

```ts
// 프론트엔드
const query = new URLSearchParams({
  amount: String(service.price),   // 400000
  goodsName: service.name
});
await apiFetch(`/api/v1/.../public-auth-window?${query}`);
```

```java
// 백엔드 - 받은 금액을 그대로 결제창 파라미터로
public AuthWindow authWindowParams(long amount, String goodsName) {
    String amt = Long.toString(Math.max(1, amount));
    String signData = sha256Hex(ediDate + mid + amt + merchantKey);  // 서명

    params.put("Amt", amt);
    params.put("SignData", signData);
    ...
}
```

`curl` 한 번이면 끝난다.

```bash
curl "https://.../public-auth-window?amount=1000&goodsName=기능%20추가"
```

## 왜 "서명이 있으니 안전하다"가 틀렸나

여기가 내가 헷갈린 지점이다.

이 결제 방식에는 `SignData` 라는 값이 붙는다. `금액 + 상점ID + 시각 + 상점키`를 해시한 값이고, 결제사는 이걸로 **"결제창을 띄운 뒤에 누가 금액을 바꿔치기했는지"** 를 잡아낸다. 상점키는 서버에만 있으니 브라우저에서 위조할 수 없다.

그래서 안전하다고 생각했다. 그런데 서명이 보장하는 건 이것뿐이다.

```
서명이 보장하는 것      : 만들어진 뒤로 바뀌지 않았다
서명이 보장하지 않는 것 : 애초에 무엇으로 만들었는가
```

내 서버는 `amount=1000` 을 받아서 **1,000원짜리 서명을 성실하게 만들어줬다.** 위조가 아니라 정식 발급이다. 결제사 입장에서는 아무 문제가 없는 요청이다.

무결성(integrity)과 진정성(authenticity)은 다른 문제인데, 서명이 앞의 것만 해결해 준다는 걸 놓쳤다.

## 고친 방법

금액을 받는 것 자체를 없앴다. 클라이언트는 **무엇을 사는지**만 말하고, **얼마인지**는 서버가 정한다.

```java
public enum OneTimeServiceCatalog {
    FEATURE("feature", "기능 추가", 400_000L),
    DESIGN("design", "디자인 변경", 200_000L);

    /** 알 수 없는 코드는 결제창 자체를 만들지 않는다(임의 금액 결제 차단). */
    public static OneTimeServiceCatalog require(String code) {
        return find(code).orElseThrow(() ->
            new ResponseStatusException(HttpStatus.BAD_REQUEST, "판매하지 않는 서비스예요."));
    }
}
```

```java
@GetMapping("/.../public-auth-window")
public ApiResponse<AuthWindow> singlePayPublicAuthWindow(
    @RequestParam(name = "service") String serviceCode   // amount 파라미터 제거
) {
    OneTimeServiceCatalog service = OneTimeServiceCatalog.require(serviceCode);
    return ApiResponse.ok(nicePaySinglePayService.authWindowParams(service));
}
```

확인:

```bash
# 예전 방식 -> 400 (amount 로는 결제창을 못 만든다)
curl -o /dev/null -w "%{http_code}" ".../public-auth-window?amount=1000"

# 정상 -> 서버가 정한 400000
curl ".../public-auth-window?service=feature"
#   "Amt": "400000",  "GoodsName": "기능 추가"
```

## 구매자 정보는 왜 그대로 받았나

같이 넣은 `BuyerName`·`BuyerEmail`·`BuyerTel` 은 **클라이언트에서 받는다.** 금액은 안 되는데 이건 되는 이유를 스스로 정리해 봤다.

기준은 **위조됐을 때 누가 손해를 보는가** 였다.

| 값 | 위조되면 | 결론 |
|---|---|---|
| 금액 | 우리가 40만원 대신 1,000원을 받는다 | 서버가 정한다 |
| 구매자 이름·연락처 | 영수증에 이상한 이름이 찍힌다(본인 손해) | 받아도 된다 |

"클라이언트 입력은 다 못 믿는다"가 아니라, **못 믿어서 곤란해지는 게 누구인지**를 보면 나눌 수 있었다.

## 되짚어 보면

사실 이 프로젝트에서 **같은 실수를 전에도 했다.** 손님 쇼핑몰 장바구니에서 클라이언트가 보낸 상품 가격을 그대로 주문 금액으로 쓰던 것을 고친 적이 있다. 그때 배웠다고 생각했는데, 몇 주 뒤 **다른 화면에서 똑같이** 했다.

코드를 고치는 걸로는 재발을 못 막는다는 걸 알았다. 그래서 이번엔 정책 문서에 한 줄을 박아뒀다.

> **금액은 항상 서버가 정한다.** 클라이언트가 보낸 금액으로 결제를 만들면 요청 한 줄을 고쳐 원하는 값에 살 수 있다.

| 상품 | 금액 출처 |
|---|---|
| 구독 요금제 | `plans` 테이블 (DB) |
| 1회성 서비스 | 서버 코드의 상품 목록 |

다음에 결제 화면을 새로 만들 때, 코드를 뒤지지 않아도 이 문장 하나면 된다.

## 배운 것
- **서명 = 변조 방지**이지 **생성 근거의 보장이 아니다.** 서명된 값이라도 "그 값을 무엇으로 만들었는지"는 따로 봐야 한다.
- 클라이언트 입력을 나눌 때는 "믿을 수 있나"가 아니라 **"위조되면 누가 손해인가"** 로 판단하면 명확하다.
- 같은 실수가 두 번 나오면 코드가 아니라 **원칙을 적어야** 세 번째를 막는다.

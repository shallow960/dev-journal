# 2026-10-31 설정 파일만 고쳤더니, 그 파일을 검사하는 시험은 UP-TO-DATE 로 건너뛰었다

> 태그: #트러블슈팅 #Gradle #증분빌드 #테스트 #계약시험

## 무엇을 / 왜
사진 키오스크 손님은 인화한 사진의 QR 을 찍어, 휴대폰으로 사진을 받는 페이지에 들어왔습니다. 2026-10-30 밤, 외주형 고객 브랜드(자기 브랜드로만 보여야 하는 고객사) 손님의 QR 주소를 플랫폼 주소 대신 그 브랜드의 주소로 내는 작업을 했습니다.

- 브랜드 주소로 들어온 요청 가운데 `/qr/*` 는 앞단 프록시(Caddy)가 손님 사진 페이지로 보내야 했습니다. 이 경로가 빠진 주소가 QR 에 찍히면, 손님은 사진 대신 관리자 화면을 받을 수 있었습니다.
- 그래서 서버 설정에 "QR 주소로 써도 되는 호스트 목록" 을 두고, 목록의 호스트마다 프록시 설정 파일에 그 경로가 있는지 대조하는 시험을 새로 만들었습니다. 프록시 설정 파일은 서버 코드(backend) 폴더 밖의 배포 설정 폴더에 있었고, 시험은 실행 중에 그 파일을 읽었습니다.
- 시험이 제 몫을 하는지 보려고 프록시 설정에서 그 경로를 지우고 돌려 봤습니다. 시험은 실패해야 했는데 빌드는 성공으로 끝났습니다. 로그를 보니 test 작업 옆에 `UP-TO-DATE` 가 찍혀 있었고, 시험은 돌지도 않았습니다.

## 어떻게 풀었나
- 찾아보니 Gradle 은 작업의 입력과 출력이 지난번과 같으면 그 작업을 다시 돌리지 않고 `UP-TO-DATE` 로 넘어간다는 걸 알게 됐습니다. test 작업의 입력은 컴파일한 시험 코드와 클래스패스 같은 것이었고, 시험이 실행 중에 읽는 파일은 따로 알려 주지 않으면 입력에 들어가지 않았습니다.
- 그래서 시험 코드는 그대로인데 프록시 설정 파일만 바뀌면, Gradle 은 바뀐 것이 없다고 보고 test 를 건너뛰었습니다. 빌드는 초록색이었지만, 그 초록색은 "시험이 통과했다" 가 아니라 "시험을 돌리지 않았다" 였습니다.
- test 작업에 그 파일을 입력으로 선언했습니다(`inputs.files(...)`). 입력에 이름을 붙이고, 빌드 파일의 다른 입력 선언과 같이 상대 경로 기준(`PathSensitivity.RELATIVE`)으로 두었습니다.
- 다시 프록시 설정에서 경로를 지우자 이번에는 test 가 다시 돌아 실패했고, 되돌리자 통과했습니다.
- 알고 보니 같은 빌드 파일에는 같은 이유로 넣어 둔 입력 선언이 이미 여럿 있었습니다. 시험이 바깥 파일을 새로 읽을 때마다 챙겨야 하는 일이었는데, 이번 시험을 처음 만들 때는 빠져 있었습니다.

## 코드로 보기 (개념 재현)
backend 폴더 밖의 프록시 설정을 읽는 시험 하나로 작은 Gradle 프로젝트를 만들었습니다. 입력 선언이 없을 때와 있을 때, 프록시 설정만 바꿔 가며 test 를 돌렸습니다. 이름은 모두 예시입니다.

```
gradle-demo/
├── proxy/Caddyfile        # 시험이 실행 중에 읽는 바깥 파일
└── backend/
    ├── build.gradle
    └── src/test/java/demo/RouteContractTest.java
```

정상일 때의 프록시 설정입니다. 고장 낸 판은 `brand-a.example` 블록에서 `handle_path /qr/*` 부분만 지운 것입니다.

```caddyfile
home.example {
	handle_path /qr/* {
		reverse_proxy guest-page:80
	}
	handle {
		reverse_proxy admin-app:80
	}
}

brand-a.example {
	handle_path /qr/* {
		reverse_proxy guest-page:80
	}
	handle {
		reverse_proxy admin-app:80
	}
}
```

시험은 목록의 호스트마다 프록시 설정에 `/qr/*` 경로가 있는지만 보게 했습니다.

```java
package demo;

import static org.junit.jupiter.api.Assertions.assertTrue;

import java.nio.file.Files;
import java.nio.file.Path;
import java.util.List;
import org.junit.jupiter.api.Test;

// 손님 QR 주소에 쓸 수 있는 호스트 목록과 프록시 설정이 맞는지 대조하는 시험(개념 재현, 이름은 모두 예시).
class RouteContractTest {

    // 실제로는 서버 설정 파일에서 읽는 목록이다.
    static final List<String> LINK_HOSTS = List.of("brand-a.example");

    @Test
    void everyQrHostRoutesQrPathToGuestPage() throws Exception {
        // 시험이 실행되는 동안 backend 폴더 밖의 파일을 읽는다. Gradle 은 이 줄을 모른다.
        String conf = Files.readString(Path.of("../proxy/Caddyfile"));
        for (String host : LINK_HOSTS) {
            int start = conf.indexOf(host + " {");
            assertTrue(start >= 0, host + ": no site block");
            String block = conf.substring(start, conf.indexOf("\n}", start));
            assertTrue(block.contains("handle_path /qr/*"), host + ": no /qr/* route");
        }
    }
}
```

고친 뒤의 build.gradle 입니다. 고치기 전 판에는 `inputs.files(...)` 세 줄이 없었습니다.

```groovy
plugins { id 'java' }

repositories { mavenCentral() }

dependencies {
    testImplementation platform('org.junit:junit-bom:5.12.2')
    testImplementation 'org.junit.jupiter:junit-jupiter'
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}

tasks.named('test') {
    useJUnitPlatform()
    testLogging { exceptionFormat = 'full' }
    // 시험이 실행 중에 읽는 바깥 파일을 입력으로 선언한다. 이 파일만 바뀌어도 test 가 다시 돈다.
    inputs.files(file('../proxy/Caddyfile'))
        .withPropertyName('proxyConfig')
        .withPathSensitivity(PathSensitivity.RELATIVE)
}
```

단계마다 프록시 설정과 build.gradle 을 바꿔 끼우고 test 를 돌린 뒤, 결과 줄만 남겼습니다. 8, 9 단계는 없는 파일을 입력으로 선언했을 때 단수형 `inputs.file` 과 복수형 `inputs.files` 가 어떻게 다른지 본 것입니다. 실제로는 내려받아 둔 Gradle 경로를 썼고, 아래에서는 `gradle` 로 줄였습니다.

```bash
#!/usr/bin/env bash
# 시험이 읽는 바깥 파일만 바꿨을 때 Gradle test 가 다시 도는지 본다.
set -u
HERE="$(cd "$(dirname "$0")" && pwd)"
G=gradle   # Gradle 8.14.4
cd "$HERE/backend"

step() {
  local title="$1"; shift
  echo "== $title"
  # 결과 줄만 남긴다: test 작업이 돌았는지, 시험 결과, 빌드 결과.
  "$G" --offline --no-daemon --console=plain test "$@" 2>&1 \
    | grep -E '^> Task :test( |$)|RouteContractTest >|AssertionFailedError:|tests? completed|not-here|^BUILD ' \
    | sed -E 's/^(BUILD [A-Z]+).*/\1/'
}

rm -rf build .gradle
cp "$HERE/Caddyfile.good" "$HERE/proxy/Caddyfile"
cp "$HERE/build-before.gradle" build.gradle
step "1) before: 처음 실행(프록시 설정 정상)"
step "2) before: 아무것도 안 바꾸고 다시 실행"
cp "$HERE/Caddyfile.broken" "$HERE/proxy/Caddyfile"
step "3) before: 프록시 설정에서 brand-a.example 의 /qr/* 경로만 지우고 실행"
step "4) before: 같은 상태에서 test 만 강제로 다시 실행(test --rerun)" --rerun

cp "$HERE/Caddyfile.good" "$HERE/proxy/Caddyfile"
cp "$HERE/build-after.gradle" build.gradle
step "5) after: 입력 선언을 넣고 실행(프록시 설정 정상)"
step "6) after: 아무것도 안 바꾸고 다시 실행"
cp "$HERE/Caddyfile.broken" "$HERE/proxy/Caddyfile"
step "7) after: 프록시 설정에서 /qr/* 경로만 지우고 실행"

cp "$HERE/Caddyfile.good" "$HERE/proxy/Caddyfile"
cp "$HERE/build-missing-file.gradle" build.gradle    # inputs.file(file('../proxy/not-here.conf'))
step "8) 없는 파일을 inputs.file(단수)로 선언하고 실행"
cp "$HERE/build-missing-files.gradle" build.gradle   # inputs.files(file('../proxy/not-here.conf'))
step "9) 없는 파일을 inputs.files(복수)로 선언하고 실행"
```

- 3 단계에서 프록시 설정의 경로를 지웠는데도 test 는 `UP-TO-DATE` 였고 빌드는 성공했습니다. 이번에 겪은 것과 같았습니다.
- 4 단계에서 같은 상태로 test 만 강제로 다시 돌리자(`test --rerun`) 바로 실패했습니다. 시험이 틀렸던 게 아니라 돌지 않았던 것입니다.
- 5~7 단계에서 입력을 선언하자, 프록시 설정만 바뀌어도 test 가 다시 돌아 실패를 잡았습니다. 아무것도 안 바꿨을 때는 전처럼 `UP-TO-DATE` 로 넘어가서 빌드가 괜히 느려지지도 않았습니다.
- 8, 9 단계에서 없는 파일을 단수형 `inputs.file` 로 선언하자 test 가 시작하기 전에 멈췄고, 복수형 `inputs.files` 는 그대로 돌았습니다. 따로 `build -x test` 로 test 를 빼고 빌드해 보니 단수형도 문제없이 끝났습니다. 파일이 없을 수 있는 곳에서 test 를 돌린다면 복수형이 안전했고, 실제 빌드 파일도 복수형으로 선언했습니다.

## 💡 배운 것
- Gradle 의 `UP-TO-DATE` 는 "시험이 통과했다" 가 아니라 "시험을 돌리지 않았다" 는 뜻이라는 걸 배웠습니다. 시험이 실행 중에 읽는 바깥 파일은 입력으로 선언해야, 그 파일이 바뀔 때 시험이 다시 돌았습니다.
- 시험을 새로 만들면, 그 시험이 막으려는 고장을 일부러 내 보고 정말 실패하는지 봐야 한다는 걸 배웠습니다. 이번에는 그 확인에서 시험이 돌지조차 않았다는 게 드러났습니다.
- "있다" 와 "돈다" 는 다르다는 걸 다시 배웠습니다([2026-10-20, 커밋 전 검사가, 이 PC 에서는 한 번도 돌지 않았다](../트러블슈팅/2026-10-20-커밋-전-검사가-이-PC-에서는-한-번도-돌지-않았다.md)). 그때는 git 훅이었고, 이번에는 Gradle 이 건너뛴 시험이었습니다.

## 소감
빌드가 초록색이면 시험도 통과했다고 믿어 왔습니다. 이번에 로그 한쪽의 `UP-TO-DATE` 한 단어가 그 믿음의 빈틈을 보여 줬습니다. 설정 파일을 지키려고 만든 시험이, 정작 설정 파일이 바뀔 때는 돌지 않을 뻔했습니다.

# 2026-11-03 표 하나에 글자 비교 규칙을 적지 않아, 모든 계정의 현금 화면이 500 이었다

> 태그: #트러블슈팅 #MariaDB #collation #마이그레이션 #배포환경

## 무엇을 / 왜
사진 키오스크 서비스의 관리 화면을 본사뿐 아니라 총판, 대리점, 매장 계정에도 열어 주는 작업을 했습니다. 역할마다 화면이 부르는 조회를 시험하다가, 현금 현황 조회가 500 을 돌려주는 걸 찾았습니다.

- 오류는 `Illegal mix of collations (utf8mb4_general_ci,IMPLICIT) and (utf8mb4_unicode_ci,IMPLICIT) for operation '='` 였습니다.
- 권한과는 상관이 없었습니다. 본사를 포함해 모든 역할이 같은 조회를 쓰고 있었습니다.
- 이번에 고친 코드도 아니었습니다. 예전부터 있던 조회였습니다.

## 어떻게 풀었나
- 오류 문구는 `=` 로 비교하는 두 값의 글자 비교 규칙(collation)이 다르다는 뜻이었습니다. 그 조회는 주문 표와 현금 정산 표를 통화 칸으로 묶고 있었습니다.
- 두 표를 만든 마이그레이션을 열어 보니 차이가 있었습니다. 주문 표에는 `COLLATE=utf8mb4_unicode_ci` 를 직접 적었고, 현금 정산 표에는 아무것도 적지 않았습니다.
- 찾아보니 표에 규칙을 적지 않으면 데이터베이스의 기본값을 따르고, 데이터베이스의 기본값은 서버의 기본값을 따른다는 걸 알게 됐습니다. 같은 마이그레이션이라도 서버에 따라 다른 표가 만들어질 수 있었습니다.
- 설정 파일을 나란히 놓고 보니 개발용은 서버 규칙을 `utf8mb4_unicode_ci` 로 정해 두었고, 배포용은 아무것도 정하지 않았습니다. 개발용 DB 에서는 두 표의 규칙이 같아져서 오류가 나지 않는 구조였습니다.
- 이 조회를 부르는 기존 시험은 저장소를 가짜로 바꿔 둔 단위 시험뿐이었습니다. SQL 이 시험 안에서 실제 DB 에 닿은 적이 없었습니다.
- 정말 그런지 같은 스크립트를 서버 규칙만 다른 MariaDB 10.11 두 대에 돌려 봤습니다(아래 코드).
  - 규칙을 정하지 않은 서버에서만 오류가 났습니다.
  - 표에 행이 하나도 없어도 같은 오류가 났습니다. 데이터가 아니라 쿼리를 해석할 때 나는 오류였습니다.
  - 그 표 하나만 글자 값과 비교할 때는 오류가 나지 않았습니다.
- 찾아보니 글자 상수는 칸의 규칙을 따라가지만, 칸과 칸은 우선순위가 같아서 DB 가 어느 쪽도 고르지 못한다는 걸 알게 됐습니다. 오류 문구의 `IMPLICIT` 가 그 뜻이었습니다. 그래서 두 표를 묶는 조회가 돌기 전에는 드러나지 않았습니다.
- 고친 방법은 이렇습니다.
  - 이미 적용된 옛 마이그레이션은 고칠 수 없어서, 새 마이그레이션으로 현금 정산 표를 주문 표와 같은 규칙으로 변환했습니다.
  - 그 표의 글자 값은 영문과 숫자뿐이라 정렬과 유일 제약이 달라지지 않는 걸 확인했습니다.
  - 이미 같은 규칙인 DB 에서는 아무것도 달라지지 않는 변환이었습니다.

## 코드로 보기 (개념 재현)
```sql
-- 먼저 만든 표: 규칙을 직접 적었다
CREATE TABLE order_record (
  id BIGINT PRIMARY KEY, kiosk_id BIGINT, currency VARCHAR(3), amount BIGINT
) DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 나중에 만든 표: 아무것도 적지 않았다. 그래서 서버 기본값을 따른다
CREATE TABLE cash_settlement (
  id BIGINT PRIMARY KEY, kiosk_id BIGINT, currency VARCHAR(3)
);

-- 표마다 어떤 규칙이 붙었는지 본다
SELECT TABLE_NAME, TABLE_COLLATION FROM information_schema.TABLES WHERE TABLE_SCHEMA='shop' ORDER BY TABLE_NAME;

-- 표 하나만 글자 값과 비교한다. 글자 상수는 칸의 규칙을 따라가서 어느 서버에서든 통과한다
SELECT COUNT(*) AS rows_krw FROM cash_settlement WHERE currency='KRW';

-- 두 표의 칸끼리 비교한다. 행이 없어도 쿼리를 해석할 때 규칙을 본다
SELECT COUNT(*) AS joined FROM order_record o
  LEFT JOIN cash_settlement c ON c.kiosk_id=o.kiosk_id AND c.currency=o.currency;

-- 고친 방법: 뒤에 만든 표의 규칙을 앞의 표에 맞춘다
ALTER TABLE cash_settlement CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

```

변환 뒤 두 표 묶기  joined = 0

| cash_settlement | utf8mb4_unicode_ci |
| order_record    | utf8mb4_unicode_ci |
표 하나만 비교   rows_krw = 0
두 표 묶기       joined = 0
```

## 💡 배운 것
- 표를 만들 때 글자 비교 규칙을 적지 않으면 서버 기본값을 따라서, 같은 마이그레이션이 서버마다 다른 표를 만든다는 걸 배웠습니다. 표를 만드는 SQL 에는 문자 집합과 규칙을 매번 적어야 했습니다.
- 이 오류는 데이터가 아니라 쿼리를 해석할 때 나고, 칸과 칸을 직접 비교할 때만 난다는 걸 배웠습니다. 표를 하나씩 볼 때는 멀쩡해서, 두 표를 묶는 조회가 실제 DB 에 닿아야 드러났습니다.
- 저장소를 가짜로 바꾼 시험은 SQL 을 확인해 주지 않는다는 걸 배웠습니다. 서비스의 흐름은 시험해도, 쿼리가 돌아가는지는 알려 주지 않았습니다.
- 시험은 실제로 돌 곳과 같은 환경에서 해야 한다는 걸 다시 배웠습니다([2026-10-21, 내 PC 에서는 통과한 배포 명령이, 서버에서는 첫 줄에서 멈췄다](../트러블슈팅/2026-10-21-내-PC-에서는-통과한-배포-명령이-서버에서는-첫-줄에서-멈췄다.md)). 그때는 PC 와 서버의 줄 끝이 달랐고, 이번에는 개발용과 배포용 DB 설정이 달랐습니다.

## 소감
메뉴를 여는 작업을 하다 찾은 문제였는데, 원인은 권한이 아니라 예전에 표를 만들 때 적지 않은 한 줄이었습니다. 개발용 설정에 규칙을 적어 둔 건 좋은 일이었지만, 그 덕분에 배포용과의 차이가 가려져 있었습니다. 설정 파일 두 개를 나란히 놓고 보기 전에는 보이지 않던 차이였습니다.

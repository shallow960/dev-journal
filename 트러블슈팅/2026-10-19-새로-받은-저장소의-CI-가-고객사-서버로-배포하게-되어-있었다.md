# 2026-10-19 새로 받은 저장소의 CI 가, 고객사 서버로 배포하게 되어 있었다

> 태그: #트러블슈팅 #CICD #GitLab #보호브랜치 #인수인계

## 무엇을 / 왜

인수받은 플랫폼 저장소는 고객사 시스템의 저장소에서 갈라져 나온 것입니다. GitLab 에서는 서로 다른 프로젝트라서, "여기에 올리면 고객사 저장소의 코드가 바뀌나?" 의 답은 "아니다" 였어요.

그런데 질문을 확인하려고 CI 설정 파일을 열어 보니, 첫 줄부터 원래 시스템 이름이었습니다. 배포 대상도 그대로였어요.

- **develop 브랜치에 올리면:** 빌드 → 테스트 → 고객사 **테스트 서버로 자동 배포**
- **main 에 올리면:** 빌드 → 테스트 → 고객사 **운영 서버 배포 버튼** 대기 (누가 누르면 배포)

지금까지 아무 일이 없었던 건 원격에 develop 브랜치가 아직 없었기 때문이에요. 안전해서가 아니라 조건이 안 맞아서였습니다.

더 걸리는 건 접속 정보였어요. 예전 개발 문서에는 배포용 변수(클라우드 키, 서버 접속 키)가 "보호 안 함" 으로 적혀 있었습니다. 보호하지 않은 변수는 보호되지 않은 브랜치의 파이프라인에도 들어가요. 그 변수가 새 프로젝트나 상위 그룹에 남아 있는지는 저장소만 봐서는 알 수 없었습니다.

## 어떻게 풀었나

1. **진행 중이던 작업과 섞이지 않게** 원격 main 에서 새 브랜치를 따고, 별도 작업 폴더(git worktree)에서 고쳤습니다. 작업 폴더 경로가 길어서 처음엔 만들어지지 않았는데, 긴 경로 지원 옵션을 켜고 다시 만들었어요.
2. **배포만 좁게 지웠습니다.** 배포 단계 6개, 그걸 위한 공통 조각, 배포 단계 이름, 배포에만 쓰던 변수를 지우고 빌드·테스트는 손대지 않았어요.
3. **"손대지 않았다" 를 말로 두지 않고 확인했습니다.** 남긴 구간을 원본에서 잘라 비교해 225줄이 한 글자도 다르지 않은 걸 봤고, 설정 파일을 직접 읽어 들여(파싱) 단계 이름과 단계 사이의 참조가 모두 살아 있는지 봤어요. 서버로 접속하거나 올리는 명령이 남았는지도 검색했습니다.
4. **main 에 바로 올리려 했더니 거절됐습니다.** 보호 브랜치라 직접 올릴 수 없었어요. 그래서 브랜치를 올리면서 합치기 요청(Merge Request)을 같이 만들었습니다. 합쳐지기 전까지 main 은 그대로예요.
5. **저장소 밖 숙제를 따로 적었습니다.** 프로젝트와 상위 그룹 변수에서 고객사 접속 정보를 지우는 일이에요. 근본적인 위험은 거기 있으니까요.

## 코드로 보기 (개념 재현)

```yaml
# 고치기 전 (개념): 갈라져 나온 저장소에 원래 시스템의 배포가 그대로 남아 있다
stages: [build, test, deploy]

deploy-test:
  stage: deploy
  script:
    - ./deploy.sh "$TEST_HOST"           # 원래 시스템의 테스트 서버
  rules:
    - if: '$CI_COMMIT_BRANCH == "develop"'   # 올리기만 하면 자동

deploy-live:
  stage: deploy
  script:
    - ./deploy.sh "$LIVE_HOST"           # 원래 시스템의 운영 서버
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual                       # 버튼 한 번이면 배포
```

```yaml
# 고친 뒤 (개념): 빌드와 테스트만 남기고, 왜 지웠는지 적어 둔다
stages: [build, test]

# 배포 job 은 없다. 원래 시스템을 가리키던 배포를 2026-10-19 에 지웠다.
# 이 플랫폼의 배포는 CI 가 아니라 별도 런북으로 한다.
```

```bash
# 남긴 구간이 원본과 같은지: 같은 구간을 잘라 비교한다
git show HEAD:ci.yml | awk '/^# build/{f=1} /^# deploy/{f=0} f' > old.txt
tr -d '\r' < ci.yml   | awk '/^# build/{f=1} /^# 배포 없음/{f=0} f' > new.txt
diff old.txt new.txt && echo "빌드·테스트 구간 동일"

# 서버로 나가는 명령이 남았는지
grep -nE 'ssh |scp |s3 sync' ci.yml || echo "없음"

# 보호 브랜치에 바로 올리면 거절된다 (remote rejected, protected branch)
git push origin fix/ci-remove-deploy:main

# 브랜치를 올리면서 합치기 요청을 같이 만든다 (GitLab push 옵션)
git push -o merge_request.create -o merge_request.target=main \
    origin fix/ci-remove-deploy
```

## 💡 배운 것

**복사해 온 것은 연결까지 데려온다는 걸 다시 배웠습니다.** 2026-10-16 에 "사본도 바깥과 연결되면 진짜처럼 움직인다" 를 리허설 서버에서 배웠는데, 이번엔 서버가 아니라 저장소였어요. 코드만 가져온 줄 알았는데 배포 대상까지 따라와 있었습니다.

**"합쳤다" 다음에 "어디로 가느냐" 를 봐야 한다는 걸 다시 배웠습니다.** 2026-07-16 에 합치기와 배포 사이를 자동으로 잇는 걸 처음 만들면서 "합쳤다와 반영됐다는 다르다" 를 배웠어요. 이번에는 그 다리의 끝이 어디에 닿아 있는지까지 확인해야 했습니다.

**아직 안 터진 이유가 "조건이 안 맞아서" 일 수 있다는 걸 배웠습니다.** develop 브랜치가 생기는 순간 바로 배포가 돌았을 거예요. 지금까지 괜찮았다는 건 안전하다는 증거가 아니었습니다.

**마지막 벽은 저장소 밖에 있다는 걸 배웠습니다.** 보호 브랜치가 제 push 를 막아 줬어요. 반대로 변수 보호가 꺼져 있으면, 어느 브랜치든 설정 파일만 바꿔서 접속 정보를 쓸 수 있습니다. 파일을 고치는 것과 권한·변수를 정리하는 것을 둘 다 해야 닫혀요.

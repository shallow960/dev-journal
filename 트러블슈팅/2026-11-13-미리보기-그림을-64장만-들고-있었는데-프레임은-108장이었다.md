# 2026-11-13 미리보기 그림을 64장만 들고 있었는데, 프레임은 108장이었다

> 태그: #트러블슈팅 #캐시 #Electron #성능 #오프라인

## 무엇을 / 왜

사진 키오스크의 프레임 선택 화면에서는 프레임 칩을 누를 때마다 왼쪽에 큰 미리보기가 떴습니다. 고객사 QA 에서 인트로를 누르고 들어오면 미리보기가 바로 안 보이고 빈 칸일 때가 잦다는 지적이 왔습니다. 칩을 빠르게 바꿀 때도 미리보기가 한 박자씩 늦게 따라왔습니다.

빈 칸에는 다른 원인(레이아웃을 하나로 고정한 매장에서 첫 프레임이 골라지지 않던 것)도 섞여 있어서 그것은 먼저 따로 고쳤습니다. 그런데 고친 뒤에도 미리보기가 늦게 뜨는 일은 남아 있었습니다.

## 어떻게 풀었나

키오스크 기록부터 봤습니다. 로그인 뒤 프레임 미리보기 그림을 미리 받아 두는 단계가 있었는데, 앱을 켤 때마다 "받은 수 108, 캐시에서 찾은 수 0" 이었습니다. 켤 때마다 8~10초 동안 108장을 처음부터 다시 받고 있었습니다.

원인은 미리보기 그림을 담는 곳에 있었습니다.

- 웹빌더로 발행한 화면을 쓰는 키오스크는 미리보기 그림을 **메모리에만**, 그것도 **64장까지만** 들고 있었습니다. 넘치면 오래된 것부터 밀어냈습니다.
- 그런데 이 매장의 프레임은 108장이었습니다. 미리 받기가 108장을 차례로 받으면 먼저 받은 44장은 이미 밀려나 있었고, 손님이 그 칩을 누르면 서버에서 다시 받아야 했습니다(한 장에 0.2초쯤).
- 앱을 다시 켜면 메모리는 비어 있으니 108장을 또 처음부터 받았습니다.

더 이상한 점은 따로 있었습니다. 같은 로그인 미리 받기의 앞 단계가, 발행본에 들어 있는 그림 파일을 이미 **디스크 캐시**에 받아 두고 있었습니다. 이 디스크 캐시는 그림 내용의 해시(sha256)를 파일 이름으로 써서, 같은 그림이면 이름도 같았습니다. 미리보기용 그림도 그 안에 다 있었는데, 미리보기는 그 캐시를 보지 않고 프레임 번호로 서버에 따로 묻고 있었던 것입니다.

그래서 새 저장소를 만들지 않고, 이미 있는 디스크 캐시를 쓰게 했습니다.

1. 발행본을 실을 때 "프레임 번호 → 미리보기 그림 경로(내용 해시)" 표를 만들어 두었습니다.
2. 미리보기는 그 경로로 메모리 → 디스크 → (둘 다 없을 때만) 서버 순서로 찾게 했습니다.
3. 경로가 그림 내용의 해시라서, 관리자가 그림을 바꾸면 새 발행본에서는 경로도 바뀌었습니다. 그래서 바뀐 프레임만 새로 받고, 나머지는 디스크에서 바로 읽게 됐습니다.

고친 뒤 시험 키오스크 기록은 "캐시에서 찾은 수 108, 새로 받은 수 0" 이 됐습니다. 칩을 바꾸면 미리보기가 바로 바뀌었고, 앱을 다시 켜거나 인터넷이 끊긴 상태에서도 미리보기가 떴습니다. 이 수정은 2026-11-16 실제 키오스크 확인에서도 정상이었습니다.

## 코드로 보기 (개념 재현)

먼저 "캐시보다 많은 것을 차례로 볼 때" 무슨 일이 생기는지 더미로 따라가 봤습니다.

```js
// 오래된 것부터 밀어내는 작은 메모리 캐시 (더미)
class SmallCache {
  constructor(limit) { this.limit = limit; this.map = new Map(); }
  get(key) {
    if (!this.map.has(key)) return undefined;
    const value = this.map.get(key);
    this.map.delete(key); this.map.set(key, value); // 방금 쓴 것을 맨 뒤로
    return value;
  }
  set(key, value) {
    this.map.delete(key);
    this.map.set(key, value);
    if (this.map.size > this.limit) this.map.delete(this.map.keys().next().value); // 가장 오래된 것 하나 밀어내기
  }
}

// 64장 캐시로 108장을 차례로 두 바퀴 본다 (미리 받기 한 바퀴 + 손님이 칩을 차례로 누름 한 바퀴)
const cache = new SmallCache(64);
let hits = 0, downloads = 0;
for (let round = 0; round < 2; round++) {
  for (let id = 1; id <= 108; id++) {
    if (cache.get(id) !== undefined) hits++;
    else { downloads++; cache.set(id, `thumb-${id}`); }
  }
}
console.log({ hits, downloads });
// { hits: 0, downloads: 216 }
// 찾는 그림은 늘 108번 전에 본 그림이고, 캐시에는 최근 64장만 남아 있어서 한 번도 맞지 않는다
```

고친 뒤의 찾는 순서입니다.

```js
// 미리보기도 내용 해시 경로로, 메모리 -> 디스크 -> 서버 순서로 찾는다 (더미)
async function getThumbnail(frameId, { thumbPathByFrame, memory, disk, server }) {
  const path = thumbPathByFrame.get(frameId);              // 발행본을 실을 때 만든 표: 프레임 번호 -> 'thumbs/<sha256>.png'
  if (!path) return server.byFrameId(frameId);   // 표에 없는 옛 방식 프레임은 예전 길 그대로

  const inMemory = memory.get(path);
  if (inMemory) return inMemory;

  const onDisk = await disk.read(path);          // 로그인 미리 받기가 이미 받아 둔 파일
  if (onDisk) { memory.set(path, onDisk); return onDisk; }

  const fresh = await server.byPath(path);       // 디스크에도 없을 때만 받는다
  await disk.write(path, fresh);
  memory.set(path, fresh);
  return fresh;
}
// 그림이 바뀌면 내용 해시가 바뀌어 경로도 바뀐다 -> 바뀐 프레임만 새로 받는다
```

## 💡 배운 것

- 캐시가 실제로 다루는 양보다 작으면, 차례로 훑는 사용 방식에서는 한 번도 맞지 않을 수 있다는 걸 배웠습니다. 64장 캐시에 108장을 순서대로 넣으면, 찾는 그림은 늘 이미 밀려난 그림이었습니다.
- 느린 곳에 새 캐시를 더하기 전에, 같은 데이터를 이미 들고 있는 층이 없는지 먼저 봐야 한다는 걸 배웠습니다. 이번에는 필요한 그림이 이미 디스크에 다 있었습니다.
- 내용의 해시를 이름으로 쓰는 저장소는 "바뀌었는지" 를 따로 묻지 않아도 된다는 걸 배웠습니다. 이름이 같으면 같은 그림이었고, 그림이 바뀌면 이름이 바뀌었습니다.

## 소감

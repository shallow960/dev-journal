# 2026-09-18 멈춘 것이 고장인지, 안전장치인지

> 태그: #트러블슈팅 #결제 #운영 #외부연동

## 무엇을 / 왜

매일 새벽 같은 시각에 이런 알림이 왔습니다.

```
정기결제 결과 미확인 - 자동 재청구를 멈춤. 결제사 승인 내역 확인 후
구독.결제시도시각 을 비워야 다시 청구된다. 구독=...
```

세 건이 며칠째 반복되고 있었고, 확인해 보니 **구독료가 일주일 넘게 한 번도 걷히지 않았습니다.**

## 어떻게 풀었나

### 먼저: 이 멈춤은 고장이 아니다

이 메시지는 제가 전에 넣어 둔 안전장치가 낸 것입니다. 결제사를 부르는 도중에 끊기면 **승인이 났는지 모르는 상태**가 되는데, 그때 다시 긁으면 두 번 받게 됩니다. 그래서 표시를 남기고 자동 재청구를 멈추게 해 뒀습니다.

즉 **"안 걷히는 것" 자체는 설계대로** 였습니다. 문제는 **왜 결과를 못 받았는가** 였습니다.

### 기록부터 읽었다

```sql
-- 멈춘 구독
select id, status, 결제시도시각, 현재주기_종료 from 구독 where 결제시도시각 is not null;
--   세 건 모두 같은 날 02:15 (정기결제 배치 시각)에 표시가 찍혔고
--   주기 종료일은 그보다 일주일 전에서 멈춰 있다

-- 결제 기록
select 요청시각, 상태, 응답->>'ResultCode', 응답->>'ResultMsg' from 결제기록 order by 요청시각 desc limit 5;
--   마지막 성공이 한 달 전. 그 뒤로는 실패 기록조차 없다
```

**실패 기록이 없다**는 게 중요했습니다. 결제사가 거절했다면 거절 기록이 남습니다. 아무것도 없다는 건 **기록을 쓰기 전에 끊겼다**는 뜻입니다.

### 토큰에 상점이 박혀 있었다

카드 정보를 직접 갖지 않고 결제사가 준 **토큰**으로 매달 긁는 구조입니다. 그 토큰을 보니 이렇게 생겼습니다.

```
BIKY<상점ID>26...
```

앞부분에 **토큰을 발급한 상점 ID 가 들어 있었습니다.** 그런데 그게 결제사의 **테스트 상점** 이었어요. 등록된 카드 네 건이 전부 그랬습니다.

설정을 열어 보니 상점 ID 는 테스트 상점인데 **상점 비밀키는 실 상점 것**이 들어가 있었습니다. 둘이 짝이 안 맞으면 서명이 틀려 거절됩니다.

### 실 상점으로 바꾸자 다른 벽이 나왔다

설정을 맞춰 넣고 카드를 다시 등록했더니 이번엔 이렇게 거절됐습니다.

```
F117 빌링 미사용 가맹점입니다.
```

여기서 "결제사에 문의" 로 넘길 수도 있었지만, **무엇을 문의할지가 애매했습니다.** 정기결제 자체가 안 열린 건지, 토큰 발급만 안 열린 건지 모르니까요.

그래서 **결제사 API 를 직접 한 번 찔러 봤습니다.** 가짜 토큰으로 승인을 요청하는 겁니다. 승인은 절대 나지 않고(토큰이 가짜니까), **상점 권한 검사는 통과하는지**만 봅니다.

```bash
# 승인 요청: 상점ID + 시각 + 주문번호 + 금액 + 토큰 + 상점키 로 서명을 만들어 보낸다
SIGN=$(printf '%s%s%s%s%s%s' "$상점ID" "$시각" "$주문번호" "$금액" "$가짜토큰" "$상점키" | sha256sum | cut -d' ' -f1)

curl -s -X POST https://<결제사>/billing/approve \
  --data "MID=$상점ID&EdiDate=$시각&Moid=$주문번호&Amt=$금액&BID=$가짜토큰&SignData=$SIGN"
```

응답이 이렇게 왔습니다.

```json
{"ResultCode":"9999","ResultMsg":"해당 BillKey 가 존재하지 않습니다"}
```

**"그런 토큰이 없다"** 는 건 상점 인증을 통과했다는 뜻입니다. 권한이 없었으면 여기서도 `F117` 이 나왔을 겁니다.

즉 **승인은 열려 있고, 토큰 발급만 막혀 있었습니다.**

## 코드로 보기 (개념 재현)

안전장치 쪽은 이렇게 생겼습니다. 결제사를 부르기 **직전에** 바깥 트랜잭션과 분리해 표시를 확정하고, 결과를 기록하면 지웁니다.

```java
for (구독 구독 : 결제일이_지난_구독들()) {
    if (!결제시도_표시(구독.id())) {
        // 표시가 이미 있으면 = 지난번 결과를 모른다 → 건너뛴다
        continue;
    }
    var 청구서 = 청구서만들기(구독);
    결제하기(청구서.id());            // 이 안에서 결제사를 부른다
    결제시도_표시_지움(구독.id());     // 결과를 기록했으니 표시를 지운다
}
```

토큰이 어느 환경에서 만들어졌는지는 눈으로 갈립니다.

```sql
select 생성시각, left(결제토큰, 16) as 앞부분 from 결제수단 order by 생성시각 desc;
-- BIKY테스트상점26...   ← 테스트 상점에서 발급된 토큰. 실 상점에서는 승인되지 않는다
```

## 💡 배운 것

**멈춰 있을 때, 그게 고장인지 안전장치인지부터 구분합니다.** 여기서는 안전장치가 제대로 동작한 것이었고, 그걸 모르고 표시를 지웠다면 결과를 모르는 결제를 다시 긁을 뻔했습니다.

**실패 기록이 "없다" 는 것도 단서입니다.** 거절이면 거절 기록이 남습니다. 아무것도 없으면 기록 이전 단계에서 끊긴 겁니다.

**외부 서비스가 준 식별자에는 정보가 들어 있습니다.** 토큰 앞부분의 상점 ID 덕분에 "이건 테스트 환경에서 만든 것" 을 한눈에 알았습니다.

**화면에서 막히면 API 를 직접 호출해 경계를 좁힙니다.** "안 된다" 와 "어디까지는 된다" 는 전혀 다른 정보입니다. 후자가 있어야 외부 담당자가 어느 설정을 봐야 할지 압니다.

**외부 업체에 문의할 때는 근거를 같이 보냅니다.** "정기결제가 안 됩니다" 대신 "발급은 F117 로 거절되는데 같은 상점으로 승인 API 는 정상 응답합니다" 라고 쓰면 주고받는 횟수가 줄어듭니다.

**설정 값은 짝으로 맞아야 합니다.** 상점 ID 와 상점 비밀키처럼 쌍으로 쓰는 값은 한쪽만 바꾸면 조용히 거절됩니다. 길이나 형식으로는 구분되지 않는 경우가 많습니다.

## 소감

알림이 며칠째 오는데도 "이미 아는 문제" 로 넘기고 있었던 게 아쉽습니다. 실제로는 **구독료가 일주일 넘게 안 걷히고 있었고**, 그건 알림 메시지에 적혀 있지 않았습니다.

반복되는 알림은 익숙해지는 순간 배경 소음이 됩니다. 같은 알림이 세 번 이상 오면 그때는 내용을 다시 읽어 보는 습관을 들여야겠습니다.

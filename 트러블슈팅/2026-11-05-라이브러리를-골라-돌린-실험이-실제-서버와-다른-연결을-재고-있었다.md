# 2026-11-05 라이브러리를 골라 돌린 실험이, 실제 서버와 다른 연결을 재고 있었다

> 태그: #트러블슈팅 #HTTP #재시도 #시간제한 #SpringBoot #결제

## 무엇을 / 왜

결제사로 승인·취소 요청을 보내는 연결에는 지켜야 할 것이 하나 있었습니다. 요청이 저절로 두 번 나가면 안 됐습니다. 결제사가 이미 처리한 승인을 우리도 모르게 다시 보내면, 손님 돈이 두 번 움직일 수 있기 때문입니다.

전날 이 연결을 정리하면서 "응답 없이 끊겨도 요청을 다시 보내지 않는다"는 설명을 달았습니다. 확인하려고 작은 실험도 돌렸습니다. 답하지 않고 연결을 끊는 시험 서버를 띄우고 요청을 보내 보니 한 번만 왔습니다.

그런데 다음 날 그 실험을 다시 보다가 걸리는 점이 있었습니다. 실험은 필요하다고 생각한 라이브러리만 손으로 골라 돌린 것이었습니다. 실제 서버는 라이브러리를 훨씬 많이 싣고 있었고, 프레임워크는 그중에서 HTTP 연결을 저절로 고릅니다. 실험이 실제 서버와 같은 연결을 쟀는지 알 수 없었습니다.

## 어떻게 풀었나

실제 서버의 라이브러리 전부와 설정, 추적 기능까지 그대로 켠 상태로 같은 시험 서버에 요청을 다시 보냈습니다. 결과는 전날과 꽤 달랐습니다.

| 본 것 | 전날 실험 | 실제 구성 |
|---|---|---|
| 기본 연결 | JDK 기본 연결 | Apache HttpClient 5 (라이브러리 목록에 있어 프레임워크가 골랐습니다) |
| 응답 없이 끊길 때 | 한 번 보냄 | 한 번 보냄 |
| 500 응답 | 한 번 보냄 | 한 번 보냄 |
| 503·429 응답 | 확인 안 함 | **1초 뒤 POST 를 한 번 더 보냄** |
| 응답 시간 제한 | 없음 | 기본 3분 |

찾아보니 Apache HttpClient 5 는 503(잠시 쓸 수 없음)과 429(요청이 너무 많음)를 "잠시 뒤 다시 해 보라"는 뜻으로 보고, 요청 종류를 따지지 않고 한 번 더 보내는 것이 기본 동작이라는 걸 알게 됐습니다. POST 도 예외가 아니었습니다.

다행히 결제사 호출은 전날부터 따로 만든 연결(JDK 기본 연결)을 쓰고 있었습니다. 그래서 할 일은 두 가지로 나뉘었습니다.

1. **결제사 연결:** 네 경우(끊김·500·503·429) 모두 한 번만 보내는지 같은 시험 서버로 재는 시험을 남기고, 틀린 설명을 실측에 맞게 고쳤습니다. 같은 시험에서 공용 연결은 두 번, 결제사 연결은 한 번 받는 것을 함께 확인하게 했습니다.
2. **결제사 밖의 바깥 호출:** 소셜 로그인, 라이브 시작처럼 결제가 아닌 바깥 호출은 공용 연결을 그대로 쓰고 있었습니다. 상대가 응답하지 않으면 그 요청이 3분까지 묶이는 상태였습니다. 연결 종류는 그대로 두고 연결 5초·응답 30초를 두었고, 상태 점검처럼 오래 기다리면 안 되는 호출은 더 짧게 두었습니다.

## 코드로 보기 (개념 재현)

시험 서버가 503 을 돌려줄 때 요청이 몇 번 오는지 세는 시험입니다. 이름과 주소는 예시입니다.

```java
// 503 만 돌려주는 시험 서버를 띄우고, 받은 요청 수를 센다
HttpServer server = HttpServer.create(new InetSocketAddress(0), 0);
AtomicInteger hits = new AtomicInteger();
server.createContext("/approve", exchange -> {
    hits.incrementAndGet();
    exchange.sendResponseHeaders(503, -1); // 잠시 쓸 수 없음
    exchange.close();
});
server.start();
String url = "http://localhost:" + server.getAddress().getPort() + "/approve";

// 1) 프레임워크가 골라 준 공용 연결 (실제 구성에서는 Apache HttpClient 5)
RestClient shared = sharedBuilder.build();
callIgnoringError(() -> shared.post().uri(url).body("{}").retrieve().toBodilessEntity());
assertThat(hits.getAndSet(0)).isEqualTo(2); // 1초 뒤 한 번 더 보냈다

// 2) 결제사용으로 따로 만든 연결 (JDK 기본 연결 + 시간 제한)
HttpClient jdk = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(5))
        .build();
JdkClientHttpRequestFactory factory = new JdkClientHttpRequestFactory(jdk);
factory.setReadTimeout(Duration.ofSeconds(30));
RestClient payment = RestClient.builder().requestFactory(factory).build();
callIgnoringError(() -> payment.post().uri(url).body("{}").retrieve().toBodilessEntity());
assertThat(hits.get()).isEqualTo(1); // 다시 보낼지는 우리 코드가 정한다
```

이 시험에서 중요한 것은 `sharedBuilder` 를 손으로 만들지 않고, 실제 서버와 같은 설정으로 뜬 애플리케이션에서 꺼내 쓰는 것입니다. 손으로 만들면 전날 실험처럼 실제와 다른 연결을 재게 됩니다.

## 💡 배운 것

- **실험도 실제로 돌아가는 구성 그대로 해야 믿을 수 있었습니다.** 라이브러리를 골라 돌린 실험은 그 라이브러리의 동작만 보여 줬고, 실제 서버가 무엇을 쓰는지는 보여 주지 못했습니다.
- **프레임워크가 저절로 고르는 것은 라이브러리 목록이 바뀌면 같이 바뀝니다.** 다른 기능 때문에 넣은 라이브러리 하나가 HTTP 연결의 재시도 동작까지 바꿀 수 있었습니다.
- **"기본값 없음"과 "기본값이 길다"는 다릅니다.** 시간 제한을 정하지 않았다고 끝없이 기다리는 것이 아니라, 모르는 사이에 3분이라는 값을 쓰고 있었습니다.
- **돈이 움직이는 요청은 다시 보낼지를 우리 코드가 정해야 합니다.** 연결이 대신 다시 보내면, 결제사가 처리했는지 모르는 채로 같은 요청이 한 번 더 나갈 수 있었습니다.

## 소감

전날 확인했다고 적어 둔 설명이 하루 만에 틀린 것으로 드러나 조금 민망했습니다. 그래도 실험을 다시 본 덕분에 결제사 연결을 따로 둔 것이 실제로 필요한 일이었다는 것도 확인했습니다. 앞으로는 "확인했다"고 적기 전에, 그 확인이 실제 서버와 같은 조건이었는지부터 묻게 될 것 같습니다.

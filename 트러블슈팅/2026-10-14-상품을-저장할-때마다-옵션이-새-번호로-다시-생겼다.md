# 2026-10-14 상품을 저장할 때마다, 옵션이 새 번호로 다시 생겼다

> 태그: #트러블슈팅 #데이터모델링 #SQL #Spring #재고

## 무엇을 / 왜

옵션 상품(사이즈·색)에서 상품 재고 칸을 비워 두면, 옵션마다 재고가 있어도 상품이 **'품절'로 저장**되는 문제가 있었습니다. 옵션을 넣으면 상품 재고 칸은 쓰지 않는데, 비어 있으면 0으로 들어가 서버가 품절로 판단했어요.

이걸 고치려고 저장 흐름을 따라가다 더 큰 문제를 찾았습니다. 상품을 저장할 때마다 **옵션을 전부 지우고 새 번호로 다시 넣고** 있었어요. 화면이 옵션 번호를 보내지 않으니, 서버는 "받은 목록으로 통째로 갈아끼우기"를 하고 있었던 거예요.

번호가 바뀌면 그 번호를 들고 있던 곳이 모두 길을 잃습니다.

1. 장바구니에 담긴 **옛 옵션 번호**로 주문하면 옵션을 못 찾아, 추가금이 0원으로 계산되고 옵션 재고도 줄지 않았습니다.
2. 이미 받은 주문은 취소해도 옵션 재고가 돌아오지 않았어요. 돌려놓을 옵션 행이 없으니까요.
3. 주문 화면에서는 손님이 무슨 옵션을 샀는지도 알 수 없게 됐습니다.

## 어떻게 풀었나

- **번호를 유지하는 저장:** 보낸 번호가 이 상품의 옵션이면 그 번호를, 번호가 없으면 같은 그룹·값(예: 사이즈/M)의 기존 옵션 번호를 그대로 씁니다. 새 목록에서 빠진 옵션만 지워요.
- **남의 옵션은 못 덮게:** 다른 상품의 옵션 번호를 보내면 그 행을 고치지 않고 새로 만듭니다.
- **재고는 옵션에서 센다:** 옵션 상품의 상품 재고는 보이는 옵션 재고의 합, 품절은 재고가 남은 보이는 옵션이 하나도 없을 때입니다. 상품을 저장한 뒤와, 주문으로 재고를 줄이거나 돌려놓을 때 같은 셈을 써요. 화면은 옵션이 있으면 상품 재고 칸을 잠그고 합계를 보여 줍니다.
- **지금 없는 옵션 주문은 막기:** 지웠거나 숨긴 옵션으로 주문하면 409와 함께 "장바구니에서 옵션을 다시 골라 주세요"를 보냅니다.
- **주문에는 그때 이름을 남기기:** 옵션은 나중에 이름이 바뀌거나 지워질 수 있어서, 결제 직전 고른 옵션 이름을 주문 품목에 따로 적어 둡니다.

## 코드로 보기 (개념 재현)

```java
// 옵션 저장: 지우고 다시 넣지 않고, 번호를 유지한다
@Transactional
public void saveOptions(UUID productId, List<OptionInput> inputs) {
    List<OptionRow> current = optionRepo.findByProduct(productId); // 지금 이 상품의 옵션
    Map<UUID, OptionRow> byId = new HashMap<>();
    Map<String, OptionRow> byName = new HashMap<>();
    for (OptionRow row : current) {
        byId.put(row.id(), row);
        byName.put(row.group() + "/" + row.value(), row);           // 예: "사이즈/M"
    }

    Set<UUID> kept = new HashSet<>();
    for (OptionInput in : inputs) {
        // 1) 보낸 번호가 이 상품의 옵션이면 그 번호
        // 2) 아니면 같은 그룹·값의 옵션 번호 (화면이 번호를 안 보내도 이어진다)
        OptionRow existing = (in.id() != null && byId.containsKey(in.id()))
            ? byId.get(in.id())
            : byName.get(in.group() + "/" + in.value());

        if (existing != null && !kept.contains(existing.id())) {
            optionRepo.update(existing.id(), in);   // 번호는 그대로, 값(추가금·재고·노출)만 고친다
            kept.add(existing.id());
        } else {
            // 3) 남의 상품 옵션 번호를 보냈어도 그 행은 건드리지 않고 새로 만든다
            kept.add(optionRepo.insert(productId, in));
        }
    }

    // 4) 새 목록에서 빠진 옵션만 지운다
    for (OptionRow row : current) {
        if (!kept.contains(row.id())) {
            optionRepo.delete(row.id());
        }
    }

    recalcStockFromOptions(productId); // 상품 재고 = 보이는 옵션 재고 합계
}
```

```sql
-- 옵션 상품의 재고와 품절을 옵션에서 센다 (숨긴 옵션은 빼고)
UPDATE product p
SET stock    = s.total,
    sold_out = (s.in_stock = 0)
FROM (
    SELECT product_id,
           COALESCE(SUM(stock), 0)           AS total,     -- 보이는 옵션 재고 합계
           COUNT(*) FILTER (WHERE stock > 0) AS in_stock   -- 재고가 남은 보이는 옵션 수
    FROM product_option
    WHERE product_id = :productId
      AND visible = true
    GROUP BY product_id
) s
WHERE p.id = s.product_id;
```

테스트는 재고 칸이 비어 있어도 옵션 재고가 있으면 품절이 아닌지, 다시 저장해도 같은 옵션 번호가 유지되고 빠진 옵션만 지워지는지, 남의 옵션 번호로 덮을 수 없는지, 지금 없는 옵션 주문이 409인지를 봤습니다.

## 💡 배운 것

**"지우고 다시 넣기"는 번호를 바꿉니다.** 화면에서는 같은 옵션이어도 DB에서는 새 행이라, 그 번호를 들고 있던 장바구니·주문이 모두 길을 잃어요. 다른 곳에서 가리키는 행은 번호를 유지한 채 고쳐야 했습니다.

**같은 실수를 두 번째 만났습니다.** [2026-10-07 글](2026-10-07-지우고-다시-넣는-저장이-연결된-기록까지-지웠다.md)에서는 주문을 저장할 때 품목을 지웠다 다시 넣어 반품 기록이 사라졌는데, 이번엔 옵션이었어요. 이제 저장 코드에서 DELETE 가 보이면 "누가 이 번호를 들고 있나"부터 찾습니다.

**같은 값을 두 곳에 두면 기준을 하나로 정해야 합니다.** 상품 재고와 옵션 재고가 따로 있으니 어긋났어요. 옵션 상품은 옵션을 기준으로 하고, 상품 재고는 거기서 계산하게 했습니다.

**바뀔 수 있는 값은 주문에 그때 값으로 남깁니다.** 주문은 지나간 일의 기록이라, 지금 상품 정보를 따라가면 안 됐어요.

## 소감

품절 하나를 고치러 들어갔다가, 주문 금액과 재고가 틀어질 수 있는 문제를 찾았습니다. 작은 증상 뒤에 저장 방식이 있었고, 고치는 범위를 증상이 아니라 원인에 맞추는 게 중요하다는 걸 다시 느꼈어요.

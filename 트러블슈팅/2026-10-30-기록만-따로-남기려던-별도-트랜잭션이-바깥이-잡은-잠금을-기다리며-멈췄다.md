# 2026-10-30 기록만 따로 남기려던 별도 트랜잭션이, 바깥이 잡은 잠금을 기다리며 멈췄다

> 태그: #트러블슈팅 #PostgreSQL #트랜잭션 #잠금 #외래키 #Spring

## 무엇을 / 왜

결제사 승인을 되돌린(망취소) 기록은, 바깥 결제 처리가 되돌려져도 남아야 했습니다. 처음에는 이 기록을 별도 트랜잭션으로 바로 쓰려 했습니다. 스프링에서 `REQUIRES_NEW` 로 새 트랜잭션을 열면 바깥과 따로 커밋되니, 바깥이 롤백돼도 기록은 남을 거라고 생각했습니다.

그런데 시험을 돌려 보니 결제 처리가 끝나지 않고 그대로 멈췄습니다. 오류도 나지 않고, 시간 제한에 걸릴 때까지 기다리기만 했습니다.

## 어떻게 풀었나

### 같은 스레드 안에서, 두 연결이 서로를 기다리고 있었습니다

찾아보니 이런 순서였습니다.

1. 바깥 결제 처리는 주문을 바꾸기 전에 그 주문 행을 잠갔습니다(`SELECT ... FOR UPDATE`).
2. 망취소 기록 표는 주문을 외래 키로 가리키고 있었습니다.
3. `REQUIRES_NEW` 는 바깥 트랜잭션을 잠시 세워 두고, 새 데이터베이스 연결로 새 트랜잭션을 열었습니다.
4. 새 트랜잭션이 기록을 넣자, PostgreSQL 은 외래 키가 가리키는 주문 행이 그 사이 지워지지 않게 그 행에 공유 잠금(`FOR KEY SHARE`)을 잡으려 했습니다.
5. 그 행은 바깥 트랜잭션이 `FOR UPDATE` 로 잡고 있었고, 두 잠금은 함께 잡을 수 없어서 새 트랜잭션은 기다렸습니다.
6. 바깥 트랜잭션은 새 트랜잭션이 끝나기를 기다리며 멈춰 있었습니다. 같은 스레드여서 바깥이 먼저 끝날 길이 없었습니다.

데이터베이스에서 보면 서로 다른 두 연결이 차례를 기다리는 것뿐이어서, 교착 상태로 알아채지 못했습니다. 두 연결이 같은 스레드에 묶여 있다는 건 데이터베이스가 모르는 일이었습니다. 그래서 오류 없이 멈춰 있었던 것이었습니다.

### 기록은 바깥 트랜잭션이 끝난 뒤에 쓰게 했습니다

바깥 트랜잭션이 끝나면(커밋이든 롤백이든) 잡고 있던 잠금이 풀렸습니다. 그래서 기록은 트랜잭션 동기화의 `afterCompletion` 에서 새 트랜잭션으로 쓰게 했습니다. 이때는 잠금이 이미 풀려 있어 기다리지 않았고, 바깥이 롤백돼도 기록은 남았습니다. 이 기록을 쓰다 실패하면 바깥 결과는 그대로 두고 서버 기록에만 남기게 했습니다.

## 코드로 보기 (개념 재현)

```sql
-- 바깥 트랜잭션 (연결 A)
BEGIN;
SELECT * FROM shop_order WHERE id = 1 FOR UPDATE;    -- 주문 행 잠금

-- 같은 요청 안에서 REQUIRES_NEW 로 연 새 트랜잭션 (연결 B)
BEGIN;
INSERT INTO cancel_log (id, order_id, amount) VALUES (10, 1, 12000);
-- 외래 키를 확인하려고 shop_order id=1 행에 FOR KEY SHARE 를 잡으려 한다
-- -> 연결 A 의 FOR UPDATE 와 부딪혀 기다린다
-- 연결 A 는 연결 B 가 끝나야 다음 줄로 간다 -> 둘 다 멈춘다
```

```java
// 처음 시도 - 멈췄다 (개념 재현 - 실제 이름과 다름)
@Transactional
public void onPaymentReturn(UUID orderId) {
    ShopOrder order = orders.lockForUpdate(orderId);          // 연결 A: FOR UPDATE
    // ...
    newTransaction.execute(s -> cancelLogs.save(cancelLog));  // 연결 B: 외래 키 확인이 A 의 잠금을 기다린다
    // ...
}

// 고친 것 - 바깥이 끝난 뒤에 쓴다
@Transactional
public void onPaymentReturn(UUID orderId) {
    ShopOrder order = orders.lockForUpdate(orderId);
    // ...
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCompletion(int status) {             // 커밋이든 롤백이든, 잠금이 풀린 뒤
            try {
                newTransaction.execute(s -> cancelLogs.save(cancelLog));
            } catch (RuntimeException ex) {
                log.error("기록을 남기지 못했습니다", ex);     // 바깥 결과는 이미 정해졌다 - 던지지 않는다
            }
        }
    });
    // ...
}
```

## 💡 배운 것

- `REQUIRES_NEW` 는 "따로 커밋되는 트랜잭션"이기 전에 "다른 데이터베이스 연결"이었습니다. 같은 스레드에서 바깥이 잡은 잠금과 부딪히면 바깥은 먼저 끝날 수 없어서 그대로 멈췄습니다.
- 외래 키가 있는 표에 행을 넣기만 해도, 가리키는 행에 잠금을 잡는다는 걸 알게 됐습니다. 그 행을 바깥이 `FOR UPDATE` 로 잡고 있으면 기다리게 됐습니다.
- 데이터베이스는 이런 기다림을 교착 상태로 알아채지 못했습니다. 그래서 오류가 아니라 멈춤으로 나타났습니다.
- 되돌려져도 남겨야 하는 기록은 바깥 트랜잭션이 끝난 뒤에 쓰는 편이 안전했습니다.

## 소감

예전에 알림 보내기를 별도 트랜잭션으로 빼서 문제를 푼 적이 있어서, 이번에도 같은 방법이면 될 거라고 생각했습니다. 그런데 별도 트랜잭션이 바깥과 같은 행을 건드리면 오히려 멈출 수 있었습니다. 시험이 멈춰 준 덕분에 운영에 나가기 전에 알 수 있었습니다.

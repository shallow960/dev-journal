# 2026-09-16 정책은 다 걸려 있었는데, 표 주인은 정책을 건너뛴다

> 태그: #트러블슈팅 #멀티테넌트 #데이터베이스 #권한

## 무엇을 / 왜

한 코드베이스로 여러 가게를 돌리는 서비스라, 데이터는 가게 단위로 갈려 있어야 합니다. 그 칸막이를 애플리케이션 조건문이 아니라 **데이터베이스 기능(행 수준 보안)** 으로 걸어 뒀습니다. 조건을 빠뜨린 조회가 하나라도 있으면 남의 가게 데이터가 나가기 때문에, 데이터베이스가 마지막 방어선이 되어야 한다고 봤거든요.

구조는 이렇습니다.

```
접속할 때 "지금 어느 가게인가" 를 연결 설정값으로 넣는다
  → 표마다 붙은 정책이 그 값과 같은 행만 보여 준다
```

표 200여 개에 정책을 다 붙였고, 시험도 통과했습니다. 그런데 운영에서 **서로 다른 두 가게가 같은 목록을 돌려주는** 것을 봤습니다.

## 어떻게 풀었나

### 먼저 의심한 것과, 실제 원인

정책 설정부터 봤습니다. 정책은 살아 있었고 조건도 맞았습니다. 그래서 정책이 아니라 **누가 접속하고 있는지** 를 봤어요.

애플리케이션이 **데이터베이스 관리자 계정** 으로 붙고 있었습니다. 설치할 때 그 계정으로 시작해서 그대로 쓰고 있었던 거죠. 그리고 PostgreSQL 에는 이런 규칙이 있습니다.

- **표를 만든 주인은 자기 표의 정책을 적용받지 않는다**
- 강제 옵션을 켜도, 관리자급 권한이면 여전히 빠져나간다

즉 정책을 아무리 잘 걸어도 **그 계정으로 접속하는 한 전부 보입니다.** 칸막이가 있는 줄 알았는데, 실제로는 없는 것과 같았습니다.

### 고치기 전에 "지금 잘못됐다" 를 숫자로 남긴다

바로 고치지 않고, 같은 조회를 두 계정으로 돌려 숫자를 먼저 기록했습니다.

```
관리자 계정 : A가게 4건, B가게 4건   (같은 4건 = 칸막이 없음)
새 앱 계정  : A가게 4건, B가게 0건   (갈림)
```

이 숫자가 없으면 "고쳤다" 를 증명할 방법이 없습니다. 고치고 나서 잘 되면 원래 잘 됐던 것처럼 보이니까요.

### 권한이 낮은 앱 전용 계정으로 갈아끼운다

정책을 손대는 대신 **접속 계정을 바꿨습니다.**

- **앱** : 권한이 낮은 전용 계정. 읽고 쓰기만 되고 표를 소유하지 않는다 → 정책이 그대로 적용된다
- **표를 만드는 작업(마이그레이션)** : 기존 소유자 계정. 이건 정책을 건너뛰어야 정상이다

여기서 한 가지 함정이 있었습니다. **앞으로 만들어질 표에는 권한이 자동으로 붙지 않습니다.** 마이그레이션이 새 표를 만들면 그 표만 앱 계정에게 "권한 없음" 이 되어, 그 기능만 통째로 죽습니다. 기본 권한을 걸어 두고, 새 표를 만드는 마이그레이션 안에서도 권한 부여를 한 번 더 하게 했습니다.

## 코드로 보기 (개념 재현)

```sql
-- 정책은 이렇게 걸려 있었다. 설정값과 같은 가게의 행만 보인다.
alter table 주문 enable row level security;
alter table 주문 force row level security;   -- 주인에게도 적용하겠다는 옵션

create policy 가게격리 on 주문
  using (가게id = nullif(current_setting('app.가게id', true), '')::uuid);
```

```sql
-- 그런데 접속 계정이 표의 주인(=관리자)이면 위 정책이 의미가 없다.
-- 그래서 앱 전용 계정을 따로 만든다. 표를 소유하지 않는 계정이다.
create role 앱계정 login password '...';

grant connect on database 서비스 to 앱계정;
grant usage on schema public to 앱계정;
grant select, insert, update, delete on all tables in schema public to 앱계정;

-- ★ 앞으로 만들어질 표에도 같은 권한이 자동으로 붙게 한다.
--   이걸 빠뜨리면 새 기능을 배포할 때마다 그 표만 "권한 없음" 이 된다.
alter default privileges in schema public
  grant select, insert, update, delete on tables to 앱계정;
```

```sql
-- 새 표를 만드는 마이그레이션에는 권한 부여를 한 번 더 넣어 둔다.
-- 기본 권한 설정이 빠진 환경에서도 기능이 죽지 않게 하는 보험이다.
do $$
begin
    if exists (select 1 from pg_roles where rolname = '앱계정') then
        execute 'grant select, insert, update, delete on 새표 to 앱계정';
    end if;
end
$$;
```

확인은 두 계정으로 같은 조회를 돌려 숫자가 갈리는지를 봅니다.

```java
@Test
void 앱_계정으로_붙으면_다른_가게_데이터가_보이지_않는다() {
    가게로_접속설정(A가게);
    assertThat(주문_건수()).isEqualTo(4);

    가게로_접속설정(B가게);
    assertThat(주문_건수()).isZero();   // 관리자 계정이면 여기서 4가 나온다
}
```

## 💡 배운 것

**설정이 맞는데 동작이 다르면, 설정이 적용되는 조건을 의심합니다.** 정책 자체를 몇 번을 읽어도 답이 안 나왔습니다. 정책은 "누가 접속했는가" 에 따라 적용 여부가 달라지는 기능이었고, 저는 그 조건을 한 번도 확인하지 않았습니다.

**권한을 낮추는 것이 규칙을 정교하게 짜는 것보다 확실할 때가 있습니다.** 정책을 더 촘촘히 쓰는 방법도 있었지만, 애초에 건너뛸 수 없는 계정으로 접속하는 쪽이 실수의 여지가 적습니다.

**애플리케이션 계정과 관리 계정은 나눠야 합니다.** 편해서 관리자 계정을 쓰고 있었는데, 그 편의가 방어선 하나를 통째로 무력화하고 있었습니다.

**새로 만들어질 것에 대한 권한까지 정해 둬야 합니다.** 지금 있는 표에만 권한을 주면, 다음 배포에서 새 표가 생기는 순간 조용히 깨집니다.

**고치기 전에 잘못된 상태를 숫자로 남겨 둡니다.** 두 계정의 조회 결과를 먼저 기록해 뒀더니, 고친 뒤 무엇이 달라졌는지 설명하기가 쉬웠습니다.

## 소감

멀티테넌트를 시작할 때 "조건문은 빠뜨릴 수 있으니 데이터베이스에 맡기자" 고 정했고, 그 판단 자체는 지금도 맞다고 생각합니다. 다만 **그 기능이 언제 적용되지 않는지** 는 알아보지 않았습니다. 기능을 고를 때는 되는 조건뿐 아니라 **안 되는 조건** 까지 읽어야 한다는 걸 이번에 값을 치르고 배웠습니다.

시험에서는 잡히지 않았던 것도 남습니다. 시험은 처음부터 권한이 낮은 계정으로 돌고 있어서 늘 통과했거든요. 운영과 다른 조건으로 도는 시험은 "통과" 가 아무 의미가 없다는 것도 같이 알았습니다.

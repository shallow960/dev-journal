# 2026-08-10 문의 접수가 통째로 500이었는데, 범인은 "알림 보내기"였다

> 태그: #트러블슈팅 #트랜잭션 #Spring #예외처리

## 오늘 한 일 (요약)
- 결제 전 요청서를 받는 접수 API가 500으로 죽었다. 저장 SQL은 아무 문제가 없었다.
- 실제 예외는 `UnexpectedRollbackException: Transaction rolled back because it has been marked as rollback-only`.
- 원인은 저장 다음에 호출되는 **운영자 알림 적재**였다. 알림 테이블이 테넌트 스코프라 테넌트가 없는 요청에서 실패.
- 그 실패를 코드가 `catch` 하고 있었는데도 트랜잭션은 이미 오염된 뒤였다. 테넌트가 없으면 알림을 아예 건너뛰게 해 해결.

## 무엇을 / 왜 (증상)
접수 서비스는 이렇게 생겼다.

```java
@Transactional
public View create(Command command) {
    UUID tenantId = TenantContext.current().map(Tenant::value).orElse(null);
    jdbcClient.sql("insert into ...").update();   // ① 저장 — 정상
    View view = get(id);
    notificationService.notifyOps("CREATED", vars(view));  // ② 알림 — 여기서 실패
    return view;
}
```

그리고 알림 쪽은 이미 "실패해도 무시"하도록 방어돼 있었다.

```java
private void enqueueIfRecipient(...) {
    try {
        sendService.enqueueIfTemplateExists(channel, code, recipient, variables);
    } catch (RuntimeException ex) {
        LOGGER.warn("notification enqueue failed", ex);   // 잡아서 로그만
    }
}
```

잡고 있는데 왜 전체가 실패할까? 여기가 핵심이었다.

## 왜 "잡았는데도" 실패하나
Spring 트랜잭션에서 **DB 예외가 한 번 발생하면 그 트랜잭션에는 `rollbackOnly` 플래그가 찍힌다.** 애플리케이션 코드가 예외를 `catch` 해도 **플래그는 지워지지 않는다.** 그래서 흐름은 이렇게 간다.

```
① insert 성공
② 알림 insert 실패 → 트랜잭션에 rollback-only 표시
   └ catch 로 예외는 삼킴 (코드는 계속 진행)
③ 메서드 정상 반환
④ 커밋 시도 → "rollback-only 인데 커밋하려 한다" → UnexpectedRollbackException
⑤ 전체 롤백 + 500
```

즉 **예외를 삼켜서 오히려 원인이 감춰지고**, 실패는 커밋 시점에 엉뚱한 메시지로 터진다. 로그의 마지막 메시지("rolled back because marked as rollback-only")만 보면 저장 로직을 의심하게 되는데, 진짜 범인은 그 뒤의 부가 작업이었다.

## 어떻게 풀었나
알림 파이프라인이 **테넌트(가게) 스코프**라는 게 근본 원인이었다. 이 접수는 플랫폼 대표 도메인에서 들어와 테넌트가 없다. 그러니 적재가 성공할 수 없다.

```java
// 알림 큐는 테넌트 스코프라 플랫폼 문의처럼 테넌트가 없으면 적재가 실패한다.
// 그 실패는 catch 해도 트랜잭션이 rollback-only 로 오염돼 접수 자체가 500 이 되므로 아예 건너뛴다.
if (tenantId != null) {
    notificationService.notifyOps("CREATED", vars(view));
}
```

접수 레코드는 남으므로 운영자는 목록에서 확인할 수 있다. **본 기능(접수)이 부가 기능(알림) 때문에 죽지 않는 것**이 우선이었다.

## 더 나은 선택지들
상황에 따라 이런 방법도 있다.

- **트랜잭션 밖으로 빼기** — 커밋 후 이벤트(`@TransactionalEventListener(AFTER_COMMIT)`)로 알림을 보낸다. 부가 작업이 본 트랜잭션에 아예 참여하지 않는다.
- **별도 트랜잭션** — `@Transactional(propagation = REQUIRES_NEW)` 로 알림만 독립 트랜잭션에서 처리한다. 실패해도 바깥이 오염되지 않는다.
- **조건부 skip** — 이번처럼 실패가 예상되는 조건이 명확하면 아예 호출하지 않는다.

이번엔 "테넌트 없으면 애초에 성립하지 않는 작업"이라 세 번째를 골랐다.

## 💡 배운 것
- **`catch` 했다고 안전하지 않다.** DB 예외는 트랜잭션에 흔적(rollback-only)을 남기고, 그건 커밋 때 터진다.
- 부가 작업(알림·로그·집계)은 **본 트랜잭션에 태우지 않는 게 기본**이다. 커밋 후 이벤트나 별도 트랜잭션으로 분리한다.
- `UnexpectedRollbackException` 이 보이면 **그 트랜잭션 안에서 먼저 실패한 다른 작업**을 찾아야 한다. 마지막 메시지는 결과일 뿐 원인이 아니다.
- 멀티테넌트에서 **테넌트를 전제로 만든 기능을 테넌트 없는 경로에서 호출**하면 이런 식으로 조용히 번진다.

## 소감
"저장은 되는데 왜 500이지?"에서 한참 헤맸다. 예외를 잡아둔 코드가 오히려 원인을 가리고 있었던 게 인상적이었다. 앞으로 트랜잭션 안에서 알림·외부 호출 같은 부가 작업을 부를 때는 "여기서 실패하면 본 작업이 죽나?"를 먼저 확인해야겠다.

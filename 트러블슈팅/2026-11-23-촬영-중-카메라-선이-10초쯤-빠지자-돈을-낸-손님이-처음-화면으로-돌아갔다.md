# 2026-11-23 촬영 중 카메라 선이 10초쯤 빠지자, 돈을 낸 손님이 처음 화면으로 돌아갔다

> 태그: #트러블슈팅 #카메라 #장애복구 #결제 #키오스크

## 무엇을 / 왜

사진 키오스크는 손님이 결제를 마친 뒤 촬영 화면에서 카운트다운을 세고 사진을 찍었습니다. 시험 키오스크에서 촬영 도중 카메라 USB 를 10초쯤 뽑아 보니, 화면이 점검 화면으로 넘어갔다가 처음 화면으로 돌아갔습니다. 돈을 낸 손님의 촬영이 통째로 사라진 것이었습니다. 2~3초 안에 다시 꽂으면 그대로 이어졌습니다.

## 어떻게 풀었나

### 실패를 받자마자 끝내고 있었다

흐름을 따라가 보니 이랬습니다.

1. 카메라가 끊겨도 촬영 화면의 카운트다운은 계속 돌았습니다.
2. 카운트다운이 끝나 셔터를 누르면, 카메라 쪽 프로그램은 끊긴 것을 알고 바로 '끊김' 으로 실패를 돌려줬습니다.
3. 촬영 화면은 그 실패를 받자마자 점검 화면을 띄우고 손님을 처음 화면으로 돌려보냈습니다.

[2026-10-27 글](2026-10-27-USB-를-다시-꽂아도-카메라는-죽은-연결을-붙잡고-있었다.md)에서 카메라가 끊긴 걸 알면 셔터를 기다리게 하지 말고 바로 실패를 알리게 고쳤고, 다시 꽂으면 저절로 붙게도 했습니다. 장치 쪽은 그대로 맞았습니다. 문제는 화면 쪽이 그 실패를 '이 손님은 끝' 으로 받은 것이었습니다. 다시 붙을 수 있는 카메라를 화면이 기다려 주지 않았습니다.

### 멈추고, 기다리고, 끝내 안 되면 기록 남기기

- **끊긴 걸 빨리 알기:** 카메라 상태 확인이 '준비 안 됨' 으로 바뀌거나, 셔터가 '끊김' 으로 실패하면 끊김으로 봤습니다. 촬영 화면에 들어올 때 이미 끊겨 있는 경우도 같게 다뤘습니다.
- **멈추고 기다리기:** 끊기면 카운트다운과 셔터를 멈추고, 손님에게는 "카메라 연결이 끊겼습니다 - 다시 연결하는 중입니다 (N초)" 를, 직원에게는 카메라 프로그램이 알려 준 사유 한 줄을 보이게 했습니다. 그동안에는 앱 전체의 카메라 점검 창을 띄우지 않고 촬영 화면이 맡게 했습니다.
- **다시 붙었는지는 화면으로 확인:** 상태가 '준비됨' 으로 돌아온 것만으로 이어 찍지 않았습니다. 카메라가 다시 붙은 뒤 라이브뷰를 다시 켜는 단계가 한 번 더 있어서, 그 뒤에 라이브뷰 프레임이 실제로 들어오는 것까지 보고 멈췄던 장부터 카운트다운을 다시 셌습니다.
- **기다림에 끝 두기:** 60초 안에 돌아오지 않거나, 한 번의 촬영에서 네 번째로 끊기면 그만 기다렸습니다.
- **그만둘 때 돈 기록 남기기:** 카드·현금·간편결제로 돈을 받은 손님이면 결제 수단·금액·이미 적은 매출 번호와 사유를 직원 화면의 '확인이 필요한 결제' 에 남기고, 서버에도 오류 기록을 보낸 뒤 점검 화면으로 갔습니다. 그 줄에는 환불하는 순서를 적어 두었고, 매출 번호를 함께 적어 '매출로 확정' 으로 같은 손님의 매출이 두 번 생기지 않게 막았습니다.

## 코드로 보기 (개념 재현)

이름은 바꾼 더미입니다.

```js
const LIMIT_MS = 60_000; // 다시 연결을 기다리는 최대 시간
const MAX_HOLDS = 3;     // 한 촬영에서 기다려 주는 횟수 (네 번째 끊김이면 그만)

// 끊김을 알았을 때: 기다림을 시작할지, 바로 그만둘지
function onCameraLost(shotTurn, t) {
  if (shotTurn.lostCount >= MAX_HOLDS) return 'stopWaiting';
  shotTurn.lostCount += 1;
  shotTurn.waitInfo = { lostAt: t, upSince: null };
  return 'keepWaiting'; // 카운트다운과 셔터를 멈추고 "다시 연결하는 중입니다" 를 띄운다
}

// 기다리는 동안 1초마다: '준비됨' 이 된 뒤에 라이브뷰 프레임이 와야 이어 찍는다
function holdStep(waitInfo, t, cameraUp, lastPictureAt) {
  if (!cameraUp) waitInfo.upSince = null;                  // 아직(또는 다시) 끊김
  else if (waitInfo.upSince == null) waitInfo.upSince = t; // '준비됨' 이 된 때
  const after = waitInfo.upSince ?? waitInfo.lostAt;
  if (cameraUp && lastPictureAt != null && lastPictureAt > after) return 'shootAgain';
  if (t - waitInfo.lostAt >= LIMIT_MS) return 'stopWaiting';
  return 'keepWaiting';
}

const w = { lostAt: 0, upSince: null };
holdStep(w, 5_000, false, null);   // 'keepWaiting' (아직 끊김)
holdStep(w, 12_000, true, null);   // 'keepWaiting' (준비됨이 됐지만 라이브뷰 프레임이 아직 없다)
holdStep(w, 12_400, true, 12_300); // 'shootAgain'  -> 멈췄던 장부터 카운트다운을 다시
holdStep({ lostAt: 0, upSince: null }, 60_000, false, null); // 'stopWaiting'

// 그만둘 때: 돈을 받은 손님은 조용히 버리지 않는다
function whenStopped(order, why, reviewBox) {
  if (['card', 'cash', 'easyPay'].includes(order.payMethod)) {
    reviewBox.push({ saleNo: order.saleNo, amount: order.amount, why }); // 직원이 환불하거나 다시 찍어 준다
  }
  return 'repairNotice'; // 점검 화면
}
```

## 💡 배운 것

- 장치가 실패를 빨리 알리는 것과, 화면이 그 실패에 무엇을 끝낼지는 다른 문제였습니다. 장치 쪽은 빨리 알리고, 화면 쪽은 돈을 낸 손님을 앞에 두고 기다릴지 끝낼지를 따로 정해야 했습니다.
- '준비됨' 이라는 값 하나만 믿지 않고 실제로 화면이 들어오는지까지 봐야 한다는 걸 [2026-10-27 글](2026-10-27-USB-를-다시-꽂아도-카메라는-죽은-연결을-붙잡고-있었다.md)에 이어 다시 배웠습니다. 그때는 선이 빠졌는데도 '연결됨' 으로 남아 있었고, 이번에는 '준비됨' 이 된 뒤에도 라이브뷰가 다시 켜지기까지 한 단계가 더 있었습니다.
- 끝내 못 한 일은 직원이 볼 수 있는 곳에 사유와 함께 남겨야 한다는 걸 [2026-11-18 글](2026-11-18-영상을-만드는-도중에-프로그램이-꺼지면-영상도-실패-기록도-남지-않았다.md)에 이어 다시 배웠습니다. 그때는 프로그램이 꺼지는 경우였고, 이번에는 카메라가 돌아오지 않는 경우였습니다.

# 2026-10-15 주문 상태를 한 번에 바꾸자, 이미 환불한 품목까지 따라 바뀌었다

> 태그: #트러블슈팅 #상태관리 #도메인모델 #Java

## 무엇을 / 왜

주문 하나에는 품목이 여러 개 있고, 품목마다 상태가 따로 있습니다. 상품 하나만 반품하면 그 품목만 '반품 완료'가 되고, 나머지 품목은 계속 배송 흐름을 타요.

그런데 주문 단위로 상태를 바꾸는 함수(구매확정, 발송, 배송완료)가 그 주문의 품목을 **전부 같은 상태로 덮어쓰고** 있었습니다. 그래서 이런 일이 생길 수 있었어요.

- 품목 하나를 이미 반품·환불했는데 손님이 구매확정을 누르면, 그 품목까지 '구매확정'이 됐습니다.
- 구매확정 품목은 판매자 정산과 적립금 계산에 들어가니, 이미 돌려준 돈의 정산금과 적립금이 다시 생겼어요.
- 구매확정 품목은 반품을 다시 신청할 수 있어서, 같은 품목을 두 번 반품할 수도 있었습니다.
- 운영자가 주문을 '발송'으로 바꿀 때도 취소된 품목이 배송중으로 되살아났습니다.

반품 기능은 품목 단위로 잘 동작했는데, 그 뒤에 누르는 주문 단위 버튼이 결과를 덮어쓰고 있었던 거예요.

## 어떻게 풀었나

- 주문 단위 변경이 **옮길 품목을 고르게** 했습니다. 정상 흐름에 있는 품목, 또는 지금까지 주문과 같은 상태로 움직이던 품목만 옮기고, 취소·반품·교환으로 빠진 품목은 그대로 둡니다.
- 반품·교환이 **진행 중인 주문은 손님이 구매확정할 수 없게** 막았습니다(409). 처리가 끝난 뒤에 확정하면 돼요.
- 구매확정 적립금(결제액의 1%)은 **결제액에서 이미 돌려준 금액을 뺀 값**으로 계산했습니다.
- 코드를 고쳐도 이미 덮어써진 데이터는 남아 있으니, 그런 행을 찾는 **읽기 전용 조회**를 따로 만들었습니다.

## 코드로 보기 (개념 재현)

```java
// 문제: 주문 상태를 바꾸면서 품목을 전부 같은 상태로 덮어쓴다
public void changeStatus(OrderStatus next) {
    this.status = next;
    for (LineItem item : items) {
        item.setStatus(next);   // 이미 반품 완료된 품목도 '구매확정'이 된다
    }
}
```

```java
// 고침: 주문을 따라가야 하는 품목만 옮긴다
public void changeStatus(OrderStatus next) {
    OrderStatus previous = this.status;
    this.status = next;
    for (LineItem item : items) {
        boolean inNormalFlow = item.status().isNormalFlow();  // 결제완료·배송준비·배송중 같은 흐름
        boolean followsOrder = item.status() == previous;     // 지금까지 주문과 같이 움직이던 품목
        if (inNormalFlow || followsOrder) {
            item.setStatus(next);
        }
        // 취소·반품·교환으로 빠진 품목은 그 상태를 그대로 둔다
    }
}

// 손님 구매확정: 반품·교환이 열려 있으면 받지 않는다
public void confirmByCustomer() {
    boolean claimOpen = items.stream().anyMatch(LineItem::hasOpenClaim);
    if (claimOpen) {
        throw new ConflictException("반품·교환이 진행 중이라 구매확정할 수 없어요");  // 409
    }
    changeStatus(OrderStatus.CONFIRMED);
}
```

## 💡 배운 것

**위에서 한 번에 바꾸는 코드는 아래의 사정을 모릅니다.** 주문과 품목이 각자 상태를 가지면, 주문 단위 변경은 "어떤 품목을 따라오게 할지"를 먼저 정해야 했어요.

**상태 버그는 곧 돈 버그였습니다.** 품목 상태 하나가 정산 대상, 적립금, 반품 가능 여부를 함께 정하고 있어서, 상태가 덮어써지면 돈 계산이 전부 따라 틀어졌습니다.

**고친 뒤에도 이미 잘못된 데이터가 남습니다.** 코드 수정과 별개로, 이미 덮어써진 행을 찾아보는 조회를 준비해 두어야 했어요.

## 소감

반품 기능을 만들 때는 품목 단위로 잘 되는 걸 확인하고 끝냈는데, 그 다음에 누르는 버튼까지는 따라가 보지 않았습니다. 기능 하나를 볼 때 그 뒤에 이어지는 동작까지 같이 봐야 한다는 걸 배웠어요.

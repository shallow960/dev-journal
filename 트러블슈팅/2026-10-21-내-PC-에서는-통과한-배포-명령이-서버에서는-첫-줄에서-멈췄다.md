# 2026-10-21 내 PC 에서는 통과한 배포 명령이, 서버에서는 첫 줄에서 멈췄다

> 태그: #트러블슈팅 #줄끝 #CRLF #배포 #PowerShell #bash #git

## 무엇을 / 왜

Windows PC 에서 리눅스 서버로 배포하는 스크립트가 있습니다. PowerShell 스크립트가 서버에서 실행할 셸 명령을 **여러 줄 문자열**로 만들고, 클라우드의 원격 명령 실행 기능으로 서버에 보내요. 명령 첫 줄은 흔히 쓰는 안전장치입니다.

```bash
set -euo pipefail
```

새 서버에 처음 배포하자, 서버가 바로 그 첫 줄에서 멈췄어요.

```
line 1: set: pipefail: invalid option name
```

원인은 줄 끝이었습니다.

- 저장소의 PowerShell 파일은 Windows 작업 폴더에서 **CRLF(\r\n)** 줄 끝으로 체크아웃돼 있었어요.
- 여러 줄 문자열은 파일에 적힌 줄 끝을 그대로 가져갑니다. 그래서 서버로 간 명령도 CRLF 였어요.
- 리눅스 bash 는 \r 을 줄 끝으로 보지 않고 글자로 읽습니다. `pipefail` 뒤에 \r 이 붙은 옵션 이름은 없으니 첫 줄에서 실패했어요.

더 곤란했던 건 **내 PC 에서는 같은 스크립트가 통과한다**는 점이었어요. Windows 의 Git Bash 는 줄 끝 \r 을 너그럽게 넘겨서, PC 에서 아무리 시험해도 이 실패가 보이지 않았습니다.

같은 뿌리의 문제가 하나 더 있었어요. 서버로 보내는 배포 묶음을 `git archive` 로 만드는데, Windows 에서 줄 끝 변환이 켜져 있으면 **줄 끝 규칙이 없는 파일은 묶음 안에서 CRLF 로 바뀝니다.** 셸 스크립트는 규칙이 있어서 괜찮았지만, 서버의 서비스 설정(systemd 유닛) 파일에는 규칙이 없어서 묶음 안에 CR 이 들어가 있었어요(실제 파일에서 12개). 서버가 읽는 설정 파일에 CR 이 섞이면 위험해서, 이건 배포 전에 막았습니다.

## 어떻게 풀었나

1. **보내기 직전에 CR 을 지웁니다.** 서버로 보내는 명령 문자열에서 \r 을 모두 없애요. 원격 명령을 보내는 공용 함수에도 같은 처리를 넣어, 다른 스크립트가 여러 줄 문자열을 보내도 안전하게 했습니다.
2. **리눅스에서 읽는 파일은 저장소 규칙으로 LF 를 고정했습니다.** 셸 스크립트뿐 아니라 서비스 설정, 타이머, Dockerfile, 웹 서버 설정 파일까지 `text eol=lf` 를 줬어요. 그러면 Windows 에서 묶음을 만들어도 LF 로 나옵니다.
3. **실제 리눅스 bash 로 재현했습니다.** PC 의 Git Bash 가 아니라 리눅스 컨테이너에서 같은 스크립트를 돌려, CRLF 는 실패하고 LF 는 통과하는 걸 확인했어요. 그 뒤 다시 배포하니 서버 명령이 끝까지 돌았고, 묶음 속 CR 은 0개가 됐습니다.

## 코드로 보기 (개념 재현)

**① 같은 스크립트, 줄 끝만 다르게.** 파일 이름은 더미입니다.

```bash
# CRLF 로 끝나는 스크립트와 LF 로 끝나는 스크립트를 만든다
printf 'set -euo pipefail\r\necho "first line passed"\r\n' > crlf.sh
printf 'set -euo pipefail\necho "first line passed"\n'     > lf.sh

bash crlf.sh   # Windows 의 Git Bash: 통과한다 (CR 을 너그럽게 넘김)

# 리눅스 bash 로 돌리면 (컨테이너, 폴더를 읽기 전용으로 붙임)
docker run --rm -v "$PWD:/w:ro" --entrypoint bash some-linux-image /w/crlf.sh
docker run --rm -v "$PWD:/w:ro" --entrypoint bash some-linux-image /w/lf.sh
```

실제로 돌린 출력입니다.

```
# Git Bash
first line passed
exit=0
# 리눅스 bash, CRLF
/w/crlf.sh: line 1: set: pipefail: invalid option name
exit=2
# 리눅스 bash, LF
first line passed
exit=0
```

**② 묶음을 만들 때 줄 끝이 바뀐다.**

```bash
git init demo && cd demo
git config core.autocrlf true                       # Windows 기본에 가까운 설정
printf '[Unit]\nDescription=demo\n' > demo.service   # 저장소에는 LF 로 들어간다
git add demo.service && git commit -m init

git show HEAD:demo.service | tr -cd '\r' | wc -c                      # 저장소 안: CR 0
git archive HEAD demo.service | tar -xO | tr -cd '\r' | wc -c         # 묶음 안: CR 2

printf '*.service text eol=lf\n' > .gitattributes   # 리눅스용 파일은 LF 고정
git add .gitattributes && git commit -m attrs
git archive HEAD demo.service | tar -xO | tr -cd '\r' | wc -c         # 묶음 안: CR 0
```

실제로 돌린 출력은 순서대로 `0`, `2`, `0` 이었습니다. 저장소 안의 파일은 멀쩡한데, 묶음을 만드는 순간 바뀌는 거예요.

## 💡 배운 것

**리눅스에서 도는 것의 줄 끝은 따로 지켜야 한다는 걸 다시 배웠습니다.** 2026-10-20 에 커밋 전 검사에 "리눅스용 파일의 CR" 검사를 넣었는데, 이번에 걸린 건 커밋된 파일이 아니었어요. 스크립트가 **만들어 보내는 문자열**과, 묶음을 **만드는 순간** 바뀌는 줄 끝이었습니다. 파일만 보면 안 되고, 서버에 실제로 도착하는 내용을 봐야 했어요.

**시험은 실제로 돌 곳과 같은 환경에서 해야 한다는 걸 배웠습니다.** PC 의 셸이 너그러우면 시험은 통과하고 서버만 실패해요. 리눅스 컨테이너 하나로 바로 재현됐습니다.

**git 의 묶음 만들기도 줄 끝 규칙을 따른다는 걸 배웠습니다.** 저장소 안이 LF 여도, 줄 끝 변환이 켜진 PC 에서 만든 묶음은 규칙이 없는 파일을 CRLF 로 바꿔요. 리눅스에서 읽을 파일 종류는 규칙으로 못 박아 두는 게 확실했습니다.

## 소감

오류 메시지에는 `pipefail` 만 보이고 \r 은 보이지 않아서, 처음엔 bash 버전 문제인 줄 알았어요. "보이지 않는 글자" 를 먼저 의심하는 습관이 하나 생겼습니다.

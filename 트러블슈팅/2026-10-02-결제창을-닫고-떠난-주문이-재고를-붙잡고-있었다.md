# 2026-10-02 결제창을 닫고 떠난 주문이, 재고를 붙잡고 있었다

> 태그: #트러블슈팅 #주문 #재고 #결제 #경쟁조건 #행잠금 #Spring

## 무엇을 / 왜

쇼핑몰 주문서에서 "결제하기" 를 누르면 이런 순서로 진행됩니다.

```
주문 생성(결제 대기) → 재고·쿠폰·적립금 잡기 → PG 결제창 → 손님 인증 → 돌아와서 승인 → 결제 완료
```

재고를 주문 만들 때 잡는 건 품절 상품이 여러 사람에게 팔리지 않게 하려는 것입니다. 그런데 손님이 **결제창을 닫고 떠나면**, 그 주문이 "결제 대기" 로 영영 남아 재고를 계속 잡고 있었습니다. 한정 수량 상품은 다른 손님이 살 수 없었어요.

게다가 손님이 그 주문을 직접 취소하려고 해도 오류가 났습니다. 취소 코드가 "승인된 결제를 PG에서 취소" 하는 길로만 가서, 아직 승인되지 않은 결제를 조정할 수 없다며 막혔기 때문입니다.

## 어떻게 풀었나

### 몇 분 뒤에 풀어 줄까

시간을 감으로 정하지 않으려고 다른 쇼핑몰 빌더들의 도움말을 찾아봤습니다. 한 곳은 결제를 마치지 않은 주문의 재고를 **15분 뒤** 되돌리고 있었고, 다른 곳은 주문을 취소하면 재고를 자동으로 복구하는 설정을 두고 있었습니다. 결제창도 열고 10분이 지나면 만료돼서 15분이면 충분하다고 판단했습니다.

그래서 1분마다 "15분이 지난 결제 대기 주문" 을 찾아 취소하고, 재고·쿠폰·적립금을 되돌리는 작업을 만들었습니다.

### 진짜 문제: 늦게 돌아온 손님

까다로운 경우는 손님이 결제창에 오래 머물다 **15분이 넘어서 돌아올 때** 였습니다. 원래 순서는 이랬습니다.

```
돌아옴 → PG에 승인 요청(여기서 돈이 빠짐) → 주문 상태를 "결제 완료" 로
```

자동 취소가 그 사이에 주문을 닫아 버렸다면, PG 승인은 이미 끝났는데 주문은 "취소" 라서 상태를 바꾸지 못하고 실패합니다. **손님 돈은 빠졌는데 주문은 없는** 상황이 생길 수 있는 거죠.

그래서 순서를 바꿨습니다.

```
돌아옴 → 주문 행을 잠그고(SELECT ... FOR UPDATE) → 아직 결제 대기인가? → 그때만 PG 승인
```

자동 취소 작업도 **같은 주문 행을 잠그고 다시 확인** 한 뒤에만 취소합니다. 그러면 둘 중 먼저 잠근 쪽만 진행됩니다.

- 결제가 먼저 잠그면: 승인 후 "결제 완료". 자동 취소는 잠금이 풀린 뒤 보니 결제 대기가 아니라서 건너뜁니다.
- 자동 취소가 먼저 잠그면: 주문을 닫습니다. 늦게 돌아온 결제는 잠금 뒤 보니 결제 대기가 아니라서 **PG 승인을 부르지 않고** 막습니다. PG는 인증만 되고 승인되지 않은 거래를 결제하지 않으므로 돈이 빠지지 않습니다.

막힐 때는 손님에게 "결제를 마치지 않은 채 시간이 지나 주문이 취소됐어요. 돈은 빠져나가지 않았으니 다시 주문해 주세요." 라고 이유를 보여 줍니다.

### 결제 전 주문 취소

손님이나 운영자가 결제 전 주문을 취소할 때는 PG를 부르지 않고 결제 기록만 "취소" 로 닫게 했습니다. 돌려줄 돈이 없으니 취소 기록의 환불 금액은 0입니다.

### 건드리면 안 되는 주문

예전 시스템에서 옮겨 온 주문 중에도 "결제 대기" 상태가 있을 수 있었습니다. 자동 취소가 이 주문들을 한꺼번에 취소하면 재고가 잘못 늘어납니다. 그래서 **결제창을 연 기록(결제 요청)이 있는 주문만**, 그리고 옮겨 온 표시가 없는 주문만 대상으로 했습니다.

## 코드로 보기 (개념 재현)

테이블·클래스 이름은 예시입니다.

```java
// 1분마다: 결제창을 연 뒤 15분이 지난 "결제 대기" 주문을 찾는다
@Scheduled(cron = "0 * * * * *")
public void cancelExpiredUnpaid() {
    List<UUID> due = jdbc.sql("""
            select o.id from shop_order o
            where o.status = 'AWAITING_PAYMENT'
              and o.placed_at <= :cutoff
              and o.imported_from_legacy = false            -- 옮겨 온 주문은 제외
              and exists (select 1 from payment_attempt p
                          where p.order_id = o.id and p.status = 'REQUESTED')
            order by o.placed_at limit 500
            """)
        .param("cutoff", OffsetDateTime.now().minus(Duration.ofMinutes(15)))
        .query(UUID.class).list();
    due.forEach(id -> {
        try { orders.cancelUnpaid(id); } catch (RuntimeException e) { log.warn("skip {}", id, e); }
    });
}

// 자동 취소: 잠근 뒤 다시 본다
@Transactional
public boolean cancelUnpaid(UUID orderId) {
    Order order = orderRepo.lockById(orderId);              // SELECT ... FOR UPDATE
    if (order.status() != AWAITING_PAYMENT) return false;   // 그 사이 결제됐으면 손대지 않는다
    payments.closeUnpaid(orderId);                          // PG 호출 없이 결제 기록만 닫는다
    order.cancel("결제 시간 초과");
    stock.restore(order); coupons.restore(order); points.restore(order);
    return true;
}

// 결제창에서 돌아왔을 때: PG 승인보다 잠금과 확인이 먼저
@Transactional
public Payment onReturnFromPg(UUID paymentId, Map<String, String> auth) {
    Payment payment = paymentRepo.find(paymentId);
    if (payment.isApproved()) return payment;               // 같은 콜백이 두 번 와도 같은 답
    Order order = orderRepo.lockById(payment.orderId());
    if (order.status() != AWAITING_PAYMENT) {
        throw new ResponseStatusException(HttpStatus.GONE, "시간이 지나 주문이 취소됐어요");
    }
    PgResult result = pg.approve(payment, auth);             // 여기서 처음으로 돈이 움직인다
    return markPaid(order, payment, result);
}
```

## 💡 배운 것

**"먼저 만들고 나중에 결제" 하는 구조에는 만료가 같이 있어야 합니다.** 재고를 잡는 순간, 언제 놓아줄지도 함께 정해야 했습니다.

**돈이 움직이는 호출 앞에서 상태를 확인합니다.** 외부 승인부터 하고 내부 상태를 나중에 바꾸면, 그 사이에 바뀐 상태와 부딪혔을 때 되돌릴 수 없는 일이 먼저 일어납니다.

**경쟁하는 두 작업은 같은 행을 잠그고 다시 확인합니다.** 잠금만으로는 부족하고, 잠근 뒤에 "아직 내가 처리할 상태인가" 를 다시 봐야 둘 중 하나만 진행됩니다.

**일괄 작업은 대상부터 좁힙니다.** 조건 하나만 빠져도 옮겨 온 옛 데이터까지 한꺼번에 바뀔 수 있었습니다.

**숫자는 근거에서 가져옵니다.** 15분은 제 감이 아니라 다른 서비스와 결제창 유효 시간에서 나온 값이라, 바꿔야 할 때도 이유를 설명할 수 있습니다.

## 소감

처음엔 "오래된 주문을 지우는 배치" 정도로 생각했는데, 실제로 시간이 걸린 건 늦게 돌아온 결제와 자동 취소가 부딪히는 순간이었습니다. 시간 기준을 정할 때 다른 서비스의 도움말부터 찾아보는 습관이 생긴 것도 이번 작업에서 얻은 것입니다. 자동 취소, 늦은 결제 차단, 결제 전 취소는 테스트로 확인했고, 실제 PG 환경에서 늦게 돌아오는 경우는 운영에서 한 번 더 확인할 예정입니다.

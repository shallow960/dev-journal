# 2026-09-16 계정을 나눴더니 서버가 뜨지 않았다

> 태그: #트러블슈팅 #배포 #설정 #테스트

## 무엇을 / 왜

데이터베이스 접속 계정을 둘로 나눴습니다. 애플리케이션은 권한이 낮은 전용 계정으로, 표를 만드는 작업(마이그레이션)만 소유자 계정으로요.

로컬에서 확인하고 배포했는데, **서버가 뜨자마자 죽고 다시 뜨기를 반복** 했습니다. 로그에는 이렇게 찍혀 있었습니다.

```
Unable to find suitable method for url
```

마이그레이션 도구가 접속 정보를 만들다가 실패하고, 그게 기동 실패로 이어지고, 컨테이너가 재시작되고, 다시 같은 지점에서 실패하는 순환이었습니다.

## 어떻게 풀었나

### 원인: 계정만 주고 주소를 안 줬다

설정을 이렇게 바꿨었습니다.

```yaml
마이그레이션:
  사용자: 소유자계정
  비밀번호: ...
  # 주소(url)는 안 적었다. 앱 설정을 물려받겠지 하고.
```

프레임워크는 마이그레이션 도구에 별도 접속 정보가 **하나라도** 주어지면, 앱이 쓰는 연결을 물려받는 대신 **접속 정보를 처음부터 새로 만듭니다.** 그런데 주소가 없으니 만들 수가 없었던 거죠. 계정을 따로 주는 순간 주소도 같이 줘야 하는 구조였습니다.

운영을 먼저 살려야 했으므로 환경변수 한 줄로 주소를 넣어 복구하고, 설정 파일에도 같은 값을 넣었습니다.

```yaml
마이그레이션:
  주소: ${DB_URL}        # ★ 계정을 따로 주면 주소도 같이
  사용자: ${DB_소유자}
  비밀번호: ${DB_소유자_비번}
```

### 진짜 문제: 시험이 검사하지 않는 영역이 있었다

복구보다 중요한 건 "왜 시험에서 안 걸렸나" 였습니다. 확인해 보니 이랬습니다.

- 모든 시험은 **시험 전용 설정** 으로 돈다
- 시험용 설정은 접속 정보를 시험이 직접 만들어 넣는다
- 그래서 **운영에서 쓰는 설정 파일은 한 번도 읽히지 않는다**

시험이 200개가 넘게 통과하고 있었지만, **운영 설정이 올바른가** 라는 질문에는 아무도 답하고 있지 않았습니다. 설정은 코드가 아니라고 생각해서 시험 대상으로 보지 않았던 겁니다.

그래서 **운영과 같은 설정으로 실제 기동해 보는 시험** 을 만들었습니다. 컨테이너로 띄운 데이터베이스에 운영 프로필로 붙여서, 애플리케이션이 뜨는지와 칸막이(행 수준 보안)가 실제로 적용되는지까지 같이 봅니다.

## 코드로 보기 (개념 재현)

```java
/**
 * 운영 프로필로 실제 기동해 보는 시험.
 *
 * 다른 시험은 전부 시험 전용 설정으로 돈다 - 그래서 운영 설정 파일에 문제가 있어도
 * 배포 전에는 아무도 모른다. 이 시험만 운영 프로필을 그대로 읽는다.
 */
@SpringBootTest
@ActiveProfiles("운영")            // ★ 핵심: 시험 프로필이 아니다
class 운영설정_기동시험 {

    @Test
    void 운영_설정으로도_애플리케이션이_뜬다() {
        // 여기까지 왔다는 것 자체가 검증이다.
        // 마이그레이션 접속 정보가 빠지면 이 지점에서 기동이 실패한다.
        assertThat(컨텍스트).isNotNull();
    }

    @Test
    void 앱이_쓰는_계정으로는_다른_가게_데이터가_보이지_않는다() {
        가게로_접속설정(A가게);
        assertThat(주문_건수()).isEqualTo(2);

        가게로_접속설정(B가게);
        assertThat(주문_건수()).isZero();
    }
}
```

설정 자체도 "빠지면 안 되는 값" 을 눈에 띄게 적어 뒀습니다.

```yaml
# 마이그레이션에 별도 계정을 주면 접속 주소도 반드시 함께 준다.
# 계정만 주면 앱 연결을 물려받지 못하고 접속 정보를 새로 만들려다 기동이 실패한다.
마이그레이션:
  주소: ${DB_URL}
  사용자: ${DB_소유자:}
  비밀번호: ${DB_소유자_비번:}
```

## 💡 배운 것

**설정도 시험 대상입니다.** 코드는 빈틈없이 시험하면서 설정은 "배포해 보면 알겠지" 로 두고 있었습니다. 기동 실패는 배포된 순간 전면 장애라서, 오히려 가장 먼저 검사해야 할 영역이었습니다.

**"통과했다" 는 무엇을 검사했느냐에 달렸습니다.** 시험이 아무리 많아도 운영과 다른 조건으로 돌면 그 조건에 대해서는 아무 말도 해 주지 않습니다.

**부분 설정은 전체를 무효로 만들 수 있습니다.** 값 하나만 주면 "나머지는 기본값" 이 아니라 "이제부터 전부 직접 주세요" 가 되는 경우가 있습니다. 프레임워크가 기본값을 어떻게 고르는지는 문서를 읽어야 알 수 있습니다.

**급한 복구와 근본 수정을 나눕니다.** 먼저 환경변수 한 줄로 살리고, 설정 파일 수정과 시험 추가는 그다음에 했습니다. 순서를 바꿨으면 장애 시간이 훨씬 길어졌을 겁니다.

## 소감

제 수정이 운영을 세웠다는 게 당황스러웠지만, 덕분에 **시험의 사각지대** 를 찾았습니다. 이전에도 "개발에선 멀쩡한데 운영에서만 터진" 일이 있었는데, 그때는 원인만 고치고 넘어갔었습니다. 이번엔 같은 종류의 문제를 앞으로 걸러 낼 장치를 만들었다는 점이 다릅니다.

장애 기록을 남길 때 "무엇이 원인이었나" 뿐 아니라 **"왜 미리 못 잡았나"** 를 같이 적으면, 고칠 것이 하나 더 보인다는 것도 알았습니다.

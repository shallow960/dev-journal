# 2026-09-09 되돌릴 수 없는 것을 먼저 하고 있었다

> 태그: #트러블슈팅 #결제 #순서설계 #안전장치의역설

## 무엇을 / 왜

무인 발권 키오스크에서 카드 결제를 취소했는데 "매출 제외 실패" 가 떴습니다.

확인해 보니 더 나쁜 상태였습니다. **카드는 실제로 환불됐는데 서버에는 그 예약이 그대로 살아 있었습니다.** 손님은 돈을 돌려받았고 장부에는 매출이 남았습니다.

한 건이 실제로 그렇게 어긋난 뒤였습니다.

## 어떻게 풀었나

### 순서가 거꾸로였다

코드를 따라가 보니 취소가 이렇게 돌고 있었습니다.

```
1) 카드 단말에 취소 요청   ← 돈이 나간다
2) 서버에 "매출에서 빼 달라"
```

문제는 서버가 아무 건이나 취소해 주지 않는다는 것이었습니다. 이미 이용을 시작했거나 끝난 건은 거절합니다. 그런데 그 거절이 **2번에서** 일어납니다. 이미 돈이 나간 뒤에요.

순서를 뒤집었습니다.

```
1) 서버에 "이 결제 취소해도 되나?"  ← 안 되면 여기서 멈춘다
2) 카드 단말에 취소 요청
3) 서버에 매출 제외
```

안 되는 건이면 사유를 화면에 띄우고 **카드는 손대지 않습니다.**

### 고치다 보니 인접 결함이 둘 더 나왔다

**재기동 뒤에는 취소가 항상 실패했습니다.** 취소가 서버를 두 번 조회하는데, 두 번째 조회가 "이 기계가 마지막으로 승인한 결제" 를 기준으로 삼고 있었습니다.

그런데 관리자가 승인번호를 손으로 입력한다는 건 **기계가 그 결제를 기억 못 한다는 뜻**입니다. 하필 그 기억에 의존하고 있었어요. 프로그램을 교체하면 그 기억이 비니까요.

첫 조회의 답을 그대로 넘겨 쓰게 고쳤습니다.

**A 결제 → B 결제 → A 취소** 순서에서는 "결제 데이터 없음" 이 떴습니다. 승인번호는 입력값을 쓰면서 거래번호는 마지막 결제 것을 같이 실어 보내, 서버가 둘을 함께 찾다가 아무것도 못 찾은 것이었습니다.

**같은 대상을 두 번 조회할 때 두 조회의 입력이 같은지** 를 안 본 탓이었습니다.

### 그리고 막았는데, 그게 더 나빴다

여기서 안전장치를 하나 더 넣었습니다. 이미 이용을 시작했거나 끝난 건은 키오스크에서 **아예 취소하지 못하게** 막았어요. 돈이 먼저 나가는 사고를 막는 게 맞다고 봤고, "관리 웹에서 환불해 주세요" 라고 안내했습니다.

그런데 현장에서 이런 질문을 받았습니다.

> 관리 웹에서 환불을 누르면 진짜 환불이 되나요?

서버 코드를 열어 봤습니다. **아니었습니다.**

관리 웹의 환불은 장부에 "환불됨" 표시만 남길 뿐 카드 단말과 대화하지 않았습니다. 서버 어디에도 카드사를 부르는 코드가 없었어요. 즉 **카드에 실제로 돈을 돌려주는 길은 키오스크 취소 하나뿐**인데, 제가 그 길을 막아 버린 겁니다.

이용을 마친 손님은 환불받을 방법이 사라진 상태였습니다.

다시 열었습니다. 대신 그냥 되돌리지 않고,

- 취소 전에 "카드는 취소되지만 매출에서는 자동으로 빠지지 않습니다" 를 확인창으로 알리고
- 취소가 끝난 뒤에도 같은 안내를 한 번 더 띄우고
- 완료 문구에서 "실패" 라는 말을 뺐습니다

마지막이 중요했습니다. 그 건은 매출 제외가 안 되는 게 **정상**인데 "실패" 라고 적으면 직원이 카드 취소까지 안 된 줄 압니다.

## 코드로 보기 (개념 재현)

되돌릴 수 없는 작업과 되돌릴 수 있는 작업이 섞여 있을 때, 순서를 어떻게 두느냐가 전부였습니다.

```js
// 문제가 됐던 순서
async function cancel(approvalNo) {
  await terminal.cancelCard(approvalNo);        // ① 돈이 나간다 (되돌릴 수 없음)
  const r = await api.excludeFromSales(approvalNo);  // ② 여기서 거절될 수 있다
  if (!r.ok) {
    // 이미 늦었다. 카드는 취소됐는데 장부는 그대로.
    showError("매출 제외 실패");
  }
}
```

```js
// 고친 순서: 되돌릴 수 없는 것 앞에 관문을 둔다
async function cancel(approvalNo) {
  // ① 먼저 묻는다. 카드는 아직 건드리지 않았다.
  const check = await api.canCancel(approvalNo);
  if (!check.allowed) {
    showError(check.reason);   // "이용 중인 예약입니다" 등 사유를 그대로
    return;                    // 카드 무사
  }

  // ② 이제 되돌릴 수 없는 일을 한다
  await terminal.cancelCard(approvalNo);

  // ③ 장부 정리. 실패해도 관리 웹에서 바로잡을 수 있다.
  //    ★ ①의 결과를 넘겨 쓴다. 여기서 다시 조회하면 기준이 어긋난다.
  await api.excludeFromSales(check.transactionId);
}
```

두 번 조회할 때 입력이 갈리던 부분입니다.

```js
// 문제: 승인번호는 입력값, 거래번호는 "마지막 결제" 를 섞어 보냈다.
//       서버가 둘을 AND 로 찾아 아무것도 못 찾는다.
await api.excludeFromSales({
  approvalNo: userInput,          // 관리자가 손으로 입력한 값
  transactionId: lastPayment.id   // 이 기계가 마지막으로 승인한 결제
});

// 고침: 입력한 승인번호가 마지막 결제와 다르면 거래번호를 비운다.
await api.excludeFromSales({
  approvalNo: userInput,
  transactionId: (lastPayment?.approvalNo === userInput)
    ? lastPayment.id
    : null
});
```

## 💡 배운 것

**되돌릴 수 없는 것을 되돌릴 수 있는 것보다 먼저 하면 안 됩니다.** 카드 승인취소는 카드사까지 걸린 일이라 되돌리기 어렵고, 장부는 관리 화면에서 고칠 수 있습니다. 그런데 어려운 쪽을 먼저 하고 있었어요. **순서만 뒤집어도 최악의 경우가 "취소가 안 됨" 으로 바뀝니다.**

**"막는 것" 이 항상 안전한 선택은 아닙니다.** 위험해 보이는 경로를 막았더니 그게 **유일한 경로**였습니다. 막기 전에 "이 길 말고 다른 길이 있나" 를 확인했어야 했습니다. 안내 문구가 가리키는 곳이 실제로 그 일을 하는지도 코드로 봐야 했고요.

**같은 대상을 두 번 조회하면 두 조회의 입력이 같은지 봐야 합니다.** 하나는 사람이 입력한 값, 하나는 기계가 기억한 값이었습니다. 평소엔 같아서 안 드러나다가 재기동이나 결제 순서가 끼면 갈라졌습니다.

**정상 동작을 "실패" 라고 적으면 안 됩니다.** 매출 제외가 안 되는 게 정상인 경우인데 "실패" 라고 띄우면, 직원은 카드 취소까지 안 된 줄 알고 한 번 더 누릅니다.

## 소감

처음엔 "취소가 실패한다" 는 단순한 버그로 봤는데, 고치는 과정에서 **안전장치를 넣었다가 그게 더 큰 구멍을 만든** 경험을 했습니다. 막는 쪽이 늘 보수적이고 안전하다고 생각했는데 아니었어요.

그리고 남는 위험도 있습니다. 직원이 "관리 웹에서 장부 맞추기" 를 잊으면 매출이 부풀어 있게 되는데, 지금은 그걸 찾아낼 화면이 없습니다. 감추지 않고 작업일지에 적어 뒀습니다. 못 고친 걸 못 고쳤다고 적어 두는 것도 일의 일부라는 걸 배웠습니다.

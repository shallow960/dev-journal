# 2026-11-13 관리자 화면만 루피아를 소수 2자리로 알고 있어서, 가격이 100배로 저장될 뻔했다

> 태그: #트러블슈팅 #다통화 #금액 #Intl #TypeScript

## 무엇을 / 왜

사진 키오스크 플랫폼은 금액을 "가장 작은 단위의 정수" 로 저장했습니다. 원화는 1원이 가장 작은 단위라 4,000원은 4000 으로, 달러는 1센트가 가장 작은 단위라 4.00달러는 400 으로 저장했습니다. 그래서 화면의 숫자와 저장값을 서로 바꾸려면 통화마다 소수 몇 자리를 쓰는지(자릿수)를 알아야 했습니다.

해외 총판이 자기 키오스크의 프레임 가격을 직접 바꾸게 해 달라는 요청을 설계하면서 가격 코드를 끝까지 읽어 봤습니다. 그러다 서버와 키오스크는 인도네시아 루피아(IDR)를 소수 0자리로 쓰는데, 관리자 화면만 소수 2자리로 다루고 있다는 걸 찾았습니다.

## 어떻게 풀었나

관리자 화면은 통화 자릿수를 브라우저의 `Intl.NumberFormat` 이 알려 주는 값으로 정하고 있었습니다. 찾아보니 국제 표준 통화 표(ISO 4217)에는 루피아의 보조 단위가 2자리로 올라 있고, `Intl` 도 그 값을 따른다는 걸 알게 됐습니다. 그런데 실제로는 루피아를 소수점 아래로 쓰지 않아서, 서버는 국가 표에 루피아를 0자리로 넣어 두었고 키오스크도 그 값을 썼습니다. 표준 표와 실제로 쓰는 값이 달랐던 것입니다.

그래서 관리자 화면에서는 이런 일이 생길 수 있었습니다.

- 매수별 가격에 15,000 루피아를 넣으면 15000 × 100 = 1,500,000 으로 저장됐습니다(100배).
- 화면에 보여 줄 때는 다시 100 으로 나눠 15,000 으로 보였습니다. 관리자 화면 안에서만 보면 맞아 보였습니다.
- 하지만 키오스크는 0자리로 읽으니, 손님에게는 1,500,000 루피아로 보였을 것입니다.

고친 내용은 세 가지였습니다.

1. 관리자 화면도 서버와 같은 통화 자릿수 표를 쓰게 했습니다(원화·루피아·엔·동은 0, 링깃·바트·싱가포르 달러·미국 달러 등은 2). 표에 없는 통화만 `Intl` 값을 쓰게 했습니다.
2. 자릿수를 넘는 입력은 반올림하지 않고 "IDR 는 소수점 0자리까지만" 처럼 이유를 보이며 거절했습니다. 몰래 반올림하면 또 다른 금액 차이를 만들 수 있었습니다.
3. 서버의 통화 표와 관리자 화면의 표가 같은지 확인하는 시험을 넣었습니다. 한쪽만 바뀌면 시험이 실패하게 했습니다.

같은 조사에서 비슷한 문제가 두 가지 더 나왔습니다.

- 대시보드의 매출 추이 그래프는 저장값(가장 작은 단위)을 그대로 그리고 있어서, 링깃·바트처럼 2자리 통화는 100배로 그려지고 있었습니다.
- 서버에는 매장 가격의 자릿수 검사가 없었습니다. 원화 매장에 1500.5 원이 저장되면 키오스크로 보낼 때 정수로 바꾸지 못해 0 을 보냈고, 키오스크에서 0원은 결제 없이 넘어가는 무료였습니다. 이제는 저장할 때 이유와 함께 거절하고, 바꿀 수 없는 가격은 0 으로 보내지 않고 그 프레임을 목록에서 빼며 기록을 남기게 했습니다.

운영 DB 를 읽기만 해서 확인해 보니 아직 인도네시아 매장이 없어서, 잘못 저장된 값은 없었습니다.

## 코드로 보기 (개념 재현)

이름은 바꾼 더미입니다.

```ts
// 통화 자릿수: 서버의 국가 표와 같은 값을 한 곳에 둔다 (일부)
const DIGITS: Record<string, number> = { KRW: 0, IDR: 0, JPY: 0, VND: 0, MYR: 2, THB: 2, SGD: 2, USD: 2 };

function digitsFor(currency: string): number {
  if (currency in DIGITS) return DIGITS[currency];
  // 표에 없는 통화만 표준(Intl) 값을 쓴다. 고치기 전에는 모든 통화를 여기서 정해 IDR 가 2 가 됐다
  return new Intl.NumberFormat('en', { style: 'currency', currency }).resolvedOptions().maximumFractionDigits ?? 2;
}

// 화면 입력("15000") -> 저장값(가장 작은 단위의 정수)
function toStoredAmount(input: string, currency: string): number {
  const digits = digitsFor(currency);
  const [whole, frac = ''] = input.trim().split('.');
  const meaningful = frac.replace(/0+$/, ''); // 끝의 0 은 세지 않는다 (1500.00 원은 괜찮다)
  if (meaningful.length > digits) {
    throw new Error(`${currency} 는 소수점 ${digits}자리까지만 넣을 수 있습니다 (넣은 값: ${input})`);
  }
  return Number(whole + frac.padEnd(digits, '0').slice(0, digits));
}

toStoredAmount('15000', 'IDR');  // 15000   (고치기 전 방식이면 1500000 - 100배)
toStoredAmount('4.00', 'USD');   // 400
toStoredAmount('1500.5', 'KRW'); // 오류: KRW 는 소수점 0자리까지만 ... (고치기 전에는 키오스크에 0 이 갔다)
```

## 💡 배운 것

- 표준 표의 통화 자릿수와 실제로 쓰는 자릿수가 다를 수 있다는 걸 배웠습니다. 루피아는 표준 표에서는 2자리였지만, 서버와 키오스크는 0자리로 쓰고 있었습니다.
- 저장할 때 곱하고 보여 줄 때 나누는 쪽이 같은 잘못된 자릿수를 쓰면, 그 화면 안에서는 늘 맞아 보인다는 걸 배웠습니다. 틀린 것은 다른 프로그램(키오스크)이 같은 값을 읽을 때에야 드러났습니다.
- 같은 사실(통화 자릿수)을 여러 곳이 따로 정하면 결국 어긋난다는 걸 [2026-10-13 글](../개선/2026-10-13-첫-구매의-뜻을-세-곳이-따로-정하지-않게-했다.md)에 이어 다시 배웠습니다. 이번에는 한 곳에 모으는 데 더해, 두 표가 같은지를 시험으로 묶어 두었습니다.
- 금액을 정수로 바꾸지 못할 때 0 을 보내는 처리는, 키오스크에서는 "무료" 라는 뜻이 됐습니다. 바꿀 수 없는 값은 0 이 아니라 거절이나 제외로 다뤄야 했습니다.

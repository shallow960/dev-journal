# 2026-09-10 보이지 않는 공백이 자리를 먹고 있었다

> 태그: #트러블슈팅 #영수증 #고정폭출력 #문자열길이

## 무엇을 / 왜

프린터가 두 대인데 같은 영수증을 뽑아야 했습니다. 실물을 나란히 놓고 보니 제목 굵기, 카드 정보 정렬, 번호 굵기가 제각각이었습니다.

손님은 어느 창구에서 받았는지에 따라 다른 영수증을 받을 이유가 없고, 직원은 두 장을 나란히 놓고 대조합니다.

## 어떻게 풀었나

### 두 프린터가 완전히 다른 코드였다

한쪽은 프린터 명령 바이트를 직접 씁니다. 다른 쪽은 제조사 라이브러리를 부르는데, **그 라이브러리에는 굵기를 정하는 창구가 없었습니다.**

라이브러리가 못 해 주는 일이라 한 단계 아래로 내려갔습니다. 두 번째 프린터도 **같은 명령 바이트를 직접 보내게** 했습니다. 같은 명령을 쓰면 결과가 같을 수밖에 없으니까요.

### 그러고 나서 자리 계산에서 결함이 셋 나왔다

영수증은 폭이 정해진 종이입니다. 한 줄이 42칸이고, 오른쪽 끝에 금액을 붙이려면 앞을 공백으로 채웁니다.

**첫째, 자리를 글자 수로 밀고 있었습니다.** 한글은 한 자가 두 칸이라 보정이 들어가 있었는데, 그 보정값이 항목마다 "이 정도 길이겠지" 로 맞춘 숫자였습니다. 실제 길이가 그와 다르면 어긋납니다.

칸 수를 세는 함수를 만들어 갈아 끼웠습니다. 그랬더니 한 항목만 여전히 오른쪽에서 떨어져 보였습니다.

**둘째, 눈에 안 보이는 것이 자리를 먹고 있었습니다.** 카드 단말이 매입사 이름을 **뒤에 공백 열 칸을 채워서** 보내고 있었어요. 고정폭 자리에 맞춰 넘겨주는 값이었던 겁니다. 화면에서는 안 보이고, 종이에서는 열 칸을 차지합니다.

**셋째, 상품명이 길면 줄이 접혔습니다.** 금액칸을 13칸으로 잡고 글자 수로 채우고 있었는데, 단위 글자가 두 칸이라 실제로는 14칸을 먹었습니다. 이름이 짧을 때만 우연히 맞고 있었어요.

### 눈으로 대조하지 않았다

두 파일이 만들어 내는 출력 줄을 뽑아 기계로 비교했습니다. 매출·취소·재발급 세 경로에서 **71줄이 모두 같은 것**을 확인했습니다.

실제 설정값과 긴 이름으로도 그려 보며 42칸을 넘는 줄이 없는지 봤습니다.

## 코드로 보기 (개념 재현)

문제가 됐던 자리 계산입니다.

```js
// 글자 수로 민다. 한글 보정은 항목마다 손으로 맞춘 숫자.
function padRight(label, value, ADJUST = 3) {
  const used = label.length + value.length + ADJUST;
  return label + " ".repeat(WIDTH - used) + value;
}
```

칸 수를 세는 함수로 바꿨습니다.

```js
// 한 글자가 몇 칸을 먹는지로 센다.
function columns(str) {
  let n = 0;
  for (const ch of str) {
    const code = ch.codePointAt(0);
    // 한글·한자·전각 구간은 두 칸
    n += (code >= 0x1100 && code <= 0x11FF) ||
         (code >= 0x3000 && code <= 0x303F) ||
         (code >= 0xAC00 && code <= 0xD7A3) ||
         (code >= 0xFF00 && code <= 0xFF60) ? 2 : 1;
  }
  return n;
}

function padRight(label, value) {
  const gap = WIDTH - columns(label) - columns(value);
  return label + " ".repeat(Math.max(gap, 1)) + value;
}
```

그래도 어긋나던 한 줄입니다.

```js
// 외부 장비가 준 값. 화면에는 안 보이지만 뒤에 공백이 붙어 있다.
const issuer = res.issuerName;      // "○○카드          "
columns(issuer);                    // 16 - 실제 글자는 6칸인데

// 고침: 바깥에서 들어온 값은 다듬고 쓴다.
const issuer = (res.issuerName ?? "").trim();
```

금액칸 쪽입니다.

```js
// 문제: 칸 수를 글자 수로 채웠다. 단위 글자가 두 칸이라 1칸씩 넘쳤다.
const amountCell = String(amount).padStart(AMOUNT_WIDTH - 1) + "원";
// "12,000원" → 글자 8개지만 실제로는 9칸

// 고침: 만들어 놓고 칸 수로 잰다.
function fitRight(text, width) {
  const gap = width - columns(text);
  return gap > 0 ? " ".repeat(gap) + text : text;
}
const amountCell = fitRight(`${amount.toLocaleString()}원`, AMOUNT_WIDTH);
```

## 💡 배운 것

**글자 수와 칸 수는 다릅니다.** 고정폭으로 출력하는 곳(영수증, 콘솔 표, 로그 정렬)에서는 `length` 가 답이 아닙니다. 한글이 섞이는 순간 어긋나고, 보정값을 손으로 맞추면 그 길이일 때만 맞습니다.

**바깥에서 들어온 값은 눈에 보이는 게 전부가 아닙니다.** 외부 장비나 API 가 고정폭 자리에 맞춰 채움 문자를 붙여 보내는 일이 흔합니다. 화면에서는 안 보이고 계산에서만 드러납니다. 받은 값을 다듬고 쓰는 습관이 필요했습니다.

**우연히 맞고 있던 계산은 우연이 깨질 때만 드러납니다.** 금액칸이 한 칸 넘치는 결함은 이름이 짧을 동안 아무 증상이 없었습니다. "지금은 되는데" 가 "맞다" 는 뜻이 아니었습니다.

**같아야 하는 두 출력은 기계로 대조해야 합니다.** 눈으로 보면 "비슷해 보인다" 에서 멈춥니다. 줄 단위로 뽑아 비교하니 차이가 0건인 것을 숫자로 확인할 수 있었습니다.

## 소감

"영수증 모양을 맞춰 달라" 는 눈에 보이는 요청이었는데, 파고드니 **길이를 세는 방법 자체가 틀려 있던** 문제였습니다.

특히 공백 열 칸은 인상적이었어요. 로그로 값을 찍어도 그냥 이름으로 보입니다. 종이에 뽑아 놓고 자리를 세어 보고서야 "뭔가가 여기를 먹고 있다" 를 알았습니다. 눈에 안 보이는 문자가 있다는 걸 처음 실감했습니다.

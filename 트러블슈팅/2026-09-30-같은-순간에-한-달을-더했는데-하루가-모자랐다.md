# 2026-09-30 같은 순간에 한 달을 더했는데, 하루가 모자랐다

> 태그: #트러블슈팅 #시간대 #날짜계산 #Java #CI

## 무엇을 / 왜

구독 서비스에서 요금제를 내리는 기능입니다. 요금제를 내리면 견적 화면이 새 결제 기간을 보여 줍니다.

```
견적 화면:  10월 1일 시작 → 11월 1일 종료
```

그런데 실제로 요금제를 바꿔 적용하는 코드는 **10월 31일에 끝나는 기간**을 만들고 있었습니다. 보여 준 것보다 하루 짧게 적용된 셈입니다.

이걸 알게 된 건 배포가 막혀서였습니다. 다른 기능을 올렸는데 CI의 전체 테스트(1,500여 개) 중 이 테스트 하나가 실패해 자동 배포가 두 번 연속 멈췄습니다. 이 테스트는 평소에 늘 통과했고, **9월 30일에만** 실패했습니다.

## 어떻게 풀었나

### 두 계산은 같은 일을 하고 있었다

견적과 적용 모두 "시작 시각에 한 달 더하기" 였습니다. 다른 건 **시작 시각을 어떤 모습으로 들고 있었나** 였어요.

```
견적:  2026-10-01T00:00+09:00  + 1개월 = 2026-11-01T00:00+09:00
적용:  2026-09-30T15:00Z       + 1개월 = 2026-10-30T15:00Z   (= 한국 10월 31일 00:00)
```

두 시작 값은 **같은 순간**입니다. 견적은 "다음날 0시(한국)" 를 한국 오프셋(+09:00)으로 만들었고, 적용 쪽은 그 값을 DB에 저장했다가 다시 읽어 썼는데, 다시 읽은 값은 같은 순간의 **UTC(+00:00) 표현**이었습니다. 기본 설정의 JSON 변환이나 `timestamptz` 조회는 보통 이렇게 UTC로 돌려줍니다.

`OffsetDateTime` 은 "어느 순간인가" 와 "어느 오프셋으로 보여 주나" 를 함께 가집니다. 두 값을 비교하면 순간으로 비교하니 같다고 나옵니다. 하지만 `plusMonths` 는 **그 오프셋의 달력**에서 달을 더합니다. UTC 달력에서는 9월 30일이라 한 달 뒤가 10월 30일이 됩니다.

### 왜 9월 30일에만 드러났나

대부분의 날에는 두 달력의 결과가 같습니다.

| 시작(한국) | UTC로는 | UTC 달력 + 1개월 | 한국 달력 + 1개월 |
|---|---|---|---|
| 9/16 00:00 | 9/15 15:00 | 10/15 15:00 = 한국 10/16 | 10/16 |
| 10/1 00:00 | 9/30 15:00 | 10/30 15:00 = 한국 **10/31** | **11/1** |
| 3/1 05:00 | 2/28 20:00 | 3/28 20:00 = 한국 **3/29** | **4/1** |

한국 시각으로는 이미 다음 달인데 UTC로는 아직 전달 말일이고, 두 달의 길이가 다를 때만 어긋납니다. 테스트는 "내일 0시" 를 시작으로 쓰니, 오늘이 9월 30일일 때 처음 걸린 거예요.

### 테스트가 아니라 계산을 고쳤다

테스트 기대값을 날짜에 맞춰 고치면 초록이 되긴 합니다. 하지만 찾아보니 **정기 결제 갱신도 같은 계산**을 쓰고 있었습니다. 서버 시계는 UTC라, 한국 새벽 0~9시에 시작한 구독은 월말 무렵 기간이 하루에서 사흘까지 짧아질 수 있었어요.

그래서 기간 계산이 받은 값의 오프셋과 상관없이 **항상 한국 달력에서 달을 더하게** 바꿨습니다. 환불 계산과 "다음날 적용" 은 이미 한국 날짜를 쓰고 있어서, 기준이 하나로 모였습니다. 돌려주는 값의 오프셋은 넣은 값을 그대로 따르게 해서, 부르는 쪽 코드는 바꾸지 않아도 되게 했습니다.

## 코드로 보기 (개념 재현)

```java
// 예전: 받은 값의 오프셋 달력에서 그대로 달을 더했다
static OffsetDateTime nextPeriodEndOld(OffsetDateTime start) {
    return start.plusMonths(1);   // UTC 값이 오면 UTC 달력, 한국 값이 오면 한국 달력
}
```

```java
private static final ZoneId BUSINESS_ZONE = ZoneId.of("Asia/Seoul");

/** 기간 끝 = 시작한 "한국 날짜" 에서 한 달 뒤의 같은 시각. 오프셋은 넣은 값을 따른다. */
static OffsetDateTime nextPeriodEnd(OffsetDateTime start) {
    ZonedDateTime local = start.atZoneSameInstant(BUSINESS_ZONE); // 같은 순간을 한국 달력으로 옮긴다
    return local.plusMonths(1)                                    // 한국 달력에서 한 달
        .toOffsetDateTime()
        .withOffsetSameInstant(start.getOffset());                // 돌려주는 표현은 입력과 같게
}
```

어느 오프셋으로 넣어도 같은 순간에 끝나는지, 월말 경계와 평소 날짜를 같이 고정했습니다.

```java
@Test
void 같은_순간이면_어느_오프셋으로_넣어도_끝나는_순간이_같다() {
    OffsetDateTime kst = OffsetDateTime.parse("2026-10-01T00:00+09:00");
    OffsetDateTime utc = kst.withOffsetSameInstant(ZoneOffset.UTC);      // 2026-09-30T15:00Z

    assertThat(nextPeriodEnd(kst)).isEqualTo(OffsetDateTime.parse("2026-11-01T00:00+09:00"));
    assertThat(nextPeriodEnd(utc).toInstant()).isEqualTo(nextPeriodEnd(kst).toInstant());
    assertThat(nextPeriodEnd(utc).getOffset()).isEqualTo(ZoneOffset.UTC); // 표현은 입력을 따른다
}

@Test
void 한국_3월1일_새벽에_시작하면_4월1일에_끝난다() {
    OffsetDateTime utc = OffsetDateTime.parse("2027-02-28T20:00Z");       // 한국 3/1 05:00
    assertThat(nextPeriodEnd(utc).withOffsetSameInstant(ZoneOffset.ofHours(9)))
        .isEqualTo(OffsetDateTime.parse("2027-04-01T05:00+09:00"));      // 예전엔 3/29
}

@Test
void 평소_날짜는_예전과_같다() {
    OffsetDateTime utc = OffsetDateTime.parse("2026-09-15T03:00Z");
    assertThat(nextPeriodEnd(utc)).isEqualTo(utc.plusMonths(1));
}
```

## 💡 배운 것

**`OffsetDateTime` 의 비교와 계산은 기준이 다릅니다.** 비교는 순간으로 하지만, `plusMonths` 같은 달력 계산은 그 값이 들고 있는 오프셋의 달력으로 합니다. 같은 순간이라도 어느 표현을 들고 있느냐에 따라 "한 달 뒤" 가 달라집니다.

**"몇 달 뒤" 는 누구의 달력인지부터 정합니다.** 결제 기간처럼 사람이 달력을 보고 이해하는 값은 서비스의 영업 시간대 달력으로 계산해야 합니다. 저장했다 읽으면 표현이 바뀔 수 있으니, 계산하는 쪽에서 달력을 명시하는 게 안전했습니다.

**특정 날짜에만 깨지는 테스트는 버그의 신호입니다.** 기대값을 맞춰 초록으로 만들었다면 정기 결제 쪽 문제는 그대로 남았을 겁니다.

**관련 테스트만 돌리고 올리면 다른 곳을 놓칩니다.** 이번엔 CI가 전체 테스트를 돌리고 통과해야 배포하게 돼 있어서, 잘못된 결제 계산이 배포되기 전에 멈췄습니다.

## 소감

처음엔 "내 변경이랑 상관없는 테스트가 왜 하필 지금" 이라는 생각이 들었습니다. 그런데 원인을 따라가 보니 날짜가 딱 맞아떨어진 날에만 보이는 진짜 버그였고, 테스트는 그걸 정확히 잡아 준 거였어요. 날짜 계산을 볼 때 "몇 시인가" 보다 "어느 달력인가" 를 먼저 묻는 습관을 들이기로 했습니다.

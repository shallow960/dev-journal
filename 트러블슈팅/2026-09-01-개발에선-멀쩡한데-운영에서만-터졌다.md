# 2026-09-01 개발에선 멀쩡한데, 운영에서만 터졌다

> 태그: #트러블슈팅 #자료구조 #환경차이 #재현

## 무엇을 / 왜

다른 작업을 끝내고 운영 화면을 확인하러 갔는데, 손님몰 상품 목록이 통째로 안 나왔습니다.

```
GET /api/v1/goods  →  500 Internal Server Error
```

제 개발 환경에서는 멀쩡했습니다. 같은 코드, 같은 요청인데요.

## 어떻게 풀었나

### 오류 기록부터 봤다

로그가 다른 오류(수집 서버 접속 실패)로 도배돼 있어서, 오류 기록 테이블을 직접 조회했습니다.

```
java.lang.NullPointerException
  at java.util.Objects.requireNonNull
  at java.util.ImmutableCollections$MapN.get
  at GoodsApiDtos$GoodsListResponse.lambda$from$0
```

**"불변 맵에서 `get`을 하다가"** 널 오류가 났다는 뜻이었습니다. 처음엔 이해가 안 갔어요. 맵에서 없는 키를 찾으면 `null`이 나오는 거지, 오류가 나는 건 아니잖아요.

### 자바 문서를 찾아봤다

찾아보니 `Map.of()`로 만든 불변 맵은 **`null` 키로 조회하는 것 자체를 거부**했습니다. 없는 키를 찾는 게 아니라, 키가 `null`인 걸 잘못된 사용으로 봅니다.

반면 `HashMap`은 `null` 키를 허용해서 그냥 `null`을 돌려줍니다.

```
HashMap.get(null)   → null      (조용히 넘어감)
Map.of().get(null)  → 예외!
```

### 그런데 왜 환경마다 달랐나

문제의 코드는 이랬습니다.

```
브랜드명 맵 만들기:
  판매자 목록이 비어 있으면  →  Map.of()   (불변)
  아니면                    →  HashMap    (일반)
```

**결과가 있느냐 없느냐에 따라 맵의 종류가 달라지고 있었습니다.**

그리고 화면 쪽에서는 상품마다 `맵.get(상품의 판매자)`를 하는데, 입점 브랜드 없이 스토어가 직접 파는 상품은 판매자가 비어 있습니다.

```
운영: 상품 8건이 전부 판매자 없음 → 맵이 빔 → Map.of() → 첫 조회에서 터짐
개발: 판매자 붙은 상품이 10건 있음 → 맵이 참 → HashMap → 조용히 넘어감
```

같은 코드가 **데이터에 따라 다르게 동작**하고 있었던 거예요. 그래서 개발에서는 아무리 눌러 봐도 재현이 안 됐습니다.

### 두 군데를 고쳤다

처음엔 조회하는 쪽만 고치려고 했습니다. 판매자가 없으면 맵을 뒤지지 않게요.

```
전: 맵.get(상품의 판매자)
후: 판매자가 없으면 → 이름도 없음. 있을 때만 맵을 뒤진다
```

이걸로 오류는 사라집니다. 그런데 **진짜 원인은 그대로** 남습니다. 맵 종류가 데이터에 따라 갈리는 한, 다음에 누가 이 맵을 쓰면 같은 일이 또 납니다.

그래서 맵을 만드는 쪽도 고쳤습니다. 결과가 있든 없든 같은 종류를 돌려주도록요.

### 테스트로 못 박았다

고치고 나서 "이게 정말 그 버그를 잡는 테스트인가"가 궁금했습니다. 그래서 **수정을 잠시 되돌리고** 테스트를 돌려 봤어요.

```
수정 있음 → 통과
수정 되돌림 → 실패 (NullPointerException)
```

실패하는 걸 보고 나서야 안심이 됐습니다. 통과만 보고는 그 테스트가 무엇을 지키는지 알 수 없더라고요.

## 코드로 보기 (개념 재현)

```
// 전 — 데이터에 따라 맵 종류가 갈린다
이름맵_만들기(판매자들):
    쓸만한거 = 판매자들 중 비어있지 않은 것
    if 쓸만한거 없음:
        return 빈_불변맵()        ← null 키를 거부
    return 조회결과를_일반맵으로()   ← null 키를 허용

화면:
    상품들.각각 → 이름맵.찾기(상품.판매자)   // 판매자가 null 일 수 있다

// 후 — 종류를 통일하고, 빈 키로는 찾지 않는다
이름맵_만들기(판매자들):
    if 쓸만한거 없음:
        return 빈_일반맵()          ← 결과가 있을 때와 같은 종류
    return 조회결과를_일반맵으로()

화면:
    상품들.각각 → 상품.판매자 없으면 이름도 없음
                 있으면 이름맵.찾기(상품.판매자)
```

## 💡 배운 것

- **같은 코드도 데이터에 따라 다르게 동작할 수 있다.** "내 환경에서는 되는데"의 원인이 환경 설정이 아니라 그 환경에 쌓인 데이터일 수 있다는 걸 처음 알았다.
- **불변 맵은 `null` 키를 안 받는다.** 편해 보여서 `Map.of()`를 쓰곤 했는데, 그냥 "고칠 수 없는 맵" 정도로만 알고 있었다. 허용하는 값의 범위도 다르다.
- **분기마다 같은 종류를 돌려줘야 한다.** 이번엔 반환 타입이 `Map` 으로 같아서 아무도 눈치채지 못했다. 타입이 같아도 성질이 다르면 다른 물건이다.
- **테스트는 실패시켜 봐야 믿을 수 있다.** 통과하는 테스트는 "지금 안 깨졌다"만 말해 준다. 고친 걸 되돌려 실패를 보고 나서야 그 테스트가 무엇을 지키는지 알았다.
- **증상만 고치면 원인은 남는다.** 조회 쪽만 막아도 오류는 사라졌겠지만, 다음 사람이 같은 맵을 쓰면 같은 일이 난다.

## 소감

제일 당황스러웠던 건 재현이 안 되는 것이었습니다. 코드를 아무리 들여다봐도 터질 이유가 안 보이는데 운영에서만 500이 나니까, 처음엔 배포가 덜 됐나부터 의심했어요.

원인을 알고 나서는 좀 서늘했습니다. 이 코드는 꽤 오래전부터 있었고, 판매자가 붙은 상품이 하나라도 있는 동안에는 **영원히 멀쩡했을** 겁니다. 스토어 하나가 "입점 브랜드 없이 직접 판매"만 하게 되는 순간 목록이 통째로 죽는 건데, 그게 언제일지는 아무도 모르죠.

앞으로는 분기해서 값을 만들 때 "양쪽이 정말 같은 물건인가"를 한 번 더 볼 것 같습니다. 타입이 같다고 같은 게 아니더라고요.

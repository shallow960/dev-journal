# 2026-11-20 결제 화면 타이머에 5초를 넣어도 저장됐고, 키오스크는 말없이 30초로 썼다

> 태그: #트러블슈팅 #입력검증 #설정 #하위호환 #키오스크

## 무엇을 / 왜

사진 키오스크의 설정(촬영 매수, 화면마다의 제한시간, 볼륨 같은 것)은 관리 웹에서 전체·나라·브랜드·키오스크 단위로 고칠 수 있었고, 키오스크의 설정창에서도 고칠 수 있었습니다. 숫자 칸만 수백 개였고, 입력 칸마다 허용 범위가 적혀 있었습니다.

그런데 서버는 촬영 매수 같은 몇 칸만 범위를 검사하고 있었습니다. 관리 웹에 결제 화면 타이머 5초(허용 30~900초)나 사진 선택 타이머 9999초(허용 0~600초)를 넣어도 그대로 저장됐습니다. 입력 칸의 범위는 안내였을 뿐, 막는 장치가 아니었습니다.

키오스크는 설정을 읽을 때 범위에 맞춰 쓰고 있었습니다. 결제 화면 타이머가 5로 저장되면 키오스크는 30초로 돌았고, 관리 웹에는 5초가 그대로 보였습니다. 화면에 보이는 값과 실제로 도는 값이 말없이 갈라질 수 있는 상태였습니다.

## 어떻게 풀었나

### 범위 표를 하나로

관리 웹과 키오스크 설정창은 각자 칸마다 최소·최대 값을 들고 있었습니다. 서버에도 따로 적으면 세 곳이 언젠가 어긋날 것 같아서, 숫자 칸 전부의 범위(칸, 정수인지, 최소, 최대, 사유에 쓸 칸 이름)를 표 하나로 만들고 서버가 그 표를 읽게 했습니다. 관리 웹과 키오스크 설정창의 범위가 이 표와 같은지는 시험으로 맞춰 보게 했습니다.

### 바꾼 칸만 검사하기

검사를 서버에 그대로 넣으려다 걸리는 것이 있었습니다. 관리 웹은 저장할 때 바꾼 칸만이 아니라 받아 온 설정 한 줄 전체를 돌려보냈습니다. 이미 범위 밖 값이 하나 저장된 곳이라면, 그 칸은 건드리지 않고 볼륨만 바꿔도 저장이 거절될 수 있었습니다.

그래서 **이번 저장에서 바뀐 칸만** 범위를 보게 했습니다. 지금 저장된 값과 같은 칸은 범위 밖이어도 건너뛰고, 범위 밖인 바뀐 칸은 하나씩이 아니라 모두 모아 한 번에 거절했습니다. 거절 사유에는 칸 이름, 허용 범위, 받은 값을 넣었습니다.

```
설정 값이 허용 범위를 벗어나 저장하지 않았습니다 - 결제 화면 타이머: 30~900 사이의 정수만 저장할 수 있습니다 (받은 값 5)
```

관리 웹도 저장하기 전에 같은 규칙으로 먼저 보고, 보는 사람의 언어로 사유를 보여 주게 했습니다.

### 키오스크가 스스로 저장할 때는 빼기

설정을 저장하는 길을 모두 찾아보니 키오스크도 서버에 설정을 저장하고 있었습니다. 인쇄가 끝날 때마다 남은 용지 수를 저장하면서, 받은 설정 전체를 함께 돌려보냈습니다. 여기에 범위 검사를 걸면 옛 값 하나 때문에 용지 수 저장까지 막힐 수 있었습니다. 키오스크 설정창의 입력 칸은 같은 범위를 이미 지키고 있어서, 키오스크가 스스로 저장할 때는 이 검사를 하지 않게 했습니다.

## 코드로 보기 (개념 재현)

이름은 바꾼 더미입니다.

```js
// 범위 표: 서버가 읽고, 관리 웹·키오스크 설정창의 범위와 같은지 시험이 맞춰 본다
const rangeBook = {
  payWait:    { label: '결제 화면 타이머', min: 30, max: 900 },
  pickWait:   { label: '사진 선택 타이머', min: 0,  max: 600 },
  beepVolume: { label: '안내음 볼륨',     min: 0,  max: 100 },
};

// 이번 저장에서 '바뀐' 칸만 본다. 지금 저장된 값과 같으면 범위 밖이어도 건너뛴다
function badChanges(fromForm, nowSaved) {
  const bad = [];
  for (const [key, rule] of Object.entries(rangeBook)) {
    const value = fromForm[key];
    if (value == null) continue;           // 보내지 않은 칸
    if (value === nowSaved[key]) continue; // 손대지 않은 칸
    if (!Number.isInteger(value) || value < rule.min || value > rule.max) {
      bad.push(`${rule.label}: ${rule.min}~${rule.max} 사이의 정수만 (받은 값 ${value})`);
    }
  }
  return bad; // 비어 있으면 저장, 아니면 모아서 한 번에 거절
}

const nowSaved = { payWait: 5, pickWait: 60, beepVolume: 50 }; // 예전에 들어간 범위 밖 값 5

badChanges({ payWait: 5, pickWait: 60, beepVolume: 70 }, nowSaved);
// []  -> 볼륨만 바꿨으니 저장된다 (5 는 손대지 않은 칸)

badChanges({ payWait: 10, pickWait: 9999, beepVolume: 70 }, nowSaved);
// ['결제 화면 타이머: 30~900 사이의 정수만 (받은 값 10)',
//  '사진 선택 타이머: 0~600 사이의 정수만 (받은 값 9999)']

// 키오스크가 스스로 저장할 때(인쇄 뒤 용지 수 등)는 검사하지 않는다
function storeConfig(fromForm, nowSaved, { byKioskItself }) {
  if (!byKioskItself) {
    const bad = badChanges(fromForm, nowSaved);
    if (bad.length > 0) throw new Error('설정 값이 허용 범위를 벗어나 저장하지 않았습니다 - ' + bad.join(' / '));
  }
  return { ...nowSaved, ...fromForm };
}
```

## 💡 배운 것

- 입력 칸에 적힌 범위는 안내일 뿐이었습니다. 서버가 보지 않으니 어떤 값이든 저장됐고, 읽는 쪽이 범위에 맞춰 쓰니 화면의 값과 실제로 도는 값이 말없이 갈라졌습니다.
- 검사를 나중에 더할 때는 이미 저장된 값부터 생각해야 했습니다. 바뀐 칸만 봐야 옛 값 하나가 상관없는 칸의 저장을 막지 않았습니다.
- 검사를 어디에 걸지 정하기 전에 저장하는 길을 모두 찾아봐야 했습니다. 키오스크처럼 설정 전체를 돌려보내는 곳에 걸었다면 인쇄 뒤 용지 수 저장이 막힐 수 있었습니다.
- 같은 기준을 여러 곳이 따로 들고 있으면 어긋난다는 걸 [2026-11-13 글](2026-11-13-관리자-화면만-루피아를-소수-2자리로-알고-있어서-가격이-100배로-저장될-뻔했다.md)에 이어 다시 배웠습니다. 그때는 통화 자릿수였고, 이번에는 설정 범위였습니다.

## 소감

키오스크가 읽을 때 알아서 맞춰 쓰니 겉으로는 아무 문제가 없어 보였고, 그래서 눈에 띄지 않았던 것 같습니다. 검사를 넣는 일보다, 이미 저장된 값과 다른 저장 길을 깨지 않게 하는 일에 따져 볼 것이 더 많았습니다.

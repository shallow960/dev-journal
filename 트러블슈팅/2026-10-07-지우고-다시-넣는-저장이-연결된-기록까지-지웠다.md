# 2026-10-07 지우고 다시 넣는 저장이, 연결된 기록까지 지웠다

> 태그: #트러블슈팅 #PostgreSQL #외래키 #upsert #주문 #Spring

## 무엇을 / 왜

쇼핑몰의 주문은 "주문" 한 줄과 "주문 품목" 여러 줄로 저장합니다. 그런데 주문을 저장하는 코드가 이렇게 동작하고 있었습니다.

```
주문 저장 → 그 주문의 품목을 전부 삭제 → 지금 들고 있는 품목을 전부 다시 삽입
```

품목 상태(배송중·반품 요청 등)가 바뀔 때마다 이 저장을 부릅니다. 같은 품목이 같은 id 로 다시 들어가니 처음엔 문제가 없어 보였습니다.

정산 코드를 따라가다 보니, 품목을 가리키는 다른 표들이 있었습니다.

| 품목을 가리키는 표 | 품목이 지워지면 |
|---|---|
| 반품·환불·교환 기록 | 같이 삭제 (on delete cascade) |
| 결제 조정 기록 | 같이 삭제 (on delete cascade) |
| 판매자 정산 | 품목 칸을 비움 (on delete set null) |

그래서 두 가지 일이 일어나고 있었습니다.

1. **기록이 사라졌습니다.** 반품을 접수하면 반품 기록을 남기고 주문을 저장합니다. 그 저장이 품목을 지우는 순간, 방금 남긴 반품 기록이 연쇄 삭제됐습니다. 보관해야 하는 거래 기록이 남지 않았습니다.
2. **저장이 실패했습니다.** 판매자 정산 표의 외래 키는 (상점 id, 품목 id) 두 칸짜리였습니다. set null 은 두 칸을 모두 비우려고 하는데, 상점 id 칸은 비울 수 없는(not null) 칸이라 품목 삭제가 오류로 끝났습니다. 반품 완료는 PG 환불을 먼저 부르고 주문을 저장하기 때문에, 돈은 손님에게 돌아갔는데 주문 상태는 그대로 남을 수 있었습니다.

## 어떻게 풀었나

"지우고 다시 넣기" 를 "빠진 것만 지우고, 있으면 고치고, 없으면 넣기" 로 바꿨습니다.

- 지금 들고 있는 품목은 upsert(`insert ... on conflict (id) do update`)로 저장합니다. 행이 지워지지 않으니 그 행을 가리키는 기록도 그대로 남습니다.
- 주문에서 빠진 품목(예: 주문 수정으로 줄어든 품목)만 골라서 지웁니다.
- 고칠 때 `where 기존 행.order_id = 새 행.order_id` 조건을 붙였습니다. 혹시 다른 주문의 품목 id 가 들어와도 남의 행을 덮어쓰지 않게 하려는 것입니다.

부수 효과도 있었습니다. 예전에는 품목을 지웠다 넣는 동안 도메인 객체에 없는 칸(쿠폰 할인 배분, 옛 시스템의 품목 번호)이 날아가서, 저장 전에 그 값을 들고 있다가 다시 써 넣는 코드가 따로 있었습니다. upsert 는 지정한 칸만 바꾸고 나머지 칸은 건드리지 않으니 그 코드를 지울 수 있었습니다.

## 코드로 보기 (개념 재현)

표·클래스 이름은 예시입니다.

```java
// 예전: 지우고 다시 넣는다 - 품목을 가리키는 기록이 cascade 로 같이 지워진다
private void saveLinesOld(Order order) {
    jdbc.sql("delete from order_line where order_id = :orderId")
        .param("orderId", order.id())
        .update();
    for (OrderLine line : order.lines()) {
        insertLine(order, line);
    }
}

// 지금: 빠진 것만 지우고, 나머지는 있으면 고치고 없으면 넣는다
private void saveLines(Order order) {
    List<UUID> keep = order.lines().stream().map(OrderLine::id).toList();

    // 1) 주문에서 빠진 품목만 지운다(품목이 하나도 없으면 전부)
    if (keep.isEmpty()) {
        jdbc.sql("delete from order_line where order_id = :orderId")
            .param("orderId", order.id())
            .update();
    } else {
        jdbc.sql("delete from order_line where order_id = :orderId and id not in (:keep)")
            .param("orderId", order.id())
            .param("keep", keep)
            .update();
    }

    // 2) 있으면 고치고 없으면 넣는다 - 행이 그대로라 연결된 기록도 그대로 남는다
    for (OrderLine line : order.lines()) {
        jdbc.sql("""
                insert into order_line (id, order_id, product_id, quantity, price, status)
                values (:id, :orderId, :productId, :quantity, :price, :status)
                on conflict (id) do update
                set quantity = excluded.quantity,
                    price    = excluded.price,
                    status   = excluded.status
                where order_line.order_id = excluded.order_id   -- 다른 주문의 행은 덮어쓰지 않는다
                """)
            .param("id", line.id())
            .param("orderId", order.id())
            .param("productId", line.productId())
            .param("quantity", line.quantity())
            .param("price", line.price())
            .param("status", line.status().code())
            .update();
    }
}
```

고치기 전에 문제를 재현하는 테스트부터 만들었습니다. 기록 개수를 세면 저장이 기록을 지우는지 바로 보입니다.

```java
@Test
void 반품_기록이_주문을_저장한_뒤에도_남는다() {
    Order order = deliveredOrder();
    UUID lineId = order.lines().getFirst().id();

    orders.requestReturn(order.id(), lineId, "단순 변심");   // 반품 기록 1건 + 주문 저장
    assertThat(countReturnLogs(lineId)).isEqualTo(1);

    orders.completeReturn(order.id(), lineId);               // 환불 + 기록 1건 + 주문 저장
    assertThat(countReturnLogs(lineId)).isEqualTo(2);        // 예전에는 저장할 때마다 지워졌다
}
```

## 💡 배운 것

**외래 키의 삭제 규칙은 "지우고 다시 넣기" 와 만나면 조용히 일을 냅니다.** cascade 는 관련 기록을 같이 지우고, set null 은 칸을 비우려다 막힙니다. 행을 다시 넣어도 이미 지워진 기록은 돌아오지 않습니다.

**여러 칸짜리 외래 키에 set null 을 걸면 모든 칸을 비우려 합니다.** 그중 하나가 not null 이면 삭제 자체가 실패합니다.

**저장 방식이 행의 정체성을 지켜야 합니다.** 같은 id 로 다시 넣는 것과 그 행을 고치는 것은 다른 일입니다. 그 행을 가리키는 쪽에서 보면 앞의 것은 "지워졌다가 새로 생긴 행" 입니다.

**돈이 나간 뒤에 실패하는 순서를 찾습니다.** 환불을 먼저 하고 저장을 나중에 하는 흐름에서 저장이 실패하면, 되돌릴 수 없는 일만 남습니다.

## 소감

정산을 보려고 연 코드에서, 정산과 상관없어 보이는 저장 방식이 문제였습니다. 기존 테스트는 주문 하나의 상태가 바뀌는지만 확인해서, 저장 뒤에 연결된 기록이 남아 있는지는 보지 않았습니다. 이번에는 기록 수를 세는 재현 테스트 4개를 먼저 만들고 고쳤고, 주문 저장은 모든 주문 흐름이 지나가는 곳이라 백엔드 전체 테스트까지 통과시킨 뒤에 올렸습니다.

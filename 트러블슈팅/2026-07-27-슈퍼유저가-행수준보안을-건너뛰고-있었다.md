# 2026-07-27 로컬에서만 로그인이 깨졌다 — 슈퍼유저가 행 수준 보안을 건너뛰고 있었다

> 태그: #트러블슈팅 #멀티테넌트 #RLS #로컬개발

## 무엇을 / 왜

새로 만든 화면을 눈으로 확인하려고 로컬 개발 서버에서 사장님 계정으로 로그인했는데, 500(서버 오류)이 났습니다. 이상했던 건 **프로덕션에서는 같은 계정이 멀쩡하게 로그인**된다는 것이었어요. 코드가 같은데 로컬에서만 깨진다면 원인은 코드가 아니라 환경에 있다는 뜻이라, 여기부터 파고들었습니다.

## 원인을 따라가기

먼저 서버 콘솔 로그를 봤는데 정작 로그인 에러 스택이 안 보였습니다. 알고 보니 우리 서버는 **처리 못한 예외를 콘솔이 아니라 DB 테이블에 적재**하는 구조였어요. 그 테이블을 열어 보니 진짜 원인이 있었습니다.

```
IncorrectResultSizeDataAccessException: 결과가 1개일 줄 알았는데 2개가 왔다
  at ...findByEmail
```

이메일로 사용자를 찾는 쿼리가 **2행**을 돌려줬습니다. `.single()`(딱 1행 기대)로 받는 자리라 바로 터진 거죠. 확인해 보니 **같은 이메일이 서로 다른 두 가게(테넌트)에 각각 존재**했습니다.

여기서 갸우뚱했습니다. 우리는 **행 수준 보안(RLS, Row Level Security)** 으로 테넌트를 격리하거든요. 로그인은 특정 가게(호스트)로 들어오니, DB는 "지금 이 가게" 소속 사용자 1명만 보여줘야 정상입니다. 그런데 왜 두 가게 것이 다 보였을까?

진짜 원인은 여기 있었습니다. **로컬 개발용 백엔드가 DB에 슈퍼유저 계정으로 접속하고 있었던 것**입니다. PostgreSQL에서 **슈퍼유저는 RLS를 통째로 건너뜁니다.** 심지어 `FORCE ROW LEVEL SECURITY`를 걸어둔 테이블도 슈퍼유저 앞에서는 정책이 적용되지 않아요. 그래서 로컬에서는 격리가 안 걸린 채 두 가게의 사용자가 모두 조회되어 2행 → 500이 났고, 프로덕션은 권한이 낮은 전용 계정으로 접속하니 RLS가 정상 작동해 1행만 나와 문제가 없었던 겁니다.

## 어떻게 풀었나

당장 막힌 로컬 로그인은 **중복된 이메일 한쪽을 로컬 데이터에서만 정리**해서 풀었습니다(프로덕션과 무관한 개발 데이터라 안전).

하지만 더 중요한 건 깨달음이었어요. **로컬 백엔드가 슈퍼유저로 붙는 한, RLS(테넌트 격리)는 로컬에서 아예 검증이 안 된다**는 사실입니다. 로컬에서 "격리가 잘 되나?"를 아무리 눌러봐도 슈퍼유저라 항상 통과처럼 보일 뿐이에요. 그래서 **격리는 프로덕션과 같은 권한(비-슈퍼유저) 계정으로 도는 통합 테스트에서만 진짜로 검증**하기로 정리했습니다. 실제로 통합 테스트는 권한 낮은 전용 롤로 DB에 붙게 되어 있어서, 거기서만 RLS가 진짜로 켜집니다.

## 💡 배운 것

- **로컬에서 되는 것/안 되는 것이 프로덕션과 다를 수 있다.** 특히 보안 계층은 "접속 권한"에 따라 켜지고 꺼진다.
- **슈퍼유저는 `FORCE RLS`도 무시한다.** 로컬을 편하게 쓰려고 슈퍼유저로 붙여둔 게, 곧 "테넌트 격리를 한 번도 실제로 검증한 적 없다"는 사각지대였다.
- **멀티테넌트에서는 같은 이메일이 여러 테넌트에 존재할 수 있다.** "이메일은 전역에서 유일하다"는 가정을 깔면 안 되고, 조회는 항상 테넌트 안에서 이뤄져야 한다.
- **처리 못한 예외를 로그 대신 DB에 쌓는 구조라면, 디버깅은 로그가 아니라 그 테이블부터 봐야 한다.** 로그만 보고 "스택이 없네?" 하다 시간을 버릴 뻔했다.

## 코드로 보기 (개념 재현)

슈퍼유저와 일반 유저가 같은 쿼리에서 왜 다른 결과를 보는지 최소로 재현했습니다.

```sql
-- 테넌트별로 격리되는 사용자 테이블
create table users (
    tenant_id uuid not null,
    id        uuid not null,
    email     text not null
);
alter table users enable row level security;
alter table users force row level security;               -- 소유자에게도 강제

-- "지금 이 테넌트"(app.tenant_id)의 행만 보이게 하는 정책
create policy users_isolation on users
    using (tenant_id = current_setting('app.tenant_id', true)::uuid);

-- 같은 이메일이 두 테넌트에 존재
insert into users values ('1111...','a...','owner@example.com'),
                         ('2222...','b...','owner@example.com');

-- 현재 테넌트를 1111 로 지정
select set_config('app.tenant_id', '1111...', false);

-- (일반 유저로 접속했을 때) → 1행. 정책이 지금 테넌트로 좁힌다.
-- (슈퍼유저로 접속했을 때)   → 2행. 정책을 통째로 건너뛴다.  ← 로컬에서 500 나던 지점
select * from users where email = 'owner@example.com';
```

로컬은 두 번째(슈퍼유저), 프로덕션은 첫 번째(일반 유저)였던 것이 차이의 전부였습니다.

## 소감

"코드가 같은데 왜 로컬에서만?"이라는 질문이 좋은 실마리였습니다. 코드가 같다면 범인은 환경이고, 환경 차이 중 가장 무서운 건 **보이지 않게 켜지고 꺼지는 보안 계층**이더라고요. 편하려고 슈퍼유저로 붙여둔 게 격리 검증을 통째로 무력화하고 있었다는 게 특히 뜨끔했습니다. 앞으로 "이건 로컬에서 확인했어요"라고 말할 때, **그게 로컬에서 검증 가능한 종류인지**부터 따져봐야겠다고 배웠습니다. RLS 같은 건 로컬이 아니라 통합 테스트가 지켜준다는 것도요.

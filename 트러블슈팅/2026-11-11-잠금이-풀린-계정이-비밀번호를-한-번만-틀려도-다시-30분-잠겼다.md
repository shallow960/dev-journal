# 2026-11-11 잠금이 풀린 계정이, 비밀번호를 한 번만 틀려도 다시 30분 잠겼다

> 태그: #트러블슈팅 #MariaDB #SQL #로그인잠금 #운영점검

## 무엇을 / 왜

관리자 로그인에는 비밀번호를 5번 틀리면 30분 동안 잠그는 규칙이 있었습니다. 계정 표에 실패 횟수와 잠금이 풀리는 시각을 함께 적었고, 로그인에 성공하면 실패 횟수를 0으로 돌렸습니다.

어느 날 운영 중인 한 브랜드의 관리자 계정 대부분이 로그인되지 않는 문제가 있었습니다. 전날 새 계정을 하나 만든 일이 있어서, 처음에는 그 작업이 다른 계정을 건드린 줄 알았습니다.

## 어떻게 풀었나

운영 DB 는 바꾸지 않고 읽기만 하는 조회로 계정 상태부터 봤습니다.

- 잠긴 계정들은 실제로 비밀번호를 여러 번 틀린 기록이 있었습니다. 새 계정을 만든 일과는 관계가 없었습니다.
- 그런데 잠금 시각이 이미 지난 계정도 실패 횟수가 5 그대로였습니다.
- 매일 로그인에 성공하던 계정 하나만 멀쩡했습니다. 성공하면 횟수가 0이 되기 때문이었습니다.

실패 횟수를 올리는 SQL 을 따라가 보니 이런 모양이었습니다(표와 칸 이름은 바꿨습니다).

```sql
UPDATE account
SET lock_end = CASE WHEN fails + 1 >= 5 THEN :lockEnd ELSE lock_end END,
    fails    = fails + 1
WHERE id = :id;
```

잠금이 끝나도 `fails` 는 5로 남아 있었습니다. 그래서 30분을 기다린 뒤 한 번만 틀려도 `5 + 1 >= 5` 가 되어 곧바로 다시 30분이 잠겼습니다. 잠금이 풀린 게 아니라, 다음 실패 한 번을 기다리고 있었던 셈입니다. 게다가 브랜드 관리 화면에는 잠금을 푸는 기능이 없었고, 비밀번호를 재설정해도 잠금은 그대로라서 풀 방법이 없었습니다. 그날은 새 계정으로 로그인해 일을 이어 가고 있었습니다.

고치는 방향은 "끝난 잠금 뒤의 첫 실패는 1회부터 센다" 였습니다. 그런데 이 SQL 을 고치다가 처음 알게 된 것이 있었습니다. 찾아보니 MariaDB(그리고 MySQL)의 한 표 UPDATE 는 SET 의 식을 왼쪽부터 차례로 계산하고, 뒤의 식은 앞에서 이미 바뀐 값을 본다는 걸 알게 됐습니다. 표준 SQL 처럼 모든 식이 바뀌기 전 값을 보게 하려면 MariaDB 에서는 `SIMULTANEOUS_ASSIGNMENT` 라는 SQL 모드를 따로 켜야 했습니다. 원래 코드의 주석에도 "순서를 바꾸면 잠금이 한 단계 일찍 걸린다" 는 경고가 적혀 있었습니다.

그래서 두 칸을 쓰는 순서를 이렇게 정했습니다.

1. 먼저 실패 횟수를 정했습니다. 지난 잠금이 끝났으면 1, 아니면 지금 값에 1 을 더했습니다.
2. 그다음 잠금 시각을 정했습니다. 1번에서 바뀐 횟수가 한도에 닿으면 새로 잠그고, 지난 잠금이 끝났으면 지웠습니다. 이때 잠금 시각은 아직 바뀌기 전 값이었습니다.

순서를 거꾸로 하면 끝난 잠금을 먼저 지워 버려서, 1번에서 "지난 잠금이 끝났는지" 를 알아볼 수 없었습니다.

함께 한 일도 있었습니다.

- 모든 계정 목록에 [잠금 초기화] 와 [정지 / 다시 사용] 을 넣고, "잠김 (18:42 까지)", "실패 3회", 마지막 로그인을 보이게 했습니다.
- 비밀번호를 재설정하면 잠금도 함께 풀리게 했습니다.
- 로그인 실패 문구에도 숫자를 넣어 "5회 실패로 계정이 잠겼습니다. 30분 뒤에 다시 시도해 주세요." 처럼 까닭이 보이게 했습니다.

## 코드로 보기 (개념 재현)

실제 표와 칸 이름은 바꾼 더미입니다. MariaDB 기본 SQL 모드에서 값이 어떻게 바뀌는지 주석으로 따라갑니다.

```sql
-- 계정 표(더미): fails = 실패 횟수, lock_end = 잠금이 풀리는 시각(없으면 NULL)
-- 상황: 5번 틀려 잠겼고(fails = 5), 30분이 지나 lock_end 도 지났다. 지금 한 번 더 틀렸다.

-- 고치기 전: 잠금이 끝났는지 보지 않는다
UPDATE account
SET lock_end = CASE WHEN fails + 1 >= 5 THEN :lockEnd   -- 5 + 1 >= 5 -> 다시 30분 잠금
                    ELSE lock_end END,
    fails    = fails + 1                                -- 6
WHERE id = :id;

-- 고친 뒤: 횟수를 먼저, 잠금을 나중에 쓴다 (SET 이 왼쪽부터 계산되는 것을 이용)
UPDATE account
SET fails    = CASE WHEN lock_end IS NOT NULL AND lock_end <= :now THEN 1  -- 끝난 잠금 뒤 첫 실패 = 1
                    ELSE fails + 1 END,
    lock_end = CASE WHEN fails >= 5 THEN :lockEnd        -- 여기의 fails 는 바로 위에서 바뀐 값(1)
                    WHEN lock_end <= :now THEN NULL      -- 여기의 lock_end 는 아직 바뀌기 전 값
                    ELSE lock_end END
WHERE id = :id;
-- 결과: fails = 1, lock_end = NULL -> 잠기지 않는다. 앞으로 4번 더 틀려야 다시 잠긴다.
```

찾아보니 같은 문장을 표준 SQL 방식(모든 식이 바뀌기 전 값을 봄)으로 계산하면, 두 번째 CASE 의 `fails` 가 5 로 읽혀 다시 잠기게 된다는 것도 알게 됐습니다. 그래서 이 순서에 기대는 코드에는 어떤 SQL 모드를 전제로 하는지 주석으로 남겨 두었습니다.

## 💡 배운 것

- MariaDB 의 UPDATE 는 SET 의 식을 왼쪽부터 계산하고, 뒤의 식이 앞에서 바뀐 값을 본다는 걸 배웠습니다. 한 문장 안에서 두 칸이 서로를 참조하면, 쓰는 순서가 곧 규칙이 됐습니다.
- "잠금이 풀렸다" 는 시각만 지난 상태가 아니라 횟수까지 처음으로 돌아간 상태여야 했습니다. 시간이 지나면 끝나는 상태는, 끝났을 때 함께 돌려놓을 값까지 같이 정해야 한다는 걸 배웠습니다.
- 잠그는 기능을 만들 때 푸는 길(잠금 초기화, 비밀번호 재설정)도 같이 만들어야 한다는 걸 배웠습니다. 이번에는 풀 방법이 없어서 새 계정을 만들어 우회하고 있었습니다.

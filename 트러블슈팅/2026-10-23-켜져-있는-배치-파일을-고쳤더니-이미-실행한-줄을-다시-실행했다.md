# 2026-10-23 켜져 있는 배치 파일을 고쳤더니, 이미 실행한 줄을 다시 실행했다

> 태그: #트러블슈팅 #Windows #배치파일 #cmd

## 무엇을 / 왜

키오스크 앱을 띄우는 Windows 배치 파일(`.cmd`)에 환경변수 한 줄을 더했습니다. 그런데 앱을 껐다 다시 켜도 새 설정이 먹지 않았습니다.

프로세스 목록을 보니 이상했습니다. 지금 떠 있는 앱은 방금 연 창이 아니라 **아침에 열어 둔 옛 창**의 자식이었습니다. 옛 창이 앱이 꺼진 뒤 `npm run dev` 를 한 번 더 실행했던 것입니다. 옛 창은 새 줄이 추가되기 전의 환경이라 새 설정이 없었습니다. 새로 연 창은 이미 떠 있는 앱 때문에 그냥 대기하고 있었습니다.

옛 창은 왜 같은 명령을 다시 실행했을까요?

## 어떻게 풀었나

cmd 는 배치 파일을 처음에 다 읽어 두지 않습니다. 명령 하나가 끝날 때마다 **파일을 다시 열고, "몇 바이트째까지 읽었는지" 기억해 둔 위치부터** 이어서 읽습니다.

실행 중에 파일 앞부분에 줄을 끼워 넣으면 내용이 뒤로 밀립니다. 그런데 cmd 는 기억해 둔 바이트 위치에서 읽으니, 그 위치에는 이제 **앞에 있던 내용**이 와 있습니다. 그래서 이미 실행한 줄을 다시 실행한 것입니다. 이번에는 그 줄이 `npm run dev` 였습니다.

해결은 옛 창과 새 창을 모두 닫고 다시 실행하는 것이었습니다. 그리고 규칙을 하나 정했습니다. **실행 중인 배치 파일은 고치지 않는다(먼저 끄고 고친다).**

## 코드로 보기 (개념 재현)

자기 자신의 앞부분에 줄을 끼워 넣는 배치 파일로 재현해 봤습니다. 끼워 넣는 길이를 "[B] 줄 + 고치는 명령 줄" 의 바이트 수(316)와 같게 맞추면, cmd 가 다시 읽는 위치가 정확히 `[B]` 줄의 시작이 됩니다.

```bat
@echo off
echo [A] setup
echo [B] long command starts
rem 아래 줄이 '오래 걸리는 명령' 자리다. 실행되는 동안 이 파일의 2번째 줄 앞에 316바이트를 끼워 넣는다.
rem (다시 실행돼도 또 끼워 넣지 않게, 이미 끼워 넣었으면 아무것도 하지 않는다)
powershell -NoProfile -Command "$p='%~f0'; $t=[IO.File]::ReadAllText($p); if (-not $t.Contains([string][char]10 + 'rem pad')) { $i=$t.IndexOf([char]10)+1; $pad='rem pad' + ('.' * 307) + [char]13 + [char]10; [IO.File]::WriteAllText($p, $t.Substring(0,$i) + $pad + $t.Substring($i)) }"
echo [C] after long command
```

```text
# 실제 출력
[A] setup
[B] long command starts
[B] long command starts      <- 이미 실행한 줄을 한 번 더 실행했다
[C] after long command
```

(위 코드 블록의 `rem` 설명 두 줄은 글로 읽기 쉽게 넣은 것이라, 실제로 돌린 파일에는 없습니다. 설명 줄이 있으면 바이트 수가 달라져 다시 읽는 위치도 달라집니다.)

## 💡 배운 것

- cmd 는 배치 파일을 한 번에 읽지 않고, 명령마다 다시 열어 바이트 위치로 이어 읽는다는 걸 배웠습니다. 그래서 실행 중에 고치면 엉뚱한 곳부터 실행될 수 있습니다.
- "설정을 바꿨는데 안 먹는다" 는 증상은, 지금 떠 있는 프로세스를 **누가 띄웠는지**(부모 프로세스와 시작 시각)부터 보면 빨리 풀립니다.

## 소감

설정 한 줄을 더했을 뿐인데 앱이 옛 설정으로 다시 떠서 한참 헷갈렸습니다. 재현해 보니 같은 줄이 정말로 두 번 찍혀서, 원리를 눈으로 확인한 게 오래 기억에 남을 것 같습니다.

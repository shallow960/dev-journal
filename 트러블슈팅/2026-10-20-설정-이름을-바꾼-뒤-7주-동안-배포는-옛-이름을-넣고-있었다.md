# 2026-10-20 설정 이름을 바꾼 뒤 7주 동안, 배포는 옛 이름을 넣고 있었다

> 태그: #트러블슈팅 #설정 #배포점검 #전자서명 #fail-closed

## 무엇을 / 왜

키오스크가 받는 손님 화면 묶음은 서버가 개인키로 서명하고, 키오스크가 공개키로 확인한 뒤에만 보여 줍니다. 이 서명 키 설정의 이름이 2026-09-02 에 바뀌었어요. 다른 용도의 서명 키(프로그램 업데이트용)와 섞이지 않게 이름을 나누고, "이 키는 화면 서명용" 이라는 용도 값도 반드시 넣게 한 변경이었습니다.

그런데 그 커밋이 바꾼 파일 25개 가운데 **배포 파일이 하나도 없었습니다.** 배포 파일은 7주 동안 옛 이름으로 키를 넣게 되어 있었고, 새로 생긴 용도 값은 어디서도 넣지 않았어요.

그런데도 아무도 몰랐습니다.

- 서버는 키가 없어도 잘 떴어요. 키는 "쓸 때" 확인하는 구조였거든요.
- 배포 점검은 "서버가 살아 있나(health)" 만 봤습니다.
- 서명 없이 내보내는 길은 없어서(fail-closed) 잘못된 화면이 나간 적은 없어요. 대신 관리자가 화면을 처음 배포하는 순간 503 이 납니다. 예약 배포는 경고 로그만 남기고 건너뛰고요.

안전하게 실패하도록 만든 설계가, 실패를 조용하게도 만들고 있었습니다.

## 어떻게 풀었나

1. **이름을 하나로 맞췄습니다.** 배포가 넣는 이름을 서버가 읽는 새 이름 4개로 바꾸고, 용도 값은 상수로 넣었어요. 옛 이름도 같이 읽어 주는 별칭은 만들지 않았습니다. 그러면 이름을 나눈 이유(다른 키와 섞이지 않게)가 다시 사라지니까요. 대신 서버가 시작할 때 옛 이름이 보이면 "이름만" 오류 로그로 남깁니다.
2. **배포 전에 서명 재료를 직접 확인합니다.** 컨테이너를 건드리기 **전에** 두 가지를 봐요.
   - 개인키에서 공개키를 다시 만들어, 설정된 공개키와 짝이 맞는지
   - 그 공개키가 키오스크 앱에 넣어 둔 신뢰 목록에, 이 서버 주소의 키로 들어 있는지

   하나라도 틀리면 그 자리에서 멈추고, 출력에는 설정 이름과 서버 주소만 남깁니다. 키 값은 남기지 않아요.
3. **서명이 안 되는 이유를 로그로 남깁니다.** 용도 값 없음, 키 없음, 공개키 없음, 짝 불일치를 코드로 구분해요. 값과 파일 경로는 남기지 않습니다. 상태 점검(health)을 "나쁨" 으로 바꾸지는 않았어요. 화면 서명 하나 때문에 결제·로그인까지 비정상으로 보이면 안 되니까요.

시험은 정상 2가지, 실패 10가지(짝 불일치, 목록에 없는 키, 목록에 없는 서버 주소 등)를 돌려 모두 기대대로 나왔고, 출력에 키 값은 없었습니다. 일부러 배포 파일을 옛 이름으로 되돌리거나 짝 비교를 빼 보면 시험이 실패하는 것도 확인했어요. 아직 커밋 전이고, 따로 받은 검토의 지적을 반영하는 중입니다.

## 코드로 보기 (개념 재현)

```bash
#!/usr/bin/env bash
# 개념 재현: 이름과 경로는 모두 더미다.
set -euo pipefail

precheck_signing() {
  # 1) 짝 확인: 개인키에서 공개키를 다시 만들어 비교한다.
  #    키는 파이프로만 흘린다. 화면·명령줄·임시 파일에 남기지 않고,
  #    도구의 오류 메시지도 버린다(실패 이유는 아래 한 줄로만).
  local derived
  derived="$(printf '%s' "$SIGN_PRIVATE_KEY_B64" | base64 -d 2>/dev/null \
    | openssl pkey -inform DER -pubout -outform DER 2>/dev/null | base64 -w0)" \
    || { echo "precheck: SIGN_PRIVATE_KEY_B64 를 읽지 못함" >&2; return 1; }
  [ "$derived" = "$SIGN_PUBLIC_KEY_B64" ] \
    || { echo "precheck: SIGN_PRIVATE_KEY_B64 와 SIGN_PUBLIC_KEY_B64 가 짝이 아님" >&2; return 1; }

  # 2) 목록 확인: 키오스크 앱에 들어간 신뢰 목록에 이 서버 주소가 있는가,
  #    그리고 그 주소의 키 가운데 이 공개키가 있는가. 실패 이유를 따로 말한다.
  jq -e --arg o "$PUBLIC_ORIGIN" '.origins[$o] != null' trust.json >/dev/null \
    || { echo "precheck: 서버 주소($PUBLIC_ORIGIN)가 신뢰 목록에 없음" >&2; return 1; }
  jq -e --arg o "$PUBLIC_ORIGIN" --arg k "$SIGN_KEY_ID" --arg p "$SIGN_PUBLIC_KEY_B64" \
     '.origins[$o] | any(.kid == $k and .publicKey == $p)' trust.json >/dev/null \
    || { echo "precheck: SIGN_KEY_ID 의 공개키가 신뢰 목록($PUBLIC_ORIGIN)에 없음" >&2; return 1; }
}

precheck_signing      # 여기서 실패하면 아래는 하나도 실행되지 않는다
docker compose pull   # 이미지·컨테이너를 건드리는 일은 검사 뒤에만
docker compose up -d
```

버리는 키로 돌려 본 결과입니다.

```text
정상(짝 맞음, 목록에 있음)  -> 통과
짝 불일치                   -> precheck: SIGN_PRIVATE_KEY_B64 와 SIGN_PUBLIC_KEY_B64 가 짝이 아님
짝은 맞지만 목록에 없는 키  -> precheck: SIGN_KEY_ID 의 공개키가 신뢰 목록(https://example.test)에 없음
목록에 없는 서버 주소       -> precheck: 서버 주소(https://other.test)가 신뢰 목록에 없음
개인키 형식 오류            -> precheck: SIGN_PRIVATE_KEY_B64 를 읽지 못함
```

## 💡 배운 것

**이름을 바꿀 때는 코드만이 아니라 그 이름을 넣어 주는 쪽(배포 파일)까지 찾아야 한다는 걸 다시 배웠습니다.** 서버와 키오스크는 같은 커밋에서 새 이름으로 바뀌었지만, 값을 넣어 주는 배포 파일은 그 커밋에 들어 있지 않았어요. 2026-09-08 에 "한 곳을 고치면 같은 정보가 필요한 자리를 다 찾아봐야 한다" 를 배웠는데, 이번엔 그 자리가 배포 파일이었습니다. 이름을 바꾸면 저장소 전체에서 옛 이름을 한 번 찾아보는 걸 습관으로 하려고 합니다.

**"서버가 살아 있다" 와 "그 기능이 된다" 는 다르다는 걸 다시 배웠습니다.** 2026-09-16 에 "통과했다는 건 무엇을 검사했느냐에 달렸다" 를 배웠는데, 이번엔 배포 점검이 health 만 보고 있었어요. 기능에 필요한 재료가 빠져도 배포는 성공이었습니다.

**배포 전에 그 기능의 재료(키 짝, 신뢰 목록)를 직접 확인하는 검사를 두는 방법을 배웠습니다.** 컨테이너를 건드리기 전에 확인하니, 틀린 키로는 배포가 시작조차 되지 않아요.

**설정이 비어도 조용히 지나가는 길은 늘 의심해야 한다는 걸 다시 배웠습니다.** 2026-09-29 에 "기본 거절은 안전하지만 조용하다" 를, 2026-10-01 에 빈 설정 하나로 백업이 말없이 끝나는 일을 겪었는데, 이번에도 서명 없이는 내보내지 않는 안전한 설계가 7주 동안 아무도 모르는 실패가 됐어요. 안전한 실패도 누군가 볼 수 있는 곳에 이유를 남겨야 합니다.

**짝으로 쓰는 값은 짝으로 확인한다는 걸 다시 배웠습니다.** 2026-09-18 에 상점 ID 와 비밀키처럼 쌍으로 쓰는 값은 한쪽만 바뀌면 조용히 거절된다는 걸 배웠어요. 개인키와 공개키도 같아서, 각각 "있는지" 가 아니라 "서로 맞는지" 를 봐야 했습니다.

## 소감

서명 없는 화면이 나가지 않게 막아 둔 덕분에 사고는 없었지만, 그 덕분에 7주 동안 아무도 몰랐다는 게 아이러니했습니다. 안전장치는 막는 것만큼 "막았다" 고 알리는 것도 중요하다는 걸 느꼈어요.

# 2026-10-16 명령을, 엉뚱한 서버 창에서 치고 있었다

> 태그: #트러블슈팅 #운영 #SSH #EC2 #메타데이터

## 무엇을 / 왜

새 서버를 만든 뒤, 서버에 붙인 권한(IAM 역할)이 맞는지 확인하는 명령을 돌렸습니다. 그런데 결과에 **원래 계정 번호** 가 나오고, 새로 만든 백업 버킷 접근은 거부됐어요. "새 서버를 엉뚱한 계정에 만들었나?" 하고 한참 헷갈렸습니다. 확인하는 사이 두 계정 번호를 서로 바꿔 말하는 바람에 더 꼬였고요.

## 어떻게 풀었나

- 터미널 창을 다시 보니, 명령을 친 창의 **프롬프트 호스트 이름이 원래 서버** 였습니다. 두 서버에 접속한 창을 같이 열어 두고 오가다 생긴 일이었어요.
- 각 서버 안에서 **인스턴스 메타데이터** 로 계정 번호와 인스턴스 ID 를 직접 찍고, 콘솔의 값과 맞춰 봤습니다. 새 서버는 처음부터 맞는 계정에 맞게 만들어져 있었어요.
- 그다음부터는 명령마다 **"어느 서버의 프롬프트에서 칠지"** 를 함께 적었습니다. 두 서버를 부르는 이름도 정확히 정했어요(개발 배포 서버 / 운영 서버).
- 긴 스크립트를 터미널에 붙여 넣다 중간이 빠져 깨진 일도 있었는데, 그건 파일로 만들어 복사한 뒤 **체크섬이 같은지** 확인하고 실행하는 것으로 바꿨습니다.

## 코드로 보기 (개념 재현)

```bash
# 지금 이 창이 어느 서버인지: 프롬프트의 호스트 이름부터 본다
hostname          # 예: ip-10-0-1-23

# 이 서버가 어느 계정·인스턴스인지 메타데이터로 확인 (IMDSv2)
TOKEN=$(curl -s -X PUT http://169.254.169.254/latest/api/token \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
  http://169.254.169.254/latest/dynamic/instance-identity/document \
  | python3 -c 'import json, sys; d = json.load(sys.stdin); print(d["accountId"], d["instanceId"], d["region"])'
```

```bash
# 긴 내용은 붙여 넣지 않고 파일로 보낸 뒤, 같은지 확인하고 실행한다
scp -i key.pem setup.sh user@server:      # 내 PC 에서
sha256sum ~/setup.sh                       # 서버에서: 내 PC 에서 본 값과 같아야 한다
bash ~/setup.sh
```

## 💡 배운 것

**명령 내용보다 지금 어디서 치는지를 먼저 봅니다.** 같은 명령도 다른 서버에서 치면 결과가 완전히 달라지고, 엉뚱한 결론으로 이어졌어요.

**기억보다 메타데이터가 정확합니다.** 계정 번호를 기억에 기대니 서로 바꿔 말했고, 서버에 직접 물어보니 바로 정리됐습니다.

**붙여 넣은 내용도 확인 대상입니다.** 긴 내용은 전송 중에 깨질 수 있어서, 파일로 보내고 체크섬으로 맞춰 보는 게 안전했어요.

## 소감

서버가 하나일 때는 생각하지 않던 것들이었습니다. 서버가 둘이 되는 순간부터는 "여기가 어디인가"를 확인하는 단계가 작업 절차에 들어가야 한다는 걸 배웠어요.

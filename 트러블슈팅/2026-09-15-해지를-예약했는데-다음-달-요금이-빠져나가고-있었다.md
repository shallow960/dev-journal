# 2026-09-15 해지를 예약했는데, 다음 달 요금이 빠져나가고 있었다

> 태그: #트러블슈팅 #결제 #구독 #상태전이

## 무엇을 / 왜

서비스 오픈을 앞두고 정기결제 코드를 처음부터 끝까지 읽었습니다. 기능이 안 된다는 신고가 있어서가 아니라, 돈이 오가는 곳이라 한 번은 눈으로 따라가 보고 싶었습니다.

구독 해지에는 두 가지가 있습니다.

| 방식 | 뜻 |
|---|---|
| 즉시 해지 | 남은 기간을 일할 환불하고 바로 끝낸다 |
| 기간 말 해지 예약 | 이미 낸 기간은 끝까지 쓰고, **다음 결제는 하지 않는다** |

두 번째가 문제였습니다. 해지를 예약해도 **다음 결제일에 한 주기 요금이 그대로 청구되고 있었습니다.**

## 어떻게 풀었나

### 예약은 적혀 있는데, 결제일은 그대로였다

기간 말 해지를 예약하면 구독에 "언제 끝난다" 는 시각만 적힙니다. 그런데 **"다음 결제일" 칸은 그대로 남아 있었습니다.**

정기결제 배치는 매일 "다음 결제일이 지난 구독" 을 모아 청구합니다. 해지를 예약한 구독도 그 목록에 그대로 들어갑니다.

```
해지 예약(끝나는 날 = 이번 주기 끝) → 그 날짜에 결제일도 도래
  → 배치가 청구 대상으로 집음 → 한 주기 결제
  → 결제 성공 후 갱신 단계에서 "끝나는 날이 지났네" → 그제야 해지
```

**돈이 먼저 나가고, 해지는 그다음**이었습니다. 게다가 이 경로에는 환불이 없습니다. 해지를 예약한 사람이 다음 달 요금을 내고 그 즉시 해지되는 셈이었습니다.

### 무료체험 중 해지는 더 이상했다

해지 예약은 끝나는 날을 **"현재 주기의 끝"** 으로 잡습니다. 그런데 무료체험 중인 구독에서 그 값은 체험 종료일이 아니라 **첫 유료 주기의 끝**이었습니다.

체험 중에 해지한 사람은 "체험만 써 보고 끝낸다" 는 뜻인데, 체험 종료일에 유료로 전환되어 한 달치가 청구되고 있었습니다.

### 청구 직전에 거르게 했다

고칠 자리가 두 곳 있었습니다.

1. 해지를 예약할 때 다음 결제일을 지운다
2. 청구 대상을 고른 뒤, 결제하기 전에 거른다

**2번을 택했습니다.** 결제일을 지우면 해지를 취소(재활성)할 때 되돌릴 값이 사라집니다. 그리고 청구 대상을 고르는 곳은 돈이 나가기 직전의 마지막 관문이라, 나중에 다른 경로가 생겨도 여기만 지나면 걸립니다.

체험 중 해지는 끝나는 날을 **체험 종료 시각**으로 잡도록 함께 고쳤습니다.

## 코드로 보기 (개념 재현)

고치기 전입니다.

```java
for (구독 구독 : 결제일이_지난_구독들(지금)) {
    var 청구서 = 청구서만들기(구독, 요금(구독.요금제()));
    결제하기(청구서);          // ★ 해지를 예약했어도 여기서 그냥 긁는다
}

// 결제 성공 후 갱신 단계
void 갱신(구독 구독, OffsetDateTime 결제시각) {
    구독.다음주기로(결제시각);
    if (구독.끝나는날() != null && !구독.끝나는날().isAfter(결제시각)) {
        구독.즉시해지(결제시각);   // 이미 긁은 뒤에야 해지된다
    }
}
```

고친 뒤입니다.

```java
for (구독 구독 : 결제일이_지난_구독들(지금)) {
    // 끝나는 날이 이번 결제일보다 뒤가 아니면, 이번 주기는 청구하지 않는다.
    if (구독.끝나는날() != null && !구독.끝나는날().isAfter(구독.다음결제일())) {
        구독.즉시해지(구독.끝나는날());   // 예약한 그 시각으로 끝낸다
        저장(구독);
        continue;                        // 결제 없음
    }
    ...
}
```

해지 예약 시각을 정하는 쪽도 체험을 구분하게 했습니다.

```java
void 기간말해지예약(OffsetDateTime 지금) {
    if (상태 == 해지됨) return;
    // 체험 중이면 "첫 유료 주기의 끝" 이 아니라 체험이 끝나는 시각이 마지막이다.
    if (상태 == 체험중 && 체험종료 != null) {
        끝나는날 = 체험종료;
        return;
    }
    끝나는날 = (이번주기끝 == null) ? 지금 : 이번주기끝;
}
```

검증은 "청구가 일어나지 않는 것" 을 봐야 합니다.

```java
@Test
void 기간말_해지를_예약한_구독은_청구하지_않고_해지된다() {
    var 구독 = 구독시작(가게, "표준", 월간, 시작일: 지금.minusDays(40));  // 주기 끝이 지났다
    구독.기간말해지예약(지금.minusDays(20));
    저장(구독);

    정기결제배치.실행();

    var 결과 = 조회(구독.id());
    assertThat(결과.상태()).isEqualTo(해지됨);
    assertThat(청구서수(구독.id())).isZero();      // 청구서가 아예 만들어지지 않았다
    assertThat(결제건수(구독.id(), "성공")).isZero();
}

@Test
void 체험_중에_해지하면_체험이_끝날_때_유료로_넘어가지_않는다() {
    var 구독 = 구독시작(가게, "표준", 월간, 시작일: 지금.minusDays(15), 체험일수: 14);
    구독.기간말해지예약(지금.minusDays(5));
    저장(구독);

    정기결제배치.실행();

    assertThat(조회(구독.id()).상태()).isEqualTo(해지됨);
    assertThat(청구서수(구독.id())).isZero();
}
```

## 💡 배운 것

**"예약" 은 적어 두는 것으로 끝나지 않습니다.** 미래 상태를 적어 뒀다면, 그 시각이 됐을 때 **누가 그것을 실제로 적용하는지**가 정해져 있어야 합니다. 여기서는 적용하는 주체가 "결제 성공 후 갱신" 이었고, 그건 이미 돈이 나간 다음이었습니다.

**상태 전이는 돈이 나가기 전에 확인해야 합니다.** 순서가 한 칸만 뒤로 밀려도 "청구하고 해지" 가 됩니다. 되돌리려면 환불이라는 별도 작업이 필요하고, 그 경로는 없었습니다.

**무료체험이 있는 구독에는 "주기의 끝" 이 두 개입니다.** 체험이 끝나는 시각과 유료 주기가 끝나는 시각. 한쪽만 생각하고 코드를 쓰면 체험 사용자에게 엉뚱한 청구가 갑니다.

**막을 자리는 여러 곳이지만, 돈이 나가는 길목이 제일 안전합니다.** 예약을 거는 쪽에서 막으면 예약을 거는 새 경로가 생길 때 또 뚫립니다.

## 소감

신고가 들어온 버그가 아니라, 읽다가 발견한 결함이었습니다. 해지를 예약한 사람은 다음 달 청구서를 받고 나서야 알았을 테고, 그때는 이미 돈이 빠져나간 뒤입니다.

돈을 받는 코드는 "잘 받아지는가" 만 보게 되는데, **"받으면 안 될 때 안 받는가" 는 따로 확인하지 않으면 드러나지 않는다**는 걸 알았습니다. 해지·체험·환불처럼 "안 받는" 경우가 오히려 검증이 약했습니다.

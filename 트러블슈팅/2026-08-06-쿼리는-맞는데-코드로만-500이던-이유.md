# 2026-08-06 손으로는 되는 쿼리가, 코드로 부르면 500이 됐다 - 숫자 컬럼을 정수로 바로 받으려다

> 태그: #트러블슈팅 #데이터베이스 #JDBC #타입변환

## 오늘 한 일 (요약)
- 상품 목록을 내려주는 조회 API를 새로 만들었는데, 호출하면 500(서버 오류)로 죽었다.
- 같은 SQL을 DB 콘솔에서 손으로 실행하면 멀쩡히 결과가 나왔다. "쿼리는 맞는데 코드로만 실패"였다.
- 범인은 가격 컬럼이었다. 십진수(numeric) 컬럼을 코드에서 정수로 "바로" 받으려 한 것.
- 드라이버가 그 변환을 지원하지 않아 예외가 났고, 십진수 그대로 받아 코드에서 변환하도록 바꿔 해결했다.

## 무엇을 / 왜 (증상)
목록 조회 결과의 각 행을 객체로 바꿀 때, 가격 필드를 이렇게 받았다.

- 컬럼 타입: `price numeric` (소수점까지 담는 십진수)
- 코드에서 요청: "이 컬럼을 정수(64비트 정수)로 바로 달라"

호출하면 500. 로그를 따라가면 결과 매핑 중 가격 컬럼에서 "이 타입 변환은 지원하지 않는다"는 예외가 떴다. SQL 자체는 문제가 없어서(콘솔에선 성공) "쿼리 오류"로 오해하기 쉬웠다.

핵심은 이거였다. **DB의 십진수 타입과 코드의 정수 타입은 자동으로 곧장 맞춰지지 않는다.** 드라이버가 "십진수 -> 문자열 / 십진수 객체"는 내주지만 "십진수 -> 정수 객체로 곧장"은 막아둔 경우가 있다. 정수로 억지 변환하면 소수점이 잘리거나 범위를 넘을 수 있어서다.

## 어떻게 풀었나
방법은 단순하다. **드라이버가 확실히 내주는 타입으로 먼저 받고, 정수 변환은 내 코드에서** 한다.

- 가격을 십진수 객체로 받는다.
- 그 다음 코드에서 정수로 바꾼다.
- 값이 없을 수 있는 컬럼(예: 할인가)은 null을 함께 처리한다. 바로 정수로 받으면 빈 값에서 또 터진다.

이렇게 하면 "타입을 바로 못 바꿔 나는 예외"와 "빈 값에서 나는 예외"를 둘 다 피한다.

## 코드로 보기 (개념 재현)
```java
// (문제) 십진수 컬럼을 정수로 "바로" 받으려 함
//   -> 드라이버가 지원 안 하면 매핑 단계에서 예외 -> 응답 500
long price     = row.getObject("price", Long.class);       // 십진수 -> Long 직행 (지원 안 될 수 있음)
Long salePrice = row.getObject("sale_price", Long.class);  // null이면 더 위험

// (해결) 드라이버가 확실히 주는 타입(십진수 객체)으로 받고, 변환은 코드에서
BigDecimal priceDec     = row.getBigDecimal("price");
BigDecimal salePriceDec = row.getBigDecimal("sale_price"); // 없을 수 있음(null)

long price     = priceDec == null ? 0L : priceDec.longValue();
Long salePrice = salePriceDec == null ? null : salePriceDec.longValue();
```

포인트는 두 개다.
- **직행 변환을 믿지 말 것:** 십진수 -> 정수처럼 "정보가 줄어드는 변환"은 드라이버가 막을 수 있다.
- **null을 먼저 생각할 것:** 원시 정수로 바로 받으면 빈 값에서 또 터진다. 없을 수 있는 값은 객체로 받아 null을 갈라 처리한다.

## 💡 배운 것
- "SQL은 맞는데 코드로만 실패"라면 쿼리가 아니라 **결과를 객체로 옮기는 매핑 단계**를 의심한다.
- DB 타입과 코드 타입 사이엔 **자동으로 안 맞춰지는 경계**가 있다. 특히 십진수와 정수처럼 정밀도가 걸린 변환.
- 드라이버가 지원하는 타입으로 받고 **변환은 내 코드에서** 하는 게 안전하다.
- 돈처럼 정밀도가 중요한 값은 애초에 십진수로 다루고, 정수로 바꿀지 여부를 의식적으로 정한다.

## 소감
"쿼리 맞잖아, 왜 안 되지"에서 시간을 좀 썼다. 콘솔에선 되니까 계속 SQL만 들여다봤는데, 진짜 범인은 결과를 객체로 옮기는 마지막 한 뼘이었다. 앞으로 "손으로는 되는데 코드로는 안 된다"가 나오면 쿼리보다 매핑을 먼저 본다.

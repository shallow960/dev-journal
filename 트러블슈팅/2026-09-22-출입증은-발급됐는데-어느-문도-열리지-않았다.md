# 2026-09-22 출입증은 발급됐는데, 어느 문도 열리지 않았다

> 태그: #트러블슈팅 #인증 #토큰 #권한 #멀티테넌트

## 무엇을 / 왜

고객사에서 "관리 화면이 이상하다" 는 문의가 오면, 운영자가 그 고객의 화면을 직접 봐야 합니다. 말로만 주고받으면 재현이 안 되니까요.

그래서 "대리 접속" 이라는 기능이 코드에 이미 있었습니다. 운영자가 사유를 적으면 그 고객 전용 출입증(토큰)을 30분짜리로 발급해 주는 구조입니다.

그런데 실제로 눌러 보니 **발급은 되는데 어느 화면도 열리지 않았습니다.** 관리 화면이든 설정 화면이든 전부 이렇게 돌려보냈습니다.

```
GET /api/.../dashboard 403 (Forbidden)
```

발급이 성공했다는 응답까지 받았는데 403 이라 처음엔 뭘 봐야 할지도 애매했습니다.

## 어떻게 풀었나

### 출입증 안을 펼쳐 봤다

403 은 "너는 누군지 알겠는데 권한이 없다" 는 뜻입니다. 그러면 출입증에 뭐라고 적혀 있는지부터 봐야 합니다. 토큰을 디코딩해서 내용을 꺼내 봤습니다.

```
sub        = 3f6c...   ← 대리 접속 세션 번호
tenant_id  = 9a21...   ← 들어가려는 가게
roles      = [ADMIN, USER]
account_id = (없음)
```

문제가 두 개 보였습니다.

- **주인 자리(sub)에 사람이 아니라 접속 번호**가 들어 있었습니다. 세션을 식별하려고 넣은 값인데, 다른 화면들은 이 자리를 "이 요청을 보낸 사용자" 로 읽습니다.
- **계정 식별자가 아예 없었습니다.**

### 문이 요구하는 것과 맞지 않았다

관리 화면들이 요청을 받아들이는 조건을 따라가 봤습니다. 이렇게 확인하고 있었습니다.

1. 이 토큰이 가게용으로 발급된 것인가
2. 토큰에 **계정 식별자**가 있는가
3. 그 계정이 **이 가게의 활성 구성원**인가

2번에서 이미 걸렸습니다. 계정 식별자가 없으니 3번은 볼 것도 없고요. 역할에 ADMIN 을 넣어 줬으니 통과할 줄 알았는데, 화면이 보는 건 역할 이름이 아니라 **"이 계정이 이 가게 사람인가"** 였습니다.

출입증에 직급은 적었는데 이름을 안 적은 셈입니다.

### 우회로를 만들지 않기로 했다

여기서 두 갈래가 있었습니다.

| 방법 | 내용 | 문제 |
|---|---|---|
| A | 화면마다 "대리 접속이면 통과" 예외를 추가 | 예외를 넣을 곳이 계속 늘어난다. 하나 빠뜨리면 그 화면만 안 열린다 |
| B | 출입증에 **그 가게 주인의 신원**을 실어서 발급 | 화면 코드는 하나도 안 건드린다 |

B 를 골랐습니다. 대리 접속의 목적 자체가 "주인이 보는 화면을 그대로 보는 것" 이라, 주인으로 들어가는 게 기능의 의도와도 맞습니다. 예외 조건을 곳곳에 뿌리면 나중에 새 화면을 만들 때마다 같은 예외를 기억해야 하는데, 그건 반드시 빠뜨립니다.

발급할 때 그 가게의 주인 계정을 찾아서 넣도록 바꿨습니다. 세션 번호는 주인 자리에서 빼고 별도 항목으로 옮겼습니다.

```
sub                  = 주인 사용자 번호   ← 바뀜
account_id           = 주인 계정 번호     ← 추가
impersonated         = true              ← 대리 접속 표시
impersonation_id     = 3f6c...           ← 세션 번호는 여기로
actor_email          = 들어간 운영자
```

이러니 화면들이 전부 열렸습니다.

### 권한을 넓혔으면, 위험한 자리는 따로 막는다

주인 권한으로 들어간다는 건 **주인이 할 수 있는 걸 다 할 수 있다**는 뜻입니다. 여기엔 결제수단 등록, 요금제 변경, 크레딧 충전, 해지, 약관 동의가 포함됩니다. 전부 **주인 카드에서 돈이 나가거나 주인 이름으로 약정이 생기는** 자리입니다.

운영자가 화면을 보러 들어갔다가 실수로 누르면 남의 카드가 긁힙니다. 그래서 요청을 받을 때마다 한 번 더 확인하는 관문을 뒀습니다.

- 이 대리 접속 세션이 **아직 살아 있는가** (종료·만료·운영자 계정 정지)
- 요청 경로가 **돈·약정과 관련된 곳인가** → 조회는 되지만 변경은 거절

읽는 건 다 되고, 돈 쓰는 것만 막힙니다.

### 저장 자체가 안 되던 문제가 하나 더 있었다

토큰을 고치고 나니 이번엔 접속 기록이 저장되지 않았습니다.

이 서비스는 가게마다 데이터를 칸막이로 나눠 둡니다. 접속하는 데이터베이스 세션에 "지금 어느 가게냐" 를 적어 두면, 그 가게 줄만 보이고 다른 가게 줄은 아예 없는 것처럼 동작합니다. 접속 기록 표에도 이 칸막이가 걸려 있었습니다.

그런데 대리 접속을 **시작하는 시점의 요청은 운영자 요청**입니다. 운영자는 특정 가게 소속이 아니라서 "지금 어느 가게냐" 가 비어 있습니다. 그러니 저장하려는 줄이 칸막이 검사에 걸려서 거절됐습니다.

칸막이를 끄는 건 답이 아닙니다. 저장하는 그 순간에만 대상 가게를 범위로 지정해 주고, 트랜잭션이 끝나면 저절로 풀리게 했습니다.

## 코드로 보기 (개념 재현)

고치기 전 발급입니다. 세션 번호가 주인 자리에 있습니다.

```java
public String 발급(UUID 가게id, UUID 세션id) {
    return 토큰만들기()
        .주인(세션id.toString())            // 사람이 아니라 세션 번호
        .넣기("tenant_id", 가게id)
        .넣기("roles", List.of("ADMIN", "USER"))
        .서명();
}
```

화면이 요청을 받아들이는 조건입니다. 여기는 그대로 뒀습니다.

```java
var 계정id = 토큰.계정id();                  // 없으면 여기서 끝
if (계정id == null) 거절(403);
if (!구성원인가(계정id, 가게id)) 거절(403);   // 이 가게 사람인가
```

고친 뒤 발급입니다. 그 가게 주인을 찾아서 신원을 싣습니다.

```java
public 대리접속 시작(UUID 가게id, 운영자 운영자, String 사유) {
    var 주인 = 주인찾기(가게id)              // 활성 상태인 owner 한 명
        .orElseThrow(() -> new IllegalStateException("주인 계정을 찾을 수 없습니다"));

    var 세션id = UUID.randomUUID();
    var 토큰 = 토큰만들기()
        .주인(주인.사용자id())                 // 사람 번호
        .넣기("account_id", 주인.계정id())      // 화면이 보는 값
        .넣기("impersonated", true)
        .넣기("impersonation_id", 세션id)
        .넣기("actor_email", 운영자.이메일())
        .서명();

    기록저장(가게id, 세션id, 운영자, 사유);
    return new 대리접속(토큰, 세션id);
}
```

칸막이 때문에 저장이 막히던 부분입니다. 저장할 때만 범위를 지정합니다.

```java
@Transactional
void 기록저장(UUID 가게id, ...) {
    // 이 트랜잭션 안에서만 이 가게 범위로 본다(세 번째 인자 true = 트랜잭션 한정).
    jdbc.sql("select set_config('app.tenant_id', :가게, true)")
        .param("가게", 가게id.toString()).update();

    jdbc.sql("insert into 대리접속기록 (...) values (...)")...
}
```

요청마다 도는 관문입니다. 돈 쓰는 경로만 막습니다.

```java
private static final List<String> 오너전용_경로 = List.of(
    "/api/v1/console/billing",   // 결제수단·요금제·해지
    "/api/v1/console/credit",    // 크레딧 충전
    "/api/v1/console/addons",    // 부가기능 구매
    "/api/v1/console/legal/accept");

public void 확인(토큰 토큰, String 메서드, String 경로) {
    if (!토큰.대리접속인가()) return;
    if (!세션이_살아있는가(토큰)) 거절(401, "대리 접속이 종료되었습니다");

    boolean 읽기 = 메서드.equals("GET") || 메서드.equals("HEAD");
    if (!읽기 && 오너전용_경로.stream().anyMatch(경로::startsWith)) {
        거절(403, "대리 접속 중에는 결제·요금제를 변경할 수 없습니다");
    }
}
```

## 💡 배운 것

**403 이 나오면 토큰부터 펼쳐 봅니다.** 401 은 "누군지 모르겠다", 403 은 "누군지는 알겠는데 자격이 없다" 입니다. 이 구분만으로 볼 곳이 갈립니다. 403 이면 발급한 쪽과 검사하는 쪽이 **같은 항목을 보고 있는지**를 맞춰 보면 됩니다.

**토큰의 주인 자리에는 사람을 넣습니다.** 세션 번호처럼 사람이 아닌 값을 넣으면, 그 값을 사용자로 읽는 코드가 전부 어긋납니다. 부가 정보는 별도 항목으로 빼면 됩니다.

**권한을 넓힐 땐 예외를 뿌리지 말고 신원을 맞춥니다.** "여기만 통과" 를 화면마다 추가하면, 새 화면을 만들 때마다 그걸 기억해야 합니다. 기억에 의존하는 규칙은 결국 빠집니다.

**대신 위험한 자리는 반드시 좁힙니다.** 넓게 열었으면 어딘가는 닫아야 합니다. 여기선 "읽기는 다 되고 돈 쓰는 것만 막는다" 가 기준이었습니다.

**칸막이가 걸린 표는 쓰는 쪽도 범위가 필요합니다.** 읽을 때만 신경 쓰다가 저장에서 걸렸습니다. 칸막이를 끄는 선택지는 없으니, 필요한 순간에만 범위를 열고 트랜잭션이 끝나면 닫히게 하는 게 안전합니다.

## 소감

기능이 "있는데 안 되는" 상태였습니다. 코드가 아예 없는 것보다 이런 쪽이 더 헷갈립니다. 만들어 둔 사람은 발급까지만 확인하고, 실제로 들어가 보지는 않았던 것 같습니다.

붙여 놓고 나서 실제로 남의 가게에 들어가 화면을 눌러 봤습니다. 사유를 12자 이상 적어야 하고, 들어가 있는 동안에는 화면 아래에 접속 중이라는 표시와 종료 버튼이 보입니다. 누가 언제 왜 들어갔는지는 우리 운영 기록에 남습니다.

남의 데이터를 보는 기능이라, 만들면서 "여기까지만" 을 정하는 데 시간을 더 썼습니다. 만들기보다 **어디를 막을지 정하는 게 더 오래 걸리는** 기능도 있다는 걸 알았습니다.

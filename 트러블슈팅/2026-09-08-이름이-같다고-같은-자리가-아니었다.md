# 2026-09-08 이름이 같다고 같은 자리가 아니었다

> 태그: #트러블슈팅 #계층데이터 #UI #오해를부르는화면

## 무엇을 / 왜

상품에 카테고리를 붙이는 기능을 만들고, 실제로 상품을 하나 등록해 봤습니다.

그런데 이런 말이 나왔습니다.

> 패션 쪽에 넣었는데 실제 판매 화면에서는 식품에 있어요

패션에 넣었는데 식품에서 나온다니, 저장이 잘못됐거나 필터가 잘못됐거나 둘 중 하나겠다 싶었습니다.

## 어떻게 풀었나

### 어디가 틀렸는지부터 좁혔다

의심할 곳이 세 군데였습니다. 저장할 때, 거를 때, 보여 줄 때.

서버에 직접 물어봤습니다. 카테고리 코드는 계층 구조라, 상위 코드를 주면 그 아래가 전부 걸리게 되어 있습니다.

```
상위 코드로 조회   → 4건
그 아래 코드로 조회 → 1건
다른 상위 코드로   → 3건
```

거르는 건 정확했습니다. 화면도 열어 보니 "N개 상품" 이 제대로 나옵니다.

그러면 남은 건 **저장된 값 자체**입니다. 목록을 받아 코드를 봤더니, 패션 계열이 아니라 전혀 다른 대분류로 시작하는 코드가 붙어 있었습니다.

### 그 코드를 풀어 봤더니

코드가 계층이라 이름을 되짚을 수 있었습니다.

```
붙어 있던 코드 = 음반/DVD > 아티스트 굿즈 > 의류·잡화 굿즈
```

아이돌 굿즈 티셔츠 같은 걸 파는 자리였습니다. 패션의류잡화와는 완전히 다른 가지인데, **이름이 거의 같습니다.**

### 진짜 원인은 화면이었다

카테고리를 고르는 화면이 이렇게 생겼습니다.

```
의류·잡화 굿즈
13-04-004          ← 코드
```

마지막 단계 이름과 코드만 보여 줍니다. 이걸 보고 "이건 패션이 아니다" 라고 알아챌 방법이 없습니다. 코드 앞자리가 다르다는 걸 눈치채려면 분류 체계를 외우고 있어야 하고요.

**잘못 고른 게 아니라 잘못 고를 수밖에 없는 화면이었습니다.**

상위 경로를 함께 보여 주기로 했습니다.

```
의류·잡화 굿즈
음반/DVD > 아티스트 굿즈     ← 추가
13-04-004
```

### 목록에서도 알아챌 수 있어야 한다

여기까지 하고 나니 한 가지가 더 걸렸습니다. **고를 때는 경로가 보이는데 목록에서는 안 보입니다.**

이미 잘못 붙은 상품이 있는데, 목록에 마지막 단계 이름만 뜨면 여전히 패션인 줄 압니다.

그런데 목록에 전체 경로를 다 넣으면 길어집니다. 그래서 **최상위와 마지막 단계만** 쓰기로 했습니다.

```
음반/DVD … 의류·잡화 굿즈
식품 … 다이어트 식품
```

고를 때는 자세히, 목록에서는 짧게. 이 정보가 필요한 화면 네 곳에 같은 표기를 넣었습니다.

### 덤으로 나온 것 두 개

**목록에 코드가 그대로 뜨고 있었습니다.** 관리자 목록은 이름을 조인해서 주면서 판매자가 쓰는 쪽만 코드뿐이었습니다. 판매자 이름을 붙이는 방식이 이미 있어서 그대로 따라 했습니다.

**필터 목록이 12개로 잘려 있었습니다.** 대분류는 16개인데 앞에서 12개만 자르고 있었어요. 잘린 쪽에 하필 이번 문제의 대분류가 있어서, **그 카테고리 상품은 필터로 찾을 방법이 아예 없었습니다.**

## 코드로 보기 (개념 재현)

계층 코드에서 상위 경로를 만드는 부분입니다. 코드 자체가 계층이라 별도 관계 테이블 없이 문자열로 조상을 찾을 수 있습니다.

```sql
-- 코드 체계: '13' > '13-04' > '13-04-004'
-- 각 코드의 상위 이름들을 " > " 로 이어 붙인다.
SELECT c.code,
       string_agg(p.name, ' > ' ORDER BY p.depth) AS ancestor_path
  FROM category c
  JOIN category p
    -- ★ 경계를 '-' 로 본다. 이게 없으면 '01' 이 '010...' 까지 조상으로 잡힌다.
    ON c.code LIKE p.code || '-%'
   AND p.depth < c.depth
 WHERE c.code IN (:codes)
 GROUP BY c.code;
```

목록용 짧은 라벨은 최상위와 마지막 단계만 씁니다. 중간을 다 붙이면 목록에서 넘칩니다.

```sql
SELECT c.code,
       CASE
         -- 자기 자신이 최상위면 이름 하나로 충분하다.
         WHEN r.name IS NULL OR r.code = c.code THEN c.name
         ELSE r.name || ' … ' || c.name
       END AS label
  FROM category c
  -- 최상위 코드 = 코드 앞 2자리 (체계상 1차는 2자리)
  LEFT JOIN category r ON r.code = LEFT(c.code, 2)
 WHERE c.code IN (:codes);
```

화면에서는 목록을 자를 때 무엇이 잘리는지 한 번 세어 봐야 합니다.

```js
// 문제가 됐던 코드
options: categories.slice(0, 12).map(toOption)
// → 대분류가 16개라 뒤 4개가 사라진다. 화면상 아무 문제 없어 보인다.

// 고친 뒤
options: categories.map(toOption)
```

## 💡 배운 것

**"사용자가 잘못 골랐다" 는 결론이 나오면 대개 화면이 잘못된 것입니다.** 처음엔 저장이나 필터를 의심했는데 둘 다 멀쩡했습니다. 남은 건 "왜 저걸 골랐지" 인데, 화면을 보니 그렇게 고를 수밖에 없었습니다. 사람을 탓하기 전에 그 사람이 본 화면을 봐야 했습니다.

**이름이 같아도 자리가 다르면 다른 것입니다.** 계층 데이터를 마지막 단계 이름만으로 보여 주면 이런 일이 반드시 생깁니다. **어디에 속하는지가 이름만큼 중요한 정보**인데 그걸 빼고 보여 주고 있었습니다.

**한 곳을 고치면 같은 정보가 필요한 자리를 다 찾아봐야 합니다.** 고르는 화면을 고쳤더니 목록에서는 여전히 안 보였습니다. 따라가 보니 네 군데가 나왔어요. 하나만 고치고 끝냈으면 반쪽이었습니다.

**목록이 잘려 있는 건 눈에 안 띕니다.** 앞에서 N개만 자르는 코드는 화면상 아무 문제 없어 보입니다. N+1번째가 있다는 걸 모르니까요. 자르는 코드를 쓸 때는 "잘리는 게 뭔지" 를 한 번은 세어 봐야겠습니다.

## 소감

버그를 찾는 과정에서 "내가 짠 게 틀렸겠지" 로 시작했다가, 확인해 보니 코드는 다 맞고 **화면이 사람을 오해하게 만들고 있었다**는 결론에 닿은 게 인상적이었습니다.

기능이 되는지만 보고 "완성" 이라고 생각했는데, 그걸 쓰는 사람이 올바른 선택을 할 수 있는 화면인지는 따로 봐야 하는 문제였습니다. 데이터가 계층 구조일 때 특히 그렇다는 걸 배웠습니다.

# 2026-09-29 이력 화면은 있었는데, 쓰는 코드가 없었다

> 태그: #트러블슈팅 #테스트 #이벤트 #트랜잭션

## 무엇을 / 왜

판매자가 자기 상품의 변경 이력(등록·가격·재고·판매 시작/중지)을 보는 화면을 전날 만들었습니다. 이력은 이미 있던 감사 기록 표에서 읽어 오고, 테스트도 통과했어요.

다음 날 실제로 상품 가격을 바꿔 봤더니, 이력 화면에 **한 줄도 안 쌓였다**는 피드백을 받았습니다.

## 어떻게 풀었나

### 읽는 쪽은 멀쩡했다

이력 조회 코드는 문제가 없었습니다. 표에 기록이 있으면 잘 보여 줬어요. 문제는 **그 표에 상품 기록을 쓰는 코드가 어디에도 없었다**는 것이었습니다.

상품 도메인에는 "생성됨·가격 바뀜·재고 바뀜" 같은 이벤트 클래스가 정의돼 있었고, 감사 기록 쪽에는 그 이벤트를 받아 표에 쓰는 리스너도 있었어요. 그런데 정작 **이벤트를 발행하는 곳이 한 군데도 없었습니다.** 받을 준비만 하고 아무도 보내지 않던 거예요.

### 테스트는 왜 통과했나

제 테스트는 이랬습니다.

```java
// 전날 테스트: 이력을 표에 직접 넣고, 화면(조회)만 확인
insertAudit(goodsId, "price.change", "{\"price\":30000}", "{\"price\":25000}");
assertThat(history(goodsId)).extracting(Row::action).containsExactly("price.change");
```

입력을 제가 대신 넣어 줬으니, 정말 필요한 "상품을 고치면 기록이 남는가" 는 한 번도 확인하지 않은 셈이었습니다.

### 이벤트를 켜면 될까

처음엔 이벤트 발행만 붙이면 끝날 줄 알았는데, 같은 이벤트를 받는 구독자가 하나 더 있었어요. **사용량 계량 리스너**가 "상품 생성" 이벤트를 받아 월간 사용량으로 세고 있었고, 옛 요금제 표에는 이 사용량에 월 100개 같은 한도가 걸려 있었습니다. 이벤트를 켜는 순간 잠들어 있던 한도가 살아나 엑셀 대량 등록이 막힐 수 있었어요.

그래서 이벤트 대신, 상품 저장 코드에서 **같은 트랜잭션 안에 이력을 직접 쓰는** 작은 기록기를 만들었습니다. 저장이 되돌려지면 이력도 같이 사라져서, 없는 변경이 이력에 남지 않아요.

### "보냈다" 와 "바뀌었다" 는 다르다

수정 폼은 저장할 때마다 옵션·이미지·설명을 **전부 다시 보냅니다.** 보냈다는 이유로 기록하면 가격만 바꿔도 "옵션 수정" 이 매번 찍혀요. 그래서 저장하기 전에 지금 값과 비교해 실제로 달라진 것만 적었습니다.

## 코드로 보기 (개념 재현)

```java
@Transactional
public Goods update(GoodsId id, UUID seller, UpdateCommand command) {
    Goods before = requireOwned(id, seller);
    // 부속은 바꾸기 전에 비교해 둔다. 바꾼 뒤에는 무엇이 달라졌는지 알 수 없다.
    List<String> changedParts = changedParts(before.id(), command);
    Goods after = repository.update(apply(before, command));
    replaceComponents(after.id(), command);
    history.updated(before, after, changedParts);      // 같은 트랜잭션에서 기록
    return after;
}

public void updated(Goods before, Goods after, List<String> changedParts) {
    if (before.price().compareTo(after.price()) != 0) {
        write(after.id(), "price.change", Map.of("price", before.price()), Map.of("price", after.price()));
    }
    if (before.stock() != after.stock()) {
        write(after.id(), "stock.change", Map.of("stock", before.stock()), Map.of("stock", after.stock()));
    }
    // 이름·설명 등은 바뀐 칸만 모아 한 줄로. 아무것도 안 바뀌었으면 쓰지 않는다.
}
```

테스트도 입력을 대신 넣지 않고, **실제 API로 등록·수정한 뒤** 이력을 읽게 바꿨습니다.

```java
@Test
void 고치면_이력이_남고_같은_값으로_다시_저장하면_남지_않는다() throws Exception {
    String id = create("{\"name\":\"가을 셔츠\",\"price\":30000,\"stockCount\":10}");
    update(id, "{\"name\":\"가을 셔츠\",\"price\":25000,\"stockCount\":8}");
    assertThat(actions(id)).containsExactlyInAnyOrder("create", "price.change", "stock.change");

    update(id, "{\"name\":\"가을 셔츠\",\"price\":25000,\"stockCount\":8}");   // 같은 값
    assertThat(actions(id)).hasSize(3);
}
```

## 💡 배운 것

**테스트가 입력을 대신 넣으면, 그 입력을 만드는 코드는 검증되지 않습니다.** 조회 기능 테스트였어도 "누가 이 데이터를 쓰는가" 까지 한 번은 끝에서 끝으로 확인해야 했어요.

**이벤트를 켜기 전에 구독자를 전부 봅니다.** 이벤트는 한 곳에서 보내지만 받는 쪽은 여러 곳일 수 있습니다. 이번엔 받는 쪽 하나가 잠든 한도를 깨울 뻔했어요.

**"보냈다" 는 "바뀌었다" 가 아닙니다.** 폼이 매번 전부 보내는 구조라면, 기록은 값을 비교한 뒤에 남겨야 이력이 의미를 가집니다.

## 소감

화면이 있고 테스트가 초록색이라 끝난 줄 알았던 기능이 실제로는 한 번도 동작한 적이 없었습니다. 이후로는 새 기능 테스트를 쓸 때 "이 데이터는 원래 어디서 오나" 를 먼저 적어 보고, 그 경로를 테스트에 포함하는지 확인하기로 했습니다.

# 2026-09-11 시작 명령을 감쌌더니 설정 파일이 만들어지지 않았다

> 태그: #트러블슈팅 #Docker #nginx #HTTPS #엔트리포인트

## 무엇을 / 왜

서버를 매장 서버 PC 로 옮기고 도메인에 무료 인증서를 붙이는 날이었습니다. 서버를 올리고 인증서 발급 스크립트를 돌렸는데 실패했습니다.

스크립트는 실패하면 흔한 원인 세 가지를 보여 줍니다.

- 도메인이 이 서버 주소를 가리키는가
- 공유기 포트포워딩이 되어 있는가
- 방화벽이 80 포트를 열었는가

**셋 다 바로 전에 확인한 것**이었습니다.

## 어떻게 풀었나

### 첫 가설은 빗나갔다

밖에서 80 포트로 들어가 보니, 우리 설정대로라면 https 로 넘겨야 하는데 **"Welcome to nginx" 기본 화면**이 나왔습니다.

처음엔 앞서 포트 시험용으로 띄워 둔 nginx 가 남아 포트를 잡고 있다고 봤습니다. 끄고 다시 올렸는데 **같았습니다.** 컨테이너 목록을 보니 80·443 을 잡고 있는 건 우리 nginx 하나뿐이었습니다.

### 증상이 나오는 자리를 직접 열었다

컨테이너 안으로 들어가 설정 폴더를 봤습니다.

- 설정 **틀** 파일(`*.template`) - 있음
- 임시 인증서 - 있음
- 틀에서 만들어져야 할 **실제 설정 파일** - **없음**

실제 설정이 없으니 nginx 는 이미지에 들어 있던 기본 설정으로 떴고, 그래서 "Welcome to nginx" 가 나온 것이었습니다.

### 원인: 이미지의 준비 단계를 건너뛰고 있었다

공식 nginx 이미지는 시작할 때 엔트리포인트 스크립트가 먼저 돕니다. 이 스크립트가 틀 파일의 환경변수를 채워 실제 설정으로 바꿔 줍니다.

그런데 **첫 인자가 `nginx` 일 때만** 그 준비 단계를 돌립니다.

저희 구성은 12시간마다 인증서를 다시 읽으려고 시작 명령을 `sh -c "..."` 로 감싸 두었습니다. 첫 인자가 `sh` 가 되니 엔트리포인트는 준비 단계를 건너뛰고 명령만 실행했습니다.

개발 PC 에는 HTTPS 구성을 올린 적이 없어서 **여기서 처음 드러난** 결함이었습니다.

### 매장에 넣기 전에 로컬에서 먼저 재현했다

인증서 발급처는 실패가 쌓이면 한동안 발급을 막습니다. 매장 서버에서 고치고 다시 시도하는 식으로는 한도를 날릴 수 있었습니다.

그래서 **개발 PC 에서 다른 포트로 같은 구성을 띄워** 확인했습니다.

- 80 → https 넘김(301)
- 인증 확인 경로 응답
- 443 연결

확인한 뒤 매장 서버에는 파일 하나만 고쳐 넣었고, 연습용 인증서부터 받아 본 다음 정식 인증서를 받았습니다.

### 올리기 전 점검에서 하나 더 나왔다

인증서가 담기는 볼륨 이름을 따로 정하지 않았더니, 도커가 **서버 PC 의 폴더 이름을 앞에 붙여** 볼륨을 만들고 있었습니다. 인증서 스크립트는 고정된 이름으로 볼륨을 찾기 때문에, 폴더 이름이 다르면 nginx 가 읽지 않는 볼륨에 인증서가 깔립니다. 이름을 못 박았습니다.

## 코드로 보기 (개념 재현)

공식 이미지 엔트리포인트의 동작을 줄이면 이렇습니다.

```sh
#!/bin/sh
# docker-entrypoint.sh (요지)
if [ "$1" = "nginx" ] || [ "$1" = "nginx-debug" ]; then
  # 여기서 /docker-entrypoint.d/*.sh 를 차례로 돌린다.
  # 그중 하나가 /etc/nginx/templates/*.template 을 conf.d 로 바꾼다.
  run_init_scripts
fi
exec "$@"
```

문제가 됐던 구성입니다.

```yaml
services:
  proxy:
    image: nginx:stable
    volumes:
      - ./templates:/etc/nginx/templates   # 틀 파일
      - cert:/etc/letsencrypt
    # 12시간마다 인증서를 다시 읽으려고 sh 로 감쌌다.
    # ★ 첫 인자가 "sh" 라서 엔트리포인트가 준비 단계를 건너뛴다.
    command: >
      sh -c "while :; do sleep 12h; nginx -s reload; done &
             nginx -g 'daemon off;'"

volumes:
  cert:        # ★ 이름을 안 주면 "<폴더이름>_cert" 로 만들어진다
```

고친 구성입니다.

```yaml
services:
  proxy:
    image: nginx:stable
    volumes:
      - ./templates:/etc/nginx/templates
      - cert:/etc/letsencrypt
    # 다시 읽기는 뒤에서 돌리고,
    # nginx 는 반드시 이미지의 엔트리포인트를 거쳐 띄운다.
    command: >
      sh -c "(while :; do sleep 12h; nginx -s reload 2>/dev/null || true; done) &
             exec /docker-entrypoint.sh nginx -g 'daemon off;'"

volumes:
  cert:
    name: cert   # 폴더 이름과 상관없이 늘 같은 이름
```

컨테이너 안에서 확인한 방법입니다.

```sh
# 틀은 있는데 실제 설정이 없는지
docker exec proxy ls /etc/nginx/templates /etc/nginx/conf.d

# 지금 nginx 가 실제로 읽고 있는 설정 전체
docker exec proxy nginx -T | head -40
```

## 💡 배운 것

**이미지의 시작 명령을 바꾸면 이미지가 해 주던 준비를 잃을 수 있습니다.** 공식 이미지는 엔트리포인트에서 조건을 보고 준비 단계를 돌립니다. 명령을 감싸거나 바꾸기 전에, 원래 엔트리포인트가 무엇을 하는지부터 봐야 했습니다.

**스크립트가 보여 주는 "흔한 원인" 은 원인이 아니라 후보입니다.** 셋 다 확인한 뒤에도 실패했다면 원인은 목록 밖에 있습니다. 거기서 목록을 다시 확인하기보다 증상이 나오는 자리(컨테이너 안)를 여는 게 빨랐습니다.

**외부 서비스에 한도가 있으면 재현은 로컬에서 먼저 합니다.** 같은 구성을 다른 포트로 띄워 확인하고, 연습용 인증서로 한 번 더 확인한 뒤에 정식 발급을 시도했습니다.

**개발 환경에서 안 쓰던 구성은 배포에서 처음 검증됩니다.** HTTPS 구성은 매장 서버에서 처음 돌았습니다. 배포 전에 운영과 같은 구성을 한 번이라도 띄워 봤으면 여기서 헤매지 않았을 겁니다.

## 소감

"인증서 발급 실패" 라는 메시지만 보면 인증서나 네트워크를 의심하게 되는데, 실제 원인은 **nginx 시작 명령 한 줄**이었습니다.

첫 가설(남은 nginx)이 빗나갔을 때 같은 방향으로 계속 파지 않고 컨테이너 안을 열어 본 게 전환점이었습니다. 원격으로만 닿는 매장 PC 에서 시행착오를 줄이려면, 로컬에서 먼저 재현하는 습관이 필요하다는 것도 알았습니다.

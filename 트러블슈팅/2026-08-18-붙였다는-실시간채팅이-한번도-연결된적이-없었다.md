# 2026-08-18 붙였다는 실시간 채팅이, 한 번도 연결된 적이 없었다 - 웹소켓 주소가 앞단에서 404였다

> 태그: #트러블슈팅 #웹소켓 #리버스프록시 #멀티테넌트

## 무엇을 / 왜

전날 라이브 방송에 실시간 채팅을 붙였습니다. 서버에는 웹소켓 처리기가 등록돼 있었고, 받은 메시지를 저장한 뒤 그 방송을 보는 모든 사람에게 뿌리는 코드까지 있었어요. 화면 쪽에서 연결하는 코드만 없길래 그걸 붙이고 "완성"이라고 적었습니다.

다음 날 같은 방송 화면에 **시청자 수**를 붙이면서 실제로 연결해 봤습니다. 숫자가 계속 `…` 이었어요. 채팅도 다시 열어봤는데 마찬가지였습니다. 서버 코드도 화면 코드도 몇 번을 봐도 맞는데 **아무 반응이 없었습니다.**

즉, 전날 완성이라고 적은 기능은 **한 번도 연결된 적이 없었던 것**입니다.

## 어떻게 풀었나

### 서버는 멀쩡했다

먼저 서버만 따로 확인했습니다. 서버를 띄우고 웹소켓으로 직접 붙어 보니 정상적으로 응답이 왔습니다. 즉 처리기도, 저장도, 뿌리는 것도 다 살아 있었어요. 문제는 **브라우저에서 그 주소까지 가는 길**이었습니다.

### 요청이 지나가는 길을 따라갔다

우리 구성은 이렇습니다.

```
브라우저 → 웹서버(HTTPS 처리) → 앞단(화면 서버) → 뒷단(API 서버)
```

웹서버는 **모든 요청을 앞단으로** 넘깁니다. 그리고 앞단은 `/api` 로 시작하는 요청만 뒷단으로 넘기도록 설정돼 있었어요.

그런데 웹소켓 주소는 `/ws/...` 입니다. **앞단 입장에서는 그런 페이지가 없습니다.** 그래서 404로 끝나고 있었습니다. 브라우저에서는 "연결이 열리자마자 닫힘"으로만 보이니 원인을 짐작하기 어려웠어요.

게다가 손님 상점 주소로 들어오면 그 전에 한 번 더 막혔습니다. 상점 주소에서는 상점과 무관한 경로(관리 화면 등)를 아예 없는 것으로 처리하려고 **허용 목록**을 두는데, 거기에 `/ws` 가 없었거든요.

문제가 **두 겹**이었던 셈입니다. 하나만 고쳤으면 여전히 안 됐을 겁니다.

### "그냥 뒷단 주소로 붙이면 되지 않나"

처음엔 그렇게 하려고 했습니다. 화면 코드에서 뒷단 주소(`API_BASE_URL`)를 가져다 웹소켓을 열면 앞단을 안 거치니까요. 실제로 그렇게 짜여 있기도 했고요.

그런데 그러면 안 되는 이유가 있었습니다. **우리는 "어느 상점인지"를 주소(호스트)로 판단합니다.** 손님이 `가게1.example.com` 으로 들어오면 그 호스트로 상점을 찾는 구조예요. 뒷단 주소로 직접 붙으면 호스트가 뒷단이 되어 **상점을 못 찾습니다.**

일반 요청(`/api`)이 잘 되던 이유도 같은 데 있었습니다. 앞단이 대신 넘겨주면서 원래 호스트를 헤더에 실어 주고 있었거든요. 웹소켓만 그 길을 못 타고 있었던 겁니다.

### 두 곳을 뚫었다

**운영에서는 웹서버가 `/ws` 만 뒷단으로 바로 넘기게** 했습니다. 웹서버는 연결 승격(업그레이드) 요청을 그대로 통과시키고 원래 호스트도 유지해 주니, 상점 판별이 그대로 됩니다.

```
가게 주소 {
    handle /ws/* {        # 실시간 통신만 뒷단으로 직접
        뒷단으로 넘김
    }
    handle {              # 나머지는 전부 화면 서버로
        앞단으로 넘김
    }
}
```

**로컬 개발에서는 웹서버가 없으니** 앞단이 `/ws` 도 넘겨주도록 열고, 허용 목록에도 추가했습니다. 앞단 프록시가 원래 호스트를 헤더에 실어 주기 때문에 상점 판별은 똑같이 됩니다.

그리고 화면 코드는 **항상 지금 보고 있는 주소로만** 붙게 바꿨습니다. 뒷단 주소를 직접 쓰는 코드를 없앤 거예요. 로컬에서만 되고 운영에서 조용히 안 붙는 종류의 코드였습니다.

### 손님이 보는 화면이 따로 있었다

여기서 더 당황스러운 걸 발견했습니다. 전날 채팅을 붙인 화면은 `/live/{id}` 였는데, **상점 주소에서는 그 경로가 404** 였습니다. 손님이 실제로 들어오는 곳은 `/shopos/live/{id}` 라는 다른 화면이었어요.

즉 저는 **손님이 올 수 없는 화면에 채팅을 붙여 놓고** 완성이라고 적은 것이었습니다. 진짜 손님 화면의 채팅은 여전히 옛날 방식(들어올 때 한 번 읽고, 보낼 때 한 번 보내는)이었고, 그래서 방송하는 쪽에는 손님 말이 실시간으로 가지 않고 있었습니다.

### 곁다리로 겪은 것

로컬에서 뒷단을 끄고 웹소켓에 붙어 봤더니 **앞단 개발 서버가 통째로 죽었습니다.** 연결이 거부되면서 난 오류를 아무도 처리하지 않아 프로세스가 내려간 거예요. 운영에서 웹서버가 `/ws` 를 직접 받게 해 둔 게 결과적으로 더 안전한 선택이 됐습니다. 화면 서버가 실시간 통신 때문에 죽으면 사이트 전체가 내려가니까요.

## 코드로 보기 (개념 재현 테스트)

이런 문제는 "화면 코드가 맞는지"를 아무리 봐도 안 잡힙니다. **실제로 연결해 보는 것** 말고는 방법이 없더군요. 그래서 검증도 실제 웹소켓 연결로 짰습니다.

```java
@Test
void 한사람이_보낸_말이_보고있는_다른사람에게_간다() {
    var 방송 = 라이브방송만들기();

    // 프록시가 붙여주는 헤더를 흉내낸다. 이게 없으면 어느 상점인지 못 찾는다.
    var 헤더 = new 헤더();
    헤더.add("X-Forwarded-Host", "가게1.test.local");

    var 말하는사람 = 붙기(방송, 헤더, "token=" + 발급한토큰);
    var 보기만하는사람 = 붙기(방송, 헤더, "");        // 비회원

    말하는사람.보내기("이 상품 재고 있나요?");

    assertThat(보기만하는사람.다음프레임().get("message").asText())
        .isEqualTo("이 상품 재고 있나요?");
}
```

`X-Forwarded-Host` 를 넣은 줄이 이 문제의 핵심을 그대로 담고 있습니다. 실시간 통신도 **일반 요청과 똑같이 "어느 상점인지"가 실려야** 동작한다는 것.

그리고 이 검증은 되돌리면 실제로 깨집니다. 뿌리는 신호를 끊으면 두 건이, 비회원 연결을 막으면 두 건이 깨지는 걸 확인하고 복구했습니다.

## 💡 배운 것

- **화면 코드가 맞는 것과 브라우저가 그 주소에 닿는 것은 다른 문제다.** 코드 리뷰로는 절대 안 잡힙니다. 한 번은 실제로 연결해 봐야 합니다.
- **실시간 통신은 일반 요청과 다른 취급을 받는다.** 프록시 설정, 접근 허용 목록, 연결 승격 처리까지 별도로 챙겨야 합니다. `/api` 가 잘 된다고 `/ws` 도 될 거라고 볼 수 없었습니다.
- **주소로 대상을 판별하는 구조에서는 "어디로 붙느냐"가 곧 데이터다.** 편하다고 뒷단에 바로 붙으면 그 정보가 날아갑니다.
- **내가 만든 화면에 손님이 실제로 오는지 확인하자.** 같은 기능의 화면이 두 개 있었고, 저는 손님이 못 오는 쪽에 붙이고 있었습니다.
- **연결이 실패했을 때 화면이 영원히 "연결 중"으로 남지 않게 하자.** 실패를 표시로 구분해서, 못 붙으면 아예 접거나 다른 값을 보여주게 했습니다.

## 소감

전날 "완성"이라고 적은 게 실은 한 번도 동작한 적이 없었다는 게 제일 뼈아팠습니다. 코드가 다 맞아 보였기 때문에 더 그랬어요. 실제로는 마지막 한 칸, 브라우저에서 서버까지 가는 길이 뚫려 있지 않았을 뿐인데 말이죠.

그래서 요즘은 기능을 붙일 때 순서를 하나 더 넣었습니다. 만들고 → 검증하고 → **입구와 경로가 실제로 뚫려 있는지 눌러보기.** 특히 새로운 종류의 통신(실시간, 파일 업로드, 외부 콜백처럼)을 처음 붙일 때는 반드시요.

같은 날 하루에만 "코드는 있는데 부르는 곳이 없다"를 여러 번 만났는데, 이번 건은 조금 달랐습니다. 부르는 곳도 있었어요. **부르는 곳에서 서버까지 가는 길이 없었을 뿐입니다.** 이런 종류가 있다는 걸 이제 알았습니다.

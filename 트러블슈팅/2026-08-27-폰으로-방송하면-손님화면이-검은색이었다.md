# 2026-08-27 폰으로 방송하면 손님 화면이 검은색이었다

> 태그: WebRTC, TURN, 모바일 NAT, 진단
> 브라우저로 방송을 붙이는 것 자체는 [어제 글](../새기술/2026-08-26-OBS-없이-브라우저로-방송-WHIP-WebRTC.md)에서 다뤘다. 이 글은 그 방송을 "폰으로" 켰을 때만 생긴 문제를 잡은 기록이다.

## 무엇을 / 왜

브라우저에서 카메라로 바로 방송하는 기능을 붙여 뒀다. PC에서는 잘 됐다. 그런데 폰으로 방송을 켜면 영상 서비스 대시보드에는 "연결됨"으로 뜨는데, 정작 시청 화면은 검은색이었다.

"연결됨"이라니 연결은 된 것 같은데 영상만 안 나왔다. 로그를 봐도 에러가 없었다. 눈에 보이는 정보가 "연결됨" 하나뿐이라 어디가 막혔는지 감이 안 잡혔다.

## 어떻게 풀었나

### 1. 모바일은 망 뒤에 숨어 있다 (NAT)

집이나 사무실 PC는 대체로 영상 서버와 비교적 직접 연결이 된다. 반면 휴대폰은 통신사 망(NAT) 뒤에 있어서, 두 지점이 서로 직접 UDP로 뚫리지 않는 경우가 많다. 이럴 때 쓰라고 있는 게 **TURN(중계 서버)**이다. 직접 못 가면 중계 서버를 한 번 거쳐서 보내는 것이다.

그래서 방송을 시작할 때 서버에서 STUN + TURN 주소(ICE 서버)를 받아 연결에 넣어 줬다. 그런데도 여전히 검은 화면이었다.

### 2. 안 보이니까, 화면에 꺼내 놓았다

로그로는 아무것도 안 보여서, **방송 화면에 진단값을 실시간으로 띄웠다.** 연결이 어느 단계인지, 지금 어떤 경로(직접/중계)로 붙었는지, 실제로 몇 바이트나 내보내고 있는지.

띄우고 나서 바로 보였다. 폰은 중계(relay) 후보를 만들어 두고도 **직접 경로로 붙은 채**, 영상을 잠깐 흘리다 멈추고 있었다. "연결됨"은 신호(handshake)만 됐다는 뜻이었고, 실제 영상은 통신사 망에서 막혀 흘러가지 못한 것이다.

### 3. 모바일이면 중계로만 가게 강제

후보를 넣어 줘도 브라우저가 알아서 직접 경로를 골라 버리니, 모바일일 때는 **아예 중계 경로로만 보내게 강제**했다(`iceTransportPolicy: "relay"`). PC는 직접 경로가 잘 되니 그대로 뒀다.

그랬더니 전송 바이트가 멈추지 않고 쭉 올라갔다. 20MB, 40MB... 처음으로 영상이 실제로 나가는 게 숫자로 보였다.

### 4. 이번엔 받는 쪽 (도착하는데 안 그려짐)

송출을 고치니 시청 화면이 이번엔 썸네일에 멈췄다. 화면을 누르면 재생/정지는 반응하는데 그림만 안 바뀌었다. 진단에 "받는 바이트"를 한 줄 더 추가해 보니, **받는 쪽에서도 20MB씩 정상으로 들어오고** 있었다. 영상은 다 도착하는데 화면에만 안 그려지는 거였다.

원인은 받은 영상 신호를 비디오 요소에 제대로 물려주지 못한 것이었다. 수신 이벤트가 주는 스트림을 그대로 믿지 말고, **받은 트랙을 직접 하나의 스트림에 담아** 비디오에 물려주니 곧바로 영상이 떴다.

## 코드로 보기 (개념 재현)

실제 구조를 단순화한 개념 코드다.

```js
// [송출] 모바일이면 미디어를 무조건 중계(TURN)로만 보낸다.
const isMobile = /Mobi|Android|iPhone|iPad/i.test(navigator.userAgent);
const pc = new RTCPeerConnection({
  iceServers,                                   // STUN + TURN
  // 직접/STUN 경로가 "붙은 척"하고 영상은 블랙홀되는 걸 막는다.
  iceTransportPolicy: isMobile && hasTurn(iceServers) ? "relay" : "all",
});

// [진단] 안 보이는 상태를 화면으로 꺼낸다. 1.5초마다 갱신.
setInterval(async () => {
  const stats = await pc.getStats();
  let path, sent = 0;
  stats.forEach((r) => {
    if (r.type === "outbound-rtp" && r.kind === "video") sent = r.bytesSent;
    // 선택된 후보쌍 -> 로컬 후보 타입(host/srflx/relay)을 찾아 path 에 담는다(생략).
  });
  showOnScreen({ state: pc.iceConnectionState, path, sent });
  // 화면에 뜬 값: state=connected, path=relay, sent=20MB -> 이제서야 정상.
}, 1500);
```

```js
// [시청] 받은 트랙을 직접 스트림에 담아 비디오에 물린다.
// event.streams[0] 에만 의존하면 영상 트랙이 안 담겨 poster(썸네일)에 멈추는 경우가 있다.
const inbound = new MediaStream();
pc.ontrack = (event) => {
  inbound.addTrack(event.track);          // 영상/소리 트랙을 하나씩 모은다
  if (video.srcObject !== inbound) video.srcObject = inbound;
  video.muted = true;                     // 음소거여야 자동재생이 허용된다
  video.play().catch(() => {});           // 트랙이 붙는 이 시점에 직접 재생
};
```

## 💡 배운 것

- **"연결됨"이 "영상이 흐름"은 아니다.** 신호(handshake)가 됐다는 것과 실제 미디어(RTP)가 흐른다는 건 다른 단계다. 상태 한 줄만 보고 판단하다 계속 헛다리를 짚었다.
- **모바일은 NAT 뒤라 TURN 중계가 필요할 때가 많다.** 그리고 후보만 넣어 주는 걸로는 부족하고, 필요하면 `iceTransportPolicy: "relay"`로 경로를 강제해야 확실하다.
- **`getStats()`는 "지금 실제로 무슨 일이 일어나는지"를 알려 준다.** 선택된 경로 타입, 보낸/받은 바이트, 디코드된 프레임 수까지. 로그가 침묵할 때 이게 유일한 진실이었다.
- **받는 쪽에서는 트랙을 직접 스트림에 담는 게 안전하다.** 수신 이벤트가 주는 스트림에만 의존하면 영상이 안 담겨 화면이 안 그려질 수 있다.

## 소감

한참을 "장님으로" 고쳤다. 안 보이는 걸 두고 이 가설 저 가설로 배포만 반복하다가, 화면에 진단값 몇 개를 꺼내 놓고 나서야 원인이 한 번에 보였다. 고치는 것보다 **보이게 만드는 게 먼저**였다. 그리고 문제는 한 겹이 아니었다 - 송출을 뚫으니 이번엔 받는 쪽 표시가 막혔다. 같은 진단을 반대편에도 한 줄 더 놓으니, "도착은 하는데 안 그려진다"는 게 바로 갈렸다. 앞으로도 안 보이는 걸 만나면, 추측보다 먼저 그 상태를 화면으로 꺼내 놓기로 했다.

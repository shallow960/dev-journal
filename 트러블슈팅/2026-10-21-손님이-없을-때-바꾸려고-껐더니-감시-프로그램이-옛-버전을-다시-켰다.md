# 2026-10-21 손님이 없을 때 바꾸려고 껐더니, 감시 프로그램이 옛 버전을 다시 켰다

> 태그: #트러블슈팅 #원격업데이트 #프로세스감시 #키오스크 #순서

## 무엇을 / 왜

매장 키오스크 앱은 원격으로 새 버전을 받아 바꾸는 구조입니다. 설계는 이랬어요.

1. 새 버전을 미리 내려받아 둔다.
2. 손님이 없을 때 앱이 스스로 꺼진다.
3. 옆에서 도는 관리 프로그램(에이전트)이 그 틈에 파일을 바꾸고 새 버전을 켠다.

내려받기, 파일 검증, 백업과 되돌리기까지 부품은 다 있었습니다. 그런데 코드를 처음부터 끝까지 따라가 보니 3번이 일어나지 않았어요.

- 에이전트에는 앱이 죽으면 다시 켜 주는 **감시 기능**이 있습니다. 10초마다 "앱이 꺼졌나" 를 보고, 꺼져 있으면 설치 폴더의 실행 파일을 바로 다시 켜요.
- 감시는 **기다리는 업데이트를 보지 않았습니다.** 교체 함수는 따로 있었지만, 감시 경로에서는 부르지 않았어요.
- 그래서 앱이 교체를 위해 꺼지면, 10초 안에 감시가 **옛 버전을 다시 켰습니다.**

실제로 확실하게 바뀌는 방법은 관리자가 보내는 강제 재시작 명령 하나였어요. 이 명령은 손님이 있어도 앱을 끕니다. 원격 업데이트라는 기능이 사실상 없었던 셈이에요.

따라가는 김에 두 가지가 더 보였습니다.

- 결제 실패·출력 실패 안내 화면도 '대기 화면' 으로 잡혀서, 손님 앞에서 앱이 꺼질 수 있었어요.
- 새 버전이 잘 떴는지 확인하기 **전에** "설치됨" 을 기록해서, 실패해 옛 버전으로 돌아가도 기록은 새 버전으로 남았어요. 그 뒤로는 양쪽 모두 "이미 설치됨" 으로 보고 멈춥니다.

## 어떻게 풀었나

1. **감시가 다시 켜기 전에 기다리는 업데이트부터 적용합니다.** 적용 결과에 따라 다음 행동이 갈려요.
   - 업데이트가 없거나 사전 검사에 걸림 → 지금처럼 설치된 버전을 켠다.
   - 적용 성공, 또는 실패해서 되돌림 → 적용 함수가 이미 켰으니 끝.
   - 다른 적용이 진행 중이거나 운영자가 일부러 끈 상태 → 아무것도 하지 않고 다음 확인을 기다린다.
2. **적용 함수는 시작하자마자 잠급니다.** 감시가 10초마다 부르게 되니 두 번 겹칠 위험이 커졌어요. 첫 비동기 대기(await) 전에 잠그고, 어떤 이른 반환에서도 풀리게 했습니다.
3. **"설치됨" 은 확인한 뒤에 기록합니다.** 새 버전이 15초 동안 살아 있는지 본 뒤에만 기록하고, 실패하면 실패를 따로 남겨요. 같은 버전이 두 번 실패하면 더 새 버전이 나올 때까지 건너뜁니다. 기록 순서만 고치고 실패를 기억하지 않으면, 깨진 버전을 대기 때마다 다시 시도하는 고리가 생기거든요.
4. **'대기 화면' 판정을 좁혔습니다.** 흐름의 첫 화면이고, 몇 분 동안 입력이 없을 때만 교체합니다. 끄기 바로 직전에 한 번 더 확인해서, 그사이 손님이 오면 멈추고 다음 기회를 기다려요.

## 코드로 보기 (개념 재현)

1초를 1칸으로 줄인 흉내입니다. 이름은 모두 더미예요.

```js
// 감시는 10칸마다 돈다. 앱은 5칸째에 교체를 위해 스스로 꺼진다.
const state = { running: true, installed: '1.0', pending: '1.1' };
const log = [];

function watchdogTick(t, fixed) {
  if (state.running) return;                 // 앱이 켜져 있으면 할 일 없음
  if (fixed && state.pending) {              // 고친 뒤: 다시 켜기 전에 대기 업데이트부터
    state.installed = state.pending;
    state.pending = null;
    log.push(`${t}s 감시: 대기 업데이트 ${state.installed} 적용`);
  }
  state.running = true;                      // 고치기 전: 설치된(옛) 버전을 바로 켠다
  log.push(`${t}s 감시: 꺼진 앱을 다시 켬 → 실행 버전 ${state.installed}`);
}

function run(fixed) {
  Object.assign(state, { running: true, installed: '1.0', pending: '1.1' });
  log.length = 0;
  for (let t = 0; t <= 30; t++) {
    if (t === 5) { state.running = false; log.push('5s 앱: 손님이 없어서 교체하려고 스스로 종료'); }
    if (t % 10 === 0) watchdogTick(t, fixed);
  }
  console.log(fixed ? '[고친 뒤]' : '[고치기 전]');
  log.forEach((l) => console.log('  ' + l));
  console.log(`  결과: 실행 버전 ${state.installed}, 남은 대기 ${state.pending ?? '없음'}`);
}

run(false);
run(true);
```

실제로 돌린 출력입니다.

```
[고치기 전]
  5s 앱: 손님이 없어서 교체하려고 스스로 종료
  10s 감시: 꺼진 앱을 다시 켬 → 실행 버전 1.0
  결과: 실행 버전 1.0, 남은 대기 1.1
[고친 뒤]
  5s 앱: 손님이 없어서 교체하려고 스스로 종료
  10s 감시: 대기 업데이트 1.1 적용
  10s 감시: 꺼진 앱을 다시 켬 → 실행 버전 1.1
  결과: 실행 버전 1.1, 남은 대기 없음
```

## 💡 배운 것

**"있다" 와 "돈다" 는 다르다는 걸 다시 배웠습니다.** 2026-08-13 에는 코드가 있어도 부르는 곳이 없으면 아무 일도 안 한다는 걸, 2026-10-20 에는 검사가 있어도 켜져 있지 않으면 소용없다는 걸 배웠어요. 이번엔 부품이 다 있어도 **순서가 맞물리지 않으면** 기능이 없는 것과 같았습니다. 이제 "어디서 부르나" 다음에 "누가 먼저 움직이나" 까지 따라갑니다.

**같은 대상을 다루는 두 장치는, 순서를 한쪽이 책임지게 해야 한다는 걸 배웠습니다.** 감시는 "꺼졌으면 켠다", 교체는 "꺼졌을 때 바꾼다" 였어요. 둘 다 맞는 말인데, 누가 먼저인지 정한 곳이 없었습니다. 감시가 교체를 먼저 부르게 해서 순서를 한곳에 모았어요.

**"됐다" 는 확인한 뒤에 기록한다는 걸 배웠습니다.** 기록이 확인보다 앞서면, 실패해도 기록은 성공으로 남고 그 뒤의 판단이 모두 틀어져요.

**자동으로 다시 하는 동작에는 한도를 둔다는 걸 다시 배웠습니다.** 2026-10-19 에 자동 재시작에 횟수를 정해 둔 것과 같은 이유로, 실패한 버전은 두 번까지만 다시 시도합니다.

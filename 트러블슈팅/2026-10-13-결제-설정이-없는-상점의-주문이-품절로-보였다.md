# 2026-10-13 결제 설정이 없는 상점의 주문이, 손님에게는 '품절'로 보였다

> 태그: #트러블슈팅 #HTTP상태코드 #오류코드 #API설계 #Spring #React

## 무엇을 / 왜

상점이 결제(PG) 설정을 아직 하지 않았을 때 손님이 주문하면, 손님 화면에 **"품절됐거나 판매가 중지된 상품이 있어요"** 가 떴습니다. 상품은 멀쩡했어요.

원인은 두 군데에 나뉘어 있었습니다.

1. 서버는 결제 설정이 없으면 **409(Conflict)** 와 함께 운영자용 문구("결제 설정에서 PG를 켜 주세요")를 보냈습니다.
2. 손님 화면은 주문 단계의 409를 **전부 재고 충돌로** 해석하고 있었어요. 재고가 모자랄 때도 409였거든요.

상태 코드 하나에 여러 이유가 실려 있었고, 화면은 그중 하나로만 읽고 있었던 겁니다.

## 어떻게 풀었나

- **이유 코드를 싣는 예외를 만들었습니다.** 기존 상태 코드 예외를 상속해서, 그 예외를 잡던 곳은 그대로 동작합니다.
- **공통 오류 처리기가 그 코드를 응답에 그대로** 내려 줍니다. 코드가 없는 예외는 예전처럼 일반 코드를 줍니다.
- 결제 설정이 없을 때는 `PAYMENT_NOT_READY`와 **손님이 읽을 문구**("이 상점은 아직 결제를 받을 준비가 되지 않았어요. 상점에 문의해 주세요.")를 보냅니다.
- 손님 화면은 409라도 코드가 `PAYMENT_NOT_READY`면 전용 안내를, 아니면 예전처럼 재고 안내를 보여 줍니다.
- 로컬·테스트용 가짜 결제 경로는 그대로 둬서 개발 흐름은 바뀌지 않게 했어요.

## 코드로 보기 (개념 재현)

```java
// 상태 코드와 이유 코드를 함께 싣는 예외.
// 기존 ResponseStatusException 을 잡던 곳은 상속 덕분에 그대로 잡힌다
public class ReasonedStatusException extends ResponseStatusException {
    private final String code;

    public ReasonedStatusException(HttpStatus status, String code, String message) {
        super(status, message);
        this.code = code;
    }

    public String code() {
        return code;
    }
}

// 공통 처리기: 이유 코드가 있으면 그 코드, 없으면 일반 코드
@ExceptionHandler(ResponseStatusException.class)
ResponseEntity<ErrorBody> handle(ResponseStatusException e) {
    String code = (e instanceof ReasonedStatusException r) ? r.code() : "REQUEST_FAILED";
    return ResponseEntity.status(e.getStatusCode()).body(new ErrorBody(code, e.getReason()));
}

// 결제 경로 고르기: 설정이 없으면 손님에게 보여 줄 수 있는 이유로 거절
throw new ReasonedStatusException(HttpStatus.CONFLICT, "PAYMENT_NOT_READY",
    "이 상점은 아직 결제를 받을 준비가 되지 않았어요. 상점에 문의해 주세요.");
```

```ts
// 화면: 상태 코드가 아니라 이유 코드로 나눈다
if (error.status === 409 && error.code === "PAYMENT_NOT_READY") {
  showNotice(t("checkout.paymentNotReady"));
} else if (error.status === 409) {
  showNotice(t("checkout.stockConflict")); // 예전 동작은 그대로
}
```

테스트는 서버 쪽(설정이 없으면 이 코드와 문구가 나오는지, 코드 없는 예외는 예전 코드인지)과 화면 쪽(두 409를 다르게 안내하는지)을 나눠서 붙였습니다.

## 💡 배운 것

**HTTP 상태 코드는 분류일 뿐, 이유가 아닙니다.** 같은 409에도 재고 부족, 결제 설정 없음처럼 전혀 다른 이유가 섞입니다. 화면이 이유별로 다르게 안내해야 하면, 이유 코드를 따로 실어야 합니다.

**누구에게 보이는 문구인지 나눕니다.** 운영자에게 필요한 안내가 손님 화면으로 가면 혼란만 줍니다. 서버가 보내는 문구도 받는 사람을 정하고 써야 했습니다.

**기존 예외를 상속하면 고칠 범위가 줄어듭니다.** 예외를 잡던 곳을 하나하나 고치지 않아도 됐어요.

## 소감

"품절"이라는 말이 실제 원인과 전혀 달랐다는 게 인상적이었습니다. 손님이 보는 문구 한 줄도, 서버가 보낸 이유를 화면이 제대로 읽어야 맞게 나온다는 걸 배웠습니다.

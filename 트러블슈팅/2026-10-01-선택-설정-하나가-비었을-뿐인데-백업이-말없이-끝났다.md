# 2026-10-01 선택 설정 하나가 비었을 뿐인데, 백업이 말없이 끝났다

> 태그: #트러블슈팅 #bash #set-e #pipefail #cron #백업

## 무엇을 / 왜

전날 만든 업로드 파일 백업 스크립트를 서버에 설치하고 처음 돌렸습니다. 이 스크립트는 끝나면 로그에 `OK` 나 `FAIL 이유` 를 한 줄 남기게 되어 있는데, 아무것도 남지 않았습니다.

매일 새벽에 cron으로 혼자 도는 스크립트입니다. 실패할 때 아무 말도 없으면, 백업이 몇 주째 안 되고 있어도 알 수 없습니다. 그래서 고치기 전에 "왜 조용히 끝났는지" 부터 찾았습니다.

## 어떻게 풀었나

### 범인은 설정을 읽는 한 줄

스크립트 맨 위에는 흔히 쓰는 안전장치가 있었습니다.

```bash
set -euo pipefail
```

- `-e`: 명령이 실패하면 그 자리에서 스크립트를 끝낸다
- `-u`: 정의되지 않은 변수를 쓰면 실패로 본다
- `-o pipefail`: 파이프(`a | b | c`) 중 하나라도 실패하면 파이프 전체를 실패로 본다

설정 파일(`.env`)에서 값을 읽는 줄은 이랬습니다.

```bash
region=$(grep -E '^BACKUP_REGION=' .env | tail -n 1 | cut -d= -f2-)
```

지역은 **선택** 설정이라 서버 `.env` 에 없었습니다. 그러면 이런 순서로 끝납니다.

1. `grep` 은 찾는 줄이 없으면 종료 코드 **1** 을 돌려줍니다. 에러 메시지는 없습니다.
2. `pipefail` 때문에 파이프 전체가 1이 됩니다.
3. `변수=$(명령)` 형태의 대입은 명령의 종료 코드를 그대로 가지므로, `set -e` 가 여기서 스크립트를 끝냅니다.

로그를 남기는 줄에 닿기도 전에 끝났으니 아무 출력이 없었던 겁니다. 필수 설정(버킷 이름)이 비었을 때도 같은 이유로 "FAIL: 버킷 없음" 대신 조용히 끝났을 상황이었습니다.

### 하나 더: 도구가 없는 걸 "진행 중" 으로 착각

같은 백업이 겹쳐 돌지 않게 `flock` 으로 잠그고 있었습니다.

```bash
exec 9>/tmp/backup.lock
flock -n 9 || { echo "SKIP 이전 백업 진행 중"; exit 0; }
```

그런데 서버에 `flock` 자체가 없으면, "명령을 찾을 수 없음" 실패도 `||` 오른쪽으로 가서 **"이전 백업 진행 중"** 으로 기록됩니다. 백업은 한 번도 안 도는데 로그만 보면 정상처럼 보이는 상황이었습니다.

### 고친 방향

- 선택 설정은 없으면 **빈 값**으로 읽고 기본값을 씁니다.
- 필수 설정은 직접 확인해서, 비어 있으면 **이유를 적고** 실패합니다.
- `flock` 이 있는지 먼저 확인해, 없으면 SKIP이 아니라 FAIL로 남깁니다.

고친 뒤에는 실패 경우를 일부러 만들어 봤습니다. 지역 없음, 버킷 없음, `flock` 없음, 자격증명 없음. 네 경우 모두 이유가 적힌 한 줄로 끝나는 것을 확인했습니다.

### 덤: 서버 터미널에 붙여 넣기

설치 중에는 긴 명령을 서버 터미널에 붙여 넣다가 줄이 깨지는 일도 있었습니다. 화면에서 줄이 넘어가는 자리의 공백이 사라져 인자가 엉뚱하게 붙거나, 여러 줄이 한 줄로 합쳐져 실행됐어요. 스크립트와 설치 명령을 **짧은 줄**로 나누고, 붙여 넣을 명령은 텍스트 파일로 따로 준비해 통째로 복사하게 했습니다.

## 코드로 보기 (개념 재현)

고치기 전과 후를 나란히 놓았습니다. 키 이름과 경로는 예시입니다.

```bash
#!/usr/bin/env bash
set -euo pipefail

log()  { echo "$(date -u +%FT%TZ) $*"; }
fail() { log "FAIL $*"; exit 1; }

# 고치기 전: 키가 없으면 grep 이 1 -> pipefail -> set -e 로 여기서 조용히 끝난다
# region=$(grep -E '^BACKUP_REGION=' .env | tail -n 1 | cut -d= -f2-)

# 고친 뒤: 못 찾아도 실패로 보지 않고 빈 값을 돌려준다
read_env() {
  grep -E "^$1=" .env | tail -n 1 | cut -d= -f2- || true
}

bucket=$(read_env BACKUP_BUCKET)
region=$(read_env BACKUP_REGION)

[ -n "$bucket" ] || fail "BACKUP_BUCKET 이 비어 있음"   # 필수 값: 이유를 남기고 실패
region=${region:-ap-northeast-2}                        # 선택 값: 기본값

# 도구가 없는 것과 "앞 백업이 도는 중" 을 구분한다
command -v flock >/dev/null || fail "flock 이 설치되어 있지 않음"
exec 9>/tmp/backup.lock
flock -n 9 || { log "SKIP 이전 백업 진행 중"; exit 0; }

# ... 실제 백업(생략) ...
log "OK"
```

비슷한 함정이 하나 더 있습니다. `local` 과 함께 쓰면 반대로 실패가 **숨겨집니다.**

```bash
f() {
  local value=$(false)   # local 의 종료 코드(0)가 남아서 set -e 가 반응하지 않는다
  echo "여기까지 온다"
}
```

## 💡 배운 것

**`set -e` 는 "조용히 끝남" 을 만들 수 있습니다.** 안전장치라고 켜 두었는데, 로그를 남기기 전에 멈추면 오히려 실패를 숨깁니다. 실패할 수 있는 곳은 직접 확인하고 이유를 남기는 편이 낫습니다.

**`grep` 의 1은 에러가 아니라 "못 찾음" 입니다.** 선택 값을 읽을 때는 이 차이를 코드로 표현해야 합니다(`|| true`).

**실패 메시지는 원인별로 달라야 합니다.** "도구가 없음" 을 "진행 중" 으로 기록하면, 로그가 있어도 틀린 안심을 줍니다.

**실패 경우를 일부러 만들어 봅니다.** 성공 경로만 돌려 보면 이런 문제는 서버에서 처음 만나게 됩니다.

## 소감

전날 글에서 "실제 동작은 서버에 설정한 뒤 확인하겠다" 고 적었는데, 그 첫 확인에서 바로 걸렸습니다. 문법 검사를 통과한 스크립트도 설정이 하나 빠진 환경에서는 전혀 다르게 움직인다는 걸 배웠습니다. 지금은 첫 실행이 `OK` 로 남고 매일 새벽에 돌도록 등록했지만, 아직 업로드된 파일이 없어서 실제 파일을 복원해 보는 건 다음으로 남겨 두었습니다.

# 2026-10-30 프린터 이름의 한글이 깨져, 있는 프린터를 없다고 했다

> 태그: #트러블슈팅 #인코딩 #UTF-8 #CP949 #NETFramework #HTTP

## 무엇을 / 왜
사진 키오스크에서는 화면 앱이 사진을 다 만들면, 같은 PC 에서 도는 장치 프로그램에 HTTP 로 인쇄를 부탁하고 있었습니다. 장치 프로그램은 .NET Framework 로 만든 작은 HTTP 서버였고, 요청 본문은 JSON 이었습니다. 어느 프린터로 보낼지도 그 JSON 에 프린터 이름으로 담겨 있었습니다.

- 회사 시험 키오스크의 포토 프린터를 바꿔 끼웠더니, Windows 가 새 프린터를 `DS-RX1 (1 복사)` 라는 이름으로 등록했습니다.
- 처음에는 키오스크의 프린터 종류 설정이 실제 모델과 달라서 인쇄가 실패했습니다. 그 설정을 맞추고 새 프린터를 고른 뒤 다시 뽑았는데, 또 "인쇄에 실패했습니다"가 떴습니다.
- 장치 프로그램 기록에는 "이 프린터가 Windows 인쇄 대기열에 설치되어 있지 않다"는 오류가 남아 있었고, 프린터 이름은 `DS-RX1 (1 蹂듭궗)` 로 찍혀 있었습니다. "복사" 두 글자만 처음 보는 글자로 바뀌어 있었습니다.

## 어떻게 풀었나
- 보내는 쪽부터 봤습니다. 화면 앱은 프린터 이름을 넣은 객체를 JSON 문자열로 만들어 fetch 로 보냈고, 머리글에는 `Content-Type: application/json` 만 붙였습니다. 따로 받아 보니 본문은 UTF-8 바이트로 나갔고, 머리글에 charset 은 붙지 않았습니다.
- 받는 쪽은 본문을 "요청이 알려 준 인코딩으로 읽고, 그게 없으면 UTF-8 로 읽는다"는 식(`ContentEncoding ?? UTF8`)으로 읽고 있었습니다. 얼핏 보면 charset 이 없을 때는 UTF-8 로 읽을 것 같았습니다.
- 그런데 그 "없으면" 이 오지 않았습니다. 같은 PC 에서 재현해 보니 .NET Framework 의 HTTP 서버(HttpListener)는 charset 이 없는 요청에 null 이 아니라 시스템 기본 인코딩을 돌려주었고, 한국어 Windows 에서 그건 CP949(ks_c_5601-1987)였습니다. 대비책으로 둔 UTF-8 은 한 번도 쓰이지 않았습니다.
- UTF-8 바이트를 CP949 로 읽으니 `복사` 가 `蹂듭궗` 가 됐고, 깨진 이름으로 Windows 프린터 목록을 찾으니 없었던 것입니다. 한글이 든 프린터 이름이 이 길을 지나가면서 드러났습니다.
- 같은 코드를 새 .NET(10)에서 돌려 보니 멀쩡했습니다. 새 .NET 은 기본 인코딩이 UTF-8 이라 charset 이 없어도 UTF-8 로 읽었습니다. 장치 프로그램의 시험도 새 .NET 에서 돌고 있어서, 시험으로는 이 깨짐을 재현할 수 없었습니다.
- JSON 표준(RFC 8259)을 찾아보니, 닫힌 생태계가 아닌 시스템 사이에 주고받는 JSON 은 UTF-8 이어야 하고(MUST), application/json 에는 charset 매개변수가 정해져 있지 않다는 걸 알게 됐습니다. 보내는 쪽이 charset 을 붙이지 않은 건 틀린 게 아니었고, 받는 쪽이 UTF-8 로 읽어야 했습니다.
- 그래서 장치 프로그램이 요청 본문을 언제나 UTF-8 로 읽게 고쳤습니다. 카드·현금·커터·프린터·QR 다섯 곳이 같은 방식으로 읽고 있어서, 모두 한 곳의 읽기 함수를 쓰게 했습니다.
- 시험 환경에서는 깨짐이 재현되지 않으니, 한글 이름이 그대로 읽히는지와 함께 본문을 요청 인코딩으로 읽는 코드가 다시 생기지 않았는지 소스를 검사하는 시험을 넣었습니다.
- 고친 판이 깔리기 전까지는 Windows 에서 프린터 이름을 영문 `DS-RX1` 로 바꿔 인쇄를 이어 갔습니다.

## 코드로 보기 (개념 재현)
같은 PC 에서 .NET Framework 위에서 도는 Windows PowerShell 5.1 과, 새 .NET 위에서 도는 PowerShell 7 로 같은 스크립트를 돌려 봤습니다. 보내는 쪽은 화면 앱처럼 UTF-8 JSON 을 charset 없이 보내고, 받는 쪽은 고치기 전 방식과 고친 뒤 방식으로 둘 다 읽어 봤습니다. 비교하려고 charset=utf-8 을 붙인 요청도 함께 보냈습니다. 이름은 모두 예시입니다.

```powershell
# 키오스크 앱처럼 UTF-8 JSON 을 charset 없이 보내고, .NET 의 HTTP 서버가 본문을 무엇으로 읽는지 본다.
# 이 파일은 UTF-8(BOM 포함)으로 저장했다. Windows PowerShell 5.1 은 BOM 없는 스크립트를 시스템 코드 페이지로 읽는다.
[Console]::OutputEncoding = [Text.Encoding]::UTF8
Add-Type -AssemblyName System.Net.Http

$installed = 'DS-RX1 (1 복사)'                        # Windows 에 등록된 프린터 이름(예시)
$json  = '{"printerName":"' + $installed + '"}'
$bytes = [Text.Encoding]::UTF8.GetBytes($json)       # 보내는 쪽은 UTF-8 바이트를 보낸다

$prefix   = 'http://localhost:18765/'
$listener = [Net.HttpListener]::new()                # 장치 프로그램 쪽 HTTP 서버 역할
$listener.Prefixes.Add($prefix)
$listener.Start()
$client = [Net.Http.HttpClient]::new()               # 키오스크 앱 쪽 역할

"런타임 $([Environment]::Version) / 기본 인코딩 $([Text.Encoding]::Default.WebName)"
foreach ($contentType in 'application/json', 'application/json; charset=utf-8') {
  $content = [Net.Http.ByteArrayContent]::new($bytes)
  $content.Headers.TryAddWithoutValidation('Content-Type', $contentType) | Out-Null
  $pending = $client.PostAsync($prefix + 'print', $content)   # 응답을 기다리지 않고 보낸다

  $ctx = $listener.GetContext()                      # 서버: 요청 하나를 받는다
  $ms  = [IO.MemoryStream]::new()
  $ctx.Request.InputStream.CopyTo($ms)
  $raw = $ms.ToArray()                               # 받은 바이트는 보낸 바이트와 같다

  # 고치기 전에 읽던 방식: 요청이 알려 준 인코딩, 그게 null 일 때만 UTF-8
  $enc = $ctx.Request.ContentEncoding
  $isNull = $null -eq $enc
  if ($isNull) { $enc = [Text.Encoding]::UTF8 }
  $before = ($enc.GetString($raw) | ConvertFrom-Json).printerName
  # 고친 뒤 읽는 방식: 언제나 UTF-8
  $after = ([Text.Encoding]::UTF8.GetString($raw) | ConvertFrom-Json).printerName

  "보낸 Content-Type: $contentType"
  "  요청이 알려 준 인코딩: $($ctx.Request.ContentEncoding.WebName) (null 인가: $isNull)"
  "  그 인코딩으로 읽은 이름: $before -> 등록된 이름과 같은가: $($before -ceq $installed)"
  "  언제나 UTF-8 로 읽은 이름: $after -> 같은가: $($after -ceq $installed)"

  $ctx.Response.StatusCode = 200
  $ctx.Response.Close()
  $pending.Wait() | Out-Null
}
$listener.Stop()
```

.NET Framework 에서는 charset 이 없는 요청에 시스템 기본 인코딩이 돌아왔고(null 이 아니었습니다), 그 인코딩으로 읽은 이름은 등록된 이름과 달랐습니다. charset=utf-8 을 붙이거나 받는 쪽이 언제나 UTF-8 로 읽으면 이름이 맞았습니다. .NET 10 에서는 고치기 전 방식으로도 이름이 맞았습니다.

스크립트를 쓰는 중에도 같은 일을 한 번 겪었습니다. 한글이 든 스크립트를 BOM 없이 저장해 Windows PowerShell 5.1 로 돌리자, 스크립트 안의 `'DS-RX1 (1 복사)'` 가 `DS-RX1 (1 蹂듭궗)` 로 읽혔습니다. 스크립트 파일도 인코딩을 밝히지 않으면 시스템 코드 페이지로 읽혔던 것입니다. 그래서 위 스크립트는 BOM 을 붙여 저장했습니다.

## 💡 배운 것
- `값 ?? 기본값` 의 기본값은 값이 정말 null 일 때만 쓰인다는 걸 배웠습니다. 이번처럼 API 가 "모름"을 null 이 아니라 환경의 기본값으로 돌려주면, 대비책은 끝내 쓰이지 않았습니다.
- 요청에 빠진 정보는 받는 쪽이 돌고 있는 환경의 기본값으로 채운다는 걸 다시 배웠습니다([2026-10-29, 입력 검사 오류 문구가, 언어 정보가 없는 요청에는 영어로 나갔다](../트러블슈팅/2026-10-29-입력-검사-오류-문구가-언어-정보가-없는-요청에는-영어로-나갔다.md)). 그때는 언어였고, 이번에는 문자 인코딩이었습니다.
- 같은 코드라도 .NET Framework 와 새 .NET 은 기본 인코딩이 달라서, 새 런타임에서 통과한 시험이 매장 PC 에서도 그대로라고 볼 수 없다는 걸 배웠습니다. 재현되지 않는 규칙은 소스를 검사하는 시험으로라도 묶어 둬야 했습니다.
- JSON 은 시스템 사이에서 UTF-8 로 주고받는 것이 표준이고, application/json 에는 charset 매개변수가 없다는 걸 배웠습니다. 그래서 받는 쪽이 UTF-8 로 읽는 것이 맞았습니다.

## 소감
프린터를 바꿔 끼운 날 생긴 문제라 처음에는 프린터 쪽을 의심했습니다. 하지만 프린터는 이름에 한글 두 글자를 붙였을 뿐이었고, 그 두 글자가 지나가면서 숨어 있던 읽기 방식이 드러났습니다. 재현 스크립트에서 같은 깨짐을 한 번 더 겪고 나서야, 인코딩을 정해 두지 않으면 환경이 대신 정한다는 말이 실감 났습니다.

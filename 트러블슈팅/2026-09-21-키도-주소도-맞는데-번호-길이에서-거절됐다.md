# 2026-09-21 키도 주소도 맞는데, 번호 길이에서 거절됐다

> 태그: #트러블슈팅 #외부연동 #본인인증 #로그

## 무엇을 / 왜

회원가입에 휴대폰 본인인증을 붙였습니다. 본인확인 기관에서 발급받은 키를 서버 설정에 넣고, 기관 콘솔에 서버 IP 도 등록했습니다. 배포하고 가입 화면에서 버튼을 눌러 보니 이렇게 떴습니다.

```
POST /api/.../identity/start 502 (Bad Gateway)
본인확인을 시작하지 못했어요. 잠시 후 다시 시도해 주세요.
```

키도 새로 받았고 IP 도 등록했는데 뭐가 문제인지 감이 오지 않았습니다.

## 어떻게 풀었나

### 짐작 대신 서버 기록부터

처음 떠오른 건 "키를 잘못 붙여 넣었나", "IP 등록이 아직 반영 안 됐나" 였습니다. 하지만 그걸 하나씩 바꿔 보는 건 시간만 듭니다.

다행히 연동을 만들 때 **실패하면 기관이 돌려준 결과 코드를 로그에 남기게** 해 뒀습니다. 응답 원문은 개인정보가 섞일 수 있어서 **단계 이름과 코드, 메시지만** 남기도록요. 서버 로그를 걸러 보니 한 줄이 나왔습니다.

```
본인확인 시작 실패: 본인확인 접근 토큰 발급 실패 (3021 유효하지 않은 항목 데이터)
```

### 오류 종류가 방향을 알려 줬다

이 한 줄에서 두 가지를 알 수 있었습니다.

- **어느 단계인가:** 인증창을 여는 단계가 아니라, 그 전에 **접근 토큰을 받는 첫 단계**에서 막혔다.
- **무슨 종류인가:** 키가 틀렸다면 "인증 실패" 류의 응답이 왔을 겁니다. "유효하지 않은 항목 데이터" 는 **내가 보낸 값 중 하나가 규격에 안 맞는다**는 뜻입니다.

즉 키나 IP 가 아니라 **요청 본문**을 봐야 했습니다.

### 샘플 코드와 한 줄씩 대조

기관이 준 샘플 코드와 제 코드를 나란히 놓고 토큰 요청 본문을 비교했습니다. 보내는 값은 두 개뿐이었어요.

```
grant_type  = client_credentials   ← 같다
request_no  = ?                     ← 여기가 달랐다
```

샘플은 요청 번호를 이렇게 만들고 있었습니다.

```
접두어 + yyyyMMddHHmmss + 랜덤 12글자   (총 30글자)
// 주석: 20~50byte 사용 가능
```

제 코드는 토큰 요청에서만 이렇게 보내고 있었습니다.

```
"TKN" + 현재시각(밀리초)   → TKN1789976488123  (16글자)
```

**20바이트보다 짧았습니다.** 재밌는 건 인증창을 여는 다음 단계에서는 규격대로 30글자짜리를 만들고 있었다는 점입니다. 토큰 요청은 "잠깐 쓰고 버리는 번호" 라고 생각하고 따로 대충 짰던 게 원인이었습니다.

## 코드로 보기 (개념 재현)

고치기 전에는 번호를 만드는 곳이 두 군데였습니다.

```java
// 토큰 요청 - 따로 대충 만들었다 (16글자)
body.put("request_no", "TKN" + System.currentTimeMillis());

// 인증창 요청 - 규격대로 (30글자 안팎)
String requestNo = "REQ" + 시각14자리() + 랜덤12자리();
```

번호 만드는 규칙을 한 곳으로 모았습니다. 이제 어느 요청이든 같은 규칙을 탑니다.

```java
/** 요청 번호 - 접두어 + 시각 14자리 + 랜덤 12자리. 20~50바이트 규격을 늘 넘긴다. */
static String newRequestNo(String prefix) {
    String timestamp = new SimpleDateFormat("yyyyMMddHHmmss").format(new Date());
    String random = UUID.randomUUID().toString().replace("-", "").substring(0, 12);
    return prefix + timestamp + random;
}

body.put("request_no", newRequestNo("TKN"));   // 토큰 요청
String requestNo = newRequestNo("REQ");        // 인증창 요청
```

그리고 같은 실수가 돌아오지 않게 길이를 확인하는 테스트를 붙였습니다.

```java
@Test
void 요청_번호는_규격_길이_20에서_50바이트_사이다() {
    for (String prefix : new String[] {"TKN", "REQ"}) {
        String requestNo = newRequestNo(prefix);
        assertThat(requestNo.getBytes(StandardCharsets.UTF_8).length).isBetween(20, 50);
    }
}
```

실패 로그는 이렇게 남기고 있었습니다. 이게 없었다면 한참 헤맸을 겁니다.

```java
private void requireSuccess(JsonNode response, String step) {
    String code = text(response, "result_code");
    if (!"0000".equals(code)) {
        // 응답 원문은 남기지 않는다 - 개인정보가 섞일 수 있다. 단계와 코드만 남긴다.
        throw new IllegalStateException(
            "본인확인 " + step + " 실패 (" + code + " " + text(response, "result_message") + ")");
    }
}
```

## 💡 배운 것

**외부 연동은 실패할 때 무엇을 남기느냐가 전부입니다.** 화면에는 "잠시 후 다시 시도해 주세요" 밖에 없습니다. 기관이 준 코드가 로그에 있었기 때문에 원인이 한 줄로 좁혀졌습니다.

**오류의 "종류" 가 어디를 볼지 알려 줍니다.** 인증 오류면 키와 권한, 항목 오류면 요청 본문. 이 구분만으로도 확인할 곳이 절반으로 줄어듭니다.

**"잠깐 쓰는 값" 도 규격이 있습니다.** 토큰 요청 번호는 제 쪽에서 다시 쓸 일이 없어 대충 만들었는데, 기관 입장에서는 똑같이 검사하는 항목이었습니다.

**같은 규칙은 한 곳에서 만듭니다.** 두 군데서 따로 만들면 한쪽만 규격을 지키는 일이 생깁니다.

## 소감

키와 IP 부터 의심했다면 콘솔을 몇 번 들락거리다 결국 로그를 봤을 겁니다. 처음에 로그 한 줄을 남기는 수고가, 나중에 헤매는 시간을 통째로 줄여 준다는 걸 다시 느꼈습니다.

고친 뒤에는 실제 휴대폰으로 인증부터 가입까지 끝까지 해 봤고, 인증 결과로 받은 이름과 번호가 그대로 저장되는 것까지 확인했습니다.

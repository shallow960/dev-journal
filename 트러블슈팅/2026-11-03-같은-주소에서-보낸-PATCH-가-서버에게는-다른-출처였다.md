# 2026-11-03 같은 주소에서 보낸 PATCH 가, 서버에게는 다른 출처였다

> 태그: #트러블슈팅 #CORS #Spring #프록시 #Origin

## 무엇을 / 왜
고객사마다 자기 도메인으로 여는 관리 화면에, 기존 관리 콘솔 화면을 올리는 작업을 했습니다. 화면과 API 가 같은 주소여서 CORS 는 생각하지 않고 있었습니다.

- 서버의 경로 허용 목록을 넓히고 통합 시험을 돌렸더니, 고치기(PATCH)와 지우기(DELETE) 요청이 `403 Invalid CORS request` 로 막혔습니다.
- 조회(GET)와 등록(POST), 수정(PUT)은 문제가 없었습니다.
- 콘솔에는 키오스크 설정, 비밀번호, 리소스 묶음 삭제 같은 PATCH, DELETE 요청이 꽤 있었습니다. 그대로 열었다면 이 버튼들이 모두 실패했을 문제였습니다.

## 어떻게 풀었나
- 먼저 같은 주소인데 왜 CORS 검사를 타는지 봤습니다. 찾아보니 브라우저는 같은 출처 요청이어도 GET, HEAD 가 아니면 `Origin` 헤더를 붙인다는 걸 알게 됐습니다.
- Spring 은 이 `Origin` 을 자기가 아는 자기 주소(scheme, host, port)와 비교해 교차 출처인지 판단하고 있었습니다.
- 서버는 https 를 풀어 주는 앞단 뒤에 있었습니다. 앞단 헤더(`X-Forwarded-Proto`)를 믿도록 설정하지 않은 서버는 자기를 http 로 알고 있었습니다. 브라우저가 보낸 `Origin` 은 https 였으니, 같은 주소인데도 교차 출처가 됐습니다.
- 교차 출처로 판단된 요청은 고객사 주소별 허용 규칙을 탔고, 그 규칙의 허용 메서드는 GET, POST, PUT, OPTIONS 뿐이었습니다. 기존 화면은 그 안의 메서드만 써서, 잘못 판단된 채로 계속 통과하고 있었습니다.
- 이 설명이 맞는지 Spring 의 CORS 처리 코드를 그대로 불러 돌려 봤습니다(아래 코드).
  - 서버가 자기를 http 로 알면 PUT 은 통과하고 PATCH, DELETE 는 같은 403 을 받았습니다.
  - 서버가 자기를 https 로 알면 같은 PATCH 가 교차 출처가 아니어서 통과했습니다.
- 고친 방법은 이렇습니다.
  - 허용 메서드를 모든 요청에 넓히지 않고, 경로 허용 목록을 통과한 콘솔 요청에만 PATCH, DELETE 를 더했습니다.
  - 허용 `Origin` 은 그 고객사 주소 하나로 그대로 두었습니다.
  - 실제 앞단 뒤의 서버가 어떤 값으로 도는지는 그날 확인하지 못했습니다. 그래서 서버가 자기를 http 로 알든 https 로 알든 통과하게 고쳤습니다.
- 서버가 앞단 헤더를 믿도록 바꾸는 쪽은 주소와 IP 를 판단하는 곳 전체에 영향을 줄 수 있어서, 따로 확인할 일로 남겼습니다.

## 코드로 보기 (개념 재현)
Spring Framework 6.2.7 의 `DefaultCorsProcessor` 와 `CorsUtils` 를 그대로 불렀습니다. 요청은 가짜 요청 객체로 만들었습니다.

```java
import java.util.List;
import org.springframework.mock.web.MockHttpServletRequest;
import org.springframework.mock.web.MockHttpServletResponse;
import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.CorsUtils;
import org.springframework.web.cors.DefaultCorsProcessor;

public class SameOriginDemo {
    static final String HOST = "admin.example.com";

    static void call(String method, String scheme, int port, List<String> allowed) throws Exception {
        // 브라우저 주소창은 https://admin.example.com, 그 화면이 같은 주소로 보낸 요청이다.
        MockHttpServletRequest request = new MockHttpServletRequest(method, "/api/things/1");
        request.setScheme(scheme);       // 서버가 자기 자신을 어떻게 알고 있는가
        request.setServerName(HOST);
        request.setServerPort(port);
        request.addHeader("Origin", "https://" + HOST);

        CorsConfiguration rule = new CorsConfiguration();
        rule.setAllowedOrigins(List.of("https://" + HOST));
        rule.setAllowedMethods(allowed);

        MockHttpServletResponse response = new MockHttpServletResponse();
        boolean passed = new DefaultCorsProcessor().processRequest(rule, request, response);
        System.out.printf("%-6s 서버가 아는 나=%s://%s:%-4d 교차 출처로 봄=%-5s 통과=%-5s 응답=%d %s%n",
                method, scheme, HOST, port, CorsUtils.isCorsRequest(request), passed,
                response.getStatus(), response.getContentAsString());
    }

    public static void main(String[] args) throws Exception {
        List<String> narrow = List.of("GET", "POST", "PUT", "OPTIONS");
        List<String> wide = List.of("GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS");

        System.out.println("-- 앞단 헤더를 안 믿는 서버, 예전 허용 목록");
        call("PUT", "http", 8080, narrow);
        call("PATCH", "http", 8080, narrow);
        call("DELETE", "http", 8080, narrow);

        System.out.println("-- 앞단 헤더를 믿어 자기를 https 로 아는 서버, 예전 허용 목록");
        call("PATCH", "https", 443, narrow);

        System.out.println("-- 앞단 헤더를 안 믿는 서버, 넓힌 허용 목록");
        call("PATCH", "http", 8080, wide);
        call("DELETE", "http", 8080, wide);
    }
}
```

## 💡 배운 것
- 같은 출처 요청에도 GET, HEAD 가 아니면 `Origin` 이 붙는다는 걸 배웠습니다. 화면과 API 가 같은 주소라고 CORS 와 상관없는 게 아니었습니다.
- CORS 판단은 브라우저의 주소가 아니라 서버가 자기를 어떻게 아는지에 달려 있다는 걸 배웠습니다. 잘못 판단해도 허용 목록 안의 메서드는 통과해서, 목록 밖의 메서드를 처음 쓸 때에야 드러났습니다.
- 프록시 뒤에서 서버가 아는 내 주소를 믿으면 안 된다는 걸 다시 배웠습니다([2026-08-07, 결제를 마치니 0.0.0.0:3000으로 튕겼다 - 프록시 뒤에서 "내 주소"를 스스로 믿으면 안 된다](../트러블슈팅/2026-08-07-결제후-0.0.0.0으로-튕겼다-프록시뒤에서-내주소.md)). 그때는 되돌아갈 주소를 만들 때였고, 이번에는 출처를 비교할 때였습니다.

## 소감
화면과 API 가 같은 주소인 서비스에서 CORS 오류를 볼 거라고는 생각하지 못했습니다. 시험이 브라우저처럼 `Origin` 을 붙여 보내 준 덕분에 화면을 열기 전에 드러났습니다. 잘 돌던 요청들도 사실은 잘못된 판단 위에서 통과하고 있었다는 걸 알고 나니, 되는 것도 왜 되는지 봐야겠다고 생각했습니다.

# 2026-11-02 부분 취소로 보낸 요청이, 칸 이름 하나 때문에 전액 취소가 될 뻔했다

> 태그: #트러블슈팅 #결제 #부분취소 #외부API #시험

## 무엇을 / 왜

손님이 주문한 상품 가운데 하나만 취소하거나 반품하면, 결제사에는 그 상품 금액만 취소해 달라고 요청해야 했습니다. 쇼핑몰은 결제사 여러 곳을 쓰고 있었고, 결제사마다 취소 요청을 만드는 코드가 따로 있었습니다.

실제 결제로 부분 취소를 시험하기 전에, 한 결제사의 개발 안내서에서 취소 항목을 다시 읽어 봤습니다. 안내서에는 부분 취소 금액을 정해진 이름의 칸 하나로 받고, 그 칸이 없으면 결제 전체를 취소한다고 적혀 있었습니다. 그런데 우리 코드는 금액을 안내서에 없는 `amount` 라는 이름으로 보내고 있었습니다.

안내서대로라면 결제사는 우리가 보낸 금액 칸을 알아보지 못하고, 금액 칸이 빠진 요청으로 받았을 것입니다. "3만 원만 취소해 주세요" 가 결제사 쪽에서는 "전부 취소해 주세요" 가 되는 셈이었습니다. 10만 원짜리 주문에서 상품 하나를 반품하면 10만 원이 모두 돌아갈 수 있는 상태였습니다.

## 어떻게 풀었나

### 시험이 못 잡은 이유부터 봤습니다

부분 취소는 금액 계산부터 처리 기록까지 시험을 모두 통과하고 있었습니다. 다만 시험에서 쓰는 흉내 결제사는 취소 요청을 만들지도 않고 바로 "취소 성공" 을 돌려줬습니다. 우리 서버 안에서 금액이 맞는지는 확인했지만, 결제사가 그 금액을 읽을 수 있는지는 확인한 적이 없었습니다.

### 칸 이름을 안내서에 맞췄습니다

부분 취소 금액을 안내서에 적힌 칸 이름으로 보내게 했습니다. 그리고 금액 칸을 빼는 경우를 하나로 좁혔습니다.

- 아직 아무것도 돌려주지 않은 결제를 남김없이 취소할 때만 금액 칸을 뺐습니다. 이때는 전체 취소가 맞는 동작이었습니다.
- 승인 금액이 주문 금액과 달라 승인을 바로 되돌리는 망취소도 결제 전체를 취소해야 해서 이 경우에 들어갔습니다.
- 일부를 이미 돌려준 뒤 남은 금액을 모두 취소할 때는 금액 칸을 넣었습니다. 남은 금액이 얼마인지 결제사에 분명히 알려 주는 쪽이 안전하다고 봤습니다.

### 요청 본문을 시험으로 고정했습니다

결제사로 나가는 요청 본문을 붙잡아 칸을 확인하는 시험을 만들었습니다. 상품 하나만 돌려줄 때, 통째로 취소할 때, 망취소할 때, 일부를 돌려준 뒤 나머지를 취소할 때를 나눠 봤습니다. 누군가 칸 이름을 다시 바꾸면 이 시험이 깨지게 했습니다.

## 코드로 보기 (개념 재현)

```java
// 결제사 취소 요청 본문 만들기 (개념 재현 - 실제 이름과 다름)
Map<String, Object> cancelBody(Payment payment, CancelRequest request) {
    Map<String, Object> body = new HashMap<>();

    // 예전: body.put("amount", request.amount());
    //   안내서에 없는 이름이라 결제사가 읽지 못한다.
    //   금액 칸이 빠진 요청으로 받으면 결제 전체를 취소한다.

    boolean wholeFirstCancel =
        payment.returnedSoFar().signum() == 0          // 아직 아무것도 돌려주지 않았고
        && request.remainingAfter().signum() == 0;      // 이번에 남김없이 취소한다
    if (!wholeFirstCancel) {
        body.put("partialAmount", request.amount());    // 안내서에 적힌 부분 취소 금액 칸
    }
    body.put("reason", request.reason());
    return body;
}
```

```java
// 요청 본문을 고정하는 시험 (개념 재현)
@Test
void 상품_하나만_돌려주면_그_금액을_부분_취소_칸으로_보낸다() {
    PgRecorder pg = new PgRecorder();                          // 나가는 요청을 그대로 붙잡는 가짜 결제사
    gateway(pg).cancel(paidPayment(100_000), partial(30_000));

    Map<String, Object> body = pg.capturedBody();
    assertThat(body).containsEntry("partialAmount", 30_000L);  // 안내서의 이름으로 들어갔는가
    assertThat(body).doesNotContainKey("amount");              // 예전 이름은 없어야 한다
}

@Test
void 아무것도_돌려주지_않은_결제를_통째로_취소하면_금액_칸을_뺀다() {
    PgRecorder pg = new PgRecorder();
    gateway(pg).cancel(paidPayment(100_000), whole(100_000));

    assertThat(pg.capturedBody()).doesNotContainKey("partialAmount");
}
```

## 💡 배운 것

- 외부 API 에 칸 이름을 틀리게 보내도 오류가 나지 않을 수 있었습니다. 그 칸은 "없는 칸" 이 되고, 빠진 칸에 정해진 기본 동작이 그대로 실행됐습니다. 이 결제사에서는 그 기본 동작이 "전체 취소" 였습니다.
- 흉내 결제사로 하는 시험은 우리가 정한 요청 모양을 우리에게 다시 확인해 줄 뿐이었습니다. 요청 본문은 안내서를 옆에 두고 칸 이름까지 맞춰 봐야 했습니다.
- 돈이 움직이는 요청은 칸마다 "이 칸이 빠지면 어떻게 되는가" 를 찾아보는 것이 좋았습니다.

## 소감

금액이 우리 서버 안에서 맞게 계산되는 것과, 결제사가 그 금액을 읽는 것은 다른 일이었습니다. 실제 결제로 시험하기 전에 안내서를 한 번 더 읽은 덕분에 찾을 수 있었습니다. 다만 결제사 시험 환경에서 실제로 일부만 취소되는지는 아직 확인하지 못해, 확인할 목록에 올려 두었습니다.

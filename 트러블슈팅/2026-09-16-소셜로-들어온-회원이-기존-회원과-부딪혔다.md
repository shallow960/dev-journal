# 2026-09-16 소셜로 들어온 회원이, 기존 회원과 부딪혔다

> 태그: #트러블슈팅 #인증 #소셜로그인 #계정탈취

## 무엇을 / 왜

쇼핑몰 회원은 두 가지로 가입할 수 있습니다. 이메일·비밀번호, 그리고 소셜 로그인.

이메일로 먼저 가입한 사람이 나중에 소셜 버튼으로 들어오면 **로그인이 실패** 했습니다. 화면에는 그냥 "로그인에 실패했습니다" 만 떴고요.

## 어떻게 풀었나

### 원인: 처음 보는 소셜이면 무조건 새 회원을 만들고 있었다

코드는 이랬습니다.

```
소셜 연결 기록이 있으면 → 그 회원으로 로그인
없으면 → 새 회원을 만든다
```

그런데 회원 이메일에는 "한 가게 안에서 하나" 라는 제약이 걸려 있습니다. 같은 이메일로 회원을 하나 더 만들려다 데이터베이스가 막았고, 그게 로그인 실패로 보였던 겁니다.

### 그렇다고 "이메일이 같으면 같은 사람" 으로 이으면 안 된다

가장 쉬운 해결은 "같은 이메일이면 그 회원에 연결" 입니다. 하지만 이건 **계정 탈취 경로** 가 됩니다.

```
1. 공격자가 소셜 서비스에서 계정을 만든다
2. 그 계정의 이메일을 피해자 주소로 적는다 (확인 절차가 없는 서비스도 있다)
3. 우리 쪽 소셜 버튼으로 들어온다
4. "이메일이 같네" → 피해자 계정으로 로그인된다
```

그래서 기준을 **"공급자가 그 이메일을 검증했는가"** 로 잡았습니다. 검증된 이메일이면 같은 사람으로 보고 잇고, 검증되지 않았으면 잇지 않습니다.

검증되지 않은 경우에는 새 회원으로 가되, **남의 이메일을 그 회원의 주소로 쓰지도 않습니다.** 공급자별로 겹치지 않는 내부 주소를 만들어 붙입니다. 그러지 않으면 나중에 그 이메일의 진짜 주인이 가입할 때 또 부딪힙니다.

### 소셜끼리는 잇지 않기로 정했다

"카카오로 가입한 사람이 네이버로 들어오면?" 이라는 질문이 남습니다. 두 가지 선택지가 있었습니다.

- 한 계정에 여러 소셜을 묶는다 → 어느 쪽이 주인인지, 하나를 끊으면 어떻게 되는지를 계속 따져야 한다
- 잇지 않고 **쓰던 쪽으로 안내한다** → "카카오로 로그인해 주세요"

후자를 골랐습니다. 사용자 입장에서도 "내 계정이 왜 둘이지" 가 생기지 않고, 구현도 규칙 한 줄로 끝납니다. 이메일 가입 계정에 **첫 소셜** 을 붙이는 것만 허용합니다.

### 플랫폼 계정은 기준이 다르다

같은 서비스라도 가게를 운영하는 사람의 계정은 연결 기준을 더 강하게 뒀습니다. 이메일이 아니라 **본인확인으로 검증된 연락처** 가 같을 때만 같은 사람으로 봅니다. 여기서 실수하면 가게 전체를 넘기는 셈이 되니까요.

## 코드로 보기 (개념 재현)

```java
/**
 * 처음 보는 소셜 신원을 기존 회원에 잇거나, 새 회원으로 만든다.
 *
 * ★예전엔 무조건 새로 만들었다. 같은 이메일의 회원이 하나 더 생기려다
 *   유니크 제약에 걸려 로그인 자체가 실패했다.
 */
private 회원 잇거나_만들기(공급자 공급자, 소셜프로필 프로필) {
    // 잇는 기준은 "공급자가 검증한 이메일" 뿐이다.
    // 미검증 이메일로 이으면 주소만 아는 사람이 남의 계정을 가져갈 수 있다.
    if (프로필.이메일검증됨() && 값있음(프로필.이메일())) {
        var 기존 = 회원저장소.이메일로찾기(프로필.이메일());
        if (기존.isPresent()) {
            회원 회원 = 기존.get();

            // 소셜끼리는 잇지 않는다. 쓰던 쪽으로 돌려보낸다.
            String 다른공급자 = 회원저장소.연결된공급자들(회원.id()).stream()
                .filter(연결 -> !연결.equalsIgnoreCase(공급자.값()))
                .findFirst().orElse(null);
            if (다른공급자 != null) {
                throw new 요청거절(409, 이름(다른공급자) + "(으)로 가입한 계정이에요. "
                    + 이름(다른공급자) + " 로그인해 주세요.");
            }

            회원저장소.소셜연결(회원.id(), 공급자, 프로필.외부식별자());
            return 회원;
        }
    }
    return 새회원만들기(공급자, 프로필);
}
```

```java
private 회원 새회원만들기(공급자 공급자, 소셜프로필 프로필) {
    // 미검증 이메일이나 이미 쓰이는 주소는 계정 주소로 쓰지 않는다.
    // 그 주소의 진짜 주인이 나중에 가입할 때 또 부딪힌다.
    boolean 쓸수있나 = 프로필.이메일검증됨()
        && 값있음(프로필.이메일())
        && 회원저장소.이메일로찾기(프로필.이메일()).isEmpty();

    String 주소 = 쓸수있나
        ? 프로필.이메일()
        : 공급자.값() + "_" + 프로필.외부식별자().toLowerCase() + "@소셜.내부";
    ...
}
```

검증은 "이어지는가" 보다 **"이어지면 안 되는 것이 안 이어지는가"** 를 더 봅니다.

```java
@Test
void 같은_이메일로_가입한_회원이_소셜로_들어오면_그_회원으로_로그인된다() {
    var 기존 = 회원만들기("손님@example.com");

    var 결과 = 소셜로그인(카카오, 프로필("손님@example.com", 이메일검증됨: true));

    assertThat(결과.회원().id()).isEqualTo(기존);
    assertThat(회원수("손님@example.com")).isEqualTo(1);   // 회원이 늘지 않았다
}

@Test
void 공급자가_검증하지_않은_이메일로는_잇지_않는다() {
    var 기존 = 회원만들기("피해자@example.com");

    var 결과 = 소셜로그인(카카오, 프로필("피해자@example.com", 이메일검증됨: false));

    assertThat(결과.회원().id()).isNotEqualTo(기존);            // 남의 계정으로 들어가지 못한다
    assertThat(결과.회원().이메일()).endsWith("@소셜.내부");    // 남의 주소를 가져가지도 않는다
}

@Test
void 카카오로_가입한_회원이_네이버로_들어오면_카카오로_안내한다() {
    회원만들기("둘다@example.com");
    소셜로그인(카카오, 프로필("둘다@example.com", 이메일검증됨: true));

    assertThatThrownBy(() -> 소셜로그인(네이버, 프로필("둘다@example.com", 이메일검증됨: true)))
        .hasMessageContaining("카카오");
}
```

## 💡 배운 것

**"연결해 준다" 와 "남의 계정을 가져갈 수 있다" 는 종이 한 장 차이입니다.** 같은 이메일을 같은 사람으로 보는 편의 기능이, 조건 하나(공급자가 검증했는가)를 빼면 그대로 탈취 경로가 됩니다.

**편의 기능을 넣기 전에 악용 시나리오부터 적어 봅니다.** "공격자가 이 기능으로 무엇을 할 수 있나" 를 세 줄로 적어 보면 필요한 조건이 보입니다.

**데이터베이스 제약 위반은 사용자에게 엉뚱한 화면으로 보입니다.** "로그인 실패" 뒤에 실제로는 유니크 제약이 있었습니다. 제약은 마지막 방어선이지, 거기까지 가면 이미 설계가 빠진 것입니다.

**단순한 규칙이 나중에 따질 일을 줄입니다.** 소셜끼리 잇지 않기로 정하니 "주 계정은 어디인가", "하나를 끊으면 어떻게 되나" 같은 질문이 통째로 사라졌습니다.

**같은 서비스라도 계정의 무게에 따라 기준이 달라야 합니다.** 물건을 사는 사람과 가게를 운영하는 사람을 같은 기준으로 묶으면 안 됩니다.

## 소감

소셜 로그인은 "붙이면 끝" 인 기능인 줄 알았는데, 실제로 시간을 쓴 곳은 **기존 계정과 만나는 지점** 이었습니다. 로그인 자체는 공급자가 해 주고, 우리가 정해야 하는 건 "이 사람이 우리 쪽 누구인가" 하나뿐이더군요.

그리고 판단 기준은 **우리가 검증하지 않은 값** 이 아니라 **누군가 검증해 준 값** 이어야 한다는 것도 분명해졌습니다. 이메일은 공급자가 확인해 줬을 때만 근거가 되고, 그렇지 않으면 그냥 사용자가 적어 넣은 글자입니다.

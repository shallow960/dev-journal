# 2026-10-16 리허설 서버가, 진짜 결제를 할 수 있었다

> 태그: #트러블슈팅 #서버이전 #DockerCompose #보안그룹 #부작용

## 무엇을 / 왜

새 서버로 옮기기 전에, 실데이터 사본으로 새 서버를 한 번 띄워 보는 리허설을 하려고 했습니다. 띄우기 직전에 백엔드 코드를 다시 보니 문제가 있었어요.

- 백엔드에는 예약 작업이 36개 있었습니다. 매일 새벽 정기결제, 결제 실패 재시도, 예약 메시지 발송, 재입고 알림, 1분마다 도는 영상 삭제 같은 것들이요.
- 이걸 **한꺼번에 끄는 스위치가 없었습니다.**
- 사본 DB 에도 정기결제 일정이 그대로 들어 있습니다.

진짜 설정 그대로 띄우면 같은 손님 카드를 **한 번 더 결제** 하고, 메일과 알림을 **두 번** 보내고, 기존 서버가 아직 쓰는 영상을 **지울** 수도 있었어요. 상점마다 쓰는 결제사 키는 DB 안에 있어서, 설정 파일만 고쳐서는 막을 수 없었습니다.

## 어떻게 풀었나

두 겹으로 막고, 막힌 걸 확인한 뒤에만 켰습니다.

1. **나가는 네트워크 막기.** 서버 보안 그룹의 아웃바운드 규칙에서 "모든 곳(0.0.0.0/0)"을 지우고 같은 VPC 대역만 남겼습니다. DB 는 같은 VPC 안이라 계속 연결되고, 결제사·메일·영상 서비스로는 아무것도 못 나가요.
2. **외부 연동 설정 비우기.** 원래 compose 파일은 그대로 두고, 결제·메일·영상·세금계산서·본인확인 설정을 빈 값으로 덮는 **리허설용 compose 파일을 위에 덧씌웠습니다.** 서버의 `.env` 에 `COMPOSE_FILE` 을 적어 두면 `docker compose` 를 어떻게 불러도 덧씌움이 빠지지 않아요.
3. **켜기 전에 검사.** 합쳐진 설정을 JSON 으로 뽑아, 비워야 할 값이 하나라도 남아 있으면 켜지 않고 멈추는 스크립트로 띄웠습니다. 값 자체는 화면에 찍지 않아요.
4. 시험은 DNS 를 바꾸지 않고, 내 PC 에서만 새 서버로 가게 해서 했습니다.

## 코드로 보기 (개념 재현)

```yaml
# compose.rehearsal.yml : 리허설 때만 덧씌운다 (원래 파일은 손대지 않음)
services:
  backend:
    environment:
      MAIL_HOST: ""              # 메일: 비우면 보내지 않고 로그만 남긴다
      PAYMENT_MERCHANT_KEY: ""   # 결제: 비우면 실제 결제를 부르지 않는다
      VIDEO_PROVIDER: "stub"     # 영상: 외부 서비스 대신 가짜 구현
      TAX_INVOICE_API_KEY: ""    # 세금계산서
```

```bash
# .env 에 적어 두면, 어떤 docker compose 명령에도 세 파일이 함께 쓰인다
COMPOSE_FILE=compose.yml:compose.override.yml:compose.rehearsal.yml
```

```bash
# 켜기 전에: 비워야 할 값이 정말 비었는지 확인하고, 아니면 멈춘다
docker compose config --format json | python3 -c '
import json, sys
env = json.load(sys.stdin)["services"]["backend"]["environment"]
must_be_empty = ["MAIL_HOST", "PAYMENT_MERCHANT_KEY", "TAX_INVOICE_API_KEY"]
left = [k for k in must_be_empty if env.get(k)]   # 값은 출력하지 않고 이름만
if left or env.get("VIDEO_PROVIDER") != "stub":
    print("아직 남은 설정:", left)
    sys.exit(1)
' || { echo "켜지 않음"; exit 1; }

docker compose up -d --pull never   # 이미지는 미리 넣어 둔 것만 쓴다

# 나가는 네트워크가 정말 막혔는지
curl -sS -m 5 -o /dev/null https://www.example.com && echo "열려 있음" || echo "막힘"
```

## 💡 배운 것

**사본도 바깥과 연결되면 진짜처럼 움직입니다.** 데이터가 사본이라는 건 DB 안의 이야기고, 결제사나 메일 서버 입장에서는 똑같은 요청이에요.

**하나씩 끄는 것보다 나가는 길을 막는 게 빠뜨리지 않습니다.** 예약 작업 36개를 하나씩 끄면 하나쯤 빠뜨리기 쉬운데, 네트워크는 한 번에 막혀요. 설정 비우기도 같이 둬서, 한 겹이 실수로 열려도 다른 한 겹이 남게 했습니다.

**덧씌움 파일은 원래 설정을 지킵니다.** 원래 파일을 고치지 않으니, 실제 이전 때는 덧씌움만 걷으면 됩니다.

**검사를 켜는 절차 안에 넣습니다.** "비웠겠지"를 믿지 않고, 비지 않았으면 아예 켜지지 않게 했어요.

## 소감

리허설은 안전한 연습이라고 생각했는데, 실데이터 사본이 들어가는 순간 가장 위험한 단계가 될 수 있었습니다. 켜기 전에 "이 서버가 바깥에 무엇을 할 수 있나"를 먼저 적어 보는 습관을 들이게 됐어요.

# 2026-08-11 이메일이 같으면 같은 사람일까 - 소셜 로그인으로 남의 계정을 가져갈 수 있었다

> 태그: #트러블슈팅 #보안 #소셜로그인 #OAuth

## 오늘 한 일 (요약)
- 카카오·네이버·구글 로그인을 붙이다가 기존 코드에서 이런 부분을 봤다.
- 소셜로 처음 들어온 사람의 **이메일이 기존 회원과 같으면 그 계정에 그냥 연결**하고 있었다.
- 친절해 보이는데, 남의 이메일로 소셜 계정을 만들면 **그 사람 계정을 가져갈 수 있는** 구멍이었다.
- 공급자가 "이 이메일 확인했음"을 알려주는 경우에만 연결하도록 바꿨다.

## 문제의 코드

```java
private PlatformAccount createSocialAccount(SnsProvider provider, SocialProfile profile) {
    String email = hasText(profile.email()) ? profile.email() : ...;

    // 같은 이메일의 비번 계정이 이미 있으면 그 계정에 소셜 링크만 붙인다(계정 중복 방지)
    PlatformAccount account = accountRepository.findByEmail(email)
        .orElseGet(() -> accountRepository.save(PlatformAccount.register(email, ...)));
    accountRepository.linkSns(account.id(), provider.dbValue(), profile.externalId());
    return account;
}
```

주석까지 보면 의도가 분명하다. **계정이 두 개 생기는 걸 막으려는 것**이다. 사용자가 예전에 이메일로 가입해 놓고 나중에 카카오로 들어오면, 같은 사람이니 하나로 합쳐주는 게 친절하다.

나도 처음엔 이 코드를 그냥 지나쳤다.

## 무엇이 문제인가

이 로직은 **"이메일이 같으면 같은 사람"** 이라는 전제 위에 서 있다. 그 전제가 성립하려면 조건이 하나 필요하다.

> 소셜 서비스가 **그 이메일이 정말 이 사람 것인지 확인했어야** 한다.

확인하지 않는다면 이런 일이 가능하다.

```
1. 공격자가 카카오 계정을 만들면서 이메일을 victim@example.com 으로 적는다
2. 그 계정으로 우리 서비스에 "카카오 로그인"
3. 서버: "victim@example.com 회원이 있네? 이 계정에 연결하자"
4. 공격자가 victim 의 계정으로 로그인된다
```

우리 서비스에서 그 계정은 **쇼핑몰과 결제수단을 쥔 사장님 계정**이다. 주문·회원 개인정보·매출이 전부 딸려 간다.

## 확인해 보니 공급자마다 달랐다

다행히 주요 공급자는 이메일 확인 여부를 응답에 담아준다.

```jsonc
// 카카오 /v2/user/me
{ "kakao_account": { "email": "a@b.com",
                     "has_email": true,
                     "is_email_verified": true } }

// 구글 OpenID userinfo
{ "email": "a@b.com", "email_verified": true }

// 네이버 - 확인 여부를 주지 않는다
{ "response": { "id": "...", "email": "a@b.com", "name": "..." } }
```

그런데 우리가 쓰던 신원 객체에는 그 값을 담을 자리가 아예 없었다.

```java
record SocialProfile(String externalId, String email, String name) { }
```

읽지 않으니 판단할 수도 없었던 것이다.

## 고친 방법

먼저 자리를 만들고, 공급자별로 읽는다.

```java
record SocialProfile(String externalId, String email, String name, boolean emailVerified) {

    /** 이메일 검증 여부를 알 수 없는 경우(목·테스트 등). */
    static SocialProfile of(String externalId, String email, String name) {
        return new SocialProfile(externalId, email, name, false);   // 모르면 미검증
    }
}
```

```java
// 카카오: 보유(has_email)와 검증(is_email_verified)이 따로다 - 둘 다여야 한다
boolean verified = asBoolean(account.get("is_email_verified"))
                && asBoolean(account.get("has_email"));

// 네이버: 검증 여부를 주지 않는다 -> 단언 없음(false)
return SocialProfile.of(id, email, name);
```

그리고 연결 여부를 이 값으로 가른다.

```java
if (existing != null) {
    if (!profile.emailVerified()) {
        throw new ResponseStatusException(HttpStatus.CONFLICT,
            "이미 이 이메일로 가입된 계정이 있어요. 비밀번호로 로그인한 뒤 소셜 계정을 연결해 주세요.");
    }
    accountRepository.linkSns(existing.id(), provider.dbValue(), profile.externalId());
    return existing;
}
```

검증되지 않았으면 **막는 대신 다른 길을 준다.** 기존 비밀번호로 로그인해서 본인임을 증명한 뒤 연결하면 된다. 진짜 주인은 그 길로 갈 수 있고, 공격자는 갈 수 없다.

## 판단이 갈린 지점

네이버를 어떻게 할지가 고민이었다. 네이버는 가입할 때 이메일을 확인하는 것으로 알려져 있다. 그러니 "사실상 검증된 것"으로 봐도 되지 않을까?

그렇게 하지 않았다. **응답이 단언하지 않는 것을 내가 추측해서 채우면**, 나중에 네이버 정책이 바뀌었을 때 아무도 모른다. 코드에는 "네이버는 검증됨"이라고 적혀 있는데 실제로는 아닌 상태가 조용히 생긴다.

> 모르면 미검증. 안전한 쪽이 기본값.

불편은 있다. 네이버로 처음 들어온 사람 중 같은 이메일로 이미 가입한 사람은 한 번 더 로그인해야 한다. 하지만 그 불편의 대가가 **계정 탈취를 막는 것**이라면 받아들일 만하다고 봤다.

## 겸사겸사 고친 것

계정을 언제 만드느냐도 바꿨다. 원래는 소셜 인증이 끝나면 **바로 계정을 만들었는데**, 우리는 그 뒤에 이름·연락처·약관 동의를 받는 화면이 있다. 그 화면에서 이탈하면 **약관 동의도 없고 연락처도 없는 반쪽 계정**이 남는다.

그래서 소셜 신원만 20분짜리 임시 보관에 두고, **추가정보를 제출하는 시점에** 계정을 만들도록 옮겼다. 중간에 나가면 아무것도 남지 않는다.

## 배운 것
- **"이메일이 같으면 같은 사람"은 전제가 붙어야 성립한다.** 그 전제(공급자의 확인)를 확인하지 않으면 편의 기능이 침입 경로가 된다.
- 외부 서비스 응답에서 **무엇을 단언하고 무엇을 단언하지 않는지** 봐야 한다. 단언하지 않는 걸 추측으로 채우면 안 된다.
- 검증 안 된 경우에 **막기만 하지 말고 대안 경로를 준다.** 진짜 주인은 통과할 수 있고 공격자는 못 하는 길이 있으면 된다.
- 계정은 **정보가 다 모인 시점에** 만든다. 중간에 만들면 불완전한 계정이 쌓인다.

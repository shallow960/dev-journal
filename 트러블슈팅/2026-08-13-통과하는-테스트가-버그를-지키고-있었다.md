# 2026-08-13 통과하는 테스트가 버그를 지키고 있었다 - 초록불을 어디까지 믿을 것인가

> 태그: #트러블슈팅 #테스트 #정산 #SQL

## 오늘 한 일 (요약)
- 정산 배치에서 **환불된 상품이 15일 뒤에 정산으로 되살아나는** 버그를 찾았다.
- 막는 조건을 한 줄 넣었더니, 멀쩡히 통과하던 **다른 테스트가 깨졌다.**
- 그 테스트를 열어보니 **취소된 상품을 "정산해야 할 상품"으로 넣어놓고** 있었다. 고칠 건 내 코드가 아니라 테스트였다.
- 그래서 반대로 해봤다. 내가 새로 쓴 테스트도 **일부러 코드를 되돌려 깨뜨려 보고** 나서야 믿기로 했다.

## 시작은 정산 배치였다

우리 서비스에는 입점 판매자에게 돈을 나눠주는 정산이 있다. 흐름은 이렇다.

```
손님이 구매확정  →  (15일 뒤)  →  배치가 "이 판매자에게 얼마" 를 만든다  →  ...  →  지급
```

15일을 기다리는 이유는 그 사이에 환불이 들어올 수 있어서다. 여기까지는 설계대로다.

문제는 배치가 무엇을 고르느냐였다.

```sql
where oi.settlement_eligible_at is not null   -- 구매확정 때 찍히는 날짜
  and oi.settlement_eligible_at <= now()      -- 15일 지났나
  and oi.dealer_user_id is not null           -- 판매자 상품인가
  and not exists (이미 정산 만들었나)
```

읽어보면 그럴듯하다. 나도 처음엔 이상한 데를 못 찾았다.

**빠진 게 하나 있다. "이 주문이 아직 살아 있나"를 안 본다.**

구매확정 때 날짜가 찍히고, 그 뒤에 환불이 되어도 **그 날짜를 지우는 코드가 어디에도 없었다.** 환불 시점에 정산을 회수하는 코드는 있는데, 그건 정산이 **이미 만들어져 있을 때만** 동작한다.

```java
// 환불되면 이걸 부른다
accountRepository.findByOrderItemForUpdate(orderItemId).ifPresent(this::reverse);
//                                                      ~~~~~~~~~ 없으면 아무 일도 안 함
```

그래서 15일이 통째로 빈다.

```
구매확정 → 날짜 찍힘 → 환불 → (회수할 게 아직 없음, 그냥 지나감) → 15일 뒤 배치 → 정산 생성 😱
```

지금은 장부에만 적히고 실제로 돈이 나가지는 않아서 아무도 몰랐다. 실제 지급을 켜는 순간 그대로 나가는 돈이다.

## 고치는 건 한 줄이었다

주문 상품의 지금 상태를 보면 된다.

```sql
  and oi.state in (800, 601, 602, 603, 604)
```

800은 구매확정, 601~604는 교환이다. 교환은 물건을 바꾼 것이지 판매가 취소된 게 아니라서 정산 대상이 맞다.

여기서 한 가지 고민했다. **막을 것을 적을까, 허용할 것을 적을까.**

- 막을 것을 적으면(취소·환불·거절…) 나중에 새로운 취소 상태가 생겼을 때 **조용히 빠져나간다.**
- 허용할 것을 적으면 새 상태가 생겼을 때 **정산이 안 잡힌다.**

둘 다 문제지만 무게가 다르다. 정산이 안 잡히면 "왜 정산이 안 돼요?" 하고 누가 말한다. 잘못 나가면 돈이 이미 나간 뒤다. **돈이 걸린 곳에서는 모르는 건 일단 막는 쪽**으로 정했다.

## 그런데 다른 테스트가 깨졌다

전체 테스트를 돌렸더니 관계없어 보이는 테스트 하나가 실패했다.

```
MultiVendorSettlementServiceIntegrationTest > settlesEachVendorByItsOwnFeeRateAndIsIdempotent

Expected size: 2 but was: 0
```

정산이 2건 생겨야 하는데 0건이 됐다는 뜻이다. 처음엔 내 조건이 너무 빡빡한가 싶었다.

테스트가 데이터를 어떻게 넣는지 봤다.

```java
insert into order_items (..., state, settlement_eligible_at, ...)
values (..., 400, :eligibleAt, ...)
//            ~~~
```

`400`. 아까 그 상태 코드 표를 다시 봤다.

```java
CANCELLED(400),
```

**취소됨.**

이 테스트는 "취소된 상품"을 넣어놓고 "정산이 2건 만들어져야 한다"고 단언하고 있었다. 그리고 지금까지 **통과하고 있었다.** 배치가 상태를 안 봤으니까.

즉 이 테스트는 버그를 잡기는커녕, **버그를 정상 동작으로 굳혀서 지키고 있었다.** 내가 조건을 넣자 "정상이 깨졌다"며 빨간불을 켠 것이다.

아마 처음 쓴 사람은 상태 값에 별 의미를 두지 않았을 것이다. 400이 무슨 뜻인지 안 보고 숫자 하나 채워 넣은 것. 나도 테스트 데이터를 그렇게 채운 적이 많다.

고친 건 테스트 쪽이었다.

```java
values (..., 800, :eligibleAt, ...)   // 구매확정
```

그리고 왜 바꿨는지 주석으로 남겼다. 안 남기면 다음 사람이 "왜 800이지?" 하고 또 아무 숫자로 바꿀 것 같아서.

## 그럼 내 테스트는 믿을 수 있나

여기서 뜨끔했다. 나도 방금 테스트를 두 개 새로 썼다.

```java
@Test
void doesNotAccrueItemsRefundedBeforeTheBatchRuns() { ... }

@Test
void doesNotAccrueCancelledItems() { ... }
```

둘 다 초록불이었다. 그런데 방금 본 것처럼, **초록불은 "내가 의도한 걸 지키고 있다"는 뜻이 아니다.** 조건을 잘못 걸었거나 애초에 아무것도 검사하지 않아도 초록불은 뜬다.

그래서 확인해봤다. 방금 넣은 한 줄을 **도로 빼고** 돌렸다.

```
tests=13 failures=2
 실패: doesNotAccrueItemsRefundedBeforeTheBatchRuns()
 실패: doesNotAccrueCancelledItems()
```

내가 쓴 테스트 두 개가, 정확히 그 둘만 깨졌다. 이제 알겠다.
- 이 테스트는 **실제로 그 한 줄을 지키고 있다**
- 다른 테스트는 이 변경과 무관하다

그리고 조건을 다시 넣었다. 초록불로 돌아왔다.

이 왕복이 30초쯤 걸렸는데, 이걸 안 했으면 나는 그냥 "테스트 썼고 통과했다"고 넘어갔을 것이다. 그리고 그 테스트가 실은 아무것도 안 지키고 있을 가능성을 영영 몰랐을 것이다.

## 배운 것

**통과하는 테스트가 옳은 동작을 지킨다는 보장은 없다.** 잘못된 동작을 정상으로 굳혀놓고 지킬 수도 있다. 오늘 그 실물을 봤다.

**새로 쓴 테스트는 한 번 깨뜨려 보고 믿는다.** 고치기 전 코드로 되돌려서 빨간불이 뜨는지 보는 것. 순서가 중요하다 — 고치고 나서 초록불을 보는 것만으로는 그 테스트가 무엇을 잡는지 알 수 없다. (나중에 알았는데 이걸 TDD에서 "red-green"이라고 부른다더라. 이름은 몰랐지만 필요해서 하게 된 순서가 같았다.)

**테스트가 갑자기 깨지면 내 코드부터 의심하되, 테스트도 용의선상에 둔다.** 오늘은 테스트가 범인이었다. "기존 테스트가 깨졌으니 내 변경이 잘못됐다"고 바로 되돌렸다면 진짜 버그를 그대로 두고 지나갔을 것이다.

**테스트 데이터에 넣는 숫자에도 뜻이 있다.** 상태 코드 400을 "아무 값"으로 쓴 순간, 그 테스트는 취소된 주문을 검증하는 테스트가 되어버렸다. 의미 있는 값을 넣고, 왜 그 값인지 적어두자.

## 남은 것

- 지급이 끝난 뒤에 환불이 들어오는 경우도 화면에 안 뜨고 있었다. 그건 따로 고쳤다.
- 실제 지급은 아직 법적 확인이 남아 있어서 켜지 않았다. 그 전에 이걸 찾아서 다행이다.

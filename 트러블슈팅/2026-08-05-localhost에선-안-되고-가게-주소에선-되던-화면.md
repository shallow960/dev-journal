# 2026-08-05 localhost에선 안 되고 가게 주소에선 되던 화면

> 태그: #트러블슈팅 #멀티테넌시 #보안 #디버깅

## 오늘 한 일 (요약)
- 가게 주인용 관리 화면의 정산 페이지가 개발 주소(localhost)에선 "못 불러왔어요"인데, 실제 가게 주소로 접속하면 잘 떴다.
- 원인은 "지금 어느 가게를 관리하는지(테넌트)"를 정하는 방식이 화면마다 달랐던 것 - 어떤 건 로그인 토큰으로, 어떤 건 접속한 웹주소로.
- 임시 우회 대신 "관리 화면의 테넌트는 토큰으로 정한다"로 정책을 통일하고, 위조 못 하게 서명된 토큰을 근거로 삼았다.

## 무엇을 / 왜 (증상)
여러 가게(테넌트)가 한 시스템을 나눠 쓰는 멀티테넌트 구조다. 요청이 오면 "이 요청이 어느 가게 것인지"를 먼저 정하고, 그 가게 데이터만 보이게 막는다.

이상한 건, 같은 관리 화면인데 접속 주소에 따라 결과가 갈렸다.
- 실제 가게 주소(예: `myshop.example.com`)로 들어가면 정산 화면이 잘 떴다.
- 개발용 `localhost`로 들어가면 정산만 "못 불러왔어요"가 떴다.

더 이상한 건, 같은 localhost에서도 상품 목록과 주문 목록은 잘 왔다는 것이다. 정산만 안 왔다.

## 어떻게 풀었나 - 같은 화면 안의 두 갈래
"상품/주문은 되는데 정산만 안 된다"가 힌트였다. 백엔드에서 이 셋이 테넌트를 정하는 방식을 따라가 보니 갈래가 둘이었다.
- 상품/주문 = 로그인 토큰에 적힌 "내가 고른 가게"로 테넌트를 정함.
- 정산 = 접속한 웹주소(호스트)로 테넌트를 정함.

`localhost`는 특정 가게에 매핑된 주소가 아니다. 그래서 호스트로 테넌트를 정하는 정산만 "여긴 가게 없음"으로 막혔고, 토큰으로 정하는 상품/주문은 멀쩡했던 것이다.

여기서 "그럼 개발도 가게 주소로 접속해"로 넘길 수도 있었다. 하지만 그러면 가게마다 관리자 주소가 따로 생긴다. 관리 화면은 한 곳(플랫폼 주소)에서 열리는 게 맞다. 그래서 코드를 급히 맞추기 전에 정책부터 정했다.

> 관리 화면은 하나의 플랫폼 주소에서 연다. "어느 가게냐"는 접속 주소가 아니라 로그인 토큰으로 정한다.

이 정책대로 정산 쪽 테넌트 판별을 토큰 기준으로 바꿨다. 핵심은 보안이었다. 토큰 안의 가게 정보는 서버가 서명해 둔 값이라 손댈 수 없다. 그래서 "주소만 바꿔서 남의 가게를 관리"하려는 시도가 원천 차단된다(주소는 위조해도 토큰 서명은 못 만드니까).

## 코드로 보기 (개념 재현)
```
// (기존) 화면마다 테넌트를 정하는 방식이 달랐다
//   상품/주문: 토큰에서   ->  resolveTenantFromToken(req)
//   정산     : 호스트에서 ->  resolveTenantFromHost(req)   // localhost엔 매핑 없음 -> 실패

// (수정) 관리 화면은 전부 "토큰의 서명된 가게 id"로 통일
function resolveTenantForAdmin(req) {
  const claims = verifySignedToken(req.token);  // 서명 검증 = 위조 불가
  if (!claims.tenantId) throw new Unauthorized();
  return claims.tenantId;                        // 접속 주소는 안 본다
}

// 정한 테넌트로 행수준 보안 세션을 건다 (그 가게 데이터만 보이게)
setCurrentTenant(resolveTenantForAdmin(req));
```
호스트는 사용자가 바꿔 보낼 수 있지만, 서명된 토큰의 가게 id는 못 바꾼다. 그래서 "무엇으로 테넌트를 정하느냐"는 기능 문제이자 보안 문제였다.

## 💡 배운 것
- **"여기선 되고 저기선 안 된다"는 같은 화면 안에서도 데이터별로 갈릴 수 있다.** 상품/주문은 되고 정산만 안 되던 게, 셋이 서로 다른 방식으로 테넌트를 정하고 있다는 결정적 단서였다.
- **증상을 임시로 우회(가게 주소로 접속)하기 전에, 그 뒤의 정책부터 정해야 한다.** 정책이 서면 코드는 거기 맞추면 된다.
- **"무엇으로 신원을 정하느냐"는 보안 결정이다.** 사용자가 바꿀 수 있는 값(호스트)이 아니라 서버가 서명한 값(토큰)으로 정해야 위조가 막힌다.
- **헷갈리는 이름은 실체에 맞춰 바꿔야 다음에 안 헷갈린다.** 방식을 통일하면서 코드 안 주소 이름도 실제 역할에 맞게 정리했다.

## 소감
처음엔 "localhost라서 뭔가 환경 문제겠지" 하고 넘길 뻔했다. 그런데 같은 localhost에서 상품은 되고 정산만 안 되는 걸 보고 "환경이 아니라 코드가 데이터마다 다르게 굴고 있다"로 방향을 틀었다. 결국 버그 하나가 아니라 "테넌트를 무엇으로 정할 것인가"라는 정책 구멍이었고, 그걸 메우는 김에 보안(호스트 위조 차단)까지 단단해졌다. 급하게 우회하지 않고 정책을 먼저 정한 게 옳았다.

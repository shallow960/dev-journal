# 2026-10-30 카드는 승인됐는데, 저장이 실패하면 손님 돈만 빠지고 주문은 취소됐다

> 태그: #트러블슈팅 #결제 #망취소 #트랜잭션 #Spring

## 무엇을 / 왜

쇼핑몰 결제는 이런 순서로 처리되고 있었습니다.

```
결제창 → 결제사 카드 승인 → 우리 서버로 돌아옴 → 금액 확인 → 결제 완료 저장(결제·주문 상태) → 결제 완료 사건 처리
```

결제사가 승인한 뒤 우리 쪽 저장 단계에서 오류가 나면(예를 들어 결제 완료 사건을 처리하는 쪽이 실패하면) 트랜잭션이 통째로 되돌려졌습니다. 그러면 손님 카드에서는 돈이 빠졌는데, 우리 기록에서는 아직 결제가 끝나지 않은 주문으로 남았습니다. 결제를 기다리는 주문은 15분이 지나면 자동으로 취소되니, 손님은 돈만 빠지고 주문은 취소된 셈이었습니다.

결제사 승인을 바로 되돌리는 망취소는 이미 만들어 두었지만, 결제 금액이 주문 금액과 다를 때만 쓰고 있었습니다.

## 어떻게 풀었나

### 저장이 실패하면 승인도 되돌렸습니다

승인을 받은 다음 저장하는 부분을 감싸서, 어떤 오류가 나든 결제사에 망취소를 보내게 했습니다. 결제창에서 돌아오는 길과, 주문하면서 결제사가 바로 승인하는 길 두 군데를 모두 같게 했습니다. 손님에게는 망취소 결과에 따라 다른 문구를 보였습니다.

- 망취소가 됐으면: "결제를 마치지 못해 카드 승인을 바로 취소했어요. 다시 주문해 주세요."
- 망취소까지 실패했으면: "결제를 마치지 못했어요. 카드가 결제됐다면 쇼핑몰에 문의해 주세요."

### 망취소 기록이 사라지지 않게 했습니다

망취소를 한 뒤에는 원래 오류를 다시 던져 저장을 되돌렸습니다. 그런데 망취소 기록도 같은 트랜잭션 안에 쓰고 있어서, 저장과 함께 되돌려졌습니다. 살펴보니 금액이 다를 때의 망취소 기록도 같은 이유로 남지 않고 있었습니다. 되돌려지는 일을 남기는 기록이 그 되돌림에 함께 쓸려 가고 있었던 것이었습니다.

그래서 이 기록은 트랜잭션이 끝난 뒤(커밋이든 롤백이든) 새 트랜잭션으로 따로 쓰게 했습니다. 처음에는 처리 중에 바로 새 트랜잭션으로 쓰려 했는데, 그러면 처리가 멈췄습니다. 그 이야기는 따로 정리했습니다.

## 코드로 보기 (개념 재현)

```java
// 결제창에서 돌아왔을 때 (개념 재현 - 실제 이름과 다름)
@Transactional
public Payment onPaymentReturn(UUID paymentId, Map<String, String> callback) {
    Payment payment = payments.lock(paymentId);
    PgResult result = gateway.confirm(payment, callback);   // 결제사 승인 - 손님 카드에서는 이미 빠졌다
    try {
        return markPaid(payment, result);                    // 결제·주문 상태 저장, 결제 완료 사건 처리
    } catch (RuntimeException ex) {
        // 우리 쪽 저장이 실패했다 - 결제사 승인도 되돌린다.
        // 안 그러면 돈만 빠지고 주문은 15분 뒤 자동 취소된다.
        boolean cancelled = networkCancel(payment, result);
        throw new PaymentNotCompleted(cancelled
            ? "결제를 마치지 못해 카드 승인을 바로 취소했어요. 다시 주문해 주세요."
            : "결제를 마치지 못했어요. 카드가 결제됐다면 쇼핑몰에 문의해 주세요.", ex);
    }
}

private boolean networkCancel(Payment payment, PgResult result) {
    CancelResult cancel = gateway.cancelWhole(payment, result);   // 승인 전체 취소
    // 기록은 이 트랜잭션이 끝난 뒤 따로 쓴다 - 지금 쓰면 위의 throw 로 함께 되돌려진다.
    afterCompletion(() -> newTransaction(() -> cancelLogs.save(cancel)));
    return cancel.succeeded();
}
```

```java
// 트랜잭션이 끝난 뒤(커밋이든 롤백이든) 실행한다 (개념 재현)
static void afterCompletion(Runnable task) {
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override
        public void afterCompletion(int status) {
            try {
                task.run();
            } catch (RuntimeException ex) {
                log.error("망취소 기록을 남기지 못했습니다", ex);   // 결과는 이미 정해졌다 - 던지지 않는다
            }
        }
    });
}
```

## 💡 배운 것

- 결제사에 다녀온 뒤의 실패는 우리 데이터베이스를 되돌리는 것으로 끝나지 않았습니다. 돈은 결제사 쪽에서 이미 움직였기 때문에, 우리 쪽이 되돌려지면 결제사 쪽도 되돌려야 했습니다.
- 되돌려질 수 있는 트랜잭션 안에 쓴 기록은 증거로 남지 않았습니다. 되돌려지는 일 자체를 남기는 기록은 그 트랜잭션이 끝난 뒤에 써야 했습니다.
- 망취소까지 실패할 수 있어서, 손님에게 보이는 문구도 두 가지로 나눴습니다.

## 소감

금액이 다를 때의 망취소를 만들어 두고 이 부분은 다 됐다고 생각했습니다. 그런데 "승인 뒤에 실패할 수 있는 곳"을 처음부터 다시 따라가 보니, 금액 확인은 그 가운데 하나였을 뿐이었습니다. 외부에서 돈이 움직인 뒤의 실패는 하나씩 따져 봐야겠다고 느꼈습니다.

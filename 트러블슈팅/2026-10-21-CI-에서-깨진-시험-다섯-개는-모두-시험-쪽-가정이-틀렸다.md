# 2026-10-21 CI 에서 깨진 시험 다섯 개는, 모두 시험 쪽 가정이 틀렸다

> 태그: #트러블슈팅 #테스트 #CI #PostgreSQL #JUnit

## 무엇을 / 왜

이 프로젝트는 푸시하면 CI 가 백엔드 시험 2,000건 정도를 모두 돌린 뒤에야 배포해요. 하루에 두 번 파이프라인이 시험 실패로 멈췄습니다. 처음엔 1건, 두 번째엔 4건이었고, 다섯 건 모두 그날 새로 쓴 시험이었어요. 기능 코드는 맞았고, 틀린 건 시험이 깔고 있던 가정이었습니다.

## 어떻게 풀었나

### 1. 같은 시각에 저장된 행에는, 정해진 순서가 없다

새 주문 알림 메일에는 "상품A 1개 외 1건"처럼 첫 상품 이름이 들어가요. 시험은 셀러 상품과 주인 상품을 한 주문에 넣고 "셀러 상품 1개 외 1건"을 기대했습니다.

그런데 한 주문의 상품들은 한 트랜잭션에서 저장되고, 저장 시각은 `now()` 로 채워요. PostgreSQL 의 `now()` 는 **트랜잭션이 시작된 시각**이라, 같은 트랜잭션 안의 행은 시각이 완전히 같습니다. 목록은 "저장 시각, 그다음 id" 순으로 읽는데 id 가 무작위 UUID 라, 어느 상품이 먼저 나올지는 그때그때 달랐어요. 로컬에서는 두 번 연속 운 좋게 통과했고, CI 에서 처음 반대로 나왔습니다.

메일에는 "아무 상품이나 하나 + 외 N건"이면 충분해서, 시험이 둘 중 하나를 받아들이게 바꿨어요. 순서가 중요한 화면이었다면 순서를 정하는 열을 따로 둬야 했을 거예요.

### 2. BigDecimal 의 equals 는 자리수까지 본다

가격 보호 금액이 10,000원인지 보는 시험 두 개가 실패했어요. 기대값은 `new BigDecimal("10000")` 이었고, DB 의 금액 열은 소수 둘째 자리까지라 돌아온 값은 `10000.00` 이었습니다. `BigDecimal.equals` 는 값뿐 아니라 **자리수(scale)** 까지 같아야 참이라, 둘은 다른 값이었어요. 값만 비교하는 `compareTo`(AssertJ 의 `isEqualByComparingTo`)로 바꿨습니다.

### 3. 외래 키는 시험 데이터에도 걸린다

운영자 환불 기록 시험 두 개는, 쇼핑몰 주인 멤버십을 만들면서 멤버십이 가리키는 회원 행 없이 임의의 id 를 넣었어요. 멤버십의 회원 id 는 회원 표를 가리키는 외래 키라 넣는 순간 실패했습니다. 회원 행을 먼저 만들게 고쳤어요.

### 4. 덤: 클래스 단위로 공유되는 시험 인스턴스

같은 시험 클래스를 보다가 하나 더 고쳤어요. 이 프로젝트의 통합 시험은 비싼 준비를 아끼려고 시험 인스턴스를 클래스마다 하나만 만듭니다(JUnit 의 PER_CLASS). 그러면 필드에 둔 가짜 메일 발송기가 시험 메서드 사이에서 비워지지 않아, 앞 시험의 메일이 다음 시험의 "메일 1통" 확인을 깨뜨릴 수 있어요. 같은 날 다른 시험 클래스에서 이 문제로 로컬 실패가 한 번 났었기 때문에, 여기서도 시험마다 비우게 했습니다.

## 코드로 보기 (개념 재현)

```sql
-- 왜 순서가 정해지지 않나: now() 는 트랜잭션이 시작된 시각이다
begin;
insert into items (id, order_id, name, created_at) values (gen_random_uuid(), :orderId, '셀러 상품', now());
insert into items (id, order_id, name, created_at) values (gen_random_uuid(), :orderId, '주인 상품', now());
commit;

-- 두 행의 created_at 이 같다 -> 결과 순서는 무작위 id 에 달렸다
select name from items where order_id = :orderId order by created_at, id;
```

```java
// 1. 순서에 기대지 않기
// 전: 같은 트랜잭션에서 저장한 두 상품 중 '셀러 상품'이 먼저라고 못 박았다
assertThat(mail.body()).contains("셀러 상품 1개 외 1건");
// 후: 둘 중 하나 + '외 1건'이면 통과
assertThat(mail.body()).containsPattern("(셀러 상품|주인 상품) 1개 외 1건");
```

```java
// 2. BigDecimal 은 값으로 비교
BigDecimal fromDb = new BigDecimal("10000.00");
fromDb.equals(new BigDecimal("10000"));          // false - scale 2 와 scale 0
fromDb.compareTo(new BigDecimal("10000")) == 0;  // true

// 전: Optional.contains 는 안에서 equals 를 쓴다
assertThat(guard.protectedAmount(subscription)).contains(new BigDecimal("10000"));
// 후: 값만 비교
assertThat(guard.protectedAmount(subscription))
    .hasValueSatisfying(amount -> assertThat(amount).isEqualByComparingTo("10000"));
```

```java
// 4. 인스턴스를 공유하는 시험은 상태를 시험마다 비운다
@TestInstance(TestInstance.Lifecycle.PER_CLASS)
class RefundRecordTest {
    private final CapturingMailer mailer = new CapturingMailer();

    @BeforeEach
    void reset() {
        mailer.sent.clear(); // 앞 시험의 메일이 남지 않게
    }
}
```

## 💡 배운 것

**"로컬에서 통과했다"는 한 번 뽑은 결과일 수 있습니다.** 정해지지 않은 순서에 기대는 시험은 대부분 통과하다가 가끔 깨져요. `now()` 처럼 트랜잭션 안에서 같은 값을 돌려주는 함수는 순서를 정해 주지 못합니다.

**금액 비교는 equals 가 아니라 compareTo 로.** DB 금액 열은 정해진 자리수로 돌아오니, 시험 기대값과 자리수가 다르기 쉬워요.

**시험 데이터도 실제 제약을 지켜야 합니다.** 외래 키를 피하려고 임의 id 를 넣으면, 그 시험은 실제로는 일어날 수 없는 상태를 시험하는 셈이에요.

**새로 쓴 시험은 푸시 전에 한 번은 돌린다.** 두 번째 실패 4건은 로컬 전체 시험이 그 클래스까지 가기 전에 먼저 푸시한 것이었어요. 전체 시험은 CI 에 맡기더라도, 새 시험 클래스만큼은 먼저 돌려 보기로 했습니다.

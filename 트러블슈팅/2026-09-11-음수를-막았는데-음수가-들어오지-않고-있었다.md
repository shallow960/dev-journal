# 2026-09-11 음수를 막았는데, 음수가 애초에 들어오지 않고 있었다

> 태그: #트러블슈팅 #입력검증 #테스트 #조용한실패

## 무엇을 / 왜

매표소에서 **음수 금액으로 표가 발권된다**는 제보를 받았습니다. 현금 금액은 숫자인지만 보고 있었고, 할인율이 100 을 넘으면 판매가가 음수가 됐습니다.

카드·현금·할인율 모두에 범위 검사를 넣고 다시 시험했습니다. 할인율 `101` 은 막혔습니다. 그런데 **`-55` 와 `-99` 는 통과해서 55%, 99% 할인이 걸렸습니다.**

## 어떻게 풀었나

### 가드가 틀린 줄 알았는데, 가드는 맞았다

검사 코드를 다시 봤는데 음수를 제대로 거르고 있었습니다. 그래서 가드에 **실제로 무엇이 도착하는지** 찍어 봤습니다.

`55` 가 도착하고 있었습니다.

할인율 칸이 숫자만 받도록 되어 있어서, **`-` 를 치면 조용히 버리고** 있었습니다. 화면에는 `-55` 를 친 것 같지만 칸에는 `55` 가 들어갔고, 가드는 정상 범위로 보고 통과시켰습니다.

막히지 않은 게 아니라 **음수가 입력되지 않은** 것이었습니다.

### 같은 병이 다른 화면에도 있었다

같은 날 관리 웹 가격 칸에서도 똑같은 것을 찾았습니다. 숫자 아닌 글자를 지우는 칸이라 `-5000` 을 넣으면 **경고 없이 5,000원으로 저장**됐습니다.

이쪽이 더 위험했습니다. 매표소는 할인율이 조금 달라지는 정도지만, 가격 칸은 **틀린 값이 그대로 저장되고 아무도 모릅니다.**

### 조용히 고치지 말고, 이유를 보여 주고 멈춘다

- 입력칸이 `-` 를 **그대로 받아 칸에 보이게** 했습니다
- 저장이나 결제를 누르면 "음수는 입력할 수 없습니다" 처럼 **이유를 띄우고 멈춥니다**
- 서버에서도 음수 금액과 1원 미만 가격을 한 번 더 거절합니다

## 코드로 보기 (개념 재현)

문제가 됐던 입력칸입니다.

```jsx
// 숫자만 남긴다. 사용자를 "도와주는" 필터처럼 보인다.
<input
  inputMode="numeric"
  onChange={(e) => setPrice(e.target.value.replace(/[^0-9]/g, ""))}
/>
// 사용자가 "-5000" 을 친다 → 칸에는 "5000" → 저장 → 성공
// ★ 틀린 입력이 에러 없이 "다른 올바른 값" 으로 바뀌었다.
```

가드는 맞게 짜여 있었습니다. 문제는 가드 앞에서 값이 이미 바뀌었다는 것입니다.

```js
function validateDiscount(rate) {
  if (rate < 0 || rate > 100) return "할인율은 0~100 사이여야 합니다";
  return null;
}

validateDiscount(55);   // null → 통과. 사용자가 친 건 -55 였다.
```

고친 입력칸입니다. `-` 는 남기고, 판단은 한 곳에서 이유와 함께 합니다.

```jsx
// 판단 규칙은 여기 한 곳. 화면 여러 곳이 같은 함수를 쓴다.
function priceProblem(raw) {
  const text = String(raw ?? "").trim();
  if (text === "")          return "가격을 입력해 주세요.";
  if (text.includes("-"))   return "음수는 입력할 수 없습니다.";
  if (!/^\d+$/.test(text))  return "숫자만 입력할 수 있습니다.";
  if (Number(text) < 1)     return "1원 이상이어야 합니다.";
  return null;
}

<input
  inputMode="numeric"
  // '-' 는 지우지 않는다. 지우면 -5000 이 5000 으로 저장된다.
  onChange={(e) => setPrice(e.target.value.replace(/[^0-9-]/g, ""))}
/>
{priceProblem(price) && <small className="error">{priceProblem(price)}</small>}
```

서버는 화면을 믿지 않고 한 번 더 봅니다.

```js
function assertPrice(value) {
  const n = Number(value);
  if (!Number.isInteger(n) || n < 1) {
    throw new BadRequest("가격은 1원 이상의 정수여야 합니다");
  }
}
```

## 💡 배운 것

**입력을 "고쳐 주는" 필터는 문제를 숨깁니다.** 숫자만 남기는 필터는 친절해 보이지만, 틀린 입력을 다른 올바른 값으로 바꿔 버립니다. 에러가 없으니 사용자도, 시험하는 사람도 모릅니다.

**가드를 시험할 때는 그 값이 가드까지 도착하는지부터 봐야 합니다.** `-55` 를 넣고 통과하는 걸 보고 가드를 의심했는데, 가드는 `-55` 를 받은 적이 없었습니다. 입력한 값과 검사받은 값이 같은지 확인하지 않으면 엉뚱한 곳을 고치게 됩니다.

**조용히 바꾸지 말고 이유를 보여 주고 멈춰야 합니다.** 사용자가 틀린 값을 넣었으면 그 사실을 알아야 다시 넣을 수 있습니다.

**화면과 서버 두 겹으로 막습니다.** 화면 검사는 사용자를 돕는 것이고, 서버 검사는 데이터를 지키는 것입니다. 역할이 달라서 둘 다 필요했습니다.

## 소감

"음수를 막아라" 는 한 줄짜리 일인 줄 알았는데, 고친 뒤 시험에서 **통과하면 안 되는 값이 통과**하는 걸 보고 멈췄습니다.

만약 `-55` 대신 `101` 만 시험하고 끝냈으면 "막았다" 고 보고했을 겁니다. 경계값을 여러 방향으로 넣어 보는 게 왜 필요한지, 그리고 "통과했다" 를 볼 때 무엇이 통과했는지까지 봐야 한다는 걸 알았습니다.

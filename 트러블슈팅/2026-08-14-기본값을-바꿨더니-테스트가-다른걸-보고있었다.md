# 2026-08-14 기본값을 바꿨더니 테스트가 다른 걸 보고 있었다

> 태그: #트러블슈팅 #테스트 #기본값

## 무엇을 / 왜

"잔액이 0이 되어도 진행 중인 작업은 잠시 더 허용한다"는 완충 기능을 만들었습니다. 처음엔 안전하게 **기본값을 0(완충 없음)** 으로 두고 넣었고, 별도 안전장치를 붙인 뒤에 기본값을 켰습니다.

기본값을 켠 순간, 멀쩡하던 테스트 세 개가 깨졌습니다.

```
expected: 20  but was: 25
expected: 0   but was: -20.000
expected: 8   but was: 100
```

숫자만 보면 원인은 명확합니다. 완충이 생겨서 잔액이 0 아래로 더 내려가고, 그만큼 더 차감된 겁니다. 첫 반응은 **"기대값만 새 숫자로 고치면 되겠다"**였어요.

## 어떻게 풀었나

고치기 전에 그 테스트들이 원래 무엇을 보던 건지 읽어봤습니다.

세 개 다 **"잔액이 0이 되면 멈춘다"**를 검증하고 있었습니다. 0에서 정확히 멈추는지, 그때 "소진됨" 신호가 뜨는지, 그 뒤로는 한 푼도 안 나가는지.

여기서 문제가 보였습니다. **기대값을 새 숫자로 바꾸면, 그 규칙을 더 이상 아무도 검증하지 않게 됩니다.** 완충 상태의 동작을 검증하는 테스트로 조용히 바뀌는 거죠. 그런데 완충 동작은 이미 별도 테스트가 있었습니다. 결국 같은 걸 두 번 보고, 원래 규칙은 아무도 안 보게 됩니다.

그래서 기대값이 아니라 **입력**을 고쳤습니다. 각 테스트가 시작할 때 완충을 **명시적으로 끄도록** 했습니다.

```java
/**
 * 완충을 명시적으로 끈다.
 *
 * 이 테스트가 보려는 건 "잔액이 0이 되면 멈춘다"는 하드 스톱이다.
 * 기본값이 바뀌면(0 → 켜짐) 조용히 다른 걸 검증하게 되므로
 * 기본값에 기대지 않고 못박는다.
 */
private void 완충끄기(가게ID) {
    upsert("완충한도", 가게ID, 0);
}
```

```java
@Test
void 잔액이_0이_되면_멈춘다() {
    var 가게 = 가게만들기("hard-stop");
    완충끄기(가게);              // ← 추가. 기본값이 무엇이든 이 테스트는 같은 걸 본다
    잔액충전(가게, 100);
    ...
}
```

## 더 무서운 쪽

이번엔 깨져서 알아챘습니다. 그런데 만약 **완충 한도가 충분히 컸다면** 어떻게 됐을까요.

- 원래 테스트: 100을 채우고 200을 쓰면 → 100만 나가고 소진, 잔액 0
- 완충이 크면: 200이 다 나가고 잔액 -100, **소진 판정이 아예 안 남**

이 경우 `차감량`이 200이 되고 `소진됨`이 거짓이 됩니다. 단언이 그 둘을 다 보고 있었다면 깨지지만, **잔액만 보고 있었다면** 어땠을까요. 숫자에 따라서는 **깨지지 않고 그냥 통과**할 수도 있습니다.

깨지는 건 알려주기라도 합니다. **조용히 통과하면서 다른 걸 보는 쪽이 훨씬 위험합니다.** 초록불은 그대로인데 지키던 규칙은 사라진 상태니까요.

## 코드로 보기 (개념 재현)

같은 함정을 만드는 최소 예시입니다.

```java
// 전역 기본값
static int 기본_완충 = 0;

int 차감(계정 a, int 요청) {
    int 바닥 = -a.완충한도;                 // 완충이 0이면 바닥도 0
    int 가능 = a.잔액 - 바닥;
    int 차감량 = Math.min(가능, 요청);
    a.잔액 -= 차감량;
    return 차감량;
}

@Test
void 기본값에_기대는_테스트() {
    var a = 새계정();                        // 완충 = 기본값
    a.잔액 = 100;
    assertThat(차감(a, 200)).isEqualTo(100);  // 기본값 0일 때만 참
}

@Test
void 기본값에_기대지_않는_테스트() {
    var a = 새계정();
    a.완충한도 = 0;                          // ← 이 테스트가 보려는 조건을 명시
    a.잔액 = 100;
    assertThat(차감(a, 200)).isEqualTo(100);  // 기본값이 바뀌어도 같은 걸 본다
}
```

두 테스트는 지금 똑같이 통과합니다. 차이는 `기본_완충`을 바꿨을 때 드러납니다.

## 💡 배운 것

- **테스트가 깨졌을 때 기대값부터 고치지 않는다.** 먼저 "이 테스트가 지키려던 규칙이 무엇인가"를 읽습니다. 규칙이 여전히 유효하면 고칠 건 기대값이 아니라 입력입니다.
- **테스트는 전역 기본값에 기대지 않는다.** 검증에 필요한 조건은 그 테스트 안에서 명시합니다. 조금 장황해져도, 기본값이 바뀔 때 조용히 의미가 달라지는 것보다 낫습니다.
- **깨지는 실패보다 조용히 통과하는 변질이 위험하다.** 기본값·설정·환경이 바뀌면 "여전히 통과하지만 다른 걸 보는" 테스트가 생길 수 있습니다.
- 기본값을 바꿀 때는 **그 기본값을 전제로 쓰인 코드와 테스트를 같이 훑는 것**이 작업의 일부입니다.

## 소감

전날에도 비슷한 걸 겪었습니다. 그때는 테스트가 잘못된 입력으로 버그를 보증하고 있었고, 이번엔 기본값이 바뀌면서 테스트가 원래 보던 걸 안 보게 됐습니다. 방향은 다른데 결론은 같더군요. **초록불은 "무엇을" 통과했는지까지 말해주지 않습니다.**

그래서 테스트를 쓸 때 습관 하나를 더했습니다. 검증에 필요한 조건은 **그 자리에 적어두기.** 기본값이라 안 적어도 되는 상황이어도요. 나중에 그 기본값을 바꾸는 사람에게 남기는 메모이기도 하니까요.

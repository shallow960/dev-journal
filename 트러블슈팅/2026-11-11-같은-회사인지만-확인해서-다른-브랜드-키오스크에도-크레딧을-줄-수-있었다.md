# 2026-11-11 같은 회사인지만 확인해서, 다른 브랜드 키오스크에도 크레딧을 줄 수 있었다

> 태그: #트러블슈팅 #권한 #멀티테넌트 #보안 #Java

## 무엇을 / 왜

사진 키오스크 플랫폼에서는 한 회사(테넌트)가 브랜드를 여러 개 가질 수 있었습니다. 브랜드마다 본사가 있고, 그 아래로 총판 → 대리점 → 매장 → 키오스크가 이어졌습니다. 키오스크는 인쇄할 때마다 '크레딧' 을 썼고, 본사와 본사가 권한을 준 매니저는 자기 브랜드 키오스크에 크레딧을 주거나 뺄 수 있었습니다.

새 기능 묶음을 올리기 전 교차 검토에서 이런 지적이 나왔습니다. A 브랜드가 권한을 준 매니저가 B 브랜드 키오스크 번호를 넣으면, B 키오스크의 크레딧을 주거나 뺄 수 있다는 것이었습니다. 지금은 회사마다 브랜드가 하나뿐이라 실제로 일어난 적은 없었지만, 크레딧은 돈처럼 쓰이는 값이라 그대로 둘 수 없었습니다.

## 어떻게 풀었나

서버 검사를 보니 "이 키오스크가 요청한 사람과 같은 회사인가" 만 묻고 있었습니다. 같은 회사 안에서 브랜드가 다른 경우는 따로 보지 않았습니다. 지금까지는 회사마다 브랜드가 하나라서 "같은 회사 = 같은 브랜드" 였고, 그래서 드러나지 않았던 것입니다.

고친 내용은 네 가지였습니다.

1. **요청한 사람의 브랜드 범위를 먼저 정했습니다.** 본사 계정과 그 본사가 권한을 준 매니저는 그 본사의 브랜드 하나, 브랜드 주소로 들어온 회사 소유자는 그 브랜드 하나, 플랫폼 콘솔로 들어온 회사 소유자는 회사의 모든 브랜드로 봤습니다.
2. **키오스크의 브랜드는 서버 데이터로 소속을 따라가 정했습니다.** 키오스크 → 매장 → 대리점 → 총판 → 본사로 올라가 그 본사의 브랜드를 봤습니다. 화면이 보낸 값은 쓰지 않았습니다.
3. **다른 브랜드면 '없는 키오스크' 와 같은 답을 줬습니다.** 403(권한 없음)이 아니라 404(없음)로 답해서, 다른 브랜드에 그 번호의 키오스크가 있다는 사실도 드러나지 않게 했습니다.
4. **브랜드를 알 수 없으면 거절했습니다.** 소속이 중간에 끊겨 브랜드를 정할 수 없으면, 허용하지 않고 409 로 멈췄습니다.

크레딧 코드도 같은 방식으로, 코드를 발행한 조직의 소속을 따라가 브랜드를 정했습니다. 그리고 같은 모양의 구멍(회사만 비교)이 같은 묶음의 키오스크 설정 조회·저장 경로에도 있어서 함께 막았습니다.

확인은 한 회사에 브랜드를 둘 만든 시험으로 했습니다. 각 계정이 자기 브랜드는 그대로 다루고, 다른 브랜드에 보낸 요청은 모두 거절되는지 봤습니다. 브랜드를 하나만 두는 시험이었다면 고치기 전에도 통과했을 시험이었습니다.

## 코드로 보기 (개념 재현)

이름은 모두 바꾼 더미이고, 구조만 옮겼습니다.

```java
// 고치기 전: 같은 회사인지만 본다
void requireSameCompany(Caller caller, long boothId) {
    Booth booth = booths.find(boothId).orElseThrow(NotFound::new);
    if (booth.companyId() != caller.companyId()) throw new NotFound();
    // 같은 회사의 다른 브랜드 키오스크는 여기를 그냥 통과한다
}

// 고친 뒤: 키오스크의 브랜드를 소속을 따라 정하고, 요청한 사람의 브랜드 범위와 비교한다
void requireSameBrand(Caller caller, long boothId) {
    Booth booth = booths.find(boothId).orElseThrow(NotFound::new);
    if (booth.companyId() != caller.companyId()) throw new NotFound();

    // 키오스크 -> 매장 -> 대리점 -> 총판 -> 본사 -> 브랜드 (서버 데이터로만 따라간다)
    Optional<Long> brand = lineage.brandOfBooth(boothId);
    if (brand.isEmpty()) {
        throw new Conflict("키오스크의 브랜드를 확인할 수 없어 처리하지 않았습니다"); // 모르면 막는다
    }

    // 본사·매니저 = {자기 브랜드}, 플랫폼 콘솔의 회사 소유자 = {회사의 모든 브랜드}
    Set<Long> allowed = caller.allowedBrands();
    if (!allowed.contains(brand.get())) throw new NotFound(); // 다른 브랜드는 '없는 키오스크' 와 같은 답
}
```

```text
한 회사에 브랜드 A, B 가 있을 때 (예)
- A 매니저 -> A 키오스크에 크레딧 부여 : 고치기 전 처리 / 고친 뒤 처리
- A 매니저 -> B 키오스크에 크레딧 부여 : 고치기 전 처리 / 고친 뒤 404
- 소속이 끊긴 키오스크에 부여           : 고치기 전 처리 / 고친 뒤 409
```

## 💡 배운 것

- "같은 회사인가" 와 "같은 브랜드인가" 는 다른 질문이었습니다. 위 단위가 맞는다고 아래 단위까지 맞는 건 아니라는 걸 배웠습니다.
- 소속은 화면이 보낸 값이 아니라 서버 데이터를 따라가 정하고, 알 수 없을 때는 거절하는 쪽(fail-closed)으로 두는 게 안전했습니다.
- 다른 브랜드의 것을 403 이 아니라 404 로 답하면, 남의 키오스크 번호가 있는지조차 알 수 없게 된다는 걸 배웠습니다.
- 브랜드가 하나뿐인 데이터로 돌린 시험은 이 빈틈을 잡지 못했습니다. 막아야 할 대상이 시험 데이터에 없으면 시험은 그냥 통과한다는 걸 [2026-11-03 글](2026-11-03-조회-전용에게-안-보인다는-시험이-숨길-자료가-없어서-통과하고-있었다.md)에 이어 다시 배웠습니다.

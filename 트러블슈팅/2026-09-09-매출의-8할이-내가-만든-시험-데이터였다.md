# 2026-09-09 매출의 8할이 내가 만든 시험 데이터였다

> 태그: #트러블슈팅 #테스트데이터 #데이터정합성 #뒷정리

## 무엇을 / 왜

대기 전광판을 확인하다 모르는 번호가 떠 있는 걸 봤습니다.

확인해 보니 제가 검증용으로 돌린 스크립트가 만든 예약 9건이 대기열에 그대로 남아 있었습니다. 치우려고 데이터를 들여다보다가 더 큰 걸 봤습니다.

## 어떻게 풀었나

### 예약은 지워졌는데 결제만 남아 있었다

**예약이 없는 결제 기록이 38건, 95만원**이 있었습니다.

결제 목록 조회가 예약과 결제를 바깥 조인으로 묶고 있어서, 예약이 사라져도 결제는 그대로 잡힙니다. 그게 전부 매출로 계산되고 있었어요.

그날 카드 단말로 실제 승인이 오간 건(제 카드로 한 시험 결제)은 22만6천원이었습니다. **매출 화면에 뜬 금액의 8할이 스크립트가 만든 데이터**였던 셈입니다.

### 원인은 뒷정리 스크립트였다

검증 스크립트 넷을 열어 보니 전부 **예약만 지우고 결제 원장을 남기고** 있었습니다. 한 스크립트는 뒷정리가 아예 없었고요.

만드는 코드는 신경 써서 짰는데 치우는 코드는 대충 짠 것이었습니다.

### 지우는 순서가 있었다

넷을 고치면서 순서를 못 박아야 했습니다.

- 예약이 결제를 참조하고 있어서 **결제를 먼저 지우면 막힙니다**
- 그런데 예약을 지운 뒤에는 **결제 식별자를 찾을 수 없습니다**

그래서 지우기 전에 결제 식별자를 미리 읽어 두고, `동의기록 → 예약 → 결제원장` 순으로 지우게 했습니다.

### 고친 뒤 다시 만들고 지워 봤다

스크립트를 고쳤다고 끝이 아니라, 넷으로 예약 21건을 만들고 지워 봤습니다. 주인 없는 결제가 늘지 않는 걸 확인하고서야 마무리했습니다.

남아 있던 38건은 전부 검증용 표식이 붙어 있어서 실제 결제와 구분해 정리했습니다.

## 코드로 보기 (개념 재현)

문제가 됐던 조회입니다. 결제를 기준으로 예약을 바깥 조인하니, 예약이 사라져도 결제가 남습니다.

```sql
-- 매출 집계. 예약이 지워져도 결제는 그대로 잡힌다.
SELECT p.id, p.amount, r.status
  FROM payment p
  LEFT JOIN reservation r ON r.payment_id = p.id
 WHERE p.paid_at >= :from;
```

조회 자체는 틀리지 않았습니다. 결제만 있고 예약이 없는 상태가 **원래 생기면 안 되는 상태**였던 거죠. 그래서 조회를 고치는 대신 그 상태를 만들지 않기로 했습니다.

뒷정리 스크립트입니다.

```js
// 문제: 예약만 지운다. 결제 원장은 그대로 남는다.
await db.reservation.deleteMany({ where: { id: { in: ids } } });
```

```js
// 고침: 지우기 전에 결제 식별자를 미리 읽는다.
//       예약을 지운 뒤에는 payment_id 를 찾을 방법이 없다.
const rows = await db.reservation.findMany({
  where: { id: { in: ids } },
  select: { id: true, paymentId: true }
});
const paymentIds = rows.map((r) => r.paymentId).filter(Boolean);

// 참조 관계 때문에 순서가 정해져 있다.
// 예약이 결제를 참조하므로 결제를 먼저 지우면 외래키에 막힌다.
await db.consentLog.deleteMany({ where: { reservationId: { in: ids } } });
await db.reservation.deleteMany({ where: { id: { in: ids } } });
await db.payment.deleteMany({ where: { id: { in: paymentIds } } });
```

## 💡 배운 것

**검증이 만든 데이터가 운영 데이터에 섞이면 숫자를 믿을 수 없게 됩니다.** 매출이라는 가장 중요한 숫자가 8할이나 틀려 있었는데, 화면은 아무 이상 없어 보였습니다. 틀린 값이 그럴듯하게 나오는 게 제일 무섭습니다.

**만드는 코드만큼 치우는 코드도 봐야 합니다.** 스크립트 넷이 전부 같은 실수를 하고 있었어요. 만들 때는 신경 쓰고 치울 때는 "대충 지우면 되지" 했던 겁니다.

**참조 관계가 있으면 지우는 순서까지 정해야 합니다.** 순서를 잘못 잡으면 막히거나, 막히지 않고 조각이 남습니다. 후자가 더 나쁩니다.

**한 곳을 치우다 발견한 더 큰 문제를 그냥 넘기지 않아야 합니다.** 원래는 전광판의 예약 9건만 지우려던 참이었습니다. 데이터를 들여다본 김에 옆을 봐서 38건을 찾았습니다.

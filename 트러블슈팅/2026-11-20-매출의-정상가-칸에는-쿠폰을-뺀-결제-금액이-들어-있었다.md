# 2026-11-20 매출의 '정상가' 칸에는, 쿠폰을 뺀 결제 금액이 들어 있었다

> 태그: #트러블슈팅 #매출 #쿠폰 #결제기록 #키오스크

## 무엇을 / 왜

사진 키오스크는 손님이 결제를 마치면 매출을 서버로 올렸고, 관리 웹의 매출 화면에서는 결제마다 펼쳐서 금액을 볼 수 있었습니다. 쿠폰을 쓴 시험 결제 하나를 펼쳐 보니 숫자가 이상했습니다. 2,000원짜리를 50% 쿠폰으로 깎아 현금 1,000원을 냈는데, '정상가' 칸에도 1,000원이 적혀 있었습니다.

## 어떻게 풀었나

### 값이 어디서 오는지 따라가 보기

'정상가' 라는 이름을 믿지 않고, 그 칸의 값이 처음 만들어지는 곳까지 거꾸로 따라가 봤습니다.

- 관리 웹의 '정상가' 는 서버 주문에 적힌 결제 승인 금액을 그대로 보여 주고 있었습니다.
- 그 금액은 키오스크가 올린 값이었고, 키오스크는 쿠폰을 뺀 뒤의 금액, 곧 손님이 실제로 낸 돈을 올리고 있었습니다.
- 정가와 쿠폰 할인은 서버 어디에도 없었습니다. 쿠폰 할인을 적는 칸은 있었지만 늘 0 이었고, 어떤 쿠폰을 썼는지는 쿠폰 사용 기록을 매출 번호로 이어 봐야 알 수 있었습니다.
- 키오스크 안의 매출 기록도 결제 금액과 쿠폰 번호만 칸으로 두고 있었습니다. 정가와 할인은 진단용으로 통째 남기는 원본 데이터(JSON) 안에만 있어서 서버로는 가지 않았습니다.

이름만 정상가였고, 내용은 결제 금액이었습니다. 정산은 처음부터 결제 금액을 기준으로 계산하고 있어서 돈 계산이 틀린 곳은 없었습니다. 틀린 것은 화면의 이름과, 서버에 한 번도 오지 않은 정보였습니다.

### 결제할 때 같이 적기

1. **키오스크:** 결제를 마칠 때 정가, 쿠폰 할인, 쿠폰 번호·이름·할인 종류·할인 값을 매출 기록에 함께 적고 서버로 보내게 했습니다. 쿠폰 이름과 할인 값은 쿠폰 표를 가리키게 하지 않고 결제 때 본 그대로 적었습니다. 쿠폰이 나중에 바뀌거나 지워져도 그 결제의 기록은 그대로 남게 하려는 것이었습니다.
2. **맞는지 보고 적기:** 키오스크와 서버 모두 "정가 - 쿠폰 할인 = 결제 금액" 이 맞을 때만 정가와 할인을 적었습니다. 맞지 않으면 그 칸만 비우고, 어느 칸이 왜 틀렸는지 로그로 남겼습니다. 매출 자체는 거절하지 않았습니다. 설명용 칸 때문에 돈을 받은 매출을 거절하면, 키오스크는 같은 매출을 계속 다시 보내고 서버에는 매출이 없는 상태가 되기 때문이었습니다.
3. **이름 바로잡기:** 관리 웹 매출 화면의 목록·펼친 칸·CSV 에서 '정상가' 를 '결제 금액' 으로 바꾸고, 쿠폰 결제에는 정가·쿠폰·쿠폰 할인 칸을 더했습니다. 키오스크 설정창의 매출 표도 같게 맞췄습니다.
4. **옛 결제는 추정하지 않기:** 이미 서버에 올라간 옛 결제는 쿠폰 사용 기록으로 어떤 쿠폰이었는지만 찾아 보여 주고, 정가와 할인은 "기록 없음" 으로 두었습니다. 쿠폰 할인율과 결제 금액으로 정가를 거꾸로 계산해 채울 수도 있었지만, 그건 그때 적은 값이 아니라 지금 짐작한 값이라 넣지 않았습니다. 키오스크에서 아직 올리지 않은 옛 기록은 진단용 데이터에 결제 때 계산한 값이 남아 있어서, 그 값으로 채워 보냈습니다.

## 코드로 보기 (개념 재현)

이름은 바꾼 더미입니다.

```js
// 결제를 마칠 때 키오스크가 올리는 매출. 예전에는 paidSum 만 있었다
const saleIn = {
  paidSum: 1000,     // 손님이 실제로 낸 돈. 예전 화면은 이 값을 '정상가' 로 보여 줬다
  priceBefore: 2000, // 쿠폰 전 금액 (새로 싣는다)
  couponCut: 1000,   // 쿠폰으로 깎은 금액 (새로 싣는다)
  couponNote: { code: 'HALF-50', label: '반값 쿠폰', percent: 50 }, // 결제 때 본 그대로
};

// 서버: 설명용 칸은 맞을 때만 적고, 틀려도 매출은 거절하지 않는다
function couponPart(s, warnLog) {
  const sumOk = s.priceBefore != null
    && s.couponCut >= 0
    && s.couponCut <= s.priceBefore
    && s.priceBefore - s.couponCut === s.paidSum;
  if (!sumOk) {
    warnLog(`정가·쿠폰 할인을 적지 않음: ${s.priceBefore} - ${s.couponCut} != ${s.paidSum}`);
    return { priceBefore: null, couponCut: 0, couponNote: s.couponNote }; // 화면에는 "기록 없음"
  }
  return { priceBefore: s.priceBefore, couponCut: s.couponCut, couponNote: s.couponNote };
}

couponPart(saleIn, console.warn);
// { priceBefore: 2000, couponCut: 1000, couponNote: {...} }

couponPart({ ...saleIn, priceBefore: 1800 }, console.warn);
// 경고: 정가·쿠폰 할인을 적지 않음: 1800 - 1000 != 1000
// { priceBefore: null, couponCut: 0, couponNote: {...} }  -> 매출(1,000원)은 그대로 저장
```

## 💡 배운 것

- 칸 이름은 그 안의 값을 보장하지 않았습니다. 이름을 믿지 않고 값이 처음 만들어지는 곳까지 따라가 보니, 손님이 낸 돈이 '정상가' 라는 이름으로 보이고 있었습니다.
- 결제할 때 적지 않은 정보는 나중에 되살릴 수 없었습니다. 서버에는 정가가 한 번도 오지 않았으니, 옛 결제는 "기록 없음" 이 정직한 답이었습니다. 바뀔 수 있는 값은 거래할 때 함께 적어 둬야 한다는 걸 [2026-10-07 글](../개선/2026-10-07-수수료율을-정산-때-읽으면-지난-주문까지-바뀐다.md)에 이어 다시 배웠습니다. 그때는 수수료율이었고, 이번에는 쿠폰과 정가였습니다.
- 돈 기록에 붙은 설명 칸이 틀렸다고 매출 전체를 거절하면, 서버에 돈 기록이 남지 않게 된다는 걸 알게 됐습니다. 틀린 칸만 버리고 이유를 남기는 쪽이 매출을 지켰습니다.

## 소감

정산이 결제 금액 기준이라 돈이 틀어진 곳은 없었지만, 매출 화면을 보는 사람은 그 칸을 할인 전 금액으로 읽었을 겁니다. 같은 이름으로 결제 금액을 보여 주는 칸이 다른 화면에 하나 더 남아 있어서, 그것도 따로 바로잡으려고 합니다.

# 2026-11-12 원격 재실행이 늘 막혔는데, 포트 주인은 System 으로만 보였다

> 태그: #트러블슈팅 #Windows #HTTP.sys #netstat #키오스크

## 무엇을 / 왜

매장 키오스크 PC 에는 촬영 앱과, 그 앱을 지켜보며 원격 명령을 받는 관리 프로그램(에이전트)이 함께 돌았습니다. 촬영 앱 옆에서는 카메라와 장치를 다루는 작은 서비스 두 개가 로컬 포트를 하나씩 열어 두고 있었습니다.

관리자 화면에서 원격 명령 '재실행' 을 보내면 아무 일도 일어나지 않고 "실패" 만 남는 문제가 있었습니다. 같은 화면의 'PC 재시작' 과 '종료' 는 잘 됐습니다. 명령 기록에는 실패 까닭이 보이지 않아서, 화면만 봐서는 이유를 알 수 없었습니다.

## 어떻게 풀었나

에이전트의 재실행 코드를 따라가 보니, 촬영 앱을 끄기 전에 "다른 키오스크 프로그램이 돌고 있지 않은지" 를 먼저 확인하고 있었습니다. 한 PC 에서는 키오스크 프로그램을 하나만 돌리자는 규칙 때문에 넣은 확인이었습니다. 확인 방법은 이랬습니다.

- 카메라·장치 서비스 포트를 쥔 프로세스를 찾았습니다.
- 그 프로세스의 실행 파일 경로가 우리 설치 폴더 밖이면 "다른 프로그램" 으로 봤습니다.

그런데 netstat 으로 그 포트를 보면 주인이 언제나 `System`(PID 4)으로 나왔습니다. 찾아보니 우리 카메라·장치 서비스는 .NET 의 HttpListener 로 포트를 열었고, HttpListener 는 Windows 의 HTTP 서비스(커널 드라이버 http.sys)에 주소를 등록해서 포트를 연다는 걸 알게 됐습니다. 실제로 포트를 듣는 쪽은 커널이라서, 어느 앱이 열었든 netstat 에는 `System` 으로 보였습니다. `System` 에는 실행 파일 경로도 없었습니다. 개발 PC 에서 HttpListener 로 포트를 하나 열어 netstat 으로 봤을 때도 똑같이 `System` 이었습니다.

정리하면, 우리 촬영 앱이 정상으로 떠 있기만 하면 에이전트는 늘 "다른 키오스크 프로그램이 실행 중" 으로 판단했고, 끄지도 다시 켜지도 않은 채 실패를 보고하고 있었습니다. PC 재시작과 종료에는 이 확인이 없어서 됐던 것입니다.

사실 같은 일 때문에 촬영 앱 쪽에서는 이미 한 번 고친 적이 있었습니다. 설정창의 [재시작] 뒤 새로 뜬 앱이 지난 실행이 남긴 포트를 보고 "다른 프로그램이 실행 중" 이라고 알리던 문제였습니다. 그때 처음에는 `System` 을 "지난 실행의 것" 으로 보고 넘어가게 고쳤는데, 검토에서 `System` 은 누구의 HttpListener 든 똑같이 보이니 우리 것이라는 증거도 아니라는 지적을 받았습니다. 그래서 촬영 앱은 `System` 을 "확인할 수 없음" 으로 보고, 포트가 풀리기를 기다리게 바꿨습니다. 에이전트의 재실행 앞 확인에는 그 규칙이 들어가지 않은 채 남아 있었던 것입니다.

에이전트에서 고친 것은 세 가지였습니다.

- 끄기 전에는 남의 것이 **확실한** 상대(경로가 우리 폴더 밖이거나, 우리 것일 수 없는 이름)만 막았습니다. `System` 이나 경로를 읽지 못한 상대는 우리 것일 수도 있어서 막지 않았습니다.
- 끈 뒤에는 끝나는 중인 서비스가 포트를 놓을 때까지 1초마다 다시 보고(최대 30초) 앱을 띄웠습니다. 끝내 안 풀리면 다시 켜지 않고 까닭을 남겼습니다.
- 실패 까닭을 한 줄로 명령 기록에 남겨 관리자 화면에 보이게 했습니다. 이때 결과 글이 서버 한도(500자)를 넘으면 서버가 결과를 받지 않아, 명령이 만료될 때까지 '전송됨' 에 머물던 것도 알게 되어 글을 줄여 보내게 했습니다.

찾아보니 `netsh http show servicestate` 로 http.sys 에 주소를 등록한 실제 프로세스를 볼 수 있다는 것도 알게 됐습니다. 다만 Windows 언어마다 출력 모양이 달라서 이번에는 쓰지 않고, 다음에 할 일로 남겼습니다.

## 코드로 보기 (개념 재현)

이름과 경로는 바꾼 더미입니다. 포트 주인 정보는 netstat 결과(PID)와 프로세스 목록(실행 파일 경로)을 합친 것이라고 가정합니다.

```js
// owner = { pid, exePath }   System(PID 4) 은 exePath 가 없다
const OUR_DIR = 'C:\\Program Files\\PhotoApp\\';
const NEVER_OURS = ['other-kiosk.exe']; // 우리 것일 수 없는 이름

// 고치기 전: 경로가 우리 폴더 밖이면 남의 것. 경로가 없으면(= System) 그것도 '밖' 으로 셌다
function isForeignBefore(owner) {
  return !(owner.exePath || '').startsWith(OUR_DIR);
}

// 고친 뒤: 남의 것이 확실할 때만 'foreign'. System 이나 경로를 모르는 상대는 'unknown'
function classify(owner) {
  if (owner.pid === 4 || !owner.exePath) return 'unknown'; // http.sys 로 연 포트는 누구 것이든 System 으로 보인다
  const name = owner.exePath.split('\\').pop().toLowerCase();
  if (NEVER_OURS.includes(name)) return 'foreign';
  return owner.exePath.startsWith(OUR_DIR) ? 'ours' : 'foreign';
}

// 촬영 앱이 정상으로 떠 있을 때 두 서비스 포트의 주인
const owners = [{ pid: 4, exePath: null }, { pid: 4, exePath: null }];

owners.some(isForeignBefore);                  // true  -> "다른 프로그램 실행 중", 재실행 안 함
owners.some((o) => classify(o) === 'foreign'); // false -> 끄고, 포트가 풀리길 기다렸다가 다시 띄운다
```

```js
// 끈 뒤: 포트가 풀릴 때까지 1초마다 다시 본다(최대 30초). 남의 것이 보이면 바로 멈춘다
async function waitUntilFree(readOwners, { timeoutMs = 30000, stepMs = 1000 } = {}) {
  const until = Date.now() + timeoutMs;
  while (Date.now() < until) {
    const owners = await readOwners();
    if (owners.length === 0) return { ok: true };
    if (owners.some((o) => classify(o) === 'foreign')) {
      return { ok: false, reason: '다른 프로그램이 카메라·장치 서비스 포트를 쓰고 있습니다' };
    }
    await new Promise((r) => setTimeout(r, stepMs));
  }
  return { ok: false, reason: '30초가 지나도 카메라·장치 서비스 포트가 풀리지 않았습니다' };
}
```

## 💡 배운 것

- netstat 의 포트 주인이 `System`(PID 4)이면 그 포트는 http.sys 를 통해 열린 것이고, 실제로 어느 프로그램이 열었는지는 알려 주지 않는다는 걸 배웠습니다. `System` 은 "남의 것" 도 "우리 것" 도 아닌 "모름" 으로 다뤄야 했습니다.
- 같은 가정이 두 프로그램에 따로 들어 있으면, 한쪽을 고쳐도 다른 쪽은 그대로 남는다는 걸 배웠습니다. 이번에는 촬영 앱을 먼저 고치고, 에이전트의 같은 확인을 놓쳤습니다.
- 실패 까닭이 화면에 보이지 않으면 "실패" 한 단어로는 아무것도 고칠 수 없었습니다. 까닭을 남기는 일도 기능의 일부라는 걸 배웠습니다.

## 소감

"PC 재시작은 되는데 재실행만 안 된다" 는 차이가 가장 큰 단서였습니다. 두 명령이 무엇을 다르게 하는지 나란히 놓고 보니 확인 하나만 남았습니다. 앞으로는 판단의 근거가 되는 값(이번에는 실행 파일 경로)이 비어 있을 때, 코드가 어느 쪽으로 기우는지부터 보려고 합니다.

# 2026-08-05 빠진 파티션을 만들려는데, 이번엔 타임존 때문에 겹쳤다

> 태그: #트러블슈팅 #데이터베이스 #파티션 #타임존

## 오늘 한 일 (요약)
- 관리 API 몇 개가 갑자기 500을 뱉었다. 원인은 로그를 쌓는 표가 월별 칸(파티션)으로 나뉘는데 이번 달 칸이 없어 저장이 실패한 것.
- 칸을 자동으로 만들고 기본 칸(못 걸린 건 다 받는)을 두는 방식으로 고치려 했는데, 이번엔 "새 칸이 지난달 칸과 겹친다"며 또 실패했다.
- 범인은 타임존이었다. 날짜 경계를 세계표준시(UTC)로 못박아 기존 칸과 딱 맞췄다.

## 무엇을 / 왜 (증상)
로그·이벤트처럼 계속 쌓이는 큰 표는 월별로 칸(파티션)을 나눠 저장한다. 그래야 특정 달만 빠르게 뒤지고 지울 수 있다. 각 칸은 "이 달 것만 받는다"는 날짜 범위를 갖는다.

문제는 이 로그 표가 과거 몇 달치 칸만 손으로 만들어져 있었다는 것이다. 달이 바뀌어 이번 달 칸이 없으니, 새 로그를 넣을 때 "받아줄 칸이 없다"며 저장이 실패했다. 그리고 그 로그 저장은 여러 관리 기능이 공통으로 거치는 길목이라, 저장 실패가 연쇄로 여러 API를 500으로 무너뜨렸다.

## 어떻게 풀었나 - 직접 하면 되는데 앱이 하면 실패
비슷한 다른 표(사용량 기록)는 안 터지고 있었다. 그 표엔 (1) 필요한 칸을 자동으로 만드는 함수와 (2) 어디에도 안 걸린 행을 다 받는 "기본 칸"이 있었다. 이 로그 표만 그게 없었다.

그래서 같은 방식을 이 표에도 넣기로 했다 - 생성 함수 + 앞으로 넉넉히(14개월) 미리 만들기 + 기본 칸. 그런데 스키마 변경을 처음 돌리니 "이번 달 칸이 지난달 칸과 겹친다"며 실패했다.

이상한 지점이 있었다. 똑같은 칸 생성 명령을 내가 DB에 직접 치면 성공하는데, 앱(마이그레이션)이 돌리면 실패했다. 명령은 같은데 실행 주체만 달랐다.

범인은 타임존이었다.
- 기존 칸들은 세계표준시(UTC) 경계로 만들어져 있었다. 예: 8월 칸의 시작 = "UTC 8월 1일 0시".
- 그런데 앱의 DB 연결은 한국시간(KST)으로 잡혀 있었다. 그 상태에서 경계를 "8월 1일"이라고만 쓰면, DB는 그걸 "KST 8월 1일 0시"로 읽는다. 이건 UTC로 환산하면 "7월 31일 오후 3시"다.
- 그래서 새로 만들려는 8월 칸의 시작(UTC 7월 31일 15시)이, 기존 7월 칸의 끝(UTC 8월 1일 0시)과 9시간 겹쳤다.

경계 날짜를 쓸 때 타임존을 UTC로 명시해 못박으니, 기존 칸과 정확히 맞물려 겹침이 사라졌다.

## 코드로 보기 (개념 재현)
```
// 증상: 이번 달 칸이 없어 저장 실패 -> 여러 API 500
//   ERROR: no partition of relation "event_log" found for row

// 함정: 경계를 타임존 없이 쓰면 세션 타임존(KST)으로 해석된다
//   기존 칸:  FROM '2026-07-01 UTC'  TO '2026-08-01 UTC'
//   새 칸(x): FROM '2026-08-01'      -> KST로 읽혀 UTC '2026-07-31 15:00'
//             => 7월 칸의 끝과 9시간 겹침 => "partition would overlap"

// 해결: 경계를 UTC로 못박는다
create table event_log_2026_08 partition of event_log
  for values
    from ('2026-08-01 00:00:00+00')   // +00 = UTC 명시
    to   ('2026-09-01 00:00:00+00');

// 그리고 영구 안전망: 어디에도 안 걸린 행을 받는 기본 칸
create table event_log_default partition of event_log default;
```
같은 SQL이 사람이 치면 되고 앱이 치면 안 됐던 이유가, 둘의 세션 타임존이 달라 "날짜 문자열"이 서로 다른 시각으로 해석됐기 때문이라는 게 이 문제의 핵심이었다.

## 💡 배운 것
- **여러 API가 동시에 500이면, 각각이 아니라 그들이 공통으로 밟는 하부를 의심하라.** 여기선 "로그 저장"이라는 공통 길목이 무너져 연쇄로 퍼졌다.
- **"직접 실행은 되는데 앱에선 실패"는 환경 차이(타임존/권한/세션 설정)를 의심하는 신호다.** 명령이 같으면 실행 맥락이 다른 것이다.
- **날짜 경계는 타임존에 흔들린다. 파티션 경계 같은 곳은 UTC로 못박아야 한다.** "8월 1일"은 어디 기준이냐에 따라 다른 순간이다.
- **자동 생성 + 기본 칸으로 영구 안전망을 만들어라.** 손으로 미리 만든 칸은 언젠가 또 떨어진다.

## 소감
빠진 칸 하나 채우는 단순한 일인 줄 알았는데, 채우려다 타임존이라는 두 번째 함정에 걸렸다. "내가 치면 되는데 앱이 치면 안 된다"는 순간이 제일 헷갈렸지만, 동시에 원인을 좁히는 결정적 단서이기도 했다. 날짜를 다룰 때 "이 0시는 어느 타임존의 0시인가"를 늘 물어야 한다는 걸 몸으로 배웠다. 그리고 이번 달만 급히 채우는 대신 자동 생성과 기본 칸까지 넣어, 다음 달에 또 안 터지게 한 게 마음에 든다.

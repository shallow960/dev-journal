# 2026-10-26 PIN 확인을 기다리는 사이 손님이 바뀌어, 늦은 응답이 다음 주문에 남을 뻔했다

> 태그: #트러블슈팅 #비동기 #경합 #결제 #키오스크

## 무엇을 / 왜
사진 키오스크의 결제 화면에는 매장 매니저용 단축키가 있었습니다. 키를 누르고 PIN 을 넣으면 그 주문을 무료로 처리하고 매출에 "매니저 무료"로 기록했습니다. 결제와 인증 경로를 따로 검토하다가, PIN 확인 응답을 기다리는 동안 화면의 제한시간이 끝나면 일이 꼬이는 문제가 있었다는 걸 알게 됐습니다.

- 제한시간이 끝나 처음 화면으로 돌아가고, 곧바로 다음 손님의 주문이 시작됐습니다.
- 그 뒤에 이전 주문의 PIN 응답이 늦게 도착하자, 코드는 아무 확인 없이 지금 주문에 "결제수단 = 무료"와 매니저 기록 번호를 써 넣었습니다.
- 다음 손님이 카드로 돈을 내도, 결제 완료 화면은 "매니저 기록이 이미 있다"고 보고 카드 매출 기록을 건너뛰었습니다. 돈은 받았는데 매출에는 남지 않는 길이었습니다.

## 어떻게 풀었나
- 먼저 실제 화면 코드를 브라우저에 띄우고, PIN 응답과 카드 승인을 붙잡아 둔 채 시계를 앞으로 돌려 이 순서를 재현했습니다. 다음 손님의 카드 매출이 기록되지 않는 것을 시험으로 확인한 뒤에 고쳤습니다.
- 단축키를 누른 순간의 "주문 표시"(지금 화면 위치, 화면 이동 기록, 고른 프레임, 매수)를 들고 있다가, PIN 응답이 온 뒤·매출을 기록하기 전·주문 상태에 쓰기 전에 지금도 같은 주문인지 확인하게 했습니다.
- 화면 이동 기록은 이동할 때마다 새 배열로 바뀌어서, 같은 배열인지만 비교해도 "그 사이 화면이 바뀌었는지"를 알 수 있었습니다.
- 같은 검토에서 나온 "제한시간이 끝나기 직전에 현금을 다 넣으면 돈만 받고 처음 화면으로 가는" 길도 함께 막았습니다. 원래 앱처럼 시간이 끝나는 순간 결제가 이미 끝났는지 먼저 보고, 끝났으면 다음으로 넘어가게 했습니다.

## 코드로 보기 (개념 재현)
주문 상태와 늦게 오는 PIN 확인을 흉내 냈습니다.

```js
// 주문 상태(가게 전체가 함께 쓰는 저장소)와, PIN 확인처럼 늦게 오는 응답을 흉내 낸다.
const store = { orderNo: 1, screenToken: {}, payMethod: 'card', saleId: null };
const verifyPin = () => new Promise((r) => setTimeout(() => r(true), 50)); // 50ms 뒤 응답

async function freePayBuggy() {            // 응답이 오면 확인 없이 기록한다
  await verifyPin();
  store.payMethod = 'free'; store.saleId = 'mgr-1';
}
async function freePayFixed() {            // 누른 때의 표시를 들고 있다가, 응답 뒤 같은 주문인지 본다
  const mark = { orderNo: store.orderNo, screenToken: store.screenToken };
  await verifyPin();
  if (store.orderNo !== mark.orderNo || store.screenToken !== mark.screenToken) return 'skip';
  store.payMethod = 'free'; store.saleId = 'mgr-1'; return 'done';
}
function nextCustomer() {                  // 응답을 기다리는 사이 시간이 끝나 다음 손님으로 넘어감
  store.orderNo += 1; store.screenToken = {}; store.payMethod = 'card'; store.saleId = null;
}
for (const [name, fn] of [['고치기 전', freePayBuggy], ['고친 뒤', freePayFixed]]) {
  Object.assign(store, { orderNo: 1, screenToken: {}, payMethod: 'card', saleId: null }); // 첫 손님 결제 화면
  const p = fn(); setTimeout(nextCustomer, 10); const r = await p;
  console.log(`${name}: 다음 손님 주문 #${store.orderNo} → 결제수단=${store.payMethod}, 매니저 기록=${store.saleId}${r ? ` (${r})` : ''}`);
}
```

실행 결과입니다.

```
고치기 전: 다음 손님 주문 #2 → 결제수단=free, 매니저 기록=mgr-1
고친 뒤: 다음 손님 주문 #2 → 결제수단=card, 매니저 기록=null (skip)
```

## 💡 배운 것
- await 뒤의 코드는 "기다리기 전과 같은 세상"에서 돈다는 보장이 없다는 걸 배웠습니다. 기다리는 동안 화면도, 주문도, 손님도 바뀔 수 있었습니다.
- 그래서 늦게 올 수 있는 응답으로 공유 상태를 바꿀 때는, 시작할 때의 표시를 들고 있다가 응답 뒤에 "이 일이 아직 유효한가"부터 확인해야 했습니다.
- 드물게 일어나는 일이라도 돈이 걸린 길이면, 실제 화면 코드로 순서를 재현하는 시험을 먼저 만들어 두는 편이 마음이 놓였습니다. 이번에도 새 시험 7건 가운데 4건이 고치기 전 코드에서 실패하는 것을 보고 나서 고쳤습니다.

## 소감
매니저가 PIN 을 넣는 몇백 ms 와 제한시간이 끝나는 순간이 겹쳐야 하는 드문 일이었습니다. 그래도 일어나면 화면에는 아무 표시 없이 매출만 빠지는 종류라, 검토에서 미리 찾은 것이 다행이었습니다.

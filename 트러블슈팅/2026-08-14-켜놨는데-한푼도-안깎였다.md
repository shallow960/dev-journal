# 2026-08-14 켜놨는데 한 푼도 안 깎였다 - catch가 삼킨 예외

> 태그: #트러블슈팅 #스케줄러 #멀티테넌트 #예외처리

## 무엇을 / 왜

사용량만큼 잔액을 깎는 기능을 확인하는 중이었습니다. 깎는 로직은 이미 있었고 테스트도 통과하고 있었어요. 문제는 **그 로직을 주기적으로 부르는 작업(스케줄러)을 한 번도 실제로 돌려본 적이 없었다**는 것이었습니다.

"테스트가 초록이니 되겠지" 하고 넘어갈 뻔했는데, 마음에 걸려서 돌려봤습니다. **잔액이 1도 줄지 않았습니다.**

서버 로그를 보니 오류도 없었습니다. 정확히는, 오류처럼 보이는 게 없었어요. 경고 한 줄이 조용히 쌓이고 있었을 뿐입니다.

## 어떻게 풀었나

스케줄러 코드는 대략 이런 모양이었습니다.

```
for (건별로) {
    if (증가분 <= 0) continue;
    try {
        잔액에서_깎기(가게ID, 증가분);
        여기까지_깎았다고_기록(건ID, 증가분);
    } catch (RuntimeException e) {
        log.warn("적용 실패 {} : {}", 건ID, e.getMessage());   // 다음 건으로
    }
}
```

한 건이 실패해도 나머지는 처리하려고 감싼 것이고, 그 자체는 합리적입니다. 문제는 **모든 건이 매번 실패하고 있었다**는 거였어요.

원인은 예상 밖이었습니다. 이 서비스는 여러 가게가 한 데이터베이스를 쓰기 때문에, 요청마다 "지금 어느 가게 일을 하는 중인지"를 세워두고 그걸로 데이터를 격리합니다. 그런데 **스케줄러는 사용자 요청이 아니라 서버가 스스로 도는 것**이라 그 정보가 없습니다. 반면 잔액을 깎는 쪽은 그 정보를 **반드시 있어야 하는 값**으로 요구했어요.

그래서 건마다 예외가 났고, `catch`가 그걸 삼켰고, 겉으로는 아무 일도 없었습니다.

고친 건 두 가지입니다.

**첫째, 건마다 가게 정보를 세우고 끝나면 지웁니다.** 스케줄러는 여러 가게의 건을 섞어서 처리하므로, 한 번 세워두고 끝내면 안 되고 건마다 갈아 끼워야 합니다. 지우는 걸 빠뜨리면 스레드가 재사용될 때 **직전 가게 정보가 남아 있어** 훨씬 위험합니다.

**둘째, 몇 건 중 몇 건을 반영했는지 남깁니다.** 이게 없으면 다음에 같은 일이 생겨도 똑같이 모릅니다.

```
int applied = 0;
for (건별로) {
    if (증가분 <= 0) continue;

    현재_가게_설정(건.가게ID);           // 스케줄러엔 요청이 없으니 직접 세운다
    try {
        반영하기(건.가게ID, 건.ID, 증가분);
        applied++;
    } catch (RuntimeException e) {
        log.warn("적용 실패 {} : {}", 건.ID, e.toString());   // getMessage()는 종종 null
    } finally {
        현재_가게_해제();                // 안 지우면 다음 건에 남는다
    }
}
log.info("대상 {}건 중 {}건 반영", 전체.size(), applied);
```

`getMessage()` 대신 `toString()`으로 바꾼 것도 작지만 컸습니다. 이번 예외는 메시지가 비어 있어서, 원래 로그는 사실상 **"적용 실패 (건ID) : null"** 이었거든요.

## 코드로 보기 (개념 재현 테스트)

이 버그의 핵심은 "스케줄러에는 요청 맥락이 없다"입니다. 테스트로 못박을 수 있습니다.

```java
@Test
void 맥락이_없어도_실제로_깎인다() {
    // given: 30분치 잔액과, 외부 집계가 10분을 보고했다고 가정
    var 가게 = 가게만들기("metering");
    맥락설정(가게);
    잔액충전(가게, 30);
    var 건 = 사용건만들기(가게, "uid-1");
    맥락해제();

    외부집계.설정("uid-1", 10);      // 누적 10분

    // when: 스케줄러가 도는 상황 그대로 - 맥락이 비어 있다
    맥락해제();
    작업.실행();

    // then
    맥락설정(가게);
    assertThat(잔액(가게)).isEqualByComparingTo("20");   // 고치기 전엔 30 그대로였다
}
```

여기서 중요한 건 `맥락해제()`를 **일부러** 넣은 부분입니다. 테스트에서 편하게 맥락을 세워둔 채 돌리면, 스케줄러가 실제로 도는 상황과 달라져서 **이 버그를 영원히 못 잡습니다.**

같은 테스트로 하나 더 확인했습니다. 외부 집계가 같은 누적치를 다시 줘도 두 번 깎으면 안 됩니다.

```java
작업.실행();                        // 누적 10 그대로
assertThat(잔액(가게)).isEqualByComparingTo("20");   // 증가분 0이므로 변화 없음
```

## 💡 배운 것

- **`catch`로 감싼 반복문은 "일부 실패"에는 좋지만 "전부 실패"를 숨긴다.** 계속 진행하더라도 몇 건을 처리했는지는 남겨야 합니다. 성공 건수 로그 한 줄이면 이번 문제는 첫날 드러났을 겁니다.
- **주기 실행 작업은 요청 맥락이 없다.** 요청 기준으로 동작하는 코드(사용자 정보, 가게 정보, 언어 설정 등)를 그대로 부르면 조용히 어긋납니다. 세울 거면 건마다 세우고 `finally`로 반드시 지웁니다.
- **테스트가 있다는 것과 그 코드가 불린다는 것은 다르다.** 이번에 깎는 로직은 테스트가 있었고 정확했습니다. 없었던 건 "그걸 부르는 쪽을 실제로 돌려본 적"이었습니다.
- **오류로 멈추는 실패가 조용한 실패보다 낫다.** 멈췄으면 첫날 알았을 텐데, 아무 일도 안 일어나서 몰랐습니다.
- `getMessage()`는 종종 `null`입니다. 로그에는 `toString()`이 안전합니다.

## 소감

"테스트 통과 = 동작함"이라고 은연중에 믿고 있었다는 걸 알았습니다. 테스트는 **부른 코드**만 검증합니다. 안 불리는 코드는 아무리 정확해도 없는 것과 같더군요.

그 뒤로 새 기능을 붙일 때 순서를 하나 추가했습니다. 만들고 → 테스트하고 → **실제로 부르는 경로를 한 번 끝까지 돌려보기.** 특히 주기 실행처럼 눈에 안 보이는 곳은 반드시요. 그리고 예외를 삼키는 자리를 만들 때는, 삼킨 만큼 **어딘가에 숫자로 남기는지** 같이 확인하게 됐습니다.

# 2026-09-18 캐시가 느린 게 아니라, 서버가 멈춰 있었다

> 태그: #트러블슈팅 #운영 #메모리 #모니터링

## 무엇을 / 왜

아침에 이런 알림이 와 있었습니다.

```
Health contributor (redis) took 18091ms to respond
```

상태 점검이 **18초** 걸렸다는 뜻입니다. 인메모리 캐시는 값을 잠깐 얹어 두는 용도라 밀리초 단위로 답해야 하는데, 18초면 그동안 그 요청을 처리하던 스레드는 아무것도 못 합니다.

## 어떻게 풀었나

### 의심한 순서

먼저 캐시 자체를 봤습니다. 컨테이너 사용량이 **2MB** 였습니다. 최대 64MB 로 잡아 뒀고 디스크에 쓰지도 않는 설정이라, 이쪽이 느릴 이유가 없었습니다.

그래서 한 칸 위, **호스트**를 봤습니다.

```
Mem:   911Mi 전체 / 776Mi 사용 / 여유 135Mi
Swap:  2.0Gi 중 655Mi 사용      ← 여기
```

1GB 짜리 서버에 애플리케이션 서버, 웹 프론트, 리버스 프록시, 캐시를 전부 올려 둔 상태였습니다. 물리 메모리가 모자라서 **메모리 일부가 디스크(스왑)로 밀려나 있었고**, 그 페이지를 건드리는 순간 수 초씩 멈춥니다.

즉 **캐시가 느린 게 아니라, 캐시에게 물어보는 쪽이 멈춰 있었습니다.** 상태 점검이 제일 먼저 티가 났을 뿐이고, 같은 멈춤은 결제든 로그인이든 어디서나 날 수 있었습니다.

### 두 가지를 같이 했다

**하나, 원인 제거** - 서버 메모리를 4GB 로 올렸습니다. 스왑 사용량이 0 이 됐습니다.

```
Mem:   3.7Gi 전체 / 815Mi 사용 / 여유 2.9Gi
Swap:  2.0Gi 중 0B 사용
```

**둘, 전파 차단** - 캐시 응답에 상한을 걸었습니다. 확인해 보니 상한이 **시험용 설정에만** 있었고 운영은 기본값(명령 60초)이었습니다. 늦으면 60초까지 기다린다는 뜻입니다.

```
운영에서 쓰는 설정:  (없음)     → 기본값 60초
시험용 설정:         timeout: 2s
```

캐시는 로그인 상태값·요청 제한·배치 잠금에 씁니다. 늦을 때 기다리는 것보다 **빨리 실패하는 편이 낫습니다.** 기다리면 스레드가 쌓여 서비스 전체가 느려지지만, 빨리 실패하면 그 요청만 실패합니다.

## 코드로 보기 (개념 재현)

```yaml
# 문제: 상한이 시험 프로필에만 걸려 있었다
spring:
  data:
    캐시:
      url: ${캐시_주소}
      # timeout 없음 → 클라이언트 기본값(명령 60초)

---
spring:
  config:
    activate:
      on-profile: test      # ★여기에만 있었다
  data:
    캐시:
      timeout: 2s
```

```yaml
# 고침: 모든 환경에 상한을 둔다
spring:
  data:
    캐시:
      url: ${캐시_주소}
      # 상한이 없으면 캐시가 막혔을 때 기본값(60초)까지 그대로 기다린다.
      # 실제로 상태 점검 한 번이 18초를 잡아먹었고, 그동안 그 스레드는 아무것도 못 한다.
      timeout: ${캐시_제한시간:2s}
      connect-timeout: ${캐시_접속제한시간:2s}
```

확인은 호스트 쪽 숫자로 합니다. 컨테이너 사용량만 보면 멀쩡해 보입니다.

```bash
free -h            # swap used 가 0 이 아니면 이미 밀려난 메모리가 있다
vmstat 1 5         # si/so 가 계속 0 이 아니면 지금도 스왑 중
docker stats --no-stream   # 컨테이너별 사용량 (여기만 보면 원인을 놓친다)
```

## 💡 배운 것

**증상이 난 부품이 아니라, 그 부품을 부르는 쪽을 봐야 할 때가 있습니다.** "캐시 응답 18초" 는 캐시 이야기처럼 들리지만 실제로는 호출자가 멈춰 있던 거였습니다.

**컨테이너 사용량과 호스트 메모리는 다릅니다.** 컨테이너는 제한 안에서 얌전히 쓰고 있어도, 호스트 전체가 모자라면 전부 느려집니다.

**스왑 사용량은 장애 신호로 읽어야 합니다.** "메모리가 부족하면 스왑이 받쳐 주니 괜찮다" 가 아니라, **스왑을 쓰기 시작한 순간부터 응답 시간이 예측 불가능해집니다.**

**설정 기본값이 환경마다 다른지 확인해야 합니다.** 시험에서는 2초로 잘 돌고 있어서 "상한이 있다" 고 착각했습니다. 운영에는 없었습니다.

**근본 해결과 전파 차단은 둘 다 합니다.** 서버를 늘려 원인을 없앴지만, 상한은 그대로 뒀습니다. 다음에 또 느려질 수 있고, 그때 기다리다 전체가 멈추는 것보다 그 요청만 실패하는 게 낫습니다.

## 소감

알림이 "redis" 라고 콕 집어 말해 주니 자연스럽게 그쪽만 봤습니다. 이름이 적혀 있으면 그게 범인처럼 보이는데, 실제로는 **가장 먼저 티가 난 자리**였을 뿐이더군요.

그리고 서버 사양은 "일단 작게 시작해서 필요하면 올리자" 로 두고 있었는데, **필요해진 시점을 알려 주는 건 CPU 그래프가 아니라 스왑 사용량** 이었습니다. 다음부터는 이 숫자를 먼저 보려고 합니다.

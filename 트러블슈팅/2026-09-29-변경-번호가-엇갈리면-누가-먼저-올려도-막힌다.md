# 2026-09-29 변경 번호가 엇갈리면, 누가 먼저 올려도 막힌다

> 태그: #트러블슈팅 #Flyway #DB마이그레이션 #배포순서

## 무엇을 / 왜

DB 구조 변경은 Flyway 로 관리합니다. `V213__...sql` 처럼 번호가 붙은 파일을 번호 순서대로 한 번씩 적용하고, 어디까지 적용했는지는 DB 에 기록해 둬요.

설정 하나가 중요했습니다.

```yaml
spring:
  flyway:
    out-of-order: false   # 이미 적용한 번호보다 작은 번호가 나중에 오면 실패
```

같은 저장소에서 다른 작업이 진행 중이었고, 그쪽은 아직 올리지 않은 변경 파일 `V214`, `V215`, `V218` 을 갖고 있었습니다. 저는 그 사이 번호인 `V216`, `V217` 을 만들었어요.

```
그쪽: V214  V215           V218   (아직 안 올림)
나  :             V216  V217      (올릴 예정)
```

이 상태면 어느 쪽이 먼저 배포돼도 문제가 됩니다.

- 제가 먼저 올리면 운영 DB 는 V217 까지 적용 → 나중에 온 V214·V215 는 "이미 지난 번호" 라 서버가 안 뜸
- 그쪽이 먼저 올리면 V218 까지 적용 → 나중에 온 제 V216·V217 이 막힘

## 어떻게 풀었나

### 1차: 뒤로 옮기기

처음엔 제 번호를 그쪽 뒤(`V219`, `V220`)로 옮겼습니다. 그러면 "그쪽 먼저, 나 나중" 이라는 순서 하나만 지키면 돼요. 그런데 그쪽 작업이 길어져서 기다릴 수 없었습니다.

### 2차: 앞으로 옮기기

거꾸로 생각했습니다. 운영에 이미 적용된 마지막 번호는 `V213` 이었어요. Flyway 는 `V213_1` 을 버전 `213.1` 로 읽으니, 제 파일을 **V213 과 V214 사이**에 넣을 수 있었습니다.

```
운영 적용: ... V213
나      :        V213_1  V213_2        ← 지금 올려도 213 다음이라 정상
그쪽    :                        V214  V215  V218   ← 나중에 와도 213.2 다음이라 정상
```

이러면 제가 먼저 올라가도, 그쪽이 나중에 올라가도 번호가 순서대로 이어집니다. 올리기 직전에 원격에 V214 이후 파일이 아직 없는지 한 번 더 확인했어요.

### 이름을 바꿨더니 "이미 있는 테이블"

번호를 바꾸고 테스트를 돌리자 이런 오류가 났습니다.

```
Migration V213_2__add_new_table.sql failed
ERROR: relation "..." already exists
```

같은 테이블을 두 번 만들고 있었어요. 빌드 폴더를 보니 **이름을 바꾸기 전 사본(`V217__...`)이 그대로 남아** 있었습니다. 소스에서 파일 이름을 바꿔도, 빌드가 리소스를 복사해 둔 폴더에서는 옛 파일이 지워지지 않았던 거예요. 옛 사본을 지우고 다시 돌려 통과했습니다.

## 코드로 보기 (개념 재현)

```text
# 번호 정하기 전에 확인할 것
1. 운영에 적용된 마지막 번호          → V213
2. 다른 작업이 들고 있는 미푸시 번호  → V214, V215, V218
3. 내 파일은 1 과 2 사이의 빈 자리    → V213_1, V213_2
```

```bash
# 이름 바꾼 뒤에는 빌드 산출물의 옛 사본을 지운다
rm -f build/resources/main/db/migration/V216__*.sql \
      build/resources/main/db/migration/V217__*.sql

# 올리기 직전, 원격에 내 번호보다 큰 파일이 먼저 올라갔는지 확인
git fetch origin
git ls-tree -r --name-only origin/main -- src/main/resources/db/migration | sort -V | tail -3
```

## 💡 배운 것

**번호 순서 규칙이 엄격하면, 병행 작업은 "누가 먼저 배포되나" 까지 같이 정해야 합니다.** 파일이 충돌하지 않아도 번호가 엇갈리면 배포 단계에서 깨져요.

**끼워 넣을 자리는 소수 번호로 만들 수 있습니다.** `V213_1` 처럼 이미 적용된 번호 바로 뒤에 두면 앞뒤 작업 모두와 순서가 맞습니다.

**파일 이름을 바꾸면 빌드 산출물도 의심합니다.** 소스에서는 사라진 파일이 복사본 폴더에 남아 있으면, 같은 변경이 두 번 실행될 수 있어요.

## 소감

충돌 없이 합쳐지는 것만 확인하고 넘어갔다면 운영 배포에서 서버가 안 뜨는 걸로 처음 알았을 겁니다. 코드 충돌보다 "적용 순서 충돌" 이 더 늦게, 더 아프게 드러난다는 걸 배웠고, 이제 새 변경 파일을 만들 때는 원격과 다른 작업의 번호부터 확인합니다.

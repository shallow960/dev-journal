# 2026-08-07 결제가 실패한 줄 알았는데, 결제 확인이 시작조차 못 하고 있었다

> 태그: #트러블슈팅 #결제연동 #멀티테넌트 #에러메시지

## 오늘 한 일 (요약)
- 카드 결제창까지는 잘 뜨는데, 돌아온 결과가 계속 "실패"였다. 처음엔 카드사/가맹점 문제로 의심했다.
- 실패 사유가 계속 비어 있는 게 걸려서, 사유를 화면까지 그대로 흘려보내게 고쳤다.
- 나온 문구는 결제사 메시지가 아니라 **우리 서버 메시지**였다. "이 호스트에 매핑된 테넌트가 없다."
- 결제 결과를 받는 콜백 경로를 **호스트 기반 테넌트 해석에서 제외**해 해결했다.

## 무엇을 / 왜 (증상)
우리 서비스는 쇼핑몰을 여러 개 굴리는 멀티테넌트 구조라, 요청이 들어오면 **접속 호스트로 어느 테넌트인지** 먼저 판별하는 인터셉터가 돈다. 대부분의 API는 `가게이름.도메인` 으로 들어오니 이게 자연스럽다.

문제는 결제사(PG) 인증 결과가 돌아오는 콜백이었다. 이건 가게 주소가 아니라 **플랫폼 대표 호스트**로 떨어진다. 대표 호스트에는 매핑된 테넌트가 없으니, 인터셉터가 요청을 컨트롤러에 넘기기도 전에 예외로 끊어버렸다.

```
[결제창] -> 인증 완료 -> [브라우저 POST: 대표호스트/콜백]
                              |
                     TenantInterceptor: "이 호스트의 테넌트가 없다" -> 예외
                              |
                      (승인 로직은 실행조차 안 됨)
```

겉으로 보이는 증상은 "결제 실패"였지만, 실제로는 **승인 요청을 보내보지도 못한 상태**였다. 그래서 실패 사유가 비어 있었던 것.

## 어떻게 풀었나
1. **사유를 숨기지 않게 먼저 고쳤다.** 콜백 결과를 화면으로 돌릴 때 실패 사유(결과코드/메시지)를 쿼리로 실어 보내고, 화면에 그대로 표시했다. 이게 없었으면 계속 카드사 탓만 하고 있었을 것이다.
2. 그러자 우리 서버의 `TENANT_NOT_FOUND` 메시지가 드러났고, 원인이 인터셉터임을 확인했다.
3. **결제 콜백 경로들을 테넌트 해석 예외 목록에 추가했다.** 근거는 명확하다.
   - 정기결제(빌키) 콜백: 테넌트를 호스트가 아니라 **서명된 예약 필드(HMAC 토큰)** 에서 복원한다. 애초에 호스트가 필요 없다.
   - 단건결제 콜백: 승인 결과만 확인하고 저장하지 않으므로 테넌트 자체가 불필요하다.

```java
private static final String[] TENANT_EXCLUDES = {
    "/api/v1/ops/**", "/api/v1/account/**", "/api/v1/console/**", "/api/v1/cms/**",
    "/api/v1/public/**", "/api/v1/auth/oauth/central-callback/**", "/api/v1/live/webhooks/**",
    // 결제 콜백은 플랫폼 호스트로 떨어진다. 테넌트는 토큰에서 복원하거나 아예 불필요.
    "/api/v1/saas/billing/nicepay/callback",
    "/api/v1/saas/billing/nicepay/single-pay/callback"
};
```

고치고 나서야 결제사의 진짜 응답이 왔다. **"회원사 서비스 개시 안됨"** — 가맹점이 아직 활성화되지 않았다는 뜻이었고, 우리 연동 코드는 정상이라는 게 확인됐다.

## 비슷한 사례가 또 있었다
지난달에도 라이브 영상 웹훅이 같은 이유로 막힌 적이 있다. 외부 서비스가 보내는 콜백/웹훅은 **우리 도메인 규칙(가게별 호스트)을 따르지 않는다**. 공통 패턴이다.

- 외부에서 들어오는 콜백은 호스트로 대상을 특정할 수 없다.
- 그래서 대상 식별은 **요청 본문이나 서명된 토큰**에서 복원해야 하고,
- 호스트 기반 전처리는 그 경로에서 **비켜서야** 한다.

## 💡 배운 것
- **에러 메시지를 삼키면 디버깅이 통째로 막힌다.** "실패"만 있고 사유가 없으면 원인을 외부로 미루게 된다. 사유를 끝까지 노출시키는 게 첫 수순이었다.
- 실패했다고 해서 **그 로직이 실행됐다는 뜻은 아니다.** 전처리(인터셉터/필터)에서 끊기면 "실패"처럼 보이지만 시작조차 안 한 것이다.
- 멀티테넌트에서 **외부 콜백은 항상 예외 경로**로 다뤄야 한다. 호스트로 테넌트를 잡는 규칙의 바깥에 있다.
- "우리 문제인가 외부 문제인가"는 **진짜 외부 응답을 받아본 뒤에** 판단해야 한다. 그 전까진 다 추측이다.

## 소감
카드사 쪽 설정 문제라고 반쯤 결론 내리고 있었는데, 사유를 화면에 띄우는 작은 수정 하나로 방향이 완전히 바뀌었다. 우리 서버 메시지가 결제사 메시지인 척 "실패"로 뭉뚱그려져 있었던 셈이다. 앞으로 외부 연동에서 실패가 나오면 **사유부터 끝까지 흘려보내게 만들고** 시작해야겠다.

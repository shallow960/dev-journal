# 2026-09-29 규칙에 없는 주소는, 누구에게나 403이었다

> 태그: #트러블슈팅 #SpringSecurity #테스트 #회귀방지

## 무엇을 / 왜

모듈마다 보안 규칙(SecurityFilterChain)을 따로 두는 구조입니다. 각 규칙은 "이 주소들은 내가 맡는다" 를 먼저 선언하고, 어디에도 해당하지 않는 요청은 맨 마지막 기본 규칙이 받아요. 기본 규칙은 안전하게 **전부 거절**입니다.

```
요청 → 회원 규칙? 상품 규칙? 주문 규칙? ... → (아무 데도 아니면) 기본 규칙: 전부 거절
```

새 API를 만들다가 보안 설정에 주소를 추가하려고 회원 규칙을 열었는데, 목록이 이랬습니다.

```
/api/auth/**, /api/me, /api/me/profile, /api/me/password
```

그런데 같은 컨트롤러에는 "개인정보 동의 현황" 과 "회원탈퇴" 주소도 있었어요. 목록에 없으니 이 둘은 기본 규칙으로 떨어지고, **로그인한 손님이 불러도 403**입니다. 화면에서 직접 눌러 본 적이 없어서 아무도 몰랐습니다.

## 어떻게 풀었나

### 먼저 재현

추측으로 고치지 않고 테스트로 확인했습니다. 로그인한 손님 토큰으로 동의 현황을 부르니 정말 403이 나왔어요. 규칙에 두 주소를 넣고 200을 확인했습니다.

### 같은 실수가 또 있을까

하나를 찾았다는 건 더 있을 수 있다는 뜻입니다. 사람이 목록을 눈으로 대조하는 대신, **서버에 등록된 모든 API 주소를 꺼내서 실제 보안 규칙들과 하나씩 맞춰 보는 테스트**를 만들었어요.

1. 스프링이 알고 있는 모든 핸들러 매핑에서 `/api/` 로 시작하는 패턴을 꺼낸다
2. `{id}` 같은 자리는 실제 값(UUID)으로 바꿔 요청을 흉내 낸다
3. 보안 규칙을 순서대로 돌며 처음 맞는 규칙을 찾는다
4. 그게 기본 규칙(모든 요청에 맞는 규칙)이면 "빠진 주소" 로 모은다

돌려 보니 7개가 더 나왔습니다. 전부 화면이 없거나 아직 연동하지 않은 기능(운영자용 옛 승인 기능, 쓰지 않는 결제 웹훅)이었어요. 이런 건 여는 쪽이 오히려 위험해서, **이유를 적은 "일부러 닫아 둔 목록"** 으로 남겼습니다.

## 코드로 보기 (개념 재현)

```java
@Test
void 모든_API는_기본_거절_규칙이_아닌_자기_규칙에_걸린다() {
    List<SecurityFilterChain> chains = filterChainProxy.getFilterChains();
    Map<String, String> uncovered = new TreeMap<>();

    handlerMapping.getHandlerMethods().forEach((info, handler) -> {
        for (String pattern : info.getPatternValues()) {
            if (!pattern.startsWith("/api/")) continue;
            String path = pattern.replaceAll("\\{[^}]+}", UUID.randomUUID().toString());
            for (String method : methodsOf(info)) {
                MockHttpServletRequest request = new MockHttpServletRequest(method, path);
                request.setServletPath(path);
                SecurityFilterChain first = chains.stream()
                    .filter(chain -> chain.matches(request))
                    .findFirst().orElse(null);
                if (first == null || isCatchAll(first)) {      // 기본 규칙까지 떨어졌다
                    uncovered.put(method + " " + pattern, handler.getBeanType().getSimpleName());
                }
            }
        }
    });

    Map<String, String> forgotten = new TreeMap<>(uncovered);
    forgotten.keySet().removeAll(CLOSED_ON_PURPOSE);          // 일부러 닫아 둔 것
    assertThat(forgotten).as("규칙에 없어 기본 거절에 걸리는 API").isEmpty();
    // 닫아 둔 목록이 실제와 어긋나지 않게: 열었으면 목록에서도 빼야 한다
    assertThat(uncovered.keySet()).containsExactlyInAnyOrderElementsOf(CLOSED_ON_PURPOSE);
}

private static boolean isCatchAll(SecurityFilterChain chain) {
    return chain instanceof DefaultSecurityFilterChain c
        && c.getRequestMatcher() instanceof AnyRequestMatcher;
}
```

마지막 줄이 중요했습니다. 닫아 둔 목록만 두면, 나중에 누가 그 기능을 열어도 목록에는 계속 남아 "왜 닫혀 있는지" 설명이 거짓말이 돼요. 목록과 실제가 어긋나면 실패하게 해서 둘을 같이 고치게 했습니다.

## 💡 배운 것

**"기본 거절" 은 안전하지만 조용합니다.** 빠진 주소가 에러 로그에 남는 게 아니라 그냥 403으로 끝나서, 누군가 그 화면을 눌러 보기 전에는 드러나지 않았어요.

**하나를 고쳤으면 같은 종류 전체를 기계로 훑습니다.** 사람이 규칙 목록과 컨트롤러를 대조하면 또 빠뜨립니다. 등록된 주소 목록은 프레임워크가 이미 갖고 있으니, 그걸 꺼내 쓰는 테스트 하나로 앞으로 생길 누락까지 막을 수 있었어요.

**열지 않는 것도 기록입니다.** "안 열려 있음" 이 실수인지 의도인지는 코드만 봐서는 알 수 없습니다. 이유를 적은 목록으로 남기니 다음에 보는 사람이 판단할 수 있었어요.

## 소감

같은 날 함께 작업하던 다른 기능이 새 API를 여러 개 추가했는데, 올리기 전에 이 테스트를 돌려 전부 규칙에 걸려 있는 걸 확인하고 올렸습니다. 한 번 만든 검사가 바로 다음 작업에서 쓰이는 걸 보니, 고치는 것보다 "다시 안 생기게 하는 것" 에 시간을 쓰길 잘했다는 생각이 들었습니다.

# 2026-08-12 조건을 빼면 죽고, 넣으면 멀쩡했다 - 파라미터에 타입이 없으면 생기는 일

> 태그: #트러블슈팅 #SQL #PostgreSQL #JDBC

## 오늘 한 일 (요약)
- 방금 배포한 오류 목록 화면이 안 열렸다. 내가 만든 화면이라 당연히 내 잘못인 줄 알았다.
- 고치기 전에 **서버 주소를 직접 불러봤더니** 어떤 조회는 되고 어떤 조회만 실패했다. 화면이 아니라 서버 문제였다.
- 원인은 **검색 조건을 하나도 주지 않았을 때**였다. 조건을 하나라도 주면 잘 돌아갔다.
- 같은 패턴을 전부 찾아보니 21곳이었고, 그 안에 **손님이 보는 고객센터 화면**도 있었다.

## 증상

화면에 "화면을 불러오지 못했습니다"만 떴다. 서버 컴포넌트가 예외를 던졌다는 뜻이다.

여기서 바로 화면 코드를 뒤지고 싶었지만, 먼저 **서버를 직접 불러서 범위를 좁혔다.**

```
GET /ops/errors/stats     → 200
GET /ops/errors/alerts    → 200
GET /ops/errors/releases  → 200
GET /ops/errors/groups    → 500   ← 이것만
GET /ops/log/search       → 500   ← 이것만
```

같은 화면이 부르는 다섯 개 중 두 개만 실패했다. 화면 코드는 용의선상에서 빠졌다.

되는 것과 안 되는 것의 차이는 분명했다. **실패한 둘만 검색 조건을 받는 조회**였다. 나머지는 조건 없이 집계만 하거나 결과가 비어 있었다.

## 문제의 SQL

```sql
select eg.*
from error_groups eg
where (:fromTime is null or eg.last_seen_at >= :fromTime)
  and (:toTime   is null or eg.last_seen_at <= :toTime)
  and (:status   is null or eg.status = cast(:status as error_group_status))
order by last_seen_at desc
limit :limit
```

"조건이 비었으면 전체, 아니면 그 조건에 맞는 것"을 쓰는 흔한 방식이다. 나도 이렇게 자주 썼다.

에러 메시지를 보고서야 무슨 일이 벌어지는지 알았다.

```
BadSqlGrammarException: bad SQL grammar [
  select eg.*
  from error_groups eg
  where (? is null or eg.last_seen_at >= ?)
    and (? is null or eg.last_seen_at <= ?)
  ...
```

`:fromTime`이 **`?` 두 개로 펼쳐져 있다.**

## 왜 이렇게 되나

이름 붙인 파라미터(`:fromTime`)는 결국 위치 파라미터(`?`)로 바뀌어 데이터베이스에 전달된다. 이때 **이름이 몇 번 나오든 나올 때마다 각각 하나씩** 만들어진다. 같은 이름이라고 하나로 합쳐지지 않는다.

그러면 첫 번째 `?`는 이런 자리에 놓인다.

```sql
where (? is null or ...)
```

PostgreSQL은 쿼리를 실행하기 전에 **각 자리에 어떤 종류의 값이 올지** 먼저 정해야 한다. 두 번째 `?`는 `last_seen_at >= ?` 이니까 "시각"이라고 알 수 있다. 그런데 첫 번째는 `? is null` 뿐이다. **`is null`은 어떤 종류에나 쓸 수 있어서 단서가 되지 못한다.**

여기서 값이라도 들어오면 그 값의 종류를 보고 정할 수 있다. 그런데 `null`이 들어오면 볼 것이 없다. 그래서 쿼리를 이해하지 못하고 문법 오류로 떨어진다.

**조건을 하나라도 넣으면 멀쩡하고, 아무것도 안 넣으면 죽는 이유가 이것이었다.**

## 그래서 여태 안 드러났다

이 부분이 제일 인상적이었다. 개발하면서 이 조회를 부를 때는 보통 무언가로 걸러 본다. 특정 상태만 보거나, 기간을 정하거나. 그럴 때는 전부 잘 돌아간다.

**아무 조건도 걸지 않는 건 사용자가 화면을 처음 열 때다.** 즉 가장 흔한 경로만 깨져 있었고, 개발자가 확인할 때는 잘 안 지나가는 경로였다.

## 고친 방법

값이 없어도 종류를 알 수 있게, 자리마다 종류를 명시했다.

```sql
where (cast(:fromTime as timestamptz) is null or eg.last_seen_at >= :fromTime)
  and (cast(:toTime   as timestamptz) is null or eg.last_seen_at <= :toTime)
  and (cast(:status   as text)        is null or eg.status = cast(:status as error_group_status))
```

이제 `null`이 들어와도 "이 자리는 시각"이라고 이미 적혀 있으니 데이터베이스가 헷갈리지 않는다.

## 하나 고치고 전부 찾아봤다

같은 방식으로 쓴 곳이 또 있을 것 같아 프로젝트 전체를 뒤졌다.

```
grep -rn ":[a-zA-Z]* is null" --include=*.java .
```

**21곳이 나왔다.** 그중에는 예상 못 한 것이 있었다.

```
GET /helpdesk/faqs     → 500
GET /helpdesk/notices  → 500
```

**손님이 보는 고객센터의 자주 묻는 질문과 공지사항**이었다. 분류를 고르지 않은 상태(=화면을 처음 연 상태)에서 열리지 않고 있었다. 관리 화면을 고치러 들어갔다가 손님 화면이 막혀 있는 걸 발견한 셈이다.

## 테스트를 붙이면서 알게 된 것

재현 테스트를 쓰면서 데이터를 미리 넣어야 하나 고민했는데, 넣지 않아도 재현됐다.

```java
@Test
void searchGroupsWithoutFilters() {
    var criteria = new ErrorGroupSearchCriteria(
        null, null, null, null, null, null, null, "lastSeen", 20, 0
    );
    assertThatCode(() -> queryService.searchGroups(criteria))
        .doesNotThrowAnyException();
}
```

당연했다. **파라미터의 종류를 정하는 건 쿼리를 실행하기 전 단계**라서, 테이블이 비어 있어도 그 단계에서 똑같이 실패한다. 덕분에 테스트가 가볍고 빨라졌다.

## 배운 것
- **이름 파라미터는 등장할 때마다 별도의 자리로 펼쳐진다.** 같은 이름이라고 하나로 합쳐지지 않는다.
- `is null`은 종류를 알려주지 못한다. **값이 없을 수 있는 자리에는 종류를 직접 적어준다.**
- **조건을 비운 경로는 따로 확인해야 한다.** 개발자는 대개 무언가로 걸러서 보기 때문에, 정작 사용자가 가장 많이 지나는 "아무것도 안 고른" 경로가 확인에서 빠진다.
- 화면이 깨졌을 때 **화면부터 고치지 말고 서버를 직접 불러 범위를 좁힌다.** 되는 것과 안 되는 것의 차이가 원인을 가리킨다.
- 하나를 고쳤으면 **같은 패턴을 전부 찾는다.** 한 곳에서 저지른 실수는 대개 여러 곳에 있다.

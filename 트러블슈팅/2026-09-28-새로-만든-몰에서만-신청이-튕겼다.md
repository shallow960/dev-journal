# 2026-09-28 새로 만든 몰에서만, 신청이 튕겼다

> 태그: #트러블슈팅 #데이터 #동시성 #유일제약 #멀티테넌트

## 무엇을 / 왜

여러 쇼핑몰을 한 서비스에서 운영하는 구조입니다. 몰 주인은 다른 판매자(셀러)를 받아 자기 몰에서 함께 팔 수 있어요. 흐름은 이렇습니다.

```
손님이 판매자 입점 신청 → 몰 주인이 심사 → 승인되면 판매 권한
```

테스트하던 몰에서는 잘 됐는데, **새로 개설한 몰**에서 신청을 내면 이렇게 튕겼습니다.

```
400 이 스토어는 아직 입점 신청을 받지 않습니다
```

신청이 저장조차 안 되니, 몰 주인의 심사 목록은 계속 비어 있었어요.

## 어떻게 풀었나

### 신청 코드가 먼저 찾는 것

신청을 저장하는 코드를 따라가 보니, 셀러를 바로 저장하지 않고 **셀러들이 소속될 "입점 마켓" 이라는 틀**을 먼저 찾고 있었습니다.

```
몰
 └─ 입점 마켓 (틀, 몰 주인 소유)
     ├─ 셀러 A
     └─ 셀러 B
```

틀이 없으면 "받지 않는 몰" 로 보고 400 을 돌려주는 구조였어요.

### 틀은 옛 데이터에만 있었다

그럼 테스트 몰에는 왜 틀이 있었을까요. 확인해 보니 테스트하던 몰은 **예전 시스템에서 옮겨 온 데이터**로 만든 데모 몰이었고, 옮기는 과정에서 틀도 같이 들어와 있었습니다.

새 서비스에서 몰을 개설하는 코드는 틀을 만들지 않았고, 몰 주인이 틀을 만들 화면도 없었어요. 결국 **새 고객은 셀러를 한 명도 받을 수 없는** 상태였습니다. 테스트 데이터가 실제 신규 데이터와 달라서 가려져 있던 문제예요.

### 만드는 시점을 정했다

두 가지 방법이 있었습니다.

1. 몰을 개설할 때 틀을 같이 만든다
2. 첫 신청이 들어올 때 틀이 없으면 그 자리에서 만든다

1번은 앞으로 만들 몰만 고쳐지고, 이미 개설된 몰은 따로 채워 넣어야 합니다. 2번은 **이미 있는 몰도 다음 신청 때 저절로 고쳐져요.** 신청 경로 한 곳만 바꾸면 되기도 해서 2번을 골랐습니다. 틀의 주인은 몰 주인 계정으로, 이름은 몰 이름으로 채웠어요.

### 동시에 두 명이 신청하면

"없으면 만든다" 에는 틈이 있습니다. 두 사람이 거의 동시에 신청하면 둘 다 "없네" 를 읽고 둘 다 만들 수 있어요. 그러면 틀이 두 개가 되고, 셀러가 서로 다른 틀에 흩어집니다.

그래서 틀의 주소 조각을 **몰 안에서 유일하게** 고정했습니다. 이미 있으면 넣지 않고(`on conflict do nothing`), 넣지 못했으면 먼저 만들어진 걸 다시 읽어서 씁니다.

## 코드로 보기 (개념 재현)

```java
private UUID resolveMarket() {
    return markets.findActive()
        .map(Market::id)
        .orElseGet(this::createDefaultMarket);   // 없으면 지금 만든다
}

/** 첫 신청 때 기본 입점 마켓을 만든다. 이미 개설된 몰도 이걸로 고쳐진다. */
private UUID createDefaultMarket() {
    UUID owner = findStoreOwnerUserId()
        .orElseThrow(() -> badRequest("이 스토어는 아직 입점 신청을 받지 않습니다"));
    UUID id = UUID.randomUUID();

    // slug 는 몰 안에서 유일하다. 동시에 두 신청이 와도 하나만 들어간다.
    int inserted = jdbc.sql("""
            insert into markets (store_id, id, owner_user_id, name, slug, is_active)
            values (:storeId, :id, :owner, :name, 'market', true)
            on conflict (store_id, slug) do nothing
            """)
        .param("storeId", currentStoreId()).param("id", id)
        .param("owner", owner).param("name", storeName())
        .update();

    if (inserted == 1) {
        return id;
    }
    // 다른 신청이 먼저 만들었다. 그걸 쓴다.
    return jdbc.sql("select id from markets where slug = 'market'")
        .query(UUID.class).single();
}
```

테스트는 "데모 데이터" 가 아니라 **실제 개설 경로로 새 몰을 만든 뒤** 확인하게 했습니다.

```java
@Test
void 새로_개설한_몰에서_신청이_심사_대기로_들어가고_승인하면_셀러가_된다() {
    var store = provisioning.createStore(owner, newStoreCommand());   // 실제 개설 경로
    var first = applications.apply(customerA, "첫 브랜드");
    var second = applications.apply(customerB, "둘째 브랜드");

    assertThat(first.status()).isEqualTo(APPLIED);
    assertThat(second.marketId()).isEqualTo(first.marketId());   // 틀은 하나
    onboarding.approve(first.marketId(), customerA);             // 승인하면 셀러
}
```

## 💡 배운 것

**테스트 데이터가 어디서 왔는지 봅니다.** 옮겨 온 데이터로 만든 테스트 몰에는 새 몰에 없는 것이 들어 있었습니다. 기능 검증은 가능하면 **실제 생성 경로로 만든 데이터**로 해야 해요.

**"필요할 때 만든다" 는 기존 데이터까지 고칩니다.** 생성 시점에 만드는 방식은 새 데이터만 고치지만, 쓰는 시점에 없으면 만드는 방식은 이미 있는 데이터도 다음 사용 때 채워집니다.

**"없으면 만든다" 에는 동시성 틈이 있습니다.** 읽고 넣는 사이에 다른 요청이 끼어들 수 있어요. 코드로 막기보다 DB 의 유일 제약에 맡기고, 충돌하면 먼저 만든 걸 다시 읽는 게 단순하고 확실했습니다.

## 소감

서비스의 핵심 흐름이 새 고객에게만 막혀 있었다는 게 아찔했습니다. 매번 같은 데모 몰로 확인하다 보니, 처음 온 사람이 겪는 상황을 한 번도 밟아 보지 않았던 거예요. 이후로는 "새로 가입한 사람 입장에서 처음부터" 를 확인 순서에 넣기로 했습니다.

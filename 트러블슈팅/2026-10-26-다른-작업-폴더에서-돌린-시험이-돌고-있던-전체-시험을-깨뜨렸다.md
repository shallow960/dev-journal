# 2026-10-26 다른 작업 폴더에서 돌린 시험이, 돌고 있던 전체 시험을 깨뜨렸다

> 태그: #트러블슈팅 #Gradle #Windows #테스트환경 #git-worktree

## 무엇을 / 왜

푸시하기 전에 백엔드 전체 시험(2천여 건)을 돌리고 있었습니다. 같은 PC 에서 다른 프로젝트의 빌드도 돌고 있어서 CPU 를 나눠 쓰느라 평소보다 훨씬 오래 걸렸습니다. 그사이 새로 만든 기능의 시험을 먼저 돌려 보고 싶었는데, 같은 폴더에서 빌드를 하나 더 돌리면 두 실행이 서로 꼬일 것 같았습니다.

그래서 저장소를 따로 꺼낸 작업 폴더(git worktree)를 만들어 거기서 새 기능의 시험만 돌렸습니다. 폴더가 다르니 안전하다고 생각했습니다.

1시간 50분 뒤 전체 시험이 끝났는데, 시험 클래스 7개가 이런 오류로 실패해 있었습니다.

```
Failed to load ApplicationContext
Caused by: java.lang.NoSuchFieldError: NEW_KIND
```

`NEW_KIND` 는 그날 새로 만든 동의 종류였습니다. 전체 시험을 시작한 시점의 코드에는 없던 값을, 어디선가 찾고 있었습니다.

## 어떻게 풀었나

### 1. 코드 문제인지 환경 문제인지부터 갈랐습니다

찾아보니 `NoSuchFieldError` 는 컴파일할 때는 있던 필드가 실행할 때는 없을 때 나는 오류라는 걸 알게 됐습니다. 소스가 틀렸다면 컴파일에서 막혔을 테니, 실행 중에 서로 다른 시점의 클래스 파일이 섞였다고 의심했습니다.

### 2. 빌드 스크립트에서 함께 쓰는 자리를 찾았습니다

빌드 스크립트를 열어 보니, Windows 에서는 시험을 돌리기 전에 컴파일한 클래스와 리소스를 **고정된 임시 폴더**로 복사하고, 시험은 그 폴더를 클래스 경로로 쓰고 있었습니다. 클래스 경로가 길면 Windows 명령줄 길이 제한에 걸려서 예전에 넣어 둔 장치였습니다.

문제는 그 폴더 이름이 저장소 위치와 상관없이 늘 같았다는 점이었습니다. 작업 폴더를 따로 만들어도 이 자리는 하나였습니다.

1. 전체 시험이 시작되면서 임시 폴더에 그때 코드의 클래스를 복사했습니다
2. 다른 작업 폴더에서 시험을 돌리자, 같은 임시 폴더를 새 코드의 클래스로 덮어썼습니다
3. 아직 돌고 있던 전체 시험이 다음 시험 클래스를 띄울 때 새 클래스와 옛 클래스를 섞어 읽었고, 새 필드를 찾다가 실패했습니다

실패한 7개가 모두 덮어쓴 뒤에 처음 띄운 시험이라는 것도 순서가 맞았습니다.

### 3. 실패한 것만 다시 돌려 확인했습니다

실패한 7개와 관련 클래스를 다른 실행 없이 혼자 다시 돌렸더니 모두 통과했습니다. 코드가 아니라 시험 환경이 섞인 문제였습니다. 그 뒤로는 백엔드 시험은 작업 폴더가 달라도 한 번에 하나만 돌리기로 했습니다.

## 코드로 보기 (개념 재현)

문제가 된 구조는 이랬습니다(Gradle Kotlin DSL, 이름은 바꿨습니다).

```kotlin
// 클래스 경로가 길면 Windows 명령줄 길이 제한에 걸려, 고정된 임시 폴더로 모아 짧게 만든다
val shortClasspathRoot = file("${System.getProperty("java.io.tmpdir")}/app-test-classpath")

val syncTestClasspath by tasks.registering(Sync::class) {
    dependsOn("classes", "testClasses")
    into(shortClasspathRoot)                                   // 저장소가 어디 있든 같은 자리
    from(sourceSets.main.get().output.classesDirs) { into("main/classes") }
    from(sourceSets.test.get().output.classesDirs) { into("test/classes") }
}

tasks.test {
    dependsOn(syncTestClasspath)
    doFirst {
        // 시험은 저장소 안의 build 폴더가 아니라, 이 공유 폴더의 클래스를 읽는다
        classpath = files(
            shortClasspathRoot.resolve("test/classes"),
            shortClasspathRoot.resolve("main/classes")
        ) + configurations.testRuntimeClasspath.get()
    }
}
```

`Sync` 는 대상 폴더를 원본과 똑같이 맞추는 작업이라, 두 번째 실행은 첫 번째 실행이 읽고 있는 폴더의 파일을 지우고 새로 채웠습니다.

자리를 작업 폴더마다 나누는 방법도 생각해 봤습니다. 아직 적용하지는 않았고, 지금은 "한 번에 하나만" 규칙으로 지키고 있습니다.

```kotlin
// 생각해 본 방법(적용 전): 저장소 경로로 폴더 이름을 나누면 작업 폴더끼리 겹치지 않는다
val shortClasspathRoot = file(
    "${System.getProperty("java.io.tmpdir")}/app-test-classpath-${rootDir.absolutePath.hashCode()}"
)
```

## 💡 배운 것

**`NoSuchFieldError`·`NoSuchMethodError` 가 나면 소스보다 실행 중에 섞인 클래스 파일을 먼저 의심하게 됐습니다.** 컴파일을 통과한 코드에서 필드가 없다는 건, 실행할 때 읽은 파일이 다른 시점의 것이라는 신호였습니다.

**작업 폴더를 나눠도, 빌드가 쓰는 공유 자리는 나뉘지 않는다는 걸 알게 됐습니다.** 임시 폴더, 고정 포트, 사용자 폴더의 캐시처럼 저장소 밖에 있는 자리는 두 실행이 함께 씁니다.

**실패한 것만 혼자 다시 돌려 보는 게 코드 문제와 환경 문제를 가르는 가장 빠른 방법이었습니다.**

## 소감

기다리는 시간을 아끼려고 한 일 때문에 2시간 가까이 돌린 전체 시험 결과를 다시 확인해야 했습니다. 폴더를 나누면 독립적이라고 생각했는데, 빌드 스크립트가 무엇을 어디에 쓰는지까지 보지 않았던 게 원인이었습니다. 다음에 병렬로 무언가를 돌릴 때는 "이 둘이 함께 쓰는 자리가 있나"를 먼저 보려고 합니다.

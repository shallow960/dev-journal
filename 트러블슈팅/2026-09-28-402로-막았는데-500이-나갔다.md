# 2026-09-28 402로 막았는데, 500이 나갔다

> 태그: #트러블슈팅 #SpringBoot #예외처리 #ControllerAdvice #요금제

## 무엇을 / 왜

요금제마다 쓸 수 있는 기능이 다른 서비스를 만들고 있습니다. 싼 요금제는 라이브 방송을 못 쓰는 식이에요. 그런데 이 "기능 목록" 을 계산해 저장만 하고 **어디서도 확인하지 않아서**, 싼 요금제로도 라이브 API 를 그대로 쓸 수 있었습니다.

그래서 요청이 컨트롤러에 닿기 전에 확인하는 **인터셉터**를 붙였습니다. 기능이 없으면 예외를 던지고, 예외 처리기가 그걸 `402 Payment Required` 와 "어느 요금제부터 쓸 수 있는지" 로 바꿔 주는 구조예요.

그런데 테스트를 돌리자 402 가 아니라 이게 나왔습니다.

```
Expected status 402 but was 500
```

## 어떻게 풀었나

### 처리기는 분명히 있었다

잠금 예외를 402 로 바꾸는 처리기는 제대로 만들어져 있었습니다. 같은 파일의 "한도 초과" 처리기는 이미 잘 동작하고 있었고요. 처리기가 없는 게 아니라 **다른 누군가가 먼저 잡고 있다** 는 뜻이었어요.

### 모든 예외를 잡는 처리기가 하나 더 있었다

프로젝트에는 서버 오류를 모아 운영 화면에 보여 주는 **전역 처리기**가 하나 있었습니다. 이 처리기는 `Exception` 전부를 잡아 기록하고 500 으로 응답해요.

```java
@RestControllerAdvice
public class GlobalErrorCaptureAdvice {
    @ExceptionHandler(Exception.class)          // 모든 예외
    ResponseEntity<?> capture(Exception ex) { ... return 500; }
}

@RestControllerAdvice
public class PlanErrorAdvice {
    @ExceptionHandler(FeatureNotInPlanException.class)   // 잠금 예외만
    ResponseEntity<?> locked(FeatureNotInPlanException ex) { ... return 402; }
}
```

Spring 은 예외가 나면 **처리기 묶음(ControllerAdvice)을 순서대로** 보면서, 그 묶음 안에서 예외를 처리할 수 있는 메서드를 찾습니다. 한 묶음 안에서는 더 구체적인 타입이 이기지만, **묶음끼리는 순서가 먼저**예요. 전역 처리기가 먼저 불리면 `Exception` 으로도 잠금 예외를 받을 수 있으니, 거기서 끝나 버립니다.

두 묶음 모두 순서를 지정하지 않아서 **같은 순위**였고, 이럴 때 누가 먼저인지는 정해져 있지 않았습니다.

### 그럼 한도 초과는 왜 잘 됐나

한도 초과 예외는 **컨트롤러나 서비스 안에서** 던져지고 있었고, 잠금 예외는 **인터셉터에서** 던져졌습니다. 던지는 위치에 따라 처리기를 찾는 경로가 달라지면서, 순서가 정해지지 않은 두 묶음 중 어느 쪽이 먼저 걸리는지가 달라졌던 걸로 보입니다. 결국 핵심은 "순서를 운에 맡기고 있었다" 였어요.

### 순서를 적어 줬다

요금제 처리기에 순서를 명시해서 전역 처리기보다 **먼저** 보게 했습니다. 402 는 정상적인 업무 결과라 오류로 기록할 대상도 아니라서, 전역 처리기까지 갈 이유가 없어요.

## 코드로 보기 (개념 재현)

```java
/**
 * 요금제 한도·기능 잠금(402).
 * 모든 예외를 잡는 전역 처리기와 순서가 같으면 누가 먼저 잡을지 정해지지 않는다.
 * 인터셉터에서 던진 잠금 예외가 500 으로 나갔다. 이쪽을 먼저 보게 앞에 둔다.
 */
@Order(Ordered.LOWEST_PRECEDENCE - 20)   // 숫자가 작을수록 먼저
@RestControllerAdvice
public class PlanErrorAdvice {

    @ExceptionHandler(FeatureNotInPlanException.class)
    ResponseEntity<FeatureNotInPlanResponse> locked(FeatureNotInPlanException ex) {
        return ResponseEntity.status(HttpStatus.PAYMENT_REQUIRED)
            .body(FeatureNotInPlanResponse.of(ex.featureCode(), ex.requiredPlan()));
    }
}
```

전역 처리기는 기본값(`LOWEST_PRECEDENCE`)이라 맨 뒤에 남습니다. 이렇게 하면 **구체적인 업무 예외는 먼저, 나머지 전부는 마지막에** 잡히는 순서가 코드에 드러나요.

테스트도 이 순서를 확인하게 두었습니다.

```java
@Test
void 요금제에_없는_기능을_쓰면_402와_필요한_요금제를_준다() throws Exception {
    mockMvc.perform(post("/api/live/streams").with(freePlanOwner()))
        .andExpect(status().isPaymentRequired())
        .andExpect(jsonPath("$.code").value("PLAN_FEATURE_LOCKED"))
        .andExpect(jsonPath("$.requiredPlan").value("growth"));
}
```

## 💡 배운 것

**처리기가 있는데 안 먹으면, 먼저 잡는 누군가를 찾습니다.** 처리기 코드를 고치기 전에 "같은 예외를 받을 수 있는 다른 처리기" 가 있는지부터 보면 빠릅니다. `Exception` 전부를 잡는 처리기는 그런 후보 1순위예요.

**ControllerAdvice 는 묶음끼리 순서가 먼저, 묶음 안에서 구체성이 나중입니다.** "더 구체적인 타입이 이긴다" 는 규칙은 한 묶음 안에서만 통합니다.

**순서가 필요한 곳은 순서를 적습니다.** 지정하지 않은 순서는 지금 우연히 맞아도 파일 하나 추가하면 바뀔 수 있어요.

**던지는 위치가 바뀌면 경로도 바뀝니다.** 같은 처리기를 쓰는 두 예외가 한쪽만 잘 되던 이유는 던지는 위치(컨트롤러 안 vs 인터셉터)였습니다. 새로운 위치에서 예외를 던지기 시작하면 처리 경로도 같이 확인해야 합니다.

## 소감

기능 잠금 자체보다 "왜 500 이지" 에 시간을 더 썼습니다. 오류를 모으려고 만든 처리기가 정상적인 402 응답까지 오류로 바꿔 버리고 있었다는 게 아이러니했어요. 전역으로 뭔가를 잡는 코드는 편한 만큼, 다른 처리기와의 순서를 같이 생각해야 한다는 걸 배웠습니다.

# 2026-10-29 빌드 설정에 복사 줄을 넣었는데도, 서버에서는 그 파일이 없었다

> 태그: #트러블슈팅 #배포 #Docker #빌드재료 #재발방지

## 무엇을 / 왜
관리자 화면을 브랜드별로 나누는 큰 작업을 합치면서, 관리자 화면 빌드가 저장소의 공용 설정 파일 하나를 새로 읽게 됐습니다.

- 합치기 전 검토에서, 이대로면 관리자 화면 이미지 빌드가 그 파일을 찾지 못한다는 지적이 나왔습니다. 그래서 빌드 설정(Dockerfile)에 그 파일을 복사하는 줄을 넣었습니다.
- 확인 빌드도 통과해서 고쳐진 줄 알았습니다.
- 그런데 합친 뒤 개발 서버 배포가 실패했습니다. 서버의 이미지 빌드가 바로 그 파일을 찾지 못하고 멈췄습니다.

## 어떻게 풀었나
- 배포 스크립트를 따라가 보니, 서버로 보내는 것은 저장소 전체가 아니었습니다. git archive 로 정해 둔 경로만 묶어 올리고, 서버는 그 묶음을 풀어 이미지를 빌드하고 있었습니다.
- 그 목록에 화면 소스 같은 폴더는 통째로 들어 있었지만, 공용 설정 폴더는 파일을 하나씩 골라 넣게 되어 있었습니다. 새 파일은 목록에 없었습니다.
- 합치기 전 확인 빌드는 제가 필요한 파일을 손으로 골라 담은 재료로 했고, 그때 새 파일도 담았습니다. 그래서 확인 빌드는 통과하고 실제 배포만 실패했던 것이었습니다.
- 목록에 파일을 넣어 고쳤습니다. 그리고 빌드 설정의 복사 줄이 가져오는 파일이 배포 목록에 모두 들어 있는지 대조하는 시험을 더했습니다. 고치기 전 목록으로 돌리면 이 시험이 실패했습니다.

## 코드로 보기 (개념 재현)
예시 저장소에서 정해 둔 경로만 묶고, 서버처럼 그 묶음을 풀어 빌드해 봤습니다. 이름은 모두 예시입니다.

```bash
# 서버로 보내는 묶음: 정해 둔 경로만 담는다
git archive --format=tar.gz --output=release.tgz HEAD -- \
  web deploy shared/route-access.json shared/signing-keys.json
tar -tzf release.tgz | sort

# 서버처럼 묶음을 풀어 빌드 재료로 쓴다
# (빌드 설정에는 shared/site-hosts.json 을 복사하는 줄이 들어 있다)
mkdir ctx && tar -xzf release.tgz -C ctx
docker build -f ctx/deploy/Dockerfile.web ctx
```

실행 결과입니다. 묶음 안 shared 폴더에는 파일이 두 개뿐이었고, 빌드는 새 파일을 찾지 못했습니다.

```
deploy/
deploy/Dockerfile.web
shared/
shared/route-access.json
shared/signing-keys.json
web/
web/package.json
ERROR: failed to build: failed to solve: failed to compute cache key: failed to calculate checksum of ref ...: "/shared/site-hosts.json": not found
```

같은 빌드 설정을 저장소 폴더 전체로 빌드하면 통과했습니다. 목록에 `shared/site-hosts.json` 을 넣은 묶음으로 빌드해도 통과했습니다.

같은 일이 다시 생기지 않게 더한 대조를 개념으로 옮겨 봤습니다. 빌드 설정의 COPY 줄에서 원본 경로를 뽑아, 재료 목록에 들어 있는지 봤습니다.

```js
// 빌드 설정(Dockerfile)이 복사하는 파일이, 서버로 보내는 묶음 목록에 모두 들어 있는지 대조한다.

// 1) 서버로 보내는 묶음 목록. 폴더는 통째로 넣고, 공용 설정은 파일을 하나씩 골라 넣는다.
const packListBefore = [
  'web/',                     // 관리자 화면 소스(폴더 통째로)
  'deploy/',                  // 빌드 설정과 웹 서버 설정
  'shared/route-access.json', // 공용 설정 파일 1
  'shared/signing-keys.json', // 공용 설정 파일 2
];
// 고친 뒤: 관리자 화면 빌드가 새로 읽는 파일을 목록에 넣었다.
const packListAfter = [...packListBefore, 'shared/site-hosts.json'];
// 합치기 전 확인 빌드: 필요한 것을 손으로 골라 담았다(새 파일도 담았다).
const handPicked = ['web/', 'deploy/', 'shared/route-access.json', 'shared/site-hosts.json'];

// 2) 관리자 화면 빌드 설정. 합치기 전에 받은 지적대로 새 파일 복사 줄(셋째 COPY)을 넣었다.
const dockerfile = `
FROM node:20 AS build
WORKDIR /app
COPY web/package.json web/package-lock.json ./web/
COPY shared/route-access.json ./shared/
COPY shared/site-hosts.json ./shared/
COPY web/ ./web/
RUN cd web && npm ci && npm run build

FROM nginx:1.27
COPY --from=build /app/web/dist /usr/share/nginx/html
COPY deploy/nginx.conf /etc/nginx/conf.d/default.conf
`;

// 3) COPY 줄에서 "빌드 재료에서 가져오는 원본"만 뽑는다.
//    --from=build 는 앞 단계에서 만든 결과를 가져오는 것이라 빌드 재료와 상관없어 뺀다.
function copySources(text) {
  const sources = [];
  for (const line of text.split('\n')) {
    const m = line.trim().match(/^COPY\s+(.+)$/i);
    if (!m) continue;
    const parts = m[1].split(/\s+/);
    if (parts.some((p) => p.startsWith('--from='))) continue;
    const args = parts.filter((p) => !p.startsWith('--')); // --chown 같은 옵션은 뺀다
    sources.push(...args.slice(0, -1));                     // 마지막 칸은 목적지다
  }
  return sources;
}

// 4) 원본 하나가 목록에 들어 있는가: 그 파일이 그대로 있거나, 그 파일을 품은 폴더가 있으면 된다.
const covered = (src, list) =>
  list.some((p) => (p.endsWith('/') ? src.startsWith(p) : src === p));

const sources = copySources(dockerfile);
console.log('빌드가 가져오는 원본:', sources);
for (const [name, list] of [
  ['손으로 담은 확인 재료', handPicked],
  ['배포 묶음(고치기 전)', packListBefore],
  ['배포 묶음(고친 뒤)', packListAfter],
]) {
  const missing = sources.filter((s) => !covered(s, list));
  console.log(`${name}: 빠진 파일 ${missing.length}개`, missing);
}
```

실행 결과입니다.

```
빌드가 가져오는 원본: [
  'web/package.json',
  'web/package-lock.json',
  'shared/route-access.json',
  'shared/site-hosts.json',
  'web/',
  'deploy/nginx.conf'
]
손으로 담은 확인 재료: 빠진 파일 0개 []
배포 묶음(고치기 전): 빠진 파일 1개 [ 'shared/site-hosts.json' ]
배포 묶음(고친 뒤): 빠진 파일 0개 []
```

손으로 담은 재료에는 빠진 것이 없어서 확인 빌드가 통과했고, 실제 배포 묶음에는 새 파일이 빠져 있었습니다. 목록을 고친 뒤에는 빠진 것이 없었습니다.

## 💡 배운 것
- 확인은 실제로 배포될 재료와 같은 방법으로 만든 재료로 해야 한다는 걸 다시 배웠습니다(2026-10-21, 내 PC 에서는 통과한 배포 명령이 서버에서는 첫 줄에서 멈춘 글). 이번에는 환경이 아니라 빌드 재료가 달랐습니다. 제가 손으로 담은 재료에는 새 파일이 있었고, 배포 스크립트가 만든 묶음에는 없었습니다.
- 빌드가 새 파일을 읽기 시작하면 빌드 설정만이 아니라 그 파일을 서버까지 실어 나르는 쪽도 봐야 한다는 걸 다시 배웠습니다(2026-10-20, 설정 이름을 바꾼 뒤 배포는 옛 이름을 넣고 있던 글).
- 서로 맞아야 하는 목록 두 개(빌드 설정의 복사 목록과 배포 묶음 목록)는 사람이 기억하기보다 시험이 대조하게 해야 한다는 걸 배웠습니다. 그래야 다음에 새 파일이 생겨도 합치기 전에 걸렸습니다.

## 소감
고쳤다고 생각한 곳과 실제로 실패한 곳 사이에 한 단계가 더 있었습니다. 확인 빌드가 통과해서 안심했는데, 그 확인이 무엇을 재료로 했는지까지는 보지 않았습니다.

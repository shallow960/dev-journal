# 2026-10-19 되돌린 비밀번호가, 계속 통하고 있었다

> 태그: #트러블슈팅 #캐시 #중단복구 #순서설계 #메시지브로커

## 무엇을 / 왜

매장 키오스크들은 메시지 브로커(MQTT)에 비밀번호로 접속합니다. 서버의 스크립트가 5분마다 "있어야 할 계정과 비밀번호" 를 계산해서, 브로커가 읽는 비밀번호 파일을 맞춰 줘요.

계정이 많아지면 매번 전부 다시 만드는 게 아까워서, "마지막으로 적용이 확인된 계정의 지문" 을 기록 파일에 따로 남겨 둡니다. 다음 실행은 이 기록과 설정을 비교해서 달라진 계정만 고쳐요.

교체 순서는 이랬습니다.

1. 지금 파일을 백업한다
2. "다시 읽혀야 할 파일이 있음" 표시를 남긴다
3. 새 비밀번호 파일로 바꾼다
4. 브로커에 다시 읽으라는 신호를 보내고, 로그로 성공을 확인한다
5. 표시를 지우고, 기록을 쓴다

교차 검토에서 이런 순서가 나왔어요.

- 비밀번호를 A 에서 B 로 바꾸는데, 3번 직후 브로커가 다른 이유로 재시작됐습니다. 4번에서 "아까 그 브로커가 아니다" 를 보고 "나중에 다시" 로 끝나요.
- 이때 파일은 이미 **B**, 기록은 **A** 입니다. 확인 못 한 값은 기록하지 않도록 며칠 전에 고쳐 뒀거든요.
- 그 사이 운영자가 설정을 다시 **A** 로 되돌립니다.
- 다음 실행은 기록(A)과 설정(A)만 비교해서 "바뀐 것 없음" 으로 봅니다. 그런데 표시가 남아 있으니 디스크의 파일을 다시 읽히고, 성공으로 처리해요. 그 파일은 **B** 입니다.
- 결과: 브로커는 B 로 돌고, 기록은 A, 설정도 A. 이후로는 매번 "바뀐 것 없음" 이에요. **되돌린 B 는 계속 통하고, 지금 설정인 A 는 거부됩니다.** 스스로 고쳐지지도 않았어요.

## 어떻게 풀었나

기록이 "확인된 사실" 에서 "예전 사실" 로 바뀌는 순간이 문제였습니다. 그 순간은 3번, 파일을 바꾸는 때예요. 그래서 두 겹으로 고쳤습니다.

1. **파일을 바꾸기 직전에 기록부터 지웁니다.** 2번(표시) 다음, 3번 바로 앞이에요. 지우는 데 실패하면 아무것도 바꾸지 않고 멈춥니다. 이제 3번 이후 어디서 끊겨도 기록이 없으니, 다음 실행은 모든 계정을 설정 기준으로 다시 만들고 확인까지 해요.
2. **"다시 읽혀야 할 파일" 표시에 비밀번호 파일이 있으면 기록을 믿지 않습니다.** 표시를 남긴 직후, 기록을 지우기 전에 끊긴 경우와 고치기 전 버전이 남긴 상태까지 덮는 두 번째 겹입니다.

그다음 시험을 다시 짰어요.

- 끊기는 지점 4곳(표시를 남긴 뒤, 기록을 지운 뒤, 파일을 바꾼 직후, 확인하고 기록을 쓰기 전)
- 설정 변화(되돌리기, 세 번째 값으로 바꾸기, 계정 삭제만, 비밀번호를 만드는 원본 키 되돌리기)

이걸 조합해 13가지를 돌렸습니다. 파일 내용만 보지 않고 **실제 브로커에 로그인해서**, 지금 설정의 비밀번호만 통하고 나머지는 거부되는지 확인했어요. 같은 시험을 고치기 전 스크립트에도 돌려서 실패하는 것까지 봤습니다. 시험이 이 결함을 정말 잡는지 확인하려고요.

## 코드로 보기 (개념 재현)

```bash
#!/usr/bin/env bash
# 개념 재현: 이름과 경로는 모두 더미다.
set -euo pipefail

cache=state/applied.cache       # 마지막으로 "적용이 확인된" 계정의 지문
pending=state/reload.pending    # "다시 읽혀야 할 파일" 표시
live=auth/accounts.txt          # 브로커가 실제로 읽는 파일

plan() {
  # 표시에 계정 파일이 있으면 기록을 믿지 않는다.
  # 끊긴 실행이 이미 파일을 바꿨을 수 있기 때문이다.
  if grep -qx 'accounts' "$pending" 2>/dev/null; then
    rm -f "$cache"
  fi
  # 기록이 없으면 모든 계정이 "달라진 계정" 이 된다.
  # 그러면 설정을 기준으로 전부 다시 만든다.
  diff_accounts "$cache" desired.list          # 더미 함수
}

apply() {
  cp -p "$live" "$live.prev"                   # 1. 되돌릴 곳을 먼저 만든다
  echo accounts > "$pending"                   # 2. 끊겨도 다음 실행이 알 수 있게

  # 바꾸기 "전에" 기록부터 지운다. 못 지우면 아무것도 바꾸지 않는다.
  rm -f "$cache" || { echo "기록을 못 지움: 아무것도 바꾸지 않음" >&2; exit 1; }

  mv new/accounts.txt "$live"                  # 3. 여기서 끊겨도 기록은 이미 없다
  reload_and_verify || { rollback; exit 1; }   # 4. 로그로 성공 확인 (더미 함수)
  rm -f "$pending"                             # 5. 확인된 뒤에만 표시를 지우고
  write_cache desired.list > "$cache"          #    기록은 맨 마지막에 쓴다
}
```

## 💡 배운 것

**기록(캐시)에는 확인된 사실만 담고, 실제를 바꾸기 전에 지워야 한다는 걸 배웠습니다.** 바꾼 뒤에 지우면, 바꾸고 지우기 전에 끊기는 순간 기록이 거짓말을 해요. 기록은 없어도 다시 만들 수 있지만, 틀린 기록은 "바뀐 것 없음" 이라는 그럴듯한 답을 계속 내놓습니다.

**되돌리는 순서도 시험해야 한다는 걸 배웠습니다.** 여러 번 검토를 거쳤는데도 놓친 건, 바꾼 값을 그대로 두는 순서만 시험했기 때문이에요. 운영에서 "바꿨다가 되돌린다" 는 아주 흔한 동작인데, 시험 목록에는 없었습니다.

**순서 하나가 결과를 바꾼다는 걸 다시 배웠습니다.** 2026-09-09 에 카드 취소와 장부 정리의 순서를 뒤집으면서 "되돌릴 수 없는 것을 먼저 하면 안 된다" 를 배웠어요. 이번에도 같은 이야기였습니다. 언제든 다시 만들 수 있는 쪽(기록 지우기)을 앞에, 되돌리기 어려운 쪽(실제 파일 바꾸기)을 뒤에 두니 끊기는 지점이 어디든 안전한 쪽으로 틀리게 됐어요.

**한쪽을 막은 수정이 다른 순서를 열 수 있다는 걸 배웠습니다.** "확인 못 한 값은 기록하지 않는다" 는 며칠 전의 수정이 맞았는데도, 그 덕분에 기록이 예전 값으로 남는 상태가 생겼어요. 고칠 때는 그 한 경로만이 아니라 "기록이 실제와 달라질 수 있는 모든 구간" 을 같이 봐야 했습니다.

**파일이 맞는지보다, 실제로 통하는지를 본다는 걸 다시 배웠습니다.** 마지막 확인은 파일 비교가 아니라 실제 로그인 허용·거부였어요.

# 2026-09-21 읽고 없으면 넣기, 그 사이의 틈을 DB가 막는다

> 태그: #개선 #동시성 #결제 #데이터베이스

## 무엇을 / 왜

서비스의 요금 원칙은 **"구독 하나에 쇼핑몰 하나"** 였습니다. 원칙은 정해 뒀는데, 이게 코드로 정말 지켜지는지는 확인해 본 적이 없었습니다. 몰을 만드는 흐름을 처음부터 따라가 봤더니 틈이 세 군데 있었습니다.

1. 무료체험을 이미 쓴 계정이 두 번째 몰을 만들면, **구독 없이 만들어지고 기능은 전부 켜진 채**였다. 결제를 안 하면 그대로 공짜.
2. "지금 결제" 를 빠르게 두 번 누르면 **카드가 두 번 긁힐 수 있었다.**
3. 몰 두 개를 거의 동시에 만들면 **무료체험을 두 번** 받을 수 있었다.

1번은 정책 구멍이고, 2번과 3번은 같은 모양의 동시성 문제였습니다.

## 어떻게 풀었나

### 2, 3번은 "읽고 없으면 넣기" 였다

결제 시작 코드는 이렇게 생겼습니다.

```java
if (구독저장소.현재구독(사용자).isPresent()) {
    throw 이미_구독_있음();
}
구독저장소.저장(새_구독);   // 그다음 청구서 만들고 카드 승인
```

요청이 하나씩 오면 문제없습니다. 그런데 두 요청이 **거의 동시에** 오면 이렇게 됩니다.

```
요청 A: 현재구독 조회 → 없음
요청 B: 현재구독 조회 → 없음      ← A 가 아직 저장 전
요청 A: 저장 → 카드 승인
요청 B: 저장 → 카드 승인          ← 두 번째 결제
```

검사와 저장 사이가 비어 있는 겁니다. 코드에서 검사를 아무리 꼼꼼히 해도 이 틈은 코드만으로는 못 막습니다.

게다가 검사 기준도 어긋나 있었습니다. **사용자 기준**으로 "이 사람한테 구독이 있나" 를 봤는데, 원칙은 **몰 기준**입니다. 같은 몰의 다른 관리자가 누르면 구독이 하나 더 생길 수 있었습니다.

### 막는 방법 세 겹

**① DB 유일 제약 - 틈을 닫는다.** "몰 하나에 살아 있는 구독은 하나" 를 데이터베이스 규칙으로 걸었습니다. 해지된 구독은 이력이라 여러 개 있어도 되니까, **조건부 유일 인덱스**로 살아 있는 것만 셉니다.

**② 검사 기준을 몰로 바꾼다.** 코드 검사는 그대로 두되 몰 기준을 추가했습니다. 대부분의 중복은 여기서 친절한 메시지로 걸러지고, 동시에 들어온 드문 경우만 ①이 막습니다.

**③ 이미 있는 구독을 결제할 때는 행을 잠근다.** 체험 중인 구독을 "지금 결제" 로 전환하는 경우는 새로 넣는 게 아니라 **있는 행을 바꾸는** 것이라 ①이 안 걸립니다. 그래서 그 행을 잠그고 다시 읽게 했습니다. 두 번째 요청은 첫 번째가 끝날 때까지 기다렸다가, 이미 유료가 된 구독을 보고 멈춥니다.

무료체험 중복(3번)도 같은 방식으로, 몰을 만들기 전에 **계정 행을 잠그고** 나서 "체험 썼나" 를 읽게 했습니다.

### 1번은 "만들되 닫아 둔다"

두 번째 몰부터는 결제를 먼저 받기로 했습니다. 그런데 이 서비스는 **카드가 몰마다 따로 붙는** 구조라, 결제할 몰이 먼저 있어야 카드를 등록할 수 있습니다.

그래서 몰은 만들되 **닫힌 상태**로 만들고, 결제가 성공하는 **그 자리에서 연다**로 정했습니다. 원래 있던 "연체로 멈춘 몰 되살리기" 는 하루 한 번 새벽에만 돌았는데, 결제 직후에 바로 여는 경로를 따로 만들었습니다. 덤으로 연체로 멈춘 몰도 결제하면 바로 열리게 됐습니다.

## 코드로 보기 (개념 재현)

① 조건부 유일 인덱스. 해지된 것은 빼고 셉니다.

```sql
create unique index uq_구독_몰당_하나
    on 구독 (몰_id)
    where 상태 <> 'cancelled';
```

두 번째 저장은 첫 번째가 끝날 때까지 기다렸다가 실패하고, **카드 승인까지 가지 않습니다.** 코드에서는 이 실패를 "이미 구독 있음" 으로 바꿔 돌려줍니다.

```java
try {
    구독저장소.저장(새_구독);
} catch (DuplicateKeyException ex) {
    // 동시에 들어온 다른 요청이 먼저 만들었다. 이 요청은 청구 전에 멈춘다.
    throw new ResponseStatusException(HttpStatus.CONFLICT, "이미 구독이 있어요", ex);
}
```

③ 있는 행을 바꿀 때는 잠그고 다시 읽습니다.

```java
Subscription 구독 = 구독저장소.잠그고_조회(현재.id())   // select ... for update
    .orElse(현재);
if (구독.유료_활성()) {
    throw 이미_결제됨();   // 뒤에 온 요청은 여기서 멈춘다
}
```

마이그레이션 쪽에서 하나 더 조심한 게 있습니다. 이미 겹친 데이터가 있으면 인덱스 생성이 실패해서 **배포 전체가 멈춥니다.** 겹친 구독 중 무엇을 살릴지는 돈이 걸린 판단이라 마이그레이션이 대신 정하면 안 되니까, 겹침이 있으면 경고만 남기고 넘어가게 했습니다.

```sql
do $$
begin
    if exists (select 1 from 구독 where 상태 <> 'cancelled' group by 몰_id having count(*) > 1) then
        raise warning '살아 있는 구독이 둘 이상인 몰이 있어 인덱스를 만들지 않았습니다. 정리 후 수동 생성';
    else
        create unique index if not exists uq_구독_몰당_하나 on 구독 (몰_id) where 상태 <> 'cancelled';
    end if;
end
$$;
```

## 💡 배운 것

**"읽고 없으면 넣기" 는 코드만으로 완전히 막을 수 없습니다.** 검사와 저장 사이의 틈은 데이터베이스 제약이나 잠금이 닫아야 합니다. 코드 검사는 친절한 메시지용, DB 는 최후의 벽으로 역할을 나눴습니다.

**새로 넣는 경합과 있는 걸 바꾸는 경합은 막는 도구가 다릅니다.** 넣는 건 유일 제약, 바꾸는 건 행 잠금.

**원칙의 "단위" 를 코드가 같은 단위로 보고 있는지 확인합니다.** 몰 기준 원칙을 사용자 기준으로 검사하고 있었습니다.

**정책 문장은 코드 흐름으로 따라가 봐야 압니다.** "구독 하나에 몰 하나" 는 문서에만 있었고, 실제로는 두 번째 몰이 공짜로 열리고 있었습니다.

**데이터를 고치는 판단은 마이그레이션에 맡기지 않습니다.** 돈이 걸린 정리는 사람이 해야 하고, 그동안 배포는 멈추지 않게 합니다.

## 소감

질문 하나("그 로직 있는 거지?")에서 시작했는데, 따라가 보니 결제가 두 번 될 수 있는 구멍까지 나왔습니다. 오픈 전에 찾아서 다행입니다.

동시성 문제는 테스트로 재현하기가 어려워서, "두 요청이 동시에 오면?" 을 종이에 순서대로 적어 보는 게 가장 확실했습니다.

# 2026-10-21 결제가 끝나는 길이 둘이라, 알릴 차례 표시는 DB 트리거가 단다

> 태그: #개선 #알림 #PostgreSQL #트리거 #배포

## 무엇을 / 왜

쇼핑몰 주인은 관리 화면을 열어 봐야 새 주문이 들어온 걸 알 수 있었어요. 결제가 끝난 주문을 주인과 관리자, 그리고 그 상품을 판 입점 셀러에게 메일로 알리기로 했습니다.

결제 완료 코드 옆에 메일 한 줄을 넣으면 될 것 같았는데, 따져 보니 걸리는 게 세 가지였어요.

1. **결제가 끝나는 길이 둘이다.** 카드 결제는 결제대행사가 승인할 때, 무통장 입금은 관리자가 입금을 확인할 때 결제 완료가 돼요. 코드에서 알림을 부르면 두 곳을 다 고쳐야 하고, 나중에 길이 하나 더 생기면 빠뜨리기 쉬워요.
2. **배포하는 날이 위험하다.** "결제는 끝났는데 아직 안 알린 주문"을 조건으로 찾으면, 배포하는 순간 지금까지 쌓인 결제 완료 주문이 전부 대상이 됩니다. 옛 자료를 들여오는 작업도 결제가 끝난 주문을 넣으니 마찬가지예요.
3. **결제를 느리게 하면 안 된다.** 결제 자리에서 바로 메일을 보내면, 메일 서버를 기다리는 만큼 결제 응답이 늦어져요.

## 어떻게 풀었나

**"결제 확인 시각이 처음 채워지는 순간"을 DB 트리거로 잡았어요.** 주문에 "알릴 차례" 표시 열을 두고(기본은 꺼짐), 결제 확인 시각이 비어 있다가 채워지는 갱신에서만 트리거가 표시를 켭니다. 두 길 모두 이미 저장된 주문을 불러와 결제 확인 시각을 채운 뒤 다시 저장하니, 어느 길로 끝나든 이 한 곳에서 잡혀요.

- 이미 있는 주문은 표시가 꺼진 채로 시작해서, 배포할 때 메일이 몰려 나가지 않아요.
- 옛 자료를 들여올 때는 결제 확인 시각이 채워진 채로 새로 넣는데(insert), 트리거는 고치기(update)에서만 돌아서 표시가 켜지지 않아요.
- 표시가 켜진 주문만 담는 조건부 인덱스를 둬서, 5분마다 찾는 비용이 전체 주문 수에 끌려가지 않게 했어요.

**보내기는 5분마다 따로 돌아요.** 결제 응답은 메일을 기다리지 않고, 쇼핑몰별로 모아 한 통으로 보냅니다. 서버가 여러 대여도 한 대에서만 돌도록 잠금을 걸었어요.

- **먼저 끄고, 끈 것만 보낸다.** 표시를 끄는 갱신이 돌려준 주문만 보내요. 같은 주문이 두 번 가지 않는 대신, 메일이 실패하면 다시 보내지 않습니다. 주문은 관리 화면에 그대로 있으니 "두 번 받는 것"보다 이쪽을 골랐어요.
- 그사이 취소된 주문은 뺍니다.
- 주인 메일에는 주문번호·상품·금액·결제 시각만 넣고, 손님 이름·연락처·주소는 넣지 않아요.
- 셀러에게는 자기 상품이 든 주문만, 자기 상품 줄만, 금액 없이 보내요.
- 한 쇼핑몰에서 실패해도 다른 쇼핑몰 알림은 계속 나갑니다.

## 코드로 보기 (개념 재현)

```sql
-- 알릴 차례 표시: 기본은 꺼짐이라 이미 있는 주문은 대상이 아니다
alter table shop_orders add column notify_pending boolean not null default false;

-- 표시가 켜진 주문만 담는 작은 인덱스
create index ix_shop_orders_notify_pending
    on shop_orders (store_id, paid_at)
    where notify_pending;

create or replace function mark_notify_pending() returns trigger
    language plpgsql
as $$
begin
    new.notify_pending := true;
    return new;
end;
$$;

-- 결제 확인 시각이 '비어 있다가 채워지는' 갱신에서만 켠다.
-- 처음부터 채워진 채로 넣는 행(옛 자료 들여오기)은 insert 라서 켜지지 않는다.
create trigger trg_mark_notify_pending
    before update of paid_at on shop_orders
    for each row
    when (old.paid_at is null and new.paid_at is not null)
    execute function mark_notify_pending();
```

```java
// 5분마다: 쇼핑몰마다 '먼저 끄고, 끈 것만' 보낸다
@Scheduled(cron = "0 */5 * * * *")
void run() {
    lock.runExclusively("new-order-notice", () -> {
        for (UUID storeId : activeStores()) {
            try {
                notifyStore(storeId);
            } catch (RuntimeException e) {
                log.warn("new order notice failed store={}", storeId, e); // 다른 쇼핑몰은 계속 보낸다
            }
        }
    });
}

void notifyStore(UUID storeId) {
    List<UUID> pending = db.sql("""
            select id from shop_orders
            where store_id = :store and notify_pending
            order by paid_at, id
            limit 200
            """).param("store", storeId).query(UUID.class).list();
    if (pending.isEmpty()) return;

    // 표시를 끈 행만 돌려받는다. 겹쳐 돈 다른 실행이 먼저 끈 주문은 여기서 빠진다.
    List<UUID> taken = db.sql("""
            update shop_orders set notify_pending = false
            where store_id = :store and id in (:ids) and notify_pending
            returning id
            """).param("store", storeId).param("ids", pending).query(UUID.class).list();

    List<NewOrder> orders = stillPaid(storeId, taken); // 그사이 취소된 주문은 뺀다
    mailOwners(storeId, orders);                       // 주문번호·상품·금액·시각만, 손님 정보는 없다
    mailSellers(storeId, orders);                      // 셀러마다 자기 상품 줄만, 금액 없이
}
```

시험은 세 가지를 봅니다. 카드 결제 주문이 주인·관리자·셀러에게 한 번씩만 가는지(두 번째 실행에서는 아무것도 보내지 않고, 셀러 메일에는 남의 상품과 금액이 없고, 어느 메일에도 손님 정보가 없는지), 무통장 주문은 입금 확인 전에는 가지 않고 확인한 다음 실행에서 가는지, 실행 전에 취소한 주문은 보내지 않고 표시만 끄는지요.

## 💡 배운 것

**여러 길이 같은 상태로 모이면, 그 상태가 바뀌는 순간을 잡는 게 빠뜨리지 않는 방법입니다.** 길마다 알림을 부르면 길이 늘 때마다 빠뜨릴 수 있는데, "결제 확인 시각이 처음 채워진다"는 사실은 어느 길이든 같았어요. 트리거의 `when (old.paid_at is null and new.paid_at is not null)` 한 줄이 그 순간을 정확히 집어 줬습니다.

**새 알림을 켤 때는 "지금까지 쌓인 것"부터 생각해야 합니다.** "아직 안 알린 것"을 조건으로 찾으면 배포하는 순간 과거 전부가 대상이 돼요. 표시를 기본 꺼짐으로 두고 앞으로 바뀌는 것만 켜니, 과거는 저절로 빠졌습니다.

**한 번만 보낼지, 적어도 한 번은 보낼지를 정하고 써야 합니다.** 먼저 끄고 보내면 중복은 없지만 실패한 메일은 사라지고, 보내고 나서 끄면 실패는 다시 보내지만 두 번 갈 수 있어요. 둘 다 가질 수는 없어서, 놓쳐도 확인할 곳이 있는 쪽을 골랐습니다.

## 소감

트리거는 기록을 지우지 못하게 막는 데만 써 봤는데, "언제 바뀌었는지"를 잡는 데도 잘 맞았어요. 대신 트리거는 코드에서 잘 보이지 않아서, 마이그레이션과 알림 작업 양쪽 주석에 서로를 적어 뒀습니다. 실제 메일이 오는지는 메일 발송 서비스 승인 뒤에 확인할 예정이에요(확인 필요).

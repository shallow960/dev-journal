# 2026-08-20 쇼핑몰인데 배송비를 한 푼도 못 받고 있었다

> 태그: #개선 #주문 #정책 #멀티벤더

## 무엇을 / 왜

주문 데이터를 다른 일로 들여다보다가 이상한 걸 봤습니다. 배송비가 전부 0원이었어요.

```
order_no        total_amount   total_shipping
DEMO-D-MULTI     123,900          0.00
SMOKE-235729      65,000          0.00
20260722-0004     15,900          0.00
```

한두 건이 아니라 **전부** 0이었습니다. 그런데 손님몰 맨 위 띠에는 이렇게 떠 있었어요.

> 지금 가입하면 1만원 쿠폰 즉시 지급 · **5만원 이상 무료배송**

조건이 있는 것처럼 말하면서 실제로는 늘 공짜로 보내고 있었던 셈입니다.

## 어떻게 풀었나

### 세 군데가 따로 놀고 있었다

원인을 따라가 보니 배송비에 관여하는 곳이 셋인데 서로 말이 달랐습니다.

| 어디 | 무슨 값 |
|---|---|
| 주문을 만드는 곳 | 품목마다 **0원을 박아 넣음** |
| 손님 화면 | "3만원 이상 무료, 아니면 3000원" 을 **자기 코드에 박아 둠** |
| 상품 등록 폼 | 배송비 칸이 있는데 **저장 요청에 실리지 않음** |

세 번째가 특히 허탈했습니다. 상품 등록 화면의 "배송" 단계에 배송비 입력 칸이 있고 기본값
3000까지 채워져 있는데, 저장할 때 그 값이 요청에 담기지 않았습니다. 서버는 처음부터 받을
준비가 돼 있었고 저장할 테이블도 있었는데, 실제 데이터는 **0행**이었어요.

두 번째도 문제였습니다. 스토어마다 배송 정책이 다른데 모든 몰이 같은 값을 보여주고 있었고,
정작 주문은 0원으로 만들어지니 **화면에 보여준 값과 실제 청구가 서로 달랐습니다.**

### 빠져 있던 조각

상품별 배송비를 담을 곳은 있었는데, **상품에 따로 안 정했을 때 쓸 스토어 기본값**이 없었습니다.
그게 없으니 계산을 붙일 수가 없었던 거예요. 그래서 스토어 기본 정책부터 만들었습니다.

기본값은 **무료(0원)** 로 뒀습니다. 이미 팔고 있는 스토어의 배송비를 마이그레이션이 말없이
올려 버리면, 손님이 어제와 다른 값을 보게 되니까요. 오너가 정하는 순간부터 받습니다.

### 여러 브랜드가 섞인 주문

우리 쇼핑몰은 여러 입점 브랜드가 함께 파는 구조입니다. 그래서 한 주문에 브랜드가 섞입니다.

**브랜드별로 묶어서** 계산하기로 했습니다. 브랜드가 다르면 각자 자기 물건을 보내니까 배송비도
따로 받는 게 맞고, 무료배송 기준도 그 묶음의 금액으로 봅니다.

한 브랜드에 여러 상품을 담았을 때는 **그중 가장 비싼 배송비 하나만** 받습니다. 같이 보내는데
상품 수만큼 받으면 손님이 나눠서 주문하는 게 이득이 되어 버리니까요.

### 정하면서 걸렸던 것

**무료 기준은 상품 금액으로 본다.** 처음엔 주문 총액으로 재려다 말았습니다. 총액에는 배송비가
들어 있어서, 배송비 때문에 무료 기준을 넘기는 이상한 일이 생깁니다. 기준이 스스로를 넘는 셈이죠.

**화면과 결제가 같은 계산을 써야 한다.** 그래서 화면이 자기가 계산하지 않고 서버에 물어보게
했습니다. 미리 보여준 값과 청구가 다르면 손님은 속았다고 느낍니다.

**바로구매도 같은 길로.** 장바구니 주문과 바로구매가 다른 코드를 타고 있어서, 둘 다 같은
계산을 태웠습니다. 담는 방법에 따라 배송비가 달라지면 안 되니까요.

## 코드로 보기 (개념 재현)

```
// 브랜드별로 묶는다
for (품목 of 주문품목) {
  브랜드금액[품목.브랜드] += 품목.상품금액   // 배송비는 빼고 센다
  브랜드배송비[품목.브랜드] = max(기존, 이 상품의 배송비)  // 가장 비싼 것 하나
}

// 무료 기준을 넘긴 묶음은 0원
for (브랜드 of 브랜드들) {
  무료 = 기준 > 0 && 브랜드금액[브랜드] >= 기준
  청구[브랜드] = 무료 ? 0 : 브랜드배송비[브랜드]
}
```

단가는 **상품에 정해진 값이 먼저**고, 없으면 스토어 기본값을 씁니다.

## 확인

실제로 주문을 넣어 봤습니다.

| 상황 | 기대 | 결과 |
|---|---|---|
| 9,900원 (기준 미만) | 3,000원 | 청구 12,900원 |
| 59,400원 (5만 이상) | 0원 | 무료 |
| 두 브랜드 각 1개 | 3,000 x 2 | 6,000원 |
| 상품에 5,000원 지정 | 스토어 기본값을 이김 | 5,000원 |

결제 화면에도 같은 값이 떴고, 저장된 주문과 결제 청구액이 일치하는 것까지 봤습니다.

## 💡 배운 것

- **화면에 칸이 있다고 저장되는 건 아니다.** 입력 칸과 저장 요청 사이가 끊겨 있으면 사용자는
  값을 넣고도 아무 일이 안 일어나는 걸 모릅니다. 오히려 기본값이 채워져 있어서 "설정했다" 고
  믿게 됩니다.
- **화면이 자기 규칙을 갖고 있으면 언젠가 서버와 갈린다.** 특히 돈이 걸린 계산은 한 곳에서만
  해야 합니다. 두 군데 적어 두면 한쪽만 고쳐지는 날이 옵니다.
- **기준을 잴 때 무엇을 세는지 정확히 해야 한다.** 무료배송 기준에 배송비를 포함하면 기준이
  스스로를 넘깁니다.
- **기본값은 보수적으로.** 이미 운영 중인 곳의 값을 마이그레이션이 바꿔 버리면, 아무도 누르지
  않았는데 손님이 보는 숫자가 달라집니다.

## 소감

문구 하나가 이상해서 들여다본 건데 결국 세 군데를 다 손보게 됐습니다. 돌아보면 "5만원 이상
무료배송" 이라는 문구가 계속 신호를 보내고 있었어요. 아무도 그 문구와 실제 데이터를 나란히
놓고 보지 않았을 뿐입니다.

쇼핑몰에서 배송비는 마진이 걸린 자리인데 그동안 한 푼도 못 받고 있었다는 게 좀 아찔했습니다.
다음엔 기능을 만들 때 "이 값이 실제로 저장되고, 실제로 청구되는지" 를 끝까지 따라가 보려고 합니다.

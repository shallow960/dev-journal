# 2026-08-18 500MB짜리 영상 하나가 1GB를 먹고 있었다 - 파는 단위와 재는 단위를 나눴다

> 태그: #개선 #과금 #설계 #단위

## 무엇을 / 왜

방송 다시보기를 저장해 두는 기능을 만들고 있었습니다. 저장 용량은 **GB 단위로 파는 자원**입니다. 요금제에 "5GB 포함" 같은 식으로 적혀 있고, 더 필요하면 추가 상품을 사는 구조예요.

한도가 정수 GB라서, 영상을 보관할 때 그 영상 길이를 GB로 **올림**해서 깎았습니다. 최소 1GB부터요. 처음엔 별생각 없었는데 숫자를 넣어 보니 이상했습니다.

- 26분짜리 다시보기 = 실제 약 0.5GB → **1GB 차감**
- 20분짜리 두 개 = 실제 약 0.75GB → **2GB 차감**
- 90초짜리 짧은 영상 = 실제 약 0.03GB → **1GB 차감** (실제의 35배)

짧을수록 왜곡이 커집니다. 5GB 포함인 요금제에서 짧은 영상 다섯 개만 올려도 용량이 끝나요. 기능을 못 쓰게 되는 수준입니다.

게다가 같은 한도를 쓰는 기능이 두 개(다시보기 보관, 짧은 영상 업로드)였는데 **서로 다른 규칙으로 깎고** 있었습니다. 한쪽은 영상마다 올림, 다른 쪽은 초 단위로 모아서 세는 방식이었어요. 같은 자원인데 **어느 문으로 들어왔느냐에 따라 값이 달라지는** 상태였습니다.

"대충 맞으면 되지 않나" 싶기도 했는데, 이건 **돈 받고 파는 자원**이라 그렇게 넘기면 안 되는 것이었습니다.

## 어떻게 풀었나

### 파는 단위와 재는 단위를 분리했다

핵심은 이 한 줄이었습니다.

> **판매와 표시는 GB로, 계량은 초로.**

한도를 MB 단위로 잘게 내리는 방법도 있었지만 그러면 요금제 정의, 추가 상품, 화면, 기존 데이터까지 전부 건드려야 합니다. 얻는 건 표시 정밀도뿐이고요.

대신 **저장 장부를 초 단위로 하나** 두고, 한도와 비교할 때만 환산했습니다. 예를 들어 5GB 한도는 15,900초로 바꿔서 직접 견줍니다. 이렇게 하면 **반올림이 끼어들 자리가 아예 없습니다.**

```
before) 영상마다: ceil(길이 → GB), 최소 1GB   →  합계가 실제보다 큼
after ) 장부에 초를 더한다: 합계(초) vs 한도(초)  →  올림하는 곳이 없음
```

### 장부를 하나로 합쳤다

두 기능이 각자 세던 걸 **같은 장부**에 넣었습니다. 무엇이 들어오든 길이(초)를 더하고, 한도를 넘는지는 합계로만 봅니다. 짧은 영상 쪽이 쓰던 방식이 맞았고, 다시보기를 그쪽으로 옮긴 셈이에요.

### "영상 하나가 몇 GB"라는 개념을 지웠다

이게 생각보다 중요했습니다. 예전에는 영상마다 "이건 1GB짜리"라고 값을 저장해 뒀는데, 합계 기준으로 바뀌면 **그 값은 더 이상 아무 의미가 없습니다.** 그런데 남겨두면 화면이 계속 그 숫자를 보여줍니다.

그래서 컬럼과 응답 필드를 지웠습니다. 보관 화면은 GB 대신 **영상 길이**를 보여주고, 전체 사용량은 사용량 화면이 맡습니다.

뺄 때(보관 해제)도 마찬가지입니다. 영상별로 잡아둔 값이 없으니, **합계를 다시 계산해서 그 차이만큼** 돌려줍니다. 애초에 항목 단위로 잡지 않았으니 그게 유일하게 어긋나지 않는 방법이었어요.

### 화면 숫자도 정확하게

표시도 소수 둘째 자리까지 내리게 했습니다. `0.5GB`를 `1GB`로 보여주면 사용자는 두 배를 쓴 줄 압니다.

```
before)  0 / 5 GB   (실제 0.28GB를 썼는데 1GB로 표시)
after )  0.28 / 5 GB
```

이제 화면에 보이는 값과 실제 깎이는 값이 같은 숫자입니다. 예전에는 "0.28GB 썼는데 왜 1GB가 찼냐"는 질문에 답할 방법이 없었어요.

## 코드로 보기 (개념 재현 테스트)

경계에서 안 튀는지가 제일 중요했습니다.

```java
@Test
void 짧은영상_열개가_1GB를_넘지_않는다() {
    // 90초짜리 10개 = 900초. 1GB = 3,180초(720p 기준)
    for (int i = 0; i < 10; i++) 장부.더하기(가게, 90);

    assertThat(장부.사용량GB(가게)).isEqualByComparingTo("0.28");   // 예전엔 10GB
}

@Test
void 경계를_정확히_채운뒤_1초를_더해도_2GB로_튀지_않는다() {
    장부.더하기(가게, 3180);                 // 딱 1GB
    장부.더하기(가게, 1);                    // 1초 추가

    assertThat(장부.사용량GB(가게)).isEqualByComparingTo("1.00");
}

@Test
void 같은_한도를_두_기능이_같은_규칙으로_깎는다() {
    장부.더하기(가게, 20 * 60);              // 다시보기 20분
    장부.더하기(가게, 20 * 60);              // 다시보기 20분

    // 예전: 영상마다 올림이라 2GB, 지금: 합계 40분이라 1GB 미만
    assertThat(장부.사용량GB(가게)).isEqualByComparingTo("0.75");
}
```

## 💡 배운 것

- **파는 자원은 정확히 재야 한다.** 대충 재면 결국 설명할 수 없는 청구서가 나옵니다. "왜 0.28GB 썼는데 1GB가 찼나요"에 답할 수 없다면 그건 이미 문제입니다.
- **판매 단위와 계량 단위는 달라도 된다.** 오히려 나누는 편이 낫더군요. 파는 건 사용자가 이해하는 단위(GB)로, 세는 건 왜곡이 안 생기는 단위(초)로.
- **반올림은 표시에서만 하고 계산에서는 하지 않는다.** 계산 중간에 한 번 올리면 그 오차가 계속 쌓입니다.
- **같은 자원을 두 곳에서 다른 규칙으로 재면 반드시 어긋난다.** 들어온 문에 따라 값이 달라지는 건 설명이 불가능합니다.
- **의미가 없어진 값은 지워야 한다.** 남겨두면 화면이 그 죽은 숫자를 계속 보여줍니다.
- 다행히 실제 사용 데이터가 아직 없어서 옮길 값이 없었습니다. 데이터가 쌓인 뒤였다면 기존 값을 전부 다시 계산해서 맞춰야 했을 거예요. **단위를 바꾸는 건 빠를수록 싸다**는 걸 알았습니다.

## 소감

처음에는 "1GB 단위로 깎아도 크게 틀리진 않겠지"라고 생각했습니다. 한 시간짜리 방송이면 왜곡이 작으니까요. 그런데 짧은 영상을 넣어 보니 실제의 수십 배가 나왔습니다. **평균만 보고 넘겼으면 계속 몰랐을 문제**였어요.

숫자로 파는 기능을 만들 때는 극단값을 한 번 넣어보는 습관이 필요하다고 느꼈습니다. 제일 짧은 것, 제일 긴 것, 딱 경계에 걸리는 것. 그 셋만 넣어봐도 이번 문제는 바로 보였을 겁니다.

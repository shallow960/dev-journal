# 2026-09-16 기본값은 올리되, 고쳐 쓴 것은 두기

> 태그: #개선 #배포 #마이그레이션 #알림

## 무엇을 / 왜

주문 메일 문안은 가게를 열 때 기본값을 깔아 주고, 가게 주인이 자기 말투로 고쳐 쓸 수 있습니다. 깔 때 쓰는 규칙은 하나입니다.

```
이미 있으면 건드리지 않는다 (있으면 그냥 넘어감)
```

배포할 때마다 주인이 고쳐 쓴 문안을 되돌리면 안 되니까요.

그런데 이번에 기본 문안을 크게 고쳐야 했습니다. 주문 메일에 **무엇을 샀는지** 가 빠져 있었거든요. 주문번호와 결제금액만 있어서, 손님은 메일만 보고는 자기 주문을 확인할 수 없었습니다(전자상거래법이 요구하는 계약 내용 통지에 해당하는 부분이기도 합니다).

여기서 규칙이 발목을 잡습니다. 기본값을 고쳐도 **이미 열린 가게에는 반영되지 않습니다.** 먼저 연 가게일수록 손님이 많은데, 그 손님들이 계속 옛 메일을 받게 되는 거죠.

## 어떻게 풀었나

### 세 가지 선택지

1. **덮어쓴다** : 고쳐 쓴 문안이 날아간다. 사용자 데이터를 배포가 지우는 셈이라 제외
2. **그대로 둔다** : 먼저 연 가게 손님은 영영 옛 메일. 법적 통지 항목이라 더 곤란
3. **손대지 않은 것만 올린다** : 기본 문안 그대로인 것만 새 기본값으로 바꾼다

3번을 골랐습니다. "손대지 않았다" 는 **현재 내용이 옛 기본값과 글자까지 같다** 로 판정합니다.

### 옛 기본값을 코드에 남겨 둔다

이 판정을 하려면 **옛 기본값이 무엇이었는지** 를 알아야 합니다. 그래서 새 기본값 옆에 옛 기본값을 상수로 남기고, 왜 남겨 뒀는지 주석을 달았습니다. 조건부 갱신은 딱 그 값과 일치할 때만 일어납니다.

```
현재 내용 = 옛 기본값  →  새 기본값으로 바꾼다
그 외(한 글자라도 다름)  →  그대로 둔다
```

### 언제 도는가

가게를 새로 열 때만 도는 코드로는 부족합니다. 이미 열린 가게를 훑어야 하니, 서버가 뜰 때 한 번 도는 채움 작업에 함께 넣었습니다. 여러 번 돌아도 결과가 같고(두 번째부터는 일치하는 문안이 없으니 아무것도 안 바뀜), 실패해도 서버 기동을 막지 않게 감쌌습니다.

## 코드로 보기 (개념 재현)

```java
/** 새 기본 문안. 품목 표와 결제 내역이 들어간다. */
private static final String 새_결제완료_문안 = 머리말
    + "<p><strong>#{손님이름}</strong>님, 결제가 완료되었습니다.</p>"
    + "<p>주문번호 <strong>#{주문번호}</strong><br>결제일시 #{일시}</p>"
    + 품목표          // 상품명·옵션·수량·금액
    + 결제내역        // 상품금액·배송비·할인·쿠폰·적립금·결제금액
    + 맺음말;

/**
 * 품목이 없던 시절의 문안. 이 문안 그대로인 가게만 새 문안으로 올린다.
 * 가게가 자기 말투로 고쳐 쓴 문안을 배포가 덮으면 안 된다.
 */
static final String 옛_결제완료_문안 = 머리말
    + "<p><strong>#{손님이름}</strong>님, 결제가 완료되었습니다.</p>"
    + "<p>주문번호 <strong>#{주문번호}</strong><br>"
    + "결제금액 <strong>#{금액}원</strong><br>"
    + "일시 #{일시}</p>"
    + 맺음말;
```

```java
private void 올리기(UUID 가게id, String 코드, String 옛문안, String 새문안, String 변수목록) {
    sql("""
        update 문안
           set 본문 = :새문안,
               변수 = cast(:변수목록 as jsonb),
               수정시각 = now()
         where 가게id = :가게id
           and 코드 = :코드
           and 본문 = :옛문안        -- ★ 손대지 않은 것만. 한 글자라도 다르면 건너뛴다
        """)
        .param("가게id", 가게id).param("코드", 코드)
        .param("옛문안", 옛문안).param("새문안", 새문안)
        .param("변수목록", 변수목록)
        .update();
}
```

```java
// 가게를 새로 열 때도, 이미 열린 가게를 훑을 때도 같은 함수를 부른다.
public void 기본문안_깔기(가게id 가게) {
    빠진것_채우기(가게);   // 없으면 넣는다 (있으면 건드리지 않는다)
    옛문안_올리기(가게);   // 손대지 않은 기본값만 새 기본값으로
}
```

검증은 양쪽을 다 봅니다. 올라가는가, 그리고 **고쳐 쓴 것이 살아남는가**.

```java
@Test
void 품목이_없던_옛_문안은_새_문안으로_올라간다() {
    기본문안_깔기(가게);
    문안_되돌리기(결제완료, 옛_결제완료_문안);          // 예전 상태로
    문안_바꾸기(주문접수, "우리 가게 말투로 고친 문안 #{주문번호}");

    기본문안_깔기(가게);                                // 배포 때 도는 것과 같은 경로

    assertThat(문안(결제완료)).contains("#{품목}");     // 올라갔다
    assertThat(문안(주문접수)).isEqualTo("우리 가게 말투로 고친 문안 #{주문번호}");   // 그대로다
}
```

## 💡 배운 것

**사용자가 고친 데이터를 배포가 덮으면 안 됩니다.** 기본값을 제공한다는 건 "여기부터 시작하세요" 이지 "우리가 계속 관리합니다" 가 아닙니다.

**그렇다고 기본값을 영영 못 고치면, 먼저 시작한 사용자가 손해를 봅니다.** 두 요구가 충돌하니 **"손대지 않은 것만" 이라는 중간 지대** 가 필요했습니다.

**"손대지 않았다" 를 판정하려면 옛 기본값을 남겨 둬야 합니다.** 지우고 싶은 코드지만, 이게 없으면 판정 자체가 불가능합니다. 주석에 이유를 적어 두지 않으면 다음 사람이 정리하다 지울 겁니다.

**여러 번 돌아도 같은 결과여야 합니다.** 기동할 때마다 도는 작업이라, 두 번째부터는 일치하는 대상이 없어 아무 일도 일어나지 않습니다.

**조용히 안 나가는 기능은 손대기 전에 확인이 필요합니다.** 문안이 없으면 메일은 아무 말 없이 넘어갑니다. 그래서 "기본값이 안 깔린 가게" 는 아무도 눈치채지 못한 채로 남아 있을 수 있습니다.

## 소감

기능을 추가하는 것보다 **이미 쓰고 있는 사람에게 어떻게 도달시킬까** 가 더 오래 걸린 작업이었습니다. 새로 여는 가게는 그냥 새 기본값을 받으면 되는데, 이미 연 가게는 사정이 제각각이니까요.

배포가 사용자 데이터를 건드릴 때는 **"내가 지금 누구 것을 바꾸는가"** 를 한 번 더 생각해야 한다는 걸 배웠습니다. 조건 한 줄(`and 본문 = :옛문안`) 차이로, 그 배포는 개선이 될 수도 있고 사고가 될 수도 있었습니다.

# 2026-11-09 프레임을 한꺼번에 만드는 도구에, 실행 전에 계획만 보여 주는 단계를 먼저 넣었다

> 태그: #개선 #데이터등록 #미리보기실행 #Node.js #관리자API

## 무엇을 / 왜

고객사가 사진 프레임 그림과, 프레임마다 사진이 들어갈 칸의 좌표 파일을 보내 주었습니다. 그런데 관리자에는 이 프레임이 하나도 등록돼 있지 않았습니다. 레이아웃만 9종이고 프레임 그림은 훨씬 많아서, 관리자 화면에서 하나씩 올리면 시간이 오래 걸리고 칸 좌표를 잘못 넣기도 쉬웠습니다.

그래서 리소스 폴더를 읽어 레이아웃, 프레임, 묶음을 관리자 API 로 한꺼번에 만드는 도구를 만들기로 했습니다. 다만 바로 서버에 쓰게 만들면 걱정되는 점이 있었습니다.

- 잘못 읽은 자료로 만든 데이터가 한꺼번에 쌓이면, 하나씩 찾아 지우는 일이 등록보다 더 커질 것 같았습니다.
- 시험 때 만들어 둔 이름이 비슷한 레이아웃이 서버에 남아 있었습니다. 같은 것을 다른 이름으로 한 번 더 만들 위험이 있었습니다.
- 이미 등록된 레이아웃이 자료와 값이 다르면, 덮어써도 되는지 도구가 판단할 수 없었습니다.

## 어떻게 풀었나

도구를 "계획 보기"와 "실행" 두 단계로 나눴습니다.

1. **기본은 읽기만 하도록 했습니다.** 옵션 없이 돌리면 서버에서 조회만 하고 "만들 것 몇 개, 이미 있는 것 몇 개, 뺀 레이아웃"을 보여 주었습니다. 실제로 만들려면 실행 옵션을 따로 줘야 했습니다.
2. **읽기 단계에서는 연결이 쓰기를 거부하게 했습니다.** "읽기 단계에서는 쓰지 않는다"를 코드 여기저기서 지키게 하지 않고, 서버 연결을 만들 때부터 조회가 아닌 요청은 서버에 닿기 전에 막았습니다. 계획 단계 코드에 실수가 있더라도 서버는 바뀌지 않게 한 것입니다.
3. **이미 있으면 건너뛰고, 값이 다르면 덮어쓰지 않게 했습니다.** 같은 이름이 있으면 크기와 칸 정보가 자료와 같은지 비교했습니다. 다르면 계획에서는 [주의]로 보여 주고, 실행에서는 그 자리에서 멈추게 했습니다.
4. **이름이 비슷한 것만 있으면 멈추게 했습니다.** 같은 이름은 없는데 비슷한 이름이 있으면 계획에서는 [주의]로 보여 주고, 실행에서는 멈췄습니다. 새로 만들어도 된다고 확인한 뒤에만, 그렇게 하라는 옵션을 주고 다시 돌리게 했습니다.
5. **멈춰도 다시 돌릴 수 있게 했습니다.** 만든 것과 멈춘 자리를 기록 파일로 남기고, 같은 명령을 다시 돌리면 이미 만든 것은 건너뛰고 이어서 만들게 했습니다.

dev 서버에서 계획을 먼저 보고 실행해 모두 등록했습니다. 회전과 좌표가 분명하지 않은 레이아웃 하나는 빼 두고 고객사에 물었습니다. 다음 날 운영 서버에 같은 도구를 돌렸을 때는, 시험 때 남은 비슷한 이름의 레이아웃 앞에서 도구가 멈췄습니다. 옛 것이 시험용인 것을 확인한 뒤 새로 만들게 해서, 두 데이터가 섞이지 않았습니다.

## 코드로 보기 (개념 재현)

실제 도구의 이름과 주소는 바꿨고, 구조만 옮긴 더미 코드입니다.

```js
// 확인이 필요해서 멈추는 경우를 일반 오류와 나눠 둔다
class StopHere extends Error {}

// 1) 계획 단계면 연결을 만들 때부터 쓰기를 막는다
function connect({ allowWrites }) {
  return {
    async request(method, path, body) {
      // 조회(GET)가 아닌 요청이 계획 단계에서 나오면, 서버에 닿기 전에 여기서 끝난다
      if (method !== 'GET' && !allowWrites) {
        throw new Error(`계획 단계인데 쓰기 요청이 나옴: ${method} ${path}`);
      }
      return callAdminApi(method, path, body); // 실제로는 관리자 API 호출
    },
  };
}

async function importLayouts(items, { write = false, acceptSimilar = false } = {}) {
  const api = connect({ allowWrites: write });
  const plan = { create: 0, exists: 0, warnings: [] };

  for (const item of items) {
    // 2) 이름으로 검색해, 같은 이름과 비슷한 이름을 나눈다
    const found = await api.request('GET', `/layouts?search=${encodeURIComponent(item.name)}`);
    const same = found.filter((l) => l.name === item.name);
    const similar = found.filter((l) => l.name !== item.name);

    // 같은 이름이 둘 이상이면 어느 것인지 고를 수 없으니 멈춘다
    if (same.length > 1) throw new StopHere(`"${item.name}" 이 ${same.length}개 있음`);

    if (same.length === 1) {
      // 3) 이미 있으면 값만 비교한다. 다르면 덮어쓰지 않는다
      const differs = same[0].width !== item.width || same[0].height !== item.height;
      if (differs) {
        const msg = `"${item.name}" 값이 자료와 다름 - 덮어쓰지 않음`;
        if (write) throw new StopHere(msg);
        plan.warnings.push(msg);
      }
      plan.exists++;
      continue; // 있는 것은 건너뛴다. 그래서 멈춘 뒤 다시 돌려도 이어서 만든다
    }

    if (similar.length) {
      // 4) 같은 이름은 없는데 비슷한 이름이 있다
      const msg = `"${item.name}" 은 없지만 비슷한 이름이 있음: ${similar.map((l) => l.name).join(', ')}`;
      if (write && !acceptSimilar) throw new StopHere(msg); // 실행에서는 멈춘다
      plan.warnings.push(msg); // 계획에서는 [주의]로만 보여 준다
    }

    plan.create++;
    if (write) await api.request('POST', '/layouts', item); // 실행일 때만 만든다
  }
  return plan;
}

// 예: 서버에 'PRINT 4x6-3' 은 없고, 시험 때 만든 'TEST PRINT 4x6-3' 만 있다면
//  - 계획: { create: 1, exists: 0, warnings: ['"PRINT 4x6-3" 은 없지만 비슷한 이름이 있음: TEST PRINT 4x6-3'] }
//  - 실행: 그 항목에서 StopHere 로 멈춘다
//  - 확인한 뒤 acceptSimilar 를 켜고 다시 실행하면 새로 만든다
```

## 💡 배운 것

- 데이터를 한꺼번에 만드는 도구는 기본을 읽기만으로 두고, 쓰기는 따로 켜게 만드는 편이 안전하다는 걸 배웠습니다.
- "계획 단계에서는 쓰지 않는다"를 약속으로 지키는 것보다, 쓰기 요청이 나가면 연결이 거부하는 구조로 만드는 편이 실수에 강하다는 걸 배웠습니다.
- 비슷한 이름이 있거나 기존 값이 다른 것처럼 자료가 애매할 때는, 도구가 짐작해서 고르게 하지 않고 멈추게 하는 편이 낫다는 걸 배웠습니다. 실제로 운영 서버에 돌렸을 때 그 멈춤 덕분에 시험 데이터와 섞이지 않았습니다.

## 소감

처음에는 빨리 올리는 것만 생각했는데, 계획 단계를 넣고 나니 실행할 때 오히려 마음이 편했습니다. 계획 결과를 보고 "만들 것"과 "이미 있는 것"이 예상과 맞는지 확인한 뒤에 실행했기 때문입니다. 등록 도구를 만들 때 실행보다 멈춰야 할 때를 먼저 정해 두는 습관을 들이려고 합니다.

# 2026-09-23 5,000행에서 끝난 내보내기가, "완료"라고 말했다

> 태그: #개선 #스트리밍 #다운로드 #데이터정합성

## 무엇을 / 왜

구독을 해지한 스토어 주인은 30일 동안 자기 자료(상품·주문·회원)를 내려받을 수 있어야 합니다. 그래서 관리 화면에 내보내기 기능이 있었어요.

해지 정책을 정리하면서 이 기능이 자료를 정말 다 넘겨주는지 코드를 따라가 봤습니다. 서버는 **5,000줄까지만** 꺼내면서, 화면에는 **"완료"** 를 띄우고 있었어요.

회원이 5,003명인 스토어라면 3명은 파일에 없는데도 "완료"라고 말하는 셈이었습니다.

## 어떻게 풀었나

### 서버가 조용히 잘라내고 있었다

내보내기 코드를 보니 조회에 상한이 걸려 있었습니다.

```sql
select ... from members where tenant_id = :tenant order by id limit 5000
```

메모리가 넘치지 않게 넣어 둔 상한이었을 텐데, **잘렸다는 사실을 아무 데도 알리지 않았습니다.** 5,000줄을 다 쓰고 나면 정상 종료했고, 화면은 "완료"를 표시했어요.

해지한 스토어가 이 파일만 믿고 떠나면, 5,001번째 회원부터는 영영 못 가져가는 겁니다.

### 한 번에 읽지 말고 흘려보냈다

상한을 그냥 없애면 큰 스토어에서 서버 메모리가 넘칩니다. 그래서 **100줄씩 읽어서 읽는 대로 바로 보내는** 방식으로 바꿨습니다. 전체를 메모리에 올리지 않으니 줄 수에 상한을 둘 이유가 없어졌어요.

### "HTTP 200"은 "파일이 다 왔다"가 아니다

상한을 없애고 나니 다른 걱정이 생겼습니다. 흘려보내는 방식은 **응답을 먼저 시작**합니다. 상태 코드 200은 첫 줄을 보내기 전에 이미 나가요. 그러니 중간에 서버가 죽거나 연결이 끊겨도, 브라우저 입장에서는 "200을 받았고, 파일이 좀 짧게 끝났다" 로 보입니다.

**반쪽짜리 파일이 정상 파일처럼 저장될 수 있는** 상황이었어요.

그래서 서버와 화면이 약속을 하나 했습니다.

1. 서버는 시작할 때 무작위 번호 하나를 만들어 응답 머리(헤더)에 실어 보낸다.
2. 자료를 다 보낸 뒤, **맨 마지막에 그 번호가 들어간 완료 표식 한 줄**을 붙인다.
3. 화면은 받는 동안 **끝부분을 잠시 붙잡아 두고**, 다 받은 뒤 끝이 정확히 그 표식인지 확인한다.
4. 표식이 맞으면 그 줄을 떼고 저장을 마친다. 맞지 않으면 **"끝까지 받지 못했습니다"** 로 실패 처리한다.

중간에 끊기면 마지막 표식이 절대 오지 않으니, 반쪽 파일이 완료로 저장될 수 없습니다.

### 받는 동안에도 권한을 다시 본다

큰 파일은 몇 분씩 걸립니다. 그 사이에 직원이 권한을 잃거나, 화면에서 다른 스토어로 전환할 수 있어요. 시작할 때 한 번만 확인하면 그 몇 분 동안은 막을 수가 없습니다. 그래서 **받는 도중에도 몰·권한을 다시 확인**하고, 바뀌었으면 중단하게 했습니다.

## 코드로 보기 (개념 재현)

서버 쪽입니다. 100줄씩 읽어 보내고, 끝에 표식을 붙입니다.

```java
String completion = UUID.randomUUID().toString();
response.setHeader("X-Export-Completion", completion);

try (var out = response.getOutputStream()) {
    UUID after = null;
    while (true) {
        List<Row> page = repository.nextPage(tenantId, after, 100);   // 100줄씩
        if (page.isEmpty()) break;
        for (Row row : page) out.write(csvLine(row));
        out.flush();                                                  // 읽는 대로 흘려보낸다
        after = page.get(page.size() - 1).id();
    }
    // 여기까지 왔다는 건 전부 보냈다는 뜻이다. 중간에 끊기면 이 줄은 절대 나가지 않는다.
    out.write(("\n--export-complete:" + completion + "\n").getBytes(UTF_8));
}
```

화면 쪽입니다. 끝부분을 표식 길이만큼 붙잡아 두고, 나머지만 저장으로 넘깁니다.

```ts
function verifiedExport(body: ReadableStream<Uint8Array>, completion: string) {
  const footer = new TextEncoder().encode(`\n--export-complete:${completion}\n`);
  let tail = new Uint8Array();   // 아직 저장으로 넘기지 않은 끝부분

  return body.pipeThrough(new TransformStream({
    transform(chunk, controller) {
      const joined = concat(tail, chunk);
      const release = joined.byteLength - footer.byteLength;
      if (release > 0) controller.enqueue(joined.subarray(0, release));   // 표식일 수 없는 앞부분은 저장
      tail = joined.subarray(Math.max(release, 0));                       // 끝부분은 계속 붙잡는다
    },
    flush() {
      // 다 받은 뒤 끝이 정확히 표식인지 확인. 아니면 반쪽 파일이다.
      if (!sameBytes(tail, footer)) throw new Error("끝까지 받지 못했습니다");
      // 표식 줄은 저장하지 않는다. 사용자가 받는 파일에는 자료만 남는다.
    }
  }));
}
```

## 💡 배운 것

**상한을 두면 잘렸다는 사실도 알려야 합니다.** 5,000이라는 숫자 자체보다, 잘렸는데 "완료"라고 말한 게 문제였습니다. 조용히 자르는 코드는 틀린 결과를 정상처럼 보이게 만듭니다.

**전부 읽지 않고 흘려보내면 상한이 필요 없어집니다.** 메모리 때문에 건 상한이었다면, 메모리를 안 쓰는 방식으로 바꾸는 게 근본적인 해결이었습니다.

**흘려보내기에서 200은 시작 신호일 뿐입니다.** 상태 코드는 첫 바이트 전에 나가니까, 끝까지 왔는지는 따로 확인해야 합니다. 서버가 마지막에만 보낼 수 있는 표식을 두고, 받는 쪽이 그걸 확인하는 방식이 간단하면서도 확실했습니다.

**오래 걸리는 작업은 중간에도 권한을 다시 봅니다.** 시작 시점의 확인만으로는 몇 분 동안 바뀐 상황을 막을 수 없습니다.

## 소감

"완료"라는 두 글자가 사실이 아닐 수 있다는 게 이번 작업에서 가장 오래 남았습니다. 화면에 뜬 "완료"는 결국 코드가 끝났다는 뜻이지, 자료가 다 전달됐다는 뜻은 아니었어요.

5,003명과 상품 옵션 105개, 부분 환불 자료까지 넣은 테스트로 전체가 끝까지 오는 것과, 중간에 끊겼을 때 완료로 저장되지 않는 것을 확인했습니다. 다만 이건 **받는 시점의 자료를 내보내는 기능**이지, 특정 시점을 그대로 얼려 둔 백업과는 다르다는 점도 따로 적어 두었습니다.

# 2026-10-07 설정 저장이, 보내지 않은 칸까지 지웠다

> 태그: #개선 #API #JSON #기본값 #부분수정 #Spring

## 무엇을 / 왜

정산 설정(결제수수료율·정산 주기)을 운영자 화면에서 바꿀 수 있게 하려다 두 가지를 발견했습니다.

1. **설정을 저장한 적이 없는 상점은 조회가 500 오류였습니다.** 조회 코드가 저장된 설정 목록에서 "기본" 설정을 찾고, 없으면 예외를 던졌습니다. 정작 정산 계산은 설정이 없으면 기본값(결제수수료 2.5%, 구매확정 후 15일)을 쓰고 있었는데, 화면은 그 값을 보여 줄 수 없었습니다.
2. **저장은 받은 JSON 으로 설정을 통째로 갈아 끼웠습니다.** 화면이 "정산 주기" 만 보내면 결제수수료율 칸이 빠진 채 저장되고, 읽을 때 빠진 칸은 0으로 읽혔습니다. 결제수수료 없이 정산될 수 있었습니다.

이 API 를 부르는 화면이 아직 없어서 두 문제 모두 드러나지 않고 있었습니다.

## 어떻게 풀었나

- **조회:** 저장된 값이 없으면 정산 계산이 쓰는 것과 같은 기본값을 돌려줍니다. 기본값을 두 군데에 따로 적지 않고 같은 기본 정책을 씁니다.
- **저장:** 지금 값(없으면 기본값)을 먼저 읽고, 받은 칸만 덮어쓴 뒤(merge) 검사하고 저장합니다. 보내지 않은 칸은 지금 값 그대로입니다.
- **검사:** 결제수수료율 0~10%, 정산 주기 0~90일 정수만 받습니다. 범위를 벗어나면 400과 함께 무엇을 고쳐야 하는지 알려 줍니다.
- **읽기 대체값:** 저장된 JSON 에 결제수수료 칸이 없으면 0이 아니라 기본 2.5%로 읽게 바꿨습니다.

## 코드로 보기 (개념 재현)

```java
@Transactional(readOnly = true)
public Policy current(String key) {
    // 저장한 적이 없으면, 정산 계산과 같은 기본값을 준다
    return repository.find(key).orElseGet(() -> Policy.defaults(Tenant.current()));
}

@Transactional
public Policy update(String key, JsonNode changes) {
    if (changes == null || !changes.isObject()) {
        throw badRequest("정산 정책 형식이 올바르지 않습니다");
    }
    // 지금 값(없으면 기본값 JSON)에 받은 칸만 덮어쓴다 - 보내지 않은 칸은 그대로
    ObjectNode merged = ((ObjectNode) repository.rawValue(key)).deepCopy();
    merged.setAll((ObjectNode) changes);
    validate(merged);
    return repository.save(key, merged);
}

private static void validate(JsonNode policy) {
    JsonNode cycle = policy.path("cycleDays");
    if (!cycle.isIntegralNumber() || cycle.asInt() < 0 || cycle.asInt() > 90) {
        throw badRequest("정산 주기는 구매확정 후 0~90일 사이로 정해 주세요");
    }
    BigDecimal payFee;
    try {
        payFee = new BigDecimal(policy.path("payFee").asText(""));
    } catch (NumberFormatException e) {
        throw badRequest("결제수수료율을 숫자로 넣어 주세요");
    }
    if (payFee.signum() < 0 || payFee.compareTo(BigDecimal.TEN) > 0) {
        throw badRequest("결제수수료율은 0~10% 사이로 정해 주세요");
    }
}
```

테스트는 세 가지를 봅니다.

```java
@Test
void 정책이_없으면_기본값이고_보낸_칸만_바뀌고_범위를_벗어나면_막는다() {
    deletePolicy();
    assertThat(policies.current("default").payFeePercent()).isEqualByComparingTo("2.5");

    Policy changed = policies.update("default", json("{\"cycleDays\": 7}"));
    assertThat(changed.cycleDays()).isEqualTo(7);
    assertThat(changed.payFeePercent()).isEqualByComparingTo("2.5");   // 보내지 않은 칸은 그대로

    assertThatThrownBy(() -> policies.update("default", json("{\"payFee\": 12}")))
        .isInstanceOf(ResponseStatusException.class);
    assertThat(policies.current("default").cycleDays()).isEqualTo(7);   // 막힌 저장은 아무것도 바꾸지 않는다
}
```

## 💡 배운 것

**"값이 없음" 을 화면과 계산이 똑같이 해석해야 합니다.** 계산은 기본값을 쓰는데 화면은 오류를 내면, 운영자는 지금 무엇이 적용되는지 알 수 없습니다.

**부분 수정과 전체 교체는 다른 약속입니다.** 화면이 일부만 보내는 API 가 전체 교체로 저장하면, 보내지 않은 칸이 사라집니다. 지금 값에 받은 칸만 합치는 방식이 화면과 서버 모두에 안전했습니다.

**빠진 칸의 대체값은 0이 아니라 안전한 기본값이어야 합니다.** 돈 계산에서 0은 오류 없이 틀린 값이 됩니다.

## 소감

설정 화면 하나를 붙이려다, 그 화면이 부를 API 가 처음부터 쓸 수 없는 상태였다는 걸 알았습니다. 부르는 곳이 없으면 고장도 드러나지 않는다는 걸 다시 느꼈습니다. 기본값 조회, 보낸 칸만 바꾸기, 범위 검사는 테스트로 확인했습니다.

# 2026-10-14 판매자에게 환불 버튼은 주되, 금액은 정하지 않게 했다

> 태그: #개선 #권한 #API설계 #Spring #트랜잭션

## 무엇을 / 왜

상점에는 상점 주인(오너)과, 자기 상품을 올리고 직접 보내는 **입점 판매자**가 있습니다. 반품 물건은 판매자의 반품지로 가는데, 반품 완료(손님 환불)·교환 완료·판매 취소는 오너만 할 수 있었어요. 판매자가 물건을 받아 오너에게 알리고, 오너가 다시 처리해야 했습니다. 반품 상품을 받은 날부터 3영업일 안에 환불해야 하는 규정도 있고요.

그래서 판매자가 자기 품목을 직접 처리하게 했습니다. 다만 **손님 돈이 판매자의 버튼으로 움직이는 일**이라, 무엇을 넘기고 무엇을 넘기지 않을지 먼저 정했어요.

## 어떻게 풀었나

- **넘긴 것은 "버튼"뿐:** 돈이 나가는 길은 새로 만들지 않았습니다. 판매자 API 는 확인만 하고, 실제 처리는 오너가 누를 때와 **같은 주문 서비스 메서드**를 부릅니다. 환불 금액·재고 복원·적립금·정산 회수가 누가 누르든 같아요.
- **금액은 서버가 정함:** 판매자는 금액을 보내지 않습니다. 처리 창의 "환불 예정 금액"도 실제 환불과 **같은 계산 함수**에서 나와, 미리 본 금액과 실제 금액이 어긋나지 않아요.
- **막는 조건은 서버에서:**
  - 남의 품목은 403이 아니라 **404**. 있는지조차 알려 주지 않습니다.
  - 오너가 그 판매자의 처리를 꺼 둔 경우, 승인 전 판매자, 구매확정 뒤 반품(정산이 걸려 있음), 계좌이체 결제의 반품(오너가 직접 이체)은 403과 **이유**를 보내, 화면이 버튼 대신 안내를 보여 줍니다.
- **동시에 누르는 경우:** 주문 행을 잠그고(`SELECT ... FOR UPDATE`) 상태를 다시 확인한 뒤 처리합니다. 오너와 판매자가 같은 품목을 동시에 눌러도 한 번만 환불돼요.
- **누가 했는지 남기기:** 처리 기록에 처리한 판매자를, 감사 기록에 판매자·IP·금액을 남기고, 오너 화면 품목 줄에 "판매자 처리"와 시각을 보여 줍니다.
- **오너의 스위치:** 판매자별로 처리를 끌 수 있고(기본 켜짐), 꺼도 오너는 언제든 대신 처리합니다.

## 코드로 보기 (개념 재현)

```java
@Transactional
public RefundResult completeReturn(long sellerId, UUID itemId, String ip) {
    // 1) 주문 행을 잠그고 품목을 읽는다. 내 품목이 아니면 404 (남의 주문이 있는지도 알리지 않는다)
    ItemRow item = itemRepo.findForUpdate(itemId)
        .filter(row -> row.sellerId() == sellerId)
        .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));

    // 2) 처리할 수 있는 판매자인지 (승인됨 + 오너 스위치 켜짐)
    Seller seller = sellerRepo.get(sellerId);
    if (!seller.approved() || !seller.canHandleReturns()) {
        throw forbidden("운영자가 처리하도록 설정된 판매자예요.");
    }

    // 3) 오너 몫인 경우는 이유와 함께 거절한다 (화면은 버튼 대신 이 문장을 보여 준다)
    if (item.purchaseConfirmed()) throw forbidden("구매확정 뒤 반품은 운영자가 처리해요.");
    if (item.paidByBankTransfer()) throw forbidden("계좌이체 결제의 환불은 운영자가 처리해요.");

    // 4) 돈은 오너와 같은 길로: 금액 계산·환불·재고·적립금이 이 메서드 하나에 있다
    RefundResult result = orderService.completeItemRefund(
        item.orderId(), itemId, Actor.seller(sellerId));

    // 5) 누가, 어디서, 얼마를 처리했는지
    audit.write("seller.return_complete", sellerId, ip,
        Map.of("itemId", itemId, "amount", result.cashRefund()));
    return result;
}

// 처리 창의 미리보기도 실제 환불과 같은 계산 함수를 쓴다 (미리 본 금액 = 실제 금액)
@Transactional(readOnly = true)
public RefundPreview previewItemRefund(UUID orderId, UUID itemId) {
    return RefundPreview.from(refundCalculator.split(orderId, itemId));
}

private static ResponseStatusException forbidden(String reason) {
    return new ResponseStatusException(HttpStatus.FORBIDDEN, reason);
}
```

테스트는 반품 금액이 오너 경로와 같은지, 남의 품목은 404인지, 스위치를 끄면 403이고 오너는 그대로 처리되는지, 구매확정 뒤·계좌이체가 막히는지, 다른 판매자가 먼저 보낸 주문에서 아직 안 보낸 내 품목만 취소되는지 등 13가지를 통합 테스트로 봤습니다.

## 💡 배운 것

**권한을 넘기는 것과 계산을 넘기는 것은 다릅니다.** 판매자에게는 "언제 누를지"만 넘기고, "얼마를"은 서버의 한 곳에 남겼어요. 처리하는 사람이 늘어도 돈 계산은 하나입니다.

**막을 때는 이유를 같이 보냅니다.** 403만 보내면 화면은 "권한이 없어요"밖에 말할 수 없어요. 이유를 보내니 화면이 버튼 대신 "구매확정 뒤 반품은 운영자가 처리해요"를 보여 줄 수 있었습니다.

**없는 것과 못 하는 것을 구분합니다.** 남의 품목은 404, 내 품목이지만 지금 못 하는 건 403. 남의 주문이 있는지는 알려 줄 필요가 없으니까요.

**미리보기와 실제 처리는 같은 함수에서 나와야 합니다.** 화면용 계산을 따로 만들면 언젠가 어긋납니다.

## 소감

처음에는 "판매자가 환불 버튼을 눌러도 될까"가 걱정이었는데, 나눠 보니 걱정의 대부분은 "금액을 누가 정하느냐"였습니다. 그 부분을 서버 한 곳에 묶어 두니, 버튼을 넘기는 일은 생각보다 단순해졌어요.

# 2026-08-12 장애를 보는 화면이 가짜 장애를 보여주고 있었다 - 화면은 다 있는데 진짜인 게 없었다

> 태그: #개선 #운영 #SSE #관측성

## 오늘 한 일 (요약)
- 운영 화면을 점검하다가, 서비스에 문제가 생겼을 때 보라고 만든 화면 **23개가 전부 예시 데이터**인 걸 알았다.
- 실시간 지표 화면은 숫자가 1초마다 움직여서 진짜처럼 보였는데, **화면이 스스로 무작위 숫자를 만들고** 있었다.
- 위험한 작업(쇼핑몰 정지 등)의 확인 절차도 다 만들어져 있었는데, **버튼에 눌렀을 때 할 일이 연결돼 있지 않았다.**
- 서버에는 필요한 기능이 전부 있었다. 화면이 한 번도 부르지 않았을 뿐이다.

## 버튼이 아무 일도 하지 않았다

먼저 눈에 띈 건 확인 절차였다. 위험한 작업에는 이런 게 붙어 있었다.

- 체크박스 두 개 ("문의 내용을 확인했다", "이 작업이 기록에 남는 데 동의한다")
- `CONFIRM` 이라고 직접 입력해야 버튼 활성화

꼼꼼하게 잘 만들었다고 생각했다. 그런데 다 채우고 눌러도 **아무 일도 일어나지 않았다.**

```tsx
<button
  className="..."
  disabled={!enabled}
  type="button"       // ← onClick 이 없다
>
  <Fingerprint className="h-4 w-4" />
  {actionLabel}
</button>
```

처음엔 서버 기능이 아직 없는 줄 알았다. 확인해 보니 있었다. 그것도 이렇게.

```java
public record TenantStatusPatchRequest(
    @NotBlank String status,
    @NotBlank String reason,
    @NotBlank String confirmText   // ← 화면에서 CONFIRM 을 받으라고 만들어 둔 것
) {}
```

**서버는 "사용자가 CONFIRM 이라고 입력했는지"까지 받도록 설계돼 있었다.** 화면과 서버가 서로를 기다리고 있었던 셈이다.

## 껍데기가 다시 안 생기게

연결하면서 하나 바꿨다. 실행할 함수를 **선택이 아니라 필수**로 만들었다.

```tsx
type OpsRiskActionProps = {
  title: string;
  actionLabel: string;
  auditTarget: string;
  /** 사유·확인문구를 받아 실제 작업을 수행한다. */
  onConfirm: (input: { reason: string; confirmText: string }) => Promise<OpsRiskResult>;
};
```

이제 실행할 게 없으면 이 위젯을 **화면에 둘 수 없다.** 타입이 막는다.

같은 방식으로 화면을 훑으니 아무 동작 없는 버튼이 여덟 군데 더 있었다. 지금 붙일 수 있는 건 붙이고, 서버 쪽이 준비 안 된 건 **버튼을 지웠다.** 눌러도 안 되는 버튼을 남겨두는 것보다 없는 게 정직하다고 봤다.

## 숫자도 가짜였다

더 신경 쓰인 건 숫자였다.

요금표가 화면 코드에 배열로 적혀 있었다.

```tsx
const plans = [
  ["starter",   "KRW 49,000",  "market",          "self serve"],
  ["standard",  "KRW 149,000", "market + seller", "default"],
  // ...
];
```

실제 판매 가격은 데이터베이스에 있다. **여기 숫자가 낡으면 운영자가 틀린 가격을 보고 판단한다.** 서버에서 가져오게 바꿨다.

대시보드는 더 심했다.

```java
new OpsMetricResponse("mrr", "MRR", currency(today.mrrBooked()), "+4.8%", "good"),
new OpsMetricResponse("activeTenants", "Active tenants", ..., "+2", "good"),
```

매출 값은 진짜인데 **그 옆의 증감률이 상수**였다. 매출이 오르든 내리든 화면에는 늘 "+4.8%"가 떠 있었다. 지우고, 지금 셀 수 있는 사실만 적었다("현재 청구 기준").

틀린 숫자를 보여주느니 안 보여주는 게 낫다.

## 실시간 지표는 난수였다

제일 그럴듯했던 화면이다. 숫자가 1초마다 살아 움직였다.

```tsx
useEffect(() => {
  const timer = window.setInterval(() => setTick((v) => v + 1), 1_000);
  return () => window.clearInterval(timer);
}, []);

useEffect(() => {
  setMetric(systemMetricSample(tick));   // ← 화면이 만들어내는 표본
}, [tick]);
```

바로 아래에 진짜 서버 스트림에 연결하는 코드도 있었다. 그런데 **1초 타이머가 계속 덮어쓰고** 있어서 실제 값이 와도 곧바로 지워졌다.

그리고 그 연결은 애초에 되지도 않았다. 이유가 흥미로웠다.

## 브라우저가 토큰을 못 싣는다

서버가 계속 밀어주는 방식(Server-Sent Events)을 브라우저에서 받을 때는 `EventSource`를 쓴다.

```ts
const source = new EventSource("/api/v1/ops/system/metrics/realtime");
```

그런데 이 API는 인증 토큰을 요구한다. **`EventSource`는 헤더를 붙일 수 없다.** `fetch`처럼 `Authorization`을 실을 방법이 없다. 게다가 우리 토큰은 자바스크립트가 못 읽는 쿠키에 들어 있다(그렇게 두는 게 맞다).

그래서 **우리 서버가 대신 받아서 브라우저로 흘려보내는 통로**를 만들었다.

```ts
export async function GET(request: NextRequest) {
  const stored = await readOpsStored();          // 서버에서만 읽히는 쿠키
  if (!stored) return new NextResponse("unauthorized", { status: 401 });

  const upstream = await fetch(`${API_BASE_URL}/api/v1/ops/system/metrics/realtime`, {
    headers: { Authorization: `Bearer ${stored.token}`, Accept: "text/event-stream" },
    cache: "no-store",
    signal: request.signal                        // 브라우저가 끊으면 위쪽도 끊는다
  });

  return new NextResponse(upstream.body, {        // 받은 스트림을 그대로 흘려보낸다
    headers: { "Content-Type": "text/event-stream", "Cache-Control": "no-cache, no-transform" }
  });
}
```

`upstream.body`를 그대로 응답 본문으로 넘기면 중간에 모아두지 않고 흘러간다. 브라우저는 인증 없는 우리 주소를 부르고, 인증은 서버가 붙인다.

그리고 가짜 표본을 만들던 타이머는 지웠다. 대신 **연결이 끊기면 끊겼다고 화면에 쓴다.**

```tsx
{connected ? "실시간 연결됨" : "연결 끊김 — 마지막으로 받은 값입니다"}
```

## 번역을 나중으로 미룬 이유

이 화면들은 영어로 되어 있어서 한글로 바꾸는 작업도 있었다. 예시 데이터인 화면들은 **일부러 번역을 미뤘다.**

가짜 숫자를 한글로 옮기면 **더 완성된 것처럼 보이기만 하기** 때문이다. 실제 데이터를 연결하면서 같이 한글로 바꿨다.

## 없는 것과 실패한 것을 구분하기

연결하면서 정한 원칙이 하나 있다. 데이터가 없을 때 **빈 화면을 두지 않는 것**이다.

```tsx
{groups.length === 0 ? (
  <p className="text-sm text-neutral-500">수집된 오류가 없습니다.</p>
) : (
  <GroupTable groups={groups} />
)}
```

빈 화면만 뜨면 "정말 없는 건지, 조회가 실패한 건지" 알 수 없다. 확인하러 들어온 사람이 화면을 못 믿게 되면 그 화면은 없는 것과 같다.

## 배운 것
- **화면이 완성돼 보이는 것과 동작하는 것은 다르다.** 확인 절차까지 정교하게 만들어 놓고 정작 실행이 연결 안 된 경우가 있다.
- 껍데기를 막으려면 **타입으로 강제한다.** 실행 함수를 필수 인자로 두면 빈 버튼을 만들 수 없다.
- **화면에 뜨는 숫자는 출처를 확인한다.** 값은 진짜인데 옆에 붙은 증감률만 가짜인 경우가 제일 위험하다. 전체가 가짜면 눈치채는데, 섞여 있으면 못 챈다.
- `EventSource`는 **헤더를 실을 수 없다.** 인증이 필요한 스트림은 서버가 중계한다.
- 확인용 화면은 **정확성이 전부다.** 장애를 보러 들어온 화면이 가짜를 보여주면, 그건 없느니만 못하다.
- **"없음"과 "실패"를 화면에서 구분해서 쓴다.**

# 2026-08-06 두 화면을 따로 만들 뻔했다 - 겹치는 UI를 공용 부품 한 벌로

> 태그: #개선 #프론트엔드 #리팩터링 #재사용

## 오늘 한 일 (요약)
- 손님용 "짧은 세로 영상(숏폼)" 시청 화면을 새로 짰다. 곧이어 "라이브 방송 시청 화면도 똑같이 해달라"는 요청이 왔다(라이브는 나중에 앱에서도 재사용).
- 라이브 화면을 따로 하나 더 만들면 빨랐지만, 그러면 오른쪽 상품/댓글/추천 패널, 공유창, 액션 버튼을 두 벌 유지하게 된다.
- 겹치는 부분을 공용 부품 한 파일로 빼서 두 화면(과 앞으로 앱)이 같은 부품을 쓰게 했다.
- 이미 검증이 끝난 숏폼 화면은 건드리지 않고, 라이브/신규만 공용 부품을 쓰게 해서 회귀 위험을 피했다.

## 무엇을 / 왜
두 화면은 겉보기엔 비슷하다. 세로 영상이 왼쪽에 있고, 오른쪽에 상품/댓글/추천 패널이 있고, 공유창과 액션 버튼(좋아요/공유/더보기)이 붙는다. 실제로 요청도 "숏폼처럼 똑같이"였다.

여기서 그냥 라이브 화면을 새로 하나 만들면 당장은 제일 빠르다. 문제는 그 다음이다. 공유창 문구 하나 바꾸려 해도 두 군데를 고쳐야 하고, 한쪽만 고치고 다른 쪽을 잊으면 두 화면이 조금씩 달라진다. 게다가 "앱에서도 재사용"이라는 조건까지 있어서, 복제해두면 나중에 세 군데(숏폼/라이브/앱)가 제각각 될 위험이 있었다.

그래서 목표를 "빨리 하나 더"가 아니라 "겹치는 걸 한 벌로"로 잡았다.

## 어떻게 풀었나 - 공통과 차이를 먼저 가르기
무작정 합치는 게 아니라, **무엇이 같고 무엇이 다른지**부터 갈랐다.

- **같은 것(공용 부품으로):** 상품 카드, 상품 전체보기 오버레이, 추천 목록, 공유창, 더보기 메뉴, 목록 끝 안내. 이건 데이터 모양만 맞으면 두 화면에서 똑같이 쓸 수 있다.
- **다른 것(각자 두기):** 숏폼은 여러 영상을 위아래로 넘기는 피드, 라이브는 단일 방송 + 실시간 채팅. 이 "영상 소스와 넘김 방식"은 서로 다르니 화면별로 남긴다.

공용 부품이 두 화면에서 같은 상품 카드를 그리려면, 상품 데이터가 서로 다른 형태로 들어와도 되게 해야 했다. 그래서 공용 부품은 **화면에 필요한 최소한의 모양(정규화된 형태)**만 받도록 정의하고, 각 화면이 자기 데이터를 그 모양으로 바꿔 넘기게 했다.

또 하나 신경 쓴 건 **안전하게 옮기기**였다. 숏폼 화면은 이미 손님 확인까지 끝난 상태라, 이걸 공용 부품으로 바꾸다 잘못 건드리면 멀쩡하던 화면이 깨진다. 그래서 이번엔 **숏폼은 그대로 두고, 새로 만드는 라이브만 공용 부품을 쓰게** 했다. 공용화의 이득(한 곳에서 관리)은 새 화면부터 바로 얻고, 검증된 화면을 공용 부품으로 옮기는 건 나중에 별도로 하기로 했다.

## 코드로 보기 (개념 재현)
```tsx
// 공용 부품 한 파일 - 두 화면이 같이 쓴다
// shared/media-panel.tsx
export type PanelProduct = {          // 화면에 필요한 "최소한의 모양"
  id: string; name: string; price: number; image?: string;
};
export function ProductCard({ p }: { p: PanelProduct }) { /* ... */ }
export function ShareModal({ url, title, onClose }: { /* ... */ }) { /* ... */ }
export function Recommendations({ items }: { items: PanelProduct[] }) { /* ... */ }

// 숏폼 화면 - 자기 데이터를 공용 부품 모양으로 바꿔 넘긴다
import { ProductCard, ShareModal } from "../shared/media-panel";
const panelItems = shortformGoods.map(g => ({ id: g.id, name: g.name, price: g.price, image: g.images[0] }));

// 라이브 화면 - 데이터 출처만 다르고, 그리는 부품은 동일
import { ProductCard, ShareModal } from "../shared/media-panel";
const panelItems = liveProducts.map(p => ({ id: p.goodsId, name: p.name, price: p.price, image: p.image }));
```

핵심은 **공용 부품이 특정 화면의 데이터 형태에 묶이지 않게** 하는 것이다. "정규화된 최소 모양"만 받게 해두면, 데이터가 어디서 오든(숏폼이든 라이브든 앱이든) 같은 부품으로 그릴 수 있다.

## 💡 배운 것
- "빨리 하나 더 복제"는 지금은 빠르지만 **수정 지점이 늘어난다**. 겹치는 게 뚜렷하면 공용 부품 한 벌이 결국 싸다.
- 합치기 전에 **공통과 차이를 먼저 가른다**. 다른 부분(영상 소스/넘김 방식)까지 억지로 합치면 오히려 복잡해진다.
- 공용 부품은 **특정 화면 데이터에 묶지 말고 최소 모양만** 받게 한다. 그래야 세 번째, 네 번째 화면이 붙어도 그대로 쓴다.
- **이미 검증된 화면은 나중에 옮긴다.** 공용화 이득은 새 화면부터 얻고, 멀쩡한 걸 건드리는 위험은 분리한다.

## 소감
요청은 "라이브도 똑같이"였지만, 진짜 결정은 "똑같은 걸 한 벌로 둘까 두 벌로 둘까"였다. 복제가 당장 편해 보여도, 나중에 세 화면이 조금씩 어긋나는 그림이 그려져서 공용화를 골랐다. 대신 검증된 화면은 안 건드리고 새것부터 적용해, 이득은 챙기되 위험은 미룬 게 스스로 괜찮은 선택이었다고 느낀다.

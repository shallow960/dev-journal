# 2026-10-29 자동 취소된 주문을 손님 목록에서 빼려다, 약관을 보고 이름을 붙였다

> 태그: #개선 #주문 #약관 #상태기록 #SQL #Spring

## 무엇을 / 왜

쇼핑몰 주문서에서 "결제하기"를 누르면 주문이 먼저 만들어지고 결제창이 열렸습니다. 손님이 결제창을 닫고 떠나면 그 주문은 15분 뒤에 자동으로 취소되게 해 두었습니다. 재고·쿠폰·적립금을 계속 붙잡고 있지 않게 하려는 장치였습니다.

그런데 이렇게 취소된 주문이 손님의 주문내역에 '취소완료'로 남아 있었습니다. 손님은 취소한 적이 없는데 취소된 주문이 보이니, 무엇을 잘못 눌렀나 하고 헷갈릴 만했습니다.

## 어떻게 풀었나

### 처음에는 목록에서 빼려고 했습니다

돈이 오가지 않은 주문이라 손님이 볼 일이 없다고 생각했습니다. 다른 쇼핑몰 빌더도 결제에 실패한 주문은 주문 목록에 두지 않는다는 걸 확인하고, 결제가 확인된 적 없는 취소 주문을 손님 목록에서 빼게 고쳤습니다.

결제창을 열기만 해도 가는 '주문 접수' 메일도 빼려고 했습니다. 결제한 손님은 몇 초 사이에 메일을 두 통 받고, 그만둔 손님은 접수 메일만 받은 채 주문이 15분 뒤 조용히 사라졌기 때문입니다. 결제가 끝났을 때 가는 '결제 완료' 메일 하나면 된다고 봤습니다.

### 약관을 읽어 보니, 둘 다 손님에게 약속한 것이었습니다

메일과 이어진 곳(메일 문안, 알림 설정, 도움말)을 찾다가 쇼핑몰 이용약관에서 이 메일을 말하는 문장을 찾았습니다. 약관에는 이런 내용이 있었습니다.

- 주문서에서 '결제하기'를 눌러 주문이 생긴 때부터 15분 안에 결제를 마치지 않으면 주문은 자동으로 취소된다.
- 결제 시간 초과로 자동 취소된 주문은 주문내역에서 확인할 수 있다.
- 주문 접수·결제 완료·상품 발송·배송완료 안내는 손님의 이메일로 보낸다.

목록에서 빼면 둘째 문장과, 메일을 빼면 셋째 문장과 어긋났습니다. 약관은 손님이 동의하고 들어온 약속이라 화면과 메일이 그와 다르게 움직이면 안 된다고 판단했습니다. 그래서 목록에서 빼던 것은 되돌리고, 메일도 그대로 두었습니다.

### 숨기는 대신 이름을 붙였습니다

다시 보니 헷갈리는 까닭은 주문이 보이는 것이 아니었습니다. 손님이 한 취소와 시스템이 한 취소가 같은 '취소완료'라는 이름을 쓰고 있었기 때문이었습니다.

다행히 주문 상태가 바뀔 때마다 누가(손님·관리자·시스템) 어떤 이유로 바꿨는지를 상태 기록에 남기고 있었습니다. 자동 취소 작업은 늘 처리자를 '시스템'으로, 이유를 "결제를 마치지 않아 자동 취소"로 남겼습니다. 이 기록으로 자동 취소된 주문만 골라 '결제 시간 초과 취소'라는 이름을 붙였습니다. 이름은 약관의 표현에서 가져왔습니다. 손님이 결제 전에 직접 취소한 주문은 그대로 '취소완료'로 두었습니다.

목록에는 주문이 여러 개라서, 주문마다 기록을 따로 묻지 않고 목록에 나온 주문 번호를 한 번에 넘겨 해당하는 번호만 받아 오게 했습니다.

### 주문 접수 메일에는 미리 알렸습니다

'주문 접수' 메일 끝에는 "15분 안에 결제를 마치지 않으면 주문은 자동으로 취소되고, 쓰려던 쿠폰·적립금은 돌아가며 대금은 청구되지 않는다. 취소된 주문은 주문내역에서 확인할 수 있다"는 안내를 붙였습니다. 쇼핑몰 주인이 메일 문안을 고쳐 두었을 수 있어서, 기본 문안을 그대로 쓰는 쇼핑몰만 바꿨습니다.

## 코드로 보기 (개념 재현)

```java
// 자동 취소 작업은 상태를 바꿀 때 처리자와 이유를 함께 남긴다 (개념 재현 - 실제 이름과 다름)
public static final String REASON = "결제를 마치지 않아 자동 취소";

orders.cancel(order.id(), Actor.SYSTEM, REASON);
```

```java
// 상태 기록에서 '시스템이 결제 시간 초과로 취소한' 주문만 고른다
public Set<UUID> timedOut(Collection<UUID> orderIds) {
    if (orderIds.isEmpty()) {
        return Set.of();                          // 빈 목록이면 묻지 않는다 (in () 는 SQL 문법 오류)
    }
    return Set.copyOf(jdbc.sql("""
            select distinct h.order_id
            from order_history h
            where h.order_id in (:orderIds)         -- 목록에 나온 주문을 한 번에
              and h.actor = 'SYSTEM'                -- 손님·관리자가 한 취소는 빼고
              and h.reason = :reason                -- 자동 취소 작업이 남기는 이유
            """)
        .param("orderIds", orderIds)              // 컬렉션은 in (...) 자리에 값마다 펼쳐진다
        .param("reason", AutoCancelJob.REASON)    // 남길 때 쓴 상수를 그대로 쓴다
        .query(UUID.class)
        .list());
}
```

## 💡 배운 것

**약관은 화면과 메일의 명세였습니다.** 손님에게 보이는 흐름을 바꾸기 전에 약관이 그 흐름에 대해 무엇을 약속했는지부터 찾아봐야 한다는 걸 알게 됐습니다. 이번에는 고친 뒤에야 확인해서 되돌리는 일이 생겼습니다.

**숨기기 전에 왜 헷갈리는지부터 봐야 했습니다.** 문제는 주문이 보이는 것이 아니라, 서로 다른 두 취소가 같은 이름을 쓰는 것이었습니다.

**누가·왜 바꿨는지 남겨 두면 나중에 이름을 가를 수 있었습니다.** 상태 하나에 이유가 여럿일 때 상태 기록의 처리자와 이유가 둘을 가르는 열쇠가 됐습니다. 이유 문구는 남기는 쪽과 읽는 쪽이 같은 상수를 쓰게 해서, 한쪽만 문구가 바뀌어 어긋나는 일을 막았습니다.

## 소감

다른 서비스의 방식을 참고하는 것도 도움이 되지만, 우리 서비스가 손님과 맺은 약속은 우리 약관에 있다는 걸 다시 느꼈습니다. 이제는 손님 화면을 바꾸기 전에 약관에서 그 화면에 나오는 낱말부터 찾아보게 됐습니다.

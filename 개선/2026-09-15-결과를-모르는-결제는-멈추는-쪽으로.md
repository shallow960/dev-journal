# 2026-09-15 결과를 모르는 결제는, 멈추는 쪽으로

> 태그: #개선 #결제 #트랜잭션 #장애대응

## 무엇을 / 왜

정기결제 한 건은 이런 순서로 처리됩니다.

```
청구서 발행 → 결제 요청 기록 → 결제사 호출 → 결과 기록 → 구독 갱신
```

이게 **한 처리 단위(트랜잭션)** 로 묶여 있었습니다. 중간에 예외가 나거나 서버가 꺼지면 우리 쪽 기록은 전부 되돌아갑니다. 깔끔해 보이지만, 결제사 호출이 끼어 있으면 얘기가 다릅니다.

**결제사가 승인한 직후에 서버가 꺼지면, 돈은 나갔는데 우리 기록은 없습니다.** 다음 날 배치는 "이 구독은 아직 결제 안 됐네" 하고 **같은 달을 다시 청구합니다.**

외부 호출에는 성공과 실패 말고 **"모름"** 이라는 결과가 있다는 걸, 이 코드를 읽으면서 처음 실감했습니다.

## 어떻게 풀었나

### 되돌아가지 않는 기록을 하나 남긴다

결제사를 부르기 **직전에** "이 구독을 지금 청구한다" 는 표시를 남기되, **바깥 트랜잭션과 분리된 별도 트랜잭션으로 먼저 확정**했습니다. 결과를 기록할 때 이 표시를 지웁니다.

```
표시 세움(즉시 확정) → 결제사 호출 → 결과 기록 + 표시 지움
```

그러면 표시가 남아 있는 구독은 **"결과를 모르는 결제가 있다"** 는 뜻입니다. 바깥이 통째로 되돌아가도 이 표시는 남습니다.

### 모르는 건은 자동으로 다시 청구하지 않는다

표시가 남아 있으면 그 구독은 건너뛰고 오류 기록을 남깁니다. 자동 재청구를 멈추는 쪽을 택한 이유는 단순합니다.

- 다시 청구했는데 실제로는 이미 결제됐다면 → **두 번 받는다**
- 청구하지 않았는데 실제로는 결제가 안 됐다면 → **못 받는다**

돈을 두 번 받는 쪽이 훨씬 나쁩니다. 못 받은 건 확인 후 받으면 되지만, 두 번 받으면 사용자가 먼저 발견하고 신뢰를 잃습니다.

대신 **사람이 무엇을 해야 하는지** 를 오류 메시지에 적었습니다. 자동 복구(결제사에 승인 여부를 조회해 맞추기)는 아직 없기 때문에, 이게 실제 절차가 됩니다.

### 표시를 세우는 방식

```
아직 비어 있을 때만 세운다 + 다른 작업이 그 행을 잡고 있으면 기다리지 않고 건너뛴다
```

기다리게 두면, 바깥 트랜잭션이 이미 그 행을 잡고 있는 상황에서 **자기 자신을 기다리는** 교착이 생길 수 있습니다. 건너뛰면 이번 회차만 거르고 다음 실행에서 다시 집습니다.

## 코드로 보기 (개념 재현)

```sql
-- 결제사 호출 직전 시각. 결과를 기록하면 비운다.
-- 남아 있으면 "결과 미확인" 이므로 자동 재청구하지 않는다.
alter table 구독 add column 결제시도시각 timestamptz;
```

```java
/** 별도 트랜잭션으로 즉시 확정한다. 바깥이 되돌아가도 이 표시는 남는다. */
private boolean 결제시도_표시(UUID 구독id) {
    Integer 세움 = 별도트랜잭션.실행(() -> sql("""
        update 구독
           set 결제시도시각 = now()
         where id = (select id from 구독
                      where id = :id and 결제시도시각 is null
                      for update skip locked)   -- 잡혀 있으면 기다리지 않고 건너뛴다
        """).param("id", 구독id).update());

    if (세움 != null && 세움 == 1) return true;

    var 남은표시 = 결제시도시각_조회(구독id);
    if (남은표시 != null) {
        log.error("결제 결과 미확인 - 자동 재청구를 멈춥니다. 결제사 승인 내역을 확인한 뒤 "
                + "구독.결제시도시각 을 비워야 다시 청구됩니다. 구독={} 시도={}", 구독id, 남은표시);
    }
    return false;   // 이번 회차는 건너뛴다
}
```

```java
for (구독 구독 : 결제일이_지난_구독들(지금)) {
    if (!결제시도_표시(구독.id())) continue;

    var 청구서 = 청구서만들기(구독, 요금(구독.요금제()));
    결제하기(청구서.id());          // 이 안에서 결제사를 부른다

    결제시도_표시_지움(구독.id());   // 결과를 기록했으니 표시를 지운다
}
```

검증은 "표시가 남아 있으면 청구하지 않는다" 를 봅니다.

```java
@Test
void 결과를_모르는_결제가_남은_구독은_다시_청구하지_않는다() {
    var 구독 = 구독시작(가게, 시작일: 지금.minusDays(8));
    결제일을_과거로(구독.id());
    // 어제 결제사를 부르던 중 서버가 꺼져 표시만 남은 상태
    sql("update 구독 set 결제시도시각 = now() - interval '1 day' where id = :id").param("id", 구독.id()).update();

    정기결제배치.실행();

    assertThat(청구서수(구독.id())).isZero();          // 청구 자체가 일어나지 않았다
    assertThat(결제시도시각(구독.id())).isNotNull();   // 표시는 그대로 남아 사람이 확인하게 둔다
}

@Test
void 정상_청구는_표시를_비운다() {
    var 구독 = 구독시작(가게, 시작일: 지금.minusDays(8));
    결제일을_과거로(구독.id());

    정기결제배치.실행();
    정기결제배치.실행();                                // 다음 날도 돈다

    assertThat(결제건수(구독.id(), "성공")).isEqualTo(1);
    assertThat(결제시도시각(구독.id())).isNull();
}
```

## 💡 배운 것

**외부 호출의 결과는 세 가지입니다.** 성공, 실패, 그리고 **모름**. 응답을 못 받았다는 건 실패가 아니라 모름이고, 이 둘을 같게 다루면 실패로 보고 다시 시도하게 됩니다.

**되돌아가면 안 되는 기록은 트랜잭션 밖에서 확정해야 합니다.** 트랜잭션은 "전부 되거나 전부 안 되거나" 를 보장하지만, 외부 세계에서 이미 일어난 일은 되돌려 주지 않습니다.

**애매할 때 어느 쪽으로 틀릴지 미리 정해 둡니다.** 여기서는 "못 받는 쪽" 입니다. 정하고 나면 코드가 단순해집니다.

**자동 복구가 없으면 사람이 할 일을 남겨야 합니다.** 로그 메시지에 "무엇을 확인하고 무엇을 지우면 다시 돈다" 를 적어 뒀습니다. 이걸 안 적으면 몇 달 뒤 그 오류를 만난 사람은 아무것도 할 수 없습니다.

**잠금은 기다리게 하는 것보다 건너뛰는 게 나을 때가 있습니다.** 주기적으로 도는 작업이라면 이번에 못 하면 다음에 하면 됩니다.

## 소감

전에 자동 충전을 만들면서 "한 번만 긁는 것" 을 고민한 적이 있는데, 그때는 **조건이 계속 참이라서 반복되는** 문제였습니다. 이번은 다릅니다. 조건도 한 번, 코드도 한 번인데 **중간에 끊기면** 반복됩니다.

같은 "두 번 긁힘" 이라도 원인이 다르면 막는 방법도 다르다는 걸 알았습니다. 그리고 결제 코드에서 제일 신경 써야 할 건 정상 흐름이 아니라 **끊겼을 때 어디까지 남는가** 라는 것도요.

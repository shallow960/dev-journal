# 2026-08-14 자동 결제에서 제일 어려운 건 "한 번만 긁는 것"이었다

> 태그: #개선 #결제 #멱등성 #트랜잭션

## 무엇을 / 왜

선불 충전 방식의 서비스를 만들고 있습니다. 잔액이 떨어지면 사용자가 직접 충전해야 하는데, **충전을 잊으면 서비스가 중간에 끊깁니다.** 그래서 잔액이 부족해지면 등록된 카드로 알아서 채우는 기능을 붙이기로 했습니다.

결제를 붙이는 것 자체는 어렵지 않았습니다. 이미 정기 결제에 쓰는 길이 있어서 그대로 재사용하면 됐거든요.

**정작 오래 붙든 건 "두 번 긁히지 않게 하는 것"이었습니다.**

## 어떻게 풀었나

### 왜 어려운가

사용량을 확인하는 작업이 15분마다 돕니다. 그리고 잔액이 부족한 상태는 **충전할 때까지 계속 유지**됩니다. 즉 아무 방어가 없으면 이렇게 됩니다.

```
10:00 확인 → 잔액 부족 → 결제
10:15 확인 → 잔액 부족(아직) → 결제
10:30 확인 → 잔액 부족(아직) → 결제
...
```

버그가 아니라 **설계대로 동작하면 그렇게 됩니다.** 조건이 "잔액이 부족하면"이니까요. 남의 카드로 하루에 96번 결제가 나가는 구조입니다.

### 세 겹으로 막았다

**1. 신호를 상태 변화로 바꿨다.** "잔액이 부족하다"(계속 참)가 아니라 **"이번에 처음 기준선을 넘었다"**(한 번만 참)를 신호로 씁니다. 잔액을 깎는 쪽이 이미 경고 단계를 관리하고 있어서, 그 계산을 결과에 실어 보내게 했습니다.

```java
public record 차감결과(
    BigDecimal 차감량,
    BigDecimal 잔액,
    boolean 소진됨,
    /** 이번 차감에서 "새로" 넘은 경고 기준(0=없음, 20, 10).
     *  이미 넘어 있던 기준은 0이다. 이게 없으면 부르는 쪽이 매번 참으로 본다. */
    int 넘은기준
) {}
```

**2. 성공하면 일정 시간 쉰다.** 신호가 한 번만 오더라도, 충전 후 다시 잔액이 내려가면 또 신호가 옵니다. 마지막 성공 시각을 저장해두고 그 안에는 하지 않습니다.

**3. 실패하면 더 오래 쉰다.** 이게 제일 중요했습니다. 카드가 막힌 상태에서 15분마다 계속 시도하면 **카드사 쪽에서 차단당합니다.** 실패 시각을 따로 저장해서 훨씬 길게 물러섭니다. 대신 사용자에게 알립니다.

```java
if (결과.넘은기준() != 10 && !결과.소진됨()) return false;   // 1: 상태 변화만

var 설정 = 설정조회(가게ID);
if (!설정.켜짐()) return false;

var 지금 = OffsetDateTime.now();
if (이내(설정.마지막성공, 지금, 성공쿨다운)) return false;    // 2: 성공 후 쿨다운
if (이내(설정.마지막실패, 지금, 실패백오프)) return false;    // 3: 실패 후 백오프

try {
    var 결제 = 충전하기(설정.상품코드());
    성공기록(가게ID, 지금);
    알림_충전됨(가게ID, 결제.금액());
} catch (RuntimeException e) {
    실패기록(가게ID, 지금);
    알림_충전실패(가게ID, e.getMessage());   // 켜뒀으니 되겠거니 하다가 끊긴다
}
```

### 결제는 트랜잭션 밖으로

처음엔 잔액을 깎는 흐름 안에서 바로 결제를 부르려고 했습니다. 코드가 짧아지니까요. 그런데 두 가지가 걸렸습니다.

- 결제 응답을 기다리는 동안 **데이터를 붙든 채로 서 있게 됩니다.** 외부 서비스 응답은 몇 초씩 걸릴 수 있고, 그동안 그 계정 행이 잠깁니다.
- 더 큰 문제. 잔액 차감이 나중에 어떤 이유로 취소되면 데이터는 되돌아가지만 **이미 긁힌 카드는 되돌아오지 않습니다.**

그래서 **차감이 확정된 뒤에** 부르도록 분리했습니다.

```java
// 주기 작업 안에서
var 결과 = 반영하기(가게ID, 건ID, 증가분);   // 여기서 트랜잭션이 끝난다
후속처리.실행(가게ID, 결과);                 // 알림 · 자동 충전은 그 다음
```

### 기본값은 꺼짐

동의 없이 카드를 긁으면 안 되니 **기본은 꺼짐**으로 두고 사용자가 직접 켜게 했습니다.

처음엔 "부족한 만큼만 카드에서 청구"하는 방식도 고민했는데 접었습니다. 금액이 매번 달라지면 영수증·환불·세금 처리가 전부 예외 케이스가 되고, 사용자 입장에서도 **예상 못 한 금액**이 카드에 찍힙니다. 정해진 상품을 하나 사는 방식이면 기존 결제 흐름을 그대로 쓰고, 사용자가 받는 안내도 명확합니다.

## 코드로 보기 (개념 재현 테스트)

"한 번만 긁힌다"는 **반복 실행해서** 확인해야 의미가 있습니다.

```java
@Test
void 반복해서_돌아도_한_번만_결제된다() {
    // given
    var 가게 = 가게만들기("refill");
    카드등록(가게);
    잔액충전(가게, 100);
    자동충전_켜기(가게, "상품A");

    // when: 95를 쓰면 잔액 5 → 10% 기준을 처음 넘는다
    var 첫결과 = 차감(가게, 95);
    assertThat(첫결과.넘은기준()).isEqualTo(10);
    후속처리.실행(가게, 첫결과);
    var 충전후 = 잔액(가게);

    // 같은 상황이 세 번 더 와도(주기 작업 재실행)
    for (int i = 0; i < 3; i++) {
        후속처리.실행(가게, 차감(가게, 1));
    }

    // then: 줄어든 건 실제 사용분 3뿐 - 충전은 한 번만 일어났다
    assertThat(잔액(가게)).isEqualByComparingTo(충전후.subtract(BigDecimal.valueOf(3)));
}

@Test
void 켜지_않았으면_아무것도_하지_않는다() {
    var 가게 = 가게만들기("refill-off");
    카드등록(가게);
    잔액충전(가게, 100);
    // 자동 충전을 켜지 않았다

    후속처리.실행(가게, 차감(가게, 95));

    assertThat(잔액(가게)).isEqualByComparingTo("5");   // 카드를 긁지 않았다
}
```

두 번째 테스트가 특히 중요합니다. 기능이 **동작하는 것**만큼 **동의 없이는 동작하지 않는 것**도 지켜야 하는 규칙이니까요.

## 💡 배운 것

- **주기 실행되는 작업에서 "조건이 참이면 실행"은 위험하다.** 조건이 계속 참으로 유지되기 때문입니다. "상태가 바뀌는 순간"을 신호로 삼거나, 실행 이력을 남겨서 막아야 합니다.
- **실패했을 때의 재시도 간격은 성공했을 때보다 길게.** 특히 외부 서비스가 상대라면, 실패를 빠르게 반복하는 게 차단으로 이어집니다.
- **외부 호출(결제·발송)은 데이터 트랜잭션 밖에서.** 안에서 하면 ①연결을 오래 붙들고 ②롤백해도 외부 효과는 안 돌아옵니다.
- **돈이 걸린 기능은 "되는지"보다 "잘못되면 어느 쪽으로 틀리는지"를 먼저 정한다.** 여기선 "안 긁히는 쪽"으로 기울였습니다.
- 자동 실행 기능은 **기본을 꺼짐으로** 두고 사용자가 켜게 합니다.

## 소감

기능 자체는 반나절이면 붙는 것이었는데, 중복 방지에 그 몇 배를 썼습니다. 처음엔 과하다 싶었어요.

그런데 테스트로 반복 실행을 흉내 내보니, 방어를 하나만 걸었을 때는 **여전히 뚫리는 경로가 남아 있었습니다.** 상태 변화만 신호로 잡아도 잔액이 오르내리면 또 걸리고, 쿨다운만 걸어도 그 시간이 지나면 다시 걸립니다. 셋을 다 걸고 나서야 반복 실행해도 한 번으로 끝나더군요.

"자동"이 붙는 기능은 만드는 시간보다 **멈추게 하는 조건을 정하는 시간**이 더 길 수 있다는 걸 배웠습니다.

# 2026-10-14 평문으로 쌓인 값을, 서버가 뜰 때 한 번 암호화한다

> 태그: #개선 #보안 #암호화 #AES-GCM #Spring #마이그레이션

## 무엇을 / 왜

암호화해야 하는 값 두 가지가 평문으로 쌓여 있었습니다.

1. 정기결제에 쓰는 **카드 결제 키(빌링키)**. 칸 이름은 "암호화된 값"이었는데 실제로는 평문이었어요.
2. 계좌이체 결제를 반품할 때 손님이 적는 **환불 계좌번호·예금주**.

새로 저장하는 값부터 암호화하는 건 어렵지 않았습니다. 문제는 **이미 쌓인 평문**이었어요. DB 마이그레이션(SQL)으로는 바꿀 수 없었습니다. 암호화 키는 앱 환경에만 있으니까요.

## 어떻게 풀었나

- **앱에서 AES-GCM 으로 암호화하고, 접두로 표시:** 암호문 앞에 `enc:` 를 붙여 "이미 암호화한 값"을 구분합니다.
- **읽는 쪽은 둘 다 읽기:** 접두가 있으면 풀고, 없으면 예전 평문으로 보고 그대로 씁니다. 그래서 예전 값이 남아 있어도 기능은 멈추지 않아요.
- **서버가 뜬 뒤 한 번 옮기기:** 앱이 준비된 뒤(`ApplicationReadyEvent`) 평문만 골라 암호화합니다. 상점마다 행 보안(RLS)이 걸린 표라 상점마다 들어가서 바꿔요.
- **몇 번 돌아도 같게:** 이미 암호화한 값은 건너뜁니다. 서버가 다시 떠도 바뀌는 게 없어요.
- **그 사이 바뀐 값은 덮지 않기:** "읽었을 때 값과 지금 값이 같을 때만" 바꿉니다.
- **실패해도 서버는 뜬다:** 옮기기가 실패하면 경고만 남기고 다음에 뜰 때 다시 시도합니다. 읽는 쪽이 평문도 읽으니 기능에는 영향이 없어요. 로그에는 값이 아니라 **바꾼 건수**만 남깁니다.
- 암호문은 평문보다 길어서, 칸 길이를 넓히는 마이그레이션만 따로 넣었습니다.

## 코드로 보기 (개념 재현)

```java
// 암호화 코덱: 접두로 "이미 암호화한 값"을 구분한다
public final class FieldCipher {
    private static final String PREFIX = "enc:";
    private final SecretKey key;                  // 앱 환경 변수에서 읽은 키 (DB 에는 없다)
    private final SecureRandom random = new SecureRandom();

    public FieldCipher(SecretKey key) {
        this.key = key;
    }

    public String encrypt(String plain) {
        try {
            byte[] iv = new byte[12];             // GCM 은 12바이트 IV 를 매번 새로 만든다
            random.nextBytes(iv);                 // 그래서 같은 평문도 암호문은 매번 다르다
            Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
            c.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
            byte[] body = c.doFinal(plain.getBytes(StandardCharsets.UTF_8));
            byte[] out = ByteBuffer.allocate(iv.length + body.length).put(iv).put(body).array();
            return PREFIX + Base64.getEncoder().encodeToString(out);
        } catch (GeneralSecurityException e) {
            throw new IllegalStateException("encrypt failed", e);
        }
    }

    public String decrypt(String stored) {
        if (stored == null || !stored.startsWith(PREFIX)) {
            return stored;                        // 접두가 없으면 예전 평문: 그대로 읽는다
        }
        try {
            byte[] all = Base64.getDecoder().decode(stored.substring(PREFIX.length()));
            Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
            c.init(Cipher.DECRYPT_MODE, key, new GCMParameterSpec(128, all, 0, 12)); // 앞 12바이트가 IV
            return new String(c.doFinal(all, 12, all.length - 12), StandardCharsets.UTF_8);
        } catch (GeneralSecurityException e) {
            throw new IllegalStateException("decrypt failed", e);
        }
    }
}
```

```java
// 서버가 준비된 뒤 한 번: 평문만 골라 암호화한다
@Component
public class LegacyAccountBackfill {

    @EventListener(ApplicationReadyEvent.class)   // 앱이 다 뜬 뒤라, 실패해도 기동을 막지 않는다
    public void run() {
        try {
            int changed = 0;
            for (UUID storeId : storeIds()) {
                changed += encryptStore(storeId); // 상점마다 들어가서 (행 보안이 걸린 표)
            }
            if (changed > 0) {
                log.info("legacy values encrypted: {}", changed); // 값이 아니라 건수만 남긴다
            }
        } catch (RuntimeException e) {
            log.warn("backfill skipped: {}", e.getClass().getSimpleName()); // 다음에 뜰 때 다시
        }
    }

    int encryptStore(UUID storeId) {
        try (var scope = StoreContext.enter(storeId)) {
            int changed = 0;
            // 평문만 고른다: 비어 있지 않고 'enc:' 로 시작하지 않는 값
            for (Row r : findPlainRows()) {
                // 읽었을 때 값과 지금 값이 같을 때만 바꾼다. 그 사이 바뀐 값은 덮지 않는다
                changed += jdbc.sql("""
                        UPDATE return_request
                           SET account_number = :newNumber
                         WHERE id = :id
                           AND account_number IS NOT DISTINCT FROM :oldNumber
                        """)
                    .param("newNumber", cipher.encrypt(r.number()))
                    .param("id", r.id())
                    .param("oldNumber", r.number())
                    .update();
            }
            return changed;
        } catch (RuntimeException e) {
            // 읽는 쪽이 평문도 읽으니 기능은 그대로 돈다. 이 상점만 건너뛴다
            log.warn("backfill failed for one store: {}", e.getClass().getSimpleName());
            return 0;
        }
    }
}
```

테스트는 새로 저장한 값이 암호문이고 풀면 원래 값인지, 예전 평문이 옮겨지는지, 두 번째로 돌리면 아무것도 바뀌지 않는지를 봤습니다. 운영에 배포한 뒤에는 서버 로그에서 예전 평문으로 저장돼 있던 카드 결제 키 5건을 암호화했다는 줄을 확인했어요. 환불 계좌 쪽 로그는 아직 확인하지 못했습니다(예전 값이 없으면 줄이 찍히지 않습니다).

## 💡 배운 것

**칸 이름이 내용을 보장하지 않습니다.** "암호화된 값"이라는 이름의 칸에 평문이 들어 있었어요. 이름이 아니라 실제로 저장된 값을 봐야 했습니다.

**이미 쌓인 데이터는 "읽는 쪽이 둘 다 읽게" 한 뒤 옮깁니다.** 그러면 옮기는 작업이 실패하거나 늦어도 기능은 멈추지 않아요. 순서가 거꾸로면 옮기기 전까지 기능이 깨집니다.

**한 번만 도는 작업도 여러 번 돌 수 있다고 보고 만듭니다.** 서버는 몇 번이고 다시 뜨니까, 이미 한 것은 건너뛰고 그 사이 바뀐 값은 덮지 않게 했어요.

**키가 앱에만 있으면, 옮기기도 앱에서.** SQL 마이그레이션에 키를 넘기지 않아도 됐습니다.

## 소감

새 값부터 암호화하는 건 금방이었는데, 이미 쌓인 값을 안전하게 옮기는 데 고민이 더 많았습니다. 운영 로그에서 실제로 5건이 바뀐 걸 확인했을 때, "옮겼다"를 말로만 하지 않고 건수로 볼 수 있게 남겨 둔 게 도움이 됐어요.

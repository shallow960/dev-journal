# 2026-10-07 쪼갠 품목은, 어디서 나왔는지 적어 둬야 했다

> 태그: #개선 #정산 #부분반품 #PostgreSQL #CTE #돈계산

## 무엇을 / 왜

손님이 한 품목을 3개 사고 그중 1개만 반품하면, 반품할 1개를 새 품목으로 쪼개서 처리합니다.

```
쪼개기 전: 품목 A (수량 3)
쪼갠 뒤:   품목 A (수량 2, id 그대로) + 품목 B (수량 1, 새 id) <- 이 품목을 반품 처리
```

반품이 끝나면 그 품목의 판매자 정산을 돌려받습니다. 그런데 구매확정 뒤 정산이 이미 쌓인 다음에 반품하면 문제가 생겼습니다.

- 정산은 쪼개기 전의 품목 A 에 3개분으로 쌓여 있습니다.
- 반품된 건 새 품목 B 인데, B 에는 정산이 없습니다.
- 회수 코드는 "반품된 품목의 정산" 만 찾았기 때문에 아무것도 하지 않았고, A 의 3개분 정산이 그대로 지급될 상황이었습니다.

## 어떻게 풀었나

### 출처를 남긴다

쪼갤 때 새 품목에 "원래 품목 id" 를 적게 했습니다. 처음엔 같은 주문·같은 상품·같은 옵션으로 원래 정산을 추측할 수 있지 않을까 생각했는데, 다음 경우를 막을 수 없었습니다.

```
구매확정 -> 반품 접수(이때 쪼갬: A 수량 2, B 수량 1) -> 며칠 뒤 정산이 A 에 "2개분" 으로 쌓임 -> 반품 완료
```

이때 A 의 정산에는 반품된 1개가 처음부터 들어 있지 않습니다. 추측으로 찾으면 2개분 정산에서 또 1개분을 깎게 됩니다. 그래서 출처 링크에 더해 **"원래 정산이 쪼개기 전에 만들어졌는가"** 를 만든 시각으로 비교했습니다. 쪼갠 품목은 쪼갤 때 만들어지므로, 정산의 생성 시각이 그보다 앞설 때만 그 정산에 반품 수량이 들어 있습니다.

### 지급 전과 지급 뒤

- **지급 전:** 정산을 그 수량 몫만큼 줄입니다. 얼마 줄였는지 조정 이력에 남깁니다.
- **지급 절차에 들어간 뒤:** 이미 나갔거나 나가는 중인 돈은 코드가 되돌리지 않습니다. 정산을 보류로 잡고 "돌려받을 금액" 을 남겨, 운영자가 다음 지급에서 빼거나 따로 받게 합니다.

### 몫을 나눌 때 합을 맞춘다

정산 한 줄에는 기준액·결제수수료·판매 수수료·지급액 같은 칸이 있고, `지급액 = 기준액 - 결제수수료 - 판매 수수료 + 배송비` 관계를 지켜야 합니다. 칸마다 따로 "x 1/3" 을 하고 반올림하면 이 관계가 1원씩 어긋날 수 있습니다. 그래서 기준액·결제수수료·판매 수수료의 몫은 각각 반올림하고, **지급액의 몫은 그 셋의 차이로 계산** 했습니다. 배송비는 일부 반품으로 돌려주지 않으므로 몫에서 뺐습니다.

### 쪼갤 때 같이 옮길 것

주문 때 고정한 수수료율과 쿠폰 몫도 새 품목에 옮겼습니다. 옮기지 않으면 교환처럼 쪼갠 품목이 따로 정산될 때 요율이 비어 있어 현재 요율로 계산되고, 쿠폰은 원래 품목에만 남습니다. 상품 쿠폰은 수량 비율로 나누되 쪼갠 쪽은 내림하고, 남은 금액은 원래 품목에 둡니다.

## 코드로 보기 (개념 재현)

표·클래스 이름은 예시입니다.

```sql
-- 반품된 쪼갠 품목에서 원래 정산을 찾는다(쪼개기 전에 만들어진 정산만)
select p.id, split.quantity as returned_quantity
from order_line split
join seller_payout p on p.order_line_id = split.split_from_line_id
where split.id = :returnedLineId
  and p.created_at < split.created_at      -- 쪼갠 뒤에 쌓인 정산은 이미 줄어든 수량이다
for update of p;
```

```sql
-- 지급 전: 수량 몫만큼 정산을 줄이고, 줄인 지급액을 돌려준다
with share as (
    select p.id,
           round(p.sale_base  * :returned / p.quantity) as base,
           round(p.pay_fee    * :returned / p.quantity) as fee,
           round(p.commission * :returned / p.quantity) as commission
    from seller_payout p
    where p.id = :payoutId
      and p.quantity > :returned           -- 다 반품이면 이 길이 아니라 통째 취소
)
update seller_payout p
set quantity   = p.quantity - :returned,
    sale_base  = p.sale_base - s.base,
    pay_fee    = p.pay_fee - s.fee,
    commission = p.commission - s.commission,
    amount     = p.amount - (s.base - s.fee - s.commission)   -- 지급액 몫은 차이로: 칸끼리 합이 맞는다
from share s
where p.id = s.id
returning s.base - s.fee - s.commission as reduced;
```

```java
@Transactional
public void reverseReturnedLine(UUID returnedLineId) {
    Optional<Payout> own = payouts.findByLineForUpdate(returnedLineId);
    if (own.isPresent()) {                       // 품목 통째 반품: 지급 전이면 취소, 뒤면 보류
        reverseWhole(own.get());
        return;
    }
    payouts.findSplitOriginForUpdate(returnedLineId).ifPresent(origin -> {
        Payout payout = origin.payout();
        int returned = origin.returnedQuantity();
        if (payout.isCancelled()) {
            return;
        }
        if (payout.isBeforePayout()) {
            BigDecimal reduced = payouts.reduceForPartialReturn(payout.id(), returned);
            adjustments.record(payout.id(), "REDUCED", reduced);    // 얼마 줄였는지 남긴다
        } else {
            BigDecimal share = payouts.partialShare(payout.id(), returned);
            payouts.hold(payout.id());
            adjustments.record(payout.id(), "CLAWBACK", share);     // 돌려받을 금액을 남긴다
        }
    });
}
```

10,000원 상품 3개(수수료 10%, 결제수수료 2.5%)에서 1개를 반품하면, 지급 전 정산은 2개분으로 줄고 8,750원(기준액 10,000 - 결제수수료 250 - 판매 수수료 1,000)이 빠집니다. 지급 절차에 들어간 정산은 그대로 두고 보류 목록에 "돌려받을 금액 8,750원" 이 뜹니다. 두 경우 모두 테스트로 확인했습니다.

## 💡 배운 것

**데이터를 쪼갤 때는 출처를 남깁니다.** 쪼갠 쪽이 어디서 왔는지 모르면, 나중에 원래 쪽에 묶인 돈이나 기록을 찾을 방법이 추측밖에 없습니다.

**추측으로 찾으면 순서가 뒤바뀐 경우를 놓칩니다.** "어느 쪽이 먼저였나" 를 만든 시각으로 확인해야, 이미 반영된 것을 두 번 깎지 않습니다.

**돈을 되돌리는 방법은 지급 전·후로 다릅니다.** 지급 전에는 숫자를 줄이면 되지만, 지급 뒤에는 숫자를 고치지 않고 돌려받을 금액을 기록해 사람이 처리하게 합니다.

**비율로 나눌 때는 관계식을 지킵니다.** 칸마다 따로 반올림하면 합이 1원씩 어긋날 수 있으니, 하나는 나머지의 차이로 계산합니다.

## 소감

예전에 수량 일부 반품을 "품목을 쪼개서 기존 반품 처리를 재사용" 하는 방식으로 만들 때는 정산까지 생각하지 못했습니다. 그때의 선택이 틀린 건 아니었지만, 쪼갠 쪽과 원래 쪽을 잇는 연결 고리 하나가 빠져 있었습니다. 지급 전 차감과 지급 뒤 보류는 테스트로 확인했고, 이미 지급한 돈을 실제로 돌려받는 일은 운영자가 처리하는 부분으로 남겨 두었습니다.

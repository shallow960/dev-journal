# 2026-11-05 외주형 브랜드 주소에서, 플랫폼 이름은 화면 밖에서 보이고 있었다

> 태그: #개선 #화이트라벨 #인증서 #CloudFront #멀티테넌트

## 무엇을 / 왜

서비스를 두 가지 방식으로 팔고 있었습니다. 가입형 고객은 플랫폼 주소에서 그대로 썼고, 외주형 고객은 자기 브랜드 주소로 들어와 자기 서비스처럼 썼습니다. 외주형 고객의 손님과 직원에게는 플랫폼 이름이 보이면 안 된다는 조건이 있었습니다.

2026-11-05 에 운영 서버를 새 계정으로 옮기면서 플랫폼 주소도 CloudFront 뒤로 옮기기로 했습니다. 그러자 "외주형 브랜드도 플랫폼과 같은 CloudFront 를 쓰면 안 되나, 따로 둬야 한다면 정확히 어디서 플랫폼 이름이 보이길래" 라는 질문이 나왔습니다. 화면 문구는 이미 브랜드 이름으로 바꿔 둔 상태여서, 화면 말고 어디서 보이는지를 하나씩 찾아봤습니다.

## 어떻게 풀었나

**1. 인증서.** 찾아보니 우리가 쓰는 방식의 CloudFront 배포 하나에는 인증서를 하나만 붙일 수 있었습니다. 플랫폼과 여러 브랜드가 배포 하나를 같이 쓰려면, 인증서 하나에 모든 주소를 이름 목록(SAN)으로 넣어야 했습니다. 그런데 브라우저 주소창의 자물쇠를 눌러 인증서를 열면 이 목록이 그대로 보였습니다. 브랜드 A 의 손님이 플랫폼 주소와 브랜드 B 의 주소까지 볼 수 있게 되는 셈이었습니다.

그래서 외주형 브랜드는 CloudFront 를 브랜드마다 따로 두고, 그 브랜드 주소만 든 인증서를 붙이기로 했습니다. 가입형은 플랫폼 것 하나를 같이 쓰게 했습니다. 브랜드가 늘 때마다 손이 가는 일이라, 연결을 자동으로 하는 작업은 첫 외주형 고객을 연 다음 순서로 미뤘습니다.

**2. 공개 파일.** 실제 브랜드 주소로 공개 파일을 하나씩 열어 보니, 화면에는 없던 이름이 남아 있었습니다.

- 검색 로봇용 파일(`robots.txt`, `sitemap.xml`)에 플랫폼 이름과 플랫폼 주소가 적혀 있었습니다.
- 로고와 제품 이미지 몇 개는 파일 이름이나 그림 안에 플랫폼 이름이 들어 있었습니다.
- 화면용 JS 파일 안에는 플랫폼 이름이 든 문구가 남아 있었습니다. 모든 브랜드가 같은 빌드를 쓰고 있어서 생긴 일이었습니다.
- 손님 사진 링크에는 파일 저장소(버킷) 이름이 들어 있었는데, 그 이름에도 플랫폼 이름이 있었습니다.

반대로 로그인 화면 HTML, 응답 헤더, 인증서, QR 페이지 HTML 에는 이름이 없었습니다.

**3. 어디까지 막을지.** 겉으로 바로 보이는 곳부터 막기로 했습니다. 브랜드 주소로 들어온 요청에는 검색 로봇용 파일과 플랫폼 이미지를 내주지 않게 막았습니다. 개발자 도구를 열어야 보이는 JS 문구와 사진 링크의 저장소 이름은 구조를 바꿔야 하는 일이라 따로 정하기로 했습니다.

## 코드로 보기 (개념 재현)

인증서 하나에 이름을 여러 개 넣으면 받는 쪽이 그 목록을 모두 본다는 것을, 연습용 인증서 두 장으로 확인했습니다. 주소는 모두 예시입니다.

```bash
# san-demo.sh - 인증서 하나에 이름을 여러 개 넣으면, 받은 쪽은 그 목록을 모두 본다
# (Git Bash 에서는 /CN= 이 경로로 바뀌지 않게 MSYS_NO_PATHCONV=1 bash san-demo.sh 로 실행)

# 1) 플랫폼과 두 브랜드가 함께 쓰는 인증서 (CloudFront 하나를 같이 쓰는 경우)
openssl req -x509 -newkey rsa:2048 -nodes -days 1 -keyout shared.key -out shared.pem \
  -subj "/CN=platform.example" \
  -addext "subjectAltName=DNS:platform.example,DNS:*.platform.example,DNS:admin.brand-a.example,DNS:admin.brand-b.example" 2>/dev/null
# 2) 브랜드 A 만 쓰는 인증서 (브랜드마다 따로 두는 경우)
openssl req -x509 -newkey rsa:2048 -nodes -days 1 -keyout brand-a.key -out brand-a.pem \
  -subj "/CN=admin.brand-a.example" \
  -addext "subjectAltName=DNS:admin.brand-a.example" 2>/dev/null

echo "== 같이 쓰는 인증서: 브랜드 A 손님 브라우저가 받는 이름 목록"
openssl x509 -in shared.pem -noout -ext subjectAltName
echo "== 브랜드 A 전용 인증서"
openssl x509 -in brand-a.pem -noout -ext subjectAltName
```

OpenSSL 3.5.4 로 돌린 결과입니다.

```text
== 같이 쓰는 인증서: 브랜드 A 손님 브라우저가 받는 이름 목록
X509v3 Subject Alternative Name: 
    DNS:platform.example, DNS:*.platform.example, DNS:admin.brand-a.example, DNS:admin.brand-b.example
== 브랜드 A 전용 인증서
X509v3 Subject Alternative Name: 
    DNS:admin.brand-a.example
```

같이 쓰는 인증서에서는 브랜드 A 주소로 들어온 손님에게도 플랫폼 주소와 브랜드 B 주소가 같이 갔습니다. 브랜드마다 따로 둔 인증서에는 자기 주소만 남았습니다.

## 💡 배운 것

- 화이트라벨에서 이름이 보이는 곳은 화면 문구만이 아니라는 걸 배웠습니다. 인증서의 이름 목록, 검색 로봇용 파일, 정적 파일 이름, 빌드된 JS, 파일 저장소 주소까지 봐야 했습니다.
- 인증서의 이름 목록은 손님이 클릭 한 번으로 볼 수 있는 공개 목록이라는 걸 알게 됐습니다. 여러 고객이 인증서 하나를 나눠 쓰면, 고객끼리 서로의 주소를 보게 됐습니다.
- 플랫폼 이름을 지우는 일이 생각보다 넓다는 걸 다시 배웠습니다([2026-10-30, 손님 페이지에서 플랫폼 이름을 지웠더니, 배포 확인이 배포를 되돌렸다](../트러블슈팅/2026-10-30-손님-페이지에서-플랫폼-이름을-지웠더니-배포-확인이-배포를-되돌렸다.md)). 그때는 이름을 지운 화면을 배포 확인이 이름으로 찾고 있었고, 이번에는 화면 밖에 이름이 남아 있었습니다.

## 소감

"CloudFront 를 같이 쓰면 이름이 보인다" 는 말만 듣고 넘어갔다면, 검색 로봇용 파일처럼 이미 열려 있던 곳은 못 봤을 것 같습니다. 질문을 "어디서 보이는가" 로 바꿔 하나씩 열어 본 덕분에, 처음 질문보다 더 급한 곳을 먼저 찾았습니다.

# 2026-09-29 잔액 하나로는, 언제 사라질지 알 수 없다

> 태그: #개선 #데이터모델링 #배치 #동시성

## 무엇을 / 왜

쇼핑몰 적립금에 유효기간이 없어서, 쌓인 적립금이 사라지지 않고 계속 부채로 남았습니다. 몰마다 기간(1개월·3개월·6개월·1년)을 고르게 하려고 저장 구조를 봤더니 이랬어요.

```
잔액 표   : 손님별 잔액 하나 (예: 1,300)
거래 기록 : +500 적립, +800 적립, -200 사용 ...
```

잔액이 1,300이라는 건 알지만, **그중 어느 부분이 언제 들어왔는지**는 알 수 없습니다. 기간을 정해도 "무엇을 언제 지울지" 계산할 수가 없었어요.

## 어떻게 풀었나

### 들어온 단위로 묶음을 남긴다

적립금이 들어올 때마다 **묶음**을 하나씩 남기게 했습니다. 묶음에는 처음 양, 남은 양, 사라질 날이 있어요.

```
묶음 A: 500 들어옴, 남은 500, 2026-10-02 사라짐
묶음 B: 800 들어옴, 남은 800, 2027-09-29 사라짐
```

잔액 표는 그대로 기준으로 두고, 묶음들의 남은 양 합이 늘 잔액과 같게 맞춥니다.

### 쓸 때는 먼저 사라질 것부터

300을 쓰면 **사라질 날이 가장 이른 묶음**부터 뺍니다. 늦게 사라질 걸 먼저 쓰면 곧 사라질 적립금이 그대로 소멸해서 손님만 손해예요.

### 날짜를 정하는 규칙

- 적립된 날부터 N개월이 되는 날의 **끝(23:59:59)** 까지 쓸 수 있게 했습니다. 1월 31일 + 1개월은 2월 말일이 돼요.
- 오너가 기간을 **줄여도** 이미 쌓인 묶음의 날짜는 그대로 둡니다. 손님이 모르는 사이에 잃지 않게요.
- 환불로 돌아온 적립금은 **돌려받은 날부터** 다시 셉니다. 환불받자마자 사라지는 일이 없게 했어요.
- 오너가 설정을 모르고 지나쳐도 손님이 불리하지 않게 **기본값은 1년**으로 뒀습니다.

### 기능 전부터 있던 잔액

기존 손님에게는 묶음이 하나도 없습니다. DB 변경 스크립트로 한 번에 채우려 했지만, 몰마다 행 수준 보안(RLS)이 강제돼 있어 변경 스크립트가 여러 몰을 넘나들며 쓸 수 없었어요.

그래서 **맞추기(reconcile)** 를 두었습니다. "잔액 - 묶음 합" 이 남으면 그만큼을 **그날 들어온 묶음**으로 만들어요. 매일 새벽 배치가 몰마다 돌면서 맞추고, 사용 시점에도 한 번 맞춥니다. 기존 적립금은 기능이 켜진 날부터 기간이 시작되는 셈이라, 갑자기 사라지지 않습니다.

### 새벽 배치가 하는 일

1. 잔액과 묶음 합이 다른 손님을 맞춘다
2. 날이 지난 묶음의 남은 양을 0으로 만들고, 잔액에서 빼고, 거래 기록에 "기간 만료 소멸" 을 남긴다
3. 7일 안에 사라질 묶음이 있는 손님에게 메일을 한 번 보낸다(묶음마다 알림 시각을 남겨 두 번 보내지 않음)

## 코드로 보기 (개념 재현)

```java
/** 잔액 행을 잠근 뒤에 부른다. 모자라면 오늘 들어온 묶음으로, 넘치면 먼저 사라질 것부터 줄인다. */
private void reconcileLocked(UUID user, long balance, OffsetDateTime now) {
    long open = lots.openTotal(user);
    if (open < balance) {
        lots.add(user, balance - open, now, policy.expiresAt(now));
    } else if (open > balance) {
        takeFromLots(user, open - balance);
    }
}

/** 먼저 사라질 묶음부터 amount 만큼 뺀다. */
private void takeFromLots(UUID user, long amount) {
    long left = amount;
    for (Lot lot : lots.lockOpenOrderByExpiry(user)) {   // for update, 사라질 날 순
        if (left <= 0) break;
        long take = Math.min(left, lot.remaining());
        lots.setRemaining(lot.id(), lot.remaining() - take);
        left -= take;
    }
}

@Transactional
public void spend(UUID user, long amount) {
    long balance = balances.lock(user);                  // 같은 손님의 동시 사용을 줄 세운다
    if (balance < amount) throw new IllegalStateException("잔액 부족");
    reconcileLocked(user, balance, OffsetDateTime.now());
    takeFromLots(user, amount);
    balances.set(user, balance - amount);
}
```

```java
@Test
void 먼저_사라질_것부터_빠지고_날이_지난_것만_사라진다() {
    earn(user, 500);  earn(user, 300);
    expireSoon(lotOf(user, 300), Duration.ofDays(3));    // 300 묶음이 먼저 사라지게

    spend(user, 100);
    assertThat(remaining(lotOf(user, 300))).isEqualTo(200);   // 곧 사라질 것에서 빠짐

    expireNow(lotOf(user, 300));
    runNightlyBatch();
    runNightlyBatch();                                   // 두 번 돌려도
    assertThat(balance(user)).isEqualTo(500);            // 한 번만 빠진다
}
```

## 💡 배운 것

**요약 값만 저장하면 나중에 못 푸는 요구가 생깁니다.** 잔액 하나로는 충분해 보였지만, "언제 들어온 것인가" 가 필요해지는 순간 구조를 바꿔야 했어요.

**기존 데이터는 한 번에 옮기지 않아도 됩니다.** 맞추기 규칙을 두고 배치와 사용 시점에 조금씩 채우면, 이전 작업 없이도 새 구조로 넘어갈 수 있었습니다.

**기본값은 사용자에게 불리하지 않은 쪽으로.** 설정은 모르고 지나치는 사람이 많아서, 기본값이 곧 대부분의 사용자가 겪는 규칙이 됩니다.

## 소감

처음엔 "소멸 배치 하나 돌리면 되겠지" 라고 생각했는데, 막상 보니 무엇을 소멸시킬지 알 방법부터 없었습니다. 기능보다 데이터 구조를 먼저 의심해야 하는 경우가 있다는 걸 배웠고, 기간을 줄였을 때나 환불됐을 때처럼 손님이 손해 볼 수 있는 경우를 하나씩 적어 가며 규칙을 정한 게 도움이 됐습니다.

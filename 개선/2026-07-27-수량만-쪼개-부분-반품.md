# 2026-07-27 3개 중 1개만 반품 - 계산을 새로 짜지 말고 데이터를 쪼갠다

> 태그: #개선 #주문 #환불 #설계

## 무엇을 / 왜
손님이 한 번에 여러 개 산 상품을 반품할 때, 지금까지는 그 품목을 통째로만 반품할 수 있었다.
"3개 샀는데 1개만 반품"이 안 됐다. 실제 쇼핑몰에선 아주 흔한 요청이라 꼭 필요했는데, 주문
데이터가 "이 상품 몇 개"를 한 덩어리로 묶고 진행 상태(반품중/완료 등)도 그 덩어리 단위라 일부만
떼어내기가 까다로워 보였다.

## 어떻게 풀었나
처음엔 "수량을 반품분/잔여분으로 쪼개서 환불 계산을 전부 수량 단위로 다시 짜야 하나" 생각했다.
그런데 그러면 이미 잘 돌아가고 검증된 계산(할인 - 적립금을 상품 비율로 나눠 돌려주는 부분, 재고
복원, 정산 회수)을 통째로 건드려야 해서 위험했다. 돈 계산은 한 번 검증해 둔 걸 함부로 손대고 싶지
않았다.

알고 보니 더 안전한 길이 있었다. 계산을 바꾸는 대신 **데이터를 쪼개는** 것이다.

- 반품할 수량만큼을 아예 **별도의 작은 품목으로 떼어내** 새로 만든다. (5개짜리 → 잔여 4개 + 반품 1개)
- 그 떼어낸 작은 품목에 **기존의 "품목 통째 반품" 처리를 그대로 태운다.**

이러면 환불 - 재고 - 정산 로직을 하나도 안 고치고 재사용할 수 있다. 대신 쪼갤 때 **합계가 원래
주문과 어긋나면 안 된다.** 환불 계산이 "이 품목이 주문 전체에서 차지하는 비율"로 돌아가기 때문에,
쪼갠 두 조각의 합이 원래와 1원이라도 달라지면 그 비율이 틀어진다. 그래서 세 가지를 지켰다.

- **단가는 그대로**(수량만 나눔): 1개값 * 반품수량 + 1개값 * 잔여수량 = 원래 값.
- **할인은 수량 비율로 나누되, 소수점은 반품 조각에 내림 - 나머지는 잔여 조각**에 둬서 두 몫의 합이
  원래 할인과 정확히 같게.
- **배송비는 잔여(원본) 조각에 그대로 두고 반품 조각은 0.** 배송비는 건당 붙는 값이라 부분 반품에선
  돌려주지 않고, 마지막 1개까지 통째로 반품될 때 그 품목의 배송비가 함께 환불되게.

여기에 운 좋게 도움이 된 게 있었다. 주문을 저장할 때 품목들을 **매번 싹 지우고 다시 넣는** 구조라,
메모리에서 품목 목록만 쪼개 놓으면 저장은 알아서 새 품목을 만들고 기존 품목을 갱신했다. 저장 코드나
데이터베이스 구조는 건드릴 필요가 없었다.

"3개 중 1개 반품 → 잔여 2 + 반품 1로 쪼개짐 → 반품한 1개만 재고 복원(남은 2개는 유지) → 환불액이
기존 계산과 정확히 일치"를 통합 테스트로 확인하고, 손님 화면엔 상품별 반품 수량 선택 버튼을 붙였다.

## 💡 배운 것
- **어려운 로직을 새로 짜기 전에 "데이터를 바꿔 기존 로직을 그대로 쓸 수 있나"를 먼저 본다.**
  계산을 수량 단위로 재작성하는 대신, 반품분을 별도 품목으로 쪼개니 검증된 계산을 손 안 대고 썼다.
- **기존 계산이 기대는 불변식을 깨지 않는 게 핵심이다.** 환불이 "비율"로 돌아가므로, 쪼갠 조각들의
  합(값 - 할인 - 배송비)이 원래와 정확히 같아야 한다. 나눌 때 내림으로 생기는 나머지는 한 조각이
  흡수하게 해서 합을 맞췄다.
- **저장 방식이 "전량 삭제 후 재삽입"이면, 목록을 바꾸는 것만으로 추가 - 수정이 처리된다.** 덕분에
  저장 - DB 변경 없이 기능이 얹혔다. 인프라의 성질을 알면 작업량이 줄어든다.

## 코드로 보기 (개념 재현 테스트)
"수량을 쪼개도 값 - 할인의 합이 원래와 같다(그래서 비율 계산이 안 틀어진다)"를 개념만 재현한
골격이다. 실제 내부 이름 - 테이블은 뺐고 값은 더미다.

```java
// 목적: 주문 품목(수량 N)을 반품 M개 + 잔여 (N-M)개로 쪼갤 때
//       값과 할인의 합이 원래와 정확히 같음을 재현. 합이 보존돼야
//       "이 품목이 주문에서 차지하는 비율"로 도는 환불 계산이 안 틀어진다.
class SplitLineTest {

    record Line(int qty, long unitPrice, long discount) {    // 배송비는 잔여 쪽에 두므로 생략
        long gross() { return unitPrice * qty - discount; }  // 이 품목의 상품값(할인 반영)
    }

    // 수량 M개를 별도 조각으로 떼어낸다. 반환: [잔여, 반품]
    static Line[] split(Line src, int claimQty) {
        int remainQty = src.qty() - claimQty;
        // 할인은 수량 비율로 나누되 "내림"은 반품 조각, 나머지는 잔여 조각 -> 두 몫의 합 = 원래 할인
        long claimDiscount = src.discount() * claimQty / src.qty();     // 정수 나눗셈 = 내림
        long remainDiscount = src.discount() - claimDiscount;           // 나머지 흡수
        return new Line[] {
            new Line(remainQty, src.unitPrice(), remainDiscount),
            new Line(claimQty,  src.unitPrice(), claimDiscount)
        };
    }

    @Test
    void 쪼개도_값과_할인의_합이_원래와_같다() {
        Line src = new Line(5, 10_000, 4_000);      // 5개, 각 10,000, 할인 4,000
        Line[] parts = split(src, 2);               // 2개 반품 + 3개 잔여

        // 할인 합 보존: floor(4000*2/5)=1600 + 나머지 2400 = 4000
        assertThat(parts[0].discount() + parts[1].discount()).isEqualTo(src.discount());
        // 상품값 합 보존 -> 주문 전체 대비 비율이 안 틀어진다
        assertThat(parts[0].gross() + parts[1].gross()).isEqualTo(src.gross());
        // 반품 조각엔 반품 수량만 담긴다 -> 재고도 그만큼만 복원된다
        assertThat(parts[1].qty()).isEqualTo(2);
    }
}
```

## 소감
"부분 반품을 지원하려면 계산을 수량 단위로 다 뜯어고쳐야겠다"가 첫 생각이었는데, 그건 검증해 둔 돈
계산을 위험에 빠뜨리는 길이었다. 방향을 "계산을 바꾸지 말고 데이터를 계산이 이해하는 모양으로
쪼개자"로 틀자 문제가 훨씬 작아졌다. 다만 쪼갤 때 합이 1원이라도 어긋나면 안 된다는 조건이 있어서,
나눗셈 나머지를 어디에 둘지까지 정해 합을 못 박았다. 이미 잘 돌아가는 걸 최대한 안 건드리는 게,
돈이 얽힌 기능에선 제일 안전한 선택이라는 걸 다시 느꼈다.

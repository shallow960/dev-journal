# 2026-09-10 가격이 "몇 번째 자리" 에 묶여 있었다

> 태그: #개선 #식별자설계 #위치기반참조 #하위호환

## 무엇을 / 왜

관리 화면에 `상품1 가격` ~ `상품5 가격` 다섯 칸이 있었습니다. 그런데 그 "상품1" 이 지금 무엇인지는 화면 어디에도 안 나옵니다.

값은 설정 표의 다섯 칸에 저장되고, 키오스크는 서버에서 받아 온 **목록의 몇 번째인가**로 가격을 골랐습니다.

열어 보니 그 목록에는 **순서를 정하는 규칙조차 없었습니다.**

## 어떻게 풀었나

### 위치로 뜻을 정하면, 목록이 바뀌는 순간 뜻이 바뀐다

종류를 하나 지우면 뒤엣것이 한 자리씩 당겨집니다. 그러면 **옆 칸 가격을 물려받습니다.**

- 종류 A 를 지우면 B 가 A 의 요금으로 팔립니다
- 종류가 다섯을 넘으면 담을 칸 자체가 없습니다
- 정렬 규칙이 없으니 서버가 목록을 다른 순서로 주기만 해도 값이 어긋납니다

값을 **종류 자체에 붙였습니다.** 가격이 종류를 따라다니니 지우든 순서를 바꾸든 어긋나지 않습니다. 관리 화면도 `상품1 가격` 대신 실제 이름이 뜨게 했습니다.

### 옛 버전이 남아 있는 곳을 고려해야 했다

설치된 장비 중에 옛 프로그램이 남아 있을 수 있어서, 예전 설정 키도 계속 내려보내야 했습니다.

여기서 조심한 게 하나 있습니다. **예전 키를 설정 표에서 읽어서 그대로 내려보내면 안 됩니다.** 그러면 두 곳이 각자 살아 있게 되고, 관리자가 고친 가격과 실제로 파는 가격이 갈라집니다.

**예전 키도 새 출처에서 만들어** 내려보냈습니다. 모양만 옛것이고 값은 한 곳에서 나옵니다.

## 코드로 보기 (개념 재현)

문제가 됐던 구조입니다.

```js
// 서버: 정렬 규칙 없이 목록을 준다
const items = await db.query("select * from item_types where active = true");

// 설정 표: 다섯 칸이 위치로 매겨져 있다
// { item1Price: 5000, item2Price: 8000, item3Price: 12000, ... }

// 키오스크: 목록의 몇 번째인가로 가격을 고른다
function priceOf(index) {
  return settings[`item${index + 1}Price`];   // ★ index 가 뜻을 지고 있다
}
```

`items[0]` 이 무엇인지는 아무도 보장하지 않습니다. 한 종류를 지우면 이렇게 됩니다.

```
지우기 전:  [A, B, C]  →  A=5000  B=8000  C=12000
A 삭제 후:  [B, C]     →  B=5000  C=8000     ← 값이 한 칸씩 당겨졌다
```

값을 종류에 붙였습니다.

```js
// 가격이 종류 자체에 들어 있다. 위치와 무관하다.
const items = await db.query(
  "select id, name, price from item_types where active = true order by sort_order, id"
);

function priceOf(item) {
  return item.price;   // 지우든 순서를 바꾸든 따라다닌다
}
```

옛 버전 호환은 이렇게 뒀습니다.

```js
// 예전 키도 계속 내려보낸다. 단, 출처는 새 값 하나뿐이다.
// ★ settings 에서 다시 읽으면 두 곳이 갈라진다.
function buildLegacySettings(items) {
  const legacy = {};
  items.slice(0, 5).forEach((item, i) => {
    legacy[`item${i + 1}Price`] = item.price;
  });
  return legacy;
}
```

## 💡 배운 것

**"몇 번째" 로 뜻을 정하면, 목록이 바뀌는 순간 뜻이 바뀝니다.** 위치는 값이 아니라 우연입니다. 지우기·순서 변경·정렬 규칙 변경 중 하나만 일어나도 다른 것을 가리키게 됩니다.

**정렬 규칙이 없는 목록을 순서대로 쓰면 안 됩니다.** 지금 순서가 일정해 보이는 건 데이터베이스가 마침 그렇게 돌려주고 있을 뿐입니다. 보장된 적이 없습니다.

**하위 호환은 모양만 유지하고 출처는 하나여야 합니다.** 옛 키를 살려 두더라도 값을 옛 자리에서 읽으면 두 개의 진실이 생깁니다. 새 값에서 옛 모양을 만들어 내보내면 갈라지지 않습니다.

**사람이 보는 화면에는 무엇에 대한 값인지 적혀 있어야 합니다.** `상품1 가격` 은 관리자에게 아무것도 알려 주지 않습니다. 이름이 떠 있으면 잘못 입력하는 일 자체가 줄어듭니다.

## 소감

"가격 칸 하나 늘려 달라" 로 시작한 일이었는데, 열어 보니 **칸을 늘릴 수 없는 구조**였습니다.

값을 어디에 두느냐가 나중에 무엇을 할 수 있는지를 정한다는 걸 봤습니다. 위치에 묶어 두면 다섯 개까지만 되고, 종류에 붙이면 몇 개든 됩니다. 처음 만들 때는 다섯 칸이 더 쉬웠을 거예요.

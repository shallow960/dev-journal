# 2026-10-26 2년마다 보낼 안내를, 때가 된 사람만 SQL 에서 골랐다

> 태그: #개선 #배치 #PostgreSQL #날짜계산 #정보통신망법

## 무엇을 / 왜

광고 메일·푸시를 받겠다고 동의한 사람에게는 동의한 날부터 2년마다 "이렇게 동의해 두셨습니다"라고 알려야 한다는 걸 알게 됐습니다(정보통신망법 제50조제8항, 시행령 제62조의3). 그때까지 서비스에는 그런 안내가 없었습니다.

매일 한 번 도는 작업을 만들면서 처음 떠올린 방식은 이랬습니다.

1. 동의한 사람을 하루 한도(예: 500명)만큼 고르기
2. 코드에서 "때가 됐나, 이번 기간에 이미 알렸나"를 거르기
3. 남은 사람에게 보내기

그런데 이렇게 하면 한도 안에 이미 알린 사람이나 아직 때가 아닌 사람이 들어와 자리를 차지했습니다. 고르는 순서가 같으면 다음 날도 같은 사람들이 뽑혀서, 정작 보내야 할 사람은 한도 밖에서 계속 밀릴 수 있었습니다. 동의한 사람이 쌓일수록 더 심해질 구조였습니다.

## 어떻게 풀었나

### 1. "때가 됐다"를 날짜 규칙으로 풀었습니다

법 조항과 시행령을 읽고 정한 규칙은 이랬습니다.

- 동의한 날부터 2년, 4년, 6년마다 끝나는 기간
- 각 기간이 끝나기 30일 전부터 그 기간의 안내를 한 번
- 놓친 안내는 늦게라도(그 기간 것으로)
- 다시 동의하면 그날부터 다시 세기

### 2. 그 규칙을 고르는 쿼리의 조건으로 옮겼습니다

"오늘로부터 30일 뒤까지, 동의한 날부터 꽉 찬 해가 2년을 몇 번 채웠나"로 지금까지 열린 기간 수를 구했습니다. 그리고 마지막으로 열린 기간이 열린 날(동의일 + 2년 × 기간 수 - 30일)보다 마지막 안내가 앞이면, 또는 안내한 적이 없으면 보낼 차례로 봤습니다. 이 조건을 `where` 에 넣으니 한도 안에는 보낼 사람만 들어왔습니다.

다시 동의하면 동의 시각이 새로 찍히니 계산이 그날부터 저절로 다시 시작됐습니다. 지난 안내 시각을 지우지 않아도, 새 동의일로 다음 기간이 열리기 전에는 기간 수가 0 이라 보내지 않았습니다.

### 3. 날짜는 영업 기준 시간대로 셌습니다

동의 시각은 세계 표준시로 저장돼 있어서, 한국 시간 새벽에 동의한 사람은 날짜가 하루 어긋날 수 있었습니다. 날짜로 바꿀 때 `at time zone` 으로 한국 시간 기준 날짜를 썼습니다.

### 4. 보낸 것만 "알렸다"로 적었습니다

메일 문안이 꺼져 있어서 실제로 나가지 않았으면 알린 것으로 적지 않았습니다. 그래야 문안을 켠 다음 날 다시 고를 수 있었습니다.

## 코드로 보기 (개념 재현)

```sql
-- :today = 오늘(영업 기준 날짜), :zone = 'Asia/Seoul'
with c as (
    select user_id, noticed_at,
           (agreed_at at time zone :zone)::date as agreed_on
      from ad_consents
     where agreed = true
), p as (
    select c.*,
           -- 지금까지 열린 기간 수: 오늘+30일까지 동의일부터 꽉 찬 해 / 2
           floor(extract(year from age(cast(:today as date) + 30, agreed_on)) / 2) as periods
      from c
)
select user_id
  from p
 where periods >= 1
   and (noticed_at is null
        or (noticed_at at time zone :zone)::date <
           -- 마지막으로 열린 기간이 열린 날 = 동의일 + 2년 × 기간 수 - 30일
           cast(agreed_on + make_interval(years => cast(2 * periods as int)) as date) - 30)
 order by agreed_on
 limit 500;
```

```java
// 보낸 사람만 '이번 기간 안내함'으로 적는다. 문안이 꺼져 있어 못 보냈으면 적지 않는다.
for (Due due : dueConsents(today, 500)) {
    if (mailer.sendReconfirm(due)) {
        consents.markNoticed(due.userId(), now);
    }
}
```

시험으로는 이런 경우를 확인했습니다.

- 동의한 지 2년이 되기 30일 전이면 한 번 알리고, 다음 날 다시 돌려도 보내지 않는지(아직 40일 남은 사람, 철회한 사람은 고르지 않는지)
- 기간이 지나도록 놓친 안내를 늦게라도 보내고, 다음 안내가 동의일부터 4년이 되기 30일 전에 가는지
- 다시 동의하면 그날부터 다시 세는지
- 메일 문안이 꺼져 있으면 보낸 것으로 적지 않고, 켜면 보내는지

같은 날 만든 정산 작업에도 같은 함정이 있었습니다. 적립할 품목을 하루 한도만큼 고른 뒤 "적립일이 됐나"를 코드에서 거르면, 아직 때가 안 된 품목이 한도를 채울 수 있었습니다. 그래서 주문마다 남겨 둔 적립일수로 SQL 에서 때가 된 품목만 골랐습니다.

## 💡 배운 것

**"한도로 먼저 고르고 코드에서 거르기"는 거를 행이 많아지면 한도가 그 행으로 찬다는 걸 알게 됐습니다.** 거르는 조건은 고르는 쿼리 안에 있어야 했습니다.

**"2년마다" 한 줄을 코드로 옮기려면 정할 게 여럿이었습니다.** 기준일, 미리 알리는 날짜, 놓친 경우, 다시 동의한 경우, 실제로 못 보낸 경우를 하나씩 정하고 나서야 조건이 하나로 모였습니다.

**사람이 달력으로 이해하는 날짜는 영업 기준 시간대로 세야 했습니다.**

## 소감

처음 떠올린 방식으로 만들었어도 처음 몇 달은 아무 문제가 없었을 것 같습니다. 동의한 사람이 적을 때는 한도가 차지 않으니까요. 문제는 사람이 쌓인 뒤에야 드러날 구조였고, 시험 데이터가 적으면 시험도 통과했을 겁니다. "지금 데이터"가 아니라 "쌓인 뒤의 데이터"에서 어떻게 될지를 생각해 본 게 이번에 가장 도움이 됐습니다.

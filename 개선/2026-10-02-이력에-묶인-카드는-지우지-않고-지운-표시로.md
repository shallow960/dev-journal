# 2026-10-02 이력에 묶인 카드는, 지우지 않고 지운 표시로

> 태그: #개선 #DB #외래키 #소프트삭제 #결제수단 #SQL

## 무엇을 / 왜

구독 서비스의 결제 화면에는 "카드 변경" 버튼이 있습니다. 새 카드를 등록하면 당연히 다음 결제부터 새 카드로 나갈 거라고 생각했는데, 두 가지가 기대와 달랐습니다.

1. 새 카드를 등록해도 **정기결제는 예전 카드로 계속** 나갔습니다. 구독에 붙은 카드는 "비어 있을 때만" 채워지고, 이미 있으면 그대로였기 때문입니다.
2. 예전 카드를 지우려 하면 막혔습니다. 구독이 쓰고 있으면 "사용 중" 이라 막히고, 구독에서 빼도 **한 번이라도 결제한 카드는 결제 기록이 그 카드를 가리키고 있어(외래 키)** 삭제가 실패했습니다. 한 번 쓴 카드는 영영 지울 수 없는 구조였어요.

## 어떻게 풀었나

### 1. 카드 변경 = 다음 결제부터 새 카드

다른 사이트 빌더의 도움말을 보니, 카드를 여러 장 등록해 두고 정기결제에 쓸 카드를 고르며, **정기결제에 쓰는 카드는 다른 카드로 바꾼 뒤에야 지울 수 있게** 하고 있었습니다. 같은 방식으로 맞췄습니다.

- 새 카드를 등록하면 그 카드가 기본 카드가 되고, 구독도 그 카드로 바꾼다.
- 등록해 둔 카드 중에서 "이 카드로 결제" 로 고를 수 있다.
- 정기결제에 쓰는 카드만 삭제를 막고, 막을 때는 "다른 카드로 정기결제를 바꾼 뒤 삭제해 주세요" 처럼 다음에 할 일을 알려 준다.

### 2. 지우는 대신 "지운 표시"

결제 기록은 지우면 안 됩니다(회계·분쟁 대응). 그렇다고 외래 키를 `ON DELETE SET NULL` 로 바꾸면 기록이 어떤 카드로 결제됐는지 잃습니다. 그래서 행은 남기고 **삭제 시각만 기록** 하는 소프트 삭제로 바꿨습니다.

다만 "남긴다" 는 게 위험할 수 있어서, 지울 때 할 일을 정했습니다.

- 결제사에 등록된 정기결제 키는 해지한다(이미 하던 일).
- **우리 DB에 남은 결제 키와 토큰도 비운다.** 남기는 건 이력에 필요한 마스킹 번호(예: `1234-****-****-5678`)뿐이다.
- 목록·기본 카드 조회·결제할 때 쓰는 조회는 모두 지운 카드를 보지 않는다.
- 지운 카드가 기본 카드였다면, 남은 카드 중 가장 최근 것을 기본으로 올린다.

### 3. "기본 카드는 하나" 를 지키는 순서

사용자당 기본 카드는 하나만 있도록 부분 유니크 인덱스(`where is_default`)가 걸려 있었습니다. 기본 카드를 바꿀 때 한 문장으로 "새 카드 true, 나머지 false" 를 하면, 행을 고치는 순서에 따라 잠깐 두 개가 true가 되는 순간 인덱스에 걸릴 수 있습니다. 그래서 **먼저 다른 카드를 모두 내리고, 그다음 하나를 올리는** 두 문장으로 나눴습니다.

## 코드로 보기 (개념 재현)

테이블 이름은 예시입니다.

```sql
-- 지운 표시 컬럼만 추가한다(행은 결제 기록이 가리키므로 남긴다)
alter table saved_card add column deleted_at timestamptz;

-- 삭제: 표시만 하고, 민감한 키는 비운다. 지운 사람(사용자)을 돌려받아 기본 카드 정리에 쓴다.
update saved_card
set deleted_at = now(),
    is_default = false,
    billing_key = null,
    provider_token = null
where id = :id and deleted_at is null
returning user_id;

-- 기본 카드가 하나도 안 남았으면, 남은 카드 중 최근 것을 기본으로
update saved_card set is_default = true
where id = (select id from saved_card
            where user_id = :userId and deleted_at is null
            order by created_at desc limit 1)
  and not exists (select 1 from saved_card
                  where user_id = :userId and deleted_at is null and is_default);

-- 기본 카드 바꾸기: 내리고 나서 올린다(부분 유니크 인덱스와 부딪히지 않게)
update saved_card set is_default = false where user_id = :userId and is_default and id <> :id;
update saved_card set is_default = true  where user_id = :userId and id = :id and deleted_at is null;

-- 결제·목록 조회는 지운 카드를 보지 않는다
select * from saved_card where id = :id and deleted_at is null;
```

```java
// 정기결제 카드 고르기: 남의 카드나 지운 카드는 "없는 카드" 로 본다(404)
@Transactional
public void useCard(UUID userId, UUID cardId) {
    SavedCard card = cards.findActive(cardId)
        .filter(c -> c.userId().equals(userId))
        .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
    cards.markDefault(userId, card.id());
    subscriptions.findCurrent(userId).ifPresent(s -> s.changeCard(card.id()));
}
```

## 💡 배운 것

**외래 키가 막는 데는 이유가 있습니다.** 기록이 가리키는 행은 지우는 대신 "더 이상 쓰지 않음" 을 표시하는 쪽이 기록도 지키고 사용자의 "지우기" 도 만족시킵니다.

**소프트 삭제는 "남기지 말아야 할 것" 을 같이 정해야 합니다.** 행을 남기면서 결제 키까지 남기면 지운 게 아닙니다. 이력에 필요한 것만 남기고 나머지는 비웠습니다.

**소프트 삭제를 넣으면 모든 조회가 대상입니다.** 결제할 때 쓰는 조회가 지운 카드를 다시 집어 오면 안 되므로, 조회 쪽을 빠짐없이 바꿨습니다.

**유니크 인덱스가 있는 값의 "바꾸기" 는 순서를 나눕니다.** 내리고 올리는 두 단계로 나누니 중간 상태에서 부딪히지 않았습니다.

## 소감

"카드 변경" 버튼 하나가 실제로는 카드를 추가만 하고 있었다는 게 이번 일의 시작이었습니다. 화면 문구와 실제 동작이 어긋난 곳을 고치다 보니, 이력 때문에 지울 수 없던 데이터를 어떻게 다룰지까지 정리하게 됐습니다. 예전 카드로 결제한 뒤 새 카드로 바꾸고 예전 카드를 지워도 결제 기록이 남는지, 지운 카드의 키가 비워지는지를 테스트로 확인했습니다.

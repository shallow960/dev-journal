# 2026-08-05 관리 화면 세 개가 각자 뭘 하는 곳인지 흐릿했다

> 태그: #개선 #설계 #커머스 #권한경계

## 오늘 한 일 (요약)
- 여러 판매자가 입점한 쇼핑몰에는 관리 화면이 여러 개다. 가게 주인이 몰 전체를 보는 화면, 입점 판매자가 자기 상품을 다루는 화면, 사이트 기술 설정 화면.
- 그런데 "배송 처리" 같은 기능이 주인 화면에도, 판매자 화면에도 있어서 경계가 흐릿했다.
- 화면마다 역할을 한 문장으로 정의하고, 배송은 판매자 화면으로 몰고, 주인 화면에는 "어느 판매자 주문/상품인지" 식별 정보를 붙였다.

## 무엇을 / 왜 (증상)
가게 주인용 관리 화면에서 주문 목록을 열면 주문번호만 잔뜩 나열됐다. 여러 판매자가 입점한 구조라 한 주문에 여러 브랜드 상품이 섞여 있는데, 목록만 봐서는 "이게 어느 판매자로 들어온 주문인지" 알 수가 없었다. 상품 목록도 상품명만 나열돼 어느 브랜드 상품인지 구분이 안 됐다.

게다가 배송을 처리하는 버튼이 주인 화면에도, 판매자 화면에도 둘 다 있었다. 실제로 물건을 부치는 건 판매자인데 주인 화면에서도 배송 처리가 되니 담당이 모호했다.

## 어떻게 풀었나 - 코드보다 "정의"를 먼저
바로 코드를 고치기 전에, 세 화면이 각각 무엇을 하는 곳인지 한 문장씩 적었다.
- 주인 화면 = 몰 전체를 "보고", 돈이 걸린 결정(주문 취소·환불·교환 승인)을 하는 곳. 배송은 안 한다.
- 판매자 화면 = 자기 브랜드 상품을 올리고, 실제 배송(송장 입력)을 하는 곳.
- 설정 화면 = 도메인·보안 같은 사이트 기술 설정.

이 정의를 기준으로 주인 화면의 주문 액션에서 배송 관련 버튼을 걷어내고, 주인이 내릴 결정 버튼만 남겼다.

그다음 "누구 것인지 안 보인다"는 문제를 풀었다. 주문 목록에는 그 주문에 든 판매자 이름을 꼬리표로 붙였다(한 주문에 여러 판매자면 여러 개). 상품 목록에는 판매자 칸을 새로 만들고, 주인이 직접 파는 상품은 "자체 상품"으로 표시했다. 화면만 바꾼 게 아니라, 뒤쪽 조회(쿼리)에서 주문·상품에 판매자 이름을 함께 뽑아 오도록 고쳤다.

## 코드로 보기 (개념 재현)
```
// (1) 주문 목록 조회 - 그 주문에 든 판매자 이름을 함께 뽑는다
//     한 주문에 여러 판매자면 콤마로 이어서
select o.id, o.order_no,
  (select string_agg(distinct s.name, ', ')
     from order_items i
     join products p on p.id = i.product_id
     join sellers  s on s.id = p.seller_id
    where i.order_id = o.id) as seller_names
from orders o;

// (2) 상품 목록 - 판매자 이름을 붙인다 (없으면 자체 상품)
select p.id, p.name, seller.name as seller_name
from products p
left join sellers seller on seller.id = p.seller_id;

// (3) 주인 화면 주문 버튼 - 배송은 빼고 "결정"만 남긴다
function ownerOrderActions(state) {
  const actions = [];
  if (state === 'PAID')       actions.push('prepare', 'reject', 'cancel');
  if (state === 'REFUND_REQ') actions.push('approveRefund');
  // 배송(ship)/배송완료(complete)는 여기 없음 - 판매자 화면 담당
  return actions;
}
```
포인트는 화면에서 버튼을 지운 것만이 아니라, 조회 단계에서 "누가 파는 상품인가"를 함께 끌어와 목록에서 바로 읽히게 한 것이다.

## 💡 배운 것
- **화면(권한)이 겹쳐 보이면 코드부터 만지지 말고 "이 화면은 무엇을 하는 곳인가"를 한 문장으로 먼저 정의하라.** 정의가 서면 어떤 버튼이 어디로 가야 하는지가 저절로 갈린다.
- **사용자가 "구분이 안 된다"고 하면 그건 대개 데이터 식별성 문제다.** 목록에 "누구 것"인지 한 칸만 붙여도 관리가 확 쉬워진다.
- **역할을 옮기는 건 기능을 더 만드는 게 아니라 제자리로 보내는 일일 때가 많다.** 배송 버튼을 지운 게 곧 담당을 명확히 한 것이었다.
- **정한 경계는 문서로 남겨야 다음에 또 안 흔들린다.**

## 소감
새 기능을 만든 날이 아니라 "정리한" 날이었다. 그런데 정리 전후로 화면이 훨씬 말이 되게 바뀌었다. 처음엔 배송 버튼 위치 문제로 보였는데, 사실은 "세 화면의 역할 정의"가 없어서 생긴 증상이었다. 정의를 먼저 세우니 나머지는 그 정의를 따라 자연스럽게 정리됐다. 코드를 짜기 전에 말로 경계를 긋는 시간이 아깝지 않다는 걸 다시 배웠다.

# 2026-11-16 효과를 누를 때마다 원본 사진을 다시 처리하던 화면을, 미리 만들어 두는 방식으로 바꿨다

> 태그: #개선 #성능 #이미지처리 #Electron #createImageBitmap

## 무엇을 / 왜

사진 키오스크에는 인쇄하기 전에 사진 효과(웜톤, 쿨톤 같은 8가지)를 고르는 화면이 있었습니다. 고객사 QA 에서 "필터를 누르면 적용이 많이 늦다, 부드럽게 해 달라" 는 요청이 왔습니다.

## 어떻게 풀었나

효과 버튼을 누를 때 하는 일을 따라가 보니, 누를 때마다 이 일을 처음부터 다시 하고 있었습니다.

1. 사진 칸에 들어간 카메라 원본(JPEG, 최대 6000×4000)을 다시 디코드
2. 화면 크기로 줄이기
3. 효과 적용
4. 다시 JPEG 로 인코딩

이 일을 사진 네 장에 대해 화면 스레드에서 하고 있었습니다. 개발 PC 에서 재 보니 한 번 누를 때마다 0.6~1.1초가 걸렸고, 그동안 화면이 최대 0.3초씩 멈췄습니다. 효과가 바뀔 때마다 달라지는 것은 3번뿐인데, 1·2·4번까지 매번 다시 하고 있었던 것입니다.

원래 쓰던 프로그램은 어떻게 했는지 찾아봤습니다. 사진을 고른 뒤의 로딩 화면에서 8가지 효과를 작은 크기로 미리 다 만들어 두고, 효과를 누르면 그림만 바꿔 끼우고 있었습니다. 같은 생각으로 고쳤습니다.

- **사진마다 한 번만, 화면 크기로 디코드했습니다.** 파일 머리에서 크기를 먼저 읽고, `createImageBitmap` 에 줄일 크기(긴 변 720)를 함께 넘겼습니다. 찾아보니 `createImageBitmap` 은 디코드와 축소를 비동기로 처리해서, 화면 스레드를 오래 붙잡지 않는다는 걸 알게 됐습니다.
- **(사진, 효과) 마다 한 번만 만들어 들고 있었습니다.** 화면에 들어오자마자 8가지를 차례로 만들되, 손님이 누른 효과를 가장 먼저 만들었습니다. 다 만든 효과는 누르면 그림만 바뀌었습니다.
- **사진을 고르는 동안 미리 디코드했습니다.** 효과 화면을 쓰는 키오스크는 손님이 사진을 고르는 사이에 고른 사진을 미리 읽어 두었습니다.
- **미리보기와 인쇄가 같은 칸 계획을 쓰게 했습니다.** 빠르게 만든 미리보기와 실제 인쇄의 효과가 픽셀까지 같은지 시험으로 묶어 두었습니다.

같은 김에 웜톤·쿨톤 계산에서 픽셀마다 작은 배열을 새로 만들던 것을 없앴습니다. 1,677만 가지 RGB 색 전부에서 결과가 예전 식과 같은 것을 확인했고, 인쇄용 큰 그림을 만드는 시간도 1초쯤 줄었습니다.

고친 뒤에는 사진 고르기 동안 미리 읽어 둔 경우, 효과 화면에 들어온 지 0.5초쯤에 8가지가 모두 준비됐고 그 뒤로는 누르면 바로 바뀌었습니다.

## 코드로 보기 (개념 재현)

이름은 바꾼 더미입니다. 파일 머리에서 크기를 읽는 함수(`readImageSize`), 효과 함수(`applyEffect`), 인코딩(`encode`)은 있다고 가정합니다.

```ts
type EffectId = 'warm' | 'cool' | 'mono' | 'film' | 'soft' | 'vivid' | 'fade' | 'sepia';
const ALL_EFFECTS: EffectId[] = ['warm', 'cool', 'mono', 'film', 'soft', 'vivid', 'fade', 'sepia'];

class PreviewMaker {
  private decoded = new Map<string, Promise<ImageBitmap>>(); // 사진 -> 화면 크기 그림 (한 번만)
  private built = new Map<string, Promise<string>>();        // 사진 + 효과 -> 미리보기 그림 (한 번만)

  constructor(private readonly longSide = 720) {}

  // 원본 JPEG 를 화면 크기로 줄여 한 번만 디코드한다
  private decode(photoId: string, file: Blob): Promise<ImageBitmap> {
    let p = this.decoded.get(photoId);
    if (!p) {
      p = readImageSize(file).then(({ width, height }) => {
        const scale = Math.min(1, this.longSide / Math.max(width, height));
        return createImageBitmap(file, {
          resizeWidth: Math.round(width * scale),
          resizeHeight: Math.round(height * scale),
          resizeQuality: 'medium',
        });
      });
      this.decoded.set(photoId, p);
    }
    return p;
  }

  // 이미 만든 효과는 같은 Promise 를 돌려준다 (누를 때마다 다시 만들지 않는다)
  get(photoId: string, file: Blob, effect: EffectId): Promise<string> {
    const key = `${photoId}:${effect}`;
    let p = this.built.get(key);
    if (!p) {
      p = this.decode(photoId, file).then((bitmap) => encode(applyEffect(bitmap, effect)));
      this.built.set(key, p);
    }
    return p;
  }
}

// 화면에 들어오면 8가지를 차례로 미리 만든다. 손님이 누른 효과가 있으면 그것부터
async function warmAll(cache: PreviewMaker, photos: { id: string; file: Blob }[], first: EffectId) {
  const order = [first, ...ALL_EFFECTS.filter((e) => e !== first)];
  for (const effect of order) {
    await Promise.all(photos.map((p) => cache.get(p.id, p.file, effect)));
  }
}

// 버튼을 누르면: 이미 만든 효과면 바로, 아직이면 그 효과만 기다린다
async function onPickEffect(cache: PreviewMaker, photos: { id: string; file: Blob }[], effect: EffectId) {
  return Promise.all(photos.map((p) => cache.get(p.id, p.file, effect)));
}
```

## 💡 배운 것

- 같은 입력으로 같은 결과를 내는 무거운 일은 누를 때마다 하지 말고, 한 번 만들어 두면 된다는 걸 배웠습니다. 원래 쓰던 프로그램의 로딩 화면이 바로 그 일을 하고 있었습니다.
- 누를 때마다 도는 코드에서 "누를 때마다 달라지는 부분" 과 "늘 같은 부분" 을 나누는 것이 먼저라는 걸 배웠습니다. 이번에는 달라지는 부분이 효과 적용 하나뿐이었습니다.
- `createImageBitmap` 에 줄일 크기를 함께 넘기면, 큰 사진의 디코드와 축소를 화면 스레드 밖에 맡길 수 있다는 걸 알게 됐습니다.
- 미리보기를 빠르게 만들면서 인쇄와 다른 계산을 쓰면, 손님이 화면에서 본 것과 받은 사진이 달라질 수 있었습니다. 그래서 빨라진 뒤에도 두 결과가 같은지 시험으로 묶어 두었습니다.

## 소감

처음에는 효과 계산 자체가 무거운 줄 알았는데, 따라가 보니 누를 때마다 효과와 상관없는 일까지 처음부터 하고 있었습니다. 원래 프로그램이 왜 로딩 화면을 두었는지도 이번에 이해했습니다. 앞으로 화면이 굼뜰 때는 "이 일은 언제 한 번만 해도 되는가" 부터 따져 보려고 합니다.

# 2026-10-22 반품비를 한 번만 빼는 규칙을, 정렬 순서가 아니라 먼저 환불한 순서로 정했다

> 태그: #개선 #정합성 #하위호환 #PostgreSQL

## 무엇을 / 왜

손님이 상품 여러 개를 한 번에 반품하면, 반품 배송비(반품비)는 신청 한 건에 한 번만 받아요. 상자 하나로 돌아오니까요. 그런데 환불은 상품마다 따로 합니다. 판매자가 둘이면 각자 자기 상품을 확인하고 환불하거든요.

그래서 "반품비는 어느 상품 환불에서 빼나"를 정해 둬야 했고, 예전 규칙은 이랬어요.

> 신청에 든 상품 번호를 정렬해서, 첫 상품이 맡는다.

어느 순서로 환불하든 결과가 같고, 따로 기록할 칸도 필요 없는 깔끔한 규칙이었어요. 그런데 이번에 반품 신청을 **거절**할 수 있게 만들면서 구멍이 생겼습니다.

1. 상품 A·B 를 한 번에 반품 신청, 정렬하면 A 가 첫 상품
2. B 를 먼저 환불 → B 는 맡는 상품이 아니라 반품비 0
3. A 를 거절 → A 는 환불되지 않음

반품비가 한 번도 빠지지 않아요. 맡기로 정해 둔 상품이 사라질 수 있게 된 거죠.

## 어떻게 풀었나

### 1. 정해 둔 상품이 아니라, 실제로 먼저 환불된 상품이 맡는다

규칙을 "신청에서 **먼저 환불되는** 상품이 맡는다"로 바꿨어요. 환불할 때 "같은 신청의 다른 상품 환불에서 반품비를 이미 뺐나?"를 보고, 뺐으면 0, 안 뺐으면 반품비를 뺍니다. 그러려면 환불마다 **뺀 반품비를 기록에 남겨야** 해서, 환불 기록에 칸을 하나 더했어요.

두 판매자가 동시에 환불하면 둘 다 "아직 안 뺐네"를 볼 수 있을까요? 같은 주문의 환불은 주문 행을 잠근 뒤에 계산하고 기록해서 하나씩 차례로 돌아요. 그래서 두 번 빠지지 않습니다.

### 2. 새 칸이 비어 있는 예전 기록은 예전 규칙으로 읽는다

새 칸은 배포 전에 환불된 기록에는 비어 있어요(null). 이걸 "반품비 0"으로 읽으면, 배포 전에 B 를 먼저 환불하고(예전 규칙이라 0) 배포 뒤에 A 를 환불하는 신청은 둘 다 0 이 됩니다. 반대로 "뺐다"로 읽으면, 예전에 A 가 이미 낸 반품비를 B 가 또 낼 수 있고요.

그래서 **비어 있으면 예전 규칙대로** 읽게 했어요. 예전 기록이 정렬해 첫 상품의 것이면 그때 반품비를 뺀 것이고, 아니면 안 뺀 것이에요.

### 3. 정렬은 예전 코드와 같은 순서로

예전 규칙의 "정렬"은 자바 문자열 정렬(문자 코드 순서)이었어요. 이걸 SQL 로 옮기면 DB 의 정렬 규칙(collation)을 따르는데, 언어별 정렬 규칙은 하이픈 같은 기호를 거의 무시하거나 순서를 다르게 매기기도 해요. 그래서 `collate "C"` 로 바이트 순서를 지정해 예전 코드와 같은 결과가 나오게 했습니다.

## 코드로 보기 (개념 재현)

```sql
-- 환불 기록에 '이 환불에서 뺀 반품비'를 남긴다(배포 전 기록은 null 로 남는다)
alter table refund_records add column fee_deducted numeric(12,2);
```

```sql
-- 이 상품을 환불할 때: 같은 신청의 다른 상품 환불에서 반품비를 이미 뺐나?
select r.return_fee,
       exists (
           select 1
             from refund_records f
            where f.order_id = r.order_id
              and f.created_at >= r.created_at          -- 이 신청 뒤의 환불만
              and f.item_id <> :itemId
              and f.item_id::text in (select jsonb_array_elements_text(r.item_ids))
              and (f.fee_deducted > 0
                   -- 칸이 비어 있는 예전 환불: 예전 규칙(정렬해 첫 상품이 맡음)대로 본다
                   or (f.fee_deducted is null
                       and f.item_id::text = (select min(t.id collate "C")
                                                from jsonb_array_elements_text(r.item_ids) as t(id))))
       ) as charged_elsewhere
  from return_requests r
 where r.order_id = :orderId
   and r.item_ids @> to_jsonb(cast(:itemId as text))
 order by r.created_at desc
 limit 1;
```

```java
/** 반품비는 신청 1건당 1회. 다른 상품 환불에서 이미 뺐으면 0. */
record ReturnFee(BigDecimal fee, boolean chargedElsewhere) {

    BigDecimal toDeduct() {
        if (chargedElsewhere || fee == null || fee.signum() <= 0) {
            return BigDecimal.ZERO;
        }
        return fee;
    }
}

// 환불: 주문 행을 잠근 뒤 계산하고, 실제로 뺀 만큼을 기록에 남긴다
@Transactional
void refundItem(UUID orderId, UUID itemId) {
    Order order = orderStore.lockForUpdate(orderId);   // 같은 주문의 환불은 차례로
    BigDecimal amount = order.itemAmount(itemId);
    BigDecimal fee = returnFees.find(orderId, itemId).map(ReturnFee::toDeduct).orElse(BigDecimal.ZERO);
    BigDecimal cash = amount.subtract(fee).max(BigDecimal.ZERO);
    payments.refund(orderId, itemId, cash);
    refundRecords.save(orderId, itemId, cash, amount.subtract(cash));   // 뺀 반품비(상품 값보다 크면 상품 값까지)
}
```

시험은 세 가지를 봐요.

- 상품 둘을 한 번에 반품 신청하고 **정렬해 둘째인 상품을 먼저** 환불하면, 그 환불에서 반품비를 뺀다(10,000원 상품이 7,000원 환불)
- 그 뒤 남은 상품의 미리보기는 반품비 0·전액 환불이고, 그 상품을 거절해도 반품비는 한 번 빠진 그대로다
- 먼저 환불한 기록의 새 칸을 비워 두면(배포 전 기록처럼), 예전 규칙대로 정렬해 첫 상품이 반품비를 맡는다

## 💡 배운 것

**"정해 둔 하나가 맡는다" 규칙은, 그 하나가 사라질 수 있게 되면 깨집니다.** 거절이 생기기 전엔 모든 상품이 언젠가 환불됐으니 정렬 규칙이 안전했어요. 기능이 하나 늘면서 전제가 바뀐 거죠. 실제로 일어난 일(먼저 환불)을 기준으로 바꾸고 그 사실을 기록에 남기니, 순서와 상관없이 한 번이 지켜졌습니다.

**새 칸을 더하면 예전 행의 빈 값이 무슨 뜻인지 정해야 합니다.** 0 으로 읽어도, "있음"으로 읽어도 배포를 사이에 둔 신청이 틀어져요. 빈 값을 "예전 규칙대로"로 정하니 진행 중이던 신청도 그대로 맞았습니다.

**코드의 정렬을 DB 로 옮길 때는 정렬 규칙까지 옮겨야 합니다.** 같은 "정렬"이라도 언어와 DB 설정에 따라 순서가 다를 수 있어요.

## 소감

거절 기능을 만들 때는 반품비를 생각하지 못했어요. 보고하면서 "아주 드문 경우 반품비가 안 빠질 수 있다"고 적었는데, 쓰고 보니 드문 경우라도 받아야 할 돈을 못 받는 건 그냥 둘 일이 아니었습니다. 기존 규칙이 왜 안전했는지(모든 상품이 결국 환불된다는 전제)를 따져 보니 고칠 방향이 바로 보였어요.

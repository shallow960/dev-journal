# 2026-09-01 두 체계가 나란히 살아 있으면, 어느 쪽도 진짜가 아니다

> 태그: #개선 #마이그레이션 #설계 #조용한버그

## 무엇을 / 왜

며칠 전 상품 카테고리를 새로 만들었습니다. 표준 분류 1,071개를 넣고, 상품에 붙이고, 인증번호까지 붙였어요.

그런데 옛 카테고리 표를 아직 안 지웠습니다. "화면부터 옮기고 기존 테이블은 나중에"로 미뤄 뒀거든요. 그 "나중에"를 하러 갔다가, 미뤄 둔 사이에 생긴 문제를 발견했습니다.

## 어떻게 풀었나

### 옛 표가 뭐였는지부터 봤다

지우기 전에 이게 뭐 하는 표인지 확인했습니다. 컬럼을 열어 보니 이랬어요.

```
legacy_cate_code     원본 쇼핑몰의 카테고리 번호
legacy_site_id       원본 사이트 아이디
origin_cate_code     원본의 원본?
source_created_at    원본에서 만들어진 시각
```

**설계된 카테고리가 아니라, 다른 쇼핑몰 데이터를 빨아들이려고 만든 적재용 표**였습니다. 그래서 스토어마다 3~4개짜리 얕은 트리만 들어 있었고, 과세·인증 같은 속성도 없었어요. 상품을 제대로 분류할 수가 없던 게 당연했습니다.

지우기로 한 판단이 맞았다는 걸 확인하고 나서 마음이 편해졌습니다. 처음엔 "혹시 내가 모르는 쓰임이 있으면 어쩌지" 싶었거든요.

### 지우기 전에 무엇이 걸려 있는지 셌다

바로 지우지 않고, 옛 표를 참조하는 곳을 전부 찾았습니다.

```
상품            8건이 옛 카테고리에만 붙어 있음
쿠폰            "이 카테고리에 할인" 겨냥이 옛 아이디 배열
라이브·숏폼      "같은 카테고리 상품 추천"이 옛 아이디로 조회
손님몰 화면      카테고리 목록·푸터가 옛 API 호출
이관 도구        옛 표에 데이터를 넣는 유일한 코드
```

생각보다 넓었습니다. 그냥 `drop table` 했으면 쿠폰 할인과 라이브 추천이 조용히 망가졌을 거예요.

### 그러다 죽어 있는 동선을 발견했다

옮기는 김에 손님 화면을 확인했는데, **홈에서 카테고리를 눌러도 상품이 안 걸러졌습니다.**

따라가 보니 이랬습니다.

```
카테고리 타일  →  /categories/01        (새 코드)
검색 화면      →  ?category=01
상품 조회      →  옛 아이디만 받음
프론트 가드    →  "아이디 모양이 아니네" → 조용히 버림
결과          →  전체 목록이 그대로
```

새 체계는 타일까지 왔는데 조회는 옛 체계에 머물러 있었고, 그 사이에 있던 검사 하나가 코드를 소리 없이 버리고 있었습니다.

**오류가 하나도 안 났습니다.** 서버는 "카테고리 없이 전체 조회"를 정상 처리했고, 로그도 깨끗했습니다. 사람이 눌러 보고 "어? 안 걸러지네" 해야만 알 수 있었어요.

### 새 방식이 오히려 더 나았다

옮기면서 알게 된 건데, 새 코드는 계층을 담고 있습니다.

```
01              패션의류잡화
01-01           그 아래
01-01-001       그 아래
01-01-001-005   반소매 티셔츠
```

그래서 "`01`로 시작하는 것 전부"를 찾으면 하위가 다 걸립니다. 트리를 따로 읽어서 자손 목록을 만들 필요가 없어요.

```
전: 카테고리 트리 조회 → 자손 아이디 모으기 → 그 목록으로 상품 조회
후: 코드가 "01" 로 시작하는가
```

옛 아이디 방식에는 **아예 없던 능력**이었습니다. 상위 카테고리를 눌러도 그 카테고리에 직접 붙은 상품만 나왔거든요.

쿠폰도 같은 이유로 좋아졌습니다. "패션 전체 10% 할인"을 코드 하나로 만들 수 있게 됐어요. 예전엔 잎 카테고리를 하나하나 나열해야 했습니다.

### 지울 때 조용히 버리지 않게 했다

쿠폰의 겨냥 값은 옛 아이디라, 새 코드로 자동 변환할 방법이 없었습니다. 확인해 보니 마침 그런 쿠폰이 0건이어서 그냥 지워도 됐어요.

그런데 배포하는 사이에 누가 하나 만들면요?

그래서 **값이 남아 있으면 배포를 멈추게** 했습니다.

```
카테고리를 겨냥한 쿠폰이 있으면 → 배포 실패 + "직접 옮긴 뒤 다시 배포하세요"
```

배포가 실패하는 건 번거롭지만, 할인은 돈이 나가는 일이라 겨냥이 틀어진 채 살아 있는 쪽이 훨씬 무섭습니다.

이관 도구도 같은 이유로 자동 매핑을 안 하기로 했습니다. 원본 쇼핑몰의 카테고리 번호와 우리 표준 분류는 대응이 없어서, 기계적으로 옮기면 엉뚱한 분류가 붙어요. 원본 번호만 남겨 두고 사람이 보고 붙이게 했습니다.

## 코드로 보기 (개념 재현)

```
// 전 - 상위를 눌러도 그 카테고리에 직접 붙은 것만
조회(카테고리아이디):
    where 상품.카테고리아이디 = 준값

// 후 - 상위를 누르면 그 아래 전부
조회(카테고리코드):
    where 상품.카테고리코드 = 준값
       or 상품.카테고리코드 가 (준값 + "-") 로 시작

// "-" 를 붙이는 이유: 그냥 접두만 비교하면 "01-01" 이 "01-010" 까지 잡는다.
// 마디 경계까지 봐야 "01-01" 로 거를 때 "01-02" 가 안 딸려 온다.
```

## 💡 배운 것

- **반쪽만 옮긴 상태가 제일 위험하다.** 옛 것도 새 것도 아닌 동안, 새 코드는 옛 조회를 만나 조용히 버려졌다. 다 옮기거나 안 옮기거나가 낫다.
- **오류가 안 난다고 맞는 게 아니다.** 카테고리 없이 조회하는 건 서버 입장에선 정상 동작이다. 자동으로 안 잡히는 종류의 버그가 있다.
- **지우기 전에 무엇이 걸려 있는지 센다.** 상품·쿠폰·라이브 추천·화면·이관 도구까지 다섯 갈래였다. 바로 지웠으면 할인과 추천이 소리 없이 망가졌을 것이다.
- **식별자에 의미를 담으면 공짜로 얻는 게 있다.** 코드가 계층을 담고 있어서, 트리를 읽지 않고도 "그 아래 전부"를 찾을 수 있었다. 처음엔 그냥 보기 좋으라고 만든 형식인 줄 알았다.
- **돈이 걸린 자리는 조용히 넘어가면 안 된다.** 겨냥이 사라진 쿠폰보다 실패한 배포가 낫다고 판단했다.

## 소감

"나중에 지우자"로 미뤄 둔 게 며칠이었는데, 그 사이에 손님이 카테고리로 상품을 찾는 길이 막혀 있었습니다. 아무도 몰랐고요.

미루는 게 안전한 선택인 줄 알았는데, 오히려 **두 체계가 나란히 사는 동안이 제일 위험했다**는 게 의외였습니다. 새 걸 만들어 놓고 옛 걸 남겨 두면 "둘 다 있으니 괜찮다"가 아니라 "어느 쪽이 진짜인지 아무도 모른다"가 되더라고요.

그리고 지울 때 그냥 지우지 않고 "값이 있으면 멈춰라"를 넣은 게 마음에 들었습니다. 제가 확인한 건 어제의 데이터고, 배포되는 건 내일이니까요.

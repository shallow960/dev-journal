# 2026-08-13 코드는 있는데 부르는 곳이 없었다 - "구현해야 한다"고 생각한 게 이미 다 있었다

> 태그: #개선 #설계 #스프링 #알림

## 오늘 한 일 (요약)
- 알림·크레딧 차감·정산, 셋을 "이제 만들어야지" 하고 시작했다.
- 열어보니 셋 다 **코드가 이미 다 있었다.** 계산도 되고 상태 관리도 되고 테스트까지 통과하고 있었다.
- 안 돌던 이유는 하나였다. **아무도 그 코드를 부르지 않았다.**
- 만드는 대신 이어붙였고, 그 과정에서 "왜 아무도 몰랐나"를 알게 됐다.

## 첫 번째 — 알림은 로그만 찍고 있었다

운영자가 오류 알림 규칙을 만드는 화면이 있다. "이런 오류가 나면 알려줘" 하고 등록하는 것.

화면에는 이렇게 적혀 있었다.

> 규칙 조건·채널은 JSON 구조라 화면에서 만드는 편집기는 아직 없습니다.

그래서 편집기를 만들려고 **규칙을 판정하는 코드**를 먼저 열어봤다. 조건이 얼마나 복잡한지 봐야 폼을 그릴 테니까.

```java
private static boolean matches(JsonNode conditions, ErrorGroup group, boolean groupCreated) {
    if (conditions.path("newGroup").asBoolean(false) && groupCreated) return true;
    int threshold = conditions.path("frequencyThreshold").asInt(0);
    if (threshold > 0 && group.eventCount() >= threshold) return true;
    int unresolvedDays = conditions.path("unresolvedDays").asInt(0);
    return unresolvedDays > 0 && ...;
}
```

읽는 값이 **세 개뿐**이었다. 처음 보는 오류인가, 몇 번 쌓였나, 며칠째 미해결인가.

JSON이라 복잡할 거라 생각했지, 실제로 뭘 읽는지는 아무도 확인 안 한 것이다. 체크박스 셋에 숫자칸 둘이면 되는 걸 "구조가 복잡해서 못 만든다"고 적어둔 채 몇 달이 지났다.

그런데 편집기를 붙이려다 더 큰 걸 발견했다. 규칙이 걸리면 무슨 일이 일어나는지 따라가 봤다.

```java
public void notify(String alertName, JsonNode channels, ErrorGroup group) {
    log.warn("Error alert triggered alert={} group={} channels={}", ...);
}
```

**로그 한 줄.** 메일도 안 가고 메신저도 안 간다. 규칙을 만들고 조건이 맞아도 서버 로그에만 남는다. 알림이라고 부르기 어렵다.

## 두 번째 — 크레딧은 한 번도 줄어든 적이 없었다

라이브 방송은 트래픽을 쓰니까 선불 크레딧을 차감하는 구조로 설계돼 있었다. "충전 → 방송 → 차감 → 소진되면 방송 중단."

차감 부분을 만들려고 봤더니, 이미 있었다.

```java
public ConsumeResult applyUsage(TenantId tenantId, UUID streamId, BigDecimal gb) {
    ConsumeResult result = creditService.consume(tenantId, gb, "live:" + streamId);
    if (result.depleted()) {
        streamControlService.forceEnd(streamId, "credit_depleted");
    }
    return result;
}
```

차감도 하고 소진되면 방송도 끊는다. 테스트까지 통과하고 있었다.

`applyUsage` 를 누가 부르는지 찾아봤다.

```
호출자: 테스트뿐
```

**아무도 안 불렀다.** 왜냐하면 "얼마나 썼는지"를 재는 코드가 없었기 때문이다. 차감할 값이 없으니 부를 수가 없다.

엔진은 완성인데 연료 게이지가 없어서 시동을 못 건 셈이다.

## 세 번째 — 정산은 만들어지는데 조건이 빠져 있었다

정산도 비슷했다. 계산기, 장부, 상태 관리, 환불 시 회수까지 다 있었다. 그런데 적립을 고르는 조건에 "이 주문이 아직 살아 있나"가 빠져 있어서, 환불된 주문이 15일 뒤에 정산으로 되살아나고 있었다. (이건 따로 글을 썼다.)

## 그래서 뭘 했나

만드는 대신 이어붙였다.

- **알림** — 규칙 편집 화면 + 실제 메일·웹훅 전달 + 어디로 갔는지 기록
- **크레딧** — 시청 시간으로 사용량을 재서 5분마다 차감
- **정산** — 빠진 조건 한 줄

셋 다 새로 만든 코드보다 **잇는 코드**가 훨씬 적었다.

## 왜 아무도 몰랐나

이게 더 중요한 질문 같았다. 셋 다 몇 달째 안 돌고 있었는데 아무도 눈치채지 못했다.

**공통점은 "조용히 아무 일도 안 일어났다"는 것이다.**

- 알림은 조건이 맞아도 로그만 찍었다 → 아무도 로그를 안 본다
- 크레딧은 차감이 안 되니 잔액이 그대로다 → "아직 안 썼나 보다"
- 정산은 잘못 만들어져도 장부에만 적혔다 → 화면에서 구분이 안 된다

**실패하지 않았다. 그냥 아무 일도 안 일어났을 뿐이다.** 에러가 났으면 진작 알았을 텐데, 조용해서 몰랐다.

그래서 이번엔 그 반대로 만들었다. 알림 전달이 실패하면 **화면에 실패로 남긴다.**

| 경로 | 결과 | 상세 |
|---|---|---|
| 웹훅 | 보냄 | |
| 메일 | 실패 | SMTP 미설정 |

메일이 안 나가는 건 그대로다(설정이 아직 없다). 달라진 건 **안 나갔다는 걸 볼 수 있다**는 것.

전달 실패는 위로 던지지 않는다. 알림 하나 못 보낸 걸로 오류 수집을 멈출 수는 없으니까. 그런데 그렇게 조용히 넘기면 아무도 모르게 된다. **조용히 넘기되 기록은 남긴다** — 이 둘을 같이 해야 했다.

## 곁다리로 배운 것

**만료가 있는 값은 저장하면 안 된다.** 라이브 재생 주소에 서명을 붙이는 작업도 했는데, 조사 메모에는 "발급할 때 서명해서 저장하면 된다"고 적혀 있었다. 그대로 했으면 큰일 날 뻔했다. 서명에는 만료 시각이 들어간다. 저장해두면 몇 시간 뒤 그 값은 죽는다. 저장은 원본으로 하고 **내보낼 때** 서명을 붙여야 한다.

**스프링에서 자기 클래스 메서드를 부르면 `@Transactional` 이 안 걸린다.** 오늘 이걸 세 번 마주쳤다. 스케줄러가 같은 클래스의 판정 메서드를 부르는 구조를 세 군데 만들려다 매번 다른 빈으로 갈랐다. 프록시를 거쳐야 트랜잭션이 걸리는데 자기 호출은 프록시를 안 지나간다. 무서운 건 **에러가 안 난다**는 것이다. 그냥 트랜잭션 없이 조용히 돈다. 오늘의 주제와 똑같다.

## 배운 것

**"구현해야 한다" 싶으면 먼저 있는지 찾아본다.** 오늘 셋 다 있었다. 특히 오래된 프로젝트일수록 "설계는 다 해놨는데 마지막 한 칸이 안 이어진" 게 많은 것 같다.

**"안 만들어져 있다"와 "안 불리고 있다"는 다르다.** 후자가 훨씬 흔하고 훨씬 안 보인다. 코드가 있으면 검색에 걸리니까 "있네" 하고 넘어가기 쉬운데, 정작 봐야 할 건 **누가 부르는가**다.

**아무 일도 안 일어나는 게 제일 나쁜 실패다.** 에러는 시끄러워서 고쳐진다. 조용한 건 몇 달이 지나도 아무도 모른다. 기능을 만들 때 "안 됐을 때 어떻게 알 수 있나"까지 만들어야 끝이다.

# 2026-09-28 잠가 둔 기록을, 기간이 지나면 지운다

> 태그: #개선 #PostgreSQL #트리거 #개인정보 #보존기간

## 무엇을 / 왜

서비스에는 "누가 언제 로그인했고, 누가 무엇을 바꿨나" 를 남기는 기록 테이블이 있습니다. 이 기록은 조작되면 의미가 없어서, 전에 **DB 트리거로 수정·삭제를 아예 막아** 두었어요(앱 코드에 삭제 기능이 없어도, DB 에서는 누구든 지울 수 있었기 때문).

그런데 개인정보처리방침에는 이렇게 적혀 있었습니다.

```
웹사이트 방문(접속) 기록: 3개월 보관 후 파기
```

실제로는 지울 수 없게 잠가 뒀으니 **영원히 쌓이고** 있었어요. 방침과 동작이 다르면 그 자체가 문제가 됩니다.

게다가 기록마다 보관 기간이 달랐습니다.

| 기록 | 근거 | 보관 |
|---|---|---|
| 손님의 로그인·접속 기록 | 통신비밀보호법 | 3개월 |
| 운영자가 개인정보를 다룬 접속·작업 기록 | 개인정보 안전성 확보조치 기준 | 최소 1년 |

운영자 기록까지 3개월에 지우면 오히려 **법정 보관 의무를 어기게** 됩니다.

## 어떻게 풀었나

### 잠금을 풀지 않았다

가장 쉬운 방법은 트리거를 지우고 배치에서 지우는 겁니다. 하지만 그러면 "지울 수 없다" 는 보장이 사라져요. 잠금은 그대로 두고, **아주 좁은 예외** 하나만 열기로 했습니다.

### 예외 조건 두 가지

1. **정리 배치가 켠 트랜잭션에서만.** 배치가 트랜잭션을 시작하면서 세션 설정값 하나를 켜고, 트리거는 이 값이 켜져 있을 때만 삭제를 고려합니다. `set_config(..., true)` 의 세 번째 인자 `true` 는 "이 트랜잭션에서만" 이라는 뜻이라, 트랜잭션이 끝나면 저절로 꺼져요.
2. **표마다 정한 하한보다 오래된 행만.** 로그인 기록은 3개월, 작업 기록은 1년이 안 된 행은 설정값이 켜져 있어도 거부합니다.

2번이 중요했습니다. 배치 코드에서 실수로 기준 날짜를 잘못 계산해도, **DB 가 최근 기록은 끝까지 지켜 줘요.** 앱 코드와 DB 가 이중으로 막는 구조입니다.

### 손님과 운영자 가르기

로그인 기록 테이블에는 손님과 운영자가 섞여 있었습니다. 사용자의 역할을 보고 "일반 회원 역할만 있는 사람" 은 손님(3개월), 판매자·관리자처럼 **손님 개인정보를 다루는 역할**이 있으면 운영자(1년)로 나눴어요. 누구인지 모르는 로그인 실패 기록은 손님 쪽(3개월)으로 넣었습니다.

## 코드로 보기 (개념 재현)

트리거입니다.

```sql
create or replace function forbid_audit_mutation() returns trigger
language plpgsql as $$
declare
    min_age interval;
begin
    -- 정리 배치가 켠 트랜잭션에서, 표별 하한보다 오래된 행만 지울 수 있다.
    if tg_op = 'DELETE'
       and coalesce(current_setting('app.retention_purge', true), '') = 'on' then
        min_age := case when tg_table_name = 'login_log'
                        then interval '3 months'
                        else interval '1 year' end;
        if old.occurred_at < now() - min_age then
            return old;                       -- 삭제 허용
        end if;
    end if;
    -- 그 밖의 수정·삭제는 전부 거부
    raise exception 'audit log is append-only: % on %', tg_op, tg_table_name;
end;
$$;
```

배치 쪽입니다.

```java
@Transactional
public int purge(OffsetDateTime now) {
    // 이 트랜잭션에서만 켠다. 끝나면 저절로 꺼진다.
    jdbc.sql("select set_config('app.retention_purge', 'on', true)").query(String.class).single();

    int deleted = 0;
    // 손님: 3개월, 운영자: 1년
    deleted += jdbc.sql("""
            delete from login_log l
            where l.occurred_at < :operatorCutoff
               or (l.occurred_at < :customerCutoff and not exists (
                     select 1 from user_roles r
                     where r.user_id = l.user_id and r.role <> 'CUSTOMER'))
            """)
        .param("operatorCutoff", now.minusYears(1))
        .param("customerCutoff", now.minusMonths(3))
        .update();
    // 작업 기록은 모두 운영자 기록이라 1년
    deleted += jdbc.sql("delete from action_log where occurred_at < :cutoff")
        .param("cutoff", now.minusYears(1))
        .update();
    return deleted;
}
```

테스트는 세 가지를 확인했습니다.

- 손님 4개월 전 기록은 지워지고, 운영자 4개월 전 기록은 남는다.
- 배치 밖에서는 오래된 기록도 못 지운다.
- 배치 안이라도 1개월 된 로그인 기록을 지우려 하면 DB 가 거부한다.

## 💡 배운 것

**보관 기간은 기록마다 따로 봅니다.** "접속 기록 3개월" 한 줄만 보고 전부 지웠으면, 최소 1년을 지켜야 하는 운영자 기록까지 사라질 뻔했어요.

**잠금을 풀기보다 좁은 예외를 엽니다.** 트랜잭션 한정 세션 설정값은 "이 작업에서만" 이라는 조건을 DB 에 전달하는 간단한 방법이었습니다.

**코드의 기준과 DB 의 하한을 둘 다 둡니다.** 날짜 계산 한 줄이 틀려도 최근 기록은 지켜지게, 마지막 방어선을 DB 에 뒀습니다.

**되돌릴 수 없는 작업은 첫 실행을 미리 알립니다.** 배포 후 첫 실행 때 그동안 쌓인 오래된 기록이 한꺼번에 지워지는데, 이건 되돌릴 수 없어서 따로 공유했어요.

## 소감

전에 "지울 수 없게" 만든 걸 이번에 "지울 수 있게" 만들면서, 두 요구가 부딪히지 않게 하는 게 핵심이었습니다. 잠금을 걸 때 나중에 기간이 지나면 어떻게 할지도 같이 생각해 뒀으면 좋았겠다는 생각이 들었어요.

# 2026-09-08 법이 정한 항목을 사용자에게 묻지 않기

> 태그: #개선 #폼설계 #스키마설계 #판단을대신하기

## 무엇을 / 왜

전자상거래법에는 "이 물건을 팔려면 이런 항목은 반드시 적어야 한다" 는 규정이 있습니다. 옷이면 소재·치수·세탁방법, 식품이면 원재료·유통기한·영양성분 같은 것들이죠.

안 적고 팔면 시정조치나 과태료 대상입니다. 그런데 우리 상품에는 **이걸 담을 자리가 아예 없었습니다.**

만들어야 했습니다.

## 어떻게 풀었나

### 품목군마다 항목이 다르다

먼저 막힌 건 "항목이 몇 개냐" 였습니다. 하나가 아니었어요.

법이 품목군을 나눠 놓고 각각 다른 항목을 요구합니다. 의류는 9개, 화장품은 11개, 건강기능식품은 11개인데 내용이 전혀 다릅니다. 건강기능식품에는 **"질병의 예방·치료를 위한 의약품이 아니다"** 라는 문구를 적으라는 항목까지 있습니다.

우리 카테고리에 맞춰 추리니 25개 품목군이 나왔습니다.

### 컬럼으로 만들지 않았다

처음엔 컬럼을 쭉 만들까 했습니다. 소재, 색상, 치수... 그런데 품목군마다 항목이 다르니 전부 합치면 100개가 넘습니다. 대부분은 비어 있고요.

게다가 **법이 바뀌면 항목도 바뀝니다.** 컬럼으로 두면 그때마다 스키마를 고쳐야 합니다.

그래서 항목 정의는 표로, 값은 문서형 한 칸에 담기로 했습니다.

```
품목군 표      의류 / 화장품 / 가공식품 ...
항목 표        의류 → 소재, 색상, 치수, 제조자 ...
상품별 값      {"material": "면 100%", "color": "블랙"}
```

품목군이 하나 바뀌어도 표의 행만 고치면 됩니다.

대신 아무 값이나 들어가지 않게 막았습니다. 저장할 때 **그 품목군에 정의된 항목만** 받습니다.

### 어려운 판단을 사용자에게 넘기지 않기

여기서 한참 고민한 게 있습니다. **"이 상품이 어느 품목군이냐" 를 누가 정하냐** 입니다.

처음엔 판매자가 고르게 하려고 했습니다. 파는 사람이 제일 잘 알 테니까요.

그런데 25개 목록을 놓고 보니 생각이 바뀌었습니다. "영상·음향가전" 과 "가정용 전기제품" 은 뭐가 다른가요? TV 는 앞이고 냉장고는 뒤인데, 파는 사람이 그걸 알아야 할 이유가 없습니다.

그러다 상품 카테고리를 보니 답이 있었습니다. **어차피 카테고리는 고르고 있습니다.** "TV" 를 고르는 건 "영상가전" 을 고르는 것보다 훨씬 쉽습니다.

한 가지 조심할 게 있었습니다. **한 카테고리 안에도 다른 품목이 섞입니다.** 가전 안에 TV 와 냉장고가 같이 있고 법정 항목이 서로 다릅니다. 그래서 추천을 상위 분류에 심어 두고 **가장 구체적인 것이 이기게** 했습니다.

### 등록 흐름 안에 넣기

다음 고민은 "어디에 두냐" 였습니다.

별도 화면으로 빼면 깔끔합니다. 상품을 등록하고 나중에 채우는 거죠. 그런데 그러면 **계속 빠뜨립니다.** 법정 의무인데요.

등록 폼의 마지막 단계로 넣었습니다.

여기서 순서 문제가 하나 있었습니다. 고시는 상품에 딸린 것이라 **상품이 저장된 뒤에야** 쓸 수 있습니다. 등록할 때는 저장 전까지 상품 식별자가 없으니까요.

그래서 상품을 먼저 저장하고 이어서 고시를 저장하는데, **고시 저장이 실패하면** 어떻게 할지 정해야 했습니다. 상품은 이미 저장된 상태입니다.

숨기지 않기로 했습니다.

> 상품은 저장됐지만 정보고시를 저장하지 못했습니다. 다시 시도해 주세요.

"저장됐습니다" 라고만 하면 법정 표기가 빠진 채로 팔립니다.

### 빈 칸은 보여 주지 않는다

판매 화면에 표로 나갑니다. 여기서 정한 것 하나.

**값이 안 적힌 항목은 아예 빼고 보여 줍니다.** 처음엔 항목을 다 늘어놓고 빈 칸으로 둘까 했는데, 그러면 "다 적었다" 는 착각만 줍니다.

대신 관리자에게는 **빠진 상품이 몇 개인지** 보여 주는 화면을 따로 만들었습니다.

## 코드로 보기 (개념 재현)

정의는 표로, 값은 문서형으로 나눕니다.

```sql
-- 법정 품목군과 항목 정의 (플랫폼 공통, 법 개정 시 이 표만 고친다)
CREATE TABLE notice_type (
  code       VARCHAR(40) PRIMARY KEY,   -- 'apparel', 'cosmetics' ...
  name       VARCHAR(80) NOT NULL,
  sort_order INT NOT NULL DEFAULT 0
);

CREATE TABLE notice_field (
  type_code  VARCHAR(40) NOT NULL REFERENCES notice_type(code) ON DELETE CASCADE,
  field_key  VARCHAR(40) NOT NULL,      -- 'material', 'color' ...
  label      VARCHAR(160) NOT NULL,     -- '제품 소재'
  sort_order INT NOT NULL DEFAULT 0,
  PRIMARY KEY (type_code, field_key)
);

-- 상품별 값. 항목이 품목군마다 다르므로 컬럼으로 펼치지 않는다.
CREATE TABLE product_notice (
  product_id   BIGINT PRIMARY KEY,
  type_code    VARCHAR(40) NOT NULL REFERENCES notice_type(code),
  field_values JSONB NOT NULL DEFAULT '{}'::jsonb
);
```

문서형으로 두면 아무 키나 들어올 수 있으므로, 저장할 때 정의된 항목만 통과시킵니다.

```java
// 그 품목군에 정의된 키만 남긴다. 화면이 잘못 보내거나 옛 폼이 남아 있어도
// 엉뚱한 키가 쌓이지 않는다. 빈 값은 없는 것과 같게 다뤄 지운다.
List<String> allowed = fieldKeys(typeCode);
if (allowed.isEmpty()) {
    throw new BadRequestException("없는 고시 품목군입니다.");
}

Map<String, String> cleaned = new LinkedHashMap<>();
for (String key : allowed) {
    String value = input.get(key);
    if (value != null && !value.isBlank()) {
        cleaned.put(key, value.trim());
    }
}
```

품목군 추천은 "가장 구체적인 분류가 이긴다" 로 풉니다. 상위에만 심어 두고 조회할 때 좁은 것부터 찾습니다.

```sql
-- 코드가 계층이라 앞자리를 잘라 상위를 만든다.
-- 대분류(2자리)와 중분류(5자리) 중 더 구체적인 쪽이 이긴다.
SELECT notice_type
  FROM category
 WHERE code IN (LEFT(:code, 5), LEFT(:code, 2))
   AND notice_type IS NOT NULL
 ORDER BY LENGTH(code) DESC   -- 긴 코드 = 더 구체적
 LIMIT 1;
```

두 단계로 나뉜 저장은 중간에 끊길 수 있다는 전제로 씁니다.

```js
const savedId = await saveProduct(form);

// 고시는 상품이 저장된 뒤에야 쓸 수 있다(등록 시점엔 식별자가 없다).
// 여기서 실패하면 상품은 이미 저장된 상태다. 그걸 숨기지 않는다.
if (savedId && form.noticeType) {
  try {
    await saveNotice(savedId, form.noticeType, form.noticeValues);
  } catch {
    setError("상품은 저장됐지만 정보고시를 저장하지 못했습니다. 다시 시도해 주세요.");
    return;   // "저장 완료" 로 넘어가지 않는다
  }
}
```

## 💡 배운 것

**사용자에게 무엇을 물을지 정하는 것도 설계입니다.** "판매자가 제일 잘 안다" 는 처음 생각이 틀렸습니다. 판매자가 아는 건 "이건 TV 다" 이지 "TV 는 영상가전 품목군이다" 가 아니었어요. **이미 알고 있는 것으로 모르는 것을 채울 수 있으면** 굳이 묻지 않는 게 맞습니다.

**법이 정한 것은 "나중에" 로 미룰 수 없습니다.** 별도 화면으로 빼면 코드는 깔끔한데 사람이 안 채웁니다. 어느 쪽이 깔끔하냐가 아니라 **어느 쪽이 실제로 지켜지냐** 로 골라야 했습니다.

**절반만 성공했을 때 뭐라고 말할지 미리 정해야 합니다.** 상품은 저장됐는데 고시는 실패한 상황을 생각 안 했으면 "저장됐습니다" 라고 했을 겁니다. 거짓말은 아니지만 중요한 걸 빠뜨린 말이죠.

**모르는 걸 아는 척하지 않는 게 낫습니다.** 빈 칸을 표에 늘어놓으면 화면은 깔끔해지지만 틀린 인상을 줍니다. 비워 두고 "이건 빠졌다" 고 말하는 편이 지저분해도 정확했습니다.

## 소감

스키마를 어떻게 짜느냐보다 **"이 질문을 사용자에게 해도 되는가"** 를 정하는 데 시간을 더 썼습니다. 처음엔 그게 설계가 아니라 화면 문제라고 생각했는데, 답을 바꾸니 데이터 구조까지 달라졌습니다.

법 요건처럼 바깥에서 정해진 규칙을 코드에 넣을 때는, 그 규칙이 나중에 바뀐다는 걸 전제로 두는 게 중요하다는 것도 알았습니다. 표로 뺀 덕분에 항목 하나 추가는 배포 없이 됩니다.

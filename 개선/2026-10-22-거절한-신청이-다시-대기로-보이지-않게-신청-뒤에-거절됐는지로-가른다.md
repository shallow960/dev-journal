# 2026-10-22 거절한 신청이 다시 대기로 보이지 않게, 신청 뒤에 거절됐는지로 가른다

> 태그: #개선 #상태설계 #SQL #기록

## 무엇을 / 왜

반품·교환은 '신청 → 완료' 두 단계뿐이었는데, 판매자가 신청을 **승인하거나 거절**할 수 있게 만들었어요. 거절하면 상품은 신청 전 단계(예: 배송완료)로 돌아가고, 손님은 기간 안이면 다시 신청할 수 있습니다.

그런데 지금까지 "이 신청이 처리를 기다리나"는 **상품의 지금 상태**로 판단하고 있었어요.

> 신청에 든 상품 중 하나라도 '신청 중'이면 그 신청은 대기

거절과 재신청이 생기면 이 판단이 틀려요.

1. 신청 1(상품 A) → 거절 → A 는 배송완료로 돌아감
2. 손님이 다시 신청 → 신청 2(상품 A) → A 는 다시 '신청 중'
3. 신청 1 도 A 를 담고 있으니 **신청 1 까지 대기로 보임**

목록에는 거절한 신청이 다시 대기로 뜨고, 할 일 숫자는 두 번 세이고, 처리 창은 거절된 예전 신청의 사유를 보여 줄 수 있었어요. 반품비도 문제였습니다. 오너가 손님 전화를 받고 대신 반품을 접수하면 신청 기록 없이 상품만 '신청 중'이 되는데, "그 상품을 담은 가장 최근 신청"을 찾으면 거절된 신청 1 의 반품비가 붙었어요.

## 어떻게 풀었나

### 1. 상품 상태에 '거절'을 만들지 않고, 결정을 기록에 남긴다

거절된 상품은 신청 전 상태로 돌아가야 하니, 상품 상태에 '거절'을 둘 수 없어요. 대신 상품마다 쌓이는 처리 기록(요청·완료가 시각과 함께 쌓이는 표)에 **승인과 거절도 한 줄씩** 남겼습니다. 거절 줄에는 사유를 적고요.

### 2. "신청 뒤에 거절됐는가"로 가른다

기준을 이렇게 정했어요.

> 신청이 그 상품에 아직 유효하다 = 신청 시각 뒤에, 그 상품에 **같은 종류**(반품이면 반품, 교환이면 교환)의 거절 기록이 없다

- 위 예에서 신청 1 은 A 의 거절 기록이 신청 1 뒤에 있으니 끝난 신청, 신청 2 는 그 뒤로 거절이 없으니 유효해요.
- "같은 종류"가 중요해요. 교환을 마친 상품을 나중에 오너가 반품 접수했다가 거절하면, 그 거절이 예전 교환 신청을 '거절'로 만들면 안 되니까요.
- 신청 기록과 상품의 요청 기록은 한 트랜잭션에서 저장돼 시각이 같고(PostgreSQL 의 now() 는 트랜잭션 시작 시각), 거절은 그 뒤의 트랜잭션이라 항상 늦어요. 그래서 `>=` 로 비교해도 안전합니다.

### 3. 조건은 한 곳에서 만들어 모두 같은 기준을 쓴다

이 조건을 SQL 조각을 돌려주는 함수 하나로 만들고, 목록 상태·할 일 숫자·반품비 계산·처리 창이 모두 그걸 쓰게 했어요. 신청의 상태도 이 기준으로 셉니다.

- 유효한 상품 중 '신청 중'이 있으면 **승인 대기**
- 없고 '승인'이 있으면 **승인(회수·완료 대기)**
- 담은 상품이 모두 거절됐으면 **거절**
- 그 밖에는 **완료**(일부만 거절된 경우 포함)

## 코드로 보기 (개념 재현)

```java
/** 신청(별칭 req)이 그 상품(itemId)에 아직 유효한가: 신청 뒤 같은 종류의 거절이 없다 */
static String notRejectedAfter(String req, String itemId) {
    return """
        not exists (
            select 1 from item_claim_events e
             where e.item_id = %2$s
               and e.kind = %1$s.kind
               and e.state = 'REJECTED'
               and e.created_at >= %1$s.created_at)""".formatted(req, itemId);
}
```

```sql
-- 신청마다 담은 상품을 세어 상태를 정한다
select r.id,
       count(*) filter (where not x.rejected and x.state = 'REQUESTED') as pending,
       count(*) filter (where not x.rejected and x.state = 'APPROVED')  as approved,
       count(*) filter (where x.rejected)                              as rejected,
       count(*)                                                        as total
  from return_requests r
  cross join lateral (
      select l.state,
             exists (select 1 from item_claim_events e
                      where e.item_id = l.id and e.kind = r.kind
                        and e.state = 'REJECTED' and e.created_at >= r.created_at) as rejected
        from order_lines l
       where l.id::text in (select jsonb_array_elements_text(r.item_ids))
  ) x
 group by r.id;
```

```java
static String status(long pending, long approved, long rejected, long total) {
    if (pending > 0) return "PENDING";      // 승인 대기
    if (approved > 0) return "APPROVED";    // 승인, 회수·완료 대기
    return total > 0 && rejected == total ? "REJECTED" : "DONE";
}
```

시험은 거절 → 재신청을 그대로 따라가요. 거절한 뒤에는 그 신청이 '거절'(사유 포함)이고 할 일 숫자가 0 인지, 손님이 다시 신청하면 목록이 [새 신청 '승인 대기', 예전 신청 '거절'] 순서인지, 그리고 거절 뒤 오너가 대신 접수한 반품에 예전 신청의 반품비가 붙지 않는지(전액 환불)를 봅니다.

## 💡 배운 것

**지금 상태만으로는 "어느 신청의 상태인지"를 알 수 없습니다.** 같은 상품에 신청이 여러 번 생길 수 있게 되자, 상품 쪽 상태는 마지막 신청만 말해 줬어요. 신청 쪽에서 "내 뒤에 무슨 일이 있었나"를 기록으로 확인하니 신청마다 제 상태를 가졌습니다.

**되돌아가는 결정은 상태 칸이 아니라 기록에 남깁니다.** 거절은 상품을 원래대로 돌리는 결정이라 상태 칸에 둘 곳이 없었어요. 시각이 있는 기록에 남기니 "언제, 어느 신청 뒤에"를 물을 수 있었습니다.

**같은 판단을 여러 쿼리가 하면, 조건을 한 곳에서 만들어야 합니다.** 목록·숫자·반품비 중 한 곳만 기준이 달라도 화면끼리 숫자가 어긋나요.

## 소감

처음엔 거절을 "상품을 되돌리고 기록 한 줄"로 가볍게 생각했어요. 그런데 재신청까지 따라가 보니, 지금까지 상태 칸 하나에 기대던 판단이 전부 흔들렸습니다. 기능을 더할 때 "이걸로 바뀌는 전제가 있나"를 먼저 따져 보는 습관이 필요하다는 걸 다시 느꼈어요.

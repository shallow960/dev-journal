# 2026-11-04 판매 기간이 지난 상품을 내리는 예약 작업을 만들지 않았다

> 태그: #개선 #설계 #SQL #쇼핑몰 #Spring

## 무엇을 / 왜

상품 표에는 판매 시작과 끝 시각을 담는 칸이 처음부터 있었습니다. 판매 가능한지 따지는 메서드에도 이 칸이 들어 있었습니다. 그런데 입력하는 화면이 없었고, 그 메서드를 부르는 곳도 없었습니다. 손님 목록도 주문도 이 칸을 보지 않았습니다.

그러다 보니 정해진 기간에만 파는 상품은 쇼핑몰 주인이 그 시각에 맞춰 직접 올리고 내려야 했습니다.

이 칸을 실제로 쓰게 만들기로 했습니다. 가장 먼저 정해야 했던 것은, 시각이 됐을 때 상품이 어떻게 바뀌게 할 것인가였습니다.

## 어떻게 풀었나

### 상태를 바꾸지 않고, 읽을 때 시각과 비교했습니다

방법은 두 가지였습니다.

- 예약 작업이 주기적으로 돌면서, 기간이 지난 상품의 상태를 판매 중지로 바꾼다.
- 상태는 그대로 두고, 손님 쪽 조회가 읽을 때마다 지금 시각과 비교한다.

예약 작업 쪽을 따져 보니 걸리는 것이 있었습니다. 쇼핑몰 주인이 직접 내린 상품과 기간 때문에 내려간 상품이 같은 상태가 되는 것이었습니다. 그러면 나중에 기간을 늘려 다시 팔려고 할 때 어느 상품을 되살려야 할지 알 수 없게 될 터였습니다. 작업이 도는 주기만큼 늦게 내려가고, 작업이 멈추면 끝난 상품을 계속 팔게 된다는 것도 걱정이었습니다.

읽을 때 비교하면 되돌릴 것이 없었습니다. 칸의 값만 바꾸면 다음 조회부터 바로 맞았고, 살펴야 할 작업도 생기지 않았습니다. 그래서 두 번째 방법으로 정했습니다.

### 손님이 상품을 만나는 입구를 모두 찾았습니다

조건은 상수 하나로 두었습니다. 찾아보니 손님이 상품을 만나는 곳은 생각보다 많았습니다. 목록과 상세 말고도 브랜드 목록, 사이트맵, 기획전, 여러 몰을 모아 보는 검색, 라이브 상품, 숏폼 추천이 각자 자기 쿼리를 갖고 있었습니다. 이 입구를 모두 찾아 같은 조건을 붙였습니다.

관리 화면의 조회에는 붙이지 않았습니다. 쇼핑몰 주인은 기간 밖의 상품도 찾아서 고칠 수 있어야 했기 때문입니다.

### 장바구니는 조회 조건으로 막을 수 없었습니다

조회 조건만으로는 막지 못하는 길이 하나 있었습니다. 장바구니였습니다. 목록에서 사라져도 어제 담아 둔 상품은 장바구니에 그대로 남아 있었고, 그 사이에 판매 기간이 끝날 수 있었습니다.

그래서 주문을 만들 때 다시 확인하게 했습니다. 기간 밖이면 어떤 상품 때문인지 이름과 함께 알려 주고 주문을 받지 않았습니다.

### 안 보이는 까닭을 관리 목록에 적었습니다

상태를 바꾸지 않은 대가도 있었습니다. 관리 목록에는 판매중으로 나오는데 손님에게는 보이지 않는 상품이 생겼습니다. 쇼핑몰 주인에게는 고장처럼 보일 수 있었습니다. 그래서 목록에 '판매 예정 · 11.10 10:00부터', '판매 기간 끝남' 을 함께 보여 줬습니다.

### 경계 시각도 하나로 맞췄습니다

시작 시각은 포함하고 끝 시각은 포함하지 않기로 정했습니다. 예전 메서드는 끝 시각 정각도 판매 중으로 보고 있어서, 새로 만든 쿼리 조건과 경계가 달랐습니다. 쿼리 조건, 메서드, 관리 목록의 안내가 모두 같은 경계를 쓰게 고쳤습니다.

## 코드로 보기 (개념 재현)

```java
// 손님 쪽 조회에 붙이는 조건 (개념 재현 - 실제 이름과 다름)
public final class SalePeriod {

    // 시작은 포함하고 끝은 포함하지 않는다. 비어 있으면 기간 없이 판다.
    public static final String IN_PERIOD =
        "(p.sale_start is null or p.sale_start <= now())"
            + " and (p.sale_end is null or p.sale_end > now())";

    private SalePeriod() {
    }
}
```

```java
// 손님 목록: 상태 칸은 건드리지 않고 읽을 때 걸러 낸다 (개념 재현)
List<ProductRow> publicProducts(UUID storeId) {
    return jdbc.sql("select p.id, p.name, p.price from product p"
            + " where p.store_id = :storeId and p.status = 'ACTIVE' and " + SalePeriod.IN_PERIOD
            + " order by p.created_at desc")
        .param("storeId", storeId)
        .query(ProductRow.class)
        .list();
}

// 주문: 조회 조건을 거치지 않고 들어온 장바구니 상품을 다시 확인한다
void requireInPeriod(UUID productId) {
    jdbc.sql("select p.name from product p where p.id = :id and not (" + SalePeriod.IN_PERIOD + ")")
        .param("id", productId)
        .query(String.class)
        .optional()
        .ifPresent(name -> {
            throw new ResponseStatusException(HttpStatus.CONFLICT,
                "지금은 판매 기간이 아닌 상품이 있어요(" + name + "). 장바구니에서 빼고 다시 주문해 주세요.");
        });
}
```

// 관리 목록의 안내: 판매중인데 왜 안 보이는지 알려 준다 (개념 재현)
function salePeriodNotice(startAt: string | null, endAt: string | null, now = new Date()) {
  if (startAt && new Date(startAt) > now) return `판매 예정 · ${label(startAt)}부터`;
  if (endAt && new Date(endAt) <= now) return `판매 기간 끝남 · ${label(endAt)}`;
  return null; // 기간 안이거나 기간이 없으면 말할 것이 없다
}

## 💡 배운 것

- 시각이 지나면 바뀌는 것을 상태 칸에 옮겨 적으면, 원래 상태와 시각 때문에 바뀐 상태가 섞였습니다. 읽을 때 계산하니 되돌릴 것이 없었습니다.
- 대신 "상태는 판매중인데 손님에게는 안 보이는" 경우가 생겼습니다. 상태를 저장하지 않기로 했다면, 그 까닭을 화면이 말해 줘야 했습니다.
- 읽을 때 비교하는 방법은 그 시각에 무언가를 보내는 일에는 쓸 수 없었습니다. 판매 시작 알림 같은 일이 생기면 그때는 예약 작업이 따로 필요하다고 봤습니다.
- 조회 조건으로 막는 규칙은 미리 담아 둔 장바구니처럼 조회를 거치지 않는 길에는 듣지 않았습니다. 돈이 오가는 마지막 단계에서 다시 확인해야 했습니다.

## 소감

칸은 오래전부터 있었는데 기능은 없었습니다. 칸을 읽게 만드는 일은 쿼리 몇 줄이었지만, 어디서 읽어야 하는지 찾고 어떻게 바뀌게 할지 정하는 일이 대부분이었습니다. 다만 시험은 이미 시작 전이거나 이미 끝난 시각의 상품을 넣어 확인한 것이라, 실제로 시각이 지나면서 상품이 나타나고 사라지는 모습은 아직 화면에서 직접 확인하지 못했습니다. 그건 남은 일로 적어 두었습니다.

# 2026-10-21 알림 구독은 확인 링크로 시작하고, 해지는 버튼으로 끝낸다

> 태그: #개선 #메일 #이중확인 #보안 #SQL

## 무엇을 / 왜

서비스 상태 페이지에는 "장애가 생기면 메일로 알려 주세요" 구독이 있어요. 살펴보니 세 가지가 비어 있었습니다.

- **확인이 없었다.** 아무 주소나 넣으면 바로 구독이 됐어요. 남의 주소를 넣을 수도 있고, 이미 구독 중인 사람의 "받을 서비스" 범위를 다른 사람이 바꿀 수도 있었습니다.
- **해지할 길이 없었다.** 메일에 해지 링크가 없었어요.
- **같은 주소로 신청을 반복할 수 있었다.** 여기에 확인 메일만 붙이면, 남의 메일함에 메일을 퍼붓는 도구가 됩니다.

## 어떻게 풀었나

1. **이중 확인(더블 옵트인).** 신청하면 구독은 아직 시작하지 않고 확인 메일만 보내요. 링크(24시간)를 눌러야 구독이 시작되고, 신청 때 고른 범위도 이때 반영합니다. 이미 구독 중인 주소여도 같아서, 남이 대신 신청해도 주인이 링크를 누르기 전엔 아무것도 바뀌지 않아요. 확인 전 구독자에게는 장애 메일을 보내지 않습니다.
2. **확인 토큰은 해시로 저장.** 링크 속 토큰은 원문 대신 해시만 DB 에 두고, 링크로 들어온 값을 해시해서 찾습니다.
3. **확인 메일은 같은 주소에 10분에 한 번.** "조회 → 판단 → 저장"을 따로 하면 동시에 두 번 들어온 신청이 둘 다 메일을 보낼 수 있어서, 신청을 받는 SQL 한 문장 안에서 판단했어요. 10분 안에 보낸 적이 있으면 예전 토큰을 그대로 두고, 돌려받은 토큰이 이번에 만든 것과 같을 때만 메일을 보냅니다.
4. **해지는 화면에서 버튼으로.** 장애 메일마다 해지 링크를 달되, 링크를 열자마자 해지되게 만들지 않았어요. 회사 메일의 보안 검사기는 받은 메일의 링크를 미리 열어 보는 경우가 있어서, 열기만 해도 해지되면 받는 사람도 모르게 알림이 끊길 수 있습니다. 그래서 해지 화면에서 버튼을 눌러야 해지 요청을 보내요. 없는 링크나 이미 해지한 링크여도 같은 답을 줘서, 그 주소가 구독 중인지 알 수 없게 했습니다.
5. **확인은 화면이 열린 뒤 스크립트가 보냅니다.** 주소만 받아 보는 검사기는 화면 스크립트를 돌리지 않으니 대부분 확인까지 가지 않아요. 혹시 확인되더라도 링크는 그 메일함에만 갔으므로 "주소의 주인 확인"이라는 목적은 지켜집니다. 조용히 일어나도 받는 사람이 손해 볼 일이 적어서, 해지와 달리 한 번 더 누르게 하지 않았어요.

이 밖에 장애 공지를 고칠 때는 상태가 바뀐 경우에만 다시 알리게 했어요. 제목 오타를 고칠 때마다 메일이 가면 안 되니까요. 구독 신청 자체도 공개 요청 남용 방지 한도(10분 5번)를 탑니다.

## 코드로 보기 (개념 재현)

```sql
-- 구독 신청: 같은 주소면 범위는 '대기'에만 두고, 확인 메일은 10분에 한 번만
insert into alert_subscribers (email, scope, pending_scope, verify_token_hash, verify_expires_at, verify_sent_at)
values (:email, '[]', :scope, :hash, now() + interval '24 hours', now())
on conflict (email) do update
set pending_scope = excluded.pending_scope,              -- 지금 받는 범위는 건드리지 않는다
    verify_token_hash = case
        when alert_subscribers.verify_sent_at > now() - interval '10 minutes'
            then alert_subscribers.verify_token_hash      -- 10분 안이면 예전 토큰 유지
        else excluded.verify_token_hash end,
    verify_expires_at = case
        when alert_subscribers.verify_sent_at > now() - interval '10 minutes'
            then alert_subscribers.verify_expires_at
        else excluded.verify_expires_at end,
    verify_sent_at = case
        when alert_subscribers.verify_sent_at > now() - interval '10 minutes'
            then alert_subscribers.verify_sent_at
        else excluded.verify_sent_at end
returning verify_token_hash = :hash as should_send;      -- 이번 토큰이 저장됐을 때만 메일을 보낸다
```

```sql
-- 확인: 대기 중인 범위를 반영하고, 해지용 토큰을 처음 한 번 만든다
update alert_subscribers
set scope = coalesce(pending_scope, scope),
    pending_scope = null,
    verified_at = coalesce(verified_at, now()),
    verify_token_hash = null,
    verify_expires_at = null,
    leave_token = coalesce(leave_token, :newLeaveToken)
where verify_token_hash = :hash
  and verify_expires_at > now()
returning email, scope;
```

```tsx
// 해지 화면: 열기만 해서는 아무 일도 없고, 버튼을 눌러야 POST 를 보낸다
export function LeavePage({ token }: { token: string }) {
  const [state, setState] = useState<"idle" | "working" | "done">("idle");

  async function leave() {
    setState("working");
    await fetch("/api/alerts/leave", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ token })
    });
    setState("done"); // 서버는 없는 링크여도 같은 답을 준다
  }

  return state === "done"
    ? <p>이제 장애 알림을 보내지 않아요.</p>
    : <button disabled={state === "working"} onClick={leave}>알림 그만 받기</button>;
}
```

## 💡 배운 것

**GET 으로 열리는 링크는 상태를 바꾸지 않는 게 기본입니다.** 메일 속 링크는 사람만 여는 게 아니라서, 되돌리기 어려운 동작(해지)은 사람이 누르는 버튼 뒤에 두는 게 안전했어요.

**"10분에 한 번" 같은 제한은 SQL 한 문장으로 판단하면 동시 요청에도 안전합니다.** `on conflict ... do update` 안의 `case` 와 `returning` 으로 "보낼지 말지"까지 한 번에 받았어요.

**이중 확인은 주소의 주인을 확인하는 장치라, 범위 변경도 그 뒤에 둬야 합니다.** 구독 시작만 막고 범위는 바로 바꿔 주면, 남이 내 알림 범위를 바꿔 버릴 수 있어요.

## 소감

처음에는 "확인 메일 하나 붙이면 끝"이라고 생각했는데, 확인 메일 자체가 남용 도구가 될 수 있고 해지 링크는 기계가 먼저 열 수 있다는 걸 떠올리니 손볼 곳이 꽤 많았어요. 확인·해지 화면이 열리는 것까지는 봤고, 실제 메일로 끝까지 해 보는 건 메일 발송 서비스 승인 뒤로 남겨 뒀습니다(확인 필요).

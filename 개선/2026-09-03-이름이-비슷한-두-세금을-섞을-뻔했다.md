# 2026-09-03 이름이 비슷한 두 세금을 섞을 뻔했다

> 태그: #개선 #도메인이해 #세금 #정산

## 무엇을 / 왜

부가세 신고는 사업자가 분기마다 반드시 하는 일입니다. 그런데 우리 쇼핑몰에는 그 숫자를 **합산해 볼 데가 없었습니다.**

주문 하나하나의 금액은 다 있어요. 문제는 신고서에 적을 형태로 모아 주는 화면이 없다는 거였습니다. 그러면 오너가 주문 목록을 엑셀로 내려받아서 직접 더해야 합니다. 분기마다요.

만들기로 했습니다. 처음엔 "이미 있는 숫자를 더하기만 하면 되니까 금방이겠네" 라고 생각했어요.

## 어떻게 풀었나

### 이미 있는 줄 알았던 값

정산 데이터를 뒤지다가 `surtax` 라는 컬럼을 찾았습니다. 우리말로 "부가세" 예요. 값도 들어 있고요.

**이걸 그냥 쓰면 되겠다** 고 생각했습니다.

그런데 이 값이 어떻게 계산되는지를 따라가 봤더니 이랬습니다.

```
surtax = (판매가 - 원가 - 결제수수료) ÷ 11
```

판매가에서 원가와 수수료를 뺀 값. 그러니까 **마진** 입니다. 마진에 붙는 부가세예요.

제가 신고서에 적어야 하는 건 그게 아니었습니다. **손님이 상품값에 얹어서 낸 부가세** 입니다.

```
마진 부가세     오너가 얼마를 남겼는지에 붙는 것
상품 부가세     손님이 물건값에 얹어서 낸 것    ← 신고할 것
```

둘 다 이름이 "부가세" 고 둘 다 정산 표에 있습니다. 그냥 썼으면 신고액이 완전히 다른 숫자가 나왔을 거예요. 세금이라 나중에 문제가 생겼을 거고요.

이름이 비슷하다고 같은 게 아니라는 걸, 컬럼 이름만 보고 넘어갈 뻔했습니다. 계산식을 열어 본 게 다행이었어요.

### 과세인지 면세인지는 누가 정하나

다음 문제가 더 어려웠습니다. 모든 상품에 부가세가 붙는 게 아닙니다.

- 과세: 대부분의 공산품
- 면세: 책, 가공 안 된 농수산물, 일부 교육·의료
- 비과세: 애초에 과세 대상이 아닌 것

이걸 누가 정해야 할까요. 처음엔 **상품 등록할 때 판매자가 고르게** 하려고 했습니다. 상품마다 다르니 파는 사람이 제일 잘 알 것 같았거든요.

그런데 생각해 보니 이게 꽤 어려운 판정이었습니다. 갓 딴 사과는 면세인데 말린 사과칩은 과세라거나, 종이책은 면세인데 전자책은 경우가 다르다거나요. 판매자가 매번 정확히 고를 거라고 기대하기 어렵고, 틀리면 **신고액이 틀립니다.**

그러다 상품 카테고리 표를 보는데 `tax_type` 컬럼이 이미 있었습니다.

```
과세     971개
면세      73개
비과세    29개
```

표준 카테고리에 구분이 이미 들어 있었어요. 카테고리는 어차피 상품을 등록할 때 고르는 거고, "이 상품이 도서인가"를 고르는 건 "이 상품이 면세인가"를 고르는 것보다 훨씬 쉽습니다.

**판매자에게는 쉬운 걸 묻고, 어려운 판정은 카테고리가 대신하게** 했습니다.

### 모르는 건 모른다고 표시하기

그런데 카테고리를 안 고른 상품이 있으면 어떻게 될까요. 실제 데이터에 있었습니다. 2건, 24,624원.

세 가지 선택지가 있었습니다.

1. 과세로 치고 합계에 넣는다 → 아닐 수도 있는데 세금을 더 내게 된다
2. 조용히 뺀다 → 신고에서 빠지는 걸 아무도 모른다
3. 빼되, 얼마인지 알려 준다

3번으로 했습니다. 합계에는 안 넣되 화면 맨 위에 이렇게 띄웁니다.

> 과세 구분을 못 정한 매출 24,624원이 아래 합계에서 빠져 있어요

그리고 **어느 상품 때문인지** 도 목록으로 보여 줍니다. 그래야 카테고리를 채워서 다음 분기엔 제대로 잡히게 할 수 있으니까요.

표 안에서도 그 줄의 공급가액 칸은 숫자 대신 `-` 로 뒀습니다. 과세인지 면세인지 모르면 공급가액도 모르는 건데, 판매가를 그대로 적어 두면 아는 척하는 게 되거든요.

### 이 숫자가 무슨 기준인지 적어 두기

만들면서 정해야 할 게 몇 개 더 있었습니다.

**언제 것으로 잡나.** 세법상 원칙은 물건을 건넨 시점입니다. 그런데 온라인 판매는 보통 결제일로 잡아요. 어느 쪽이든 한쪽으로 정해야 합니다.

**취소·환불은.** 빼야죠. 그런데 **교환** 은 넣습니다. 물건만 바뀌고 돈은 그대로라 매출이 유지되거든요. 이건 좀 헷갈려서 주문 상태를 하나씩 짚어 가며 정했습니다.

정하고 나서, **화면 아래에 이 기준들을 그대로 적어 뒀습니다.**

세무 담당자가 보고 "우리는 인도 기준으로 잡아야 한다" 고 하면 기준을 바꿔야 하는 일입니다. 그런데 안 적어 두면 **이 숫자가 어느 기준인지 아무도 모릅니다.** 코드를 열어 보는 수밖에 없어요.

숫자를 보여 주는 화면은 숫자만으로 부족하다는 걸 이번에 알았습니다.

### 반올림을 두 번 하지 않기

사소한데 안 하면 티 나는 것도 하나 있었습니다.

우리 가격은 소비자가라 부가세가 이미 들어 있습니다. 그래서 거꾸로 계산해요.

```
공급가액 = 판매가 ÷ 1.1
세액     = 판매가 - 공급가액
```

세액도 `판매가 ÷ 11` 로 따로 구할 수 있는데, 그러면 나눗셈을 두 번 하게 됩니다. 각각 반올림하면 **공급가액 + 세액이 판매가와 안 맞는** 일이 생겨요. 몇 원 차이지만 신고 숫자에서 몇 원이 안 맞으면 이상합니다.

한 번만 나누고 나머지는 빼기로 구했습니다.

## 배운 것

**이름이 같다고 같은 값이 아닙니다.** `surtax` 를 그냥 썼으면 잘못된 신고액을 화면에 띄웠을 거예요. 그리고 이건 화면이 깨지는 종류의 버그가 아니라 **숫자가 그럴듯하게 틀리는** 종류라서, 아무도 눈치 못 챘을 겁니다. 이미 있는 값을 갖다 쓰기 전에 그게 어떻게 만들어진 값인지 한 번 열어 보는 습관을 들여야겠습니다.

**어려운 판단은 사용자에게 넘기지 않는 게 낫습니다.** 처음엔 "판매자가 제일 잘 아니까 고르게 하자" 고 생각했는데, 사실은 **판매자도 잘 모르는** 판단이었어요. 이미 고르고 있는 것(카테고리)에서 답이 나온다면 그쪽이 훨씬 낫습니다. 사용자에게 뭘 물을지 정하는 것도 설계라는 걸 알았습니다.

**모르는 걸 숨기지 않는 게 더 안전합니다.** 카테고리 없는 상품을 과세로 쳐서 넣었으면 화면은 깔끔했을 거예요. 대신 틀렸겠죠. 조용히 뺐으면 화면은 깔끔하고 숫자도 맞지만 누락을 영영 몰랐을 거고요. 빼고 알리는 게 화면은 제일 지저분한데 제일 정직합니다.

**숫자를 보여 주는 화면에는 기준도 같이 적어야 합니다.** 이번에 처음 해 봤는데, 쓰면서 제 머릿속도 정리됐어요. "교환은 왜 포함이지?" 를 글로 적으려니 스스로 근거를 대야 했거든요. 적을 수 없는 기준은 사실 제가 아직 안 정한 기준이었습니다.

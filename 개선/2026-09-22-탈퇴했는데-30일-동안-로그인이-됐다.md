# 2026-09-22 탈퇴했는데, 30일 동안 로그인이 됐다

> 태그: #개선 #개인정보 #탈퇴 #배치 #데이터정합성

## 무엇을 / 왜

개인정보 보관 기간을 정리하는 문서를 쓰다가, 문서에 적으려던 문장을 실제로 확인해 봤습니다. "탈퇴하면 개인정보를 즉시 파기합니다" 라는 문장이었습니다.

코드를 따라가 보니 탈퇴 처리가 하는 일은 하나뿐이었습니다.

```sql
update users set status = 'withdrawn' where id = ?
```

상태값만 바뀝니다. 그래서 이런 일이 벌어지고 있었습니다.

| 확인한 것 | 실제 |
|---|---|
| 로그인 | 남아 있던 토큰으로 **최대 30일 계속 접속** |
| 재입고 알림 | 신청해 둔 상품이 들어오면 **계속 발송** |
| 배송지·장바구니·찜 | 그대로 남음 |
| 본인인증 원본 | 실명·휴대폰·생년월일 그대로 남음 |
| 관리 화면에서 탈퇴 처리 | 개인정보가 통째로 남음 |

"즉시 파기" 라고 쓸 수 있는 상태가 아니었습니다.

## 어떻게 풀었나

### 출구가 두 개인데, 하는 일이 달랐다

먼저 탈퇴가 일어나는 경로를 찾아봤습니다. 두 곳이었습니다.

- 회원이 직접 탈퇴하는 화면
- 관리자가 관리 화면에서 회원 상태를 바꾸는 기능

둘 다 결국 같은 결과여야 하는데, 각자 다른 코드를 타고 있었습니다. 관리자 쪽은 상태값만 바꾸고 끝이었고요.

처리를 한곳으로 모았습니다. 어느 문으로 나가든 같은 절차를 밟습니다.

1. 로그인 토큰·세션·비밀번호 재설정 링크 폐기
2. 배송지·장바구니·찜·좋아요·재입고 알림·푸시 토큰 삭제
3. 본인인증 원문(실명·휴대폰·생년월일) 삭제
4. 적립금 소멸, 쿠폰 사용 불가
5. 이름·이메일·연락처를 알아볼 수 없는 값으로 바꾸기

### 다 지우면 안 되는 것도 있었다

전부 지우면 될 줄 알았는데 아니었습니다.

**주문 기록**은 법으로 5년 보관해야 합니다. 그래서 주문은 남기되 받는 사람 정보만 가립니다. **리뷰**는 다른 손님들이 보고 물건을 고르는 자료라, 지우면 남아 있는 손님이 손해입니다. 작성자 이름만 "탈퇴한 회원" 으로 바꿨습니다.

**적립금**은 조금 달랐습니다. 잔액을 0으로 만들면 끝일 것 같은데, 적립금은 "얼마를 왜 주고 뺐다" 를 줄 단위로 쌓아 두는 장부입니다. 잔액만 손대면 장부 합계와 잔액이 어긋납니다. 그래서 **"탈퇴 소멸" 이라는 줄을 하나 더 쌓아서** 0으로 만들었습니다. 지우는 게 아니라 흐름을 이어 둡니다.

### 지웠더니 숫자가 틀어졌다

찜을 지우고 나서 상품 화면을 보니 **찜한 사람 수가 그대로** 였습니다.

찜 수를 매번 세면 느리니까 상품 행에 숫자로 들고 있었습니다. 찜을 추가할 때 +1, 뺄 때 -1 하는 식입니다. 그런데 탈퇴에서는 찜 줄만 지우고 숫자를 건드리지 않았습니다. 아무도 찜하지 않은 상품이 "12명이 찜했어요" 라고 표시됩니다.

숏폼 좋아요 수도 같은 구조라 같은 문제가 있었습니다. 지우면서 숫자도 같이 줄이게 고쳤습니다.

**미리 세어 둔 숫자가 있으면, 원본을 지울 때 숫자도 같이 손봐야 한다.** 지울 때는 잘 안 떠오르는 부분이었습니다.

### 진행 중인 주문이 있으면 탈퇴를 막았다

주문 흐름을 보다가 하나 더 걸렸습니다.

배송 중인 상태에서 탈퇴하면, 나중에 그 주문이 취소되거나 반품될 수 있습니다. 그런데 취소·환불 처리는 **썼던 적립금을 돌려주고 쿠폰을 되살립니다.** 탈퇴로 방금 소멸시킨 적립금이 다시 생깁니다.

```
탈퇴 → 적립금 소멸(0원)
  ↓ 3일 뒤
배송 중이던 주문 반품 → 환불 처리 → 적립금 5,000원 복원
  ↓
탈퇴한 회원에게 적립금이 남는다
```

되살아난 적립금은 쓸 사람이 없습니다. 그렇다고 환불 로직에서 "탈퇴 회원이면 건너뛰기" 를 넣으면, 이번엔 손님이 받아야 할 돈을 못 받는 경우가 생길 수 있습니다.

그래서 **진행 중인 주문·취소·반품·교환이 있으면 탈퇴 자체를 막기로** 했습니다. 끝나지 않은 거래가 있는 채로 관계를 정리할 수는 없으니까요. 화면에는 왜 막혔는지와 어떤 주문 때문인지를 같이 보여 줍니다.

### 이미 나간 사람들은 어떻게 하나

고친 코드는 앞으로 탈퇴하는 사람에게만 적용됩니다. 예전 방식으로 **상태만 "탈퇴" 인 채 남아 있는 회원**은 그대로입니다.

새벽에 도는 배치를 하나 만들었습니다. 상태가 "탈퇴" 인데 아직 파기되지 않은 회원을 찾아서 같은 절차를 태웁니다.

여기서 고민한 건 **"파기했는지 안 했는지를 어떻게 아느냐"** 였습니다. "처리했음" 컬럼을 새로 만들 수도 있지만, 컬럼을 하나 더 만들면 그 값이 실제와 어긋날 수 있습니다.

이메일을 파기할 때 알아볼 수 없는 값으로 바꾸는데, 이때 **정해진 형태**를 쓰기로 했습니다.

```
withdrawn:9a21c4f0@withdrawn.local
```

이 형태면 파기된 것이고, 아니면 아직입니다. **상태를 따로 기록하지 않고 결과 자체로 판별**합니다. 배치가 여러 번 돌아도 이미 처리한 회원은 두 번째부터 그냥 걸러집니다.

### 순서 때문에 멀쩡한 사람이 로그아웃될 뻔했다

파기 절차 안에서 로그인 세션을 끊는데, 이걸 어디에 둘지가 문제였습니다.

처음엔 절차 중간에 뒀습니다. 그런데 뒤쪽에서 오류가 나면 데이터베이스 작업은 전부 되돌아갑니다(탈퇴가 취소됨). 반면 **세션 종료는 되돌아가지 않습니다.** 결과적으로 탈퇴는 안 됐는데 로그아웃만 당한 회원이 생깁니다.

세션 종료를 **탈퇴가 확정된 뒤에 실행**되도록 옮겼습니다. 되돌릴 수 없는 작업은 되돌릴 수 있는 작업이 다 끝난 뒤에 해야 한다는 걸 이때 알았습니다.

### 인증만 하고 가입 안 한 사람의 정보도 남아 있었다

찾다 보니 하나 더 나왔습니다.

본인인증을 하면 기관이 실명·휴대폰·생년월일을 돌려주고, 가입 화면이 그걸 쓸 수 있게 잠깐 저장해 둡니다. 그런데 인증만 하고 가입을 안 하면 그 기록이 **계속 남아 있었습니다.** 가입한 적도 없는 사람의 실명과 전화번호가요.

한 시간마다 도는 정리 배치를 붙였습니다. 인증 후 1시간이 지난 기록의 원문을 지웁니다. 재가입 방지용으로 쓰는 해시값만 남깁니다.

정리하다가 알게 된 건, **만료된 인증창 세션을 지우는 코드는 이미 있었는데 부르는 곳이 없었다**는 점입니다. 만들어 두고 연결을 안 한 상태였습니다. 이번에 같이 불러 줬습니다.

## 코드로 보기 (개념 재현)

고치기 전입니다.

```java
public void 탈퇴(UUID 회원id) {
    회원저장소.상태변경(회원id, "withdrawn");   // 이게 전부
}
```

고친 뒤입니다. 되돌릴 수 없는 작업은 맨 뒤로 뺐습니다.

```java
@Transactional
public void 탈퇴(UUID 가게id, UUID 회원id) {
    var 회원 = 회원저장소.찾기(회원id).orElseThrow();
    if (이미_파기됨(회원.이메일())) return;      // 여러 번 돌려도 안전

    진행중인_거래_확인(회원id);                  // 있으면 409 로 막는다

    개인정보_지우기(회원id);                     // 배송지·장바구니·찜·재입고·푸시
    찜_지우고_상품_찜수_줄이기(회원id);           // 세어 둔 숫자도 같이
    본인인증_원문_지우기(회원id);                 // 해시는 남긴다
    적립금_소멸시키기(회원id);                    // 장부에 소멸 줄을 쌓는다
    익명화(회원id);                              // 이메일을 정해진 형태로

    // 되돌릴 수 없는 작업은 커밋된 다음에
    커밋후실행(() -> 세션전부종료(가게id, 회원id));
}

private void 진행중인_거래_확인(UUID 회원id) {
    int 건수 = 주문저장소.진행중_건수(회원id, 진행중_상태들);
    if (건수 > 0) {
        throw new 충돌("진행 중인 주문이 " + 건수 + "건 있어 탈퇴할 수 없습니다");
    }
}
```

파기 여부를 결과로 판별하는 부분입니다.

```java
/** 파기된 이메일은 이 형태다. 따로 표시 컬럼을 두지 않는다. */
static String 익명이메일(UUID 회원id) {
    return "withdrawn:" + 회원id.toString().substring(0, 8) + "@withdrawn.local";
}

static boolean 이미_파기됨(String 이메일) {
    return 이메일 != null
        && 이메일.startsWith("withdrawn:")
        && 이메일.endsWith("@withdrawn.local");
}
```

찜을 지울 때 숫자도 같이 줄입니다.

```java
void 찜_지우고_상품_찜수_줄이기(UUID 회원id) {
    // 어떤 상품을 찜했는지 먼저 확보한다. 지우고 나면 알 수 없다.
    List<UUID> 상품들 = 찜저장소.상품목록(회원id);
    찜저장소.삭제(회원id);
    for (UUID 상품id : 상품들) {
        상품저장소.찜수_감소(상품id);   // 0 밑으로는 안 내려가게
    }
}
```

## 💡 배운 것

**정책 문장은 코드로 확인해 봐야 압니다.** "즉시 파기합니다" 는 문서에 이미 적혀 있었습니다. 실제로는 상태값만 바뀌고 있었고요. 문서에 쓰기 전에 한 번 따라가 본 게 다행이었습니다.

**같은 결과여야 하는 일은 입구가 여러 개여도 처리는 하나여야 합니다.** 본인 탈퇴와 관리자 탈퇴가 각자 코드를 갖고 있으니 한쪽만 부실했습니다.

**미리 세어 둔 숫자는 원본과 같이 손봅니다.** 찜 수, 좋아요 수처럼 성능을 위해 들고 있는 값은 지울 때 잊기 쉽습니다.

**처리 여부는 별도 표시보다 결과 자체로 판별하는 게 안전합니다.** 컬럼을 하나 더 두면 그 값이 실제와 어긋날 수 있습니다. "이 형태면 처리됨" 으로 두면 어긋날 일이 없고, 여러 번 돌려도 안전합니다.

**되돌릴 수 없는 작업은 맨 뒤로 뺍니다.** 세션 종료, 메일 발송, 외부 호출은 트랜잭션이 되돌아가도 같이 되돌아가지 않습니다.

**지우기 전에 남은 거래를 확인합니다.** 끝나지 않은 주문이 있으면 나중에 되살아나는 값이 생깁니다. 막는 게 정리하는 것보다 낫습니다.

## 소감

"지운다" 가 이렇게 손이 많이 가는 일인 줄 몰랐습니다. 지워야 할 것, 남겨야 할 것, 남기되 가려야 할 것이 섞여 있고, 지운 뒤에 틀어지는 숫자까지 챙겨야 했습니다.

작업을 마치고 실제로 계정을 만들어 탈퇴시켜 봤습니다. 다시 로그인이 안 되고, 상품의 찜 수가 줄고, 리뷰는 남되 작성자가 "탈퇴한 회원" 으로 바뀌는 걸 확인했습니다.

남은 건 두 단계 더 있습니다. 30일 뒤 잔여 기록을 정리하는 것과, 가게 자체가 문을 닫을 때의 파기입니다. 개인정보는 한 번에 다 끝나는 작업이 아니라 기한별로 나눠서 도는 일이라는 걸 이번에 알았습니다.

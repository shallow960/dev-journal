# 2026-08-04 배송은 주문 하나로 묶였는데, 정산은 상품마다 쪼개져 있었다

> 태그: #개선 #데이터모델 #커머스 #정산

## 오늘 한 일 (요약)
- 여러 판매자의 상품이 한 주문에 함께 담기는 마켓에서, **판매자마다 자기 상품만 배송 처리**하게 만들어야 했다.
- 그런데 배송·송장 정보가 **"주문 1건당 1세트"** 로만 저장돼 있어서, 판매자 A가 배송 처리를 하면 같은 주문의 판매자 B 상품까지 "배송중"으로 바뀌었다.
- 위험한 주문 상태 로직은 그대로 두고, **품목마다 송장·배송상태를 따로 저장하는 표를 새로 얹어** 판매자별 독립 배송을 만들었다.

## 무엇을 / 왜 (증상)
여러 판매자가 입점한 마켓에서는 손님이 한 번에 여러 브랜드 상품을 함께 담아 결제한다. 결제는 한 건이지만, 실제 배송은 **브랜드마다 따로** 나간다. A 브랜드가 자기 상품을 오늘 부치고, B 브랜드는 내일 부칠 수 있다.

그런데 기존 구조에서는 배송 정보(택배사, 송장번호, 배송상태)가 **주문 하나당 한 줄**로만 저장돼 있었다. 주문 상태를 바꾸는 로직도 "주문이 배송중이 되면 그 주문의 모든 품목이 배송중"처럼 **주문 전체를 한꺼번에** 움직이게 돼 있었다.

이 구조로는 "A 상품만 배송 시작"이 표현되지 않는다. A가 송장을 넣으면 주문 전체가 배송중이 되고, 같은 주문에 든 B 상품도 (아직 안 부쳤는데) 배송중으로 보인다.

## 어떻게 풀었나 - 기억에 남는 비대칭 하나
코드를 따라가다 **이상한 비대칭**을 발견했다.

- **정산(누가 얼마 받나)** 은 이미 **상품(품목) 단위**로 쪼개져 있었다. "이 품목은 이 판매자 매출"이라고 품목마다 주인이 적혀 있었다.
- 그런데 **배송만 주문 단위**로 묶여 있었다.

같은 "판매자별로 갈라야 하는 일"인데, 정산은 품목 단위로 준비돼 있고 배송은 주문 단위에 머물러 있던 것이다. 배송을 정산과 같은 "품목 단위"로 맞추면 문제가 풀리는 구조였다.

문제는 **주문 상태 로직을 직접 건드리는 건 위험**하다는 거였다. 취소·환불·재고 복원 같은 게 다 그 상태 흐름에 얽혀 있어서, 거길 "품목별"로 바꾸면 파장이 너무 크다.

그래서 코어를 건드리는 대신, **품목별 배송 정보를 담는 표를 따로 만들었다.** 품목 하나가 한 줄이고, 각 줄에 그 품목의 배송상태(준비/배송중/배송완료)·택배사·송장번호를 담는다. 판매자가 송장을 넣으면 이 표의 "그 품목 줄"만 갱신된다. 코어 주문 상태머신은 그대로 두고, **판매자의 배송 이행은 이 새 표가 진실**이 되게 했다.

한 가지 더 중요한 건 **소유 판정**이었다. 판매자는 자기 상품만 건드릴 수 있어야 한다. 그래서 송장을 넣을 때 "이 품목의 상품 주인이 요청한 판매자와 같은가"를 확인하고, 아니면 아예 없는 것처럼(404) 막았다.

## 코드로 보기 (개념 재현)
```
// (기존) 배송이 주문 단위 - 주문 하나에 배송 정보 한 줄
//   order_shipping(order_id PK, courier, tracking_no, status)
//   => A가 송장 넣으면 order_id 기준이라 주문 전체가 배송중

// (개선) 배송을 품목 단위로 - 품목 하나에 배송 정보 한 줄
create table item_shipping (
  order_item_id  bigint primary key,        // 주문의 "품목" 단위
  status         text not null default 'preparing', // preparing/shipped/delivered
  courier        text,
  tracking_no    text,
  shipped_at     timestamptz,
  delivered_at   timestamptz
);

// 판매자가 송장 등록 - 본인 품목만
function shipItem(sellerId, orderItemId, courier, trackingNo) {
  const item = findOrderItem(orderItemId);

  // 소유 판정: 이 품목의 상품 주인이 요청한 판매자인가?
  if (item.productOwnerId !== sellerId) {
    throw new NotFound();       // 남의 품목은 존재 자체를 숨긴다
  }

  // 이 "품목 줄"만 갱신 - 같은 주문의 다른 품목엔 영향 없음
  upsert(item_shipping, {
    order_item_id: orderItemId,
    status: 'shipped',
    courier, tracking_no: trackingNo,
    shipped_at: now(),
  });
}
```
핵심은 배송의 **키를 order_id에서 order_item_id로** 내린 것이다. 그러면 같은 주문 안에서도 품목마다 상태가 독립적으로 존재한다.

## 💡 배운 것
- **같은 성격의 일이 두 군데에서 다른 단위로 다뤄지고 있으면, 그 비대칭이 버그의 씨앗이다.** 정산은 품목 단위인데 배송만 주문 단위였던 게 정확히 문제의 원인이었다. 단위를 맞추는 게 해법이었다.
- **위험한 코어 로직은 바꾸지 말고, 옆에 평행한 표를 얹어 필요한 단위를 표현하라.** 주문 상태머신을 품목별로 뜯는 대신, 품목별 배송 표를 따로 두니 파장 없이 필요한 동작만 얻었다.
- **여러 주체가 같은 데이터를 나눠 쓸 때는 소유 판정이 필수다.** "본인 것만" 건드리게 하고, 남의 것은 실패가 아니라 존재를 숨기는(404) 편이 안전하다.
- **하나의 결제 = 여러 배송**은 마켓형 커머스의 기본 구조다. 결제 건수와 배송 건수를 1:1로 묶어두면 멀티 판매자에서 반드시 막힌다.

## 소감
처음엔 "배송상태 하나 바꾸는 건데 왜 이렇게 얽혀 있지" 싶었다. 그런데 정산 쪽을 보다가 "어? 정산은 이미 품목별로 갈라놨네"를 발견한 순간 방향이 잡혔다. 결국 새로 발명한 게 아니라, 이미 한쪽(정산)이 하고 있던 "품목 단위"를 배송에도 똑같이 맞춰준 것뿐이다. 위험한 코어를 안 건드리고 옆에 표 하나를 얹는 방식이, 큰 기능을 안전하게 더하는 좋은 패턴이라는 걸 다시 느꼈다.

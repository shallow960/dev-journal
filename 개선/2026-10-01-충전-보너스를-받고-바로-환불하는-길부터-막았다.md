# 2026-10-01 충전 보너스를 받고 바로 환불하는 길부터 막았다

> 태그: #개선 #결제 #선불크레딧 #정책설계 #TypeScript

## 무엇을 / 왜

쇼핑몰 운영자가 손님에게 문자·알림톡을 보낼 때 내는 요금을, 미리 충전해 두고 보낸 만큼 차감하는 **선불 크레딧** 방식으로 바꾸기로 했습니다. 문자 서비스들이 흔히 쓰는 방식이고, 많이 충전할수록 보너스 크레딧을 더 줍니다.

실제 결제와 발송은 서비스를 열 때 붙이기로 해서, 이번에는 그때 그대로 쓸 화면과 **요금 규칙** 을 먼저 정했습니다. 규칙을 정하다 보니 단가보다 먼저 막아야 할 구멍이 보였습니다.

## 어떻게 풀었나

### 1. 차감이 소수점 없이 나뉘는 단위

처음에는 "문자 1건 = 1크레딧" 처럼 건수를 단위로 생각했는데, 장문·알림톡처럼 값이 다른 메시지가 섞이면 0.7크레딧 같은 소수가 생깁니다. 소수 크레딧은 화면에서도, 환불 계산에서도 반올림 문제를 계속 만듭니다.

그래서 크레딧을 **돈에 가까운 작은 단위** 로 잡고(예: 결제 금액 몇 원 = 1크레딧), 메시지마다 차감량을 정수로 정했습니다. 결제 금액은 부가세까지 포함한 금액을 기준으로 해서 "내가 낸 돈으로 몇 크레딧" 이 한눈에 보이게 했고요.

### 2. 보너스율은 "1건에 얼마" 로 비교

충전 단계마다 보너스율을 정할 때, 퍼센트만 보면 감이 잘 안 왔습니다. 그래서 **보너스를 포함했을 때 메시지 1건이 실제로 얼마인지** 를 계산해 단계끼리, 그리고 흔한 시세와 비교하면서 정했습니다. 충전 창에도 "이 단계로 충전하면 1건에 약 얼마" 를 같이 보여 줍니다.

### 3. 보너스가 만든 구멍: 충전하고 바로 환불

보너스가 커지면 이런 일이 가능해집니다.

1. 가장 큰 단계로 충전해서 보너스 크레딧을 크게 받는다
2. 몇 건만 쓰고
3. 남은 크레딧(보너스 포함)을 기준으로 환불을 받는다

남은 크레딧에 보너스가 섞여 있으면, 환불 금액이 실제로 낸 돈보다 커질 수 있습니다. 그래서 환불 규칙을 이렇게 정했습니다.

- 환불 기준은 **결제한 금액** 이다. 보너스로 받은 크레딧은 남은 금액 계산에 넣지 않는다.
- 결제 후 일정 기간 안에, 한 건도 쓰지 않았으면 전액 환불한다.
- 쓴 적이 있으면 사용분과 수수료를 빼고 환불한다.
- 남은 금액이 너무 작으면 환불하지 않는다(처리 비용이 더 크다).

### 4. 미리보기와 실제 연결 지점을 한곳으로

지금 화면은 결제·발송 없이 **브라우저에만 저장되는 미리보기** 이고, 화면에도 그렇게 적었습니다. 나중에 실제 API를 붙일 때 여러 곳을 고치지 않도록, 충전·차감·설정을 처리하는 함수와 단가·보너스율 표를 **한 파일** 에 모았습니다. 열 때는 그 파일의 함수 안쪽만 실제 호출로 바꾸면 됩니다.

## 코드로 보기 (개념 재현)

숫자는 모두 예시입니다.

```ts
// 단가와 보너스율은 한곳에만 둔다(바꿀 때 여기만 고친다)
export const WON_PER_CREDIT = 1;                 // 예시: 결제 1원 = 1크레딧
export const DEDUCTION = { sms: 10, lms: 30, alimtalk: 7 } as const; // 메시지당 차감(정수)
export const TIERS = [
  { amount: 10_000, bonusRate: 0 },
  { amount: 100_000, bonusRate: 0.1 },
  { amount: 1_000_000, bonusRate: 0.2 }
];

export function quote(amount: number, bonusRate: number) {
  const vat = Math.round(amount * 0.1);
  const paid = amount + vat;                               // 실제 결제 금액(부가세 포함)
  const baseCredits = Math.floor(paid / WON_PER_CREDIT);   // 낸 돈으로 산 크레딧
  const bonusCredits = Math.floor(baseCredits * bonusRate);
  const credits = baseCredits + bonusCredits;
  return { paid, baseCredits, bonusCredits, credits, wonPerSms: (paid / credits) * DEDUCTION.sms };
}

type Charge = { paid: number; baseCredits: number; usedCredits: number; daysSincePaid: number };

// 환불: 보너스는 계산에 넣지 않는다. 쓴 크레딧은 "낸 돈으로 산 크레딧" 에서 먼저 뺀다.
export function refundable(c: Charge): number {
  if (c.usedCredits === 0 && c.daysSincePaid <= 7) return c.paid;        // 미사용·기간 내 전액
  const leftBase = Math.max(0, c.baseCredits - c.usedCredits);           // 보너스 제외 잔량
  const leftWon = Math.floor(leftBase * WON_PER_CREDIT);
  const fee = Math.floor(leftWon * 0.1);                                  // 예시 수수료율
  const refund = leftWon - fee;
  return refund < 1_000 ? 0 : refund;                                     // 너무 작으면 환불 없음
}
```

`refundable` 에서 보너스를 넣었다면, 큰 단계로 충전하고 조금 쓴 뒤 환불받는 것만으로 낸 돈보다 많이 돌려받을 수 있었습니다.

## 💡 배운 것

**혜택을 설계할 때는 "되돌릴 때" 를 같이 봅니다.** 보너스는 충전 화면에서는 장점이지만, 환불 규칙과 만나면 바로 악용 경로가 됩니다.

**단위가 계산을 단순하게 만듭니다.** 크레딧을 작은 단위로 잡으니 차감·잔액·환불이 모두 정수로 떨어졌습니다.

**비교 가능한 숫자로 정합니다.** 퍼센트보다 "1건에 얼마" 가 단계 사이, 그리고 다른 서비스와 비교하기 쉬웠습니다.

**미리보기라도 바꿀 곳은 한 군데로.** 나중에 실제 연결할 때 빠뜨리는 곳이 생기지 않습니다.

## 소감

처음엔 충전 화면을 예쁘게 만드는 일이라고 생각했는데, 실제로 시간이 걸린 건 숫자와 규칙이었습니다. 특히 보너스 환불 문제는 단가표를 다 정하고 나서야 보였는데, 실제 결제를 붙이기 전에 찾은 게 다행이었습니다. 실제 결제·발송과 환불 처리는 서비스를 열 때 연결할 예정이라, 그때 이 규칙이 서버 쪽에서도 똑같이 지켜지는지 확인하려고 합니다.

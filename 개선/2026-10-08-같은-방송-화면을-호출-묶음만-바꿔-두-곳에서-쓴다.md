# 2026-10-08 같은 방송 화면을, 호출 묶음만 바꿔 두 곳에서 쓴다

> 태그: #개선 #React #의존성주입 #WebSocket #권한 #멀티테넌트

## 무엇을 / 왜

라이브 방송 화면(방송 만들기·스튜디오·상품 패널·채팅·송출기)은 판매자 센터 전용이었습니다. 이번에 상점 운영자(오너)도 관리 화면에서 **상점 이름으로** 방송할 수 있게 해야 했어요. 걸리는 게 두 가지였습니다.

1. **화면 부품이 판매자용 서버 주소를 직접 import 해서 불렀습니다.** 복사해서 오너용을 따로 만들면 같은 화면이 두 벌이 되고, 한쪽만 고쳐지는 일이 생깁니다.
2. **채팅 웹소켓은 접속 주소(상점 도메인)로 어느 상점인지 찾았습니다.** 그런데 관리 화면은 플랫폼 공통 주소에서 돌아서, 주소만으로는 상점을 찾을 수 없었어요.

## 어떻게 풀었나

- **호출 묶음을 밖에서 받기:** 방송에 필요한 서버 호출(조회·시작·종료·상품 편성·채팅 접속권 등)을 하나의 타입으로 묶고, 부품은 props 로 받게 했습니다. **기본값을 판매자 묶음으로 둬서** 판매자 센터 코드는 한 줄도 바꾸지 않았고, 관리 화면에서만 오너용 묶음을 넘깁니다.
- **서버 경로 나누기:** 오너용 API 는 관리 화면 토큰으로만, 오너·관리자 역할만 쓸 수 있게 했습니다. 방송 주인을 사람이 아니라 상점으로 둬서, 같은 상점의 다른 관리자가 이어서 진행할 수 있어요.
- **채팅 접속권에 상점을 서명해 넣기:** 접속권을 발급할 때 상점 ID 를 서명해서 넣고, 웹소켓은 **주소로 상점을 못 찾을 때만** 접속권의 상점을 씁니다. 주소로 찾은 상점과 접속권의 상점이 다르면 거절해요.
- **걸 수 있는 상품 묶기:** 상점 방송에는 상점이 직접 파는 상품만, 판매자 방송에는 그 판매자 상품만 걸 수 있게 서버에서 검사했습니다. 이 작업 중에, 예전에는 API 로 다른 판매자 상품도 걸 수 있어서 **걸지도 않은 판매자 앞으로 영상 판매 수수료가 생길 수 있었다**는 걸 알게 됐어요.

```java
// 웹소켓 연결 때 상점 정하기: 주소가 우선, 못 찾으면 서명된 접속권의 상점
UUID resolveStore(UUID storeFromHost, ChatTicket ticket) {
    UUID signed = ticket.verifiedStoreId();       // 서명 검증을 통과한 값만 쓴다
    if (storeFromHost == null) {
        return signed;                            // 플랫폼 공통 주소(관리 화면)에서 온 연결
    }
    if (signed != null && !signed.equals(storeFromHost)) {
        throw new ForbiddenException("다른 상점의 접속권입니다"); // 상점이 섞이지 않게 거절
    }
    return storeFromHost;
}
```

## 💡 배운 것

**화면을 복사하기 전에, 화면이 무엇에 기대고 있는지 봅니다.** 부품이 서버 주소를 직접 import 하면 재사용이 막힙니다. 호출을 묶어서 주입하면 같은 화면이 여러 권한에서 돌아갑니다.

**기본값은 기존 사용처를 지키는 쪽으로 둡니다.** 기본 묶음을 판매자로 두니 기존 화면을 고칠 필요가 없었고, 바뀌는 범위가 관리 화면으로 좁아졌습니다.

**맥락을 주소에서 얻을 수 없으면, 서명한 값으로 넘기고 충돌은 거절합니다.** 서명은 위조를 막고, 주소와의 비교는 상점이 섞이는 걸 막습니다.

## 소감

방송 버튼 하나를 오너에게 열어 주는 일인 줄 알았는데, 권한을 나누다 보니 수수료가 붙는 연결 관계까지 점검하게 됐습니다. "누가 무엇을 걸 수 있나"가 곧 "누구 앞으로 돈이 쌓이나"였어요.

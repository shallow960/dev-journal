# 2026-10-21 가장 큰 번호만 봤더니, 빠진 마이그레이션 하나를 놓쳤다

> 태그: #개선 #DB마이그레이션 #배포점검 #검사설계 #리허설

## 무엇을 / 왜

지워진 서버를 새로 세우기 전에, 배포 스크립트를 처음부터 읽으며 로컬에서 리허설했습니다.

이 서비스의 DB 마이그레이션은 번호가 붙은 파일 수백 개입니다. 거의 다 SQL 파일인데, 하나만 **코드로 쓴 마이그레이션**이에요. 옛 데이터를 정리하면서 형식 번호를 새 값으로 바꾸는 일이라, SQL 한 줄로는 안 되는 작업이었습니다.

문제는 서버에서 마이그레이션을 실행하는 방식이었어요.

- 서버 배포는 앱을 켜기 **전에** 별도 마이그레이션 도구로 DB 를 먼저 올립니다.
- 그 도구에는 **SQL 파일 폴더만** 넘기고 있었어요. 코드로 쓴 마이그레이션은 거기 없으니 실행되지 않습니다.
- 배포 뒤 검사는 "DB 에 기록된 가장 큰 번호가, SQL 파일 중 가장 큰 번호와 같은가" 만 봤어요. 중간 번호 하나가 빠져도 가장 큰 번호는 그대로라서 **통과**합니다.

앱 안의 마이그레이션 기능은 둘 다 실행하기 때문에, 개발 PC 에서는 아무 문제가 없었어요. 서버에서만 빠지는 구조였습니다. 빠진 채로 서버를 세웠다면, 앱은 새 형식 번호로 쓰려 하고 DB 는 옛 제약을 들고 있어서 화면 만들기·게시가 실패했을 거예요.

## 어떻게 풀었나

1. **서버에서도 코드 마이그레이션까지 실행합니다.** 배포하는 릴리스의 앱 이미지로 마이그레이션만 한 번 돌리고 끝나는 컨테이너를 띄워요. 앱이 쓰는 것과 같은 실행기라서 SQL 과 코드 마이그레이션을 같은 순서로 적용합니다.
2. **검사를 "하나씩 전부" 로 바꿨습니다.** 릴리스에 든 마이그레이션 목록을 만들고, 그 번호 하나하나가 DB 기록에 "성공" 으로 있는지 봅니다. 실패한 기록이 하나라도 있어도 멈춰요.
3. **옛 방식과 새 방식을 빈 DB 두 개로 리허설했습니다.**
   - 새 방식: 354개(SQL 353 + 코드 1) 전부 성공.
   - 옛 방식: 353개만 적용, 코드 마이그레이션 없음. 이 DB 에 **옛 검사는 통과**, 새 검사는 빠진 번호를 대며 실패.
4. 그 뒤 실제 개발 서버 첫 배포에서도 354개가 적용된 것을 확인했습니다.

## 코드로 보기 (개념 재현)

번호와 이름은 모두 더미입니다. 8개 가운데 7번만 코드로 쓴 마이그레이션이라고 해 볼게요.

```js
// 릴리스에 들어 있는 마이그레이션: 대부분 SQL 파일, 하나만 코드로 쓴 것
const resolved = [
  ...Array.from({ length: 6 }, (_, i) => ({ version: i + 1, kind: 'sql' })),
  { version: 7, kind: 'code' },            // 코드로 쓴 마이그레이션
  { version: 8, kind: 'sql' },
];
// 서버의 도구가 SQL 폴더만 읽고 실행했다 → 7번은 실행되지 않음
const applied = resolved
  .filter((m) => m.kind === 'sql')
  .map((m) => ({ version: m.version, success: true }));

// 옛 검사: "SQL 파일 중 가장 큰 번호" 까지 적용됐는가
const maxSql = Math.max(...resolved.filter((m) => m.kind === 'sql').map((m) => m.version));
const maxApplied = Math.max(...applied.map((a) => a.version));
console.log('옛 검사(가장 큰 번호):', maxApplied === maxSql ? '통과' : '실패');

// 새 검사: 릴리스에 있는 모든 마이그레이션이 하나씩 적용·성공했는가
const missing = resolved
  .filter((m) => !applied.some((a) => a.version === m.version && a.success))
  .map((m) => m.version);
console.log('새 검사(전부 하나씩):', missing.length === 0 ? '통과' : `실패 - 빠진 번호 ${missing.join(', ')}`);
```

실제로 돌린 출력입니다.

```
옛 검사(가장 큰 번호): 통과
새 검사(전부 하나씩): 실패 - 빠진 번호 7
```

## 💡 배운 것

**최댓값은 '빠짐' 을 말해 주지 않는다는 걸 배웠습니다.** "끝까지 갔나" 와 "하나도 안 빠졌나" 는 다른 질문이에요. 순서대로 쌓이는 기록이라도, 빠짐을 보려면 하나씩 맞춰 봐야 했습니다.

**같은 마이그레이션이라도 '누가 실행하나' 에 따라 실행되는 범위가 다를 수 있다는 걸 배웠습니다.** 앱 안의 실행기는 코드 마이그레이션까지 찾고, 외부 도구는 넘겨받은 폴더만 봅니다. 개발 PC 에서 잘 된다고 서버에서도 같다고 볼 수 없었어요.

**검사는 막아야 할 때 실제로 막는지까지 확인한다는 걸 다시 배웠습니다.** 2026-10-20 에 시험을 일부러 깨뜨려 정말 실패하는지 확인했는데, 이번에도 옛 방식 DB 를 만들어 새 검사가 실패하는 것까지 봤어요. 통과만 보는 검사는 아무것도 증명하지 않습니다.

## 소감

검사가 있다는 것만 보고 넘어갔으면 서버를 세우는 첫날 화면 게시가 실패했을 거예요. 리허설에서 일부러 "옛 방식으로 만든 DB" 를 만들어 본 게 가장 쓸모 있었습니다.

# 2026-10-07 수수료율을 정산 때 읽으면, 지난 주문까지 바뀐다

> 태그: #개선 #정산 #스냅샷 #돈계산 #반올림 #PostgreSQL

## 무엇을 / 왜

입점 셀러가 있는 쇼핑몰에서는 운영자가 셀러마다 판매 수수료율을 정합니다. 그런데 기획 문서와 코드를 항목별로 대조해 보니, 수수료율은 저장만 되고 정산 계산은 그 값을 읽지 않았습니다. 정산은 예전 시스템에서 가져온 식이었습니다.

```
지급액 = 판매가 - 결제수수료 - (판매가 - 결제수수료) / 11
```

10,000원 상품이면 수수료율이 0%든 30%든 8,864원이 나왔습니다. 1/11 공제는 어느 기획 문서에도 없던 것이었습니다. 이 밖에도 정산 기준일, 배송비, 수량 일부 반품 회수 등 10가지가 문서와 달라서, 항목마다 추천안을 붙여 결정을 받은 뒤 고쳤습니다.

## 어떻게 풀었나

### 식

```
기준액      = 판매가 - 셀러가 부담한 상품 쿠폰     (운영자 쿠폰·적립금은 운영자 부담이라 빼지 않는다)
결제수수료  = 기준액 x 결제수수료율               (셀러 부담, 10원 미만 버림)
판매 수수료 = 기준액 x 셀러 수수료율             (원 단위 반올림)
지급액      = 기준액 - 결제수수료 - 판매 수수료 + 셀러 배송비
```

셀러가 정한 배송비는 수수료 없이 셀러에게 가고, 셀러가 발행한 무료배송 쿠폰은 그 배송비에서 뺍니다. 10,000원에 10%면 8,750원, 배송비 3,000원이 있으면 11,750원입니다.

### 수수료율은 언제 읽나

처음 떠오른 방법은 정산할 때 셀러의 현재 수수료율을 읽는 것이었습니다. 그런데 정산은 구매확정 뒤 며칠이 지나야 만들어집니다. 그 사이 운영자가 요율을 10%에서 20%로 바꾸면, 10%일 때 팔린 주문도 20%로 정산됩니다. 셀러 입장에서는 팔 때와 다른 조건으로 돈을 받는 셈입니다.

그래서 주문이 만들어지는 순간 그 시점의 요율을 주문 품목에 복사해 두고(스냅샷), 정산은 그 값을 쓰게 했습니다. 이 칸이 생기기 전의 주문은 값이 비어 있으므로, 그때만 현재 요율을 쓰도록 `coalesce` 로 대체값을 정했습니다. 영상에서 팔린 품목에 붙는 영상 판매 수수료율도 같은 방식으로 주문에 연결되는 시점에 고정했습니다.

### 쿠폰이 어디에 붙었는지

상품 쿠폰과 배송비 쿠폰이 같은 할인 칸에 적히고 있어서, 정산이 이 할인을 상품 금액에서 뺄지 배송비에서 뺄지 알 수 없었습니다. 쿠폰을 품목에 나눠 적을 때 "상품" 인지 "배송비" 인지를 같이 남기게 했습니다.

### 이미 쌓인 정산은

예전 식으로 쌓인 정산은 다시 계산하지 않고 "옛 식" 으로 표시만 했습니다. 이미 셀러와 맞춘 금액일 수 있어서, 숫자를 조용히 바꾸지 않는 쪽을 택했습니다.

## 코드로 보기 (개념 재현)

표·클래스 이름은 예시입니다.

```sql
-- 주문을 저장한 직후: 그 시점의 셀러 요율을 품목에 복사한다
update order_line l
set seller_fee_rate = coalesce((
        select s.fee_rate
        from seller s
        where s.shop_id = l.shop_id and s.user_id = l.seller_id
        order by (s.status = 'approved') desc, s.updated_at desc
        limit 1
    ), 0)
where l.order_id = :orderId
  and l.seller_id is not null;           -- 운영자 상품(셀러 없음)은 정산 대상이 아니다

-- 정산을 만들 때: 고정한 값을 먼저 쓰고, 없을 때만(옛 주문) 현재 값을 쓴다
select l.id,
       coalesce(l.seller_fee_rate, s.fee_rate, 0) as fee_rate
from order_line l
left join seller s on s.shop_id = l.shop_id and s.user_id = l.seller_id
where l.order_id = :orderId;
```

```java
// 원 단위 돈 계산 - 반올림 규칙을 항목마다 정해 둔다
public Payout calculate(Line line, Policy policy, BigDecimal feeRatePercent) {
    BigDecimal sellerGoodsCoupon = line.couponBySeller() && !line.couponOnShipping()
        ? line.couponAmount() : BigDecimal.ZERO;
    BigDecimal base = line.price().multiply(BigDecimal.valueOf(line.quantity()))
        .subtract(sellerGoodsCoupon)
        .max(BigDecimal.ZERO);

    // 결제수수료: 10원 미만 버림(정책)
    BigDecimal payFee = base.multiply(policy.payFeePercent()).movePointLeft(2)
        .divide(BigDecimal.TEN, 0, RoundingMode.FLOOR)
        .multiply(BigDecimal.TEN);

    // 판매 수수료: 원 단위 반올림
    BigDecimal commission = base.multiply(feeRatePercent).movePointLeft(2)
        .setScale(0, RoundingMode.HALF_UP);

    // 셀러 배송비: 수수료 없음, 셀러 배송비 쿠폰은 여기서 뺀다
    BigDecimal sellerShippingCoupon = line.couponBySeller() && line.couponOnShipping()
        ? line.couponAmount() : BigDecimal.ZERO;
    BigDecimal shipping = line.shippingFee().subtract(sellerShippingCoupon).max(BigDecimal.ZERO);

    BigDecimal amount = base.subtract(payFee).subtract(commission).add(shipping);
    return new Payout(base, payFee, commission, shipping, amount);
}
```

테스트는 "주문 뒤에 요율을 바꿔도 주문 때 요율로 정산되는지" 를 직접 확인합니다.

```java
@Test
void 주문_뒤에_요율을_바꿔도_주문_때_요율로_정산한다() {
    UUID seller = seller("10.00");
    Order order = checkout(goodsOf(seller), 1, 10_000);

    updateSellerFeeRate(seller, "20.00");    // 주문 뒤 운영자가 요율을 올렸다
    confirmPurchase(order, daysAgo(20));

    settlement.accrueDue();
    assertThat(payoutOf(order).commission()).isEqualByComparingTo("1000");   // 20%가 아니라 10%
    assertThat(payoutOf(order).amount()).isEqualByComparingTo("8750");
}
```

## 💡 배운 것

**문서의 "완료" 는 코드로 확인하기 전까지 가설입니다.** 저장 화면이 있다는 것과 그 값이 계산에 쓰인다는 것은 다른 일이었습니다.

**바뀔 수 있는 조건은 거래 시점에 고정합니다.** 요율·가격처럼 나중에 바뀌는 값을 정산 때 읽으면, 이미 끝난 거래의 결과가 바뀝니다. 고정한 값이 없는 옛 데이터를 위한 대체 규칙도 같이 정해야 합니다.

**할인이 어디에 붙었는지도 데이터입니다.** 같은 금액이라도 상품 할인인지 배송비 할인인지에 따라 누가 얼마를 받는지가 달라집니다.

**반올림 규칙은 항목마다 정해 둡니다.** 결제수수료는 10원 미만 버림, 판매 수수료는 원 단위 반올림처럼 규칙을 코드에 드러내면, 명세의 숫자가 왜 그 값인지 설명할 수 있습니다.

**이미 쌓인 숫자는 조용히 다시 계산하지 않습니다.** 식이 바뀌어도 지난 정산은 표시만 바꾸고 그대로 둡니다.

## 소감

처음엔 "수수료율 하나 넣으면 되겠지" 했는데, 언제 읽을지, 쿠폰이 어디에 붙었는지, 옛 데이터는 어떻게 할지를 정하는 데 더 오래 걸렸습니다. 차이를 표로 만들어 결정을 먼저 받은 덕분에, 구현 중에 같은 질문으로 다시 돌아가지 않았습니다. 정산·주문 관련 테스트는 통과했고, 실제 운영 데이터로 맞춰 보는 일은 배포 뒤에 남아 있습니다.

# 2026-09-30 백업을 올리는 서버가, 백업을 지울 수는 없게

> 태그: #개선 #백업 #AWS #S3 #IAM #최소권한

## 무엇을 / 왜

DB는 관리형 서비스(RDS)가 매일 자동으로 백업합니다. 그런데 상품 사진이나 반품·교환 신청에 첨부한 사진 같은 **업로드 파일**은 서버 디스크의 도커 볼륨에만 있었습니다. 디스크가 망가지거나 서버를 새로 만들면 같이 사라지는 상태였어요.

## 어떻게 풀었나

### 세 가지 방법을 비교했다

| 방법 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| 매일 S3로 복사 | 파일 하나씩 되살릴 수 있음, 비용 적음 | 하루치는 잃을 수 있음, 서버에 설정 필요 |
| 디스크 스냅샷 | 코드 작업 없음 | 파일 하나를 되살려도 디스크를 통째로 복원해야 함 |
| 저장소를 아예 S3로 | 장기적으로 가장 좋음 | 코드 변경과 기존 파일 이전, 오픈 직전에는 위험 |

오픈을 앞두고 있어서 코드를 크게 바꾸지 않으면서 파일 단위로 복원할 수 있는 **"매일 S3로 복사"** 를 골랐습니다.

### 지워진 파일은 버전 관리가 지킨다

`aws s3 sync --delete` 로 버킷을 서버와 **똑같이** 맞춥니다. 그러면 서버에서 지운 파일은 버킷에서도 지워지는데, 실수로 지운 거라면 곤란하죠. 그래서 버킷의 **버전 관리**를 켰습니다.

- 버전 관리가 켜진 버킷에서 지우면, 파일이 사라지는 게 아니라 "삭제 표시" 만 붙고 예전 판이 남습니다.
- 수명 주기 규칙으로 **예전 판은 30일 뒤** 지워지게 해서, 보관 비용이 끝없이 늘지 않게 했습니다.

### 서버 권한에서 일부러 뺀 한 가지

서버는 키 파일 대신 EC2에 붙인 **역할(IAM Role)** 로 권한을 받습니다. 여기서 고민한 건 "서버가 털렸을 때" 입니다. 서버가 버킷의 모든 걸 지울 수 있다면, 백업도 서버와 같이 사라집니다.

그래서 서버 역할에는 지금 판을 올리고 지우는 권한까지만 주고, **예전 판을 지우는 권한(`s3:DeleteObjectVersion`)은 주지 않았습니다.** 누가 서버에서 `sync --delete` 로 전부 지워도, 예전 판은 30일 동안 남아 있습니다. 수명 주기 설정을 바꾸는 권한도 없어서 이 30일을 줄일 수도 없어요.

### 백업하면 안 되는 것도 있다

애플리케이션 컨테이너가 쓰는 볼륨이 셋 있었는데, 업로드 파일만 대상으로 했습니다.

- **보관 기한이 지나면 파기해야 하는 자료**: 같은 규칙으로 복사하면 원본을 파기해도 백업에 30일 더 남습니다. 규칙을 따로 정해야 해서 뺐습니다.
- **로그인 토큰 서명 비밀키**: 잃어도 모두 다시 로그인하면 끝이지만, 새면 위험합니다. 비밀키를 다른 곳으로 복사하지 않았습니다.

### 서버에 아무것도 설치하지 않는다

aws-cli는 서버에 설치하지 않고 공식 컨테이너 이미지로 돌렸습니다. 컨테이너 안에서 인스턴스 역할의 임시 자격증명을 받으려면 인스턴스 메타데이터(IMDSv2)에 닿아야 하는데, 기본 설정(응답 홉 1)에서는 브리지 네트워크의 컨테이너가 토큰을 못 받는 경우가 있어 **호스트 네트워크**로 돌렸습니다. 전날 백업이 길어져 다음 실행과 겹치지 않게 `flock` 으로 막았고요.

## 코드로 보기 (개념 재현)

서버 역할의 권한입니다. 버킷 이름은 예시입니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:ListBucketVersions"],
      "Resource": "arn:aws:s3:::example-uploads-backup"
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:GetObjectVersion", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::example-uploads-backup/uploads/*"
    }
  ]
}
```

`s3:DeleteObjectVersion` 과 `s3:PutLifecycleConfiguration` 이 **없다는 것** 이 핵심입니다.

백업 스크립트(요약)입니다.

```bash
#!/usr/bin/env bash
set -euo pipefail

bucket=$(grep -E '^BACKUP_BUCKET=' .env | tail -n 1 | cut -d= -f2-)  # .env 전체를 source 하지 않는다
volume=app_uploads

# 앞 백업이 아직 돌고 있으면 겹쳐 돌지 않는다
exec 9>/tmp/backup-uploads.lock
flock -n 9 || { echo "SKIP 이전 백업 진행 중"; exit 0; }

# aws-cli 는 컨테이너로. 볼륨은 읽기 전용으로 붙이고, 역할 자격증명은 호스트 네트워크로 받는다
docker run --rm --network host \
  -e AWS_DEFAULT_REGION=ap-northeast-2 \
  -v "$volume":/data:ro \
  amazon/aws-cli:2.15.0 \
  s3 sync /data "s3://$bucket/uploads" --delete --only-show-errors

echo "$(date -u +%FT%TZ) OK"
```

매일 한국 시간 새벽 3시 30분(서버는 UTC라 18:30)에 돌립니다.

```
30 18 * * * $HOME/deploy/backup-uploads.sh >> $HOME/deploy/logs/backup-uploads.log 2>&1
```

## 💡 배운 것

**백업 권한은 "쓰기" 와 "이력 지우기" 를 나눕니다.** 백업을 올리는 쪽이 백업 이력까지 지울 수 있으면, 그 서버가 털리는 순간 백업도 의미가 없어집니다.

**`sync --delete` 와 버전 관리는 같이 씁니다.** 똑같이 맞추는 편리함과 실수로 지운 파일을 되살리는 안전함을 둘 다 얻을 수 있었습니다.

**전부 백업하는 게 답은 아닙니다.** 파기 의무가 있는 자료나 비밀키는 백업이 오히려 문제가 됩니다. 무엇을 뺄지도 설계의 일부였습니다.

## 소감

처음엔 "파일을 S3에 복사하는 cron 하나" 라고 생각했는데, 권한을 적다 보니 "이 서버가 털리면 무엇까지 잃나" 를 계속 묻게 됐습니다. 아직 스크립트는 문법 검사까지만 했고 실제 동작은 서버에 버킷과 역할을 설정한 뒤 확인할 예정이라, 그때 복원까지 한 번 해 보고 결과를 덧붙이려고 합니다.

# 2026-08-20 조용히 틀린 화면이 제일 늦게 발견된다

> 태그: #개선 #점검 #신뢰성

## 무엇을 / 왜

관리 화면이 잘 돌아간다고 믿고 있었습니다. 그런데 며칠 전 오너 계정으로 화면 **두 개**를
열어 봤다가 진짜 버그를 세 개나 찾았어요. 만들어 놓고 실제로 열어 본 적이 없는 화면이 많다는
뜻이었습니다.

그래서 아예 다 열어 보기로 했습니다.

## 어떻게 풀었나

### 73개를 열었다

로그인해서 화면을 자동으로 하나씩 열고, 그때 오간 요청과 화면에 찍힌 글자를 모아 보는 방식으로
훑었습니다.

| 대상 | 개수 |
|---|---|
| 스토어 오너 관리 화면 | 26 |
| 스토어 콘솔 | 12 |
| 입점 브랜드(셀러) 화면 | 14 |
| 손님몰 | 21 |

찾을 것은 네 가지로 잡았습니다. 실패한 요청, 화면이 죽었는지, 번역이 안 붙어 키가 그대로
찍히는지, "불러오지 못했습니다" 같은 문구가 떠 있는지.

### 오류를 내는 것보다, 오류 없이 틀린 것이 많았다

결과가 뜻밖이었습니다. 찾은 문제의 절반 이상이 **오류를 내지 않았습니다.**

**하나. 실패를 삼키고 지어낸 값을 보여준다.**

마이페이지가 누가 로그인하든 "홍길동 / customer@example.com" 을 보여주고 있었습니다. 게다가
조회에 **성공해도** 이름은 바뀌지 않았어요. 지어낸 이름이 초기값으로 박혀 있고, 성공하면
포인트와 쿠폰 수만 덮어쓰고 이름은 그대로 뒀거든요.

더 나쁜 것도 있었습니다. 주문이 거절되면 **가짜 주문을 만들어 돌려주고** 있었습니다.

```
주문 요청이 400이나 401을 주면
  → 지어낸 주문 객체를 만들어 반환
  → 화면은 "주문이 완료되었습니다 / 주문번호 260820-XXXXX"
```

손님은 주문번호까지 받고 완료 화면을 봅니다. 실제로는 주문이 없고, 재고도 안 빠지고, 결제도
안 됐습니다. **오류가 났으면 손님이 다시 시도했을 텐데, 성공한 것처럼 보이면 그럴 기회조차
없습니다.**

**둘. 아무 동작 없는 버튼.**

셀러 화면 위쪽 알림 종은 눌러도 아무 일이 없었습니다. 주문이 들어왔는지, 문의가 왔는지는
각 화면에 직접 들어가 봐야만 알 수 있었어요.

**셋. 화면엔 있는데 저장되지 않는 입력.**

상품 등록 폼의 배송비 칸이 저장 요청에 실리지 않아 늘 버려지고 있었습니다. 기본값까지 채워져
있어서 오히려 "설정했다" 고 믿게 만들었습니다.

**넷. 닿지 못하는 화면.**

성과 화면 하나는 화면이 부르는 주소와 서버에 달린 주소가 달라서 **아예 열리지 않았습니다.**
컴파일도 되고 테스트도 다 통과했지만, 열면 "요청한 경로를 찾을 수 없습니다" 만 떴어요.
계산이 맞아도 닿지 못하면 없는 기능입니다.

### 고친 방식

- 실패는 실패로 보이게 했습니다. 가짜를 돌려주는 건 화면을 만들 때 쓰는 모드에서만 하도록 좁혔습니다.
- 지어낸 기본값(사람 이름, 주소)을 걷어내고, 비면 비운 채로 두거나 실제 값을 채워 오게 했습니다.
- 동작 없는 버튼은 실제 기능으로 채웠습니다.
- 같은 종류의 사고를 막으려고 **"화면이 부르는 주소가 서버에 실제로 있는지"** 검사하는 테스트를
  넣었습니다. 고치기 전 상태로 되돌려서 그 테스트가 실제로 실패하는 것도 확인했습니다.

## 💡 배운 것

- **조용히 틀린 화면이 제일 늦게 발견된다.** 오류가 나면 누군가 신고합니다. 그럴듯한 가짜 값은
  아무도 신고하지 않습니다.
- **실패를 감추는 코드는 대개 좋은 의도로 들어온다.** "화면이 죽지 않게" 하려고 넣은 폴백이,
  나중에는 "실패했는데 성공처럼 보이는" 장치가 됩니다. 감출 거면 무엇을 감추는지 좁게 정해야 합니다.
- **지어낸 기본값은 언젠가 진짜처럼 저장된다.** 배송지 예시값이 실제 주문에 그대로 들어간 걸
  확인하고 나서 확신했습니다. 예시는 자리 표시(placeholder)로 두고 값으로 넣지 않는 게 맞습니다.
- **눌러 보지 않으면 알 수 없다.** 테스트가 통과해도, 화면이 부르는 주소가 틀렸는지는 열어 봐야
  압니다.

## 소감

절반은 제가 잘못 짚기도 했습니다. "새로고침하면 데이터가 안 뜬다" 고 봤던 건 정상 동작이었고
(페이지를 새로 열면 메모리의 토큰이 사라지니 첫 거절은 당연했습니다), 리다이렉트 두 개는
의도된 것이었어요. 4xx를 전부 문제로 세면 정상 동작까지 버그로 보고하게 된다는 걸 배웠습니다.

그래도 이렇게 한 바퀴 도는 게 값이 있었습니다. 기능을 새로 만드는 것보다, 이미 만든 것 중
**말과 실제가 다른 것**을 찾아내는 쪽이 사용자에게는 더 크게 다가올 것 같습니다.

# 2026-11-01 종이에 찍힐 QR 주소는, 그 주소가 열리는 걸 확인한 뒤에 바꿨다

> 태그: #개선 #QR #화이트라벨 #리버스프록시 #배포순서

## 무엇을 / 왜
사진 키오스크는 인화한 사진에 QR 을 함께 찍었고, 손님은 그 QR 로 휴대폰에서 사진을 받았습니다. QR 주소는 서버가 정해 키오스크에 내려 줬습니다.

- 외주형 고객 브랜드(자기 브랜드로만 보여야 하는 고객사)의 손님 QR 에 플랫폼 주소가 그대로 찍히고 있었습니다. 2026-10-30 밤, 이 주소를 그 브랜드가 소유를 확인한 주소로 바꾸는 작업을 했습니다.
- 2026-11-01 에 배포를 마치고, 그 브랜드의 손님 QR 이 실제로 브랜드 주소로 나가도록 스위치를 켰습니다.
- QR 은 종이에 찍혀 손님에게 가는 주소라, 한번 나가면 고칠 수 없었습니다. 그래서 어떤 주소를 내는지만큼 언제 바꾸는지도 중요했습니다.

## 어떻게 풀었나
- 처음에는 브랜드가 외주형이고, 도메인 소유를 DNS TXT 로 확인했고, 공개 스위치를 켰으면 그 브랜드 주소로 내게 했습니다. 브랜드 주소 앞단의 프록시에는 `/qr/*` 를 손님 사진 페이지로 보내는 경로를 더했습니다.
- 검토에서 이런 지적이 나왔습니다. "소유 확인" 과 "공개" 는 관리 화면의 데이터일 뿐, 그 주소로 들어온 요청을 손님 사진 페이지로 보내는 길(프록시 경로, 인증서)이 있다는 증거는 아니라는 것이었습니다.
  - 그때 길이 깔린 브랜드 주소는 하나뿐이었습니다.
  - 다른 외주형 브랜드가 관리자 화면을 열려고 공개를 켜는 순간, 그 브랜드의 새 QR 이 모두 그 주소로 나갈 수 있었습니다. 그 주소에 `/qr/*` 경로가 없으면 요청은 관리자 화면으로 가서, 손님은 사진 대신 관리자 화면을 받았을 것입니다.
  - 공개 스위치 하나가 브랜드 관리자 화면과 손님 QR 주소를 함께 바꾸고 있었습니다.
- 그래서 세 가지를 고쳤습니다.
  - 서버 설정에 "QR 주소로 써도 되는 호스트 목록" 을 두고, DB 조건을 모두 갖췄더라도 이 목록에 있을 때만 브랜드 주소를 내게 했습니다. 목록 밖이면 플랫폼 주소를 내고 경고를 남기게 했습니다. 목록은 프록시 설정과 같은 배포에 묶었습니다.
  - 목록의 호스트마다 프록시 설정에 손님 페이지 경로가 있는지 대조하는 시험을 넣었습니다. 이 시험이 프록시 설정만 바뀌어도 다시 돌게 한 이야기는 따로 적었습니다([2026-10-31, 설정 파일만 고쳤더니, 그 파일을 검사하는 시험은 UP-TO-DATE 로 건너뛰었다](../트러블슈팅/2026-10-31-설정-파일만-고쳤더니-그-파일을-검사하는-시험은-UP-TO-DATE-로-건너뛰었다.md)).
  - 목록은 주소를 내는 쪽만 막고, 주소를 받는 쪽은 막지 않게 했습니다. 이미 찍힌 브랜드 주소 QR 은 계속 열려야 했기 때문입니다.
- 되돌리는 규칙도 적어 두었습니다. 새 QR 만 플랫폼 주소로 돌리고 싶으면 목록을 비우고, 공개 스위치는 끄지 않기로 했습니다. 공개를 끄면 브랜드 주소가 통째로 닫혀서, 그동안 찍힌 QR 까지 열리지 않게 되기 때문이었습니다.
- 켜는 순서도 정했습니다. 공개가 켜진 채로 배포되면 그 순간부터 새 QR 이 브랜드 주소로 나가므로, 배포하고, 배포된 서버에서 그 주소가 손님 사진 페이지로 열리는지 확인하고, 그다음에 공개를 켜기로 했습니다. 배포된 프록시가 새 설정을 실제로 읽었는지는 열어 봐야 알 수 있었습니다.
- 2026-11-01 새벽 배포가 끝난 뒤, 브랜드 주소의 `/qr/아무코드` 가 관리자 화면이 아니라 손님 사진 페이지로 열리는지부터 봤습니다. 손님 사진 페이지에만 있는 표시가 응답에 있었고, 그 주소의 HTTPS 인증서도 받아져 있었습니다. 이 표시는 2026-10-30 에 배포 확인용으로 넣어 둔 것이었습니다([2026-10-30, 손님 페이지에서 플랫폼 이름을 지웠더니, 배포 확인이 배포를 되돌렸다](../트러블슈팅/2026-10-30-손님-페이지에서-플랫폼-이름을-지웠더니-배포-확인이-배포를-되돌렸다.md)).
- 그걸 보고 낮에 공개를 켰습니다. 켠 뒤에는 브랜드 주소에서 손님 QR 조회가 열린 것(없는 코드에는 "없음" 응답)과 브랜드 이름이 제대로 나오는 것을 확인했습니다. 실제 키오스크로 찍어 보는 시험은 다음 날로 미뤘습니다.

## 코드로 보기 (개념 재현)
서버가 QR 주소를 고르는 규칙을 고치기 전과 뒤로 나눠 돌려 보고, 허용 목록과 프록시 설정의 대조, 이미 찍힌 QR 이 되돌리기에 따라 어떻게 되는지까지 흉내 냈습니다. 프록시와 DB 는 흉내이고, 이름은 모두 예시입니다.

```javascript
// 손님 QR 주소를 고르는 규칙을 고치기 전과 뒤로 돌려 보고, 이미 찍힌 QR 이 어떻게 되는지 본다. 이름은 모두 예시다.
const PLATFORM = 'home.example';

// 프록시 설정(개념): 호스트마다 /qr/* 를 어디로 보내는지. 경로가 없으면 그 호스트의 나머지 요청처럼 관리자 화면으로 간다.
const proxy = {
  'home.example': { qr: '손님 사진 페이지' },
  'brand-a.example': { qr: '손님 사진 페이지' }, // 손님 경로까지 넣어 둔 브랜드
  'brand-b.example': { qr: null },               // 관리자 화면만 열어 둔 브랜드
};

// 브랜드 설정(DB 개념): 도메인 소유 확인, 공개 스위치
const brands = {
  A: { domain: 'brand-a.example', verified: true, open: true },
  B: { domain: 'brand-b.example', verified: true, open: true }, // 관리자 화면을 열려고 공개를 켰다
};

// 서버가 QR 주소를 고르는 규칙
const pickBefore = (b) => (b.verified && b.open ? b.domain : PLATFORM);                         // DB 표시만 본다
const pickAfter = (b, allow) => (b.verified && b.open && allow.has(b.domain) ? b.domain : PLATFORM); // 허용 목록도 본다

// 손님이 그 주소를 열었을 때. 브랜드 주소는 공개가 켜져 있을 때만 받아 준다(허용 목록과는 상관없다).
function open(url) {
  const host = new URL(url).host;
  const brand = Object.values(brands).find((b) => b.domain === host);
  if (brand && !(brand.verified && brand.open)) return '열리지 않음(404)';
  return proxy[host].qr ?? '관리자 화면(사진 없음)';
}

// 허용 목록과 프록시 설정을 대조하는 시험
const contract = (allow) =>
  [...allow].map((h) => `${h} ${proxy[h] && proxy[h].qr === '손님 사진 페이지' ? '맞음' : '/qr/* 경로 없음'}`).join(', ');

const allow = new Set(['brand-a.example']);
const qr = (host) => `https://${host}/qr/AB12CD34`;

console.log('[주소 고르기]');
for (const [name, b] of Object.entries(brands)) {
  const before = qr(pickBefore(b));
  const after = qr(pickAfter(b, allow));
  console.log(`브랜드 ${name} 고치기 전: ${before} -> ${open(before)}`);
  console.log(`브랜드 ${name} 고친 뒤:  ${after} -> ${open(after)}`);
}

console.log('[대조 시험]');
console.log('허용 목록 그대로:', contract(allow));
console.log('B 를 목록에만 더하면:', contract(new Set([...allow, 'brand-b.example'])));

console.log('[이미 찍힌 A 의 QR]');
const printed = qr(pickAfter(brands.A, allow));
console.log(`찍힌 주소: ${printed} -> ${open(printed)}`);
console.log(`허용 목록을 비우면: 새 QR ${qr(pickAfter(brands.A, new Set()))}, 찍힌 QR -> ${open(printed)}`);
brands.A.open = false;
console.log(`공개를 끄면: 새 QR ${qr(pickAfter(brands.A, allow))}, 찍힌 QR -> ${open(printed)}`);
```

Node v22.11.0 에서 돌린 결과입니다.

```

브랜드 A 고치기 전: https://brand-a.example/qr/AB12CD34 -> 손님 사진 페이지
브랜드 A 고친 뒤:  https://brand-a.example/qr/AB12CD34 -> 손님 사진 페이지
브랜드 B 고치기 전: https://brand-b.example/qr/AB12CD34 -> 관리자 화면(사진 없음)
브랜드 B 고친 뒤:  https://home.example/qr/AB12CD34 -> 손님 사진 페이지
[대조 시험]
허용 목록 그대로: brand-a.example 맞음
B 를 목록에만 더하면: brand-a.example 맞음, brand-b.example /qr/* 경로 없음
[이미 찍힌 A 의 QR]
찍힌 주소: https://brand-a.example/qr/AB12CD34 -> 손님 사진 페이지
허용 목록을 비우면: 새 QR https://home.example/qr/AB12CD34, 찍힌 QR -> 손님 사진 페이지
공개를 끄면: 새 QR https://home.example/qr/AB12CD34, 찍힌 QR -> 열리지 않음(404)
```

- 고치기 전에는 프록시에 손님 경로가 없는 브랜드 B 의 QR 도 브랜드 주소로 나갔고, 그 주소는 관리자 화면으로 갔습니다.
- 고친 뒤에는 목록에 없는 B 의 QR 이 플랫폼 주소로 나가 손님 사진 페이지가 열렸습니다. 목록에 있는 A 는 그대로 브랜드 주소였습니다.
- 누가 B 를 목록에만 더하면, 대조 시험이 "/qr/* 경로 없음" 으로 잡았습니다.
- 이미 찍힌 A 의 QR 은 목록을 비워도 열렸고, 공개를 끄자 열리지 않았습니다. 새 QR 만 되돌리려면 공개가 아니라 목록을 비워야 했던 이유입니다.

## 💡 배운 것
- 도메인 소유를 확인했다는 것과 그 주소로 손님 페이지가 열린다는 것은 다른 사실이라는 걸 배웠습니다. 앞의 것은 DB 에 있었고, 뒤의 것은 프록시 설정과 배포된 서버에 있었습니다. 종이에 찍힐 주소는 뒤의 것까지 맞을 때만 내야 했습니다.
- 되돌릴 수 없는 것을 내보내는 스위치는, 내보내는 쪽과 받는 쪽을 따로 끌 수 있게 나눠야 한다는 걸 배웠습니다. 공개 스위치 하나로 둘 다 바꾸면, 새 QR 을 멈추려다 이미 찍힌 QR 까지 닫을 뻔했습니다.
- 서로 맞아야 하는 두 곳은 사람이 기억하기보다 시험이 대조하게 해야 한다는 걸 다시 배웠습니다([2026-10-30, 손님 페이지에서 플랫폼 이름을 지웠더니, 배포 확인이 배포를 되돌렸다](../트러블슈팅/2026-10-30-손님-페이지에서-플랫폼-이름을-지웠더니-배포-확인이-배포를-되돌렸다.md)). 그때는 배포 확인 글자와 페이지였고, 이번에는 QR 호스트 목록과 프록시 경로였습니다.

## 소감
QR 주소 한 줄을 바꾸는 작업이었는데, 가장 오래 고민한 건 코드보다 순서였습니다. 키오스크에서 나간 종이는 다시 불러올 수 없어서, 스위치를 켜기 전에 그 주소를 직접 열어 본 몇 분이 이번 작업에서 가장 값졌습니다.

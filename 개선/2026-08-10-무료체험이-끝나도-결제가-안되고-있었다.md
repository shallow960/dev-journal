# 2026-08-10 무료체험이 끝나도 돈이 안 걷히고 있었다 - 카드를 나중에 받으면 늦는다

> 태그: #개선 #구독결제 #스케줄러 #설계

## 오늘 한 일 (요약)
- 14일 무료체험을 **카드 없이** 시작할 수 있게 해두고, "체험 끝나기 전에 등록하세요"라고 안내하고 있었다.
- 체험 종료 시 동작을 확인해보니 청구가 아니라 **연체(PAST_DUE) 처리**로 끝나고 있었다. 실제 DB에도 그런 구독이 쌓여 있었다.
- 카드를 나중에 등록해도 **구독에 연결되지 않아** 여전히 "결제수단 없음"이었다.
- 체험 시작 시 카드를 먼저 받도록 바꾸고, 카드 등록 시 결제수단이 빈 구독에 자동 연결되게 했다.

## 무엇이 문제였나
정기결제 스케줄러는 이렇게 생겼다.

```java
for (Subscription subscription : findDueForBilling(now, LIMIT)) {
    if (subscription.paymentMethodId() == null) {
        subscription.markPastDue(now.plusDays(3));   // 청구 시도조차 안 함
        save(subscription);
        continue;
    }
    Invoice invoice = createForSubscription(subscription, price(...));
    chargeInvoice(invoice.id());
}
```

의도는 합리적이다. 카드가 없으면 청구할 수단이 없으니 연체로 넘긴다. 문제는 **체험 구독이 전부 이 분기에 걸린다**는 것이었다.

DB를 열어보니 그대로였다.

```
 status   | no_card | trial_ends
----------+---------+-----------
 trialing | t       | 08-24
 trialing | t       | 08-24
```

체험은 잘 시작됐는데, 전환은 구조적으로 일어날 수 없는 상태였다.

## 두 번째 함정 — 카드를 등록해도 연결되지 않았다
"그럼 체험 중에 카드를 등록하면 되지 않나?" 싶었는데, 그것도 아니었다.

카드 등록은 **결제수단(PaymentMethod)** 을 만들어 사용자에게 붙일 뿐이고, **구독의 `paymentMethodId` 는 여전히 null** 이었다. 구독 생성 시점(카드 없음)에 null 로 박힌 값이 그대로 남아 있었던 것.

즉 사용자가 안내대로 카드를 등록해도 스케줄러는 여전히 "카드 없음"으로 판단했다.

## 어떻게 고쳤나

### ① 카드 등록 시 구독에 연결
```java
/**
 * 카드(빌키) 등록 직후, 결제수단이 비어 있는 현재 구독에 그 카드를 연결한다.
 * 이게 없으면 체험 종료일에 스케줄러가 '결제수단 없음'으로 보고 청구 없이 연체 처리한다.
 * 이미 연결된 구독은 건드리지 않는다(카드 변경은 별도 경로).
 */
@Transactional
public void attachPaymentMethodIfMissing(UUID userId, UUID paymentMethodId) {
    subscriptionRepository.findCurrentByUserId(userId)
        .filter(s -> s.paymentMethodId() == null)
        .ifPresent(s -> {
            s.changePaymentMethod(paymentMethodId);
            subscriptionRepository.save(s);
        });
}
```
카드 등록이 끝나는 모든 경로(결제창 콜백 / 카드정보 직접입력)에서 이걸 호출한다.

### ② 체험 시작 시 카드를 먼저 받기
안내 문구로 해결할 문제가 아니라 **흐름을 바꿔야** 했다. 넷플릭스·유튜브가 하는 방식(card-on-file trial)이 표준이다.

```
[이전] 체험 시작(카드 없음) → 14일 → "카드 등록하세요" 안내 → (대부분 안 함) → 연체
[이후] 체험 시작 = 카드 등록 → 14일 무료 → 종료일 자동 결제 → 유료 전환
```

주문 화면에서도 체험임을 명확히 보여준다 — 무료체험 14일 / **첫 결제일** / 첫 결제 금액 / "지금은 결제되지 않습니다".

## 부수적으로 드러난 것
체험은 계정당 1회라, 체험을 소진한 계정의 **두 번째 스토어에는 구독 자체가 생성되지 않았다.** 그 스토어에서 "지금 결제"를 누르면 `subscription not found`(404). 구독이 없으면 그 스토어의 플랜으로 **체험 없이 유료 구독을 시작하며 첫 결제를 승인**하도록 고쳤다.

## 💡 배운 것
- **"나중에 하세요" 안내로 메우는 설계는 대부분 실패한다.** 필요한 정보는 그게 필요한 시점이 아니라 **흐름상 자연스러운 시점**에 받아야 한다.
- 자동 청구는 "스케줄러가 돈다"로 끝나지 않는다. **청구에 필요한 값이 그때 채워져 있는지**까지가 기능이다.
- 리소스를 만들 때 null 로 둔 필드는 **나중에 누가 채우는지**를 반드시 정해야 한다. 안 정하면 영원히 null 이다.
- 배치·스케줄러의 조용한 분기(`continue`)는 **아무 에러 없이 기능을 죽인다.** 로그도 예외도 없어서, 실제 데이터를 확인하기 전엔 모른다.

## 소감
에러가 하나도 안 났기 때문에 더 오래 몰랐던 버그다. 체험 가입은 성공하고, 화면도 정상이고, 스케줄러도 "정상 동작"했으니까. 실제로 종료일에 무슨 일이 일어나는지 데이터로 확인해보지 않았으면 유료 전환이 통째로 안 되는 채로 운영할 뻔했다.

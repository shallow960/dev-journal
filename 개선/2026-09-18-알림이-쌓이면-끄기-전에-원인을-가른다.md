# 2026-09-18 알림이 쌓이면, 끄기 전에 원인을 가른다

> 태그: #개선 #운영 #관측성 #알림

## 무엇을 / 왜

서버 오류를 메일로 받게 붙여 뒀습니다. 그동안은 메일 발송 계정이 없어 조용했는데, 발송을 붙이자마자 **메일함이 알림으로 찼습니다.**

여기서 제일 나쁜 선택은 **알림을 꺼 버리는 것**입니다. 그러면 조용해지지만 진짜 장애도 같이 안 보입니다. 그렇다고 그대로 두면 **진짜 장애가 소음에 묻힙니다.**

제목을 모아 보니 여섯 종류였습니다.

```
· 내보내기 실패 (로그)
· Exporter failed
· 상태 점검(캐시) 이 18초 걸림
· 반송 알림 서명 확인 실패
· 정기결제 결과 미확인
· 계정 메일 발송 실패
```

한 덩어리로 보이지만 원인은 전부 달랐습니다.

## 어떻게 풀었나

### 하나씩 갈랐다

| 알림 | 실제 원인 | 처리 |
|---|---|---|
| 내보내기 실패 · Exporter failed | 추적 데이터를 **없는 수집기**로 보내고 있었다 | 내보내기를 기본 꺼짐으로 |
| 상태 점검 18초 | 서버 메모리 부족(스왑) + 응답 상한 없음 | 서버 증설 + 상한 2초 |
| 반송 서명 실패 | 수신 구독 설정이 잘못됨 | 로그에 고칠 방법을 적음 |
| 정기결제 결과 미확인 | **진짜 장애** | 따로 파고듦 |
| 계정 메일 발송 실패 | 발송 서비스가 아직 승인 전(테스트 단계) | 외부 승인 대기 |

여섯 중 **둘은 설정 문제, 하나는 안내 부족, 하나는 진짜 장애, 둘은 외부 대기** 였습니다.

### 소음 1: 없는 수집기로 내보내기

추적 도구를 붙일 때 기본 설정이 "로컬의 수집기로 보내기" 였습니다. 개발 기계에는 수집기를 띄울 수 있지만 **서버에는 없습니다.** 그러니 몇 초마다 실패하고, 실패는 경고가 되고, 경고는 메일이 됐습니다.

```yaml
# 문제
추적:
  내보내기: otlp                      # 항상 켜짐
  주소: ${수집기주소:http://localhost:4318}   # 서버엔 없는 주소
```

여기서 **추적 자체를 끄면 안 됩니다.** 요청마다 붙는 추적 번호로 로그를 이어 보고 있어서요. 꺼야 하는 건 **내보내기** 뿐입니다.

```yaml
# 고침
추적:
  # 수집기가 없는 곳에서는 내보내기를 끈다. 켜 두면 몇 초마다 "내보내기 실패" 가 쌓이고
  # 그게 그대로 알림 메일로 나가 진짜 장애가 묻힌다.
  # 추적 번호는 그대로 만들어져 로그에 남는다 - 끄는 것은 "내보내기" 뿐이다.
  내보내기: ${추적_내보내기:none}
  로그_내보내기: ${로그_내보내기:none}
  지표_내보내기: ${지표_내보내기:none}
```

### 소음 2: 상한 없는 기다림

상태 점검이 18초 걸린 건 서버 메모리 문제였는데(그건 따로 정리했습니다), 확인해 보니 **응답 상한이 시험용 설정에만** 걸려 있었습니다. 운영은 기본값(60초)이었고요. 원인을 없앤 뒤에도 상한은 남겼습니다.

### 안내 부족: 무엇을 고쳐야 하는지 안 적혀 있었다

반송 알림 수신 주소에서 서명 검증이 실패하고 있었습니다. 로그에는 이렇게만 남았습니다.

```
서명 확인 실패라 버립니다. messageId=null
```

이걸 보고 운영자가 할 수 있는 게 없습니다. 원인이 둘인데 구분이 안 되니까요.

```java
// 서명이 아예 없으면 십중팔구 구독의 "원시 메시지 전송" 이 켜진 것이다 -
// 그 설정을 켜면 서명 봉투 없이 알맹이만 와서 진짜인지 확인할 방법이 사라진다.
// 운영자가 무엇을 고쳐야 하는지 알 수 있게 두 경우를 갈라 적는다.
boolean 봉투없음 = 값(메시지, "Signature") == null && 값(메시지, "Type") == null;
log.warn("알림: 서명 확인 실패라 버립니다. {} messageId={}",
    봉투없음
        ? "서명 봉투가 없습니다 - 구독에서 '원시 메시지 전송' 을 꺼 주세요."
        : "서명이 맞지 않습니다 - 주제가 우리 것인지, 인증서를 받아올 수 있는지 확인하세요.",
    값(메시지, "MessageId"));
```

### 마지막에, 꼭 필요한 만큼만 껐다

소음을 없애고 나니 남은 건 **진짜 장애 하나**였습니다. 그건 외부 업체 회신을 기다려야 해서 당장 고칠 수 없었고, 매일 새벽 같은 알림이 나가는 상태였습니다.

그래서 그 규칙만 잠시 껐습니다. 대신 **되살릴 방법을 같이 남겼습니다.**

```sql
-- 끈 규칙을 그대로 출력받아 기록으로 남긴다
update 알림규칙 set 사용중 = false where 사용중 = true returning id, 이름;

-- 재개할 때
update 알림규칙 set 사용중 = true where id = '<기록해 둔 id>';
```

## 💡 배운 것

**알림이 쌓이면 끄기 전에 원인을 가릅니다.** 여섯 개가 한 덩어리로 보였지만 실제로는 설정·안내·장애·외부대기가 섞여 있었습니다. 가르지 않고 껐다면 진짜 장애 하나를 며칠 더 몰랐을 겁니다.

**소음은 알림 규칙이 아니라 소음원을 고칩니다.** 필터를 걸어 가리면 그 자리에서 다른 소음이 또 생깁니다.

**관측 도구가 관측 대상을 시끄럽게 만들 수 있습니다.** 추적을 붙인 목적은 문제를 보기 위해서인데, 그 도구의 실패가 알림을 채워 오히려 문제를 가리고 있었습니다.

**"기능을 끈다" 와 "내보내기를 끈다" 는 다릅니다.** 추적 번호는 살리고 전송만 껐습니다. 어느 부분이 진짜 필요한지 갈라 보면 대개 전부 끌 필요가 없습니다.

**로그에는 "무엇이 잘못됐다" 가 아니라 "무엇을 고쳐야 한다" 를 적습니다.** 몇 달 뒤 그 로그를 만난 사람이 할 수 있는 일이 있어야 합니다.

**임시로 끈 것은 되살릴 방법과 함께 기록합니다.** 끄는 명령의 출력을 그대로 복구 목록으로 남겨 뒀습니다.

## 소감

알림을 붙일 때는 "빠짐없이 받자" 는 생각만 했는데, 실제로 받아 보니 **받는 것보다 가려 받는 게 어렵다**는 걸 알았습니다.

특히 조용했던 이유가 "문제가 없어서" 가 아니라 **"보낼 수단이 없어서"** 였다는 게 뜨끔했습니다. 알림 경로를 붙인 첫날은 그동안 쌓여 있던 것이 한꺼번에 드러나는 날이라, 그날 하루는 소음 정리에 쓸 각오를 하는 게 맞겠습니다.

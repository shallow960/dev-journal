# 2026-09-15 권한을 뺐는데, 15분은 그대로 열려 있었다

> 태그: #개선 #인증 #권한 #토큰

## 무엇을 / 왜

"직원이 퇴사하면 관리 화면 접근이 바로 끊기는가" 를 확인해야 했습니다. 운영자 목록에서 사람을 빼면 그 가게의 소속 기록이 지워집니다. 거기까지는 맞습니다.

그런데 관리 화면이 두 종류였고, 둘의 확인 방식이 달랐습니다.

| 화면 | 확인 방식 | 결과 |
|---|---|---|
| 여러 가게를 넘나드는 화면 | 요청마다 소속을 조회 | 즉시 차단 |
| 가게 하나를 관리하는 화면 | **발급된 토큰만 확인** | 토큰이 만료될 때까지 통과 |

토큰 유효기간이 15분이라, 빠진 사람이 **최대 15분간 계속 들어올 수 있었습니다.**

## 어떻게 풀었나

### 더 나쁜 쪽은 따로 있었다

15분보다 신경 쓰인 건 **그 15분 동안 권한 제한이 오히려 풀린다**는 점이었습니다.

이 화면에는 등급이 있습니다. 제한된 등급(스태프)은 정산·결제 같은 민감한 영역에 못 들어갑니다. 그 등급을 **소속 기록에서 읽어 옵니다.** 그런데 소속 기록이 지워지면 읽을 등급이 없습니다.

등급을 못 찾으면 어떻게 할지가 문제인데, 코드는 **"제한 없음"** 으로 두고 있었습니다. 잠기는 사고를 막으려는 선택이었을 겁니다. 문제는 이 선택이 **"소속이 사라진 사람" 에게도 똑같이 적용**된다는 것입니다.

```
소속 있음 + 스태프 → 정산 화면 차단
소속 삭제됨        → 등급 없음 → 제한 없음 → 정산 화면 통과
```

**막아야 할 사람에게 오히려 다 열리는** 상태였습니다.

### 요청마다 확인하게 했다

가게 하나를 관리하는 화면도, 이미 그렇게 하고 있던 다른 화면과 같은 방식으로 맞췄습니다. 요청이 들어올 때마다 이 셋을 봅니다.

1. 이 토큰이 **가게용으로 발급된 토큰**인가
2. 토큰에 **계정 식별자**가 들어 있는가
3. 그 계정이 **이 가게의 활성 운영자**인가

하나라도 아니면 거절합니다. 소속이 없으면 "제한 없음" 이 아니라 **접근 불가**입니다.

### 고치기 전에 발급 경로를 먼저 확인했다

접근 조건을 강하게 만들면 **기존 사용자가 통째로 잠길 위험**이 있습니다. 그래서 이 화면에 들어오는 토큰이 어디서 발급되는지 전부 따라가 봤습니다.

확인해 보니 이 화면은 계정 로그인 후 "가게 선택" 을 거쳐야만 열리고, 그 과정에서 발급되는 토큰에는 조건 1·2가 이미 들어 있었습니다. 다른 경로로 들어오는 사용자는 없었습니다. 그걸 확인하고 나서 고쳤습니다.

## 코드로 보기 (개념 재현)

고치기 전입니다.

```java
public boolean 사전확인(요청 요청) {
    var 토큰 = 인증토큰(요청);
    var 가게id = 토큰.가게id();          // 토큰에 적힌 값을 그대로 믿는다
    if (가게id == null) 거절(403);
    가게컨텍스트.설정(가게id);
    return true;                         // 소속 확인 없음
}

// 등급 게이트(다른 곳)
var 등급 = 소속조회(사용자id, 가게id);
if (등급 == null) return true;           // ★ 소속이 없으면 제한하지 않는다
if (등급 == 스태프 && 민감영역(요청)) 거절(403);
```

고친 뒤입니다.

```java
public boolean 사전확인(요청 요청) {
    var 토큰 = 인증토큰(요청);

    var 가게id = 필수클레임(토큰, "가게id");
    if (!"가게".equals(토큰.클레임("발급평면"))) 거절(403, "가게용 토큰이 필요합니다");
    var 계정id = 필수클레임(토큰, "계정id");

    // 소속은 요청마다 조회한다. 토큰은 발급 시점의 사실일 뿐이다.
    if (!활성운영자인가(계정id, 가게id)) 거절(403, "이 가게의 운영자가 아닙니다");

    가게컨텍스트.설정(가게id);
    return true;
}

boolean 활성운영자인가(UUID 계정id, UUID 가게id) {
    return sql("""
        select exists(
            select 1 from 가게운영자
             where 계정id = :계정id and 가게id = :가게id and 상태 = '활성'
        )
        """).param("계정id", 계정id).param("가게id", 가게id).query(Boolean.class).single();
}
```

검증은 **토큰을 그대로 둔 채** 권한만 빼고 다시 요청하는 것입니다.

```java
@Test
void 운영자에서_빠지면_토큰이_남아_있어도_바로_거절된다() {
    var 사람 = 운영자로_등록(가게, "관리자");

    assertThat(요청(쿠폰화면, 사람)).isEqualTo(200);

    정지시킴(사람);                                  // 소속 상태만 바꾼다
    assertThat(요청(쿠폰화면, 사람)).isEqualTo(403);

    소속삭제(사람);
    assertThat(요청(쿠폰화면, 사람)).isEqualTo(403);
}

@Test
void 이_가게의_운영자가_아닌_계정은_거절된다() {
    var 계정 = 계정만들기();                          // 어느 가게에도 속하지 않은 계정
    assertThat(요청(쿠폰화면, 계정)).isEqualTo(403);  // 예전에는 "제한 없음" 으로 통과했다
}
```

## 💡 배운 것

**토큰에 적힌 건 발급 시점의 사실입니다.** 지금도 그런지는 답해 주지 않습니다. 권한이 바뀔 수 있는 값이라면 요청마다 확인해야 합니다.

**만료 시간을 짧게 잡는 건 완화지 해결이 아닙니다.** 15분을 5분으로 줄여도 5분은 열려 있습니다.

**권한 정보를 못 찾았을 때의 기본값이 제일 위험합니다.** "없으면 제한 없음" 은 정상 사용자를 위해 넣은 배려였는데, 권한을 뺏긴 사람에게도 그대로 적용됐습니다. 판단할 수 없으면 막는 쪽이 맞습니다.

**접근 조건을 강화할 때는 발급 경로를 먼저 전수 확인합니다.** 어떤 경로로 들어오는지 모른 채 조건을 올리면 멀쩡한 사용자가 잠깁니다.

**같은 성격의 화면이 서로 다른 방식으로 보호되고 있으면, 약한 쪽이 실제 보안 수준입니다.**

기능을 넣을 때 "잠기면 안 되니까 통과" 로 둔 곳들이 있는데, 그 선택이 **누구에게 적용되는지** 를 다시 봐야겠다고 생각했습니다. 배려로 넣은 예외가 제일 위험한 구멍이 될 수 있더군요.
